30D — Chat Application

Design a real-time chat app: WebSocket connection management, message delivery states, offline message queue, cursor-based pagination for history, push notifications, and media sharing.

ID: 30D ★ Senior Differentiator
🔍
1. Problem Statement

Requirements

Functional

  • Real-time messaging between users (1:1 and group)
  • Offline support: compose and queue messages when disconnected
  • Read receipts: sent → delivered → read indicators
  • Typing indicators
  • Message history pagination (load older messages)
  • Push notifications for new messages when app is in background
  • Media sharing (images, files)

Non-Functional

  • Sub-second message delivery when connected
  • Message ordering guaranteed (no out-of-order display)
  • No duplicate messages on reconnect
  • Battery-efficient connection management

3. Data Flow

Send Message Flow

User types message → taps Send
  → ChatViewModel.onSendMessage(text)
  → Create Message(id=UUID, status=SENDING)
  → Insert into Room immediately (optimistic)
    → UI shows message with "sending" indicator
  → WebSocket.send(message JSON)
  → Server ACK: { message_id, status: "SENT", timestamp }
  → Update Room: status=SENT, serverId=message_id
    → UI shows single checkmark (sent)
  → Recipient receives message
  → Server pushes: { type: "DELIVERED", message_id }
  → Update Room: status=DELIVERED
    → UI shows double checkmark (delivered)
  → Recipient opens chat
  → Server pushes: { type: "READ", message_id }
  → Update Room: status=READ
    → UI shows blue double checkmark (read)

Offline Message Queue

User sends message while offline
  → Create Message(status=SENDING, localOnly=true)
  → Save to Room
  → WebSocket send fails (not connected)
  → Message stays in Room with status=SENDING
  → NetworkConnectivityObserver detects online
  → WebSocketManager reconnects
  → MessageRepository.flushPendingMessages()
      → Query Room: messages WHERE localOnly=true ORDER BY timestamp
      → Send each via WebSocket in order
      → On ACK: update status=SENT, localOnly=false

Load Message History

User scrolls to top of chat
  → ChatViewModel.onLoadMore()
  → Fetch oldest message timestamp in Room
  → GET /messages?chatId={id}&before={timestamp}&limit=30
  → Insert into Room (don't clear existing)
  → Room Flow auto-updates — messages appear above
  → Cursor-based ensures no duplicates or gaps

Typing Indicator

// Typing: lightweight WebSocket events (NOT stored in Room)
User starts typing
  → debounce 1s → send { type: "TYPING", chatId }
  → WebSocket broadcasts to conversation participants
  → Received by other device: show "{name} is typing..."
  → Auto-clear after 3s of no new TYPING event from that user

// Implementation in ViewModel:
private val typingFlow = MutableSharedFlow<Unit>()
init {
    typingFlow.debounce(1000)
        .onEach { webSocket.sendTypingEvent(chatId) }
        .launchIn(viewModelScope)
}

4. Key Design Decisions

1. WebSocket Connection Management

class WebSocketManager @Inject constructor(
    private val okHttpClient: OkHttpClient
) {
    private var webSocket: WebSocket? = null
    private val reconnectDelay = listOf(1, 2, 4, 8, 16)  // exponential backoff in seconds

    val messageFlow: SharedFlow<ChatEvent> = callbackFlow {
        val request = Request.Builder().url("wss://api.example.com/ws").build()
        webSocket = okHttpClient.newWebSocket(request, object : WebSocketListener() {
            override fun onMessage(ws: WebSocket, text: String) {
                trySend(parseChatEvent(text))
            }
            override fun onFailure(ws: WebSocket, t: Throwable, r: Response?) {
                // Reconnect with backoff
            }
            override fun onClosed(ws: WebSocket, code: Int, reason: String) {
                close()
            }
        })
        awaitClose { webSocket?.close(1000, "Client closing") }
    }.shareIn(scope, SharingStarted.WhileSubscribed())

    // Heartbeat — keep connection alive, detect silent failures
    private fun startHeartbeat() {
        scope.launch {
            while (true) {
                delay(30_000)  // ping every 30 seconds
                webSocket?.send("""{"type":"ping"}""")
            }
        }
    }
}

7. Interview Framework

30-Second Answer

"The chat uses OkHttp WebSocket for real-time messaging. Messages are saved to Room immediately on send (SENDING state) for offline support. The WebSocket pipeline is: send → server ACK → SENT → recipient online → DELIVERED → recipient reads → READ. Reconnection uses exponential backoff. Offline messages queue in Room and flush when the WebSocket reconnects. History uses cursor-based pagination to avoid gaps when new messages arrive."

2-Minute Answer

"Architecture: ChatScreen → ChatViewModel → MessageRepository → Room + WebSocketManager. The WebSocket is managed as a callbackFlow — events are emitted and observed reactively. Messages go through four delivery states: SENDING (local only), SENT (server ACKed), DELIVERED (recipient device received), READ (recipient opened). All states stored in Room — the message list is a Flow<List<Message>> from Room, always up-to-date. For offline: messages with localOnly=true wait in Room; when WebSocket reconnects, flushPendingMessages() sends them in order. Duplicate prevention: every message has a client-generated UUID; Room uses INSERT OR IGNORE; server also deduplicates by UUID. Heartbeat pings every 30 seconds detect silent connection failures before users notice. When backgrounded, WebSocket disconnects and FCM data messages handle incoming notifications — onMessageReceived() saves the message to Room and shows a notification. History loads via GET /messages?before={timestamp} — cursor-based so new messages mid-scroll don't shift older pages."

Must-Mention Points

1
WebSocket lifecycle: connect on foreground, disconnect on background; heartbeat every 30s
2
Message delivery: SENDING → SENT → DELIVERED → READ — all stored in Room
3
Offline queue: localOnly messages flushed on reconnect in timestamp order
4
Duplicate prevention: client UUID + INSERT OR IGNORE in Room
5
Background: FCM data message → onMessageReceived → Room + notification

Senior Insight

Senior Differentiator
The WebSocket reconnection gap is a classic problem: what happens to messages sent to you while the connection was broken? Solution: on reconnect, send the server your last received message timestamp. Server replies with all events since that timestamp (missed messages, status updates). Client inserts them with INSERT OR IGNORE to deduplicate. This gap-fill pattern is what separates a production chat system from a demo.

9. Interview Questions
1. Why use WebSocket over HTTP polling for real-time chat?
Basic⌄
WebSocket: persistent bidirectional connection, sub-second delivery, server pushes without client request, minimal overhead (no HTTP headers per message). HTTP polling: client polls every N seconds — higher latency (up to N seconds), higher battery drain, higher server load (N clients × 1/poll_interval requests/second). SSE (Server-Sent Events): server-to-client only, not bidirectional — can't easily send messages. WebSocket is the standard for full-duplex real-time communication like chat.
2. What are the four message delivery states and when does each apply?
Basic⌄
SENDING: message saved locally, WebSocket send not yet acknowledged. Shows clock icon. SENT: server received and stored — confirmed by server ACK. Single checkmark. DELIVERED: recipient device received (recipient online, device received). Double checkmark. READ: recipient opened the conversation. Blue double checkmark. FAILED: send failed after retries — red error icon with "tap to retry".
3. How do you prevent duplicate messages when the WebSocket reconnects?
Basic⌄
Two layers: (1) Every message has a client-generated UUID. Room uses INSERT OR IGNORE (or REPLACE with conflict strategy). If the server replays a message the client already has, the insert is silently ignored. (2) Server-side deduplication: server tracks message UUIDs and ignores duplicate sends from the client (important for the offline flush queue). Also: on reconnect, send lastReceivedTimestamp to server → server sends only events after that timestamp, minimizing the replay set.
4. How does the offline message queue work?
Intermediate⌄
Messages sent while offline are saved to Room with localOnly=true and status=SENDING. They display in the chat immediately (optimistic). When NetworkConnectivityObserver emits connected=true AND WebSocket reconnects: call flushPendingMessages() — query Room for messages WHERE localOnly=true ORDER BY timestamp ASC. Send each via WebSocket in timestamp order (critical — messages must arrive in the order they were composed). On ACK per message: set localOnly=false, status=SENT.
5. How do you handle messages received while the app is in the background?
Intermediate⌄
When the app is backgrounded, the WebSocket connection is closed. The server sends an FCM data message (not notification message — you want to handle it yourself). FirebaseMessagingService.onMessageReceived() runs in the background: parse the message, insert into Room, build and show a notification. When the user opens the app from the notification: ChatScreen collects from Room's Flow — the message is already there. No additional API call needed. The chat opens showing the new message seamlessly.
6. How do you implement typing indicators efficiently?
Intermediate⌄
Typing is ephemeral — never stored in Room. On each keystroke: emit to a SharedFlow → debounce(1000ms) → send {type:"TYPING", chatId} via WebSocket. Debounce prevents N messages for N keystrokes. Receiver side: maintain a typingUsers: Map<userId, Long> where Long is the last TYPING event timestamp. Every second: remove users whose last TYPING was more than 3 seconds ago. UI shows "Alice is typing..." while her userId is in the map. Auto-clear handles the case where the WebSocket drops mid-typing.
7. How do you implement WebSocket reconnection with backoff?
Intermediate⌄
On WebSocketListener.onFailure() or onClosed(): use exponential backoff. delays = [1s, 2s, 4s, 8s, 16s, max 60s]. Increment attempt counter on each failure. If reconnect succeeds: reset counter. If NetworkConnectivityObserver emits offline: stop retrying — restart only when it emits online. Show "Reconnecting..." in the connection status banner. Cap at 60 seconds to prevent 10+ minute gaps. On successful reconnect: send gap-fill request (lastTimestamp) before resuming normal operation.
8. How do you handle the "gap" in messages during a WebSocket disconnect?
Senior⌄
On reconnect: client sends {type:"SYNC", lastTimestamp: T} where T = max(createdAt) of messages in Room. Server responds with all events from T to now (missed messages + status updates). Client processes each: INSERT OR IGNORE for messages (dedup), UPDATE for status changes. This gap-fill ensures no messages are lost during disconnects. Server should have a reasonable limit (e.g., events from last 24h max) to prevent massive replays. For longer gaps: trigger a full refresh of recent message history.
9. Design the media sharing flow for images.
Senior⌄
Flow: (1) User picks image. (2) Compress to ≤1MB (Compressor library or Bitmap.compress). (3) Show sending state with progress indicator on the message bubble. (4) POST /media/upload (multipart/form-data) → response {cdn_url, thumbnail_url}. (5) On upload complete: send WebSocket message {type:"IMAGE", cdnUrl, thumbnailUrl, localId}. (6) Insert to Room with cdnUrl. (7) UI loads thumbnail via Coil. Handle upload failures: retry button on the message; don't retry automatically to avoid multiple uploads. Never send binary images via WebSocket — use CDN.
10. How do you load older message history without disrupting the current view?
Scenario⌄
LazyColumn in reverse order (reverseLayout=true) — newest messages at bottom, user scrolls up for older. On reaching top (first item becomes visible): trigger onLoadMore(). Fetch GET /messages?chatId={id}&before={oldestTimestamp}&limit=30. Insert into Room. Room Flow emits new list — old messages appear above. Maintain scroll position: save the firstVisibleItemIndex and scroll offset before update, restore after. This is the standard pattern for chat — new messages auto-scroll to bottom via LazyListState.scrollToItem(0). Cursor-based ensures no page gaps or duplicates when new messages arrive during history loading.
