2C — Launch Modes & Back Stack

Tier 2 standard · singleTop · singleTask · singleInstance · Tasks · Back Stack · Intent Flags

1 · Overview

Android manages Activities in a task — a stack of Activities forming a logical user flow. A task has a back stack: pressing Back pops the top Activity and returns to the previous one. Launch modes control how and whether a new Activity instance is created when it is started.

Why it matters: Without understanding launch modes, apps produce duplicate Activities, broken back navigation, unexpected task switches, and deep-link bugs. Senior engineers are expected to know exactly what happens to the back stack in each mode and when to pick each one.

Core question launch modes answer: "When Activity A starts Activity B, should Android create a new instance of B, bring an existing one to the front, or pop everything above B?"

2 · How It Works

Task and Back Stack

Task (user flow) ┌────────────────────────────────────────────┐ │ [TOP] CheckoutActivity (currently shown) │ │ CartActivity │ │ ProductActivity │ │ HomeActivity (bottom) │ └────────────────────────────────────────────┘ BACK press: CheckoutActivity popped → CartActivity shown Each app launch creates a new Task (unless reusing existing)

The Four Launch Modes

standard (default)

A new instance is created every time the Activity is started, pushed onto the top of the current task.

Stack before: [Home][Product] Start ProductActivity again: Stack after: [Home][Product][Product] ← second instance pushed

singleTop

If an instance of this Activity is already at the top of the current task, no new instance is created. onNewIntent() is called on the existing instance. If it is NOT at the top, a new instance is created normally.

Stack before: [Home][Product] (Product is at top) Start ProductActivity: Stack after: [Home][Product] ← same instance, onNewIntent() called Stack before: [Home][Product][Cart] (Product NOT at top) Start ProductActivity: Stack after: [Home][Product][Cart][Product] ← new instance

singleTask

Only one instance of this Activity exists in the system at a time (within a task). If an instance exists anywhere in the task, all Activities above it are popped (destroyed) and onNewIntent() is called on the existing instance. If no instance exists, a new one is created.

Stack before: [Home][Dashboard][Profile] Start Dashboard (singleTask): Stack after: [Home][Dashboard] ← Profile popped, onNewIntent() called on Dashboard

singleInstance

Like singleTask, but the Activity is the only one in its task — it has its own private task. Any Activity started from it goes into a different task.

Task 1: [Home][App screens...] Task 2: [CallActivity] ← singleInstance; exclusive task User presses Back from CallActivity → returns to Task 1

Intent Flags — Programmatic Control

Launch modes can also be set via Intent flags at runtime, overriding the manifest declaration (flags take priority).

FlagEffectEquivalent Mode
FLAG_ACTIVITY_SINGLE_TOPsingleTop behaviour for this launchsingleTop
FLAG_ACTIVITY_CLEAR_TOPIf instance exists in task, pop all above it; onNewIntent called. No manifest equivalent.≈ singleTask (within task)
FLAG_ACTIVITY_NEW_TASKStart Activity in a new task (or bring existing task to foreground)Required when starting from non-Activity context
FLAG_ACTIVITY_CLEAR_TASKClears entire task before starting; always used with NEW_TASKUsed for logout → login flow
FLAG_ACTIVITY_NO_HISTORYActivity not kept in back stack; removed when user leavesSplash screen, auth redirect
FLAG_ACTIVITY_REORDER_TO_FRONTBring existing instance to front without destroying others—

onNewIntent()

Called when an existing Activity instance receives a new Intent (singleTop if at top, or singleTask). The old intent is still accessible via getIntent() until you call setIntent(intent).

override fun onNewIntent(intent: Intent) {
    super.onNewIntent(intent)
    setIntent(intent)               // Update getIntent() to return new intent
    val orderId = intent.getStringExtra("orderId")
    viewModel.loadOrder(orderId)   // Handle new navigation target
}

3 · Why and When to Use Each

ModeUse when…Real example
standard Default for most screens. Multiple independent instances make sense. Product detail screen (user can open multiple products in back stack)
singleTop Re-triggering the same screen with new data (notification tap, push notification deep link) Notification taps to NewsDetailActivity — don't stack duplicates if already open
singleTask App's root/home screen that should not be duplicated; deep-link destination that must clear back stack above it HomeActivity (main tab), Login screen after logout, deep link to dashboard
singleInstance Standalone utility with its own isolated task; must not share task with any other Activity System alarm screen, incoming call screen, floating assistant

When NOT to Use

  • singleTask for most screens: Popping the back stack above it is destructive. Users lose navigation history unexpectedly.
  • singleInstance for regular screens: Having Activities in separate tasks breaks the expected back navigation and ViewModel sharing.
  • Launch modes at all (modern apps): Single-activity with Navigation Component / Compose NavHost — you manage the back stack in NavGraph, not via launch modes. Launch modes matter only for the single root Activity and for cross-app scenarios.

4 · Production Example (Banking App — Logout + Deep Link)

Scenario 1: Logout — Clear Entire Task

// After successful logout, navigate to LoginActivity and clear everything
fun navigateToLoginAfterLogout() {
    val intent = Intent(this, LoginActivity::class.java).apply {
        // FLAG_ACTIVITY_NEW_TASK: start in the task stack root
        // FLAG_ACTIVITY_CLEAR_TASK: destroy all existing Activities in task
        flags = Intent.FLAG_ACTIVITY_NEW_TASK or Intent.FLAG_ACTIVITY_CLEAR_TASK
    }
    startActivity(intent)
    // User cannot press Back to return to account screens
}

Scenario 2: Notification Deep Link with singleTop

// In AndroidManifest.xml — singleTop prevents stacking notification taps
<activity
    android:name=".ui.transaction.TransactionDetailActivity"
    android:launchMode="singleTop"
    android:exported="false" />

// Activity handles new intent from FCM notification
override fun onNewIntent(intent: Intent) {
    super.onNewIntent(intent)
    setIntent(intent)
    val txId = intent.getStringExtra("transactionId") ?: return
    viewModel.loadTransaction(txId)
    // If Activity already open at top, just refreshes with new transaction
}

Scenario 3: Home Activity as singleTask Root

<activity
    android:name=".ui.HomeActivity"
    android:launchMode="singleTask"
    android:exported="true">
    <intent-filter>
        <action android:name="android.intent.action.MAIN" />
        <category android:name="android.intent.category.LAUNCHER" />
    </intent-filter>
</activity>

// Deep link from push notification: go home, clear sub-screens
fun goHome() {
    val intent = Intent(this, HomeActivity::class.java).apply {
        // With singleTask declared, FLAG_ACTIVITY_CLEAR_TOP pops Activities above
        flags = Intent.FLAG_ACTIVITY_CLEAR_TOP
    }
    startActivity(intent)
}

Modern Approach: Navigation Component (Single Activity)

// In a single-activity + Navigation Compose app, launch modes are mostly irrelevant.
// Navigation Component handles back stack with popUpTo and launchSingleTop.
navController.navigate(Route.Home) {
    popUpTo(Route.Home) {
        inclusive = true              // remove Home itself from back stack before re-adding
    }
    launchSingleTop = true          // don't stack if already at top
}

// Logout in Navigation Compose — equivalent of FLAG_ACTIVITY_CLEAR_TASK
navController.navigate(Route.Login) {
    popUpTo(navController.graph.startDestinationId) { inclusive = true }
}

6 · Pitfalls and Best Practices

Forgetting setIntent() in onNewIntent()

❌ Bad — stale intent after restart

override fun onNewIntent(intent: Intent) {
    super.onNewIntent(intent)
    // Does NOT call setIntent(intent)
    // If Activity is recreated, getIntent() returns OLD intent
    val id = getIntent().getStringExtra("id")
}

✅ Good

override fun onNewIntent(intent: Intent) {
    super.onNewIntent(intent)
    setIntent(intent)    // Update so getIntent() returns new one
    val id = intent.getStringExtra("id")
}

singleTask Unexpectedly Destroys Back Stack

Gotcha: Declaring your HomeActivity as singleTask means that whenever it is launched (e.g. from a notification), ALL Activities above it in the task are destroyed. Users lose navigation state. Only use singleTask when popping the back stack is intentional.

Other Critical Pitfalls

  • Using singleInstance for regular screens: Activities in separate tasks cannot share ViewModels and have broken Back navigation. Only use for truly isolated system-level screens.
  • Not handling FLAG_ACTIVITY_NEW_TASK correctly: When starting an Activity from a Service, Application, or BroadcastReceiver (non-Activity context), FLAG_ACTIVITY_NEW_TASK is required. Omitting it causes RuntimeException.
  • Deep links with wrong launch mode: A deep link to a singleTask Activity destroys the back stack the user had. Prefer Navigation Component's deep link handling with addToBackStack.
  • Duplicate Activities from double-tap: Users tapping a button twice quickly can start two Activities. Use singleTop or disable the button after first tap + re-enable in onResume.
  • Ignoring task affinity: android:taskAffinity combined with singleTask can route Activities to unexpected tasks. Default affinity is the package name.
Modern best practice: In single-activity apps with Navigation Component, you rarely need launch modes. Use launchSingleTop = true and popUpTo in NavOptions for the equivalent behaviour. Reserve manifest launch modes for the MainActivity and cross-app deep-link scenarios.

7 · Interview Answer Framework

30-Second Answer

"Launch modes control how Android creates Activity instances and manages the back stack. There are four: standard creates a new instance every time; singleTop reuses if already at the top of the stack; singleTask ensures one instance per task and pops everything above it on re-launch; singleInstance is like singleTask but the Activity has its own isolated task. In modern single-activity apps with Navigation Component, I rarely use launch modes — launchSingleTop and popUpTo in NavOptions give the same control in a cleaner way."

2-Minute Structured Answer

The four modes: standard (new instance always), singleTop (reuse if at stack top → onNewIntent called), singleTask (one instance, pop above on re-launch → onNewIntent called), singleInstance (own private task).

Intent flags override manifest: FLAG_ACTIVITY_CLEAR_TOP pops everything above an existing instance. FLAG_ACTIVITY_NEW_TASK + FLAG_ACTIVITY_CLEAR_TASK is the classic logout pattern — clears the task and starts fresh with LoginActivity so the user cannot press Back into the account screens.

onNewIntent: Called on singleTop (at top) and singleTask re-launches. Must call setIntent(intent) to update what getIntent() returns — otherwise after rotation the stale original intent is restored.

Modern practice: Single-activity apps use Navigation Component. NavController.navigate with launchSingleTop = true and popUpTo replace singleTop and singleTask respectively. This keeps all navigation logic in one NavGraph rather than scattered across manifests and flag combinations.

Must-Mention Points

  1. Four modes and what each does to the back stack.
  2. singleTask pops ALL activities above it — the most dangerous / commonly misused mode.
  3. onNewIntent() — when it's called and why setIntent() is necessary.
  4. Intent flags: CLEAR_TOP, CLEAR_TASK + NEW_TASK for logout.
  5. FLAG_ACTIVITY_NEW_TASK required when starting from non-Activity context.
  6. Navigation Component replaces launch modes for in-app navigation.
  7. taskAffinity and its interaction with singleTask.

Likely Follow-up Questions

QuestionShort Answer
What's the difference between singleTask and singleInstance?Both allow one instance. singleTask lives in a task that can contain other Activities too. singleInstance lives in its own exclusive task — no other Activity can be in that task.
When is onNewIntent() called?When an Activity with singleTop launch mode (and it's at the top of the stack) or singleTask (existing instance anywhere in task) receives a new Intent. The existing instance is reused instead of creating a new one.
How do you implement logout so the user can't press Back to the dashboard?startActivity with FLAG_ACTIVITY_NEW_TASK + FLAG_ACTIVITY_CLEAR_TASK to clear the entire task. Or in Navigation Compose: navController.navigate(login) { popUpTo(graph.startDestination) { inclusive = true } }

Senior-Level Insight

"The real problem with launch modes is that they're a global, declarative contract set in the manifest, but navigation decisions are often context-dependent. A screen may sometimes need to clear the back stack (on logout deep link) and sometimes not (regular navigation). Intent flags give per-launch control, but scatter navigation logic. Navigation Component solves this by centralising all back-stack decisions in one NavGraph with per-navigate NavOptions — and in Compose, there's no Activity back stack at all, only a Composable call back stack managed by NavHost. For any new project I treat manifest launch modes as a last resort, used only for the root MainActivity (often singleTask for deep-link correctness) and cross-app Activities."

9 · Interview Questions (Self-Check)

Basic What are the four Activity launch modes?
standard, singleTop, singleTask, singleInstance.
• standard: new instance every launch
• singleTop: reuse if at stack top (onNewIntent called), else new instance
• singleTask: one instance per task; pops all above it on re-launch (onNewIntent called)
• singleInstance: one instance, own exclusive task
Basic What is onNewIntent() and when is it called?
onNewIntent() is called when a new Intent arrives for an existing Activity instance (instead of creating a new one). Called for singleTop if the Activity is at the top of the stack, and for singleTask/singleInstance when the instance already exists. Always call setIntent(intent) inside onNewIntent() to keep getIntent() up-to-date after potential future recreations.
Basic What Intent flags would you use to implement a logout flow where the user cannot go Back to the account screens?
FLAG_ACTIVITY_NEW_TASK combined with FLAG_ACTIVITY_CLEAR_TASK:
intent.flags = Intent.FLAG_ACTIVITY_NEW_TASK or Intent.FLAG_ACTIVITY_CLEAR_TASK
This clears all Activities in the task before starting LoginActivity, so Back press exits the app rather than returning to any account screen.
Intermediate What is the difference between singleTask and FLAG_ACTIVITY_CLEAR_TOP?
singleTask is a manifest property — it applies every time the Activity is started and ensures one instance in the system. FLAG_ACTIVITY_CLEAR_TOP is a per-launch flag that pops everything above an existing instance in the current task. CLEAR_TOP does not enforce one global instance; it only affects the current task and the current launch. singleTask implies CLEAR_TOP behaviour plus the one-instance guarantee. For in-task navigation, CLEAR_TOP is often preferred as it's less aggressive.
Intermediate When is FLAG_ACTIVITY_NEW_TASK required?
When starting an Activity from a context that is not an Activity — a Service, BroadcastReceiver, Application class, or any non-Activity Context. Omitting it in these scenarios throws: "Calling startActivity() from outside of an Activity context requires the FLAG_ACTIVITY_NEW_TASK flag."
Intermediate How does singleTop differ from singleTask when the target Activity is NOT at the top of the stack?
singleTop: if the Activity is NOT at the stack top, a new instance is created and pushed normally — no special back-stack manipulation. singleTask: if an instance exists ANYWHERE in the task (even buried), all Activities above it are popped and onNewIntent() is called on the existing instance. If no instance exists, a new one is created. singleTop is the "gentle" version; singleTask is "destructive."
Intermediate In Navigation Compose, how do you achieve singleTop behaviour when navigating? 
navController.navigate(Route.Home) {
    launchSingleTop = true  // Don't create duplicate if already at top
}
For singleTask-like clearing (e.g. going to Home from deep stack):
navController.navigate(Route.Home) {
    popUpTo(Route.Home) { inclusive = false }  // pop above Home, keep Home
    launchSingleTop = true
}
Senior/Scenario [Scenario] A user taps a push notification for Order #123 while they already have the OrderDetailActivity open showing Order #456. What launch mode/flag strategy ensures Order #123 loads without stacking a duplicate Activity?
Declare OrderDetailActivity as singleTop in the manifest. When the notification PendingIntent fires with the new orderId, Android calls onNewIntent() on the existing instance instead of creating a new one (if it's at the top of the stack). In onNewIntent(), call setIntent(intent) and then viewModel.loadOrder(newOrderId). If OrderDetailActivity is NOT at the top (other screens stacked above), you might also add FLAG_ACTIVITY_CLEAR_TOP to pop those and reach the existing instance. In Navigation Compose with a single Activity, handle this in the notification tap by navigating with launchSingleTop = true and popUpTo to ensure clean state.
Senior/Scenario [Debug] After the user taps a notification, they see the correct screen, but pressing Back takes them to the wrong screen (an unrelated Activity from a different flow). What's the problem?
The PendingIntent is launching the Activity with FLAG_ACTIVITY_NEW_TASK into a task that already has a different activity history. When the user presses Back, they're navigating through that existing task's back stack, not the expected flow. Fix: Use TaskStackBuilder to construct a synthetic back stack that matches the expected navigation hierarchy. Example:
val stackBuilder = TaskStackBuilder.create(context).apply {
    addNextIntentWithParentStack(orderDetailIntent)  // auto-adds HomeActivity → OrderListActivity → OrderDetailActivity
}
val pendingIntent = stackBuilder.getPendingIntent(0, PendingIntent.FLAG_UPDATE_CURRENT or PendingIntent.FLAG_IMMUTABLE)
This ensures a proper back stack even when the app was killed.
Senior/Scenario [Coding] Write the logout navigation code for both a multi-Activity app and a single-Activity Compose app.
Multi-Activity:
fun logout() {
    authRepository.clearSession()
    val intent = Intent(this, LoginActivity::class.java).apply {
        flags = Intent.FLAG_ACTIVITY_NEW_TASK or Intent.FLAG_ACTIVITY_CLEAR_TASK
    }
    startActivity(intent)
    // No finish() needed — CLEAR_TASK destroys all Activities
}
Single Activity + Compose NavHost:
// In ViewModel
fun logout() {
    viewModelScope.launch {
        authRepository.clearSession()
        _navigationEvent.emit(NavigationEvent.LoggedOut)
    }
}

// In Composable / NavHost
LaunchedEffect(Unit) {
    viewModel.navigationEvent.collect { event ->
        if (event is NavigationEvent.LoggedOut) {
            navController.navigate(Route.Login) {
                popUpTo(0) { inclusive = true }  // pop entire graph
            }
        }
    }
}
