6D — Sharing: stateIn & shareIn

stateIn() converts cold Flow to StateFlow. shareIn() to SharedFlow. SharingStarted strategies: Eagerly, Lazily, WhileSubscribed(5000). When to use each.

ID: 6D ⭐ Tier 1
🔍
1. Overview

The problem they solve

Repository functions typically return cold Flow<T>. If two collectors subscribe, the upstream (network/DB) runs twice. If a collector comes and goes, the network call restarts. stateIn and shareIn convert cold flows to hot flows, sharing one upstream execution among all collectors.

stateIn vs shareIn

  • stateIn() — converts to StateFlow; requires initial value; always has a current value; deduplicates; use for ViewModel UI state
  • shareIn() — converts to SharedFlow; configurable replay; no required initial value; use for shared event streams

SharingStarted strategies

  • Eagerly — starts immediately when scope starts; never stops
  • Lazily — starts when first subscriber appears; never stops after that
  • WhileSubscribed(stopTimeoutMillis) — starts on first subscriber; stops after the last subscriber leaves (with optional delay)
Senior Mental Model
WhileSubscribed(5000) is the production-grade default. The 5-second timeout means a configuration change (Activity rotation) won't cancel the upstream — the ViewModel survives rotation, and the new Activity subscribes within milliseconds. But navigating away and the upstream cancels after 5 seconds, saving battery and network resources.

2. stateIn()

Signature

fun <T> Flow<T>.stateIn(
    scope: CoroutineScope,       // where the shared coroutine lives
    started: SharingStarted,    // when to start/stop upstream
    initialValue: T              // value before first emission
): StateFlow<T>

Standard ViewModel pattern

class AccountViewModel(repo: AccountRepository) : ViewModel() {

    // Cold Flow from Room (re-queries on every collect without stateIn)
    val accountState: StateFlow<AccountUiState> =
        repo.getAccountFlow()    // cold Flow<Account> from Room
            .map { AccountUiState.Success(it) }
            .catch { emit(AccountUiState.Error(it)) }
            .stateIn(
                scope = viewModelScope,
                started = SharingStarted.WhileSubscribed(5_000),
                initialValue = AccountUiState.Loading
            )
    // Now: single shared Room subscription
    // Stops 5s after last subscriber (background navigation)
    // Multiple Compose collectors share one upstream query
}

stateIn with operators

// Complex transformation → stateIn at the end
val filteredProducts: StateFlow<List<Product>> =
    combine(repo.allProducts(), searchQuery, activeFilters) { products, q, f ->
        products.filter { it.matches(q, f) }
    }
    .stateIn(viewModelScope, SharingStarted.WhileSubscribed(5_000), emptyList())

3. shareIn()

Signature

fun <T> Flow<T>.shareIn(
    scope: CoroutineScope,
    started: SharingStarted,
    replay: Int = 0       // how many values to replay to new subscribers
): SharedFlow<T>

Shared event stream

// Share one WebSocket connection among multiple ViewModels
class PriceRepository(private val socket: PriceSocket) {

    // SharedFlow: one socket, multiple subscribers
    val priceUpdates: SharedFlow<PriceUpdate> =
        socket.priceFlow()  // cold callbackFlow
            .shareIn(
                scope = repositoryScope,
                started = SharingStarted.WhileSubscribed(5_000),
                replay = 1    // new subscribers get latest price immediately
            )
}

// ProductViewModel and CartViewModel can both subscribe
// without opening separate WebSocket connections

5. Production Example

Banking: shared account data across multiple ViewModels

// Repository exposes cold Flow from Room
class AccountRepository(
    private val dao: AccountDao,
    private val api: AccountApi,
    private val scope: CoroutineScope  // inject app-level scope
) {
    // Shared: one DB subscription, multiple ViewModels
    val accountFlow: StateFlow<Account?> =
        dao.observeAccount()  // Room Flow — cold
            .stateIn(scope, SharingStarted.WhileSubscribed(5_000), null)
}

// ViewModel transforms the shared flow for its screen
class DashboardViewModel(repo: AccountRepository) : ViewModel() {

    val dashState: StateFlow<DashboardState> =
        repo.accountFlow
            .filterNotNull()
            .map { account ->
                DashboardState(
                    balance = account.formatBalance(),
                    accountName = account.name
                )
            }
            .stateIn(
                viewModelScope,
                SharingStarted.WhileSubscribed(5_000),
                DashboardState.Loading
            )
}

// TransferViewModel also uses the same repo.accountFlow
// → No duplicate DB queries, both observe same Room cursor
class TransferViewModel(repo: AccountRepository) : ViewModel() {
    val senderAccount = repo.accountFlow
        .filterNotNull()
        .stateIn(viewModelScope, SharingStarted.WhileSubscribed(5_000), null)
}

6. Pitfalls & Best Practices
Pitfall 1 — Using Eagerly in ViewModel
SharingStarted.Eagerly in a ViewModel starts the upstream immediately and keeps it running forever in viewModelScope. If the ViewModel is created but the screen is never shown, the network/DB query still runs. Use WhileSubscribed(5000) instead — starts when the UI collects and stops when it leaves.
Pitfall 2 — stateIn without initial value in cold start
The initialValue in stateIn is what collectors get before the first upstream emission. If you pass a blank/empty value and the UI renders it, the user sees an empty flash before real data loads. Design your state to include a Loading sentinel: stateIn(scope, WhileSubscribed(5000), UiState.Loading).
Best Practice — stateIn in ViewModel, shareIn in Repository
Use stateIn in ViewModels (to expose UI state as StateFlow). Use shareIn in Repositories (to share one upstream data source — WebSocket, GPS — among multiple subscribers without creating duplicate connections).
Best Practice — WhileSubscribed timeout for config changes
The 5000ms timeout in WhileSubscribed(5000) is the standard for ViewModels. It bridges Android configuration changes (rotation, language change) which typically complete in under 1 second. For app-global state (auth, user session), use Eagerly on the application scope.

7. Interview Framework

30-second answer

"stateIn() converts a cold Flow to a StateFlow by starting a shared coroutine that collects the upstream and broadcasts to all subscribers. shareIn() converts to SharedFlow with configurable replay. The SharingStarted strategy WhileSubscribed(5000) is the standard — it starts on first subscriber and stops 5 seconds after the last subscriber leaves, bridging device rotations while saving resources when the screen is gone."

2-minute answer

"The problem stateIn and shareIn solve is the cold Flow duplication issue. Without them, if a ViewModel exposes a Flow from a Room DAO and three Compose components collect it, you get three separate database subscriptions. stateIn creates one shared collection coroutine that all subscribers observe — one DB connection regardless of subscriber count.

WhileSubscribed(5000) is carefully designed for Android's lifecycle. Device rotation destroys and recreates the Activity in under a second, so 5 seconds safely bridges the gap without stopping the upstream. But if the user navigates back, the 5-second timeout fires and the upstream stops, freeing the DB connection and stopping network polling.

Eagerly is for app-global state (authentication, user session) — you want it ready before any screen opens. In ViewModels, always use WhileSubscribed — never Eagerly (which would run the upstream even if the UI never subscribes)."

Follow-up Q&A

Q: "What is the difference between stateIn and creating a MutableStateFlow manually?"

A: With a manual MutableStateFlow, you write the boilerplate: init { viewModelScope.launch { repo.flow().collect { _state.value = it } } } — a coroutine that forever collects and pushes values. stateIn does exactly this but as a one-liner, also handling the SharingStarted lifecycle policy. It's more readable and less error-prone.

Q: "When would you use shareIn with replay=1?"

A: When new subscribers should immediately get the latest value but you don't want the StateFlow semantics (initial value requirement, deduplication). Example: a shared WebSocket price feed where new subscribers should see the current price immediately, but you don't have a meaningful initial price before the first server message.

Senior insight

Senior Insight
In a banking app, put shareIn(appScope, WhileSubscribed(5000)) on the account balance Room flow in the Repository. DashboardViewModel, TransactionViewModel, and any widget that shows balance all subscribe to the same shared flow — one Room cursor open, one DB connection, consistent data. Without sharing, each ViewModel would open its own Room subscription, causing unnecessary DB load and potentially showing briefly inconsistent balances.

9. Interview Questions
What does stateIn() do?
Basic⌄
stateIn() converts a cold Flow into a hot StateFlow. It starts a shared coroutine in the given scope that collects the upstream Flow and broadcasts the latest value to all subscribers. The initialValue is returned to new subscribers before the first upstream emission. Multiple collectors share one upstream execution.
What is WhileSubscribed(5000) and why is 5000ms the standard value?
Basic⌄
WhileSubscribed(5000) starts the upstream when the first subscriber joins and stops it 5 seconds after the last subscriber leaves. The 5-second value is chosen to survive Android configuration changes (screen rotation destroys and recreates Activity in ~100–500ms). The upstream doesn't stop during rotation. When the user navigates away permanently, it stops after 5 seconds, freeing resources.
What is the difference between stateIn and shareIn?
Basic⌄
stateIn produces a StateFlow: requires an initial value, always has a current value, uses equals() deduplication, suitable for UI state. shareIn produces a SharedFlow: no initial value required, configurable replay (0 for events, 1+ for state), no deduplication. Use stateIn in ViewModels for UI state; use shareIn in Repositories for shared connections (WebSocket, GPS).
Why is SharingStarted.Eagerly dangerous in a ViewModel?
Intermediate⌄
Eagerly starts the upstream immediately when the scope starts (ViewModel init) and never stops until the scope is cancelled. This means network/DB calls start even if no collector ever subscribes — wasteful. It also means the upstream runs even when the app is in the background. Use WhileSubscribed to only run while the UI is active.
A ViewModel has a cold Room Flow. Three Compose composables all collect it. How many DB queries happen and how do you fix it?
Intermediate⌄
Three DB queries — each collector starts an independent Room subscription (cold Flow). Fix: convert to a hot flow with stateIn(viewModelScope, WhileSubscribed(5000), initialValue) in the ViewModel. Now there's one shared Room subscription, and all three Compose composables observe the same StateFlow. Result: one DB query regardless of subscriber count.
How is stateIn different from manually collecting a Flow into a MutableStateFlow?
Intermediate⌄
Functionally equivalent, but stateIn is a one-liner that handles: (1) the coroutine launching; (2) the SharingStarted lifecycle policy (WhileSubscribed stops the upstream when no subscribers — impossible to express concisely with manual approach); (3) cancellation and restart logic. Manual approach requires boilerplate in init {} and careful handling of stopping/restarting.
When would you use shareIn in a Repository instead of stateIn?
Intermediate⌄
Use shareIn in a Repository when you want to share an expensive upstream (WebSocket connection, Bluetooth GATT, GPS listener) among multiple ViewModels. shareIn with replay=1 means any new subscriber immediately gets the latest value without opening a new connection. Use stateIn in ViewModel for the UI-facing StateFlow (requires initial value, deduplication).
What happens to a stateIn(WhileSubscribed(5000)) flow when the user rotates the device?
Senior⌄
The Activity is destroyed (Compose unsubscribes) and recreated (Compose resubscribes), typically within 200–500ms. The 5000ms timeout means the upstream does NOT stop — it keeps running throughout. When the new Activity subscribes, it immediately gets the latest StateFlow value and the ongoing upstream. No data is lost, no network call is restarted. Without the 5000ms timeout (WhileSubscribed(0)), the upstream would stop on destroy and restart on the new Activity, causing a brief loading flash.
Design a Repository that shares a WebSocket price feed among multiple ViewModels with appropriate lifecycle management.
Senior⌄
class PriceRepository(socket: PriceSocket, scope: CoroutineScope) { val prices: SharedFlow<Map<String,Price>> = socket.priceFlow().scan(emptyMap()) { acc, update -> acc + (update.symbol to update) }.shareIn(scope, SharingStarted.WhileSubscribed(5_000), replay=1) }. The scan accumulates the latest price per symbol. shareIn(WhileSubscribed(5000)) means the WebSocket connects when the first ViewModel subscribes and disconnects 5s after all ViewModels unsubscribe (navigation away). replay=1 ensures new ViewModels instantly get the latest price map without waiting for the next WebSocket message.
What is the difference between SharingStarted.Lazily and WhileSubscribed(Long.MAX_VALUE)?
Senior⌄
Functionally nearly identical in practice — both start on first subscriber and stop only when the scope is cancelled. The subtle difference: Lazily is a first-class API with clear semantics. WhileSubscribed(Long.MAX_VALUE) technically stops after MAX_VALUE milliseconds (after ~292 million years, so effectively never). In practice, use Lazily when you want "start on first subscriber, keep forever" semantics. Use Eagerly when you want to pre-warm before any subscriber. Use WhileSubscribed(5000) for the standard ViewModel use case.
