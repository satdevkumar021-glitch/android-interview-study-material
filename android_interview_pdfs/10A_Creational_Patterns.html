10A — Creational Patterns

Singleton, Factory Method, Abstract Factory, and Builder — the four creational patterns that govern object construction in production Android apps.

ID: 10A ⭐ Tier 1
🔍
1. Overview

What are Creational Patterns?

Creational design patterns deal with object creation mechanisms. They abstract the instantiation process, making code more flexible and independent of how objects are created, composed, and represented. In Android, you encounter creational patterns constantly — often without realising it.

PatternProblem it solvesAndroid example
SingletonExactly one instance shared app-wideRoom database, Retrofit client, SharedPreferences
Factory MethodCreate objects without specifying exact classFragment.newInstance(), payment method creation
Abstract FactoryCreate families of related objectsThemed UI component factories (light/dark)
BuilderConstruct complex objects step by stepOkHttpClient, Retrofit, NotificationCompat, AlertDialog
Senior Mental Model
Creational patterns answer: "Who is responsible for creating this object, and how do we control the creation so callers don't need to know the details?" When combined with DI (Hilt), creational patterns shift object lifetime management to the framework — but knowing the underlying patterns is critical for reasoning about Hilt scopes.

2. How It Works

1. Singleton Pattern

Ensures a class has exactly one instance, with a global access point. In Kotlin, the object keyword creates a thread-safe, lazily-initialised singleton by default.

// Kotlin object — thread-safe singleton, initialised on first access
object AnalyticsTracker {
    private val events = mutableListOf<AnalyticsEvent>()
    fun track(event: AnalyticsEvent) { events.add(event) }
}

// companion object — factory + singleton access on a class
class AppDatabase : RoomDatabase() {
    companion object {
        @Volatile
        private var INSTANCE: AppDatabase? = null

        fun getInstance(context: Context): AppDatabase =
            INSTANCE ?: synchronized(this) {
                INSTANCE ?: Room.databaseBuilder(
                    context.applicationContext,
                    AppDatabase::class.java,
                    "bank_db"
                ).build().also { INSTANCE = it }
            }
    }
}

// Thread-safe lazy — initialised once, on first access, by the calling thread
val httpClient: OkHttpClient by lazy {
    OkHttpClient.Builder()
        .connectTimeout(30, TimeUnit.SECONDS)
        .build()
}
Singleton Problems
Global mutable state is the enemy of testability. object AnalyticsTracker cannot be replaced with a fake in unit tests — you'd need Hilt or a service locator to swap it. Prefer injecting singleton instances via DI rather than accessing object directly.

2. Factory Method Pattern

Defines an interface for creating an object, but lets subclasses or callers decide which class to instantiate. In Android, Fragment.newInstance() is the canonical example.

// Factory method for Fragment creation — avoids direct constructor call
class ProductDetailFragment : Fragment() {
    companion object {
        private const val ARG_PRODUCT_ID = "product_id"

        fun newInstance(productId: String): ProductDetailFragment =
            ProductDetailFragment().apply {
                arguments = bundleOf(ARG_PRODUCT_ID to productId)
            }
    }
}

// Factory method for payment method objects
interface PaymentGateway { suspend fun process(amount: BigDecimal): PaymentResult }

object PaymentGatewayFactory {
    fun create(method: PaymentMethod): PaymentGateway = when (method) {
        is PaymentMethod.CreditCard -> StripeGateway(method.token)
        is PaymentMethod.PayPal      -> PayPalGateway(method.email)
        is PaymentMethod.Crypto      -> CoinbaseGateway(method.address)
    }
}

3. Abstract Factory Pattern

Creates families of related objects without specifying their concrete classes. Useful when the app must produce different UI components based on configuration (theme, tenant, platform).

// Abstract factory for themed UI components (e.g., white-label banking app)
interface UiComponentFactory {
    fun createPrimaryButton(context: Context): Button
    fun createInputField(context: Context): TextInputLayout
    fun createLoadingIndicator(context: Context): View
}

class LightThemeFactory : UiComponentFactory {
    override fun createPrimaryButton(context: Context) =
        Button(context).apply { setBackgroundColor(context.getColor(R.color.primary_light)) }
    // ...
}

class DarkThemeFactory : UiComponentFactory {
    override fun createPrimaryButton(context: Context) =
        Button(context).apply { setBackgroundColor(context.getColor(R.color.primary_dark)) }
    // ...
}

// Usage: factory is injected — callers never know which theme is active
class CheckoutScreen(private val factory: UiComponentFactory) {
    fun buildUi(context: Context) {
        val button = factory.createPrimaryButton(context)
    }
}

4. Builder Pattern

Constructs a complex object step by step. The builder separates the construction from the representation. In Android, OkHttp, Retrofit, NotificationCompat.Builder, and AlertDialog.Builder all use this pattern.

// Builder pattern — Retrofit + OkHttp composition
val okHttpClient = OkHttpClient.Builder()
    .connectTimeout(30, TimeUnit.SECONDS)
    .readTimeout(30, TimeUnit.SECONDS)
    .addInterceptor(AuthInterceptor(tokenStore))
    .addInterceptor(HttpLoggingInterceptor().apply { level = HttpLoggingInterceptor.Level.BODY })
    .build()

val retrofit = Retrofit.Builder()
    .baseUrl("https://api.bank.com/")
    .client(okHttpClient)
    .addConverterFactory(MoshiConverterFactory.create())
    .build()

// Custom builder — type-safe, avoids large constructor parameter lists
data class TransferRequest private constructor(
    val fromAccount: String,
    val toAccount: String,
    val amount: BigDecimal,
    val currency: String,
    val reference: String?
) {
    class Builder {
        private var fromAccount: String? = null
        private var toAccount: String? = null
        private var amount: BigDecimal? = null
        private var currency: String = "GBP"
        private var reference: String? = null

        fun from(account: String) = apply { fromAccount = account }
        fun to(account: String) = apply { toAccount = account }
        fun amount(amount: BigDecimal) = apply { this.amount = amount }
        fun currency(currency: String) = apply { this.currency = currency }
        fun reference(ref: String) = apply { reference = ref }

        fun build() = TransferRequest(
            fromAccount = requireNotNull(fromAccount) { "fromAccount required" },
            toAccount = requireNotNull(toAccount) { "toAccount required" },
            amount = requireNotNull(amount) { "amount required" },
            currency = currency, reference = reference
        )
    }
}
Kotlin Builder Alternative
In Kotlin, named parameters + default values often replace the Builder pattern for data classes. Use Builders when: (1) object construction requires validation at build time, (2) the object is mutable during construction but immutable after, or (3) you're designing a public API that Java callers will use.

4. Production Example

E-Commerce App — Notification Builder + Payment Factory

// ── Builder: NotificationCompat.Builder in production ────────────
class OrderNotificationBuilder @Inject constructor(
    private val context: Context
) {
    fun buildOrderShippedNotification(order: Order): Notification =
        NotificationCompat.Builder(context, CHANNEL_ORDERS)
            .setSmallIcon(R.drawable.ic_package)
            .setContentTitle("Order #${order.id} shipped")
            .setContentText("Expected delivery: ${order.estimatedDelivery}")
            .setPriority(NotificationCompat.PRIORITY_HIGH)
            .setAutoCancel(true)
            .setContentIntent(
                PendingIntent.getActivity(context, order.id.hashCode(),
                    Intent(context, OrderDetailActivity::class.java).putExtra("order_id", order.id),
                    PendingIntent.FLAG_IMMUTABLE)
            )
            .build()
}

// ── Factory + Singleton: Payment Processor Factory ───────────────
sealed class PaymentConfig {
    data class Card(val stripeToken: String) : PaymentConfig()
    data class Wallet(val walletType: WalletType) : PaymentConfig()
    data class BankTransfer(val iban: String) : PaymentConfig()
}

interface PaymentProcessor {
    suspend fun charge(amount: BigDecimal, currency: String): ChargeResult
}

class PaymentProcessorFactory @Inject constructor(
    private val stripeClient: StripeClient,   // injected singleton
    private val googlePayClient: GooglePayClient
) {
    fun create(config: PaymentConfig): PaymentProcessor = when (config) {
        is PaymentConfig.Card         -> StripeProcessor(stripeClient, config.stripeToken)
        is PaymentConfig.Wallet       -> GooglePayProcessor(googlePayClient)
        is PaymentConfig.BankTransfer -> BankTransferProcessor(config.iban)
    }
}

Abstract Factory in Practice
Abstract Factory is most valuable in white-label or multi-tenant apps where an entire UI skin must be swappable. For single-design apps, it's over-engineering. Compose's MaterialTheme is essentially an Abstract Factory delivered via the composition locals system.

6. Pitfalls & Best Practices

Singleton Pitfalls

Global Mutable State
A Kotlin object with mutable state (e.g., a mutable list, a mutable property) shared across threads is a race condition waiting to happen. Either make it thread-safe (Mutex, AtomicReference, synchronized) or eliminate the mutability by letting DI manage the instance.
Context Leaks
Never store a reference to an Activity or Fragment Context in a singleton. It will outlive the Activity and cause a memory leak. Use applicationContext only.

Builder Best Practices

  • Validate at build time: throw descriptive exceptions from build() for required fields — not at usage time
  • Return this from setters (or use apply) to enable method chaining
  • Make the built object immutable: the Builder is mutable; the product should be a data class with val properties

Factory Method vs Direct Construction

Use the factory method when construction has conditions or side effects. Fragment.newInstance() exists because Android reconstructs Fragments from the back stack using the empty constructor — passing data via arguments bundle is the required pattern. A factory method hides this implementation detail from callers.

7. Interview Framework

30-Second Answer

"Creational patterns control object creation. The main four in Android: Singleton — one instance app-wide, Kotlin's object keyword handles it. Factory Method — creates objects without coupling callers to concrete types, like Fragment.newInstance(). Abstract Factory — creates families of related objects, useful for theming. Builder — constructs complex objects step-by-step with validation, exactly what OkHttp and Retrofit use."

2-Minute Deep Dive

"For Singleton in production Android: Kotlin's object is thread-safe but not testable — Hilt's @Singleton scope is better because the instance can be replaced with a mock. For Builder: I'd use it when an object has 5+ optional parameters or requires validation before creation — like building an OkHttpClient with optional interceptors, timeouts, and pinning config. For Factory Method: the typical Android pattern is a static factory on the class, like Fragment.newInstance(args). Abstract Factory is most useful in white-label or multi-tenant apps where an entire set of UI components must be swappable without touching the consuming code."

Must-Mention Points

1
Kotlin object = thread-safe singleton; companion object = class-level factory + access
2
Singleton problems: global mutable state (hard to test, potential race conditions, context leaks)
3
Hilt @Singleton is preferred over raw object because the instance is injectable and replaceable
4
Builder: OkHttpClient, Retrofit, NotificationCompat.Builder — step-by-step construction, validate at build()
5
Factory Method: decouples creation from usage; Fragment.newInstance() is the Android canonical example
6
Kotlin named params often replace Builder for internal data classes

Do NOT Go Deeper On

  • Prototype pattern (rarely relevant in Android)
  • Double-checked locking implementation details (just say "use Kotlin object or Hilt")
  • Abstract Factory in depth unless asked about white-labelling

9. Interview Questions
Basic How does Kotlin's object keyword implement Singleton? ⌄
Kotlin's object declaration creates a class with a private constructor and a INSTANCE static field. The JVM guarantees the initialisation is thread-safe via the class loading mechanism (static initialiser). The instance is lazily created on first access. This is equivalent to the "Initialization-on-demand holder" idiom in Java — thread-safe without synchronized blocks.
Basic Why is Fragment.newInstance() a factory method and why does it exist? ⌄
It's a factory method because it centralises Fragment creation and hides the argument bundle setup from callers. It exists because Android's Fragment system requires a public no-argument constructor — the system recreates Fragments from the back stack using that constructor. Arguments must be passed via setArguments(Bundle), not via a parameterised constructor. newInstance() encapsulates this requirement so callers can't accidentally use a parameterised constructor.
Basic Where does Android use the Builder pattern? ⌄
Builder pattern is pervasive in Android: OkHttpClient.Builder(), Retrofit.Builder(), NotificationCompat.Builder(), AlertDialog.Builder(), Room.databaseBuilder(), WorkRequest.Builder(), NavOptions.Builder(). All share the same characteristics: many optional parameters, method chaining, and a terminal build() that creates the immutable product.
Intermediate What are the problems with the Singleton pattern and how does Hilt address them? ⌄
Problems: (1) Global mutable state — any component can modify it, causing unpredictable behaviour. (2) Hard to test — you can't replace a object with a test fake without reflection. (3) Hidden dependencies — callers don't declare dependencies; they reach globally. (4) Context leaks — storing Activity context in a singleton leaks the Activity.

Hilt's solution: @Singleton scope creates one instance per application component, but the instance is provided via injection. Callers declare the dependency in their constructor; in tests, a test module replaces it with a fake. The singleton is managed by Hilt's component, not by static state.
Intermediate Implement a thread-safe lazy singleton for a Room database. ⌄
@Volatile private var INSTANCE: AppDatabase? = null in a companion object, then double-checked locking: INSTANCE ?: synchronized(this) { INSTANCE ?: Room.databaseBuilder(...).build().also { INSTANCE = it } }. @Volatile ensures the write is immediately visible to other threads. synchronized ensures only one thread creates the instance. In practice, Hilt's @Singleton is preferred over manual double-check locking.
Intermediate When would you choose a Builder over Kotlin named parameters? ⌄
Choose Builder when: (1) Construction requires validation before the object can exist — build() enforces invariants like required fields. (2) The object is being built across multiple method calls or time steps. (3) The API is consumed by Java callers (named parameters aren't available in Java). (4) You need to reuse a partial configuration — hold a Builder reference and call build() multiple times with different last-step variations. For internal Kotlin-only data classes with defaults, named parameters are almost always cleaner.
Intermediate Describe Abstract Factory with a white-label banking app example. ⌄
A white-label banking app serves 10 banks, each with their own brand colours, fonts, button styles, and icon sets. Define interface BrandComponentFactory with methods: createPrimaryButton(), createHeaderView(), createLogoImage(). Each bank gets its implementation: BarclaysFactory, HSBCFactory, etc. The checkout and home screens receive a BrandComponentFactory via injection — they call factory.createPrimaryButton() and get the bank-correct component without knowing which bank it is. Switching banks only requires changing which factory Hilt provides.
Senior How does Hilt's module system map to the Abstract Factory pattern? ⌄
A Hilt @Module is effectively an Abstract Factory for a set of related dependencies. The module interface (@Provides/@Binds methods) defines what the factory creates. Different test/production modules are different factories producing the same interface. For example, a NetworkModule creates OkHttpClient, Retrofit, and API interfaces as a consistent family. A FakeNetworkModule in tests produces fakes for the same interfaces. Hilt selects which module to use at compile time — the client code never changes.
Senior A Singleton holds a reference to a Context. What are the consequences and how do you fix it? ⌄
Consequences: If it's an Activity context, the Activity cannot be garbage collected as long as the singleton exists (application lifetime). This leaks all views, Drawables, and resources attached to that Activity — potentially hundreds of MB. The GC can't reclaim them until the process dies.

Fix: (1) Always use context.applicationContext in singletons — it lives as long as the app process. (2) For UI-related resources that require an Activity context, don't store them in singletons — let the Activity own them and pass them as parameters. (3) Use LeakCanary in debug builds to detect these leaks automatically.
Senior Design an OkHttpClient builder configuration for a production banking app. ⌄
Production banking client builder includes: (1) CertificatePinner — pin the server's certificate to prevent MITM. (2) AuthInterceptor — adds Bearer token from TokenStore, refreshes on 401. (3) HttpLoggingInterceptor — Level.NONE in production, Level.BODY in debug (wrap with BuildConfig check). (4) connectTimeout(15s) / readTimeout(30s) / writeTimeout(30s). (5) ConnectionPool(5, 5, MINUTES) — reuse connections. (6) Authenticator — for automatic token refresh on 401. (7) retryOnConnectionFailure(false) — let the app handle retries with exponential backoff for payment idempotency.
