43A — CameraX, Photo Picker & Media

CameraX lifecycle-aware camera, Android 13+ Photo Picker (replaces READ_EXTERNAL_STORAGE), MediaStore, video recording, image analysis with ML Kit integration, and media permission changes across Android versions.

ID: 43A ⭐ Tier 2 — Camera & Media
📷
1. Overview & Why It Matters

Plain-Words Analogy

Think of Camera2 as raw engine parts — powerful but you have to assemble the crankshaft, pistons, and timing yourself. CameraX is the assembled engine with a warranty: same power, lifecycle-aware, consistent across every manufacturer's quirks. Photo Picker is the ATM machine of media access — the user gets to choose exactly which photos to hand you, and you never touch the vault yourself.

Why CameraX Replaced Camera2 for Most Apps

  • Lifecycle-aware: Binds to a LifecycleOwner; automatically starts/stops the camera stream without leaks.
  • Use-case based API: Declare what you need (Preview, ImageCapture, ImageAnalysis, VideoCapture) — CameraX handles device-specific wiring.
  • Cross-device consistency: Abstracts vendor-specific bugs on Samsung, Xiaomi, and others through the camera-camera2 compatibility layer.
  • Extensions support: Night mode, Portrait, HDR, Face Retouch — same API across OEMs that support them.

Photo Picker — Privacy by Design

Android 13 (API 33) introduced the system Photo Picker. Instead of granting an app broad access to the entire media library, the user selects specific items and the app receives only those URIs. The system never grants storage access — the permission dialog is gone entirely.

Breaking Change
READ_EXTERNAL_STORAGE was grandfathered out in Android 13. Apps targeting API 33+ that still request it get no access. You must use the Photo Picker or the new granular permissions (READ_MEDIA_IMAGES, READ_MEDIA_VIDEO, READ_MEDIA_AUDIO).

Senior Mental Model
"Every feature that touches media has a permission cliff at API 33 and another at API 29. Before writing a single line of camera code, ask: 'Does this need to read other apps' media or only capture new content?' If capturing only, you need zero storage permissions — just CAMERA."

2. How CameraX Works

The Four Use Cases

┌─────────────────── CameraX Use Cases ───────────────────┐ │ Preview → Render live stream to PreviewView │ │ ImageCapture → Take a still photo (JPEG/RAW) │ │ ImageAnalysis → Real-time frame processing (ML Kit) │ │ VideoCapture → Record video with audio │ └──────────────────────────────────────────────────────────┘ Bound together via ProcessCameraProvider + LifecycleOwner

ProcessCameraProvider — The Binding Hub

ProcessCameraProvider is a singleton that manages camera lifecycle. You retrieve it asynchronously, then bind your use cases to a LifecycleOwner. When the lifecycle owner is destroyed, CameraX automatically releases the camera.

Full Production Example: CameraX + Compose

This example wires up Preview + ImageCapture inside a Compose screen using AndroidView to host the PreviewView.

// build.gradle.kts (app)
dependencies {
    val cameraxVersion = "1.3.4"
    implementation("androidx.camera:camera-core:$cameraxVersion")
    implementation("androidx.camera:camera-camera2:$cameraxVersion")  // Camera2 compat layer
    implementation("androidx.camera:camera-lifecycle:$cameraxVersion")
    implementation("androidx.camera:camera-view:$cameraxVersion")     // PreviewView
    implementation("androidx.camera:camera-video:$cameraxVersion")    // VideoCapture
    implementation("androidx.camera:camera-extensions:$cameraxVersion") // Night, Portrait etc.
}
// CameraScreen.kt
import android.content.Context
import androidx.camera.core.CameraSelector
import androidx.camera.core.ImageCapture
import androidx.camera.core.ImageCaptureException
import androidx.camera.core.Preview
import androidx.camera.lifecycle.ProcessCameraProvider
import androidx.camera.view.PreviewView
import androidx.compose.foundation.layout.*
import androidx.compose.material3.*
import androidx.compose.runtime.*
import androidx.compose.ui.Alignment
import androidx.compose.ui.Modifier
import androidx.compose.ui.platform.LocalContext
import androidx.compose.ui.platform.LocalLifecycleOwner
import androidx.compose.ui.viewinterop.AndroidView
import androidx.core.content.ContextCompat
import java.io.File
import java.util.concurrent.Executors

@Composable
fun CameraScreen(onPhotoSaved: (File) -> Unit) {
    val context       = LocalContext.current
    val lifecycleOwner = LocalLifecycleOwner.current  // ✅ correct in Compose

    // Hold a reference so we can call takePicture later
    var imageCapture by remember { mutableStateOf<ImageCapture?>(null) }

    Box(modifier = Modifier.fillMaxSize()) {
        // AndroidView hosts the PreviewView (SurfaceView-based)
        AndroidView(
            factory = { ctx: Context ->
                val previewView = PreviewView(ctx)

                val cameraProviderFuture = ProcessCameraProvider.getInstance(ctx)
                cameraProviderFuture.addListener({
                    val cameraProvider = cameraProviderFuture.get()

                    // 1. Preview use case — connects to PreviewView surface
                    val preview = Preview.Builder().build().also {
                        it.setSurfaceProvider(previewView.surfaceProvider)
                    }

                    // 2. ImageCapture use case
                    val capture = ImageCapture.Builder()
                        .setCaptureMode(ImageCapture.CAPTURE_MODE_MINIMIZE_LATENCY)
                        .build()
                    imageCapture = capture

                    // 3. Select back camera (can switch to LENS_FACING_FRONT)
                    val cameraSelector = CameraSelector.DEFAULT_BACK_CAMERA

                    try {
                        // Unbind all before re-binding
                        cameraProvider.unbindAll()
                        cameraProvider.bindToLifecycle(
                            lifecycleOwner,
                            cameraSelector,
                            preview,
                            capture
                        )
                    } catch (e: Exception) {
                        e.printStackTrace()
                    }
                }, ContextCompat.getMainExecutor(ctx))

                previewView
            },
            modifier = Modifier.fillMaxSize()
        )

        Button(
            onClick = { capturePhoto(context, imageCapture, onPhotoSaved) },
            modifier = Modifier.align(Alignment.BottomCenter).padding(bottom = 32.dp)
        ) {
            Text("Take Photo")
        }
    }
}

private fun capturePhoto(
    context: Context,
    imageCapture: ImageCapture?,
    onPhotoSaved: (File) -> Unit
) {
    val capture = imageCapture ?: return
    val photoFile = File(context.cacheDir, "photo_${System.currentTimeMillis()}.jpg")
    val outputOptions = ImageCapture.OutputFileOptions.Builder(photoFile).build()
    val executor = Executors.newSingleThreadExecutor()

    capture.takePicture(
        outputOptions, executor,
        object : ImageCapture.OnImageSavedCallback {
            override fun onImageSaved(output: ImageCapture.OutputFileResults) {
                onPhotoSaved(photoFile)
            }
            override fun onError(exception: ImageCaptureException) {
                exception.printStackTrace()
            }
        }
    )
}

3. Photo Picker (Android 13+)

Why Photo Picker Exists

Before Android 13, an app needing to display a user's photo had to request READ_EXTERNAL_STORAGE — a permission that grants access to the entire media library. The Photo Picker fixes this: the system displays its own selection UI, and the app only receives URIs for the items the user chose. No storage permission is ever granted to the app.

Old flow: App → request READ_EXTERNAL_STORAGE → user grants → app sees ALL media New flow: App → launch Photo Picker → user selects items → app gets ONLY those URIs (zero storage permission change; system handles access)

PickVisualMedia Contract (API 33+)

// Gradle dependency (backported to API 19+ via Jetpack)
implementation("androidx.activity:activity-ktx:1.9.0")

// In your Fragment or Activity
import androidx.activity.result.contract.ActivityResultContracts.PickVisualMedia
import androidx.activity.result.contract.ActivityResultContracts.PickMultipleVisualMedia

// Single image picker
val pickMedia = registerForActivityResult(PickVisualMedia()) { uri: Uri? ->
    if (uri != null) {
        // URI is valid for the lifetime of this app session
        // Persist via takePersistableUriPermission() if needed across sessions
        viewModel.onPhotoSelected(uri)
    } else {
        // User cancelled picker
    }
}

// Launch — images only
pickMedia.launch(PickVisualMedia.ImageOnly)
// Or images + video
pickMedia.launch(PickVisualMedia.ImageAndVideo)
// Or a specific MIME type
pickMedia.launch(PickVisualMedia.SingleMimeType("image/gif"))

// Multiple selection (up to system max, typically 100)
val pickMultiple = registerForActivityResult(PickMultipleVisualMedia(10)) { uris ->
    uris.forEach { uri -> viewModel.addPhoto(uri) }
}

Fallback for API < 33

The PickVisualMedia contract is backported to API 19+ via Jetpack. On devices running API 21–32 without the Android 13 Photo Picker backport (available via Google Play System Updates), it automatically falls back to ACTION_GET_CONTENT. However, the fallback does require READ_EXTERNAL_STORAGE on those older devices.

// Permission decision: what to request at each API level
fun requestMediaPermissionsIfNeeded(activity: ComponentActivity) {
    when {
        // API 34+: partial access may be needed for MediaStore queries
        Build.VERSION.SDK_INT >= Build.VERSION_CODES.UPSIDE_DOWN_CAKE -> {
            // If using Photo Picker only: no permission needed
            // If querying MediaStore directly: request READ_MEDIA_IMAGES
            // + READ_MEDIA_VISUAL_USER_SELECTED for partial access
            activity.requestPermissions(
                arrayOf(
                    Manifest.permission.READ_MEDIA_IMAGES,
                    Manifest.permission.READ_MEDIA_VISUAL_USER_SELECTED
                ), REQUEST_CODE
            )
        }
        // API 33: granular media permissions
        Build.VERSION.SDK_INT >= Build.VERSION_CODES.TIRAMISU -> {
            activity.requestPermissions(
                arrayOf(
                    Manifest.permission.READ_MEDIA_IMAGES,
                    Manifest.permission.READ_MEDIA_VIDEO
                ), REQUEST_CODE
            )
        }
        // API 29–32: scoped storage, READ_EXTERNAL_STORAGE
        Build.VERSION.SDK_INT >= Build.VERSION_CODES.Q -> {
            activity.requestPermissions(
                arrayOf(Manifest.permission.READ_EXTERNAL_STORAGE),
                REQUEST_CODE
            )
        }
        // API ≤ 28: READ + WRITE both needed for external storage
        else -> {
            activity.requestPermissions(
                arrayOf(
                    Manifest.permission.READ_EXTERNAL_STORAGE,
                    Manifest.permission.WRITE_EXTERNAL_STORAGE
                ), REQUEST_CODE
            )
        }
    }
}

Best Practice
Prefer Photo Picker as the primary flow. Only fall back to direct MediaStore queries (and therefore request permissions) when you must display a gallery of the user's photos without them picking. For all other cases, Photo Picker gives the best privacy posture and user trust.

4. MediaStore & File Access

Scoped Storage Rules (API 29+)

  • Apps can read/write their own files in app-specific directories (getExternalFilesDir()) without any permission.
  • To contribute media to the shared MediaStore (Photos, Music, Downloads), use ContentResolver.insert() — no WRITE_EXTERNAL_STORAGE needed on API 29+.
  • To read other apps' media, you need READ_MEDIA_IMAGES (API 33+) or READ_EXTERNAL_STORAGE (API 29–32).
  • You can only delete your own contributed media without a permission dialog; deleting others' files triggers a system confirmation dialog.

Writing a Captured Photo to MediaStore

import android.content.ContentValues
import android.provider.MediaStore
import android.os.Build
import android.os.Environment

fun savePhotoToMediaStore(context: Context, jpegBytes: ByteArray): Uri? {
    val contentValues = ContentValues().apply {
        put(MediaStore.Images.Media.DISPLAY_NAME, "photo_${System.currentTimeMillis()}.jpg")
        put(MediaStore.Images.Media.MIME_TYPE, "image/jpeg")
        if (Build.VERSION.SDK_INT >= Build.VERSION_CODES.Q) {
            // IS_PENDING marks the file as "in progress" while we write bytes
            put(MediaStore.Images.Media.IS_PENDING, 1)
            put(MediaStore.Images.Media.RELATIVE_PATH,
                Environment.DIRECTORY_PICTURES + "/MyApp")
        }
    }

    val resolver = context.contentResolver
    val collection = if (Build.VERSION.SDK_INT >= Build.VERSION_CODES.Q) {
        MediaStore.Images.Media.getContentUri(MediaStore.VOLUME_EXTERNAL_PRIMARY)
    } else {
        MediaStore.Images.Media.EXTERNAL_CONTENT_URI
    }

    val itemUri = resolver.insert(collection, contentValues) ?: return null

    resolver.openOutputStream(itemUri).use { stream ->
        stream?.write(jpegBytes)
    }

    // Clear IS_PENDING so the photo is visible in the gallery
    if (Build.VERSION.SDK_INT >= Build.VERSION_CODES.Q) {
        contentValues.clear()
        contentValues.put(MediaStore.Images.Media.IS_PENDING, 0)
        resolver.update(itemUri, contentValues, null, null)
    }

    return itemUri
}

Querying MediaStore with ContentResolver

fun queryRecentPhotos(context: Context): List<Uri> {
    val uris = mutableListOf<Uri>()
    val projection = arrayOf(
        MediaStore.Images.Media._ID,
        MediaStore.Images.Media.DISPLAY_NAME,
        MediaStore.Images.Media.DATE_ADDED
    )
    val sortOrder = "${MediaStore.Images.Media.DATE_ADDED} DESC"

    context.contentResolver.query(
        MediaStore.Images.Media.EXTERNAL_CONTENT_URI,
        projection, null, null, sortOrder
    )?.use { cursor ->
        val idCol = cursor.getColumnIndexOrThrow(MediaStore.Images.Media._ID)
        while (cursor.moveToNext()) {
            val id = cursor.getLong(idCol)
            val uri = ContentUris.withAppendedId(
                MediaStore.Images.Media.EXTERNAL_CONTENT_URI, id
            )
            uris.add(uri)
        }
    }
    return uris
}

Common Pitfall
Never pass a raw File path to another app on Android 7+ — it will throw FileUriExposedException. Always use FileProvider.getUriForFile() to create a content URI.

5. Video Recording with CameraX

VideoCapture Use Case

CameraX VideoCapture records video with synchronized audio. It returns a Recording object that supports pause/resume/stop.

import androidx.camera.video.*
import androidx.core.content.ContextCompat
import android.Manifest

// 1. Build the Recorder (quality selector)
val recorder = Recorder.Builder()
    .setQualitySelector(QualitySelector.from(Quality.HIGHEST))
    .build()

// 2. Wrap in VideoCapture use case
val videoCapture = VideoCapture.withOutput(recorder)

// 3. Bind to lifecycle (alongside Preview)
cameraProvider.bindToLifecycle(
    lifecycleOwner,
    CameraSelector.DEFAULT_BACK_CAMERA,
    preview,
    videoCapture
)

// 4. Start recording — MediaStore output
var activeRecording: Recording? = null

fun startRecording(context: Context) {
    val contentValues = ContentValues().apply {
        put(MediaStore.Video.Media.DISPLAY_NAME, "video_${System.currentTimeMillis()}.mp4")
        put(MediaStore.Video.Media.MIME_TYPE, "video/mp4")
        if (Build.VERSION.SDK_INT >= Build.VERSION_CODES.Q) {
            put(MediaStore.Video.Media.RELATIVE_PATH, "Movies/MyApp")
        }
    }

    val mediaStoreOutput = MediaStoreOutputOptions.Builder(
        context.contentResolver,
        MediaStore.Video.Media.EXTERNAL_CONTENT_URI
    ).setContentValues(contentValues).build()

    // RECORD_AUDIO permission must be granted before calling prepareRecording
    activeRecording = videoCapture.output
        .prepareRecording(context, mediaStoreOutput)
        .withAudioEnabled()   // requires RECORD_AUDIO permission
        .start(ContextCompat.getMainExecutor(context)) { recordEvent ->
            when (recordEvent) {
                is VideoRecordEvent.Start  -> { /* Recording started */ }
                is VideoRecordEvent.Pause  -> { /* Paused */ }
                is VideoRecordEvent.Resume -> { /* Resumed */ }
                is VideoRecordEvent.Finalize -> {
                    if (!recordEvent.hasError()) {
                        val savedUri = recordEvent.outputResults.outputUri
                        // Handle saved video URI
                    } else {
                        // Handle error: recordEvent.error
                    }
                }
            }
        }
}

// Pause / Resume / Stop
fun pauseRecording()  { activeRecording?.pause() }
fun resumeRecording() { activeRecording?.resume() }
fun stopRecording()   { activeRecording?.stop(); activeRecording = null }

6. Image Analysis & ML Kit

ImageAnalysis Use Case

ImageAnalysis delivers frames to an Analyzer callback on a background thread. This is the integration point for ML Kit, OpenCV, or any real-time vision pipeline.

import androidx.camera.core.ImageAnalysis
import androidx.camera.core.ImageProxy
import com.google.mlkit.vision.barcode.BarcodeScanning
import com.google.mlkit.vision.common.InputImage
import java.util.concurrent.Executors

// 1. Configure ImageAnalysis
val imageAnalysis = ImageAnalysis.Builder()
    .setTargetResolution(Size(1280, 720))
    // STRATEGY_KEEP_ONLY_LATEST: drops frames if analyzer is busy
    // This prevents frame queuing which would cause ever-growing latency
    .setBackpressureStrategy(ImageAnalysis.STRATEGY_KEEP_ONLY_LATEST)
    .build()

// 2. Set the analyzer on a background executor
val cameraExecutor = Executors.newSingleThreadExecutor()
imageAnalysis.setAnalyzer(cameraExecutor, BarcodeAnalyzer { barcodes ->
    barcodes.forEach { barcode ->
        // Handle detected barcodes on background thread
        // Post UI updates back to main thread
    }
})

// 3. Bind alongside Preview
cameraProvider.bindToLifecycle(lifecycleOwner, cameraSelector, preview, imageAnalysis)
// BarcodeAnalyzer.kt — ML Kit integration
class BarcodeAnalyzer(
    private val onBarcodeDetected: (List<Barcode>) -> Unit
) : ImageAnalysis.Analyzer {

    private val scanner = BarcodeScanning.getClient()

    override fun analyze(imageProxy: ImageProxy) {
        val mediaImage = imageProxy.image
        if (mediaImage == null) {
            imageProxy.close()  // ✅ ALWAYS close in all code paths
            return
        }

        val image = InputImage.fromMediaImage(
            mediaImage,
            imageProxy.imageInfo.rotationDegrees
        )

        scanner.process(image)
            .addOnSuccessListener { barcodes ->
                if (barcodes.isNotEmpty()) {
                    onBarcodeDetected(barcodes)
                }
            }
            .addOnFailureListener { /* log error */ }
            .addOnCompleteListener {
                // ✅ CRITICAL: close ImageProxy in addOnCompleteListener
                // This ensures it's closed even on failure, allowing the
                // next frame to be delivered
                imageProxy.close()
            }
    }
}

Backpressure Strategy — Why It Matters

StrategyBehaviorWhen to Use
STRATEGY_KEEP_ONLY_LATESTDrops all frames while analyzer is busy; delivers only the most recent when freeReal-time ML processing (barcode, face detection) — always prefer this
STRATEGY_BLOCK_PRODUCERBlocks camera frame production until analyzer is doneNever recommended — causes preview stutter and ANR risk

Thread Considerations

  • The analyze() callback runs on the executor you pass to setAnalyzer(). Use a background executor, not the main thread.
  • ML Kit's process() is asynchronous — never close ImageProxy before the ML Kit task completes. Close it in addOnCompleteListener.
  • If you forget to call imageProxy.close(), CameraX will never deliver the next frame. The camera appears frozen.

Face Detection Pipeline (Simplified)

import com.google.mlkit.vision.face.FaceDetection
import com.google.mlkit.vision.face.FaceDetectorOptions

class FaceAnalyzer(
    private val onFacesDetected: (List<Face>) -> Unit
) : ImageAnalysis.Analyzer {

    private val options = FaceDetectorOptions.Builder()
        .setPerformanceMode(FaceDetectorOptions.PERFORMANCE_MODE_FAST)
        .build()
    private val detector = FaceDetection.getClient(options)

    override fun analyze(imageProxy: ImageProxy) {
        val mediaImage = imageProxy.image ?: run { imageProxy.close(); return }
        val inputImage = InputImage.fromMediaImage(mediaImage, imageProxy.imageInfo.rotationDegrees)
        detector.process(inputImage)
            .addOnSuccessListener { faces -> onFacesDetected(faces) }
            .addOnCompleteListener { imageProxy.close() }  // ✅ always close here
    }
}
Expert Note
Shut down the ML Kit detector and the camera executor when done to avoid resource leaks: detector.close() in onDestroy(), and cameraExecutor.shutdown() similarly. CameraX does not own these resources.

7. Pitfalls & Production Bugs
Bug 1 — Leaking ImageProxy (Frozen Camera)
Symptom: Camera preview freezes after first frame is analyzed. ML Kit callbacks never fire again.
Cause: imageProxy.close() was not called after analysis. CameraX holds the next frame until the current one is closed.
Fix: Always close in addOnCompleteListener, not addOnSuccessListener. The complete listener fires regardless of success or failure.
// ❌ Wrong — not closed on failure
scanner.process(image).addOnSuccessListener { imageProxy.close() }

// ✅ Correct — always closed
scanner.process(image).addOnCompleteListener { imageProxy.close() }
Bug 2 — Wrong LifecycleOwner in Fragments
Symptom: Camera binds successfully once, but after navigating away and back, the camera stream is black or never starts again.
Cause: Using this (the Fragment itself) as the lifecycle owner instead of viewLifecycleOwner. The Fragment instance can outlive its view, and CameraX's binding becomes inconsistent.
Fix: 
// ❌ Wrong — Fragment lifecycle, not View lifecycle
cameraProvider.bindToLifecycle(this, cameraSelector, preview)

// ✅ Correct — View lifecycle tears down cleanly with the view
cameraProvider.bindToLifecycle(viewLifecycleOwner, cameraSelector, preview)
Bug 3 — Requesting CAMERA Permission After CameraX Starts
Symptom: CameraAccessException: CAMERA_DISABLED or camera never opens on first launch.
Fix: Always check and request CAMERA permission before calling ProcessCameraProvider.getInstance(). Gate the entire CameraX initialization behind permission grant.
Bug 4 — Photo Picker Returns Null URI
Symptom: The picker callback fires with null.
Cause: User pressed "Back" or cancelled the picker. This is normal behavior, not an error.
Fix: Always null-check the result URI. Do not show an error toast on null — the user simply cancelled.
Bug 5 — MediaStore URI Invalid After Process Death
Symptom: App is killed by the system, restored from background, and previously stored MediaStore URIs throw FileNotFoundException.
Cause: Temporary URIs obtained from ContentResolver.insert() with IS_PENDING=1 are not persistent across process death.
Fix: Clear IS_PENDING immediately after writing. For URIs received from Photo Picker that must persist, call contentResolver.takePersistableUriPermission(uri, Intent.FLAG_GRANT_READ_URI_PERMISSION).
Bug 6 — READ_MEDIA_IMAGES vs READ_EXTERNAL_STORAGE Confusion
Symptom: MediaStore queries return zero results on Android 13+ despite permission being granted at runtime.
Cause: App requests READ_EXTERNAL_STORAGE on API 33+, which is no longer granted for media access. The system silently ignores it or shows a one-time dialog that doesn't actually gate media access.
Fix: Use version-gated permission requests. On API 33+, request READ_MEDIA_IMAGES/READ_MEDIA_VIDEO. On API 34+, also handle READ_MEDIA_VISUAL_USER_SELECTED for partial access gracefully.
Bug 7 — Using File Paths Directly on Android 10+
Symptom: FileNotFoundException or permission denied when accessing absolute file paths from MediaStore on Android 10+ in scoped storage.
Cause: cursor.getString(DATA_COL) returns a path that your app cannot access under scoped storage.
Fix: Never use the DATA column path directly. Use ContentUris.withAppendedId() to build a content URI and open it through ContentResolver.openInputStream().

What Interviewers Are Testing

1

2

3

Resource management: ImageProxy must be closed. Where and why (addOnCompleteListener, not addOnSuccessListener).
5
Scoped storage: Why you don't need WRITE_EXTERNAL_STORAGE on API 29+ for MediaStore writes. The IS_PENDING pattern.

30-Second Answer

"CameraX is a lifecycle-aware camera library built on Camera2. It uses a use-case based API — Preview, ImageCapture, ImageAnalysis, VideoCapture — bound to a LifecycleOwner so the camera is automatically released. For media access, Android 13 introduced the Photo Picker as a privacy-preserving replacement for READ_EXTERNAL_STORAGE: the user picks items and the app gets only those URIs with no storage permission needed. For writing media, scoped storage on Android 10+ means we use MediaStore.insert() with IS_PENDING to write atomically, no storage permission required."

2-Minute Answer

"CameraX replaced Camera2 for most use cases because it handles the lifecycle complexity — you bind use cases to a LifecycleOwner and the framework manages start/stop. The three main use cases are Preview, which renders to a PreviewView surface; ImageCapture for stills; and ImageAnalysis for real-time frame processing, which is where ML Kit integrates. VideoCapture handles recording with pause/resume through the Recorder API.

For media access, the permission model changed significantly across Android versions. Below API 29, you needed READ and WRITE_EXTERNAL_STORAGE. API 29 introduced scoped storage — apps can write to MediaStore without WRITE_EXTERNAL_STORAGE. API 33 deprecated READ_EXTERNAL_STORAGE for media entirely, replacing it with granular READ_MEDIA_IMAGES, READ_MEDIA_VIDEO, READ_MEDIA_AUDIO permissions. API 34 added partial access with READ_MEDIA_VISUAL_USER_SELECTED.

The best modern approach is the Photo Picker introduced in API 33 — it requires zero permissions, is backported to earlier APIs via Jetpack, and preserves user privacy by never granting the app broad storage access. For production camera apps, the key pitfalls are: not closing ImageProxy in addOnCompleteListener (causes a frozen camera), using 'this' instead of viewLifecycleOwner in Fragments, and using raw File paths instead of content URIs on Android 10+."

9. Flash Cards
CameraX 3 core use cases?
Preview (surface render), ImageCapture (still photo), ImageAnalysis (frame processing). VideoCapture is the 4th for recording.
Photo Picker contract name?
ActivityResultContracts.PickVisualMedia (single) or PickMultipleVisualMedia(max). Available via Jetpack, backported to API 19.
Permission to request on API 33+ for media access?
READ_MEDIA_IMAGES, READ_MEDIA_VIDEO, READ_MEDIA_AUDIO. NOT READ_EXTERNAL_STORAGE (deprecated for media at API 33).
ImageProxy leak — what happens & fix?
Camera freezes — no more frames delivered. Fix: call imageProxy.close() in addOnCompleteListener (not just success listener) so it always executes.
viewLifecycleOwner rule in Fragments?
Always use viewLifecycleOwner (not this) when binding CameraX. Fragment lifecycle outlives the View; using this causes camera stream inconsistencies after navigation.
Scoped storage: write photo on API 29+ — permission needed?
No. Use ContentResolver.insert(MediaStore.Images.Media.EXTERNAL_CONTENT_URI, contentValues). No WRITE_EXTERNAL_STORAGE needed on API 29+.
MediaStore vs raw File path on Android 10+?
Never use the DATA column absolute path — inaccessible under scoped storage. Build a content URI with ContentUris.withAppendedId() and open via ContentResolver.
ML Kit integration point in CameraX?
ImageAnalysis use case with a custom Analyzer. Feed each ImageProxy to InputImage.fromMediaImage(), then pass to BarcodeScanning.getClient().process().
VideoCapture pause/resume API?
Call prepareRecording(...).start(executor, listener) → returns a Recording. Then recording.pause() / recording.resume() / recording.stop().
FileProvider — why needed & when?
Sharing a File with another app via Intent on Android 7+ requires a content:// URI. Passing a file:// URI throws FileUriExposedException. Use FileProvider.getUriForFile() + FLAG_GRANT_READ_URI_PERMISSION.

10. Interview Questions
Q1 — What are the main advantages of CameraX over Camera2, and when would you still use Camera2 directly?
Medium▼
CameraX advantages:
1. Lifecycle-aware: Binds to a LifecycleOwner — no manual start/stop in onResume/onPause, no resource leaks.
2. Use-case based API: Declare what you need (Preview, ImageCapture, ImageAnalysis, VideoCapture); CameraX handles device-specific wiring.
3. Cross-device consistency: Abstracts OEM-specific Camera2 quirks through the camera-camera2 layer. Samsung, Xiaomi, Pixel all behave consistently.
4. Jetpack integration: Works naturally with Compose, Hilt, and coroutines.
5. Extensions: Night mode, Portrait, HDR via the Extensions API — same code across OEMs that support them.

When to use Camera2 directly:
— Ultra-low-level control (specific sensor modes, RAW capture pipelines, manual sensor exposure/focus bracketing for professional camera apps).
— When the CameraX compatibility layer introduces unacceptable latency for a specific device or use case.
— Legacy code that can't be migrated without significant risk.

In practice: CameraX uses Camera2 internally via the camera-camera2 dependency. 99% of apps should use CameraX. Only go to Camera2 directly if a CameraX use case doesn't expose the hardware control you need.
Q2 — Explain the security model behind Android's Photo Picker. Why is it more secure than requesting READ_EXTERNAL_STORAGE?
Medium▼
Security model:
The Photo Picker runs as a system-owned process. The system UI displays the user's media library, the user selects items, and the system returns content URIs scoped only to those selected items. The app process never receives the storage permission — it just gets URIs.

Why it's more secure than READ_EXTERNAL_STORAGE:
— READ_EXTERNAL_STORAGE granted an app access to everything in the shared storage: all photos, videos, and audio from all apps. A malicious or compromised app could exfiltrate the user's entire camera roll.
— Photo Picker is permission-less from the app's perspective. No permission dialog is shown. The user is never tricked into granting broad access.
— The selected URIs are only valid for the current app session unless the app explicitly calls takePersistableUriPermission().

From an interview standpoint: This is a "principle of least privilege" answer — the app gets the minimum data access it needs to complete its task.
Q3 — Your camera screen uses ImageAnalysis with ML Kit. After shipping, users report the camera freezes after a few seconds. What is the most likely cause and fix?
Hard▼
Root cause: ImageProxy.close() is not being called after the ML Kit task completes. CameraX holds a buffer slot open for each unprocessed frame. When all buffer slots are exhausted (typically after 3–4 frames depending on hardware), CameraX stops delivering new frames — the camera appears frozen.

Why it's subtle: If you placed imageProxy.close() in addOnSuccessListener instead of addOnCompleteListener, it works fine under normal conditions but silently leaks on ML Kit failures (network errors, unsupported input, etc.).

Fix: 
scanner.process(image)
    .addOnSuccessListener { barcodes -> handleBarcodes(barcodes) }
    .addOnFailureListener  { err -> /* log */ }
    .addOnCompleteListener { imageProxy.close() }  // ✅ always runs
Additional fix: Ensure backpressure strategy is STRATEGY_KEEP_ONLY_LATEST so that if analysis is slow, frames are dropped rather than queued.
Q4 — Walk me through the permission decision tree for accessing photos on a device running each of Android 9, 11, 13, and 14. What do you request in each case?
Hard▼
Android 9 (API 28) and below:
Request READ_EXTERNAL_STORAGE + WRITE_EXTERNAL_STORAGE. Both needed for full media read/write.

Android 11 (API 30):
Request READ_EXTERNAL_STORAGE only — WRITE_EXTERNAL_STORAGE does nothing on API 29+ for shared media (scoped storage). Write via MediaStore.insert() without permission.

Android 13 (API 33):
Do NOT request READ_EXTERNAL_STORAGE — it's ignored for media. Instead:
— READ_MEDIA_IMAGES for photos
— READ_MEDIA_VIDEO for videos
— READ_MEDIA_AUDIO for music
OR: Use the Photo Picker (zero permissions needed).

Android 14 (API 34):
Same as API 33 + add READ_MEDIA_VISUAL_USER_SELECTED for partial access. When the user grants partial access, you only see the photos they chose. Handle this gracefully — re-request access when needed, don't assume full library access.

Key takeaway: Always check Build.VERSION.SDK_INT and request the appropriate permission for the running version. Never hard-code a single permission for all API levels.
Q5 — How do you query MediaStore to get a list of recent photos, and what is the correct way to build the content URI for each photo?
Medium▼
Correct approach:
1. Query with ContentResolver.query() against MediaStore.Images.Media.EXTERNAL_CONTENT_URI.
2. Project only the columns you need: _ID, DISPLAY_NAME, DATE_ADDED.
3. Build each photo's URI using: ContentUris.withAppendedId(MediaStore.Images.Media.EXTERNAL_CONTENT_URI, id)

Critical mistake to avoid: Do NOT use the DATA column (MediaStore.Images.Media.DATA) to get an absolute file path on Android 10+. The path may be inaccessible under scoped storage. Always build and use a content URI.

Load via: contentResolver.openInputStream(uri) or pass the URI to Coil/Glide for async loading — they handle content URIs natively.
Q6 — What is scoped storage? A junior dev says "I'll just add WRITE_EXTERNAL_STORAGE to save photos to the gallery." What do you tell them?
Medium▼
What is scoped storage:
Scoped storage (introduced in Android 10, enforced in Android 11) means each app has isolated access to storage. Apps can freely read/write their own app-specific directories. To contribute media to shared collections (Gallery, Music), they use MediaStore — a content-addressed API — rather than raw file system paths.

What to tell the junior dev:
"On Android 10+, WRITE_EXTERNAL_STORAGE is a no-op for shared media — granting it doesn't give you any additional file access. To save a photo to the gallery, use ContentResolver.insert(MediaStore.Images.Media.EXTERNAL_CONTENT_URI, contentValues). You don't need any write permission. The MediaStore API is the correct — and only reliable — way to add photos to the shared gallery on modern Android."

Key scoped storage facts:
— App-specific directories (getExternalFilesDir()): zero permissions needed to read/write.
— Shared MediaStore collections: use ContentResolver.insert() to write, no WRITE_EXTERNAL_STORAGE needed.
— Use IS_PENDING = 1 while writing, set to 0 when done (prevents partial files appearing in gallery).
Q7 — How do you switch between front and back camera in a CameraX-based app? What is the correct way to do it without leaking resources?
Easy▼
Correct approach:
1. Keep a reference to the ProcessCameraProvider.
2. Call cameraProvider.unbindAll() to release the current camera.
3. Create a new CameraSelector with the desired lens facing.
4. Call cameraProvider.bindToLifecycle() with the new selector and same use cases.
var lensFacing = CameraSelector.LENS_FACING_BACK

fun flipCamera() {
    lensFacing = if (lensFacing == CameraSelector.LENS_FACING_BACK)
        CameraSelector.LENS_FACING_FRONT
    else
        CameraSelector.LENS_FACING_BACK

    cameraProvider.unbindAll()  // ✅ must unbind before rebinding
    val newSelector = CameraSelector.Builder()
        .requireLensFacing(lensFacing).build()
    cameraProvider.bindToLifecycle(lifecycleOwner, newSelector, preview, imageCapture)
}
Common mistake: Forgetting to call unbindAll() before rebinding. This can cause both cameras to be bound simultaneously, leading to a CameraState.ERROR_CAMERA_IN_USE error.
Q8 — Describe the end-to-end pipeline for real-time barcode scanning using CameraX + ML Kit. Include the key threading and resource management considerations.
Hard▼
Pipeline:
1. Setup: Create ImageAnalysis with STRATEGY_KEEP_ONLY_LATEST backpressure. Create a single-thread background executor.
2. Analyzer: Implement ImageAnalysis.Analyzer. In analyze(imageProxy): get imageProxy.image (YUV_420_888), wrap in InputImage.fromMediaImage() with rotation degrees.
3. ML Kit: Call BarcodeScanning.getClient().process(inputImage). Handle success in addOnSuccessListener; close ImageProxy in addOnCompleteListener.
4. UI update: Post barcode result to the main thread via Handler(Looper.getMainLooper()).post() or a Channel/StateFlow.
5. Binding: Bind imageAnalysis alongside preview to viewLifecycleOwner.

Key resource management:
— imageProxy.close() MUST be called in addOnCompleteListener, not just success.
— Shutdown the executor in onDestroyView(): cameraExecutor.shutdown().
— Close the ML Kit client: scanner.close() when done.
— Use STRATEGY_KEEP_ONLY_LATEST — if ML Kit takes 100ms per frame and the camera delivers at 30fps, without this strategy you'd build a 3-second backlog in 1 second, causing severe latency.
