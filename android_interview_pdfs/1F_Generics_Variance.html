1F — Generics & Variance

Generics, in/out variance annotations, covariance, contravariance — the type-system mechanics behind Flow, StateFlow, Result, and Clean Architecture generics.

ID: 1F ⭐ Tier 1
🔍
1. Overview

What it is

Generics let you write type-safe code that works with multiple types without duplication. Variance (in/out) controls how generic types relate when their type parameters are in a subtype relationship — determining whether List<Dog> can be used as a List<Animal>.

Why it matters for Android

  • Flow<T>, StateFlow<T>, Result<T>, LiveData<T> are all generic — understanding variance explains why StateFlow<UiState> is safe to assign to Flow<UiState>.
  • BaseUseCase<in P, out R> — the variance annotations are meaningful and necessary.
  • Repository generics: Resource<T>, ApiResult<T> — you need to design these correctly.
  • Compose: @Composable functions with generic state types.
Senior Mental Model
out T (covariant) = T only comes OUT (returned). Safe to read, not write. A Producer<Dog> IS-A Producer<Animal>.
in T (contravariant) = T only goes IN (consumed). Safe to write, not read. A Consumer<Animal> IS-A Consumer<Dog>.
Invariant (no annotation) = T both in and out. No subtype relationship. MutableList<Dog> is NOT a MutableList<Animal>.
⚙
2. How It Works

Basic Generics

// Generic function
fun <T> wrapInResult(value: T): Result<T> = Result.success(value)

// Generic class
class Box<T>(val value: T)

// Multiple type params
class Pair<A, B>(val first: A, val second: B)

// Upper bound constraint
fun <T : Comparable<T>> max(a: T, b: T): T = if (a > b) a else b

// Multiple bounds — use where
fun <T> process(item: T) where T : Serializable, T : Comparable<T> { }

The Variance Problem — Why Invariance Exists

// Dogs are Animals — OK
val dog: Animal = Dog()  // fine

// But MutableList<Dog> is NOT a MutableList<Animal> — why?
val dogs: MutableList<Dog> = mutableListOf(Dog())
// val animals: MutableList<Animal> = dogs  // ❌ compile error

// If it were allowed:
// animals.add(Cat())  // would corrupt the dogs list!
// dogs[0] is now a Cat — type safety broken

This is why generic types are invariant by default — to prevent type-unsafe writes.

out T — Covariance (Producer)

// out T: T only appears in OUT position (return type / val)
interface Producer<out T> {
    fun produce(): T   // ✅ T in out position
    // fun consume(item: T)  // ❌ compile error: T in in-position
}

val dogProducer: Producer<Dog> = DogFactory()
val animalProducer: Producer<Animal> = dogProducer  // ✅ safe — can only read

// Real example: Flow is covariant
val dogFlow: Flow<Dog> = flowOf(Dog())
val animalFlow: Flow<Animal> = dogFlow  // ✅ Flow<out T>

in T — Contravariance (Consumer)

// in T: T only appears in IN position (parameter)
interface Consumer<in T> {
    fun consume(item: T)   // ✅ T in in-position
    // fun produce(): T     // ❌ T in out-position — not allowed
}

val animalConsumer: Consumer<Animal> = AnimalPrinter()
val dogConsumer: Consumer<Dog> = animalConsumer  // ✅ Animal consumer can handle Dog

// Real example: Comparator is contravariant
val animalComparator: Comparator<Animal> = compareBy { it.name }
val dogComparator: Comparator<Dog> = animalComparator  // ✅ works

Declaration-site vs Use-site Variance

// Declaration-site: variance on the class/interface itself
interface Flow<out T>   // covariant — defined by the library

// Use-site: variance at the call site (type projection)
fun copy(from: Array<out Animal>, to: Array<Animal>) {
    // 'from' is projected — can only read from it
    for (item in from) to[0] = item
}
// Array is invariant, but use-site 'out' projects it to read-only

Star Projection *

// * = "I don't know the type parameter"
fun printList(list: List<*>) {
    list.forEach { println(it) }  // elements are Any? — read-only
}
// Equivalent to List<out Any?> for reading
// Cannot add elements — type unknown

Key Terms Summary

Nothing and Any? in variance

// Nothing is a subtype of everything — bottom type
data object Loading : UiState<Nothing>()
// With UiState<out T>, Loading (UiState<Nothing>) is assignable to UiState<Any>

// Any? is supertype of everything — top type
fun <T : Any> nonNull(value: T): T = value  // T is non-nullable

3. Why and When to Use It

Real Android Use Cases

SituationVariance usedWhy
Flow<out T>CovariantFlow only emits (produces) T — safe to assign Flow<Dog> to Flow<Animal>
StateFlow<out T>CovariantSame — value is read-only from the outside
BaseUseCase<in P, out R>Contravariant P, Covariant RP is consumed (input), R is produced (output)
sealed class UiState<out T>CovariantAllows UiState.Loading : UiState<Nothing> to be used as UiState<SomeData>
Resource<T> wrapperCovariantResource only wraps and exposes data — never mutates it
Generic RepositoryInvariant (usually)Both reads and writes needed

When NOT to annotate variance

Do NOT
  • Add out if T appears in a function parameter — compile error
  • Add in if T appears as a return type — compile error
  • Use * when you know the type — use the concrete type or bound instead
  • Over-engineer variance for simple use cases — most app-level classes don't need it

4. Production Example
Scenario
Banking app — generic result wrapper, covariant UiState, contravariant use case base — all in Clean Architecture.

Covariant UiState — Loading works for any T

// domain/state/UiState.kt
sealed class UiState<out T> {           // out T: only produced, never consumed
    data object Loading : UiState<Nothing>()   // Nothing = valid subtype of any T
    data class  Success<T>(val data: T) : UiState<T>()
    data class  Error(val msg: String) : UiState<Nothing>()
}

// Because UiState is covariant:
val state: UiState<List<Transaction>> = UiState.Loading  // ✅
val state2: UiState<UserProfile> = UiState.Loading       // ✅ same Loading instance

Covariant Flow — StateFlow assignable to Flow

// presentation/TransactionViewModel.kt
@HiltViewModel
class TransactionViewModel @Inject constructor(
    private val getTransactions: GetTransactionsUseCase
) : ViewModel() {

    private val _uiState = MutableStateFlow<UiState<List<Transaction>>>(UiState.Loading)

    // Exposed as Flow — safe because StateFlow is covariant (out T)
    val uiState: StateFlow<UiState<List<Transaction>>> = _uiState.asStateFlow()
    // Could also expose as Flow<UiState<...>> — valid because Flow<out T>
}

Generic BaseUseCase with in/out

// domain/usecase/BaseUseCase.kt
abstract class BaseUseCase<in P, out R> {
    // P is consumed (input param) → in P
    // R is produced (return value) → out R
    protected abstract suspend fun execute(params: P): R

    suspend operator fun invoke(params: P): Result<R> = try {
        Result.success(execute(params))
    } catch (e: CancellationException) { throw e }
      catch (e: Exception) { Result.failure(e) }
}

// Usage: P=String (userId), R=UserProfile
class GetUserProfileUseCase @Inject constructor(
    private val repo: UserRepository
) : BaseUseCase<String, UserProfile>() {
    override suspend fun execute(params: String) = repo.getUser(params)
}

Generic ApiResult wrapper

// data/remote/ApiResult.kt
sealed class ApiResult<out T> {
    data class  Success<T>(val data: T) : ApiResult<T>()
    data class  HttpError(val code: Int, val message: String) : ApiResult<Nothing>()
    data class  NetworkError(val cause: Throwable) : ApiResult<Nothing>()
    data object Loading : ApiResult<Nothing>()
}

// Map the data while preserving error cases
fun <T, R> ApiResult<T>.map(transform: (T) -> R): ApiResult<R> = when (this) {
    is ApiResult.Success      -> ApiResult.Success(transform(data))
    is ApiResult.HttpError    -> this
    is ApiResult.NetworkError -> this
    ApiResult.Loading          -> ApiResult.Loading
}

5. Alternatives & Trade-offs
ApproachProsConsWhen to pick
Invariant generic (default)Simple, safe, no annotationNo subtype flexibilityMutable containers, classes with both reads + writes
out T (covariant)Subtype flexibility for producersCannot accept T as inputRead-only wrappers: Flow, UiState, Result, ApiResult
in T (contravariant)Supertype flexibility for consumersCannot return TConsumers: Comparator, event sinks, callbacks
Use-site variance (Array<out T>)Project invariant types read-only at call siteVerbose; type projection loses write capabilityWhen working with Java invariant types like Array
Star projection *Works when type unknownLoses type info; can only read as Any?Logging, reflection, type-erasure scenarios

Interviewer Comparisons

Expect These
  • Java wildcards vs Kotlin variance — Java uses ? extends T (covariant) and ? super T (contravariant) at use-site. Kotlin uses out/in at declaration-site (cleaner) or use-site projection.
  • List vs MutableList variance — List<out T> is covariant (read-only). MutableList<T> is invariant (read+write).
  • Flow vs StateFlow vs SharedFlow — all are out T covariant; StateFlow is a subtype of Flow, which is why it can be assigned to a Flow reference.

6. Pitfalls & Best Practices

out T with mutable state — type safety violation attempt

// ❌ Won't compile — correctly rejected by the compiler
class BadBox<out T>(var value: T) // ❌ var exposes T in in-position (setter)

// ✅ GOOD — val only for covariant types
class Box<out T>(val value: T)   // ✅ read-only property

Forgetting Nothing for no-data sealed subtypes

// ❌ BAD — UiState.Loading has type param UiState<Unit> — awkward
sealed class UiState<out T> {
    object Loading : UiState<Unit>()   // Unit — leaks into type signature
}
val s: UiState<List<User>> = UiState.Loading  // ❌ won't compile
// ✅ GOOD — Nothing is subtype of every type; works with covariant out T
data object Loading : UiState<Nothing>()
val s: UiState<List<User>> = UiState.Loading  // ✅

Type erasure at runtime

// ❌ BAD — generic type erased at runtime
fun <T> isListOf(list: List<*>): Boolean = list is List<T>  // ❌ unchecked cast warning

// ✅ GOOD — use reified with inline (covered in 1I)
inline fun <reified T> isListOf(list: List<*>): Boolean =
    list.all { it is T }

Production Best Practices

  1. Use out T for read-only wrappers: UiState<out T>, ApiResult<out T>, Resource<out T>.
  2. Use Nothing as type arg for no-data sealed subtypes — allows assignment to any covariant generic.
  3. Expose StateFlow as StateFlow (not Flow) in ViewModels — provides .value access; covariance means it's still assignable to Flow when needed.
  4. Don't over-annotate — most application-level classes are invariant and that's fine.
  5. Use where T : SomeInterface for multiple type bounds instead of complex inheritance.

7. Interview Answer Framework

30-Second Answer

"Generics let you write type-safe code that works across multiple types. Variance controls how generic types relate under subtyping. out T means covariant — T is only produced, never consumed, so Producer<Dog> is safely assignable to Producer<Animal>. in T means contravariant — T is only consumed, so Consumer<Animal> works as a Consumer<Dog>. This is why Flow<out T> allows StateFlow<T> to be used as a Flow<T>, and why I annotate UiState<out T> so UiState.Loading : UiState<Nothing> works for any state type."

2-Minute Structured Answer

"The core question variance answers is: if Dog is a subtype of Animal, is Box<Dog> a subtype of Box<Animal>? By default, no — because if it were, you could write a Cat into a Dog box.

out T (covariant) makes it safe by restricting T to output positions only — return types and val properties. You can only read T, never write it. So Producer<Dog> is safe as Producer<Animal> — you can only get animals out, and dogs are animals.

in T (contravariant) restricts T to input positions only. A Consumer<Animal> can handle dogs since dogs are animals — so Consumer<Animal> works as Consumer<Dog>.

In my Android code: I annotate all read-only result wrappers — UiState<out T>, ApiResult<out T> — as covariant. This lets me use Nothing as the type arg for no-data states like Loading, which then satisfies any UiState<SomeDataType> requirement. This is exactly how Kotlin's built-in Flow<out T> works — StateFlow is a subtype of Flow because of covariance."

Must-Mention Points

1
Generic types are invariant by default — MutableList<Dog> is NOT a MutableList<Animal>
2
out T = covariant = T only in output positions = producer; subtype relationship follows type param
3
in T = contravariant = T only in input positions = consumer; subtype relationship reverses
4
Flow<out T> — that's why StateFlow<T> is assignable to Flow<T>
5
Nothing is the bottom type — subtype of everything; enables UiState.Loading : UiState<Nothing> to satisfy any UiState<T> with covariance
6
Declaration-site variance (on the class) is cleaner than use-site projection (on each call site)

  • JVM type erasure and how generics are implemented at bytecode level

Say This
"The practical payoff of understanding variance in Android is the UiState<out T> + Nothing pattern. By making UiState covariant, a single data object Loading : UiState<Nothing> satisfies every screen's state type — UiState<List<Transaction>>, UiState<UserProfile>, whatever. 9. Interview Questions (Self-Check)
How to use
Answer first, then reveal.

Basic

B1 — What does it mean for a generic type to be invariant? Give an Android example.
Easy▼
Invariant means no subtype relationship exists between generic types even if their type arguments have a subtype relationship. MutableList<Dog> is NOT a subtype of MutableList<Animal>, even though Dog extends Animal. This prevents type-unsafe mutations: if it were allowed, you could add a Cat to a list that was expected to contain only Dogs. Android example: MutableStateFlow<UiState> — invariant because it supports both reads and writes.
B2 — What does out T mean? Give a real Kotlin/Android example.
Easy▼
out T declares covariance — T appears only in output positions (return types, val properties). This means if Dog is a subtype of Animal, then Producer<Dog> is a subtype of Producer<Animal>.

Real example: Flow<out T> in Kotlin coroutines. Because Flow is covariant, StateFlow<Dog> (which extends Flow<Dog>) can be assigned to a Flow<Animal> variable. Also: List<out T> is covariant because it's read-only — no add() method takes T as a parameter.
B3 — What is Nothing and why is it used with covariant sealed classes?
Easy▼
Nothing is Kotlin's bottom type — a subtype of every type. No instance of Nothing can be created. Because of covariance: if Nothing is a subtype of T, and UiState is covariant (out T), then UiState<Nothing> is a subtype of UiState<T> for ANY T. This means data object Loading : UiState<Nothing> is assignable to UiState<List<Transaction>>, UiState<UserProfile>, etc. — one Loading object works for all generic types.

Intermediate

I1 — Why is List covariant but MutableList invariant in Kotlin?
Medium▼
List<out T> is read-only — it has no add(T) or set(T) methods. T only appears in output positions (get, iterator, etc.). Because it can never be used to write a T, it's safe to treat a List<Dog> as a List<Animal> — you can only read animals from it, and dogs are animals.

MutableList<T> has add(T) where T is in an input position. If it were covariant, you could assign a MutableList<Dog> to MutableList<Animal> and call add(Cat()) — corrupting the dog list. Invariance prevents this.
I2 — (Coding) Why won't this compile? How do you fix it?
MediumCoding▼
class Box<out T>(var value: T)  // ❌
Problem: var value: T generates a setter that takes T as a parameter — an input position. out T restricts T to output positions only. The setter violates this, so the compiler rejects it.

Fix: Use val instead of var: 
class Box<out T>(val value: T)  // ✅ val = getter only = out position
I3 — What is declaration-site variance vs use-site variance? Which does Kotlin prefer?
Medium▼
Declaration-site variance: annotate the class/interface once — class Flow<out T>. Every usage site automatically gets the covariance. Kotlin-idiomatic.

Use-site variance (type projection): annotate at each call site — fun copy(src: Array<out T>). Used when the class itself can't be annotated (e.g., invariant Java classes like Array).

Kotlin prefers declaration-site — less repetition, clearer intent. Java only has use-site wildcards (? extends T, ? super T). Kotlin supports both but declaration-site is idiomatic for your own code.
I4 — What is contravariance? Give a real Android/Kotlin use case.
Medium▼
Contravariance (in T): T appears only in input positions. The subtype relationship is reversed — Consumer<Animal> is a subtype of Consumer<Dog> because a consumer that can handle animals can certainly handle dogs.

Real Kotlin example: Comparator<in T>. A Comparator<Animal> that compares by name can be used to sort a list of dogs — dogs are animals, so the comparator works. You can pass an animalComparator wherever a dogComparator is needed.

Android example: BaseUseCase<in P, out R> — the params type P is consumed (input), so contravariant; the result R is produced (output), so covariant.

Senior / Scenario

S1 — Design a generic Resource<T> sealed class for the data layer. Justify the variance annotation.
HardCoding▼
sealed class Resource<out T> {           // out T: only produced, never consumed
    data class  Success<T>(val data: T) : Resource<T>()
    data class  Error(val exception: Throwable) : Resource<Nothing>()
    data object Loading : Resource<Nothing>()
}

// Extension to transform the data
fun <T, R> Resource<T>.map(f: (T) -> R): Resource<R> = when (this) {
    is Resource.Success -> Resource.Success(f(data))
    is Resource.Error   -> this
    Resource.Loading    -> Resource.Loading
}
Justification: out T because Resource only wraps and exposes data — it never accepts T as input anywhere. This allows: (1) Resource.Loading and Resource.Error with Nothing to satisfy any Resource<T>; (2) a Resource<Dog> to be assigned to Resource<Animal> when the consuming code only reads.
S2 — (Scenario) A teammate asks: "Why can I assign a StateFlow<UiState> to a Flow<UiState> variable but not a MutableStateFlow to a MutableSharedFlow?" Explain.
HardScenario▼
StateFlow → Flow is valid because both are declared as interface Flow<out T> and interface StateFlow<out T> : Flow<T>. StateFlow IS-A Flow — it extends it. The covariance (out T) isn't even needed here; it's a direct subtype relationship via interface inheritance.

MutableStateFlow → MutableSharedFlow is invalid because MutableStateFlow and MutableSharedFlow are separate interfaces in different parts of the hierarchy. MutableStateFlow<T> extends both StateFlow<T> and MutableSharedFlow<T>, so a MutableStateFlow IS-A MutableSharedFlow — actually this assignment IS valid. If it fails in practice it may be a generics invariance issue with a specific type argument.

The key insight: variance enables subtype relationships based on type params. Direct interface inheritance enables them based on the class hierarchy. Both matter.
S3 — When would you use star projection * vs a bounded type parameter vs a concrete type?
Hard▼
Concrete type (List<String>): use when you know and care about the exact type at compile time. Most common case.

Bounded type parameter (<T : Serializable>): use when you don't know the exact type but need it to satisfy a constraint. The type is known within the function scope. Use this for generic utility functions.

Star projection (List<*>): use when you truly don't care about the type and only need to work with the container, not the elements — e.g., logging a list's size, checking if it's empty, or passing to a reflection API. Elements read as Any?. Cannot write. Use sparingly — it loses type information.
