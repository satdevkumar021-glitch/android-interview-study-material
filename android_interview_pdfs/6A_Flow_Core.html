6A — Flow Core

Cold Flow vs hot StateFlow vs hot SharedFlow. collect vs collectLatest. The definitive StateFlow vs SharedFlow vs LiveData comparison. Most-asked Flow questions.

ID: 6A ⭐ Tier 1 🔥 Highest Priority
🔍
1. Overview

Three Flow types

  • Flow<T> — cold: does nothing until collected; each collector gets its own independent execution; like a function that you call
  • StateFlow<T> — hot: always has a value; emits current state to new collectors immediately; single shared execution; like a property
  • SharedFlow<T> — hot: configurable replay buffer; multi-cast; for events like navigation, one-time UI messages; like a broadcast

Cold vs hot — the key mental model

Cold: the flow block runs fresh for each collector. Think of it as a lazy factory — no work until you call collect(). If two collectors subscribe, the upstream runs twice, independently.

Hot: the source runs regardless of collectors. A collector joining late gets the current/recent state. StateFlow and SharedFlow are hot — they exist independently of any collector.

Senior Mental Model
Flow = cold = pull model. StateFlow/SharedFlow = hot = push model. Repository functions should return cold Flow<T> (each collection triggers a new network/db request). ViewModels should expose hot StateFlow<UiState> (the current UI state always exists, new subscribers get it immediately without re-triggering the data source).
⚙
2. How It Works

Cold Flow — runs per collector

// Cold: each collect() runs the block independently
fun userFlow(): Flow<User> = flow {
    println("Fetching user...")  // runs for EACH collector
    val user = api.getUser()
    emit(user)
}

val f = userFlow()
// Nothing has run yet! No network call.
f.collect { println(it) }  // NOW fetches — prints "Fetching user..."
f.collect { println(it) }  // fetches AGAIN — second independent call

StateFlow — hot, always has value

// StateFlow: always has a value, replays current value to new collectors
private val _state = MutableStateFlow(UiState.Loading)
val state: StateFlow<UiState> = _state.asStateFlow()

// Collector 1 subscribes now — gets Loading immediately
state.collect { render(it) }

// 2 seconds later, data arrives:
_state.value = UiState.Success(data)

// Collector 2 subscribes NOW — gets Success immediately (current value)
state.collect { render(it) }  // gets Success(data) right away

// StateFlow uses equals() to deduplicate — won't emit same value twice
_state.value = UiState.Success(data)  // IGNORED if data == existing value

SharedFlow — hot, configurable

// SharedFlow: for one-time events (navigation, snackbar, dialogs)
private val _events = MutableSharedFlow<UiEvent>(
    replay = 0,         // no replay — events not re-sent to late collectors
    extraBufferCapacity = 1  // buffer 1 event if no collector
)
val events: SharedFlow<UiEvent> = _events.asSharedFlow()

fun showError(msg: String) {
    viewModelScope.launch {
        _events.emit(UiEvent.ShowSnackbar(msg))
    }
}

collect vs collectLatest

// collect: processes EVERY emission — blocks until lambda completes
flow.collect { value ->
    expensiveOperation(value)  // new value waits until this finishes
}

// collectLatest: cancels previous lambda when new emission arrives
flow.collectLatest { value ->
    delay(300)                   // if new value arrives during delay,
    expensiveOperation(value)  // this run is CANCELLED
}
// Use collectLatest for search queries — only process the latest input

SharedFlow: navigation commands, snackbars, dialogs — one-time events that should NOT be replayed on config change.

4. Production Example

E-commerce: product screen with state + events

class ProductViewModel(
    private val repo: ProductRepository
) : ViewModel() {

    // StateFlow: UI state (always has a value)
    private val _uiState = MutableStateFlow<ProductUiState>(ProductUiState.Loading)
    val uiState: StateFlow<ProductUiState> = _uiState.asStateFlow()

    // SharedFlow: one-time events (no replay)
    private val _events = MutableSharedFlow<ProductEvent>(extraBufferCapacity = 1)
    val events: SharedFlow<ProductEvent> = _events.asSharedFlow()

    fun loadProduct(id: String) {
        viewModelScope.launch {
            // collectLatest: if a new load() is called while loading,
            // cancel the previous and start fresh
            repo.getProduct(id)  // returns cold Flow from Room
                .collect { product ->
                    _uiState.value = ProductUiState.Success(product)
                }
        }
    }

    fun addToCart(productId: String) {
        viewModelScope.launch {
            try {
                cartRepo.add(productId)
                _events.emit(ProductEvent.ShowSnackbar("Added to cart"))
            } catch (e: Exception) {
                _events.emit(ProductEvent.ShowError(e.message!!))
            }
        }
    }
}

// Fragment collection (safe lifecycle)
override fun onViewCreated(view: View, saved: Bundle?) {
    viewLifecycleOwner.lifecycleScope.launch {
        viewLifecycleOwner.lifecycle.repeatOnLifecycle(Lifecycle.State.STARTED) {
            launch { viewModel.uiState.collect { renderState(it) } }
            launch { viewModel.events.collect { handleEvent(it) } }
        }
    }
}

One-Time Events Pattern
For navigation/snackbar events, use SharedFlow(replay=0, extraBufferCapacity=1, onBufferOverflow=DROP_OLDEST). replay=0 means rotating the device won't replay the navigation event. extraBufferCapacity=1 means if no one is collecting (e.g., activity in background), one event is buffered rather than suspending the ViewModel.

6. Pitfalls & Best Practices
Pitfall 1 — StateFlow for events
Using StateFlow for one-time UI events (navigation, snackbar) causes the event to replay on configuration change — the user sees the navigation happen again or the snackbar re-appears. Use SharedFlow(replay=0) for events.
Pitfall 2 — Missing StateFlow deduplication
StateFlow uses equals() to check if a new value differs from the current. If your state class doesn't implement equals() correctly (e.g., a regular class, not a data class), StateFlow may silently drop updates. Always use data classes for state.
Pitfall 3 — Collecting Flow in ViewModel
Calling flow.collect { } inside a ViewModel is usually wrong — it creates an infinite suspension that never returns. Use stateIn() or shareIn() to convert a Flow to a StateFlow/SharedFlow that the ViewModel exposes. (See 6D for stateIn/shareIn.)
Best Practice — Expose StateFlow, not MutableStateFlow
Always expose the read-only StateFlow<T> interface: val state: StateFlow<T> = _state.asStateFlow(). The UI should never mutate state directly. Only the ViewModel mutates via _state.value = ... or _state.update { ... }.

7. Interview Framework

30-second answer

"Flow is cold — it does nothing until collected, and each collector gets its own execution. StateFlow is hot — it always has a current value and replays it to new collectors; perfect for ViewModel UI state. SharedFlow is hot with configurable replay — for one-time events like navigation where replay=0 prevents re-triggering on config change."

2-minute answer

"The cold vs hot distinction is fundamental. Cold Flow is a factory — calling collect() triggers a fresh execution, so two collectors each trigger their own network/database call. This is correct for repositories. Hot StateFlow/SharedFlow exist independently of collectors — they have ongoing state.

StateFlow is specifically designed for UI state: it requires an initial value, uses equals() deduplication so the same state isn't re-rendered, and always replays the current value to new subscribers. When Compose recomposition happens or a Fragment is re-attached, it immediately gets the current state without triggering a new data fetch.

SharedFlow is for events — things that happen once. For navigation commands, set replay=0 so a device rotation doesn't re-navigate. For the collect vs collectLatest choice: use collectLatest for search — cancel processing the previous query when a new keystroke arrives."

Must-mention points

1
Cold Flow: each collector triggers fresh execution; hot StateFlow/SharedFlow: shared execution
2
StateFlow deduplicates using equals() — data class states are required
3
SharedFlow replay=0 for events — prevents replay on config change
4
collectLatest cancels previous when new emission arrives — use for search/debounce
5
Always expose StateFlow (not MutableStateFlow) from ViewModel

Follow-up Q&A

Q: "When would you use SharedFlow over StateFlow?"

A: When the data represents an event, not state. State = what the UI should currently show (always relevant, can be replayed). Event = something that happened once (navigation, show snackbar, play sound — should not re-happen on config change). SharedFlow with replay=0 models this correctly; StateFlow would re-trigger the event every time a new subscriber joins.

Q: "How does StateFlow handle equals()?"

A: StateFlow uses structural equality (==) to decide whether to emit. If the new value equals the current value, the emission is dropped. For data classes, this is automatic. For custom classes without equals(), all updates emit. This deduplication is important for performance — you don't want to recompose the UI for an identical state.

Senior insight

Senior Insight
In banking apps where UI state includes balance data, StateFlow deduplication can cause bugs if the balance wrapper doesn't override equals() correctly. A data class BalanceState(val amount: BigDecimal, val lastUpdated: Instant) — even if amount hasn't changed, a new lastUpdated will trigger a re-render. Design state classes carefully: include only data that should trigger a render when it changes.

9. Interview Questions
What is the difference between a cold and hot Flow?
Basic⌄
Cold Flow: the block runs fresh for each collector — nothing executes until collect() is called. Each collector gets its own independent execution. Hot Flow (StateFlow/SharedFlow): runs independently of collectors, always producing values. New collectors get the current/recent values without triggering a new execution.
What is StateFlow and what makes it different from a regular Flow?
Basic⌄
StateFlow is a hot flow that always holds a current value (requires an initial value). It replays the current value to every new subscriber. It uses equals() to deduplicate — if you set the same value again, no emission occurs. Unlike regular Flow, it's multicast — multiple collectors share one execution. It's the recommended ViewModel UI state holder in Android.
When would you use SharedFlow instead of StateFlow?
Basic⌄
Use SharedFlow for one-time events that should not be replayed on configuration changes: navigation commands, showing snackbars, triggering dialogs, playing sounds. With replay=0, rotating the device won't re-trigger the event. StateFlow would replay the current value to every new collector — wrong for events.
What is the difference between collect and collectLatest?
Intermediate⌄
collect processes every emission sequentially — if the lambda takes time, the next emission waits. collectLatest cancels the current lambda when a new emission arrives and starts fresh with the new value. Use collectLatest for search queries (only process the latest keystroke), live updates where only the freshest value matters.
Why should you always use data classes for StateFlow state objects?
Intermediate⌄
StateFlow uses equals() for deduplication. Data classes auto-generate structural equals() — two instances with the same fields are equal, so updating state to the same values won't trigger unnecessary recompositions. Regular classes don't override equals(), so every assignment emits even if nothing changed, causing unnecessary UI updates. Also, data classes support copy() for immutable updates.
A cold Flow is collected from two places in the UI simultaneously. What happens?
Intermediate⌄
Each collector starts an independent execution of the flow's block — two network/database calls happen. This is correct for some use cases (e.g., two independent widgets both need the latest price) but often undesirable (duplicate network calls, inconsistent data). The fix is to convert the cold Flow to a hot StateFlow using stateIn() in the ViewModel — then both collectors share one upstream execution.
Why should you expose StateFlow<T> instead of MutableStateFlow<T> from a ViewModel?
Intermediate⌄
Encapsulation. MutableStateFlow exposes .value as settable — any code that gets the reference can modify state. This breaks the UDF (Unidirectional Data Flow) principle where state should only flow down from the ViewModel. Expose val state: StateFlow<T> = _state.asStateFlow() — read-only, the UI can only observe, never write.
Your ViewModel navigation event fires twice after a screen rotation. What is the root cause and fix?
Senior⌄
Root cause: the event is stored in a StateFlow or a SharedFlow with replay > 0. After rotation, the new collector immediately receives the last emitted event and triggers navigation again. Fix: use MutableSharedFlow(replay=0) for events. replay=0 means new collectors don't receive past events. Also ensure collection is inside repeatOnLifecycle(STARTED) so the collector is recreated, not just a stale collector receiving past buffered events.
Compare StateFlow with LiveData — when would you still use LiveData in 2024?
Senior⌄
StateFlow advantages over LiveData: fully coroutine-native, no Android framework dependency (testable without AndroidX), richer operator chain (map, filter, combine), works with Flow operators. LiveData advantages: built-in lifecycle awareness (no repeatOnLifecycle boilerplate), automatic dispatch to main thread. In 2024, prefer StateFlow + collectAsStateWithLifecycle() for all new code. LiveData is acceptable in legacy XML-view code where the automatic lifecycle handling reduces boilerplate, or in Room queries that you don't want to migrate.
Design the state and event architecture for a checkout screen that has: loading state, form validation errors, a payment processing state, and a navigation-to-confirmation event.
Senior⌄
Use a sealed state class in StateFlow: sealed class CheckoutState { object Loading; data class Form(val errors: List<Error>, val isSubmitting: Boolean); object Success }. For navigation event: SharedFlow<CheckoutEvent>(replay=0, extraBufferCapacity=1) where CheckoutEvent.NavigateToConfirmation(orderId). The distinction: state represents what the screen should currently show (StateFlow replaying current state on rotation is correct). Navigation event should NOT replay — use SharedFlow replay=0 to prevent duplicate navigation after rotation.
