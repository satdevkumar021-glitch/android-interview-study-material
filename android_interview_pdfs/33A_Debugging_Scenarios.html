33A — Debugging Scenarios

Six production debugging scenarios with root cause analysis, fixes, and prevention strategies. Each scenario: Problem → Clarifying Questions → Root Cause → Solution → Prevention.

ID: 33A ⭐ Senior Differentiator

1. Overview

Debugging Framework (use in interviews)

  1. Clarify: Ask when does it happen? Always or sometimes? Which devices? Which Android version? After rotation?
  2. Hypothesize: Form 2–3 root cause hypotheses based on symptoms
  3. Investigate: Name the tool you'd use (Logcat, Profiler, Compose metrics, LeakCanary)
  4. Root cause: Identify the exact cause
  5. Fix: Describe the code change
  6. Prevent: What process/pattern prevents this class of bug in future
Senior Signal
Juniors describe what happened. Seniors diagnose WHY it happened and add a prevention step. Always end your scenario answer with: "To prevent this in future, I would..."

2. API Called Twice After Rotation
1
Network call fires twice every time the screen rotates
Problem

User rotates the device. The loading indicator appears briefly, network call is made again, UI flickers. Happens every rotation.

Clarifying Questions
  • Is the network call in a ViewModel or in the Fragment/Activity directly?
  • Where exactly is the call triggered — onCreate, onStart, or in init?
  • Is it a Fragment or Activity?
Root Cause

The API call is made in Activity.onCreate() or Fragment.onViewCreated() directly — not in a ViewModel. On rotation, the Activity/Fragment is destroyed and recreated, so onCreate() runs again, triggering a new network call.

Solution
// ❌ Wrong — call in Activity/Fragment lifecycle
override fun onCreate(savedInstanceState: Bundle?) {
    super.onCreate(savedInstanceState)
    viewModel.loadUser()   // called AGAIN on every rotation
}

// ✅ Correct — call in ViewModel init{} (survives rotation)
class UserViewModel @Inject constructor(
    private val repo: UserRepository
) : ViewModel() {

    val userState = MutableStateFlow<UiState<User>>(UiState.Loading)

    init {
        loadUser()  // called ONCE; ViewModel survives rotation
    }

    private fun loadUser() = viewModelScope.launch {
        userState.value = UiState.Loading
        userState.value = repo.getUser().fold(
            onSuccess = { UiState.Success(it) },
            onFailure = { UiState.Error(it.message) }
        )
    }
}

// Fragment observes — not triggers
viewLifecycleOwner.lifecycleScope.launch {
    repeatOnLifecycle(Lifecycle.State.STARTED) {
        viewModel.userState.collect { renderState(it) }
    }
}
Prevention
  • Code review rule: no network calls in Fragment/Activity lifecycle methods
  • All data loading happens in ViewModel init{} or in response to user actions

3. Compose Screen Continuously Recomposes
2
Compose screen flickers or Profiler shows constant recompositions
Problem

UI is janky. Compose Profiler shows 60+ recompositions per second even with no user interaction. Frame rate drops under scroll.

Clarifying Questions
  • What type is being passed as a parameter to the composable? Is it a List or custom class?
  • Are lambdas captured from the composition scope?
  • Is there a State that is being updated on every frame?
Root Cause

The composable parameter is an unstable type — Compose can't determine if it's changed, so it recomposes every time the parent recomposes. Common causes: passing a plain List<T> (mutable, considered unstable), a class without @Stable/@Immutable, or inline lambdas that are recreated every composition.

Solution
// ❌ Unstable — List is mutable, Compose marks it unstable
@Composable
fun FeedList(items: List<FeedItem>) { ... }

// ✅ Option 1: Wrap with ImmutableList (kotlinx.collections.immutable)
@Composable
fun FeedList(items: ImmutableList<FeedItem>) { ... }

// ✅ Option 2: Mark domain class @Immutable
@Immutable
data class FeedItem(val id: String, val title: String)

// ✅ Option 3: Wrapper class marked @Immutable
@Immutable
data class FeedUiState(val items: List<FeedItem> = emptyList())

// For lambdas — hoist out of composition or use remember
// ❌ New lambda instance every recomposition
FeedItem(onClick = { viewModel.onItemClick(item.id) })

// ✅ Stable lambda with rememberUpdatedState or function reference
val onClick = remember(item.id) { { viewModel.onItemClick(item.id) } }
Tools
  • Compose compiler metrics: freeCompilerArgs += "-P", "plugin:androidx.compose.compiler.plugins.kotlin:metricsDestination=..." — shows stable/unstable/skippable per class
  • Layout Inspector recomposition counts in Android Studio
Prevention
  • Mark all domain/UI state classes with @Immutable or use ImmutableList
  • Enable Compose compiler metrics in CI to catch unstable types before they merge

4. App Crashes Only in Production
3
ClassNotFoundException or NullPointerException in production, not in debug
Problem

Crashlytics shows a crash affecting 3% of users. Stack trace points to a JSON parsing method. Works perfectly in debug and staging builds.

Clarifying Questions
  • Is minifyEnabled=true only in release builds?
  • Are any data classes used with Gson/Moshi for JSON parsing?
  • Was a new model class added recently without corresponding keep rules?
Root Cause

Missing R8 keep rules: R8 removed or renamed a data class used for JSON deserialization. Gson uses reflection to map JSON fields to class fields. When R8 renames userAddress to a, Gson can't find the field → NullPointerException or wrong data.

Solution
// Option 1: Add keep rule in proguard-rules.pro
-keep class com.myapp.data.model.** { *; }
-keepclassmembers class com.myapp.data.model.** { *; }

// Option 2: Annotate with @Keep
@Keep
data class UserDto(
    @SerializedName("user_address")
    val address: String
)

// Option 3: Switch to kotlinx.serialization (works with R8 without keep rules)
@Serializable
data class UserDto(val address: String)

// Debug the crash in release mode locally:
// adb shell setprop debug.viewAttributeInspectionEnabled true
// Or build a release APK locally and install via adb install -r app-release.apk
Other Causes of Prod-only Crashes
  • Different API levels — test against minimum supported API on a real device or emulator
  • Missing exception handling for edge cases that only occur with real data
  • Race conditions that only manifest under production load
Prevention
  • Run a release build smoke test before every production push
  • Add tests that instantiate all model classes via the serialization library
  • Use kotlinx.serialization instead of Gson — no reflection at runtime

5. App Startup Takes 5 Seconds
4
Cold start time is 5 seconds — users complain about slow launch
Problem

Firebase Performance shows p50 cold start = 5.2s. Target is <2s. App shows blank white screen for 3+ seconds before content appears.

Clarifying Questions
  • What SDK initializations happen in Application.onCreate()?
  • Is there any synchronous disk I/O or network call during startup?
  • How large is the database being opened at startup?
Root Cause Analysis

Common causes: (1) Heavy SDK init in Application.onCreate() — each SDK adding 100–300ms; (2) Blocking I/O on main thread — database open, SharedPreferences read, file access; (3) Synchronous network call before showing UI; (4) Large Activity/Fragment inflation with complex view hierarchy.

Solution
// ❌ Blocking Application.onCreate()
class App : Application() {
    override fun onCreate() {
        super.onCreate()
        Firebase.initializeApp(this)           // ok - fast
        heavyDatabase.initialize(this)       // ❌ blocking, 800ms
        analyticsLibrary.init(this)           // ❌ blocking, 400ms
        legacySharedPrefs.loadAll(this)      // ❌ disk I/O on main thread
    }
}

// ✅ App Startup library for lazy, ordered initialization
class AnalyticsInitializer : Initializer<Unit> {
    override fun create(context: Context) {
        // Runs on background thread via WorkManager startup
        analyticsLibrary.init(context)
    }
    override fun dependencies() = emptyList<Class<out Initializer<*>>>()
}

// ✅ Lazy inject: Room DB not opened until first query
val database: AppDatabase by lazy {
    Room.databaseBuilder(appContext, AppDatabase::class.java, "app.db").build()
}

// ✅ Baseline Profile — pre-compile critical startup code paths
// Generate with Macrobenchmark BaselineProfileRule
// Reduces JIT compilation overhead at startup by 30-40%
Measurement Tools
  • adb shell am start-activity -W — measures Time To Initial Display (TTID)
  • Android Studio Profiler → CPU → System Trace
  • Firebase Performance Monitoring — _app_start automatic trace
  • Macrobenchmark library for reliable CI measurement
Prevention
  • Rule: no blocking calls on main thread in Application.onCreate()
  • Macrobenchmark startup test in CI — fails if startup > 2s threshold
  • Baseline Profiles generated and shipped with every release

6. Flow Collected Multiple Times
5
UI updates are duplicated or Flow emissions trigger actions multiple times
Problem

A toast appears twice for the same event. A navigation action triggers twice. A network request is fired multiple times for one user action.

Root Cause

The Flow is collected without repeatOnLifecycle in a Fragment. When the Fragment goes to background and returns, a new collector is created without cancelling the old one. Two collectors are now active for the same Flow.

Solution
// ❌ Wrong — creates new collector on each onStart(), old one still active
override fun onStart() {
    super.onStart()
    lifecycleScope.launch {
        viewModel.events.collect { handleEvent(it) }
        // This coroutine lives as long as lifecycleScope (until onDestroy)
        // but collect() is called AGAIN on next onStart()
    }
}

// ✅ Correct — exactly ONE collector active when STARTED, cancelled on STOPPED
override fun onViewCreated(view: View, savedInstanceState: Bundle?) {
    viewLifecycleOwner.lifecycleScope.launch {
        viewLifecycleOwner.repeatOnLifecycle(Lifecycle.State.STARTED) {
            viewModel.events.collect { handleEvent(it) }
            // Automatically cancelled when Fragment STOPPED, re-starts on STARTED
        }
    }
}

// For one-shot events: use SharedFlow with replay=0
val events = MutableSharedFlow<UiEvent>(replay = 0, extraBufferCapacity = 1)
// Emits to currently-active collectors only; no replaying on new collector
Prevention
  • Team convention: always use repeatOnLifecycle(STARTED) in Fragments — never naked lifecycleScope.launch { flow.collect }
  • Lint rule: Android Studio provides a lint check for this exact pattern

6

Root Causes (Most Common)
CausePatternFix

Anonymous inner classInner Runnable/Listener holds implicit outer class (Activity) referenceUse named static class or WeakReference
Unregistered listenerregisterX() without unregisterX() in onDestroyUnregister in onDestroy or use lifecycle-aware components

// ❌ Handler leak
private val handler = Handler(Looper.getMainLooper())
private val runnable = Runnable { updateUI() }  // holds Activity ref
handler.postDelayed(runnable, 5000)

// ✅ Fix: cancel in onDestroy
override fun onDestroy() {
    super.onDestroy()
    handler.removeCallbacks(runnable)
}

// ✅ Better: use lifecycle-aware coroutine instead of Handler
lifecycleScope.launch {
    delay(5000)
    updateUI()
    // Auto-cancelled when lifecycle is destroyed
}

9. Practice Questions
How do you diagnose why a Compose screen is recomposing too frequently?
Hard▼
Step 1: Enable Layout Inspector in Android Studio → Show Recomposition Counts — this shows how many times each composable recomposed. Step 2: Enable Compose compiler metrics (freeCompilerArgs plugin args) — generates a report showing which classes are stable/unstable/skippable. Step 3: Look for parameters marked as "unstable" — these force recomposition. Fix: @Immutable annotation, ImmutableList, stable lambda references.
A colleague's code causes an Activity leak. How do you detect and fix it?
Medium▼
Detection: Add LeakCanary to the debug build — it automatically detects and reports retained objects with a full path to the leak root. Also check Android Profiler → Memory → Force GC → Heap Dump for Activity instances. Fix: look at the LeakCanary report path (static field → Activity, or anonymous class holding outer Activity), then apply: WeakReference for static refs, removeCallbacks for Handler, unregister listeners in onDestroy.
Why does repeatOnLifecycle(STARTED) prevent double-collection in Fragments?
Hard▼
repeatOnLifecycle(STARTED) creates a new coroutine block when the lifecycle reaches STARTED and cancels it when it drops below STARTED (i.e., STOPPED). This means: (1) Only one collection is active at a time. (2) When the Fragment returns to foreground, the old collection was already cancelled, so a fresh one starts. Without it, each call to launch { flow.collect } adds a permanent collector that survives background/foreground transitions.
How would you measure and improve cold start time to under 2 seconds?
Hard▼
Measure: adb shell am start-activity -W (TTID/TTFD), Firebase Performance _app_start trace, Macrobenchmark. Improve: (1) Profile Application.onCreate() — move heavy init off main thread via App Startup library; (2) Lazy initialization for Room DB, heavy singletons; (3) Reduce ContentProviders (each adds startup overhead); (4) Generate and ship Baseline Profiles — pre-compiles critical code paths, 30-40% faster startup; (5) Splash screen API to fill perceived wait with branded splash.
What is @Immutable in Compose and when is it not safe to use?
Hard▼
@Immutable is a contract you make to the Compose compiler saying "none of the public properties of this class will change after construction." It enables skippable recomposition. It is NOT safe to use if: the class has mutable properties (var), the class contains a mutable List or Map (even if the field is val), or you might mutate the object after passing it to a composable. Misusing @Immutable causes silent UI bugs where the UI doesn't update when data changes.
Name three patterns that cause Activity memory leaks and their fixes.
Medium▼
(1) Static reference: companion object holds Activity → use WeakReference or remove. (2) Handler with postDelayed: delayed runnable holds Activity reference → cancel with removeCallbacks in onDestroy, or replace with lifecycle-aware coroutine + delay(). (3) Unregistered listener: registerReceiver without unregister → use lifecycle-aware components (LifecycleObserver) that auto-unregister, or manually unregister in onStop/onDestroy.
How do you debug a crash that only happens in production and has an obfuscated stack trace?
Medium▼
Step 1: Check Crashlytics dashboard — if the firebase-crashlytics Gradle plugin uploaded the mapping.txt at build time, Crashlytics auto-symbolicated the trace. Step 2: If not, find the mapping.txt file at app/build/outputs/mapping/release/mapping.txt for that build (store in CI artifacts). Step 3: Run retrace mapping.txt obfuscated-trace.txt. Step 4: Reproduce locally with a release build (adb install -r app-release.apk). Step 5: Add missing keep rules for the affected class.
What tool would you use for each: memory leak, slow startup, Compose jank, network call frequency?
Easy▼
Memory leak → LeakCanary (debug) + Android Profiler Heap Dump. Slow startup → adb am start-activity -W + Macrobenchmark + Firebase Performance _app_start + Android Studio CPU System Trace. Compose jank → Layout Inspector Recomposition Counts + Compose compiler metrics report. Network call frequency → Android Studio Profiler Network tab + OkHttp logging interceptor in debug + Firebase Performance HTTP traces in production.
What is the App Startup library and how does it help?
Medium▼
The App Startup library provides a single ContentProvider (InitializationProvider) that replaces the pattern of each SDK registering its own ContentProvider. Each ContentProvider adds ~5ms startup overhead — with 10 SDKs that's 50ms. App Startup initializes them all through one ContentProvider. Additionally it supports: ordered initialization (Initializer dependencies), lazy initialization (on first use), and explicit initialization from code (useful for testing).
A user reports that tapping a button sends duplicate API requests. Walk through your debugging approach.
Hard▼
(1) Check if the Flow is collected multiple times — look for missing repeatOnLifecycle. (2) Check if the button click listener is set multiple times (e.g., in onViewCreated called multiple times without cleanup). (3) Check if the ViewModel launches without deduplication — add a loading guard: if (uiState.value is Loading) return. (4) Check for debounce — rapid taps can trigger multiple launches; add viewModelScope.launch with debounce or a flag. Fix: use a loading/in-progress state flag in the ViewModel to prevent concurrent requests.
