9A — SOLID Principles

Five object-oriented design principles that produce maintainable, scalable Android code. Each principle with definition, Android violation, and correct fix.

ID: 9A ⭐ Tier 1
🔍
1. Overview

What are the SOLID principles?

SOLID is an acronym coined by Robert C. Martin for five design principles that, when applied together, produce code that is easy to understand, maintain, extend, and test. They are not rules — they are guidelines for managing complexity as a codebase grows.

LetterPrincipleOne-line definition
SSingle ResponsibilityA class should have one, and only one, reason to change
OOpen/ClosedOpen for extension, closed for modification
LLiskov SubstitutionSubtypes must be substitutable for their base types
IInterface SegregationClients should not be forced to depend on interfaces they don't use
DDependency InversionDepend on abstractions, not concretions
Senior Mental Model
SOLID principles are forces that counter entropy. Every codebase drifts toward tangled dependencies and god classes over time. SOLID provides the vocabulary and patterns to actively push back. In interviews, always connect each principle to a real Android violation and its concrete fix.
⚙
2. How It Works

S — Single Responsibility Principle (SRP)

"A class should have one, and only one, reason to change."

Android Violation: An Activity that makes network calls, accesses SharedPreferences, formats dates, and updates UI — it changes whenever the network layer, database, UI, or business logic changes.

// ❌ VIOLATION: Activity doing everything
class OrderActivity : AppCompatActivity() {
    fun loadOrders() {
        // Network call directly in Activity
        Retrofit.create(OrderApi::class.java).getOrders()
        // Database access directly
        AppDatabase.getInstance().orderDao().getAll()
        // Business logic directly
        val total = orders.sumOf { it.price * it.quantity }
    }
}
// ✅ FIX: Each class has one responsibility
class OrderRepository() { /* data concern */ }
class CalculateOrderTotalUseCase() { /* business logic */ }
class OrderViewModel(val repo: OrderRepository, val calcTotal: CalculateOrderTotalUseCase) { /* UI logic */ }
class OrderActivity { /* display only */ }

O — Open/Closed Principle (OCP)

"Software entities should be open for extension, but closed for modification."

Android Violation: A method with a growing when statement that must be modified every time a new payment type is added.

// ❌ VIOLATION: adding a new payment type requires modifying this class
fun processPayment(type: String, amount: BigDecimal) {
    when (type) {
        "credit"  -> chargeCreditCard(amount)
        "paypal"  -> chargePayPal(amount)
        // every new type requires modifying this file
    }
}
// ✅ FIX: Strategy pattern + sealed class — closed for modification
sealed class PaymentMethod {
    abstract suspend fun charge(amount: BigDecimal): PaymentResult

    class CreditCard(val token: String) : PaymentMethod() {
        override suspend fun charge(amount: BigDecimal) = /* ... */
    }
    class PayPal(val email: String) : PaymentMethod() {
        override suspend fun charge(amount: BigDecimal) = /* ... */
    }
}
// New payment methods extend PaymentMethod — processPayment never changes
suspend fun processPayment(method: PaymentMethod, amount: BigDecimal) =
    method.charge(amount)

L — Liskov Substitution Principle (LSP)

"Objects of a subtype should be substitutable for objects of their base type without altering program correctness."

Android Violation: A subclass overrides a method to throw an exception or do nothing — code using the base type breaks unexpectedly.

// ❌ VIOLATION: ReadOnlyRepository cannot honour the full contract
open class UserRepository {
    open fun save(user: User) { /* saves to DB */ }
    open fun delete(user: User) { /* deletes from DB */ }
}
class ReadOnlyUserRepository : UserRepository() {
    override fun save(user: User) { throw UnsupportedOperationException() } // 💥 LSP violated
}
// ✅ FIX: Separate interfaces — ReadableRepository and WritableRepository
interface ReadableUserRepository { fun getUser(id: String): User? }
interface WritableUserRepository { fun save(user: User); fun delete(user: User) }
interface UserRepository : ReadableUserRepository, WritableUserRepository

I — Interface Segregation Principle (ISP)

"Clients should not be forced to depend on interfaces they do not use."

Android Violation: A fat Repository interface that every screen must implement, even screens that only need one or two methods.

// ❌ VIOLATION: ProductListFragment only needs getProducts() but depends on this fat interface
interface ProductRepository {
    fun getProducts(): Flow<List<Product>>
    suspend fun createProduct(p: Product)
    suspend fun deleteProduct(id: String)
    suspend fun bulkImport(csv: String)
    suspend fun exportToCsv(): String
}
// ✅ FIX: Split into role-specific interfaces
interface ProductReader { fun getProducts(): Flow<List<Product>> }
interface ProductWriter { suspend fun createProduct(p: Product); suspend fun deleteProduct(id: String) }
interface ProductImportExport { suspend fun bulkImport(csv: String); suspend fun exportToCsv(): String }

// ProductListViewModel only depends on ProductReader
class ProductListViewModel @Inject constructor(val reader: ProductReader)

D — Dependency Inversion Principle (DIP)

"High-level modules should not depend on low-level modules. Both should depend on abstractions."

Android Violation: ViewModel directly instantiates or imports a concrete repository class.

// ❌ VIOLATION: ViewModel is coupled to the concrete Retrofit implementation
class UserViewModel : ViewModel() {
    private val repo = UserRepositoryImpl(RetrofitClient.create())  // concrete class
}
// ✅ FIX: ViewModel depends on the interface; Hilt provides the impl
@HiltViewModel
class UserViewModel @Inject constructor(
    private val repo: UserRepository   // interface — can be mocked in tests
) : ViewModel()

3. When to Use

These are default — not optional

SOLID principles aren't situational. They are default design hygiene for any codebase you expect to maintain or hand off to other developers. However, their application is graduated:

  • SRP: Apply from day one. God classes create an ever-growing change surface.
  • OCP: Apply when you identify variation points — places where new types or behaviours will be added. Don't over-engineer stable code.
  • LSP: Apply when designing inheritance or interface hierarchies. Prefer composition over inheritance to avoid LSP traps.
  • ISP: Apply when interfaces grow beyond 3–4 methods or when different callers need different subsets.
  • DIP: Apply to any class that needs to be testable. If you can't inject a mock, you're probably violating DIP.
The Litmus Test
"Can I write a unit test for this class in under 30 seconds — without setting up a Room database, Retrofit, or an Android emulator?" If the answer is no, at least one SOLID principle is being violated.

4. Production Example

E-Commerce App — Checkout Feature Refactor

A realistic before/after showing all five principles applied to a checkout flow:

// ❌ BEFORE: CheckoutManager violates SRP, OCP, DIP
class CheckoutManager {
    fun checkout(cart: Cart, paymentType: String) {
        // Validates cart (SRP violation)
        if (cart.items.isEmpty()) throw Exception("Empty cart")

        // Chooses payment (OCP violation — must modify for new types)
        when (paymentType) {
            "card"   -> StripeClient().charge(cart.total)   // DIP violation
            "paypal" -> PayPalClient().charge(cart.total)  // DIP violation
        }

        // Saves order and sends email (SRP violation)
        AppDatabase.getInstance().orderDao().insert(cart.toOrder())
        EmailClient().sendConfirmation(cart.email)
    }
}
// ✅ AFTER: Each responsibility extracted, depends on abstractions

// ISP: split interfaces
interface CartValidator { fun validate(cart: Cart): ValidationResult }
interface PaymentProcessor { suspend fun charge(amount: BigDecimal): PaymentResult }
interface OrderPersistence { suspend fun save(order: Order) }
interface NotificationService { suspend fun sendConfirmation(order: Order) }

// OCP: new payment methods extend this, CheckoutUseCase never changes
sealed class Payment : PaymentProcessor {
    class Card(val token: String) : Payment() { override suspend fun charge(amount: BigDecimal) = /* ... */ }
    class PayPal(val email: String) : Payment() { override suspend fun charge(amount: BigDecimal) = /* ... */ }
}

// SRP: one class orchestrates the flow, delegates everything
// DIP: depends only on interfaces injected via Hilt
class CheckoutUseCase @Inject constructor(
    private val validator: CartValidator,
    private val persistence: OrderPersistence,
    private val notifications: NotificationService
) {
    suspend operator fun invoke(cart: Cart, payment: PaymentProcessor): CheckoutResult {
        validator.validate(cart).onFailure { return CheckoutResult.ValidationFailed(it) }
        val paymentResult = payment.charge(cart.total)
            .onFailure { return CheckoutResult.PaymentFailed(it) }
        val order = cart.toOrder(paymentResult)
        persistence.save(order)
        notifications.sendConfirmation(order)
        return CheckoutResult.Success(order)
    }
}

5. Alternatives & Trade-offs

Over-applying SOLID

SOLID can be over-engineered. A simple settings screen that just toggles a flag doesn't need five interfaces and three UseCases. Premature abstraction creates indirection without benefit.

PrincipleBenefitOver-application risk
SRPFocused, small classesExcessive fragmentation — too many tiny classes to trace
OCPAdding types without breaking existing codePremature abstraction of stable code that never changes
LSPSafe polymorphismForcing inheritance where composition is cleaner
ISPLean interfacesInterface explosion — too many one-method interfaces
DIPTestability, swappable implementationsInterface-for-everything anti-pattern when only one impl exists
Rule of Three
Create an abstraction when you see a concept appearing in three or more places, or when you need to mock it in a test. Before that, the "wrong" code is often the simplest code.

6. Pitfalls & Best Practices

SRP in Android — The Activity God Class

Most Common Android SOLID Violation
Activities/Fragments that contain network calls, business logic, database access, date formatting, and navigation. This is the top anti-pattern in legacy Android code. The fix: ViewModel for UI logic, UseCase for business logic, Repository for data, separate formatters and mappers.

DIP in Tests

The most immediate payoff of DIP is testability. When CheckoutViewModel depends on interface PaymentProcessor, you can inject a FakePaymentProcessor in tests. When it depends on class StripeClient, you can't test it without hitting the network.

LSP and Kotlin Sealed Classes

Sealed classes are naturally LSP-compliant: all subtypes are declared in the same file, so you always know the complete set. A when expression on a sealed class is exhaustive — the compiler forces you to handle all cases, preventing substitution surprises.

ISP and Click Listeners

// ❌ Fat listener — every implementer must implement all methods
interface OnItemInteractionListener {
    fun onItemClick(id: String)
    fun onItemLongClick(id: String)
    fun onItemSwipeLeft(id: String)
    fun onItemSwipeRight(id: String)
}

// ✅ Specific lambdas passed only where needed
class OrderAdapter(
    private val onClick: (String) -> Unit,
    private val onSwipeDelete: ((String) -> Unit)? = null
)

7. Interview Framework

30-Second Answer

"SOLID is five design principles: Single Responsibility — one reason to change; Open/Closed — extend without modifying; Liskov Substitution — subtypes are safely substitutable; Interface Segregation — small, focused interfaces; Dependency Inversion — depend on abstractions. In Android, the most common violation is an Activity doing networking, database access, and UI — SRP says those belong in separate ViewModel, Repository, and UseCase classes."

2-Minute Deep Dive

"Let me give Android-specific examples for each. SRP: an Activity that makes Retrofit calls violates SRP — extract to Repository, UseCase, and ViewModel. OCP: a when(paymentType) switch that grows every sprint violates OCP — replace with a sealed class hierarchy where each subtype implements a charge() interface. LSP: a read-only repository subclassing a read-write repository and throwing UnsupportedOperationException violates LSP — separate the interfaces. ISP: a fat Repository interface where each ViewModel uses only two of its ten methods violates ISP — split into role interfaces. DIP: a ViewModel constructing a concrete Retrofit client violates DIP — inject the interface, let Hilt provide the implementation. The unified benefit: every one of these makes the class unit-testable without Android framework setup."

Must-Mention Points

1
SRP: Activity doing everything = classic violation. Extract ViewModel, Repository, UseCase
2
OCP: sealed classes + strategy pattern let you add types without modifying existing code
3
LSP: prefer composition over inheritance; sealed classes are naturally LSP-safe
4
ISP: split fat Repository interfaces into role interfaces (ProductReader, ProductWriter)
5
DIP: ViewModel depends on interface Repository injected by Hilt — not on class RepositoryImpl
6
Testability link: every SOLID principle ultimately enables unit testing without Android framework

Do NOT Go Deeper On

  • Academic definitions and history (Robert Martin, 2000s publications)
  • Contrived examples that don't connect to Android
  • Every possible interpretation of LSP (keep it practical)

Follow-up Q&A

QuestionAnswer
"Which SOLID principle does Clean Architecture enforce?"DIP primarily — Domain defines interfaces, Data implements them. Also SRP via layer separation.
"Can you violate SOLID even with Hilt?"Yes. Hilt only enforces DIP if you inject interfaces. If you inject concrete classes, DIP is still violated.
"How does OCP relate to the open keyword in Kotlin?"Kotlin's open keyword is syntactic, not principled. OCP is about design — using polymorphism so callers never change. Not all open classes follow OCP.

Senior Insight

Senior Signal
The five principles aren't independent — they reinforce each other. SRP limits class scope, which makes ISP natural. DIP requires ISP (you need interfaces to invert). OCP is enabled by DIP. In practice, applying one principle to a violation usually requires applying two or three simultaneously. That's the sign of mature design thinking.

9. Interview Questions
Basic What does SRP mean and give an Android example of a violation? ⌄
SRP: a class should have only one reason to change. Classic Android violation: an Activity that contains Retrofit calls, SharedPreferences access, date formatting, and UI updates. It changes when the API changes, when the database schema changes, when the UI design changes, and when the business logic changes. Fix: extract to ViewModel (UI state), Repository (data), UseCase (business logic), and Formatter (display formatting).
Basic What is DIP and how does Hilt enforce it? ⌄
DIP: high-level modules should depend on abstractions, not concretions. In Android, a ViewModel should depend on interface UserRepository, not class UserRepositoryImpl. Hilt enforces this via @Binds in a @Module, which maps the interface to its implementation at compile time. The ViewModel only knows the interface — in tests, you inject a fake; in production, Hilt injects the real impl.
Basic How does OCP apply to handling different payment methods in an app? ⌄
A when(paymentType: String) that keeps growing with new cases violates OCP — every new method modifies existing code. The fix is to define a PaymentProcessor interface with a charge() method, and represent each payment type as a sealed class subtype implementing it. The checkout logic calls processor.charge(amount) and never changes when a new payment type is added — it only extends via a new subclass.
Intermediate Spot the SOLID violations in this code and suggest fixes. ⌄
Scenario: class ProfileViewModel : ViewModel() { val retrofit = Retrofit.Builder().build(); fun loadUser() { retrofit.create(Api::class.java).getUser(); Room.databaseBuilder(...).build().userDao().getAll() } }

SRP violation: ViewModel constructs Retrofit and Room directly — data access is not its responsibility.
DIP violation: Depends on concrete Retrofit and AppDatabase classes, not interfaces.
Fix: Inject a UserRepository interface via Hilt. The ViewModel calls repository.getUser() and knows nothing about HTTP or SQL.
Intermediate Explain ISP with a RecyclerView listener example. ⌄
A fat OnItemInteractionListener with onClick, onLongClick, onSwipeLeft, onSwipeRight forces every implementer to implement all four methods, even if only one is used. ISP says: give clients only what they need. The fix: accept separate lambdas — onClick: (String) -> Unit, onSwipeDelete: ((String) -> Unit)? = null — so the screen only provides what it actually handles.
Intermediate How do sealed classes relate to LSP and OCP? ⌄
LSP: sealed class subtypes are all declared in one file with full visibility — you always know every possible subtype. A when on a sealed type is exhaustive, so the compiler enforces that all cases are handled. No subtype can introduce unexpected behaviour because the set is closed.

OCP: a sealed class with a when expression in a single place isn't OCP (adding a subtype requires modifying the when). But using the subtypes polymorphically — e.g., each subtype implements render() — achieves OCP because calling code never changes.
Intermediate Why can a class that uses Hilt still violate DIP? ⌄
Hilt is a DI framework, not a DIP enforcer. If you write @Inject constructor(val repo: UserRepositoryImpl), you're injecting a concrete class — DIP is still violated. For Hilt to enforce DIP, you must: (1) define an interface UserRepository in the domain layer, (2) implement it as UserRepositoryImpl in the data layer, (3) use @Binds to map the interface to the impl in a Hilt module, (4) inject the interface everywhere. Hilt automates the wiring; you must choose to depend on the interface.
Senior A PR adds a new feature by subclassing a Fragment and overriding onResume() to throw if a condition isn't met. What principle does this violate and what's the correct fix? ⌄
This violates LSP. Any code that uses the base Fragment type and calls resume() now has to defensively check whether it might throw — the subtype is not safely substitutable for the base type. The precondition (the condition that must be met) is stronger in the subtype than in the base, which is precisely what LSP forbids.

Fix: represent the precondition check as part of the Fragment's visible state machine. Use a UiState.RequiresCondition sealed class variant and navigate away or show an error screen. Never throw exceptions from lifecycle methods — the calling framework doesn't expect it and won't recover gracefully.
Senior How would you identify SOLID violations in a codebase of 200,000 lines during a technical interview review? ⌄
I'd look for these signals:

SRP: Classes >300 lines, or classes with methods that import 3+ different subsystems (network + db + UI).
OCP: Files with large when blocks on string/int types, especially in service or handler classes.
LSP: Overridden methods that throw UnsupportedOperationException, or empty overrides.
ISP: Interfaces with 8+ methods; implementers that stub half the methods with empty bodies.
DIP: Classes that construct their own dependencies (val x = ConcreteClass()) inside constructors or init blocks.

Tooling: Detekt rules enforce class/method line counts. ArchUnit assertions verify layer dependencies. These run in CI so violations are caught automatically.
Senior SOLID was defined for OOP. How relevant is it for Kotlin with its functional features? ⌄
Still very relevant, but Kotlin's features change the implementation idioms:

SRP: Even more relevant — Kotlin's extension functions let you decompose behaviour without subclassing.
OCP: Sealed classes are Kotlin's native way to express a closed-for-modification set of types with compile-time exhaustiveness.
LSP: Less of a problem because Kotlin discourages inheritance (open must be explicit) and favours interfaces and composition.
ISP: Functional interfaces (fun interface) and lambdas are naturally segregated — a lambda is a single-method interface.
DIP: Extension functions on interfaces allow default behaviour without breaking DIP. The principle remains; the syntax is more concise.
