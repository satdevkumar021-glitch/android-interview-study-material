Senior Mental Model
Firebase is a backend-as-a-service that lets small teams ship quickly. The trade-off is vendor lock-in and limited query flexibility (Firestore can't do JOINs). At scale (>10M users), cost and query limitations push teams to custom backends. Know when to use Firebase vs custom backend.

2. Authentication & Firestore

Firebase Authentication

// Email/password sign-in
suspend fun signIn(email: String, password: String): FirebaseUser? {
    return try {
        val result = auth.signInWithEmailAndPassword(email, password).await()
        result.user
    } catch (e: FirebaseAuthInvalidCredentialsException) {
        null   // wrong password
    }
}

// Google Sign-In flow
val googleSignInClient = GoogleSignIn.getClient(context, gso)
val signInIntent = googleSignInClient.signInIntent
launcher.launch(signInIntent)  // in Activity/Fragment

// In callback: get credential and sign in to Firebase

val credential = GoogleAuthProvider.getCredential(account.idToken, null)
auth.signInWithCredential(credential).await()

// Auth state listener — observe sign-in/out changes
auth.addAuthStateListener { firebaseAuth ->
    val user = firebaseAuth.currentUser
    // user != null → signed in; null → signed out
}

// Force token refresh (call when getting 401 from backend)
val idToken = auth.currentUser?.getIdToken(/* forceRefresh = */ true)?.await()?.token

Cloud Firestore

// Structure: /users/{userId}/orders/{orderId}
val db = FirebaseFirestore.getInstance()

// Write document
db.collection("users").document(userId)
    .set(userMap).await()

// Real-time listener (Flow wrapper)
fun userFlow(userId: String): Flow<User> = callbackFlow {
    val listener = db.collection("users").document(userId)
        .addSnapshotListener { snapshot, error ->
            if (error != null) { close(error); return@addSnapshotListener }
            snapshot?.toObject(User::class.java)?.let { trySend(it) }
        }
    awaitClose { listener.remove() }   // clean up on Flow cancellation
}

// Pagination with startAfter
val firstPage = db.collection("posts")
    .orderBy("timestamp", Query.Direction.DESCENDING)
    .limit(20)
    .get().await()

val lastDoc = firstPage.documents.last()
val nextPage = db.collection("posts")
    .orderBy("timestamp", Query.Direction.DESCENDING)
    .startAfter(lastDoc)
    .limit(20)
    .get().await()

Firestore Security Rules (must know)

rules_version = '2';
service cloud.firestore {
  match /databases/{database}/documents {
    match /users/{userId} {
      // Only authenticated user can read/write their own document
      allow read, write: if request.auth != null && request.auth.uid == userId;
    }
    match /posts/{postId} {
      allow read: if true;  // public read
      allow write: if request.auth != null && request.resource.data.authorId == request.auth.uid;
    }
  }
}
Firestore vs Realtime Database
Use Firestore for: structured data, complex queries, subcollections, offline support. Use Realtime Database for: simple data structures, very low latency (<10ms), presence (online/offline status). Firestore is the default for new apps.

3. FCM & Realtime Database

Firebase Cloud Messaging (FCM)

// FirebaseMessagingService — extend in your app
class MyFCMService : FirebaseMessagingService() {

    // Called when a message is received while app is in foreground
    override fun onMessageReceived(message: RemoteMessage) {
        val title = message.notification?.title
        val body  = message.notification?.body
        val data  = message.data   // Map<String, String> — custom payload
        showNotification(title, body)
    }

    // Called when FCM token is refreshed (or first time)
    override fun onNewToken(token: String) {
        // Send token to your backend so it can target this device
        sendTokenToServer(token)
    }
}

// Notification payload (handled by system, shown even in background)
// vs Data payload (always delivered to onMessageReceived)

Crash-free Users Metric
Crashlytics tracks "crash-free users" — percentage of unique users who had NO crashes. This is the production SLA metric. A 99.5% crash-free rate means 5 in 1,000 users experienced a crash. Monitor this per version in the Crashlytics dashboard.

5. Remote Config & Performance

Firebase Remote Config

val remoteConfig = FirebaseRemoteConfig.getInstance()

// Set default values (used if fetch fails or before first fetch)
remoteConfig.setDefaultsAsync(R.xml.remote_config_defaults)

// Fetch and activate (MUST call before reading values)
suspend fun initRemoteConfig() {
    try {
        remoteConfig.fetchAndActivate().await()
    } catch (e: Exception) {
        // Network failure — defaults are active, safe to proceed
    }
}

// Read values
val isNewCheckoutEnabled = remoteConfig.getBoolean("new_checkout_enabled")
val heroColor = remoteConfig.getString("hero_banner_color")
val maxRetries = remoteConfig.getLong("api_max_retries").toInt()
Fetch Throttling
In production, Remote Config caches fetched values for 12 hours by default. Calls to fetch() more frequently return cached values. In debug builds, use setMinimumFetchIntervalInSeconds(0) for instant updates. Never call fetchAndActivate() on every screen because it's throttled.

6. Pitfalls & Best Practices
PitfallFix
Reading Remote Config before fetchAndActivate()Defaults are served — always await fetchAndActivate() at startup
Firestore listener not removedStore ListenerRegistration, call remove() in onStop/onDestroy or awaitClose in callbackFlow
FCM token not refreshed on serverAlways implement onNewToken and update the server with the new token
Posting notification without channel on Android 8+Create NotificationChannel before building notification
Auth token not refreshed on 401Use OkHttp Authenticator to call getIdToken(forceRefresh=true) and retry
Writing sensitive data without security rulesAlways define and test Firestore security rules; default is deny-all after rules version 2
Crashlytics user ID containing PIIUse hashed or anonymous ID, not email/name in setUserId()

7. Interview Framework
How to Answer Firebase Questions
Structure: What it does → How to set it up → Production pattern → Pitfall to avoid. For any Firebase question, always mention the coroutine/Flow integration pattern.

Common Question Patterns

  • "How do you handle auth token expiry?" → OkHttp Authenticator intercepts 401, calls getIdToken(forceRefresh=true), retries with new token. Use Mutex to prevent concurrent refreshes.
  • "Firestore vs Realtime Database?" → Firestore: structured, better querying, offline, scales. RTDB: simpler, lower latency, presence tracking. Use Firestore for new apps.
  • "How do you handle FCM when app is killed?" → Use notification payload (not data-only) — the system delivers it even when app is killed. Data-only messages require high priority and may not be delivered on doze mode.
  • "What's a crash-free user rate?" → Percentage of users with zero crashes in the time window. Industry target: 99.5%+. Monitor per app version in Crashlytics dashboard.

9. Interview Questions
How do you handle an expired Firebase auth token when making API calls?
Hard▼
Implement OkHttp Authenticator: when a 401 is received, call FirebaseAuth.currentUser?.getIdToken(forceRefresh=true)?.await()?.token. Use a Mutex to ensure only one refresh happens concurrently — if 5 requests fail with 401, only one should refresh and the others wait. Retry the failed request with the new token.
When would you choose Realtime Database over Firestore?
Medium▼
Realtime Database is better for: (1) Presence/online status tracking (built-in onDisconnect handlers), (2) Very simple flat data structures (JSON tree), (3) Ultra-low latency requirements (<10ms). Firestore is better for everything else: subcollections, complex queries, better offline support, scales horizontally. Use Firestore for new apps by default.
What is the difference between FCM notification payload and data payload?
Medium▼
Notification payload: handled by the FCM SDK automatically — shows a system notification when app is in background or killed. Data payload: always delivered to onMessageReceived() regardless of app state. Best practice: use notification+data payload so system handles display when backgrounded, and you also receive data in onMessageReceived() when foreground. Pure data messages need high priority for background delivery.
How do you prevent a Firestore memory leak from an unremoved snapshot listener?
Medium▼
Wrap the listener in callbackFlow { ... awaitClose { listener.remove() } }. The awaitClose block is called when the Flow is cancelled (collector's coroutine cancelled), which happens when the ViewModel is cleared. This automatically removes the Firestore listener. Never add a listener in Fragment without a corresponding remove() in onDestroyView().
What are Crashlytics custom keys used for?
Easy▼
Custom keys add context to crash reports — they appear in the Crashlytics dashboard alongside the stack trace. Examples: user's subscription tier, current screen name, feature flag values, cart size. This helps reproduce crashes by understanding the app state at the time. Limit: 64 custom keys, 1KB per value.
Why must fetchAndActivate() be called before reading Remote Config values?
Easy▼
Remote Config values are not automatically synced. The app has a local cache of fetched values. fetchAndActivate() fetches the latest values from the server AND activates them (makes them available to getBoolean/getString). Without this call, you read stale cached values or the default values you set in R.xml.remote_config_defaults. Always await this coroutine at startup before using any flag.
How does Firestore offline persistence work on Android?
Medium▼
Firestore caches all documents you've read in a local SQLite database. When offline, reads are served from this cache. Writes are added to a local queue and automatically synced when connectivity is restored. Snapshot listeners still fire with cached data. This is enabled by default on Android. Set setCacheSizeBytes to control storage usage.
How do you track screen views with Firebase Analytics in a Compose app?
Medium▼
In Compose there's no Activity lifecycle tied to screens, so you must log manually. Use a NavigationListener on NavController that fires on every destination change. In the listener, read the current destination route and log FirebaseAnalytics.Event.SCREEN_VIEW with SCREEN_NAME and SCREEN_CLASS params. This replaces the automatic Activity-based screen tracking.
What Firestore security rule would you write to allow a user to read/write only their own data?
Easy▼
allow read, write: if request.auth != null && request.auth.uid == userId; — where userId is the document ID wildcard. This checks that the requesting user is authenticated AND their auth UID matches the document path. Without this, any authenticated user could read all users' data.
How would you use Firebase Performance Monitoring to measure checkout speed?
Easy▼
Create a named trace: val trace = FirebasePerformance.getInstance().newTrace("checkout_complete"). Call trace.start() when user taps "Pay". Add attributes (payment method, item count). Call trace.stop() when the order confirmation is received. Firebase aggregates the duration across all users — you can view p50/p90/p99 in the Performance Monitoring console.
