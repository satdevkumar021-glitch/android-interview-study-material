39A — Android Accessibility

Building accessible Android apps: TalkBack, semantics in Compose, content descriptions, focus management, and WCAG compliance.

ID: 39A ⭐ Tier 2 — Senior Differentiator
🔍
1. Overview

Why Accessibility Matters

Approximately 15% of users worldwide have some form of disability — visual, motor, auditory, or cognitive. In regulated markets (banking, government, healthcare), accessibility is not optional — it is a legal requirement under laws such as the Americans with Disabilities Act (ADA), the European Accessibility Act, and EN 301 549. Accessibility audits can block app store releases and result in legal liability.

Android Accessibility Services

ServicePurposeUsers
TalkBackScreen reader — reads UI aloud via text-to-speechVisually impaired / blind

BrailleBackRefreshable braille display integrationBlind / deafblind
Voice AccessControl device entirely by voice commandsMotor disabilities
Select to SpeakUser selects portion of screen to read aloudLow vision / dyslexia

Two Implementation Layers

  • View system — android:contentDescription, android:importantForAccessibility, ViewCompat.setAccessibilityDelegate()
  • Jetpack Compose — Semantics API: Modifier.semantics { } — adds structured metadata to composables for accessibility services

Standards & Guidelines

  • WCAG 2.1 (Web Content Accessibility Guidelines) — the international standard; Android apps are measured against AA compliance
  • Google Material Design accessibility guidelines — minimum touch target, colour contrast ratios, typography scaling
  • Key WCAG principles: Perceivable, Operable, Understandable, Robust (POUR)
Senior Mental Model
Accessibility is not a feature to add at the end — it is an architectural property of the component library. If every Button, Card, TextField, and Icon component in your design system has semantics baked in, every screen that uses them is automatically accessible. The right level to enforce it is at the component level, not the screen level.

2. How It Works

TalkBack — How It Reads the Screen

TalkBack is an AccessibilityService that listens to accessibility events from the Android framework. The framework exposes the UI as an AccessibilityNodeInfo tree — a hierarchical representation of every interactive or meaningful element on screen. TalkBack traverses this tree and reads each node's label, role, and state aloud.

User swipes right on screen │ ▼ TalkBack service receives AccessibilityEvent (TYPE_VIEW_FOCUSED) │ ▼ Queries AccessibilityNodeInfo tree │ ▼ ┌──────────────────────────────────┐ │ AccessibilityNodeInfo │ │ contentDescription: "Add item" │ │ role: Button │ │ state: enabled │ └──────────────────────────────────┘ │ ▼ ┌───────────────────────┐ ┌───────────────────────┐ │ Compose Semantics │ │ View contentDesc │ │ Modifier.semantics{} │ │ android:contentDesc │ └───────────────────────┘ └───────────────────────┘ │ ▼ Text-to-speech: "Add item, Button"

Compose Semantics API

Modifier.semantics { } adds metadata to a composable node in the accessibility tree. Key properties:

Semantics PropertyPurposeExample
contentDescriptionLabel read by TalkBack; overrides visual text"Add John Smith to cart"
stateDescriptionDescribes current state"Selected" / "Expanded"
roleWhat kind of element it isRole.Button, Role.Checkbox
headingMarks as section heading for navigationheading()
onClickAction label for clickonClick("Submit payment") { ... }
liveRegionAnnounces dynamic content changesLiveRegionMode.Polite
invisibleToUserHides from accessibility treeFor decorative elements

mergeDescendants vs clearAndSetSemantics

// mergeDescendants = true — combine all child nodes into one TalkBack announcement
Card(
    modifier = Modifier.semantics(mergeDescendants = true) {}
) {
    // TalkBack reads ALL children as one unit: "iPhone 15 Pro, $999, in stock"
    Text("iPhone 15 Pro")
    Text("$999")
    Text("In stock")
}

// clearAndSetSemantics — replace ALL descendant semantics with your own
Box(
    modifier = Modifier.clearAndSetSemantics {
        contentDescription = "iPhone 15 Pro, 999 dollars, in stock"
        role = Role.Button
    }
) {
    // children are invisible to TalkBack — only the custom description is announced
}

Full Compose Semantics Example

@Composable
fun ProductCard(product: Product, onAddToCart: () -> Unit) {
    Card(
        modifier = Modifier.semantics(mergeDescendants = true) {
            // Merge all child semantics into one node for TalkBack
        }
    ) {
        Image(
            painter = rememberAsyncImagePainter(product.imageUrl),
            // Never null for meaningful images — describes what the image shows
            contentDescription = "${product.name}, ${product.price}"
        )
        Text(product.name)  // auto-read by TalkBack via default semantics
        Button(
            onClick = onAddToCart,
            modifier = Modifier.semantics {
                // Override generic "Button" announcement with actionable description
                contentDescription = "Add ${product.name} to cart"
            }
        ) {
            // null contentDescription = decorative — TalkBack ignores it
            Icon(Icons.Default.Add, contentDescription = null)
        }
    }
}

// Live region — announces dynamic content changes to TalkBack without user focus
@Composable
fun SearchResults(isLoading: Boolean, results: List<Product>) {
    Box(
        modifier = Modifier.semantics {
            if (isLoading) liveRegion = LiveRegionMode.Polite
            contentDescription = if (isLoading)
                "Loading results"
            else
                "${results.size} results found"
        }
    ) { /* content */ }
}

Focus Management in Compose

@Composable
fun LoginForm() {
    val emailFocusRequester = remember { FocusRequester() }
    val passwordFocusRequester = remember { FocusRequester() }

    TextField(
        modifier = Modifier
            .focusRequester(emailFocusRequester)
            .focusProperties {
                next = passwordFocusRequester  // explicit tab order
            },
        label = { Text("Email") }
    )
    TextField(
        modifier = Modifier.focusRequester(passwordFocusRequester),
        label = { Text("Password") }
    )

    // Request focus on first field when screen opens
    LaunchedEffect(Unit) {
        emailFocusRequester.requestFocus()
    }
}

Minimum Touch Target

WCAG 2.5.5 and Material Design both require a minimum touch target of 48dp × 48dp for interactive elements. In Compose:

// Compose — ensure minimum interactive size even if visual size is smaller
Icon(
    imageVector = Icons.Default.Close,
    contentDescription = "Dismiss",
    modifier = Modifier
        .minimumInteractiveComponentSize()  // enforces 48dp minimum
        .clickable { onDismiss() }
)

// Alternative: explicit minimum size
IconButton(
    onClick = onDismiss,
    modifier = Modifier.size(48.dp)  // 48dp × 48dp
) {
    Icon(Icons.Default.Close, contentDescription = "Dismiss")
}

3. When to Use It
Always — No Exceptions
Accessibility is not optional. Every interactive element must be accessible. The question is how thoroughly to implement it, not whether to implement it.

Minimum Accessibility Requirements (Every App)

  • Every interactive element (Button, IconButton, custom click target) must have a contentDescription or readable text label
  • Every meaningful image must have a descriptive contentDescription
  • Every decorative image/icon must have contentDescription = null
  • All touch targets must be at minimum 48dp × 48dp
  • Colour contrast ratio: at least 4.5:1 for normal text, 3:1 for large text (WCAG AA)

High-Priority Scenarios

App CategoryWhy CriticalSpecific Requirements
Banking / FintechLegal requirement; accessibility audits block releasesForms, error announcements, balance screens, transaction lists
GovernmentMandated under Section 508 (US) / EN 301 549 (EU)Full WCAG 2.1 AA compliance
HealthcarePatient safety; users may have stress-induced motor issuesLarge targets, clear labels, no time limits
E-commerceRevenue impact — inaccessible checkout = lost salesCart, checkout flow, product descriptions
Custom UI componentsDefault composables lose semantics when wrappedAlways add semantics to custom components

When to Pay Extra Attention

  • Custom composables — any composable that wraps basic components MUST add semantics; custom drawing (Canvas) loses all accessibility by default
  • Icon-only buttons — all icon buttons MUST have a meaningful contentDescription
  • Loading states — use LiveRegionMode.Polite so TalkBack announces when content loads
  • Error states — inline validation errors must be announced; use error semantics or LiveRegion
  • Animations — respect LocalReduceMotion for users with vestibular disorders

4. Production Example
Scenario
Banking app fund transfer form: proper focus order, field-level error announcements via LiveRegion, loading state feedback, and accessible confirmation screen. This is exactly what banking compliance auditors check.

Accessible Fund Transfer Form

@Composable
fun TransferFundsScreen(viewModel: TransferViewModel = hiltViewModel()) {
    val uiState by viewModel.uiState.collectAsStateWithLifecycle()

    val amountFocusRequester = remember { FocusRequester() }
    val recipientFocusRequester = remember { FocusRequester() }

    Column(modifier = Modifier.padding(16.dp)) {

        // Heading — TalkBack users navigate by headings (swipe with 2 fingers)
        Text(
            text = "Transfer Funds",
            style = MaterialTheme.typography.headlineMedium,
            modifier = Modifier.semantics { heading() }
        )

        // Amount field with explicit focus order
        OutlinedTextField(
            value = uiState.amount,
            onValueChange = viewModel::onAmountChanged,
            label = { Text("Amount") },
            isError = uiState.amountError != null,
            supportingText = {
                uiState.amountError?.let { error ->
                    // Error text is announced via LiveRegion — appears without user navigating to it
                    Text(
                        text = error,
                        color = MaterialTheme.colorScheme.error,
                        modifier = Modifier.semantics {
                            liveRegion = LiveRegionMode.Assertive  // interrupt TalkBack immediately
                        }
                    )
                }
            },
            keyboardOptions = KeyboardOptions(keyboardType = KeyboardType.Decimal),
            modifier = Modifier
                .fillMaxWidth()
                .focusRequester(amountFocusRequester)
                .focusProperties { next = recipientFocusRequester }
                .semantics {
                    contentDescription = "Transfer amount in pounds"
                }
        )

        // Recipient field
        OutlinedTextField(
            value = uiState.recipient,
            onValueChange = viewModel::onRecipientChanged,
            label = { Text("Recipient account number") },
            modifier = Modifier
                .fillMaxWidth()
                .focusRequester(recipientFocusRequester)
        )

        // Loading state announced via LiveRegion — no user action required
        if (uiState.isLoading) {
            Box(
                modifier = Modifier.semantics {
                    liveRegion = LiveRegionMode.Polite
                    contentDescription = "Processing your transfer, please wait"
                }
            ) {
                CircularProgressIndicator()
            }
        }

        // Submit button — full contextual description
        Button(
            onClick = viewModel::submitTransfer,
            enabled = uiState.isSubmitEnabled,
            modifier = Modifier
                .fillMaxWidth()
                .minimumInteractiveComponentSize()
                .semantics {
                    contentDescription = if (uiState.isSubmitEnabled)
                        "Transfer ${uiState.amount} pounds to ${uiState.recipient}"
                    else
                        "Transfer button, disabled. Please fill in all required fields."
                }
        ) {
            Text("Transfer")
        }

        // Success state — announced when it appears
        uiState.successMessage?.let { msg ->
            Text(
                text = msg,
                color = MaterialTheme.colorScheme.primary,
                modifier = Modifier.semantics {
                    liveRegion = LiveRegionMode.Polite
                }
            )
        }
    }

    // Move focus to amount field when screen opens
    LaunchedEffect(Unit) {
        amountFocusRequester.requestFocus()
    }
}

What the Accessibility Auditor Will Check

  • All fields have descriptive labels — not just "Edit text"
  • Error messages are announced without user manually navigating to them
  • Loading state is communicated — TalkBack doesn't fall silent during async operations
  • Submit button describes its action with the actual data, not just "Button"
  • Disabled state is described with a reason
  • Focus order matches visual top-to-bottom reading order
  • Success/failure state is announced after the action completes

6. Pitfalls & Best Practices

Icon Buttons with Null contentDescription

// ❌ BAD — TalkBack reads "Button" — useless, cannot differentiate
IconButton(onClick = { navigateBack() }) {
    Icon(Icons.Default.ArrowBack, contentDescription = null)
}

// ✅ GOOD — TalkBack reads "Navigate back, Button"
IconButton(onClick = { navigateBack() }) {
    Icon(Icons.Default.ArrowBack, contentDescription = "Navigate back")
}

contentDescription = "" vs contentDescription = null

⚠ Critical Distinction
  • contentDescription = null on an Image → TalkBack announces nothing (correct for decorative images)
  • contentDescription = "" (empty string) → TalkBack may say "Image" or announce an empty label — ambiguous; avoid
  • contentDescription = null on an IconButton → TalkBack announces "Button" without a label — NOT accessible
  • Rule: null = decorative, skip entirely. Non-null = meaningful, read aloud.
// Decorative icon inside a button that already has text
Button(onClick = { submit() }) {
    Icon(Icons.Default.Send, contentDescription = null)  // ✅ decorative — button text provides label
    Text("Send")
}

// Icon-only button — MUST have contentDescription
IconButton(onClick = { deleteItem() }) {
    Icon(Icons.Default.Delete, contentDescription = "Delete item")  // ✅ required
}

Duplicate Announcements from mergeDescendants + explicit contentDescription

// ❌ BAD — TalkBack reads "John Smith" then also "John Smith profile, Button" = double reading
Card(
    modifier = Modifier.semantics(mergeDescendants = true) {
        contentDescription = "John Smith profile, Button"
    }
) {
    Text("John Smith")   // this text will ALSO be merged in
}

// ✅ GOOD — use clearAndSetSemantics to fully control the announcement
Card(
    modifier = Modifier.clearAndSetSemantics {
        contentDescription = "John Smith profile"
        role = Role.Button
    }
) {
    Text("John Smith")   // invisible to TalkBack — clearAndSetSemantics takes over
}

Custom Touch Targets Below 48dp

// ❌ BAD — 24dp icon with no touch target expansion
Icon(
    imageVector = Icons.Default.MoreVert,
    contentDescription = "More options",
    modifier = Modifier.size(24.dp).clickable { showMenu() }
)

// ✅ GOOD — minimumInteractiveComponentSize() or size(48.dp)
IconButton(
    onClick = { showMenu() },
    modifier = Modifier.minimumInteractiveComponentSize()
) {
    Icon(Icons.Default.MoreVert, contentDescription = "More options")
}

Do Not Override Focus Order Unless Necessary

Focus order should match visual reading order (top-left to bottom-right). Overriding it creates disorientation for TalkBack and Switch Access users. Only override focus order when the visual layout genuinely differs from the logical reading order (e.g., RTL layouts, custom dialogs).

Color Contrast & "Color Alone" Anti-pattern

// ❌ BAD — uses only color to distinguish transaction types
Text(
    text = transaction.description,
    color = if (transaction.type == TransactionType.CREDIT) Color.Green else Color.Red
)

// ✅ GOOD — color + explicit semantics + icon
Row(modifier = Modifier.semantics(mergeDescendants = true) {}) {
    Icon(
        imageVector = if (isCredit) Icons.Default.Add else Icons.Default.Remove,
        contentDescription = if (isCredit) "Credit" else "Debit"
    )
    Text(
        text = transaction.description,
        color = if (isCredit) creditGreen else debitRed  // must be 4.5:1 contrast ratio
    )
}

Always Test with TalkBack On

Rule
Accessibility Scanner finds structural issues. TalkBack finds UX issues. You need both. Every new screen or component must be tested by a developer with TalkBack enabled using only swipe gestures — no looking at the screen while navigating. If you can't navigate to every interactive element and understand what it does, it is not accessible.

7. Interview Answer Framework

30-Second Answer

"In Compose, accessibility is implemented through the Semantics API — Modifier.semantics { } attaches metadata to composables that TalkBack and other accessibility services read via the AccessibilityNodeInfo tree. The three key rules are: every interactive element needs a meaningful contentDescription, all touch targets must be at least 48dp, and dynamic content changes should use LiveRegion so TalkBack announces them without requiring user focus. I always test with TalkBack on — Accessibility Scanner catches structural issues but not UX issues."

2-Minute Structured Answer

"Android accessibility works through an AccessibilityNodeInfo tree — the framework exposes every UI element as a node with properties like label, role, and state. Services like TalkBack traverse that tree to read the screen aloud. In Compose, the Semantics API populates those node properties declaratively via Modifier.semantics { }.

The key semantics properties are: contentDescription (what TalkBack reads), role (Button, Checkbox, Heading), stateDescription (Selected/Expanded), and liveRegion for dynamic content. mergeDescendants = true combines multiple child nodes into one TalkBack announcement — important for cards and list items. clearAndSetSemantics replaces all descendant semantics with a single custom description.

For banking apps specifically, focus management matters: FocusRequester controls which field gets focus when a screen opens, and focusProperties sets the tab order. Error messages on form fields must use LiveRegionMode.Assertive so they're announced immediately when they appear. Loading states use LiveRegionMode.Polite — announced after TalkBack finishes its current sentence.

For the View system, it's android:contentDescription in XML and ViewCompat.setAccessibilityDelegate() for dynamic or complex cases. The minimum touch target is 48dp — enforced with Modifier.minimumInteractiveComponentSize() in Compose."

Senior-Level Insight (Stand Out)

Say This
"I treat accessibility as architecture, not afterthought. In our component library, every AppButton, AppCard, and AppTextField has semantics baked into the component definition — so every screen that uses them is automatically accessible without developers thinking about it. 9. Interview Questions (Self-Check)
How to use
Try to answer each question before revealing the answer. Click the arrow to reveal.

Basic

B1 — What is TalkBack and how does it access the UI content of an Android app?
Easy▼
TalkBack is Android's built-in screen reader — an AccessibilityService that reads UI elements aloud using text-to-speech for visually impaired users. It does not directly read pixels; instead, the Android framework exposes the UI as an AccessibilityNodeInfo tree — a hierarchical structure where each node represents an interactive or meaningful UI element with properties like contentDescription, role, state, and bounds. TalkBack subscribes to accessibility events, queries this tree, and reads the relevant node properties aloud. In Compose, the Modifier.semantics { } API populates these node properties.
B2 — What is the difference between contentDescription = null and contentDescription = "" on an Image composable?
Easy▼
contentDescription = null marks the image as decorative. TalkBack completely ignores it and does not announce it. This is the correct choice for purely decorative images that add no informational value (background illustrations, decorative borders).

contentDescription = "" (empty string) has ambiguous behaviour — on some Android versions TalkBack may still say "Image" or announce something empty, creating a confusing pause. It should be avoided.

Rule: Use null for decorative; use a descriptive string for meaningful images. Never use an empty string.
B3 — What is the minimum touch target size per WCAG and how do you enforce it in Compose?
Easy▼
The minimum interactive target size is 48dp × 48dp, per WCAG 2.5.5 and Google Material Design guidelines. This ensures that users with motor impairments can reliably tap the target.

In Compose, enforce it with:
1. Modifier.minimumInteractiveComponentSize() — automatically ensures the touch target is at least 48dp without changing the visual size of the element
2. Modifier.size(48.dp) — explicitly sets the composable size
3. Wrapping in IconButton — its default size is 48dp × 48dp

Note: the visual size of the icon can remain 24dp while the touch target is 48dp — the extra space is transparent but tappable.

Intermediate

I1 — Explain mergeDescendants vs clearAndSetSemantics. When would you use each?
Medium▼
mergeDescendants = true: Combines all child semantic nodes into a single TalkBack announcement. The parent node becomes the focus point and TalkBack reads all children's text and descriptions as one unit. Use this for cards, list items, and compound components where children individually would produce too many separate TalkBack stops. The child semantics are still present — they're just merged up into the parent.

clearAndSetSemantics { }: Completely replaces the semantics of the node AND all its descendants with the semantics you define in the block. Children's text and descriptions are invisible to TalkBack. Use this when you need full control over what TalkBack says and the default merged output would still be wrong or incomplete — for example, a product card with a price like "$12.99" that TalkBack would read as "Dollar 12 period 99" — you want to set contentDescription = "12 pounds 99" explicitly.

Key difference: mergeDescendants preserves child semantics but consolidates focus; clearAndSetSemantics discards child semantics entirely and replaces with custom content.
I2 — What is a LiveRegion? When should you use Polite vs Assertive?
Medium▼
A LiveRegion tells accessibility services to automatically announce when the content of that node changes — without the user navigating to it. This is essential for dynamic UI states that appear after user actions (loading completion, error messages, search results count).

LiveRegionMode.Polite: The announcement is queued and delivered after TalkBack finishes whatever it is currently saying. Use for non-critical updates — loading states, result counts, success confirmations. The user's current focus is not interrupted.

LiveRegionMode.Assertive: The announcement interrupts TalkBack immediately, even if it is mid-sentence. Use only for urgent, time-sensitive information — form validation errors, security alerts, session expiry warnings. Overusing Assertive is disruptive and will frustrate users.

Rule of thumb: Polite for informational updates, Assertive for errors and warnings.
I3 — How do you test accessibility in Compose UI tests (automated)?
Medium▼
Compose UI testing exposes the semantic tree via ComposeTestRule. You can query nodes by semantic properties and assert their values:

@Test
fun submitButton_hasCorrectContentDescription() {
    composeTestRule.setContent {
        TransferButton(amount = "50", recipient = "John")
    }
    composeTestRule
        .onNodeWithContentDescription("Transfer 50 pounds to John")
        .assertIsDisplayed()
        .assertHasClickAction()
}

@Test
fun errorMessage_isAnnounced() {
    composeTestRule.setContent { AmountField(error = "Amount required") }
    composeTestRule
        .onNodeWithText("Amount required")
        .assertIsDisplayed()
    // Verify LiveRegion property via semantics:
    composeTestRule
        .onNodeWithText("Amount required")
        .assert(hasScrollAction().not()) // sanity check
}
Key test methods: onNodeWithContentDescription(), onNodeWithText(), assertHasClickAction(), onNode(hasSemantics { ... }). Use printToLog() to dump the semantic tree for debugging.
I4 — [Coding] Add proper semantics to a row of icon buttons: Delete, Edit, and Share. Each has only an icon and no text.
MediumCoding▼
@Composable
fun ActionButtons(
    itemName: String,
    onDelete: () -> Unit,
    onEdit: () -> Unit,
    onShare: () -> Unit
) {
    Row(
        modifier = Modifier.semantics(mergeDescendants = false) {},
        horizontalArrangement = Arrangement.spacedBy(8.dp)
    ) {
        IconButton(
            onClick = onDelete,
            modifier = Modifier.minimumInteractiveComponentSize()
        ) {
            // Context-aware: includes item name so user knows what they're deleting
            Icon(
                imageVector = Icons.Default.Delete,
                contentDescription = "Delete $itemName"
            )
        }
        IconButton(
            onClick = onEdit,
            modifier = Modifier.minimumInteractiveComponentSize()
        ) {
            Icon(
                imageVector = Icons.Default.Edit,
                contentDescription = "Edit $itemName"
            )
        }
        IconButton(
            onClick = onShare,
            modifier = Modifier.minimumInteractiveComponentSize()
        ) {
            Icon(
                imageVector = Icons.Default.Share,
                contentDescription = "Share $itemName"
            )
        }
    }
}
Key points: each button's contentDescription includes the item name for context — TalkBack reads "Delete Invoice #1234" not just "Delete". minimumInteractiveComponentSize() ensures 48dp targets. Each button is a separate TalkBack focus point (not merged) so users can individually navigate to each action.

S1 — [Scenario] A user reports: "TalkBack reads the product price as 'Button 12 99' on the product card. It should say 'Product: Wireless Headphones, Price: 12 pounds 99'." The card is a Card composable with Image, two Texts (name and price), and an IconButton. How do you fix it?
HardScenario▼
Root causes:
1. The price Text "£12.99" is being read character-by-character because TalkBack doesn't know it's a monetary amount
2. The IconButton inside is probably not merged correctly — creating a "Button" announcement
3. mergeDescendants = true on the card merges ALL children including the button, producing "Button 12 99"

Fix — use clearAndSetSemantics on the card, and handle the button separately: 
Card(
    modifier = Modifier
        .clickable { onCardClick() }
        .clearAndSetSemantics {
            // Full control — format price for correct TalkBack reading
            contentDescription = "Product: ${product.name}, " +
                "Price: ${product.priceLabel}"  // priceLabel = "12 pounds 99"
            role = Role.Button
        }
) {
    Image(
        painter = rememberAsyncImagePainter(product.imageUrl),
        contentDescription = null  // card description covers it
    )
    Text(product.name)
    Text(product.priceLabel)
    // Add to cart button — OUTSIDE the clearAndSetSemantics scope or wrapped separately
    IconButton(onClick = onAddToCart) {
        Icon(
            Icons.Default.Add,
            contentDescription = "Add ${product.name} to cart"
        )
    }
}
Alternative: Keep mergeDescendants = true on the outer card but exclude the IconButton by wrapping it in a non-merged container. The best production pattern is clearAndSetSemantics for the card content + a separate IconButton outside that block with its own contentDescription. Also: priceLabel should be a formatted string like "12 pounds 99" not "£12.99" — the screen reader cannot reliably parse currency symbols.
S2 — A banking app fails an EU accessibility audit. The auditor's report says: "Form validation errors are not announced when they appear; users must manually navigate to discover them." How do you fix this architecturally?
Hard▼
The problem: Validation errors appear on screen but TalkBack does not announce them because the error message node does not have a LiveRegion set. TalkBack only reads nodes when the user navigates to them — it doesn't spontaneously read new content unless it's a LiveRegion.

Architectural fix — add at the component library level so all forms are covered automatically: 
@Composable
fun AppTextField(
    value: String,
    onValueChange: (String) -> Unit,
    label: String,
    error: String? = null,
    modifier: Modifier = Modifier
) {
    Column(modifier = modifier) {
        OutlinedTextField(
            value = value,
            onValueChange = onValueChange,
            label = { Text(label) },
            isError = error != null
        )
        if (error != null) {
            Text(
                text = error,
                color = MaterialTheme.colorScheme.error,
                style = MaterialTheme.typography.bodySmall,
                modifier = Modifier.semantics {
                    // Assertive: interrupts TalkBack to announce error immediately
                    liveRegion = LiveRegionMode.Assertive
                    contentDescription = "Error: $error"
                }
            )
        }
    }
}
Additional steps:
1. After form submission fails, move TalkBack focus to the first error field using FocusRequester.requestFocus()
2. Add a summary live region at the top: "3 errors found. Please correct the highlighted fields."
3. Ensure the error parameter is not a static string — it must change when the error appears (empty/null → error text) for LiveRegion to trigger
4. Write Compose UI tests that verify onNodeWithText(errorMessage).assertIsDisplayed() after submission
5. Test manually with TalkBack: submit invalid form, verify error is announced without touching the screen
S3 — How do you handle accessibility for a completely custom composable drawn with Canvas (a custom chart, a signature pad, a progress ring)?
Hard▼
The problem: Canvas drawing produces no AccessibilityNodeInfo entries — TalkBack sees nothing. Custom Canvas composables are completely invisible to accessibility services by default.

Solution: add explicit semantics to the Canvas composable: 
@Composable
fun AccountBalanceChart(
    dataPoints: List<Float>,
    currency: String,
    modifier: Modifier = Modifier
) {
    val latestValue = dataPoints.lastOrNull() ?: 0f
    val trend = if (dataPoints.last() > dataPoints.first()) "upward" else "downward"

    Canvas(
        modifier = modifier.semantics {
            // Describe the chart content meaningfully
            contentDescription = "Balance trend chart. " +
                "Current balance: $latestValue $currency. " +
                "Trend over last 30 days: $trend."
            // Mark as an image role so TalkBack announces it correctly
            role = Role.Image
        }
    ) {
        // canvas drawing code
    }
}

// For interactive Canvas (e.g., signature pad):
Canvas(
    modifier = Modifier
        .semantics {
            contentDescription = "Signature pad. Draw your signature here."
            role = Role.Image
            onClick("Clear signature") { clearSignature(); true }
        }
        .pointerInput(Unit) { /* gesture handling */ }
) { /* canvas drawing */ }
Key rules for Canvas accessibility:
1. Always add Modifier.semantics { contentDescription = "..." } — describe what the canvas shows, not how it's drawn
2. For decorative charts/illustrations: contentDescription = null if the data is described elsewhere on screen
3. For interactive canvas elements: add onClick action in semantics
4. For complex data visualisation: consider providing a text alternative (toggle button to switch to data table view) — much more useful than a long description
