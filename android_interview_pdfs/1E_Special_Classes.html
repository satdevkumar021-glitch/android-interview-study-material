1E — Kotlin Special Classes

data classes, enum classes, sealed classes & interfaces, object declarations, companion objects, anonymous objects — the Kotlin class variants that power Android architecture daily.

ID: 1E ⭐ Tier 1
🔍
1. Overview

What they are

Kotlin's special class variants solve recurring patterns that require verbose boilerplate in Java: value objects (data classes), fixed sets of constants (enum), exhaustive type hierarchies (sealed), singletons (object), static-like members (companion object), and one-off anonymous implementations (anonymous object).

Why they matter for Android

  • data class — domain models, DTOs, UI states, events
  • sealed class/interface — UiState, Result, navigation events, one-time UI effects
  • enum class — fixed sets: order status, payment type, network state
  • object — singleton services, Retrofit instance, constants file
  • companion object — factory methods, constants, newInstance() for Fragments
  • anonymous object — one-off interface implementations, test fakes inline
Senior Mental Model
sealed class is the most interview-critical here. It models closed type hierarchies — the compiler knows every possible subtype, enabling exhaustive when expressions. This is the foundation of safe, compile-time-checked UiState machines in MVVM.

2. How It Works

data class

data class UserProfile(
    val userId: String,
    val name: String,
    val email: String?
)

The compiler auto-generates: equals() / hashCode() (structural equality), toString(), copy(), and componentN() functions (for destructuring). All based on properties declared in the primary constructor.

val u1 = UserProfile("1", "Alice", "a@b.com")
val u2 = u1.copy(name = "Bob")          // new object, only name changed
val (id, name, email) = u1               // destructuring via componentN()
u1 == u2                                  // false — structural equality
Key Rules
  • Properties in body (not primary constructor) are NOT included in equals/hashCode/copy
  • Data classes cannot be abstract, open, sealed, or inner
  • At least one primary constructor parameter required
  • All primary constructor params should be val — mutability with var in data classes breaks structural equality invariants

enum class

enum class PaymentStatus(val displayName: String) {
    PENDING("Pending"),
    PROCESSING("Processing"),
    SUCCESS("Paid"),
    FAILED("Failed"),
    REFUNDED("Refunded");

    fun isFinal(): Boolean = this == SUCCESS || this == FAILED || this == REFUNDED
}

val status = PaymentStatus.SUCCESS
println(status.displayName)   // "Paid"
println(status.name)          // "SUCCESS" — built-in
println(status.ordinal)       // 2 — zero-based index
PaymentStatus.valueOf("PENDING")  // by name string
PaymentStatus.entries           // all values (Kotlin 1.9+), replaces values()

sealed class

sealed class UiState<out T> {
    data object Loading : UiState<Nothing>()
    data class  Success<T>(val data: T) : UiState<T>()
    data class  Error(val message: String) : UiState<Nothing>()
}

// Exhaustive when — compiler error if a subtype is missing
when (val state = uiState) {
    is UiState.Loading  -> showLoading()
    is UiState.Success  -> showData(state.data)
    is UiState.Error    -> showError(state.message)
    // No else needed — compiler guarantees exhaustiveness
}
sealed class vs sealed interface
sealed class: subclasses can only be in the same package (Kotlin 1.5+: same compilation unit). Can hold state via constructor. sealed interface: subclasses/implementors can be data classes, objects, or regular classes — more flexible. Preferred for pure type hierarchies with no shared state. Use sealed interface when subtypes need to implement multiple interfaces.

object declaration (Singleton)

// Thread-safe singleton — initialized on first access
object NetworkConfig {
    const val BASE_URL = "https://api.bank.com/"

    fun buildOkHttpClient(): OkHttpClient = OkHttpClient.Builder()

// Usage: NetworkConfig.BASE_URL
// Compiled to: public final class NetworkConfig with static INSTANCE field

companion object

class PaymentFragment : Fragment() {
    companion object {
        private const val ARG_PAYMENT_ID = "payment_id"

        // Factory method — idiomatic Fragment instantiation
        fun newInstance(paymentId: String): PaymentFragment =
            PaymentFragment().apply {
                arguments = Bundle().apply { putString(ARG_PAYMENT_ID, paymentId) }
            }
    }

    override fun onViewCreated(view: View, ...) {
        val paymentId = arguments?.getString(ARG_PAYMENT_ID)
    }
}
// Usage: PaymentFragment.newInstance("pay_123")
// companion object members are NOT truly static — accessed via INSTANCE
// Add @JvmStatic for Java interop

anonymous object

// One-off implementation — no need for a named class
val loginListener = object : AuthListener {
    override fun onSuccess(token: String) { navigateToHome() }
    override fun onFailure(e: Exception) { showError(e.message) }
}

// Anonymous object with no supertype — local temporary state
val counter = object {
    var count = 0
    fun increment() = ++count
}

sealed class vs enum class — when to pick which

When NOT to Use

Do NOT
  • Use data class for mutable state — all properties should be val
  • Put business logic in a data class body — keep it a dumb value object
  • Use object for things that need DI or testing — use Hilt @Singleton instead
  • Use enum when subtypes need different data shapes — use sealed class
  • Use companion object as a dumping ground for utility functions — extract to top-level or proper class
  • Use a plain object for sealed singleton subtypes (use data object instead — better toString() / equality)

Scenario
E-commerce app — order management. Each special class type appears in its natural production context across Clean Architecture layers.

data class — Domain Model

// domain/model/Order.kt
data class Order(
    val id: String,
    val items: List<OrderItem>,
    val status: OrderStatus,
    val totalAmount: Double,
    val createdAt: Long

    // Body properties excluded from equals/hashCode/copy

// Deep copy with modification — immutable update pattern
val updatedOrder = order.copy(status = OrderStatus.DELIVERED)

enum class — Order Status

// domain/model/OrderStatus.kt
enum class OrderStatus(
    val displayName: String,
    val colorRes: Int
) {
    PLACED("Order Placed", R.color.status_blue),
    CONFIRMED("Confirmed", R.color.status_indigo),
    SHIPPED("Shipped", R.color.status_orange),
    DELIVERED("Delivered", R.color.status_green),
    CANCELLED("Cancelled", R.color.status_red);

    val isFinal: Boolean

sealed interface — UiState

// presentation/orders/OrderListUiState.kt
sealed interface OrderListUiState {
    data object Loading  : OrderListUiState
    data object Empty    : OrderListUiState
    data class  Success(val orders: List<Order>) : OrderListUiState
    data class  Error(val message: String, val retryable: Boolean = true) : OrderListUiState
}

// One-time events (side effects) — also sealed
sealed interface OrderEvent {
    data class NavigateToDetail(val orderId: String) : OrderEvent
    data class ShowSnackbar(val message: String) : OrderEvent
    data object ShowCancelConfirmation : OrderEvent
}

ViewModel — sealed state + events

// presentation/orders/OrderListViewModel.kt
@HiltViewModel
class OrderListViewModel @Inject constructor(
    private val getOrders: GetOrdersUseCase
) : ViewModel() {

    private val _uiState = MutableStateFlow<OrderListUiState>(OrderListUiState.Loading)
    val uiState = _uiState.asStateFlow()

    private val _events = MutableSharedFlow<OrderEvent>()
    val events = _events.asSharedFlow()

    fun loadOrders() {
        viewModelScope.launch {
            getOrders()
                .onSuccess { orders ->
                    _uiState.value = if (orders.isEmpty())
                        OrderListUiState.Empty
                    else
                        OrderListUiState.Success(orders)
                }
                .onFailure {
                    _uiState.value = OrderListUiState.Error(it.message ?: "Unknown")
                }
        }
    }

    fun onOrderClicked(orderId: String) {
        viewModelScope.launch {
            _events.emit(OrderEvent.NavigateToDetail(orderId))
        }
    }
}

Compose UI — exhaustive when on sealed

@Composable
fun OrderListScreen(viewModel: OrderListViewModel = hiltViewModel()) {
    val uiState by viewModel.uiState.collectAsStateWithLifecycle()

    when (uiState) {                                     // exhaustive — no else needed
        OrderListUiState.Loading -> LoadingIndicator()
        OrderListUiState.Empty   -> EmptyState()
        is OrderListUiState.Success -> OrderList((uiState as OrderListUiState.Success).orders)
        is OrderListUiState.Error   -> ErrorView((uiState as OrderListUiState.Error).message)
    }
}

Interviewer Comparisons

Expect These
  • sealed class vs enum — enum: fixed instances, same data shape; sealed: fixed subtypes, different data per subtype
  • sealed class vs sealed interface — interface: more flexible (multi-interface), no shared state; class: shared constructor/fields
  • data class vs regular class — data: auto value semantics; regular: manual, needed for inheritance
  • object vs companion object — object is standalone singleton; companion is tied to an enclosing class
  • object vs Hilt @Singleton — object is hard to test; Hilt singleton is injectable and mockable

6. Pitfalls & Best Practices

data class with var — breaks equals/hashCode contract

// ❌ BAD — mutable data class breaks structural equality guarantees
data class CartItem(var quantity: Int, val productId: String)
val item = CartItem(1, "p1")
val set = hashSetOf(item)
item.quantity = 2    // mutates! hashCode changes → item "lost" in the set
println(item in set)  // false! bucket changed
// ✅ GOOD — all val; use copy() for updates
data class CartItem(val quantity: Int, val productId: String)
val updated = item.copy(quantity = 2)   // new object

Body property included in equals — invisible bug

// ❌ BAD — 'displayName' is in the body; NOT compared in equals()
data class Product(val id: String) {
    var displayName: String = ""   // body property — ignored by equals/hashCode
}
val a = Product("1").apply { displayName = "Phone" }
val b = Product("1").apply { displayName = "Laptop" }
println(a == b)  // true! displayName not in equals
// ✅ GOOD — all meaningful fields in primary constructor
data class Product(val id: String, val displayName: String)

sealed class when without else — missing new subtype

// ❌ BAD — using else loses the compile-time exhaustiveness guarantee
when (state) {
    is UiState.Loading -> showLoading()
    is UiState.Success -> showData()
    else -> showError()  // silently swallows new subtypes added later
}
// ✅ GOOD — no else; adding a new sealed subtype causes compile error here
when (state) {
    is UiState.Loading -> showLoading()
    is UiState.Success -> showData()
    is UiState.Error   -> showError()
}

object singleton vs Hilt — testability trap

// ❌ BAD — singleton object impossible to replace in tests
object AnalyticsManager {
    fun track(event: String) { /* sends to Firebase */ }
}
// In tests: can't inject a no-op; real events fire
// ✅ GOOD — interface + Hilt @Singleton
interface Analytics { fun track(event: String) }
class FirebaseAnalytics @Inject constructor() : Analytics { ... }
// Test: inject FakeAnalytics that does nothing

enum ordinal as persisted value — fragile

// ❌ BAD — storing ordinal in DB; reordering enum breaks all stored data
dao.insert(order.copy(statusCode = status.ordinal))

// ✅ GOOD — store name or a stable Int field
enum class OrderStatus(val code: Int) {
    PLACED(1), SHIPPED(2), DELIVERED(3), CANCELLED(4)
}
dao.insert(order.copy(statusCode = status.code))  // stable

Production Best Practices

  1. All data class primary constructor properties should be val — use copy() for updates.
  2. Use sealed interface over sealed class when subtypes need no shared state — more flexible.
  3. Never use else in a when on a sealed type — defeats the exhaustiveness guarantee.
  4. Use data object (Kotlin 1.9+) for no-data sealed subtypes — correct toString() and equality.
  5. Use enum class for fixed constants; use a stable explicit code: Int field if persisting to DB.
  6. Keep companion object lean — factory methods and constants only, not utility functions.
  7. Prefer Hilt @Singleton over raw object for anything that needs to be replaced in tests.

7. Interview Answer Framework

30-Second Answer

"Kotlin's special classes each solve a specific pattern. Data classes give you value semantics — equals, hashCode, copy, destructuring — auto-generated from primary constructor properties. Sealed classes and interfaces model closed type hierarchies, enabling exhaustive when expressions — the compiler guarantees you handle every subtype. I use sealed interface for UiState and UI events throughout my ViewModels. Enum classes handle fixed constant sets. Object declarations are thread-safe singletons. Companion objects provide factory methods and constants scoped to a class."

2-Minute Structured Answer

"I'll focus on the ones that come up most in Android work.

Data classes: I use these for domain models, DTOs, and UI states. The key thing is they provide structural equality — two instances with the same property values are equal. All primary constructor properties should be val. Properties in the body are NOT included in equals or copy, which is a common source of subtle bugs. I use copy() for immutable updates — never mutate.

Sealed classes/interfaces: this is the most powerful one. A sealed type has a closed set of subtypes known at compile time. This makes when exhaustive — no else branch needed, and if I add a new subtype later, every when expression that doesn't handle it becomes a compile error. I model every ViewModel's state as a sealed interface with data object Loading, data object Empty, data class Success(val data), and data class Error(val message). I also use a separate sealed interface for one-time events like navigation and snackbars.

Sealed vs enum: enum is for a fixed set of named constants where all instances share the same fields. Sealed is for when each subtype needs different data — Success needs a result, Error needs a message, Loading needs nothing.

Object vs companion: object is a standalone singleton. Companion object lives inside a class and gives you factory methods and constants scoped to that class — the idiomatic way to do Fragment.newInstance()."

Must-Mention Points

Likely Follow-up Questions

Senior-Level Insight (Stand Out)

Say This
"I model UI state as a sealed interface with data object for no-data states and data class for states with data. I keep state and one-time events separate — state goes in StateFlow, events go in SharedFlow (replay=0). The sealed interface guarantees the UI handles every state, and adding a new state (e.g., Refreshing) causes compile errors at every when expression — you can't miss it. 9. Interview Questions (Self-Check)
How to use
Answer first, then reveal.

Basic

B1 — What does a data class auto-generate? What is NOT included in equals/hashCode?
Easy▼
Auto-generated: equals(), hashCode(), toString(), copy(), and componentN() functions for destructuring — all based on properties declared in the primary constructor only.

NOT included: properties declared in the class body (outside the primary constructor). This is a common source of bugs — if you add a var property in the body, two instances with different body-property values will still be considered equal if their constructor properties match.
B2 — What is a sealed class? How does it enable exhaustive when?
Easy▼
A sealed class defines a closed type hierarchy — all direct subclasses must be in the same compilation unit (package in Kotlin 1.5+). Because the compiler knows every possible subtype at compile time, a when expression on a sealed type can be exhaustive without an else branch. If you add a new subtype later, every when expression that doesn't handle it becomes a compile error — preventing silent bugs.
B3 — What is the difference between object and companion object?
Easy▼
object is a standalone singleton class declaration — it exists independently. companion object lives inside another class and its members are accessed via the enclosing class name (like Java static members, but not truly static in JVM bytecode). Only one companion object per class is allowed. Add @JvmStatic to companion members for actual Java static interop. Common use: companion object { fun newInstance() } for Fragment factories.

Intermediate

I1 — When would you use a sealed class vs an enum class?
Medium▼
Enum: fixed set of named constants where all instances share the same data shape. Good for: PaymentStatus, Theme, NetworkType. Each enum value is a singleton.

Sealed class: fixed set of subtypes where each subtype can carry different data. Good for: UiState (Loading has no data, Success has a list, Error has a message), Result, navigation events. Each subtype can have its own constructor and multiple instances.

Rule: if the variants have the same fields → enum. If each variant needs different data → sealed.
I2 — (Coding) What is wrong? data class User(val id: String) { var name = "" }; val a = User("1").apply { name = "Alice" }; val b = User("1").apply { name = "Bob" }; println(a == b)
MediumCoding▼
Prints true — which is likely NOT what the developer intended.

name is declared in the class body, not the primary constructor. Data class equals() and hashCode() are generated only from primary constructor properties (id here). So two User objects with the same id but different name values are considered equal.

Fix: move name to the primary constructor: data class User(val id: String, val name: String)
I3 — What is data object? Why is it better than plain object for sealed subtypes?
Medium▼
data object (Kotlin 1.9+) is a singleton with auto-generated equals(), hashCode(), and toString() — like a data class with no properties.

Why better for sealed subtypes: a plain object's toString() returns the JVM identity string like "UiState$Loading@1a2b3c" — useless for logging and debugging. A data object's toString() returns "Loading" — much cleaner. Also, equals() works correctly (two references to the same singleton are equal), though for objects this is true anyway since there's only one instance.
I4 — Why should you never use else in a when expression on a sealed type?
Medium▼
Using else defeats the compile-time exhaustiveness guarantee. If you add a new subtype to the sealed hierarchy later, the when with else will silently handle it with the else branch — the compiler won't warn you. You could be rendering the wrong UI for a new state for weeks without realizing.

Without else, adding a new sealed subtype causes a compile error at every when expression that doesn't handle it. This is intentional — it forces you to explicitly handle every state, making the system fail fast at compile time rather than silently at runtime.

Senior / Scenario

S1 — Design a complete UiState and ViewEvent sealed hierarchy for a payment screen. Justify your choices.
HardCoding▼
// State — flows in StateFlow, represents current screen state
sealed interface PaymentUiState {
    data object Idle       : PaymentUiState
    data object Loading    : PaymentUiState
    data class  Success(val transactionId: String) : PaymentUiState
    data class  Error(val message: String, val retryable: Boolean) : PaymentUiState
}

// Events — one-time side effects in SharedFlow(replay=0)
sealed interface PaymentEvent {
    data class  NavigateToReceipt(val txId: String) : PaymentEvent
    data class  ShowSnackbar(val msg: String) : PaymentEvent
    data object NavigateBack : PaymentEvent
}
Justifications: sealed interface (not class) — no shared state; subtypes can implement other interfaces. data object for Idle/Loading — no data, but clean toString(). data class for Success/Error — each has different fields. Events separate from state — state is persistent (StateFlow), events fire once (SharedFlow replay=0) to prevent re-delivery on recomposition.
S2 — (Scenario) A junior dev stored PaymentStatus.ordinal in the Room database. Three months later, the team added a new status between PROCESSING and SUCCESS. What broke and how do you fix it?
HardScenario▼
What broke: ordinal is the zero-based position in the enum declaration. Adding a new status shifted all ordinals after it by 1. Every row in the DB that had ordinal 2 (SUCCESS) is now interpreted as the new status. Orders that were previously marked SUCCESS are now read back as the wrong status — silent data corruption.

Fix: Add a stable code: Int field to the enum that never changes regardless of declaration order: 
enum class PaymentStatus(val code: Int) {
    PENDING(1), PROCESSING(2), UNDER_REVIEW(5), SUCCESS(3), FAILED(4)
}
Write a Room migration to convert stored ordinal values to the new stable codes. Going forward, always persist status.code, not status.ordinal. Add a Room TypeConverter that converts by code.
S3 — (Scenario) copy() on a data class gives you a "deep copy" — true or false? What are the implications in an Android app?
HardScenario▼
False. copy() performs a shallow copy — only the top-level object is a new instance. Any nested objects (lists, other data classes) are shared references.

Implications: 
data class Cart(val items: MutableList<Item>)
val cart1 = Cart(mutableListOf(Item("A")))
val cart2 = cart1.copy()
cart2.items.add(Item("B"))   // MUTATES cart1.items too!
Fix: use immutable collections (List not MutableList) in data classes. If you need a deep copy, manually create new instances. In StateFlow with Compose, sharing mutable lists between states causes incorrect recomposition — Compose compares by reference for stability. Always use immutable List<T> in your UI state data classes.
