30B — Login / Authentication System

Design a complete authentication system: email/password login, OAuth, biometric, JWT token management, silent refresh via OkHttp interceptor, secure storage, and session lifecycle.

ID: 30B ★ Senior Differentiator
🔍
1. Problem Statement

Requirements

Functional

  • Email/password login and registration
  • OAuth 2.0 / social login (Google, Apple)
  • Biometric authentication (fingerprint, face)
  • Remember me / persistent sessions
  • Secure token storage and automatic token refresh
  • Logout — clear all session data, navigate to login

Non-Functional

  • Tokens never stored in plaintext or SharedPreferences
  • Silent token refresh — user never sees "session expired" unexpectedly
  • Biometric enrollment tied to security key — re-enrollment required if biometrics change
  • Thread-safe token refresh (concurrent requests during refresh must wait, not each refresh independently)

3. Data Flow

Login Flow

User enters email + password → taps Login
  → AuthViewModel.onLoginClicked()
  → LoginUseCase.invoke(email, password)
  → AuthRepository.login(email, password)
  → Retrofit POST /auth/login
  → Response: { access_token, refresh_token, expires_in }
  → TokenStorage.save(accessToken, refreshToken, expiry)
  → AuthRepository emits Success(AuthSession)
  → AuthViewModel updates uiState = LoggedIn
  → NavController navigates to HomeScreen
    (FLAG_ACTIVITY_CLEAR_TASK clears login back stack)

Automatic Token Refresh Flow

App makes any API request
  → TokenRefreshInterceptor adds Authorization: Bearer {accessToken}
  → Server returns 401 Unauthorized (token expired)
  → OkHttp Authenticator is called
  → Checks refreshToken exists
  → Calls AuthApi.refreshToken(refreshToken) synchronously
  → (Thread-safe: Mutex prevents concurrent refreshes)
  → On success: save new accessToken + refreshToken
  → Retry original request with new accessToken
  → On refresh failure (401 on refresh):
      → TokenStorage.clear()
      → Emit session expired event
      → Navigate to LoginScreen

Biometric Auth Flow

Biometric Login button tapped
  → BiometricUseCase creates CryptoObject
      (Cipher initialized with Keystore key)
  → BiometricPrompt.authenticate(cryptoObject)
  → User authenticates with fingerprint/face
  → OnSuccess callback: CryptoObject has authenticated Cipher
  → Decrypt stored refresh_token using Cipher
  → AuthRepository.refreshToken(decryptedRefreshToken)
  → Navigate to HomeScreen

Logout Flow

Logout tapped / session expired
  → LogoutUseCase.invoke()
  → AuthRepository.logout()
      → API POST /auth/logout (invalidate server-side)
      → TokenStorage.clear()
  → AuthViewModel emits LoggedOut state
  → NavController navigate to LoginScreen with:
      Intent.FLAG_ACTIVITY_CLEAR_TASK or
      NavOptions popUpTo(root) inclusive=true

4. Key Design Decisions

1. Token Storage — EncryptedSharedPreferences vs Keystore

OptionSecurityUse When
SharedPreferences (plain)❌ Plaintext on rooted deviceNever for tokens
EncryptedSharedPreferences✅ AES-256 encrypted, Keystore-backed keyAccess + refresh tokens — standard choice
Android Keystore directly✅✅ Hardware-backed, key never leaves KeystoreKeys for biometric binding — highest security
In-memory only✅ Wiped on process killAccess token only (short-lived)

2. JWT Strategy

// Access token: short-lived (15 min)
// • Stored in memory (most secure) OR EncryptedSharedPreferences
// • Sent in every API request as Bearer token
// • If it expires: use refresh token to get a new one silently

// Refresh token: long-lived (30 days)
// • Stored in EncryptedSharedPreferences only
// • Used only to get a new access token
// • Rotated on each refresh (server issues new refresh token)
// • On refresh failure: session expired → force login

3. Thread-Safe Token Refresh

class TokenRefreshAuthenticator @Inject constructor(
    private val authRepository: AuthRepository
) : Authenticator {

    private val refreshMutex = Mutex()

    override fun authenticate(route: Route?, response: Response): Request? {
        if (response.code != 401) return null
        // runBlocking here because OkHttp Authenticator is synchronous
        return runBlocking {
            refreshMutex.withLock {
                // Check if another thread already refreshed while we waited
                val currentToken = authRepository.getAccessToken()
                val requestToken = response.request.header("Authorization")
                    ?.removePrefix("Bearer ")
                if (currentToken != requestToken) {
                    // Token already refreshed by another request
                    return@runBlocking response.request.newBuilder()
                        .header("Authorization", "Bearer $currentToken")
                        .build()
                }
                val result = authRepository.refreshToken()
                result.getOrNull()?.let { session ->
                    response.request.newBuilder()
                        .header("Authorization", "Bearer ${session.accessToken}")
                        .build()
                }
            }
        }
    }
}

4. Biometric Binding

// Keystore key tied to biometric enrollment
// Key is invalidated if biometrics change (new fingerprint added)
val keyGenSpec = KeyGenParameterSpec.Builder(
    "biometric_key",
    KeyProperties.PURPOSE_ENCRYPT or KeyProperties.PURPOSE_DECRYPT
).apply {
    setBlockModes(KeyProperties.BLOCK_MODE_CBC)
    setEncryptionPaddings(KeyProperties.ENCRYPTION_PADDING_PKCS7)
    setUserAuthenticationRequired(true)
    setInvalidatedByBiometricEnrollment(true)  // KEY SECURITY FEATURE
}.build()
KeyGenerator.getInstance(KeyProperties.KEY_ALGORITHM_AES, "AndroidKeyStore")
    .also { it.init(keyGenSpec) }
    .generateKey()

7. Interview Framework

30-Second Answer

"The auth system has three layers: a LoginScreen with AuthViewModel, AuthRepository handling API calls, and TokenStorage using EncryptedSharedPreferences for secure persistence. Access tokens are short-lived (15 min), refresh tokens long-lived (30 days). An OkHttp Authenticator handles silent refresh on 401 — thread-safe via Mutex so concurrent requests don't each trigger their own refresh. Biometrics use a Keystore key with setInvalidatedByBiometricEnrollment — re-enrollment required if fingerprints change."

2-Minute Answer

"Login flow: email/password → AuthRepository.login() → Retrofit POST /auth/login → tokens stored in EncryptedSharedPreferences (AES-256, Keystore-backed). JWT strategy: access token is short-lived (15 min), refresh token is long-lived (30 days) and rotated on use. Token refresh is completely transparent via OkHttp Authenticator: on 401, it calls /auth/refresh synchronously, saves new tokens, and retries the original request. Mutex ensures only one refresh runs — if 5 concurrent requests all get 401, only one refresh happens and the others reuse the result. Biometric: the Keystore key has setInvalidatedByBiometricEnrollment(true) — if the user adds a new fingerprint, the key is invalidated and we catch KeyPermanentlyInvalidatedException to force re-enrollment. Logout clears all tokens and navigates with FLAG_ACTIVITY_CLEAR_TASK so the back stack contains only the login screen. For OAuth, use AppAuth library with PKCE — never implement OAuth manually."

Must-Mention Points

1
EncryptedSharedPreferences for tokens — never plain SharedPreferences
2
OkHttp Authenticator for silent token refresh on 401 — transparent to all callers
3
Mutex in Authenticator — prevents 5 concurrent 401s each triggering independent refreshes
4
setInvalidatedByBiometricEnrollment(true) — biometric key invalidated if enrollment changes
5
Logout: clear tokens + FLAG_ACTIVITY_CLEAR_TASK — back button cannot return to authenticated screens

Senior Insight

Senior Differentiator
The concurrent token refresh problem is a classic. Without Mutex: 5 simultaneous API calls all get 401, all call refreshToken() concurrently, the server issues 5 new tokens but only one is stored. The other 4 refresh tokens are now invalid — user gets logged out unnecessarily. The fix: check whether the token has already changed before using your result (another thread may have already refreshed). This "check-after-lock" pattern is the correct solution.

9. Interview Questions
1. Where should you store JWT tokens on Android?
Basic⌄
EncryptedSharedPreferences backed by Android Keystore. It uses AES-256-GCM encryption with the key stored in the hardware-backed Keystore — the key cannot be extracted from the device. Never use plain SharedPreferences (plaintext on rooted devices), DataStore (not designed for tokens), or external storage. For extra security: keep access token in memory only (wiped on process kill) and only persist refresh token in EncryptedSharedPreferences.
2. How does OkHttp Authenticator differ from an Interceptor for token refresh?
Basic⌄
Interceptor runs before every request — you'd need to check token expiry time and refresh proactively. This can miss edge cases (clock skew, server-side revocation). Authenticator is triggered reactively by the server's 401 response — always accurate. OkHttp calls authenticate() exactly when authentication is needed, passes the failed response, and returns a new Request with updated credentials. Much cleaner and accurate than timestamp-based proactive refresh.
3. What is the "concurrent token refresh" problem and how do you solve it?
Basic⌄
Problem: 5 simultaneous API calls all get 401. All 5 call refreshToken() concurrently. Server issues 5 tokens — but each refresh token can only be used once (server rotates them). 4 of the 5 refresh attempts fail → user force-logged-out. Solution: Mutex in the Authenticator. Only one thread refreshes at a time. Threads 2-5 wait for the Mutex. When they get the lock, they check: is the current stored token different from what was in our failed request? If yes, another thread already refreshed — just retry with the new token without calling refresh again.
4. How does setInvalidatedByBiometricEnrollment(true) work?
Intermediate⌄
When creating a Keystore key with setInvalidatedByBiometricEnrollment(true), Android invalidates the key if the device's biometric enrollment changes — e.g., a new fingerprint is added. The next time the app tries to use the key, it gets KeyPermanentlyInvalidatedException. This prevents an attacker from adding their fingerprint and accessing the app's biometric-locked data. On exception: catch it, delete the key, show "biometric re-enrollment required" dialog, and generate a new key after re-authentication.
5. Walk through the biometric authentication flow.
Intermediate⌄
Setup (once): Generate Keystore key. Encrypt refresh_token with the key. Store encrypted token in EncryptedSharedPreferences. Login flow: Get Cipher from Keystore key in DECRYPT mode. Wrap in CryptoObject. Call BiometricPrompt.authenticate(cryptoObject). User authenticates. onAuthenticationSucceeded provides authenticated CryptoObject. Use Cipher to decrypt refresh_token. Call AuthRepository.refreshToken(decryptedToken). Navigate to home on success. The private key never leaves the Keystore — biometric authentication unlocks the hardware key operation.
6. How do you implement "remember me" functionality securely?
Intermediate⌄
Store the refresh_token in EncryptedSharedPreferences on successful login. On next app launch: check if refresh_token exists → call /auth/refresh → if successful, user is silently logged in. If refresh fails (token expired): clear tokens, show login screen. For "remember me" toggle: if unchecked, only store tokens in memory — they're lost on process kill. If checked, persist in EncryptedSharedPreferences. Distinguish between session timeout (acceptable UX warning) vs force logout (security event requiring re-auth).
7. How do you ensure the back stack is clean after logout?
Intermediate⌄
Two approaches: (1) Activity-based: startActivity(loginIntent.apply { flags = Intent.FLAG_ACTIVITY_NEW_TASK or Intent.FLAG_ACTIVITY_CLEAR_TASK }) — clears entire back stack, makes login the only activity. (2) Navigation Component: navController.navigate(loginRoute) { popUpTo(navGraph.startDestinationId) { inclusive = true } } — clears entire nav back stack to root. After this, pressing back exits the app rather than returning to authenticated screens. Also check AuthState on every screen's onResume to catch token expiry across deep links.
8. How would you implement OAuth 2.0 login (Google Sign-In) securely?
Senior⌄
Use AppAuth-Android library with PKCE (Proof Key for Code Exchange). Never implement OAuth manually. Flow: (1) Create AuthorizationRequest with code_verifier (random). Send authorization_code request to provider. (2) Receive authorization code via custom URI scheme or App Link callback. (3) Exchange code for tokens using code_verifier (server-side PKCE validation). (4) Send ID token to your backend for validation → your backend issues your app's JWT pair. Never use the OAuth provider's access token directly with your backend — always exchange for your own tokens.
9. How do you detect and handle session expiry across different app states?
Senior⌄
Multiple detection points: (1) Foreground API call gets 401 and refresh fails → Authenticator emits sessionExpiredFlow. (2) App resumes from background → check token expiry timestamp in EncryptedSharedPreferences — if expired, trigger refresh or show re-auth. (3) WorkManager background task gets 401 → emit session event. Handle via: a SharedFlow<Unit> sessionExpiredFlow in AuthRepository. Collect in RootComposable or Application.onCreate with a ProcessLifecycleOwner. On emission: clear tokens, navigate to login. UX: show "Your session expired. Please log in again." — don't silently lose user state.
10. What security risks exist in mobile auth and how do you mitigate them?
Scenario⌄
Risks: (1) Token in plaintext storage → Mitigation: EncryptedSharedPreferences. (2) Token in logs → Mitigation: never log auth headers; okhttp.log level = BASIC not HEADERS. (3) SSL stripping → Mitigation: Certificate pinning (OkHttp CertificatePinner). (4) Biometric bypass → Mitigation: setInvalidatedByBiometricEnrollment + CryptoObject binding — biometric without crypto is weaker. (5) Refresh token reuse attack → Mitigation: refresh token rotation — server invalidates old refresh token on use. (6) Backup/restore exposes tokens → Mitigation: android:allowBackup="false" or exclude EncryptedSharedPreferences file from backup rules.
