7A — Compose Fundamentals

@Composable, declarative vs imperative UI, the Composition, recomposition mechanics, slot table, State<T>, remember, and the composable lifecycle.

ID: 7A ⭐ Tier 1 🔥 Highest Priority
🔍
1. Overview

Declarative vs Imperative UI

Imperative (View system): You mutate existing UI objects — find the TextView, call setText(). The view lives in memory, you issue commands to change it. You control HOW the view changes.

Declarative (Compose): You describe what the UI should look like for the current state. When state changes, Compose re-runs your function and figures out what changed. You control WHAT the UI should show, Compose handles HOW to update it.

Key concepts

  • @Composable — annotates a function that describes UI; can call other composables and read state
  • Composition — the in-memory tree of composable calls; the result of running all your @Composable functions
  • Recomposition — Compose re-runs composables when their inputs (state) change
  • Slot table — the data structure Compose uses to store composition state (remember values, positions)
  • State<T> — a value holder that triggers recomposition when its value changes
Senior Mental Model
In Compose, a function is not called once. It is called on every recomposition. Code inside a composable runs for every state change that affects it. This is fundamentally different from the View system. Everything that should NOT re-run on every frame must be wrapped in remember { } or moved outside the composable.
⚙
2. How Compose Works

The Composition tree

// This produces a tree in the Composition:
@Composable
fun ProductScreen(product: Product) {
    Column {            // node in tree
        ProductImage(product.imageUrl)    // child node
        ProductTitle(product.name)        // child node
        PriceTag(product.price)           // child node
    }
}
// Compose tracks each node's position using the slot table
// Position = call site in source code (not runtime object)

The Slot Table — how Compose tracks state

The slot table is a flat array of slots. Every composable call occupies a group of slots that store: the node identity, remember values, and position. When recomposition runs, Compose walks the slot table comparing old and new state at each position.

// The POSITION in the call tree is the identity
// Two calls at the same position are the SAME composable
for (item in items) {
    ItemCard(item)  // each has a position based on loop index
}
// If you insert an item at the beginning, ALL positions shift
// → Compose sees all cards as "changed"
// Fix: use key() to give stable identity
for (item in items) {
    key(item.id) { ItemCard(item) }  // stable identity by item.id
}

Composition lifecycle

PhaseDescription
Enter CompositionComposable called for the first time; remember initializers run; effects (LaunchedEffect) are launched
RecomposeState changed; composable re-runs with new inputs; unchanged composables skipped
Leave CompositionComposable removed from tree; remember values cleared; DisposableEffect cleanup runs

3. Recomposition

What triggers recomposition

Recomposition is triggered when a State<T> value that was read during a previous composition changes. Compose tracks every State read during composition — this is the "snapshot system."

@Composable
fun Counter() {
    var count by remember { mutableStateOf(0) }

    // Compose reads "count" here — this composable is subscribed
    Text(text = "Count: $count")     // re-runs when count changes
    Button(onClick = { count++ }) {   // lambda captures count
        Text("Increment")
    }
}
// When count++ fires: State changes → Compose schedules recomposition
// Only Counter() re-runs (not the whole screen)

Smart recomposition — skipping

@Composable
fun Parent() {
    var count by remember { mutableStateOf(0) }
    Column {
        CounterDisplay(count)    // ← reads count: WILL recompose
        StaticContent()         // ← reads nothing from count
    }
}

@Composable
fun StaticContent() {
    Text("I never change")
    // Compose: if inputs same as before → SKIP this composable
}
// StaticContent is NOT recomposed when count changes
// Compose checks all params — if equal, skips execution

4. State<T> & remember

State<T> — the recomposition trigger

// Three equivalent ways to declare state:

// 1. State + by delegate (most common)
var isExpanded by remember { mutableStateOf(false) }
isExpanded = true   // direct assignment via delegate

// 2. Explicit State object
val expandedState: MutableState<Boolean> = remember { mutableStateOf(false) }
expandedState.value = true

// 3. Destructure (read only + setter separate)
val (expanded, setExpanded) = remember { mutableStateOf(false) }

remember — survival across recompositions

// remember: survives recomposition, does NOT survive Activity recreation
val items = remember { mutableListOf<String>() }
// Created once, stored in slot table, same object on every recomposition

// remember(key): re-creates when key changes
val formatter = remember(locale) {
    NumberFormat.getInstance(locale)  // re-create only if locale changes
}

// WITHOUT remember: object created on EVERY recomposition
val expensiveObj = ExpensiveObject()  // ❌ new instance per recomposition!
val expensiveObj = remember { ExpensiveObject() }  // ✅ created once
Key Rule
Any object creation that should NOT happen on every recomposition must be inside remember { }. This includes: list allocations, format objects, painters, gesture detectors, and any complex objects.

5. Production Example

E-commerce: product card with composition lifecycle

@Composable
fun ProductCard(
    product: Product,
    onAddToCart: () -> Unit   // event callback — hoisted
) {
    // Local UI state — survives recompositions but not process death
    var isExpanded by remember { mutableStateOf(false) }

    // Expensive object — created once, reused on recompositions
    val currencyFormat = remember(product.currency) {
        NumberFormat.getCurrencyInstance(Locale.forLanguageTag(product.currency))
    }

    Card(onClick = { isExpanded = !isExpanded }) {
        Column {
            ProductImage(url = product.imageUrl)

            // This composable only recomposes if product.name changes
            Text(text = product.name, style = MaterialTheme.typography.titleMedium)
            Text(text = currencyFormat.format(product.price))

            // AnimatedVisibility: enters/leaves composition
            AnimatedVisibility(visible = isExpanded) {
                Text(text = product.description)
            }

            Button(onClick = onAddToCart) {
                Text("Add to Cart")
            }
        }
    }
}

// Screen-level: state hoisted to ViewModel
@Composable
fun ProductScreen(viewModel: ProductViewModel = hiltViewModel()) {
    val state by viewModel.uiState.collectAsStateWithLifecycle()

    when (val s = state) {
        is Loading -> LoadingSpinner()
        is Success -> ProductCard(s.product, onAddToCart = viewModel::addToCart)
        is Error -> ErrorMessage(s.message)
    }
}

6. Pitfalls & Best Practices
Pitfall 1 — Side effects in composable body
Composables can run multiple times. Writing to a database, logging analytics, or network calls in the composable body (not in a LaunchedEffect) will happen on every recomposition — potentially thousands of times. Side effects must always be in LaunchedEffect, DisposableEffect, or SideEffect.
Pitfall 2 — Creating objects without remember
Creating a new list, Painter, Animator, or any object directly in a composable body allocates a new object on every recomposition. Wrap with remember { } to create once and store in the slot table.
Pitfall 3 — Reading State outside of composable context
If you read a State<T> inside a lambda (like an onClick handler) without reading it in the composable body, the composable doesn't subscribe — it won't recompose when the state changes. Ensure state reads happen directly in the composable body.
Best Practice — Keep composables stateless
Composables should ideally be pure functions: same inputs → same output. Push state up to the ViewModel or calling composable. Stateless composables are easier to test, preview, and reuse.

7. Interview Framework

30-second answer

"Compose is a declarative UI framework. @Composable functions describe what the UI should look like for given state. When state changes, Compose re-runs affected composables — this is called recomposition. The slot table stores composition state including remember values. Compose skips composables whose inputs haven't changed — smart recomposition."

2-minute answer

"The fundamental shift is from imperative (mutate views) to declarative (describe what you want). In the View system, you call setText() on a TextView. In Compose, you call Text('currentValue') — when the value changes, the composable reruns automatically.

The Composition is the in-memory tree of composable calls. The slot table is the data structure backing it — a flat array where each composable call's position is its identity. This is why key() matters in lists — without stable keys, inserting an item shifts all positions, making Compose think every item changed.

State<T> is the trigger for recomposition. When you read a State value inside a composable, Compose subscribes that composable to the state. When the state changes, only the composables that read it are recomposed — not the whole tree. Everything that should survive recompositions but not re-execute must be in remember { }."

Must-mention points

1
Declarative: describe WHAT; Compose figures out HOW to update
2
Recomposition: triggered by State reads; only affected composables re-run
3
Slot table: position-based identity; why key() matters in lists
4
remember { }: survives recomposition; stores in slot table
5
No side effects in composable body: use LaunchedEffect/DisposableEffect

Follow-up Q&A

Q: "How does Compose know which composables to recompose?"

A: Compose uses a snapshot system. Every State read inside a composable registers the composable as an observer. When the state mutates, all registered observers are scheduled for recomposition. Compose then re-runs those composables and compares their output with the previous run — unchanged subtrees are skipped.

Q: "What is the slot table?"

A: The slot table is the data structure that stores the composition. It's a flat array of slots where each composable call occupies a group of slots containing: the composable's runtime state, remember values, position in the call hierarchy. The position in the source code (call site) is used as the composable's identity — not a runtime object reference like the View system uses.

Senior insight

Senior Insight
Understanding the slot table explains the Compose "if" gotcha: if (condition) { TextA() } else { TextB() } — depending on whether condition is true, a different composable occupies the same slot position. If condition flips, Compose sees a composable "leaving" and "entering" at that position — re-initializing all remember values. This is why conditional composables lose their state when the condition changes, and why you sometimes need key() around them.

9. Interview Questions
What is the difference between declarative and imperative UI?
Basic⌄
Imperative UI: you manage view objects explicitly — find a TextView, call setText(), handle null checks, manage lifecycle. You describe HOW to change the UI. Declarative UI (Compose): you describe WHAT the UI should look like for a given state. When state changes, the framework re-runs your description and applies the diff. You don't touch existing views — you re-describe the desired output.
What triggers recomposition in Compose?
Basic⌄
Recomposition is triggered when a State<T> value that was read during the last composition changes. Compose tracks every State read inside a composable function — when any of those states change, the composable is scheduled for recomposition. Only composables that read the changed state are recomposed — not the entire UI tree.
What is remember and why do you need it?
Basic⌄
remember { } stores a value in the slot table so it persists across recompositions. Without it, the code inside runs on every recomposition — creating new objects, resetting state. Use remember for: mutableStateOf holders, expensive objects (formatters, painters), list instances. remember does NOT survive Activity recreation — use rememberSaveable for that.
What is the Composition and what is the slot table?
Intermediate⌄
The Composition is the in-memory representation of the UI — a tree built from composable function calls. The slot table is the data structure that backs it: a flat array where each composable call occupies slots storing its runtime state and remember values. The composable's identity in the slot table is its position in the call hierarchy (call site), not a runtime object reference.
How does Compose "skip" composables during recomposition?
Intermediate⌄
If all parameters of a composable are equal to their previous values (using equals()), Compose skips executing that composable entirely — its output is assumed unchanged. This is "smart recomposition." For a composable to be skippable, all its parameters must be stable types (primitives, String, data classes, @Stable annotated classes). Unstable types (like plain List<>) prevent skipping.
A composable creates a new List inside its body on every recomposition. Is this a problem and how do you fix it?
Intermediate⌄
Yes. Without remember, a new list is allocated on every recomposition — causing unnecessary GC pressure and potentially triggering further recompositions if the list is passed as a parameter (since new list instance != old list instance in equals()). Fix: val items = remember(key) { buildList { ... } }. If the list is derived from state, use remember(sourceData) { processData(sourceData) } — only recomputes when sourceData changes.
Why might a composable lose its state when a condition around it flips?
Intermediate⌄
Compose identifies composables by their position in the call tree (slot table). if (condition) ComponentA() else ComponentB() — both A and B occupy the same position. When condition flips, Compose sees the previous composable leaving and a new one entering at that position. The new composable's remember values start fresh — state is lost. Fix: use key(condition) { ComponentA() } or restructure so both branches are independent positions.
A developer calls an analytics tracking function directly in the composable body. What is wrong?
Senior⌄
Composables can recompose many times — every state change triggers re-execution. Calling analytics directly in the body would log the event on every recomposition, potentially hundreds of times. Additionally, composables may be run during previews, tests, or Compose internal optimizations (recomposition can be speculative). Side effects must be in LaunchedEffect or SideEffect: LaunchedEffect(Unit) { analytics.track("ScreenView") } — runs once when the composable enters composition.
Explain how the snapshot system works in Compose and how it enables fine-grained recomposition.
Senior⌄
Compose's snapshot system is a transactional state system. Every State value has a list of observers (composable scopes). During composition, reading a State registers the current composition scope as an observer. When you write to a State, it creates a new snapshot. The write is committed atomically — all observers are notified and scheduled for recomposition. This is how two different composables can read the same State and only both recompose when that specific state changes, while other composables that don't read it are untouched. The snapshot system also enables multi-thread safety for State mutations.
How does key() affect composable identity and recomposition in a LazyColumn?
Senior⌄
Without key: each item's identity is its index. Insert an item at position 0 → all items shift → Compose thinks every item changed → full recomposition of all items, all remember values reset. With key = { item.id }: each item's identity is its unique ID. Insert at 0 → only the new item is created, existing items keep their position (by key) → Compose skips recomposing unchanged items. This is critical for lists with animations — without keys, items appear to "jump" because all are treated as new.
