1. Overview — The Full Release Pipeline

Releasing an Android app is not just "clicking upload." It's an engineering pipeline with 13 discrete stages. Missing any one of them can mean a crash-heavy rollout, a rejected build, or a security vulnerability shipped to millions of devices.

2. Pre-Release Checklist — What to Do Before Building

2.1 Version bump — the most critical step

Every Play Store upload must have a strictly increasing versionCode. versionName is what users see; versionCode is the integer Play uses to order releases. Using the same or lower code will hard-fail the upload.

// app/build.gradle.kts — production pattern
android {
    defaultConfig {
        // versionCode = CI build number (always incrementing)
        // GitHub Actions: System.getenv("GITHUB_RUN_NUMBER")?.toInt() ?: 1
        versionCode = System.getenv("VERSION_CODE")?.toInt() ?: 1
        versionName = "3.7.2"       // semantic: major.minor.patch
        minSdk = 26
        targetSdk = 35               // Must be current year's API or Play warns
        applicationId = "com.acme.bankapp"
    }
}

2.2 Mandatory pre-release checks

1

Run full test suite — unit + integration + UI

./gradlew testReleaseUnitTest connectedReleaseAndroidTest — must be green before any build is promoted.

2

Run Android Lint on release variant

./gradlew lintRelease — check for missing translations, deprecated API calls, hardcoded strings. Treat errors as build failures.

3

Check targetSdkVersion

Google Play requires new apps to target at minimum Android 14 (API 34) and existing apps must be updated by August of the following year. Failing this causes upload rejection.

4

Audit permissions in AndroidManifest.xml

Remove any permission not used in the release build. Play reviews permissions and will flag unused dangerous permissions.

5

Verify no debug flags in release

android:debuggable="true" in the manifest, BuildConfig.DEBUG checks, Stetho/Flipper interceptors — must all be release-guarded.

6

Verify no sensitive keys in code or git

API keys, Firebase credentials, and signing passwords must come from CI environment variables or local.properties (gitignored), never hardcoded.

Hard Stop — targetSdkVersion
As of 2025, Google Play requires targetSdkVersion ≥ 34 for all new app submissions and updates. Apps targeting API 33 or below get a hard rejection. Update targetSdk and test against the newer behaviour changes (photo picker, notification permission, predictive back gesture).

3. Build Variants & Product Flavours

Build types: debug vs release

// app/build.gradle.kts
android {
    buildTypes {
        debug {
            applicationIdSuffix(".debug")      // install alongside release
            isDebuggable = true
            isMinifyEnabled = false
            isShrinkResources = false
        }
        release {
            isMinifyEnabled = true           // R8 code shrinking
            isShrinkResources = true         // remove unused resources
            proguardFiles(
                getDefaultProguardFile("proguard-android-optimize.txt"),
                "proguard-rules.pro"
            )
            // Signing configured here or via signingConfigs block
            signingConfig = signingConfigs.getByName("release")
        }
    }
}

Product flavours — staging vs production

android {
    flavorDimensions("env")
    productFlavors {
        create("staging") {
            dimension = "env"
            applicationIdSuffix(".staging")
            buildConfigField("String", "API_BASE_URL", "\"https://api-staging.acme.com\"")
            buildConfigField("Boolean", "ENABLE_LOGS", "true")
        }
        create("production") {
            dimension = "env"
            buildConfigField("String", "API_BASE_URL", "\"https://api.acme.com\"")
            buildConfigField("Boolean", "ENABLE_LOGS", "false")
        }
    }
}
// This creates build variants:
// stagingDebug, stagingRelease, productionDebug, productionRelease
// Upload variant: productionRelease

Build the release AAB

# Build production release AAB (not APK — AAB is required for Play Store)
./gradlew bundleProductionRelease

# Output: app/build/outputs/bundle/productionRelease/app-production-release.aab

# Run lint before building — fail fast
./gradlew lintProductionRelease bundleProductionRelease

4. APK vs AAB & App Signing

APK vs AAB — what's the difference

PropertyAPK (Android Package)AAB (Android App Bundle)
Required for Play Store❌ Rejected since Aug 2021✅ Mandatory for new apps
What it containsAll resources & code for all devicesSplit by ABI, screen density, language
Size on deviceFull size regardless of device15–40% smaller (Play serves device-specific splits)
SigningYou sign the APK directlyGoogle re-signs splits with your upload key
Direct installYes — sideload with adb installNo — must go through Play or bundletool
Dynamic features❌ Not supported✅ Dynamic Feature Modules

4.1 Keystore and signing — the most critical permanent decision

Irreversible — losing your keystore = losing your app
Your keystore is the permanent identity of your app. If you lose it and you don't use Play App Signing, you can never push another update to the same package name. Store it in: password manager + encrypted cloud backup + offline USB drive. Never store it in git.

Generate a new release keystore (one-time, production)

# Create keystore — do this ONCE and store it permanently
keytool -genkeypair \
  -alias acme-release-key \
  -keyalg RSA \
  -keysize 4096 \
  -validity 10000 \
  -keystore acme-release.keystore \
  -storepass '$STORE_PASSWORD' \
  -keypass  '$KEY_PASSWORD' \
  -dname "CN=Acme Corp, OU=Android, O=Acme, L=London, S=England, C=GB"

# Verify the keystore contents
keytool -list -v -keystore acme-release.keystore -storepass '$STORE_PASSWORD'

Configure signing in Gradle (secure CI pattern)

// app/build.gradle.kts — reads from environment variables (CI-safe)
android {
    signingConfigs {
        create("release") {
            storeFile   = file(System.getenv("KEYSTORE_PATH") ?: "../acme-release.keystore")
            storePassword = System.getenv("KEYSTORE_PASSWORD") ?: properties["KEYSTORE_PASSWORD"].toString()
            keyAlias    = System.getenv("KEY_ALIAS") ?: "acme-release-key"
            keyPassword = System.getenv("KEY_PASSWORD") ?: properties["KEY_PASSWORD"].toString()
        }
    }
    buildTypes {
        release {
            signingConfig = signingConfigs.getByName("release")
        }
    }
}

4.2 Play App Signing — the modern approach

Since 2021, Google Play manages two keys: the app signing key (held by Google, used to sign APK splits delivered to devices) and the upload key (you hold this to sign the AAB you upload).

KeyWho holds itWhat it signsIf lost
App signing keyGoogleAPK splits delivered to devicesGoogle can reset it via identity verification
Upload keyYouAAB you upload to Play ConsoleRequest an upload key reset from Google support
Best Practice — Always use Play App Signing
Enrol every new app in Play App Signing from the first upload. This decouples your upload key (which you can reset) from the actual signing key (held by Google). You get: key rotation support, smaller APKs, and safety against keystore loss.

Verify your signed AAB before uploading

# Use bundletool to test locally (download from github.com/google/bundletool)
java -jar bundletool.jar build-apks \
  --bundle=app-production-release.aab \
  --output=app.apks \
  --ks=acme-release.keystore \
  --ks-pass=pass:$KEYSTORE_PASSWORD \
  --ks-key-alias=acme-release-key \
  --key-pass=pass:$KEY_PASSWORD

# Install on connected device to verify before uploading to Play
java -jar bundletool.jar install-apks --apks=app.apks

5. R8, ProGuard & Obfuscation

R8 is the compiler + shrinker + obfuscator + optimiser that runs during release builds. It replaces ProGuard. Understanding it prevents the most common release crash: "Class not found at runtime even though it compiled fine."

What R8 does — four passes

PassWhat it doesControlled by
Tree shakingRemoves unreachable classes, methods, fieldsminifyEnabled true
ObfuscationRenames classes/methods to a, b, c…minifyEnabled true
Resource shrinkingRemoves unused drawable, layout, string resourcesshrinkResources true
OptimisationInlines methods, removes dead code paths, constant propagationproguard-android-optimize.txt

Complete production ProGuard rules — proguard-rules.pro

##──────── Kotlin ────────────────────────────────────────────────────────────
-keepclassmembers class **$WhenMappings { <fields>; }
-keepclassmembers class ** implements kotlin.coroutines.CoroutineContext$Element { *; }
-keep class kotlin.** { *; }
-keep class kotlinx.** { *; }
-dontwarn kotlin.**

##──────── Retrofit + OkHttp ─────────────────────────────────────────────────
-keepattributes Signature, Exceptions, *Annotation*
-keepattributes EnclosingMethod
-keep,allowobfuscation,allowshrinking interface retrofit2.**
-keep class retrofit2.** { *; }
-keep class okhttp3.** { *; }
-dontwarn okhttp3.**

##──────── Gson / Moshi / Kotlinx Serialisation ──────────────────────────────
# Keep all data classes used in JSON serialisation (Gson uses reflection)
-keep class com.acme.bankapp.data.model.** { *; }
-keepclassmembers class ** {
    @com.google.gson.annotations.SerializedName <fields>;
}
# Moshi generated adapters
-keep class **JsonAdapter { *; }

##──────── Room ───────────────────────────────────────────────────────────────
-keep class * extends androidx.room.RoomDatabase { *; }
-keep @androidx.room.Entity class * { *; }

##──────── Hilt / Dagger ─────────────────────────────────────────────────────
-keep,allowobfuscation @dagger.hilt.android.HiltAndroidApp class *
-keep class dagger.** { *; }
-keep class javax.inject.** { *; }
-keep class * extends dagger.hilt.android.internal.managers.** { *; }

##──────── Firebase / Crashlytics ────────────────────────────────────────────
-keepattributes SourceFile,LineNumberTable
-keep public class * extends java.lang.Exception
-keep class com.google.firebase.** { *; }
-dontwarn com.google.firebase.**

##──────── Parcelable / Serializable ─────────────────────────────────────────
-keepclassmembers class * implements android.os.Parcelable {
    public static final android.os.Parcelable$Creator CREATOR;
}
-keepclassmembers class * implements java.io.Serializable {
    static final long serialVersionUID;
    private static final java.io.ObjectStreamField[] serialPersistentFields;
    private void writeObject(java.io.ObjectOutputStream);
    private void readObject(java.io.ObjectInputStream);
    java.lang.Object readResolve();
}

##──────── WebView / JS interface ─────────────────────────────────────────────
-keepclassmembers class * {
    @android.webkit.JavascriptInterface <methods>;
}

##──────── Enums ─────────────────────────────────────────────────────────────
-keepclassmembers enum * {
    public static **[] values();
    public static ** valueOf(java.lang.String);
}

##──────── Keep mapping file for Crashlytics deobfuscation ───────────────────
-printmapping build/outputs/mapping/release/mapping.txt
Always upload mapping.txt to Crashlytics
R8 obfuscates stack traces. Without the mapping.txt file, your Crashlytics crashes show a.b.c() line 12 instead of real class names. Upload it automatically via ./gradlew uploadCrashlyticsProguardMappingProductionRelease or the Firebase Gradle plugin handles it automatically when firebaseCrashlytics { mappingFileUploadEnabled = true }.

Verify R8 output with apkanalyzer

# Check what's in your AAB / check which classes survived shrinking
$ANDROID_HOME/cmdline-tools/latest/bin/apkanalyzer dex packages \
  app/build/outputs/bundle/productionRelease/app-production-release.aab \
  | grep "com.acme"

# Check final APK size breakdown (after bundletool build-apks)
$ANDROID_HOME/cmdline-tools/latest/bin/apkanalyzer apk download-size app.apks

6. Play Console Upload — Step-by-Step

6.1 Manual upload via Play Console UI

1

Go to play.google.com/console → Your app → Release → Testing or Production

Choose the track: Internal testing → Closed testing (Alpha) → Open testing (Beta) → Production.

2

Create new release → Upload AAB

Drag and drop the .aab file. Play validates: package name, versionCode, signing certificate, minimum SDK, and target SDK. Any mismatch gives a hard rejection with a specific error code.

3

Fill release notes (What's new)

Required for production; optional for testing tracks. Supports 500 chars per locale. Must be filled for each locale your app supports.

4

Review → Save → Review release

Play runs pre-launch checks: screenshots, robo-test, policy scan, permission audit. Results appear in the Pre-launch report within 30–60 minutes.

5

Start rollout

For production: choose rollout percentage (1–100%). For internal/alpha/beta: 100% to all testers in the track group.

6.2 Automated upload via Play Developer API (Fastlane / CI)

# Using Fastlane supply — the standard CI upload tool
# Gemfile
gem "fastlane"

# fastlane/Fastfile
lane :deploy_production do
  # 1. Run tests
  gradle(task: "test", build_type: "Release", flavor: "Production")

  # 2. Build AAB
  gradle(
    task:        "bundle",
    build_type:  "Release",
    flavor:      "Production",
    properties: {
      "KEYSTORE_PATH"     => ENV["KEYSTORE_PATH"],
      "KEYSTORE_PASSWORD" => ENV["KEYSTORE_PASSWORD"],
      "KEY_ALIAS"         => ENV["KEY_ALIAS"],
      "KEY_PASSWORD"      => ENV["KEY_PASSWORD"]
    }
  )

  # 3. Upload to internal track first
  upload_to_play_store(
    track:               "internal",
    aab:                 "app/build/outputs/bundle/productionRelease/app-production-release.aab",
    json_key:            "fastlane/play-store-api-key.json",
    skip_upload_apk:     true,
    release_status:      "completed",
    version_name:        android_get_package_version_name()
  )
end

7. Tracks & Staged Rollout Strategy

The four tracks — what each means

TrackWho sees itPurposeCrash rate threshold
Internal testingUp to 100 internal testers (email list)First smoke test after QA sign-offNo automatic hold
Closed testing (Alpha)Closed group — up to thousands; invite onlyBroader regression test with real devicesNo automatic hold
Open testing (Beta)Opt-in from Play Store page — publicGather real-world feedback before full launchPlay may flag >1.09% crash rate
ProductionAll usersLive release — partial rollout supportedPlay halts rollout at >1.09% crash rate

Staged rollout — the only safe way to release

Never push directly to 100% of production users. A staged rollout lets you monitor crash rate and vitals before the damage scales.

RECOMMENDED STAGED ROLLOUT TIMELINE Day 0 │ Internal track (100 testers) │ ✓ Zero P0 crashes → promote after 4h │ Day 1 │ Closed Alpha (2,000 testers) │ ✓ Crash rate < 0.5% → promote after 24h │ Day 2 │ Open Beta (opt-in, ~10,000 users) │ ✓ Crash rate < 0.8% → promote after 48h │ Day 4 │ Production rollout ── 1% │ Monitor 4h → crash rate? force-stop rate? │ ✓ Still below threshold → expand to 5% │ Day 5 │ Production ── 10% │ Monitor 8h → Play vitals still green? │ Day 6 │ Production ── 20% → 50% → 100% │ Automate with Fastlane promote lane or │ Play Developer API incremental_rollout

Programmatic staged rollout via Fastlane

# fastlane/Fastfile — promote lane
lane :promote_to_production do |options|
  upload_to_play_store(
    track:                    "beta",
    track_promote_to:         "production",
    rollout:                  options[:rollout] || "0.01",  # 1%
    json_key:                 "fastlane/play-store-api-key.json",
    skip_upload_aab:          true,
    skip_upload_apk:          true
  )
end

# Expand rollout
lane :expand_rollout do |options|
  upload_to_play_store(
    track:           "production",
    rollout:         options[:percentage].to_s,
    json_key:        "fastlane/play-store-api-key.json",
    skip_upload_aab: true,
    skip_upload_apk: true
  )
end

# Halt rollout (emergency stop)
lane :halt_rollout do
  upload_to_play_store(
    track:           "production",
    rollout:         "0",     # 0% halts new installs
    json_key:        "fastlane/play-store-api-key.json",
    skip_upload_aab: true
  )
end
Automatic Halt — Play Store safety net
If your app's crash rate exceeds 1.09% or ANR rate exceeds 0.47% on Android Vitals, Play Console displays a warning and can automatically pause the rollout. You'll see this as "Rollout paused due to Play policy". Fix the issue and manually resume — it does NOT auto-resume.

8. CI/CD Automation — Full GitHub Actions Pipeline

Complete production release workflow

# .github/workflows/release.yml
name: Release to Play Store
on:
  push:
    tags: [ 'v*.*.*' ]          # trigger on version tag e.g. v3.7.2

jobs:
  release:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

      # 1. Set up JDK
      - name: Set up JDK 17
        uses: actions/setup-java@v4
        with: { java-version: '17', distribution: 'temurin' }

      # 2. Cache Gradle dependencies
      - name: Cache Gradle
        uses: actions/cache@v4
        with:
          path: |
            ~/.gradle/caches
            ~/.gradle/wrapper
          key: gradle-${{ runner.os }}-${{ hashFiles('**/*.gradle*') }}

      # 3. Decode keystore from base64 secret
      - name: Decode Keystore
        run: |
          echo "${{ secrets.KEYSTORE_BASE64 }}" | base64 --decode \
            > $GITHUB_WORKSPACE/acme-release.keystore

      # 4. Run tests
      - name: Run Unit Tests
        run: ./gradlew testProductionReleaseUnitTest

      # 5. Run Lint
      - name: Run Lint
        run: ./gradlew lintProductionRelease

      # 6. Build AAB
      - name: Build Release AAB
        env:
          KEYSTORE_PATH: ${{ github.workspace }}/acme-release.keystore
          KEYSTORE_PASSWORD: ${{ secrets.KEYSTORE_PASSWORD }}
          KEY_ALIAS: ${{ secrets.KEY_ALIAS }}
          KEY_PASSWORD: ${{ secrets.KEY_PASSWORD }}
          VERSION_CODE: ${{ github.run_number }}
        run: ./gradlew bundleProductionRelease

      # 7. Upload AAB artifact
      - name: Upload AAB
        uses: actions/upload-artifact@v4
        with:
          name: release-aab
          path: app/build/outputs/bundle/productionRelease/

      # 8. Upload to Play Store internal track
      - name: Deploy to Play Store (Internal Track)
        uses: r0adkll/upload-google-play@v1
        with:
          serviceAccountJsonPlainText: ${{ secrets.PLAY_STORE_JSON_KEY }}
          packageName: com.acme.bankapp
          releaseFiles: app/build/outputs/bundle/productionRelease/app-production-release.aab
          track: internal
          status: completed
          whatsNewDirectory: fastlane/metadata/android/en-US/changelogs/

      # 9. Upload mapping.txt to Crashlytics
      - name: Upload Crashlytics Mapping
        env:
          GOOGLE_SERVICES_JSON: ${{ secrets.GOOGLE_SERVICES_JSON }}
        run: ./gradlew uploadCrashlyticsProguardMappingProductionRelease

Firebase Crashlytics alert setup

// In your Application class — set up Crashlytics before any crash can occur
class BankApp : Application() {
    override fun onCreate() {
        super.onCreate()
        // Enable crash collection in release only
        FirebaseCrashlytics.getInstance()
            .setCrashlyticsCollectionEnabled(!BuildConfig.DEBUG)

        // Set user ID for better debugging (anonymised)
        FirebaseCrashlytics.getInstance().setUserId(
            getAnonymisedUserId()  // hash of real ID, never PII directly
        )
    }
}

// In build.gradle.kts — automatically upload mapping.txt on every release build
firebaseCrashlytics {
    mappingFileUploadEnabled = true   // auto-upload proguard mapping
    nativeSymbolUploadEnabled = false  // set true if using NDK/C++
}

Setting up Crashlytics alerts (Firebase Console)

1

Firebase Console → Crashlytics → Alerts

Set up: "Velocity alerts" — triggers when a new crash hits 0.1% of sessions within 1 hour.

2

Set regression alerts

Alerts when a previously resolved crash re-opens — catches regressions introduced by new releases immediately.

3

Connect to PagerDuty / Slack

4

10. Pitfalls & Best Practices
Pitfall 1 — Losing your keystore
Never store the keystore in git. Store it in a password manager + two separate encrypted cloud vaults. The only recovery is enrolling in Play App Signing before you lose it. Without it, your only option is to publish under a new package name (losing all your users and reviews).
Pitfall 2 — Skipping ProGuard -keep rules
R8 will shrink away classes referenced only via reflection (Gson models, Room entities, Parcelable classes, JS interfaces). The app compiles but crashes at runtime with ClassNotFoundException. Always test the release build on a real device before uploading.
Pitfall 3 — Uploading APK instead of AAB
Google Play has required AAB for all new apps since August 2021. An APK upload will fail with error UPLOAD_APK_FORBIDDEN_PACKAGE_NAME for new apps, and for existing apps it still works but misses on-demand delivery and significantly larger install sizes.
Pitfall 4 — Not testing the release build variant
Debug and release builds behave differently: R8 removes branches, ProGuard renames classes, signing is different. Always install productionRelease on a physical device and smoke-test the critical flows before uploading.
Pitfall 5 — Hardcoding API keys in code
R8 obfuscates method names but does NOT encrypt string literals. Any string in your code is visible via strings command on the APK. Use Google Cloud Secret Manager, remote config, or at minimum place keys in local.properties and inject them as BuildConfig fields — never commit them.
Best Practice — Baseline Profiles
Add a baseline-prof.txt generated by the Macrobenchmark library. It pre-compiles the hot startup paths (app startup, main screen rendering). Result: 15–30% faster cold start visible in Play Console Core Vitals. Must be regenerated for each release. 
./gradlew :app:generateBaselineProfile

11. Interview Framework

30-second answer — "Walk me through your release process"

"We follow a gated pipeline: code freeze on the release branch, full test suite and lint must pass in CI. We build a signed AAB using a Release build type with R8 enabled, sign it with our upload key via Play App Signing, upload to the internal track first, then promote through Alpha → Beta → Production with a staged rollout starting at 1%. We monitor Crashlytics and Play Vitals — if crash rate exceeds 0.5% we halt the rollout. Everything is automated via GitHub Actions and Fastlane."

2-minute answer — what separates seniors

"Beyond the basics, the senior-level considerations are: keystore management (Play App Signing so we can rotate the upload key), ProGuard/R8 keep rules (I've been burned by missing Gson model keeps causing runtime ClassNotFoundException), Baseline Profiles to maintain cold start SLA, and the monitoring setup — Crashlytics velocity alerts with PagerDuty integration so P0s page on-call within 60 seconds of hitting 0.1% of sessions. For versioning, we use the CI build number as versionCode so it's guaranteed to be monotonically increasing. And we never roll out to 100% immediately — 1% → 5% → 10% → 50% → 100% over 3–5 days."

Must mention — the examiner's checklist

  • AAB vs APK — AAB mandatory, Play re-signs the splits
  • Upload key vs signing key — Play App Signing manages the distinction
  • R8 keep rules — Gson/Retrofit/Parcelable all need explicit keeps
  • mapping.txt — must be uploaded to Crashlytics for readable stack traces
  • versionCode — must be strictly increasing; use CI build number
  • Staged rollout — 1% first, monitor vitals, expand over days
  • Play Vitals thresholds — 1.09% crash rate triggers automatic rollout halt

Follow-up: "What's the difference between versionCode and versionName?"

A: versionCode is an internal integer used by Play to order releases — must strictly increase with each upload. versionName is the human-readable string shown to users (e.g. "3.7.2") — semantic versioning convention, but Play doesn't enforce any format. You can have versionCode=1042 with versionName="3.7.2".

Follow-up: "How do you handle a P0 crash post-release?"

A: Immediately halt the rollout in Play Console (drops new installs to 0%). Assess if previous version should be rolled back — Play Console lets you re-publish the last release without re-uploading. Create a hotfix branch from the release tag, fix, fast-track through CI and expedited Play review (available for critical security/crash fixes), then resume rollout.

13. Interview Questions
What is the difference between APK and AAB, and which does Google Play require?
Basic⌄
AAB (Android App Bundle) is required for all new apps since August 2021. Unlike APK which bundles all code and resources for all device configurations, AAB is a publishing format — Google Play generates and delivers optimised APKs per device (correct ABI, screen density, language only). This makes installs 15–40% smaller. You cannot sideload an AAB directly; use bundletool to test locally.
You upload a new build and get "VERSION_CODE_NOT_INCREMENTING". What happened and how do you fix it?
Basic⌄
The new build has a versionCode equal to or lower than the last uploaded build. Play requires strictly increasing version codes. Fix: increment the versionCode in build.gradle.kts and rebuild. Production pattern: use the CI build number (System.getenv("GITHUB_RUN_NUMBER").toInt()) as the versionCode — it's guaranteed to increase with every CI run.
What is Play App Signing, and why should you use it?
Intermediate⌄
Play App Signing separates the upload key (you hold) from the app signing key (Google holds). You sign your AAB with the upload key before uploading. Google re-signs the APK splits it delivers to devices with the app signing key. Benefits: (1) if your upload key is lost, you can request a reset from Google support and your users are unaffected; (2) enables key rotation; (3) enables APK split optimisation. Without it, losing your keystore permanently blocks you from updating your app.
Your app crashes in production after enabling R8. The crash is ClassNotFoundException for a Gson model. What caused it and how do you fix it?
Intermediate⌄
R8 tree-shaking removed the Gson model class because it detected no direct code references (Gson accesses it via reflection, which R8 cannot see statically). Fix: add a ProGuard keep rule: -keep class com.acme.bankapp.data.model.** { *; } or more specifically -keepclassmembers class ** { @com.google.gson.annotations.SerializedName <fields>; }. After adding the rule, rebuild the release, install it on a device, and test the affected API call before re-uploading.
Walk through your complete staged rollout strategy for a major feature release.
Intermediate⌄
Internal track (100 internal testers, 4h, zero P0 crashes) → Closed Alpha (2,000 testers, 24h, crash rate <0.5%) → Open Beta (public opt-in, 48h, crash rate <0.8%) → Production 1% (4h monitor) → 5% (8h) → 10% (overnight) → 20% → 50% → 100%. At each production step: check Crashlytics crash-free session rate, Play Vitals ANR rate, and force-stop rate. If crash rate exceeds 1%, halt the rollout immediately and assess whether to fix-forward with a hotfix or roll back to the previous version.
Why is it important to upload the mapping.txt file to Crashlytics after each release?
Basic⌄
R8 obfuscates class and method names during release builds (e.g., MainActivity becomes a, fetchUser becomes b). Without the mapping.txt, Crashlytics stack traces show only obfuscated names — impossible to debug. The mapping.txt maps obfuscated names back to original names. It must be re-uploaded for every release since each build produces a different mapping. Enable automatic upload with firebaseCrashlytics { mappingFileUploadEnabled = true }.
A P0 crash is found 2 hours after rollout reaches 10% of production users. What do you do?
Senior⌄
1. Immediately halt the rollout in Play Console (sets rollout % to 0, stops new installs of the buggy version). 2. Assess scope: how many users affected, is it recoverable at runtime or data-corrupting? 3. If crash is isolated and fixable in <4h: create a hotfix branch off the release tag, fix, merge, trigger CI, upload to internal track for smoke test, then request expedited review from Google (available for critical bugs). 4. If fix will take >4h or is complex: roll back by promoting the previous production version (Play Console allows re-publishing without re-upload). 5. After hotfix is ready: resume rollout from 10% and monitor. Post-mortem within 48h.
How do you ensure secrets like API keys are not bundled in the release APK?
Senior⌄
Several layers: (1) Never hardcode secrets in source — R8 obfuscates method names but string literals remain readable via strings on the APK. (2) Use local.properties (gitignored) for local dev, inject as BuildConfig fields via Gradle — these are embedded in the binary but at least not in version control. (3) For production: use server-side secret delivery — app fetches config from a secure backend endpoint authenticated with an app attestation (Play Integrity API). (4) For keys that must be on-device (e.g., payment SDK): use Android Keystore-backed encrypted storage, never plain SharedPreferences. (5) Regularly rotate API keys in the backend, monitoring for unauthorized usage.
What are Baseline Profiles and how do they affect the release process?
Senior⌄
Baseline Profiles are a list of hot code paths (baseline-prof.txt) that tell the Android runtime (ART) to AOT-compile those methods ahead of time during app installation, instead of waiting for JIT compilation at first run. Generated by the Macrobenchmark library targeting real user startup flows. They reduce cold start time by 15–30% and eliminate initial jank. Release process impact: (1) They must be re-generated for each release because class/method references change. (2) They're included in the AAB automatically when using the androidx.profileinstaller library. (3) Results become visible in Play Console Core Vitals 7–14 days post-release as user install data accumulates.
