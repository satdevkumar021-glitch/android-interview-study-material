1J — Equality, Interop & Errors

== vs ===, Kotlin–JVM interoperability, Kotlin compilation basics, exceptions, and the Result type — the final Kotlin unit before moving into Android fundamentals.

ID: 1J ⭐ Tier 1
🔍
1. Overview

What it covers

  • == vs ===: structural equality vs referential equality — critical for data classes, caches, state comparison
  • Kotlin–JVM interop: how Kotlin and Java code call each other, platform types, @JvmStatic, @JvmOverloads, @JvmField
  • Kotlin compilation: source → IR → JVM bytecode (or JS/Native); how the compiler outputs .class files; what kotlinc does differently from javac
  • Exceptions: Kotlin's unchecked exception model, try/catch/finally, runCatching, exception hierarchy
  • Result type: Result<T>, runCatching, fold, onSuccess/onFailure, when to use vs sealed class
Senior Mental Model
In Android, == vs === is critical for StateFlow: MutableStateFlow uses structural equality (==) to decide whether to emit a new value. If your state object doesn't override equals() correctly, state updates get silently dropped. This is the most common source of "my UI isn't updating" bugs.
⚙
2. How It Works

== vs ===

// == : structural equality — calls equals()
// === : referential equality — same object in memory

data class User(val id: String, val name: String)

val a = User("1", "Alice")
val b = User("1", "Alice")
val c = a

println(a == b)   // true  — same content (data class equals)
println(a === b)  // false — different objects in memory
println(a === c)  // true  — same reference

// For nullable types: a == null calls a?.equals(null) ?: (a === null)
val x: String? = null
println(x == null)   // true — safe null check
println(x === null)  // true — referential null check
StateFlow & Equality
MutableStateFlow.value = newValue compares newValue == currentValue. If equal, no emission. This is why data class with all val properties is critical for UI state — equals() auto-generated from constructor properties. Regular classes with no equals() override use reference equality — the state object is "new" even if content is identical, always emitting.

Exceptions in Kotlin

// ALL Kotlin exceptions are unchecked (unlike Java checked exceptions)
// No 'throws' declaration required (unlike Java)

try {
    val result = riskyOperation()
} catch (e: SpecificException) {
    handleSpecific(e)
} catch (e: Exception) {
    handleGeneral(e)
} finally {
    cleanup()   // always runs
}

// try is an expression — returns the last value
val parsed = try { input.toInt() } catch (e: NumberFormatException) { 0 }

// throw is also an expression (type: Nothing)
val port = config.port ?: throw IllegalStateException("Port not configured")

Result<T>

// Result<T> = either Success(value: T) or Failure(exception: Throwable)
val result: Result<User> = runCatching { api.getUser(id) }

// Access:
result.getOrNull()                       // T? — null on failure
result.getOrDefault(User.empty())        // T — default on failure
result.getOrElse { e -> User.fromError(e) }
result.getOrThrow()                       // T — rethrows exception
result.isSuccess; result.isFailure

// Chain transformations:
result
    .map { user -> user.toDomain() }       // transform on success
    .mapCatching { user -> enrich(user) }  // transform, catches exceptions
    .onSuccess { user -> cacheUser(user) } // side effect on success
    .onFailure { e -> logError(e) }         // side effect on failure
    .fold(
        onSuccess = { user -> UiState.Success(user) },
        onFailure = { e    -> UiState.Error(e.message) }
    )

// runCatching — wraps a block in Result
val r: Result<Int> = runCatching { "42".toInt() }   // Success(42)
val r2: Result<Int> = runCatching { "abc".toInt() }  // Failure(NumberFormatException)

3. Why and When to Use It

== vs === — When it matters in Android

SituationUseWhy
Compare UI state objects== (structural)StateFlow uses == to detect changes
Check if two references point to the same singleton===Singletons (object, Hilt @Singleton) should be referentially equal
Null check in smart cast== null or === nullBoth work; == null is idiomatic Kotlin
Check enum values==Enums are singletons; structural and referential equality are the same

Result<T> vs Sealed Class — Decision

Use Result<T>Use Sealed Class
Repository / data layer wrapping exceptionsPresentation layer UiState (Loading, Success, Error)
Simple success/failure from a use caseMultiple distinct error types with different data
Wrapping existing exception-throwing codeOne-time UI events (navigation, snackbar)
When stdlib operators (map, fold, onSuccess) are sufficientWhen you need exhaustive when + compile-time safety for all states

When NOT to use Result<T>

Do NOT
  • Use Result as a return type in public API — use sealed class for explicit, exhaustive error handling
  • Wrap CancellationException in Result — always rethrow it
  • Use runCatching to swallow exceptions silently without logging
  • Use === for value comparison of data classes — use ==

4. Production Example
Scenario
Banking app — repository wraps API calls in Result, ViewModel converts to sealed UiState, Java interop layer uses @JvmStatic and @JvmOverloads.

Repository — Result wrapping

// data/repository/AccountRepositoryImpl.kt
internal class AccountRepositoryImpl @Inject constructor(
    private val api: AccountApi
) : AccountRepository {

    override suspend fun getBalance(accountId: String): Result<Balance> =
        runCatching {
            api.getBalance(accountId).toDomain()
        }.onFailure { e ->
            if (e is CancellationException) throw e  // never swallow cancellation
            Timber.e(e, "getBalance failed for $accountId")
        }
}

UseCase — Result propagation

// domain/usecase/GetAccountSummaryUseCase.kt
class GetAccountSummaryUseCase @Inject constructor(
    private val accountRepo: AccountRepository,
    private val txRepo: TransactionRepository
) {
    suspend operator fun invoke(accountId: String): Result<AccountSummary> =
        runCatching {
            val balance = accountRepo.getBalance(accountId).getOrThrow()
            val recentTx = txRepo.getRecent(accountId, limit = 5).getOrThrow()
            AccountSummary(balance, recentTx)
        }

ViewModel — Result → sealed UiState

// presentation/account/AccountViewModel.kt
@HiltViewModel
class AccountViewModel @Inject constructor(
    private val getAccountSummary: GetAccountSummaryUseCase
) : ViewModel() {

    private val _uiState = MutableStateFlow<AccountUiState>(AccountUiState.Loading)
    val uiState = _uiState.asStateFlow()

    fun load(accountId: String) {
        viewModelScope.launch {
            _uiState.value = AccountUiState.Loading

            val newState = getAccountSummary(accountId)
                .fold(
                    onSuccess = { AccountUiState.Success(it) },
                    onFailure = { AccountUiState.Error(it.message ?: "Unknown error") }
                )

            // StateFlow uses == to detect change — data class AccountUiState needed
            _uiState.value = newState
        }
    }
}

sealed interface AccountUiState {
    data object Loading                                    : AccountUiState
    data class  Success(val summary: AccountSummary)        : AccountUiState
    data class  Error(val message: String)                  : AccountUiState
}

Equality in StateFlow — == matters

// ❌ If UiState is a regular class (no data), StateFlow may not emit
class UiState(val count: Int)  // no equals() override
_state.value = UiState(5)     // always emits — new object ≠ old (reference)
_state.value = UiState(5)     // emits again even with same content! (5 == 5 but different obj)

// ✅ data class: equals() uses structural comparison
data class UiState(val count: Int)
_state.value = UiState(5)     // emits
_state.value = UiState(5)     // NOT emitted — same content, == returns true
_state.value = UiState(6)     // emits — content changed

6. Pitfalls & Best Practices

runCatching swallows CancellationException

// ❌ BAD — CancellationException caught and wrapped, coroutine not cancelled
val result = runCatching { api.call() }
// If coroutine is cancelled during api.call(), CancellationException is swallowed!
// ✅ GOOD — always rethrow CancellationException
val result = runCatching { api.call() }
    .onFailure { if (it is CancellationException) throw it }

// Or use a safeRunCatching wrapper:
suspend inline fun <T> safeRunCatching(block: suspend () -> T): Result<T> = try {
    Result.success(block())
} catch (e: CancellationException) { throw e }
  catch (e: Exception) { Result.failure(e) }

StateFlow with regular class — no emission

// ❌ BAD — regular class; StateFlow.value = x checks x == current
// Regular class inherits equals() from Any → reference comparison
class ProfileState(val name: String)
_state.value = ProfileState("Alice")
_state.value = ProfileState("Alice")  // emits again! different object references
// ✅ GOOD — data class; structural equality prevents duplicate emissions
data class ProfileState(val name: String)
_state.value = ProfileState("Alice")
_state.value = ProfileState("Alice")  // NOT emitted — == returns true

Platform types — silent NPE from Java

// ❌ BAD — Java returns String! (platform type); assigned as non-null
val name: String = javaApi.getName()  // crashes if getName() returns null
// ✅ GOOD — treat Java returns defensively
val name: String = javaApi.getName() ?: "Unknown"
// Or: annotate the Java side with @NotNull / @Nullable

Production Best Practices

  1. Use data class for all StateFlow state types — structural equality ensures correct emission/de-dup.
  2. Always rethrow CancellationException — wrap all runCatching with a re-throw check.
  3. Use Result<T> in data/domain layer, sealed UiState in presentation layer — they serve different purposes.
  4. Add @Throws to Kotlin functions called from Java that may throw checked exceptions.
  5. Add @JvmStatic to companion object methods used from Java — avoids MyClass.Companion.method() verbosity.
  6. Prefer KSP over KAPT for annotation processors in new code — significantly faster build times.
  7. Use try as an expression for simple parse operations: val n = try { s.toInt() } catch { 0 }.

7. Interview Answer Framework

30-Second Answer

"== is structural equality — calls equals(). === is referential equality — same object in memory. This matters critically for StateFlow: it uses == to decide whether to emit. A regular class with no equals() will always emit; a data class correctly de-duplicates identical states. For error handling, Result<T> with runCatching is good for data/domain layer wrapping; sealed UiState is right for the presentation layer. Java interop uses @JvmStatic, @JvmOverloads, and @JvmField to make Kotlin code natural to call from Java. All Kotlin exceptions are unchecked — no forced try/catch."

2-Minute Structured Answer

"Three topics. Equality: == calls equals() — structural. === is the same-object check. The most practically important implication in Android is StateFlow: it internally uses == to compare the new and current value. If they're equal, no emission happens. With a data class, this correctly suppresses duplicate state pushes. With a regular class that hasn't overridden equals(), you get reference comparison — every new object emits, even if content is identical. That can cause unnecessary recomposition or repeated side effects.

Errors and Result: Kotlin has no checked exceptions — unlike Java, you're never forced to declare or catch. For wrapping exception-throwing code I use runCatching { } which produces a Result<T>. I chain map, onSuccess, onFailure, and fold on it. The one trap: runCatching catches ALL exceptions including CancellationException, which breaks coroutine cancellation. I always add a rethrow for CancellationException inside onFailure, or use a custom safeRunCatching.

Java interop: Kotlin companion object members aren't static on the JVM — they need @JvmStatic for Java to call without .Companion. Default arguments don't generate Java overloads — use @JvmOverloads. Platform types from Java (T!) have unknown nullability — treat them defensively with ?:."

9. Interview Questions (Self-Check)
How to use
Answer first, then reveal.

Basic

B1 — What is the difference between == and === in Kotlin?
Easy▼
== is structural equality — it calls equals(). === is referential equality — it checks whether two variables point to the exact same object in memory. For a data class, == compares field values (auto-generated equals()). For a regular class with no equals() override, == behaves the same as === (reference comparison, inherited from Any).
B2 — Does Kotlin have checked exceptions? How do you expose checked exceptions to Java callers?
Easy▼
No — all Kotlin exceptions are unchecked. You are never forced to declare which exceptions a function throws, nor are callers forced to catch them. This is a deliberate design decision that avoids Java's checked exception verbosity.

To expose a checked exception contract to Java callers, annotate the Kotlin function with @Throws(IOException::class). This tells the Java compiler to treat it as a checked exception, enabling Java's try/catch requirement.
B3 — What is runCatching and what does it return?
Easy▼
runCatching { block } executes a block and wraps the result in a Result<T>. If the block succeeds, it returns Result.success(value). If it throws any exception, it returns Result.failure(exception). You can then chain map, onSuccess, onFailure, fold, and getOrNull on the result.

Intermediate

I1 — Why is StateFlow UI state broken if you use a regular class instead of a data class?
Medium▼
MutableStateFlow.value = newValue checks if newValue == currentValue before emitting. If they're equal, no emission occurs — this is the de-duplication mechanism.

A regular class inherits equals() from Any, which compares by reference. So every new instance is "different" even if the content is identical — the state always emits. This can cause unnecessary recompositions.

Conversely, if the same instance is mutated in-place (mutable properties), the reference stays the same — == returns true — and no emission occurs even though the content changed. Either way breaks the reactive contract. Fix: use data class with all val properties.
I2 — What is a platform type in Kotlin? How do you handle it safely?
Medium▼
A platform type (expressed as T! in error messages) is a type from Java code that has no nullability annotation. Kotlin cannot determine if it's nullable or non-null, so it defers to the developer. You can assign it to either T or T? — but if you assign to T and Java returns null, you get a NPE.

Safe handling: (1) Annotate the Java side with @Nullable/@NotNull — Kotlin then knows the contract. (2) Defensively treat all Java returns as nullable: javaApi.getName() ?: "default". (3) In modern code, use Kotlin APIs that are already annotated.
I3 — (Coding) What's the critical bug in this code? Fix it.
MediumCoding▼
// ❌ BUG
suspend fun fetchUser(id: String): Result<User> =
    runCatching { api.getUser(id) }
Bug: runCatching catches ALL exceptions, including CancellationException. When the coroutine is cancelled (e.g., user navigates away), the cancellation exception is caught and wrapped in a Result.failure. The coroutine thinks it completed normally — it doesn't propagate the cancellation. The scope doesn't cancel properly, causing leaked coroutines.

// ✅ Fixed
suspend fun fetchUser(id: String): Result<User> =
    runCatching { api.getUser(id) }
        .onFailure { if (it is CancellationException) throw it }
I4 — What is the difference between KAPT and KSP? Which should you use in new projects?
Medium▼
KAPT (Kotlin Annotation Processing Tool): converts Kotlin source to Java stubs, then runs Java annotation processors. Works with all Java annotation processors but adds a full compilation step — significantly slower, especially on incremental builds.

KSP (Kotlin Symbol Processing): processes Kotlin symbols directly without Java stub generation — typically 2x faster than KAPT. Has a Kotlin-first API. Supported by major Android libraries: Hilt (1.0.0+), Room (2.4.0+), Moshi, Glide.

Use KSP in new projects wherever the library supports it. Only fall back to KAPT for processors that haven't migrated to KSP yet.

Senior / Scenario

S1 — (Scenario) A developer reports "my UI sometimes doesn't update when the state changes." You look at the ViewModel and see _state.value = ProfileState(name = newName) where ProfileState is a regular class. Diagnose and fix.
HardScenario▼
Diagnosis: MutableStateFlow.value = x uses == (structural equality) to decide whether to emit. ProfileState is a regular class — it inherits equals() from Any, which compares by reference. So every ProfileState(name = newName) creates a new object, and ===-based comparison makes it always emit (new reference ≠ old reference) — that would actually cause over-emission.

But the "UI doesn't update" scenario happens if the developer is mutating the existing object: profileState.name = newName (if name is a var). The reference hasn't changed, so == (reference for non-data class) returns true — no emission.

Fix: 1. Make ProfileState a data class with val properties — now == compares field values. 2. Never mutate state in-place; always create a new object: _state.value = _state.value.copy(name = newName) 
data class ProfileState(val name: String)
_state.value = _state.value.copy(name = newName)  // emits if name changed
S2 — When would you choose Result<T> over a sealed class for error handling? Give a specific architecture example.
HardScenario▼
Use Result<T> at the repository and use-case layer — it's the boundary between exception-throwing code (network, database) and your clean domain logic. The repository wraps a Retrofit call with runCatching; the use case propagates or maps the result. No custom state is needed here — it's just success/failure.

Use sealed class at the presentation layer — because UI has states beyond just success/failure: Loading, Empty, Refreshing, etc. Each state may carry different data, and the when expression must be exhaustive.

The pattern in production: 
// Data layer → Result
suspend fun getUser(): Result<User> = runCatching { api.getUser() }

// Presentation layer → sealed UiState
getUser().fold(
    onSuccess = { UiState.Success(it) },
    onFailure = { UiState.Error(it.message) }
)
They complement each other — Result handles the exception boundary; sealed UiState handles the display contract.
S3 — You have a Kotlin library consumed by a Java project. List all the annotations you'd apply and why.
HardScenario▼
@JvmStatic — on companion object members: generates a true Java static method so Java can call MyClass.method() instead of MyClass.Companion.method().

@JvmOverloads — on functions with default parameters: generates Java-visible overloaded methods so Java callers can omit optional parameters.

@JvmField — on val/var properties you want exposed as Java fields: removes the getter/setter and exposes the field directly. Useful for constants.

@Throws(ExceptionType::class) — on suspend functions or functions that throw: tells Java's compiler to treat them as checked exceptions.

@JvmName — when Kotlin generates a method name that clashes with another JVM method name (e.g., extension functions on the same receiver type).

@Nullable / @NotNull — on all public function parameters and return types: prevents Java from treating them as platform types, giving Java callers proper nullability warnings.

Also: avoid using Kotlin-specific features in the public API surface (default arguments without @JvmOverloads, companion objects without @JvmStatic, extension functions in interfaces).
