43C — Passkeys & Credential Manager

FIDO2/WebAuthn passkeys replacing passwords, CredentialManager API (unifies passwords + passkeys + federated sign-in), biometric integration, and the security model that makes passkeys phishing-resistant.

ID: 43C ⭐ Tier 1 🔥 Hottest New Topic
🔑
1. Overview & Why It Matters

Passkeys are cryptographic key pairs where the private key never leaves your device and the public key is stored on the server. The one-sentence security argument: "You can't phish what never travels the wire."

Why Passwords Are Dying

Passwords fail at every layer of the security stack:

  • Phishing — users are tricked into typing credentials into fake login pages. Even with 2FA (SMS OTP), attackers use real-time phishing proxies to intercept codes.
  • Credential stuffing — leaked password databases are replayed against other services. Humans reuse passwords across sites.
  • Server-side data breaches — even if passwords are hashed with bcrypt, weak or reused passwords are cracked offline. With passkeys, the server stores only a public key. A breach of the server reveals nothing useful — the attacker gets a public key, which by definition is public.
  • SIM-swap & SS7 attacks — SMS OTP is compromised when the attacker takes over the phone number. TOTP is better but still vulnerable to real-time phishing.

What CredentialManager Does

Before CredentialManager, Android apps used three separate APIs for three auth methods:

Auth MethodOld APINew API
PasswordsAutofill framework / Smart Lock for PasswordsCredentialManager
Passkeys (FIDO2)FIDO2 API (com.google.android.gms.fido)CredentialManager
Federated (Google Sign-In)GoogleSignInClient / One TapCredentialManager

androidx.credentials.CredentialManager is the single unified API. One sign-in call returns whichever credential type the user selects — passkey, saved password, or Google account — with a consistent response object.

The Senior Interview Question

🌟 Common Interview Prompt

"How would you add passkey support to an existing password-based app?" — This requires understanding the FIDO2 registration + authentication flows, the CredentialManager API, the migration strategy for existing users, server-side requirements, and fallback handling for unsupported devices. All of that is in this topic.

Quick Mental Map

  • FIDO2 / WebAuthn — the open standard (W3C + FIDO Alliance) that defines the protocol
  • Passkey — the user-facing marketing term for a FIDO2 credential synced via a platform (Google Password Manager, iCloud Keychain, 1Password)
  • CredentialManager — the Android API that implements FIDO2 + password + federated sign-in
  • Relying Party (RP) — your server; identified by the RP ID (typically your domain, e.g. example.com)
  • Authenticator — the device (or security key) that generates and stores the private key

2. How Passkeys Work — FIDO2/WebAuthn Protocol

Key Pair Generation

When a user registers a passkey, the device generates a public/private key pair:

  • Private key — stored in the Android Keystore (hardware-backed on devices with a Secure Enclave or StrongBox). It never leaves the secure hardware. Not even your app can read it — you can only request a signing operation.
  • Public key — sent to your server and stored alongside the user's account. Not a secret. A breach of the public key reveals nothing.

Registration Flow

CLIENT (Android App) SERVER (Relying Party) ───────────────────────────────────────────────────────────── 1. User taps "Create Passkey" ──────── (1) Challenge request ──────▶ ◀─────── (2) Challenge (random nonce) ─ + rpId, userId, userName 3. CredentialManager calls system authenticator (Android Keystore) • Generates EC key pair (P-256) • Private key → hardware-backed • User verification via biometric 4. Authenticator signs challenge with NEWLY GENERATED private key Produces: authenticatorData + clientDataHash signature ──── (3) Send public key + signature ─▶ + credentialId + attestation object (4) Server verifies signature, stores public key + credentialId ◀──────── (5) Registration success ───

Authentication Flow

CLIENT (Android App) SERVER (Relying Party) ───────────────────────────────────────────────────────────── 1. User taps "Sign In with Passkey" ──────── (1) Challenge request ──────▶ ◀─────── (2) Challenge (random nonce) ─ + rpId + allowCredentials list 3. CredentialManager shows UI: "Sign in as Alice?" User approves via biometric/PIN 4. Authenticator signs challenge with EXISTING private key (looked up by credentialId) ──── (3) Send signed assertion ───────▶ + credentialId + signature (4) Server looks up public key for credentialId, verifies sig ◀──────── (5) Auth token / session ───

Why Passkeys Are Phishing-Resistant

Two properties combine to make phishing structurally impossible:

  1. Private key never leaves the device — a phishing site cannot steal the private key. There is no password to capture. Even a man-in-the-middle sees only the public key and a signature bound to a specific challenge.
  2. Challenge is origin-bound (rpId binding) — the authenticator cryptographically binds the signing operation to the Relying Party ID (your domain). A challenge from evil-bank.com cannot be used with a passkey registered for bank.com. The origin is included in clientDataJSON, which is part of the signed payload. If the origin doesn't match, the authenticator refuses to sign.
✅ Phishing-Resistance Mechanism

Even if a user is tricked into visiting evil-bank.com and clicks the fake sign-in button, the FIDO2 authenticator checks that evil-bank.com doesn't match the registered RP ID of bank.com. It refuses to sign. The phishing attempt fails at the cryptographic layer — not at the user's ability to detect fake sites.

Key FIDO2 Data Structures

Passkey Registration (Full Production Code)

The JSON request body mirrors the WebAuthn PublicKeyCredentialCreationOptions spec. Your server generates the JSON; the app passes it to CredentialManager.

import androidx.credentials.*
import androidx.credentials.exceptions.*

class PasskeyManager(
    private val context: Context,
    private val credentialManager: CredentialManager = CredentialManager.create(context)
) {

    /**
     * Register a new passkey for the user.
     * @param requestJson  JSON from your server: PublicKeyCredentialCreationOptions
     *                     Must contain: challenge, rp, user, pubKeyCredParams, etc.
     */
    suspend fun registerPasskey(requestJson: String): Result<String> {
        return try {
            val request = CreatePublicKeyCredentialRequest(
                requestJson = requestJson,
                // preferImmediatelyAvailableCredentials: if true, only show authenticators
                // that are immediately available (no hybrid/QR fallback).
                preferImmediatelyAvailableCredentials = false
            )

            val response = credentialManager.createCredential(
                context = context,
                request = request
            ) as CreatePublicKeyCredentialResponse

            // response.registrationResponseJson contains the JSON to send to your server:
            // { id, rawId, response: { attestationObject, clientDataJSON }, type }
            Result.success(response.registrationResponseJson)

        } catch (e: CreateCredentialCancellationException) {
            // User cancelled the passkey creation dialog
            Result.failure(e)
        } catch (e: CreateCredentialInterruptedException) {
            // System interrupted — retry is safe
            Result.failure(e)
        } catch (e: CreatePublicKeyCredentialDomException) {
            // DOMException from WebAuthn layer: invalid rpId, excluded credential, etc.
            // e.domError contains the specific error string
            Result.failure(e)
        } catch (e: CreateCredentialUnknownException) {
            Result.failure(e)
        }
    }
}

Passkey Sign-In — Unified GetCredentialRequest

The power of CredentialManager is that one GetCredentialRequest can simultaneously request passkeys, saved passwords, AND Google Sign-In. The system shows a single bottom-sheet picker; the user chooses one credential type.

suspend fun signIn(
    passkeyRequestJson: String,    // PublicKeyCredentialRequestOptions from server
    googleClientId: String        // For Google Sign-In option
): Result<SignInResult> {

    val getCredentialRequest = GetCredentialRequest(
        credentialOptions = listOf(
            // Option 1: passkey (FIDO2)
            GetPublicKeyCredentialOption(
                requestJson = passkeyRequestJson
            ),
            // Option 2: saved password from Password Manager
            GetPasswordOption(),
            // Option 3: Google Sign-In via Identity Services
            GetGoogleIdOption.Builder()
                .setFilterByAuthorizedAccounts(true)
                .setServerClientId(googleClientId)
                .setAutoSelectEnabled(true)
                .build()
        )
    )

    return try {
        val result = credentialManager.getCredential(
            context = context,
            request = getCredentialRequest
        )
        handleSignInResult(result.credential)
    } catch (e: NoCredentialException) {
        // ⚠️ No matching credentials found — user hasn't registered yet
        // Show registration UI or fall back to username/password form
        Result.failure(e)
    } catch (e: GetCredentialCancellationException) {
        Result.failure(e)
    } catch (e: GetCredentialInterruptedException) {
        Result.failure(e)
    } catch (e: GetCredentialUnknownException) {
        Result.failure(e)
    }
}

private fun handleSignInResult(credential: Credential): Result<SignInResult> {
    return when (credential) {
        is PublicKeyCredential -> {
            // Passkey: send credential.authenticationResponseJson to your server
            // Server verifies signature and issues session token
            Result.success(SignInResult.Passkey(credential.authenticationResponseJson))
        }
        is PasswordCredential -> {
            // Saved password: credential.id = username, credential.password = password
            Result.success(SignInResult.Password(credential.id, credential.password))
        }
        is CustomCredential -> {
            // Google Sign-In token via GoogleIdTokenCredential
            if (credential.type == GoogleIdTokenCredential.TYPE_GOOGLE_ID_TOKEN_CREDENTIAL) {
                val googleId = GoogleIdTokenCredential.createFrom(credential.data)
                Result.success(SignInResult.Google(googleId.idToken))
            } else {
                Result.failure(IllegalStateException("Unknown credential type"))
            }
        }
        else -> Result.failure(IllegalStateException("Unexpected credential"))
    }
}

sealed class SignInResult {
    data class Passkey(val responseJson: String) : SignInResult()
    data class Password(val username: String, val password: String) : SignInResult()
    data class Google(val idToken: String) : SignInResult()
}

4. Biometric Integration

Two Different Roles of Biometrics in Auth

This distinction trips up most candidates. There are two entirely different uses of biometrics in an Android auth system:

ScenarioWhat It DoesAPI UsedIs it FIDO2?
Biometric auth to unlock appReplaces password to unlock the app; backend doesn't know biometric was usedBiometricPrompt + KeyStoreNo
Biometric for passkey user verificationRequired by FIDO2 UV flag; authenticates the user to authorize the private key operationCredentialManager (internally uses system biometric)Yes

FIDO2 User Verification (UV) Requirement

When your server creates the FIDO2 challenge, it specifies userVerification in the request JSON:

// In your server-generated requestJson (PublicKeyCredentialRequestOptions):
{
  "challenge": "base64url-encoded-challenge",
  "rpId": "example.com",
  "userVerification": "required",   // "required" | "preferred" | "discouraged"
  "timeout": 60000
}
userVerificationBiometric Required?Use CasePitfall
"required"Yes — alwaysHigh-value operations (payments, account changes)Fails on devices with no biometric hardware enrolled
"preferred"Yes if availableMost sign-in flowsUV flag in authData may be 0 — server must still accept
"discouraged"NoLow-security, convenience sign-in onlyWeaker security; FIDO2 spec still allows UV if device chooses

How the System Handles Biometric for Passkeys

You do not call BiometricPrompt yourself for passkey operations. CredentialManager handles the biometric UI internally through the platform authenticator. Your app sees the result only after the user has successfully verified:

// ✅ CORRECT: CredentialManager handles biometric internally
val result = credentialManager.getCredential(context, request)
// By the time you get here, the user has already completed biometric verification
// The UV flag in the assertion's authenticatorData confirms verification occurred

// ❌ WRONG: Do NOT wrap this in your own BiometricPrompt
// That would double-prompt the user for biometric

BiometricPrompt for Non-Passkey Operations

For app-level biometric auth (e.g. unlocking the app after it was backgrounded, or authorizing a payment via a server-signed JWT rather than FIDO2), you use BiometricPrompt directly with a KeyStore-backed CryptoObject:

private fun authenticateForAppUnlock(onSuccess: (ByteArray) -> Unit) {
    val biometricPrompt = BiometricPrompt(
        this,
        ContextCompat.getMainExecutor(this),
        object : BiometricPrompt.AuthenticationCallback() {
            override fun onAuthenticationSucceeded(result: BiometricPrompt.AuthenticationResult) {
                val cipher = result.cryptoObject?.cipher ?: return
                // Use cipher to decrypt app data / issue local session
                val decrypted = cipher.doFinal(encryptedSessionToken)
                onSuccess(decrypted)
            }
            override fun onAuthenticationError(errorCode: Int, errString: CharSequence) {
                // Handle lockout, no hardware, etc.
            }
        }
    )

    val promptInfo = BiometricPrompt.PromptInfo.Builder()
        .setTitle("Unlock App")
        .setSubtitle("Use biometric to continue")
        .setNegativeButtonText("Use PIN")
        .setConfirmationRequired(false)
        .build()

    biometricPrompt.authenticate(promptInfo, BiometricPrompt.CryptoObject(cipher))
}
💡 Key Distinction for Interviews

CredentialManager passkey sign-in: biometric is managed by the platform authenticator internally — you call getCredential() and receive a signed assertion only after the user verifies. BiometricPrompt with KeyStore: you manage the biometric UI yourself, receive a CryptoObject (cipher/signature/mac) on success, and use it to perform a local crypto operation. They solve different problems.

5. Migration Strategy

The Core Challenge

You can't force existing users onto passkeys overnight. They have saved passwords, they're on older devices, and they don't know what a passkey is. A good migration strategy preserves continuity for all users while progressively nudging them toward passkeys.

Three-Phase Migration

Phase 1 — Opt-In Post-Login Registration

After a successful password sign-in, prompt the user to create a passkey. This is the lowest-friction entry point — the user is already authenticated, so registration can proceed without re-auth.

// Called after successful password sign-in, user is authenticated
suspend fun offerPasskeyUpgrade(userId: String, userName: String) {
    // 1. Ask server for registration options
    val registrationJson = authApi.startPasskeyRegistration(userId)

    // 2. Attempt passkey creation (may fail on unsupported devices)
    val result = passkeyManager.registerPasskey(registrationJson)
    result.onSuccess { responseJson ->
        // 3. Send response to server to complete registration
        authApi.completePasskeyRegistration(userId, responseJson)
        // 4. Mark this user as passkey-enrolled in local preferences
        prefs.edit().putBoolean("passkey_enrolled", true).apply()
    }.onFailure {
        // Silent failure — user stays on passwords. Don't block sign-in flow.
    }
}

Phase 2 — Passkey as Primary Sign-In Option

Once a user has a passkey, show it as the first/preferred option on the sign-in screen. The GetCredentialRequest with GetPublicKeyCredentialOption first naturally achieves this — if a passkey exists, the system bottom-sheet surfaces it prominently.

Phase 3 — Password Deprecation

Once passkey adoption crosses a threshold (e.g. 80%+ of active users), you can:

  • Remove password fields from the sign-in UI for passkey-enrolled users
  • Require passkey re-enrollment for users whose passwords haven't been used in 180+ days
  • Offer account recovery via email/SMS only (not passwords) as the fallback
  • Never fully remove password auth until you have a solid account recovery story

Handling Unsupported Devices

Passkeys require API 28+. Devices below that threshold (very small percentage by 2025) and devices without biometric hardware enrolled cannot use passkeys. Detect and gracefully degrade:

fun isPasskeySupported(context: Context): Boolean {
    // Passkeys via CredentialManager need API 28+ and Play Services
    if (Build.VERSION.SDK_INT < Build.VERSION_CODES.P) return false

    // Check if BiometricManager reports biometric hardware is available
    val biometricManager = BiometricManager.from(context)
    return when (biometricManager.canAuthenticate(
        BiometricManager.Authenticators.BIOMETRIC_STRONG or
        BiometricManager.Authenticators.DEVICE_CREDENTIAL
    )) {
        BiometricManager.BIOMETRIC_SUCCESS -> true
        else -> false  // NO_HARDWARE, NONE_ENROLLED, SECURITY_UPDATE_REQUIRED
    }
}

Server-Side Requirements

  • FIDO2 server library — you need a server-side WebAuthn library (e.g. webauthn4j for Java/Kotlin, fido2-lib for Node). Libraries handle verifying attestation and assertion objects.
  • Relying Party ID must match your domain — if your app is at example.com, the RP ID must be example.com (or a registrable domain suffix). Cannot be an IP address.
  • assetlinks.json — https://example.com/.well-known/assetlinks.json must list your app's package name and signing certificate SHA256, just like App Links. This proves to the Android platform that the app is the legitimate RP for that domain.
  • Challenge storage — server must store issued challenges with a TTL (typically 60 seconds) and mark them as used after one verification. Prevents replay attacks.
🌟 Production Migration Pattern

The safest migration architecture: always have both password and passkey auth working simultaneously on the server. A user can sign in with either. Passkey is the preferred UI path; password is the fallback path. Only remove password auth when your metrics show near-zero usage and you've shipped robust account recovery.

6. Security Deep Dive

Android Keystore Hardware-Backed Storage

When CredentialManager creates a passkey, the private key is stored in the Android Keystore backed by the Trusted Execution Environment (TEE) or StrongBox. This is the critical security property:

  • Private key material is generated inside the secure hardware and never exported — not to your app, not to the OS, not via adb.
  • All cryptographic operations (signing the FIDO2 assertion) happen inside the secure enclave. Your app only receives the output (signature), never the key.
  • The key can be configured to require user authentication before each use (setUserAuthenticationRequired(true) in KeyGenParameterSpec) — this is how biometric gating works at the hardware level.

For passkeys, the system automatically uses the best available hardware. You can check attestation level in the attestation statement returned during registration — your server should validate this for high-security use cases.

OWASP MASVS Alignment

  • MSTG-AUTH-8: Biometric authentication, if used, is not event-bound and the local authentication must be bound to the device — passkeys satisfy this by tying the private key operation to biometric verification in hardware.
  • MSTG-AUTH-1: Users are identified and authenticated at the remote endpoint using credentials that are not locally stored in cleartext — public key stored server-side, private key never leaves TEE.
  • MSTG-STORAGE-1: System credential storage facilities are used appropriately — Android Keystore is the recommended facility.

To create a device-bound (non-syncable) passkey, include "residentKey": "required" and "authenticatorAttachment": "platform" and instruct users to not enroll in passkey sync — though enforcing non-sync from the app side is not directly controllable on Android 14+ (the platform may still choose to sync).

7. Pitfalls & Production Bugs

Bug 1: Not Handling NoCredentialException

The most common production mistake: calling getCredential() and not handling NoCredentialException. This exception fires when the user has no saved credentials of any of the requested types. The correct response is to show the registration UI.

// ❌ WRONG — crashes silently or shows a generic error
try {
    val result = credentialManager.getCredential(context, request)
} catch (e: GetCredentialException) {
    showError("Sign in failed")  // ← wrong: hides the "no credentials" case
}

// ✅ CORRECT — handle NoCredentialException specifically
try {
    val result = credentialManager.getCredential(context, request)
    handleSignInResult(result.credential)
} catch (e: NoCredentialException) {
    // No passkey/password/Google account found — route to registration
    showRegistrationOptions()
} catch (e: GetCredentialCancellationException) {
    // User cancelled — do nothing, let them retry
}

Bug 2: Relying Party ID Mismatch

The RP ID in the registration request must exactly match the RP ID in the authentication request. A common mistake is using the full origin (https://example.com) as the RP ID instead of just the domain (example.com). Another: using a subdomain for one and the apex domain for the other.

// ❌ WRONG — rp.id is the full origin, not the domain
{
  "rp": { "id": "https://example.com", "name": "Example" }
}

// ✅ CORRECT — rp.id is the registrable domain suffix
{
  "rp": { "id": "example.com", "name": "Example" }
}

// ❌ ALSO WRONG — inconsistent RP IDs between registration and auth
// Registration: "rp.id": "login.example.com"
// Auth:         "rpId": "example.com"   ← mismatch → auth always fails

Bug 3: No Password Fallback for Unsupported Devices

If you only call GetPublicKeyCredentialOption without GetPasswordOption, users on API < 28 or without biometric hardware get a NoCredentialException with no way to sign in. Always include GetPasswordOption() in the list.

Bug 4: Challenge Replay Attack (Server-Side)

Server issues a challenge with a long TTL (e.g. 10 minutes). An attacker intercepts the signed assertion, waits for the server to accept it, then replays it within the TTL window. Fix: set challenge TTL to 60 seconds and mark each challenge as consumed after first successful verification.

Bug 5: userVerification Required on Biometric-Less Devices

Setting "userVerification": "required" on authentication challenges means the authenticator MUST verify the user (biometric or device PIN). On devices where no biometric is enrolled and the device has no screen lock, this fails with a WebAuthn error. Check your device population before requiring UV.

Bug 6: Testing on Emulator Only

Android emulators have limited passkey support. Passkey creation via the system authenticator (Google Password Manager) requires a real device with biometric enrolled and Google Play Services. Use a real device for passkey E2E testing. Emulators are sufficient only for unit tests that mock the CredentialManager interface.

// For unit tests: inject a mock CredentialManager
class PasskeyManagerTest {
    private val mockCredentialManager = mockk<CredentialManager>()
    private val sut = PasskeyManager(context, mockCredentialManager)

    @Test
    fun `registerPasskey returns failure on cancellation`() = runTest {
        coEvery {
            mockCredentialManager.createCredential(any(), any())
        } throws CreateCredentialCancellationException()

        val result = sut.registerPasskey("""{"challenge":"abc"}""")
        assertTrue(result.isFailure())
    }
}

8. Interview Framework

What Interviewers Test (Especially Fintech)

  • Phishing resistance — can you explain why passkeys are phishing-resistant at the cryptographic level (origin-bound challenge + private key never leaves device)?
  • CredentialManager unification — do you know it handles passkeys + passwords + federated sign-in in one call?
  • Migration path — can you describe a three-phase approach that doesn't break existing users?
  • Error handling — do you handle NoCredentialException specifically?
  • FIDO2 flow — can you walk through registration vs authentication at the protocol level?

30-Second Answer

"Passkeys are FIDO2 key pairs where the private key is hardware-backed in the Android Keystore and never leaves the device. The server stores only the public key, so a server breach leaks nothing useful. The challenge is origin-bound — signed with a hash of the RP ID in the payload — so a phishing site on a different domain can't replay the assertion. On Android, I'd use CredentialManager from androidx.credentials, which unifies passkeys, saved passwords, and Google Sign-In into a single GetCredentialRequest. For migration: phase one is offering passkey registration post-login as an opt-in upgrade; phase two is surfacing passkeys as the primary sign-in option; phase three is deprecating passwords only once adoption is high and account recovery is solid."

2-Minute Answer — FIDO2 Flow Detail

"For the FIDO2 registration flow: the server generates a random challenge and sends it along with the RP ID, user handle, and allowed key algorithms. CredentialManager calls the platform authenticator (Android Keystore), which generates an EC P-256 key pair, performs user verification via biometric, signs the challenge with the private key, and returns an attestation object containing the public key and the signature. The app sends this to the server, which verifies the signature, extracts the public key, and stores it indexed by the credential ID.

For authentication: the server sends a new random challenge. The authenticator looks up the private key by credential ID, performs user verification, signs the challenge (bound to the origin via clientDataJSON), and sends the assertion. The server verifies the signature using the stored public key. At no point does a secret travel over the wire.

In production, I'd handle NoCredentialException by routing to registration, set userVerification: preferred for normal sign-in (required only for sensitive operations), and include GetPasswordOption as a fallback for users who haven't enrolled a passkey yet. The RP ID must match the domain in assetlinks.json exactly."

Must-Mention Checklist

1
Private key never leaves device — hardware-backed in Android Keystore (TEE or StrongBox). This is the fundamental security property.
2
Origin-bound challenge — RP ID hash is included in the signed payload. A phishing site on a different domain cannot reuse the assertion.
3
CredentialManager unifies three auth methods — one GetCredentialRequest with GetPublicKeyCredentialOption + GetPasswordOption + GetGoogleIdOption.
4
Handle NoCredentialException explicitly — route to registration UI. Don't treat it as a generic error.
5
RP ID must match assetlinks.json domain — must be a registrable domain suffix, not a full URL.
6
Three-phase migration — post-login opt-in, then primary option, then deprecate passwords. Never remove password auth without account recovery.
7
userVerification required vs preferred — required fails on devices without enrolled biometric; preferred is the safe default.

9. Flash Cards

Tap a card to reveal the answer.

What is a passkey?
A FIDO2 public/private key pair where the private key is hardware-backed in the Android Keystore and never leaves the device. The public key is stored on the server. No secret ever travels over the wire — instead, the device signs server-issued challenges to prove possession of the private key.
FIDO2 Registration Flow (4 steps)
1. Server sends challenge + RP ID + user info. 2. Device generates EC key pair; private key stays in hardware. 3. Device signs challenge, sends public key + signature + attestation. 4. Server verifies signature and stores public key indexed by credentialId.
FIDO2 Authentication Flow (4 steps)
1. Server sends challenge + RP ID + allowCredentials list. 2. User approves via biometric (user verification). 3. Device signs challenge with stored private key; sends assertion. 4. Server looks up public key for credentialId and verifies signature.
Why are passkeys phishing-resistant?
Two properties: (1) Private key never leaves the device — nothing to steal from the wire. (2) Challenge is origin-bound — the RP ID hash is in the signed payload; a phishing site on a different domain can't produce a valid assertion for your domain.
CredentialManager vs BiometricPrompt
CredentialManager: unified API for passkeys + passwords + federated sign-in. Biometric handled internally by platform authenticator. BiometricPrompt: app-managed biometric UI for app-level auth (unlock, local key operations). Don't wrap CredentialManager in BiometricPrompt — that double-prompts the user.
GetCredentialRequest unification
A single GetCredentialRequest can contain: GetPublicKeyCredentialOption (passkeys) + GetPasswordOption (saved passwords) + GetGoogleIdOption (Google Sign-In). The system shows one picker UI; the app handles whichever credential type the user selects.
NoCredentialException — correct handling
Thrown when no matching credentials exist for the request. Do not show a generic error. Do route the user to a registration flow (passkey creation or username/password form). It is an expected, non-error state for first-time or unenrolled users.
Relying Party ID (rpId) rules
Must be a registrable domain suffix (e.g. example.com), NOT a full URL (https://example.com). Must match the domain in assetlinks.json. Must be the same value in both registration and authentication requests. A mismatch causes assertion verification to fail with a DOM error.
Device-bound vs syncable passkeys
Syncable: backed up and synced via Google Password Manager / iCloud Keychain. Lost device → restore from cloud. Best UX for consumers. Device-bound: locked to one device; not synced. Lost device → must re-register. Better for high-assurance enterprise use cases.
Android version requirements for passkeys
API 28 (Android 9) minimum with Google Play Services 23.3+. Full passkey sync via Google Password Manager requires API 34 (Android 14). Below API 28: no passkey support — must fall back to password + GetPasswordOption.

10. Interview Questions
Q1. Why are passkeys more secure than passwords + SMS OTP?
Easy ⌄

Three compounding problems with password + SMS OTP:

  1. Passwords are phishable — users can be tricked into entering them on fake sites. A real-time phishing proxy forwards credentials to the real site immediately.
  2. SMS OTP is interceptable — real-time phishing proxies capture the OTP in flight. SIM-swap attacks let attackers receive SMS messages. SS7 protocol vulnerabilities allow carrier-level interception.
  3. Server stores a secret — even a bcrypt-hashed password is a secret. If the database is breached and the password is weak or reused, it's cracked offline.

Passkeys solve all three: the private key never leaves the device (nothing to phish), the challenge is origin-bound (a phishing proxy on evil.com can't produce a valid assertion for bank.com), and the server stores only a public key (a breach reveals nothing useful).

Q2. Walk me through how CredentialManager unifies sign-in. What does GetCredentialRequest look like for a production app?
Medium ⌄

A production GetCredentialRequest includes all three credential types so the system can surface whatever the user has:

val request = GetCredentialRequest(
    credentialOptions = listOf(
        GetPublicKeyCredentialOption(requestJson = passkeyChallenge), // passkeys
        GetPasswordOption(),                                              // saved passwords
        GetGoogleIdOption.Builder().setServerClientId(clientId).build()   // Google
    )
)

The system presents a single bottom-sheet showing all available options. The response is a Credential sealed class — you switch on PublicKeyCredential, PasswordCredential, or CustomCredential (Google ID token) to handle each case. This replaced three separate APIs: FIDO2 API, Smart Lock for Passwords, and One Tap / Google Sign-In.

Q3. Spot the bug: this sign-in code works in testing but breaks for 20% of users in production. What's missing?
Medium ⌄ 
suspend fun signIn(): Result<Credential> {
    return try {
        val result = credentialManager.getCredential(context, request)
        Result.success(result.credential)
    } catch (e: GetCredentialException) {
        showError("Sign in failed. Please try again.")
        Result.failure(e)
    }
}

Bug: NoCredentialException is a subtype of GetCredentialException but it's NOT an error — it means the user hasn't registered a passkey or saved password yet. The code catches it as a generic error and shows "Sign in failed", which is wrong.

Fix: catch NoCredentialException before the generic catch and route to registration:

} catch (e: NoCredentialException) {
    navigateToRegistration()   // show passkey/password registration UI
    Result.failure(e)
} catch (e: GetCredentialException) {
    showError("Sign in failed")
    Result.failure(e)
}

The 20% who "break" are new users or users who've never saved credentials — a completely expected state.

Q4. Your passkey authentication always fails in production but works in your test environment. The logs show a DOMException. What's the most likely cause?
Medium ⌄

The most likely cause is a Relying Party ID mismatch. Common scenarios:

  1. Registration used one RP ID, authentication uses a different one. e.g., registration used staging.example.com and production auth uses example.com. Each passkey is cryptographically bound to the RP ID used during registration — it will never verify against a different RP ID.
  2. RP ID is a full URL instead of a domain. The RP ID must be example.com, not https://example.com. WebAuthn validation fails on the format.
  3. assetlinks.json mismatch. The RP ID in the request doesn't match the domain in /.well-known/assetlinks.json for your app. Android's platform authenticator validates this at the time of both registration and authentication.

Debug approach: compare the exact rpId values in the registration JSON vs the authentication JSON logged server-side. They must be character-for-character identical. Verify your assetlinks.json is deployed and publicly accessible at the domain matching your RP ID.

Q5. How do you migrate a 5-million-user app from username/password to passkeys without breaking anyone?
Hard ⌄

A phased migration strategy that never removes access for any user:

  1. Phase 1 — Opt-in post-login (months 1-3): After successful password sign-in, show a one-time bottom sheet: "Create a passkey for faster sign-in?" Call CreatePublicKeyCredentialRequest with the server-generated challenge. Store the passkey on the server indexed by user ID. Measure enrollment rate. Target: 30%+ of active users.
  2. Phase 2 — Passkey as primary UI (months 4-6): Update the sign-in screen to call GetCredentialRequest with passkey + password options. Enrolled users see their passkey surfaced first. Add a "Use password instead" link for fallback. Measure passkey sign-in success rate.
  3. Phase 3 — Password deprecation (month 7+): Once 80%+ of sign-ins use passkeys, begin prompting non-enrolled users to upgrade on each password sign-in. Mark stale passwords (180+ days unused) and send re-enrollment emails. Never delete password auth — keep it as account recovery alongside email link. Ship account recovery via email + passkey re-registration before removing the password UI entirely.

Fallback throughout: always include GetPasswordOption in your requests. Users on API < 28 silently get password-only. Users who dismiss passkey prompts can sign in normally. Never force-break access.

Q6. What's the difference between userVerification "required" vs "preferred" and when does the wrong choice break your app?
Medium ⌄

"required": the authenticator MUST verify the user (biometric or device PIN) before signing. If the device has no enrolled biometric or screen lock, the operation fails with a WebAuthn error (NotAllowedError). This breaks your app for all users on devices with biometric hardware but no enrolled fingerprint/face.

"preferred": the authenticator will try to verify the user if it can, but proceeds even if it can't. The UV flag in the returned authenticatorData tells you whether verification happened. Your server must be configured to accept assertions where UV=0.

When to use which:

  • "required": high-value operations (payment authorization, account settings changes, admin actions). You explicitly need proof of physical presence.
  • "preferred": standard sign-in. Best for most apps. Doesn't break on biometric-less devices.
  • "discouraged": low-security convenience (remember-me style). Biometric UI won't be shown.

Pitfall: setting "required" for your default sign-in call. A user who hasn't enrolled a fingerprint (e.g. tablet users, older users) can't sign in at all.

Q7. A user loses their phone. How do they recover access to your app if they only had a passkey and no password?
Hard ⌄

Recovery depends on whether the passkey was syncable or device-bound:

If syncable (Google Password Manager): the user signs in to their Google account on a new device. Google Password Manager restores the passkey automatically. On Android 14+, synced passkeys appear on the new device immediately after Google account setup. This is the recommended consumer flow.

If device-bound (non-syncable): the passkey is lost with the device. The user needs an alternative recovery path. This must be designed in advance:

  • Account recovery via email — send a magic link; user clicks it, gets a temporary session, registers a new passkey on the new device.
  • Recovery code — generated at passkey registration time; user stores it separately. Presented during recovery to authorize a new passkey registration.
  • Backup passkey on a second device — encourage users to register a passkey on a second device (tablet, laptop) at enrollment time.
  • Support-assisted recovery — identity verification by support team; manual account unlock. Expensive but necessary for high-security apps that ban passkey sync.

Key design rule: never ship passkey-only auth without a robust account recovery flow. The recovery flow is the attack surface to protect — it must require proof of identity equivalent to the passkey security level.

Q8. How does Google Password Manager sync passkeys, and what are the security implications for enterprise apps?
Hard ⌄

On Android 14+, Google Password Manager encrypts passkeys using keys derived from the user's Google account credentials (end-to-end encrypted). The private key material is synced encrypted to Google's servers and restored to new devices after Google account sign-in. Google cannot decrypt the passkey material in transit or at rest.

Security implications for enterprise:

  • Cloud trust boundary: even though Google can't read the key, the passkey is as secure as the user's Google account. A compromised Google account (via password + SIM-swap) could theoretically allow restoration of passkeys to an attacker's device. For enterprise, this may violate "device-bound" requirements.
  • BYOD risk: on a shared or corporate device, if the user's personal Google account syncs passkeys for work apps, there's a policy concern about key custody.
  • Mitigation: enterprise apps that require device-bound passkeys should use the FIDO2 "authenticatorAttachment": "platform" + non-syncable storage. This is enforced via MDM policy or by validating the attestation to confirm the credential is not backed by a credential provider that performs sync.
  • Alternative: use security keys (hardware tokens) as the authenticator for highest-assurance enterprise scenarios. CredentialManager supports cross-platform authenticators via the hybrid transport.
