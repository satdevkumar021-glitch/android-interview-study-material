1G — Delegation & Operators

Class delegation (by), property delegation, by lazy, observable, vetoable, custom delegates, operator overloading, and destructuring — Kotlin features used throughout Android architecture.

ID: 1G ⭐ Tier 1
🔍
1. Overview

What it is

Kotlin's by keyword enables two delegation patterns: class delegation (forward interface calls to another object — composition over inheritance) and property delegation (delegate get/set logic to a reusable object). Operator overloading lets you define intuitive syntax for domain types. Destructuring unpacks objects into multiple variables via componentN().

Why it matters for Android

  • by lazy — deferred initialization of ViewBinding, expensive dependencies (used everywhere)
  • by viewModels(), by activityViewModels() — Jetpack property delegates for ViewModel creation
  • by Delegates.observable() — trigger recomposition/logging when a property changes
  • Class delegation: compose complex classes from simpler ones without inheritance
  • Destructuring: data class deconstruction in for loops and function returns
Senior Mental Model
Property delegation is the underlying mechanism for by lazy, by viewModels(), by remember { } (Compose), and by mutableStateOf(). Understanding it means you can build your own delegates for cross-cutting concerns — logging, validation, preference-backed properties.

2. How It Works

Class Delegation — by

interface Logger {
    fun log(msg: String)
    fun error(msg: String)
}

class TimberLogger : Logger {
    override fun log(msg: String) = Timber.d(msg)
    override fun error(msg: String) = Timber.e(msg)
}

// PaymentService delegates Logger to TimberLogger — no need to implement manually
class PaymentService(private val api: PaymentApi, logger: Logger) : Logger by logger {
    // log() and error() are automatically forwarded to 'logger'
    suspend fun pay(amount: Double) {
        log("Paying $$amount")   // uses delegated Logger
        api.pay(amount)
    }
}
// Compiled: calls to Logger methods forwarded to the delegate instance

Property Delegation — how it works

// A delegate must implement getValue (and setValue for var)
class StringDelegate {
    operator fun getValue(thisRef: Any?, property: KProperty<*>): String =
        "Value of ${property.name}"
    operator fun setValue(thisRef: Any?, property: KProperty<*>, value: String) {
        println("Setting ${property.name} = $value")
    }
}

class Foo {
    var name: String by StringDelegate()  // get/set delegated
}

by lazy — deferred init

// Computed once on first access, thread-safe by default (SYNCHRONIZED)
private val binding: FragmentHomeBinding by lazy {
    FragmentHomeBinding.inflate(layoutInflater)
}

// LazyThreadSafetyMode options:
val x by lazy(LazyThreadSafetyMode.NONE) { expensiveInit() }  // single-thread only

Delegates.observable — react to changes

import kotlin.properties.Delegates

var userName: String by Delegates.observable("Guest") { property, old, new ->
    println("${property.name}: $old → $new")
    analytics.track("name_changed")
}

Delegates.vetoable — conditional update

var age: Int by Delegates.vetoable(0) { _, old, new ->
    new >= 0    // return true to accept, false to reject the new value
}
age = 25   // accepted
age = -1   // rejected — stays 25

Custom Property Delegate — SharedPreferences-backed

class PrefsDelegate<T>(
    private val prefs: SharedPreferences,
    private val key: String,
    private val default: T
) {
    @Suppress("UNCHECKED_CAST")
    operator fun getValue(thisRef: Any?, prop: KProperty<*>): T =
        (prefs.all[key] as? T) ?: default

    operator fun setValue(thisRef: Any?, prop: KProperty<*>, value: T) {
        prefs.edit { putString(key, value.toString()) }
    }
}

// Usage:
var authToken: String by PrefsDelegate(prefs, "auth_token", "")

Operator Overloading

// Must use 'operator' keyword + predefined function name
data class Money(val amount: Double, val currency: String) {
    operator fun plus(other: Money): Money {
        require(currency == other.currency) { "Currency mismatch" }
        return copy(amount = amount + other.amount)
    }
    operator fun compareTo(other: Money): Int = amount.compareTo(other.amount)
    operator fun unaryMinus(): Money = copy(amount = -amount)
}

val total = Money(100.0, "INR") + Money(50.0, "INR")  // 150.0 INR
val refund = -Money(25.0, "INR")
if (balance > Money(0.0, "INR")) { ... }    // compareTo

Destructuring

// data classes auto-generate componentN()
data class Transaction(val id: String, val amount: Double, val type: String)

val tx = Transaction("t1", 250.0, "DEBIT")
val (id, amount, type) = tx  // calls component1(), component2(), component3()

// In for loops:
for ((key, value) in map) { println("$key = $value") }

// Skip fields with _:
val (_, amount2, _) = tx   // only care about amount

// Custom componentN() for non-data classes:
operator fun Transaction.component4() = amount * 0.18  // GST

When NOT to Use

Do NOT
  • Overload operators for non-obvious semantics — only when it reads naturally
  • Use class delegation to avoid understanding an interface — it's a composition tool, not a shortcut
  • Use by lazy for mutable values that need to change — use a function or StateFlow instead
  • Use Delegates.observable in performance-critical tight loops — adds overhead per assignment
  • Destructure when you only need one field — just access it directly

4. Production Example
Scenario
Banking app — transaction processing and ViewModel delegates. Shows class delegation, custom property delegate, operator overloading, and destructuring together.

Class delegation — composing a repository

// data/repository/TransactionRepositoryImpl.kt
internal class TransactionRepositoryImpl @Inject constructor(
    private val api: TransactionApi,
    cache: TransactionCache,           // injected cache implementation
    logger: Logger                       // injected logger implementation
) : TransactionRepository,
    TransactionCache by cache,         // all Cache methods forwarded to 'cache'
    Logger by logger {                  // all Logger methods forwarded to 'logger'

    override suspend fun getTransactions(accountId: String): List<Transaction> {
        log("Fetching transactions for $accountId")   // uses delegated Logger
        return getCached(accountId)                     // uses delegated Cache
            ?: api.getTransactions(accountId).also { store(accountId, it) }
    }
}

Custom delegate — encrypted SharedPreferences property

// data/local/SecurePrefsDelegate.kt
class SecureStringDelegate(
    private val securePrefs: EncryptedSharedPreferences,
    private val key: String
) {
    operator fun getValue(ref: Any?, prop: KProperty<*>): String? =
        securePrefs.getString(key, null)

    operator fun setValue(ref: Any?, prop: KProperty<*>, value: String?) =
        securePrefs.edit {
            if (value != null) putString(key, value)
            else remove(key)
        }
}

// data/local/SessionManager.kt
class SessionManager @Inject constructor(securePrefs: EncryptedSharedPreferences) {
    var authToken: String? by SecureStringDelegate(securePrefs, "auth_token")
    var refreshToken: String? by SecureStringDelegate(securePrefs, "refresh_token")
    // Reading/writing tokens reads/writes encrypted prefs automatically
}

Operator overloading — Money domain type

// domain/model/Money.kt
data class Money(val paise: Long, val currency: String = "INR") {
    operator fun plus(other: Money): Money {
        require(currency == other.currency) { "Currency mismatch: $currency vs ${other.currency}" }
        return copy(paise = paise + other.paise)
    }
    operator fun minus(other: Money): Money {
        require(currency == other.currency)
        return copy(paise = paise - other.paise)
    }
    operator fun compareTo(other: Money): Int = paise.compareTo(other.paise)

    val rupees: Double get() = paise / 100.0
    override fun toString() = "₹${rupees}"
}

// Usage in use case — reads like domain language
val balance = Money(50000)  // ₹500
val charge  = Money(1500)   // ₹15
val remaining = balance - charge
if (remaining > Money(0)) { processPayment() }

Destructuring in a ViewModel

// presentation/TransactionViewModel.kt
fun processTransactions(transactions: List<Transaction>) {
    val summary = transactions.groupBy { it.type }
    for ((type, txList) in summary) {       // destructuring map entry
        log("$type: ${txList.size} transactions")
    }

    // Destructuring a Pair return
    val (debits, credits) = transactions.partition { it.type == "DEBIT" }
}

6. Pitfalls & Best Practices

Delegate object created every time

// ❌ BAD — new delegate object created per property access (if not cached)
class Foo {
    val x by ExpensiveDelegate()  // new instance each time Foo is instantiated
}
// ✅ GOOD — cache the delegate or use a factory function
fun <T> prefs(key: String, default: T) = PrefsDelegate(sharedPrefs, key, default)
var token by prefs("token", "")  // cleaner factory usage

Operator overloading with side effects — confusing

// ❌ BAD — + operator triggers a network call? Never expected
operator fun Cart.plus(item: Item): Cart {
    repository.addItemToCart(item)  // side effect in +!
    return copy(items = items + item)
}
// ✅ GOOD — operator returns new value, side effects in ViewModel/UseCase
operator fun Cart.plus(item: Item): Cart = copy(items = items + item)
// Let the ViewModel call repository.addItem() separately

Class delegation with val — delegate fixed at construction

// The delegate is the object passed at construction — cannot change later
class Repo(logger: Logger) : Logger by logger

// If you need to swap the delegate at runtime → use manual forwarding instead

Destructuring with position — fragile if data class changes

// ❌ BAD — positional destructuring breaks if fields are reordered
val (id, name, email, phone) = user  // breaks if User adds a field at position 2
// ✅ GOOD — use named properties unless destructuring is clearly for iteration
val id = user.id
val name = user.name
// Destructure only in for loops or when all fields are needed in order

Production Best Practices

  1. Use class delegation to compose multiple interfaces without inheritance hierarchies.
  2. Custom property delegates are excellent for cross-cutting concerns: encryption, preferences, logging on set.
  3. Operator overloading: only for value types with natural arithmetic semantics — never with side effects.
  4. Keep destructuring to data classes with stable field order, or map iteration — avoid for complex classes.
  5. Prefer by lazy over lateinit for immutable computed properties.

7. Interview Answer Framework

30-Second Answer

"Kotlin's by keyword enables two patterns. Class delegation forwards interface method calls to a delegate object — it's composition over inheritance without boilerplate. Property delegation lets you reuse get/set logic — by lazy, by Delegates.observable, and Jetpack's by viewModels() are all property delegates. I use custom delegates for cross-cutting concerns like storing properties to EncryptedSharedPreferences transparently. Operator overloading lets domain value types like Money support natural arithmetic. Destructuring unpacks data classes via componentN() functions."

2-Minute Structured Answer

"Two delegation patterns. Class delegation with by: if a class implements an interface, you can forward all calls to a delegate object. This gives you composition over inheritance — a Repository can delegate its Logger and Cache interfaces to separate implementations injected via constructor. The compiler generates the forwarding code; you don't write it manually.

Property delegation: any object with operator fun getValue/setValue can back a property. This is how by lazy works — it's a standard library delegate. I use this pattern for things like EncryptedSharedPreferences-backed properties: reading authToken reads from encrypted prefs; writing it encrypts and persists automatically. The call site is just var authToken by secureDelegate — completely transparent.

Operator overloading: I use it for domain value types. A Money type with +, -, and compareTo operators makes financial calculations read like arithmetic rather than method calls. The critical rule: operators must be pure — no side effects.

Destructuring via componentN: data classes auto-generate these, enabling val (id, name) = user and for ((key, value) in map). Useful but fragile if field order changes — I use it mainly in for loops."

Must-Mention Points

1
Class delegation (by) = composition over inheritance — auto-forwards interface methods, no boilerplate
2
Property delegation requires operator fun getValue (and setValue for var) — by lazy, by viewModels(), custom delegates all use this
3
Custom delegates enable cross-cutting concerns: encrypted storage, observable properties, validation
4
Operator overloading requires the operator keyword + predefined function names (plus, invoke, compareTo...)
5
Destructuring uses componentN() — auto-generated by data classes; positional, so fragile if class structure changes
6
Operators must be pure — no side effects; use for value types with natural semantics

Do NOT Go Deeper Unless Asked

  • Delegation compilation details (synthetic accessors, delegate field storage)
  • ReadOnlyProperty / ReadWriteProperty interfaces in stdlib
  • Compose's by remember and by mutableStateOf internals

Likely Follow-up Questions

How does by lazy work internally?It's a property delegate. lazy { } returns a Lazy<T> object implementing getValue. On first getValue call, it runs the lambda and caches the result. Subsequent calls return the cached value. Thread-safety handled by SYNCHRONIZED mode (default double-checked locking).

9. Interview Questions (Self-Check)
How to use
Answer first, then reveal.

Basic

B1 — What is the difference between class delegation and property delegation in Kotlin?
Easy▼
Class delegation: forwards interface method calls to a delegate object. class A(b: SomeInterface) : SomeInterface by b — all methods of SomeInterface are auto-forwarded to b. This is composition over inheritance.

Property delegation: delegates the get/set logic of a property to an object that implements operator fun getValue/setValue. val x by lazy { ... } — the Lazy object handles when and how x's value is computed. They solve different problems at different levels.
B2 — What does Delegates.observable do? Give a use case.
Easy▼
Delegates.observable(initialValue) { property, oldValue, newValue -> } — a property delegate that calls the lambda every time the property is assigned a new value. The lambda receives the property metadata, the old value, and the new value. It does NOT prevent the change (use vetoable for that).

Android use case: trigger analytics when a user's status changes, or call notifyDataSetChanged() on a RecyclerView adapter when the data property is updated.
B3 — What requirements must a class meet to be a property delegate?
Easy▼
The class must implement (or provide as extension functions):
• operator fun getValue(thisRef: T?, property: KProperty<*>): R — for val properties
• operator fun setValue(thisRef: T?, property: KProperty<*>, value: R) — additionally for var properties

Alternatively, the class can implement the ReadOnlyProperty<T, R> or ReadWriteProperty<T, R> stdlib interfaces, which declare the same methods. The operator keyword is required.

Intermediate

I1 — How does by lazy achieve thread safety? What modes are available?
Medium▼
by lazy { } creates a SynchronizedLazyImpl by default. On first getValue call it checks if the value has been initialized (double-checked locking with @Volatile field). If not, it acquires a lock, checks again, runs the initializer, and caches the result. Subsequent calls return the cached value without locking.

Three modes:
• SYNCHRONIZED (default) — thread-safe, uses a lock
• PUBLICATION — multiple threads may initialize, but only first written is used; safe for concurrent access without a lock
• NONE — no synchronization; fastest, but only safe in single-threaded contexts
I2 — (Coding) Implement a custom property delegate that logs every get and set with Timber.
MediumCoding▼
class LoggingDelegate<T>(private var value: T) {
    operator fun getValue(ref: Any?, prop: KProperty<*>): T {
        Timber.d("GET ${prop.name} = $value")
        return value
    }
    operator fun setValue(ref: Any?, prop: KProperty<*>, newValue: T) {
        Timber.d("SET ${prop.name}: $value → $newValue")
        value = newValue
    }
}

// Usage:
var isLoading: Boolean by LoggingDelegate(false)
I3 — What does operator fun invoke() enable? Why is it used for use cases?
Medium▼
operator fun invoke() makes an object instance callable like a function — obj() calls obj.invoke(). For use cases in Clean Architecture: instead of useCase.execute(params), you write useCase(params) or even just val result = getUser(userId). This makes the call site read like a function call — the use case name IS the operation. Combined with suspend it integrates naturally with coroutines. This is the standard pattern in clean architecture Kotlin code.
I4 — Why is positional destructuring fragile? When is it safe to use?
Medium▼
Destructuring is positional — val (a, b, c) = obj calls component1(), component2(), component3(). If the data class changes — a field is inserted, removed, or reordered — the destructuring silently assigns the wrong values. No compile error.

Safe to use: (1) Map entry iteration: for ((key, value) in map) — Map.Entry has stable component1()/component2(); (2) Pair/Triple; (3) partition result: val (positives, negatives) = list.partition { it > 0 }; (4) When all fields are immediately needed and the class is stable/simple. Avoid for complex domain models with more than 3 fields.

Senior / Scenario

S1 — Design a property delegate that caches a value and invalidates the cache after a timeout (TTL).
HardCoding▼
class TtlDelegate<T>(
    private val ttlMs: Long,
    private val loader: () -> T
) {
    private var cachedValue: T? = null
    private var lastLoaded: Long = 0L

    operator fun getValue(ref: Any?, prop: KProperty<*>): T {
        val now = System.currentTimeMillis()
        if (cachedValue == null || now - lastLoaded > ttlMs) {
            cachedValue = loader()
            lastLoaded = now
        }
        return cachedValue!!
    }
}

// Usage: refresh config every 5 minutes
val remoteConfig: AppConfig by TtlDelegate(5 * 60 * 1000L) { api.fetchConfig() }
Note: for production use, this needs thread-safety (synchronize around cache check/set or use @Volatile + double-checked). Also a suspend version would be needed for async loaders in coroutines.
S2 — (Scenario) A junior dev wants to override equals() and hashCode() on a class to support a == b and if (a in list). They ask if they should use operator overloading instead. What's your answer?
HardScenario▼
No — use equals() + hashCode(), not operator overloading, for equality and membership.

a == b in Kotlin calls equals() — not an operator. The operator fun equals override is just the regular equals() with the operator keyword, which is required for structural equality. a in list calls list.contains(a) which also uses equals().

The right approach: use a data class — it auto-generates correct equals() and hashCode() from primary constructor properties. Only if you need non-default equality (e.g., case-insensitive comparison) should you manually override both. Operator overloading (plus, minus, etc.) is for arithmetic-style operations, not equality.
