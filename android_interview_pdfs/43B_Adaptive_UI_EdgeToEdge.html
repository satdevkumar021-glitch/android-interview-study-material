1. Overview & Why It Matters
🌟 In Plain Words

"With Android 15 making edge-to-edge mandatory, and with foldables + tablets having 20%+ of screen time, adaptive UI is no longer optional." Your app will be drawn behind the status bar and navigation bar whether you like it or not, and it will be opened in windows you never designed for: a 7.6" unfolded screen, a split-screen window, a ChromeOS desktop window, a tablet in landscape.

The Three Forces

ForceWhat changedWhat breaks if ignored
1. Edge-to-edge enforcementApps targeting API 35 running on Android 15 are drawn edge-to-edge by default. The system bars are transparent/translucent and your window extends behind them.Toolbars under the status bar, buttons under the gesture/3-button nav bar, input fields under the keyboard.
2. Foldable & large-screen guidelinesGoogle Play large-screen quality tiers, Android 16 ignoring orientation / resizability restrictions on large screens for apps targeting API 36, and a growing share of tablets, foldables and ChromeOS devices.Stretched phone UIs, letterboxing, a 10" screen showing one narrow column, poor Play store ranking on large-screen devices.
3. Predictive back gestureThe user can peek at the destination (home screen, previous activity, previous screen) while swiping back, before committing.Overridden onBackPressed() / key handling disables the animation; custom back logic feels broken next to system apps.
⚠ Be Precise About the Trigger

Enforcement is tied to targetSdkVersion = 35 and a device running Android 15+. An app targeting 34 on an Android 15 device is not forced edge-to-edge. The temporary opt-out attribute (android:windowOptOutEdgeToEdgeEnforcement) is deprecated and is not honoured once you target API 36. Saying "it's a trap on target-SDK bump day" is a good senior-level framing.

One Mental Model for All Three

Edge-to-edge, adaptive layouts and predictive back are all the same discipline: stop assuming the window is a fixed, fully-owned rectangle. The system tells you (1) how much of the window is obscured (insets), (2) how big the window is (window size class), (3) whether the window is folded (FoldingFeature), and (4) whether the user is mid-gesture (back progress). A good app reacts to those signals instead of hardcoding assumptions.

What Senior Interviewers Ask

"How do you make your app work on a foldable without duplicating layouts?"
1
One UI, many windows. Compose the screen from panes/slots; the window size class decides how many panes show at once. No layout-sw600dp-style duplication of logic.
2
State outside the layout. Selected item, scroll position and filters live in a ViewModel / saved state so folding, rotating or resizing doesn't reset them.
3
Fold-awareness only where it matters. Use WindowInfoTracker / FoldingFeature for tabletop and book postures, and let the adaptive scaffolds avoid the hinge.
4
Test across window sizes using the Resizable emulator, @PreviewScreenSizes, and UI tests with overridden window sizes.

2. Edge-to-Edge & WindowInsets

How It Works

Historically the decor view fit system windows: the framework padded your content so it never touched the status bar or nav bar. Edge-to-edge flips this: you tell the window not to fit system windows, your content draws under the bars, and you receive insets describing what is covered, then pad accordingly.

// Classic API (still valid, works on any AndroidX-supported API level)
override fun onCreate(savedInstanceState: Bundle?) {
    WindowCompat.setDecorFitsSystemWindows(window, false)
    super.onCreate(savedInstanceState)
    setContent { AppRoot() }
}

In practice prefer enableEdgeToEdge() from androidx.activity (1.8+). It calls the above, makes the bars transparent, picks icon colors from the theme (light/dark), and applies the correct 3-button-nav scrim. Call it before super.onCreate().

class MainActivity : ComponentActivity() {
    override fun onCreate(savedInstanceState: Bundle?) {
        enableEdgeToEdge(
            statusBarStyle = SystemBarStyle.auto(
                lightScrim = android.graphics.Color.TRANSPARENT,
                darkScrim  = android.graphics.Color.TRANSPARENT
            ),
            navigationBarStyle = SystemBarStyle.auto(
                lightScrim = android.graphics.Color.argb(0xE6, 0xFF, 0xFF, 0xFF),
                darkScrim  = android.graphics.Color.argb(0x80, 0x1B, 0x1B, 0x1B)
            )
        )
        super.onCreate(savedInstanceState)
        setContent { AppTheme { AppRoot() } }
    }
}

Handling Insets in Compose

Compose exposes insets as WindowInsets. Modifier.windowInsetsPadding(...) pads by the insets and marks them as consumed for descendants, which is what prevents double padding. consumeWindowInsets(paddingValues) tells children "this much has already been padded" without adding padding itself. That is the pattern needed when padding came from somewhere else (e.g. Scaffold's innerPadding).

// 1. Simple screen without Scaffold: pad by everything that could hide content
@Composable
fun SettingsScreen() {
    Column(
        Modifier
            .fillMaxSize()
            .windowInsetsPadding(WindowInsets.safeDrawing)
            .padding(16.dp)
    ) { /* content */ }
}

// 2. Scaffold + IME: consume what Scaffold already padded, then add the IME on top
@OptIn(ExperimentalMaterial3Api::class)
@Composable
fun ChatScreen(messages: List<Message>, onSend: (String) -> Unit) {
    Scaffold(
        topBar = { TopAppBar(title = { Text("Chat") }) }  // M3 bar pads for the status bar itself
    ) { innerPadding ->
        Column(
            Modifier
                .fillMaxSize()
                .padding(innerPadding)               // systemBars from Scaffold
                .consumeWindowInsets(innerPadding)   // tell children it's handled
                .imePadding()                        // only the part of the IME above the nav bar
        ) {
            LazyColumn(
                Modifier.weight(1f),
                contentPadding = PaddingValues(16.dp),
                reverseLayout = true
            ) { items(messages, key = { it.id }) { MessageRow(it) } }

            MessageInput(onSend)
        }
    }
}

// 3. Scrolling content that should scroll UNDER the bars but stop clear of them at rest
@Composable
fun FeedList(items: List<Post>) {
    LazyColumn(
        Modifier.fillMaxSize(),
        contentPadding = WindowInsets.safeDrawing.asPaddingValues()
    ) { items(items, key = { it.id }) { PostCard(it) } }
}

Handling Insets in Views

ViewCompat.setOnApplyWindowInsetsListener(binding.root) { view, insets ->
    val bars = insets.getInsets(
        WindowInsetsCompat.Type.systemBars() or WindowInsetsCompat.Type.displayCutout()
    )
    val ime = insets.getInsets(WindowInsetsCompat.Type.ime())
    view.updatePadding(
        left = bars.left, top = bars.top, right = bars.right,
        bottom = maxOf(bars.bottom, ime.bottom)   // IME already includes the nav bar height
    )
    WindowInsetsCompat.CONSUMED
}
📝 Manifest Detail

Keep android:windowSoftInputMode="adjustResize" on activities with text input. Mixing adjustPan with imePadding() makes the framework pan and your layout pad, so content jumps twice.

What Breaks If You Don't Handle Insets

  • Content hidden behind the keyboard — the focused text field is below the IME because nobody applied ime insets.
  • Content hidden behind the nav bar — a bottom button is untappable because the gesture/3-button bar sits on top of it.
  • Top bar under the status bar — title overlaps the clock/battery icons.
  • Landscape cutout overlap — text clipped by a notch because displayCutout was ignored.
  • Unreadable system icons — dark icons on a dark app bar because the bar style wasn't configured for your theme.

3. WindowSizeClass

The Breakpoints

A WindowSizeClass buckets the current window (not the physical screen) into coarse categories, independently for width and height. It updates when the window is resized: split-screen, fold/unfold, desktop windowing, rotation.

ClassWidthHeightTypical device
Compact< 600dp< 480dpPhone portrait / phone landscape (height)
Medium600dp – < 840dp480dp – < 900dpSmall tablet portrait, unfolded foldable portrait
Expanded≥ 840dp≥ 900dpTablet landscape, large unfolded foldable, desktop window
⚠ Newer Breakpoints

Recent Material 3 adaptive / WindowManager releases add Large (≥ 1200dp) and ExtraLarge (≥ 1600dp) width breakpoints for desktop-class windows. The three above are the core ones every interview expects. Width is what most layout decisions key off; height matters for landscape phones and tabletop mode.

Dependencies & API

// build.gradle.kts
implementation("androidx.compose.material3:material3-window-size-class")   // calculateWindowSizeClass(activity)
implementation("androidx.compose.material3.adaptive:adaptive")               // currentWindowAdaptiveInfo()
implementation("androidx.compose.material3.adaptive:adaptive-layout")        // ListDetail / SupportingPane scaffolds
implementation("androidx.compose.material3.adaptive:adaptive-navigation")    // pane navigators
implementation("androidx.window:window")                                       // WindowInfoTracker, FoldingFeature

calculateWindowSizeClass(activity) ships in material3-window-size-class; the adaptive library offers currentWindowAdaptiveInfo().windowSizeClass, which is the same idea and does not require an Activity reference (better for previews and tests).

Single-Pane vs Two-Pane + Adaptive Navigation

Rule of thumb: Compact → bottom navigation bar + single pane. Medium → navigation rail + single (or two) pane. Expanded → navigation rail (or drawer) + two panes.

enum class HomeDestination(val label: String, val icon: ImageVector) {
    Catalog("Catalog", Icons.Default.Storefront),
    Favorites("Favorites", Icons.Default.Favorite),
    Profile("Profile", Icons.Default.Person)
}

class MainActivity : ComponentActivity() {
    @OptIn(ExperimentalMaterial3WindowSizeClassApi::class)
    override fun onCreate(savedInstanceState: Bundle?) {
        enableEdgeToEdge()
        super.onCreate(savedInstanceState)
        setContent {
            AppTheme {
                val sizeClass = calculateWindowSizeClass(this)   // recomposes on resize / fold
                HomeScreen(widthClass = sizeClass.widthSizeClass)
            }
        }
    }
}

@Composable
fun HomeScreen(widthClass: WindowWidthSizeClass) {
    var selected by rememberSaveable { mutableStateOf(HomeDestination.Catalog) }
    val useRail = widthClass != WindowWidthSizeClass.Compact

    if (!useRail) {
        // COMPACT: bottom bar + single pane
        Scaffold(
            bottomBar = {
                NavigationBar {                         // pads for the nav bar inset itself
                    HomeDestination.entries.forEach { dest ->
                        NavigationBarItem(
                            selected = dest == selected,
                            onClick = { selected = dest },
                            icon = { Icon(dest.icon, contentDescription = null) },
                            label = { Text(dest.label) }
                        )
                    }
                }
            }
        ) { inner ->
            Box(Modifier.padding(inner).consumeWindowInsets(inner)) {
                DestinationContent(selected, twoPane = false)
            }
        }
    } else {
        // MEDIUM / EXPANDED: rail on the start edge, content fills the rest
        Row(Modifier.fillMaxSize()) {
            NavigationRail {                           // pads for status/nav/cutout inset itself
                Spacer(Modifier.weight(1f))
                HomeDestination.entries.forEach { dest ->
                    NavigationRailItem(
                        selected = dest == selected,
                        onClick = { selected = dest },
                        icon = { Icon(dest.icon, contentDescription = null) },
                        label = { Text(dest.label) }
                    )
                }
                Spacer(Modifier.weight(1f))
            }
            Box(
                Modifier
                    .weight(1f)
                    .fillMaxHeight()
                    .windowInsetsPadding(
                        WindowInsets.safeDrawing.only(WindowInsetsSides.End + WindowInsetsSides.Vertical)
                    )
            ) {
                DestinationContent(selected, twoPane = widthClass == WindowWidthSizeClass.Expanded)
            }
        }
    }
}

@Composable
fun DestinationContent(dest: HomeDestination, twoPane: Boolean) {
    when (dest) {
        HomeDestination.Catalog -> if (twoPane) CatalogTwoPane() else CatalogList()
        HomeDestination.Favorites -> FavoritesScreen()
        HomeDestination.Profile -> ProfileScreen()
    }
}

The Shortcut: NavigationSuiteScaffold

Material 3 adaptive ships a scaffold that makes exactly this switch for you (bottom bar, rail, or drawer based on window size / posture):

@Composable
fun HomeScreenSuite() {
    var selected by rememberSaveable { mutableStateOf(HomeDestination.Catalog) }
    NavigationSuiteScaffold(
        navigationSuiteItems = {
            HomeDestination.entries.forEach { dest ->
                item(
                    selected = dest == selected,
                    onClick = { selected = dest },
                    icon = { Icon(dest.icon, contentDescription = null) },
                    label = { Text(dest.label) }
                )
            }
        }
    ) { DestinationContent(selected, twoPane = false) }
}
✅ Key Rules
  • Branch on size class, not on "is tablet" or device model.
  • Hoist state (selected) above the branch so switching layouts on fold/rotate preserves it.
  • Don't read LocalConfiguration.current.screenWidthDp for layout decisions: it describes the configuration, not necessarily the current window in multi-window mode.

4. SupportingPaneScaffold & Foldables

The Scaffold Family

  • ThreePaneScaffold — the low-level building block: up to three panes (Primary, Secondary, Tertiary) with an adapt strategy for each (show, hide, reflow into a sheet / levitated).
  • ListDetailPaneScaffold — list + detail (+ optional extra) built on it.
  • SupportingPaneScaffold — one main pane plus a supporting pane (filters, related items, notes, a chat sidebar) and an optional extra pane.

These scaffolds come from androidx.compose.material3.adaptive and are the supported successor to the older Accompanist adaptive utilities (TwoPane, DisplayFeature helpers). They are fold-aware by default: the pane directive they derive from currentWindowAdaptiveInfo() avoids placing content across a hinge that separates the screen.

ScaffoldPanesUse when
ListDetailPaneScaffoldList · Detail · (Extra)Selecting an item changes what you're looking at (email, product, chat)
SupportingPaneScaffoldMain · Supporting · (Extra)Secondary content supports a primary task (document + comments, product + recommendations)
ThreePaneScaffoldCustom rolesYou need a custom arrangement or custom adapt strategies

Detecting the Hinge: WindowInfoTracker & FoldingFeature

WindowInfoTracker (Jetpack WindowManager) emits a WindowLayoutInfo flow containing a list of DisplayFeatures; the one you care about is FoldingFeature.

PropertyValuesMeaning
stateFLAT / HALF_OPENEDFully open vs. partially folded (laptop-like angle)
orientationHORIZONTAL / VERTICALDirection of the hinge line
isSeparatingBooleanWhether the fold splits the window into two logical areas
occlusionTypeNONE / FULLWhether the hinge hides pixels
boundsRectHinge rectangle in window coordinates

Postures

  • Tabletop = HALF_OPENED + HORIZONTAL hinge. Device is like a tiny laptop: put media / viewport on the top half, controls on the bottom half.
  • Book = HALF_OPENED + VERTICAL hinge. Device is like a book: two side-by-side pages — list on the left, detail on the right, never straddling the hinge.
  • Flat = FLAT: treat as a normal large (Medium/Expanded) window.

Product Catalog Adapted for Foldables

// ---- Posture model (the only fold-aware code in the app) ----
sealed interface FoldPosture {
    data object Flat : FoldPosture
    data class TableTop(val hingeTopPx: Int) : FoldPosture
    data class Book(val hingeLeftPx: Int) : FoldPosture
}

fun WindowLayoutInfo.toPosture(): FoldPosture {
    val fold = displayFeatures.filterIsInstance<FoldingFeature>().firstOrNull()
        ?: return FoldPosture.Flat
    return when {
        fold.state == FoldingFeature.State.HALF_OPENED &&
            fold.orientation == FoldingFeature.Orientation.HORIZONTAL -> FoldPosture.TableTop(fold.bounds.top)
        fold.state == FoldingFeature.State.HALF_OPENED &&
            fold.orientation == FoldingFeature.Orientation.VERTICAL -> FoldPosture.Book(fold.bounds.left)
        else -> FoldPosture.Flat
    }
}

// ---- Activity: observe the hinge via WindowInfoTracker ----
class CatalogActivity : ComponentActivity() {

    private val posture: StateFlow<FoldPosture> by lazy {
        WindowInfoTracker.getOrCreate(this)
            .windowLayoutInfo(this)
            .map { it.toPosture() }
            .stateIn(lifecycleScope, SharingStarted.WhileSubscribed(5_000), FoldPosture.Flat)
    }

    override fun onCreate(savedInstanceState: Bundle?) {
        enableEdgeToEdge()
        super.onCreate(savedInstanceState)
        setContent {
            AppTheme {
                val currentPosture by posture.collectAsStateWithLifecycle()
                ProductCatalogScreen(currentPosture)
            }
        }
    }
}

// ---- UI: one screen, three arrangements ----
@OptIn(ExperimentalMaterial3AdaptiveApi::class)
@Composable
fun ProductCatalogScreen(
    posture: FoldPosture,
    viewModel: CatalogViewModel = viewModel()
) {
    val state by viewModel.uiState.collectAsStateWithLifecycle()

    when (posture) {
        // Tabletop: product hero on the top half, controls on the bottom half
        is FoldPosture.TableTop -> Column(Modifier.fillMaxSize().safeDrawingPadding()) {
            ProductHero(state.selected, Modifier.weight(1f))
            ProductControls(state.selected, Modifier.weight(1f))
        }

        // Flat or Book: the scaffold picks 1 or 2 panes and avoids the hinge itself
        else -> {
            val navigator = rememberSupportingPaneScaffoldNavigator<Any>()
            SupportingPaneScaffold(
                directive = navigator.scaffoldDirective,   // derived from window size + posture
                value = navigator.scaffoldValue,
                mainPane = {
                    AnimatedPane {
                        ProductGrid(
                            products = state.products,
                            onSelect = viewModel::select
                        )
                    }
                },
                supportingPane = {
                    AnimatedPane {
                        FiltersAndRecommendations(
                            filters = state.filters,
                            recommended = state.recommended,
                            onFilterChange = viewModel::updateFilter
                        )
                    }
                }
            )
        }
    }
}
🌟 Senior Insight

Notice what is not in the code: no device checks, no if (isFoldable). The selected product, filters and recommendations live in the ViewModel; the composable only decides how to arrange them. On a plain phone the same scaffold collapses to a single pane.

Also available in the adaptive library: currentWindowAdaptiveInfo().windowPosture exposes isTabletop and the separating hinge bounds without handwriting the toPosture() mapping. Use window-testing's WindowLayoutInfoPublisherRule / TestWindowLayoutInfo to fake folds in tests.

5. Predictive Back Gesture

What It Is

With the back gesture, the user can drag from the screen edge and see an animated preview of the destination (the home screen, the previous activity, the previous screen) before they release. Releasing past the threshold commits; releasing before it cancels and the UI snaps back. This requires the system to know — before the gesture finishes — what back will do. That is why it needs an explicit opt-in and a callback-based model instead of "intercept onBackPressed() and decide at the last moment".

How to Opt In

<!-- AndroidManifest.xml: application-wide (or per-activity) -->
<application
    android:enableOnBackInvokedCallback="true"
    ... >
  • Android 13 (API 33): available behind a developer option; opt-in flag introduced.
  • Android 14–15: system animations (back-to-home, cross-activity, cross-task) for opted-in apps; in-app custom animations via the new callback APIs.
  • Targeting Android 16 (API 36): predictive back is enabled by default; you can still set the flag to false to opt out while you migrate.

The Callback Model

APIStatusNotes
Activity.onBackPressed() / KEYCODE_BACK handlingDeprecated; not called when predictive back is enabledOverriding it silently breaks the gesture and your custom logic
OnBackInvokedDispatcher (platform, API 33+)Platform APIregisterOnBackInvokedCallback(priority, callback); OnBackAnimationCallback on API 34+ receives start/progress/cancel/invoke
OnBackPressedCallback (androidx.activity)Supported; the recommended bridgeBacked by the platform dispatcher; in 1.8+ also has handleOnBackStarted/Progressed/Cancelled
Compose BackHandlerWorksIntercepts back; the system shows no animated preview while a handler is enabled because the app owns the outcome
Compose PredictiveBackHandlerSupported (activity-compose 1.8+)Gives you a Flow<BackEventCompat> of gesture progress for custom animations
⚠ Terminology Trap

It is the old patterns — overriding onBackPressed(), intercepting KEYCODE_BACK — that conflict with predictive back. OnBackPressedCallback itself is not deprecated; it is the AndroidX way to hook into OnBackInvokedDispatcher. The thing to avoid is an always-enabled callback that swallows back (disabling the system animation) when it has nothing meaningful to intercept. Enable callbacks only while you really have state to unwind.

Code

// ❌ Legacy — breaks predictive back (never invoked when the flag is on)
override fun onBackPressed() {
    if (viewModel.hasUnsavedChanges) showDiscardDialog() else super.onBackPressed()
}

// ✅ AndroidX: callback is enabled ONLY while there is something to intercept
class EditorActivity : ComponentActivity() {
    private val discardGuard = object : OnBackPressedCallback(false) {
        override fun handleOnBackPressed() { showDiscardDialog() }
    }

    override fun onCreate(savedInstanceState: Bundle?) {
        super.onCreate(savedInstanceState)
        onBackPressedDispatcher.addCallback(this, discardGuard)
        lifecycleScope.launch {
            repeatOnLifecycle(Lifecycle.State.STARTED) {
                viewModel.hasUnsavedChanges.collect { discardGuard.isEnabled = it }
            }
        }
    }
}

// ✅ Custom in-app animation with the platform API (API 34+)
if (Build.VERSION.SDK_INT >= 34) {
    onBackInvokedDispatcher.registerOnBackInvokedCallback(
        OnBackInvokedDispatcher.PRIORITY_DEFAULT,
        object : OnBackAnimationCallback {
            override fun onBackStarted(backEvent: BackEvent) { sheet.prepareDismiss() }
            override fun onBackProgressed(backEvent: BackEvent) { sheet.scaleTo(1f - 0.1f * backEvent.progress) }
            override fun onBackInvoked() { sheet.dismiss() }
            override fun onBackCancelled() { sheet.reset() }
        }
    )
}

// ✅ Compose: BackHandler = works, no preview. PredictiveBackHandler = progress + preview.
@Composable
fun DetailOverlay(onClose: () -> Unit) {
    var scale by remember { mutableFloatStateOf(1f) }

    PredictiveBackHandler(enabled = true) { progress: Flow<BackEventCompat> ->
        try {
            progress.collect { event -> scale = 1f - 0.1f * event.progress }
            onClose()                                    // gesture committed
        } catch (e: CancellationException) {
            scale = 1f                                   // gesture cancelled: snap back
        }
    }

    Box(Modifier.fillMaxSize().graphicsLayer { scaleX = scale; scaleY = scale }) { /* content */ }
}
🚫 Production Pitfall

Apps that override onBackPressed(), or register an always-enabled OnBackPressedCallback / BackHandler(true) at the root, break the system animation for the whole app — typically unnoticed until QA tests on Android 14+ with the developer option on. Audit every BackHandler: enabled must reflect real state (open drawer, unsaved edits, multi-select), not true.

Related Library Support

  • Navigation Compose 2.8+ animates destination transitions with the back gesture.
  • Fragment 1.7+ supports predictive back with Animator/AndroidX Transition (not legacy Animation resources).
  • Material Components provide back-aware behaviors for bottom sheets, side sheets, search bar and navigation drawer.
  • In multi-pane scaffolds, the adaptive navigator exposes canNavigateBack()/navigateBack(); hook them to back, so back means "close detail" on Compact but "leave screen" on Expanded.

6. Canonical Layouts

Google's canonical layouts are three proven starting points so you don't invent a bespoke layout for each screen:

LayoutStructureUse whenCompose building block
List-DetailList of items + detail of the selected oneBrowsing a collection and drilling in: email, messaging, products, settingsListDetailPaneScaffold
Supporting PaneMain content + related secondary contentA primary task with helpful context: document + comments, video + relatedSupportingPaneScaffold

List-Detail with Navigation

@OptIn(ExperimentalMaterial3AdaptiveApi::class)
@Composable
fun CatalogRoute(
    products: List<Product>,
    initialProductId: String?        // from a deep link like app://catalog/product/42
) {
    val scope = rememberCoroutineScope()

    // Selected id is the nav "content key": survives resize, fold and rotation
    val navigator = rememberListDetailPaneScaffoldNavigator<String>(
        initialDestinationHistory = listOfNotNull(
            ThreePaneScaffoldDestinationItem(ListDetailPaneScaffoldRole.List),
            initialProductId?.let { ThreePaneScaffoldDestinationItem(ListDetailPaneScaffoldRole.Detail, it) }
        )
    )

    // Back: close the detail pane first (Compact), only then leave the screen
    BackHandler(enabled = navigator.canNavigateBack()) {
        scope.launch { navigator.navigateBack() }
    }

    ListDetailPaneScaffold(
        directive = navigator.scaffoldDirective,
        value = navigator.scaffoldValue,
        listPane = {
            AnimatedPane {
                ProductList(products) { product ->
                    scope.launch {
                        navigator.navigateTo(ListDetailPaneScaffoldRole.Detail, product.id)
                    }
                }
            }
        },
        detailPane = {
            AnimatedPane {
                val id = navigator.currentDestination?.contentKey
                if (id != null) ProductDetail(id) else SelectProductPlaceholder()
            }
        }
    )
}
📝 Version Note

navigateTo/navigateBack are suspend functions in newer adaptive releases (hence the scope.launch); contentKey was previously named content. Newer releases also provide NavigableListDetailPaneScaffold / NavigableSupportingPaneScaffold, which wire up (predictive) back handling for you. Check the version in your project.

Feed Layout

@Composable
fun FeedGrid(posts: List<Post>, onOpen: (Post) -> Unit) {

    }

operator fun PaddingValues.plus(other: PaddingValues): PaddingValues {
    val dir = LayoutDirection.Ltr
    return PaddingValues(
        start = calculateStartPadding(dir) + other.calculateStartPadding(dir),
        top = calculateTopPadding() + other.calculateTopPadding(),
        end = calculateEndPadding(dir) + other.calculateEndPadding(dir),
        bottom = calculateBottomPadding() + other.calculateBottomPadding()
    )
}

Navigation in Multi-Pane: Deep Links & State

  • Selection is navigation state, not UI state. Store the selected id in the nav back stack / saved state / ViewModel. Panes are a presentation of it.
  • A deep link to "detail" must work in both shapes. Compact: show detail with back returning to the list. Expanded: show list and detail. Seed the navigator's history with [List, Detail(id)] as shown above.
  • Resize while in detail. Fold/unfold or split-screen resize must keep the selection. Compact→Expanded reveals the list beside the same detail; Expanded→Compact keeps the detail on top.
  • Back semantics change by size. On Compact, back closes detail → list. On Expanded, list and detail are both visible so back leaves the screen.
  • Don't restart the Activity on size changes. Declare screenSize|smallestScreenSize|screenLayout|orientation in configChanges only if you actually handle them in Compose; otherwise keep default recreation but preserve state.

How to Test

  • Android Studio Resizable emulator — one AVD that switches between Phone, Unfolded foldable, Tablet and Desktop at runtime. Fastest way to see size-class transitions.
  • Layout Inspector — inspect the composition/view hierarchy at each size to see what padding/insets were actually applied and which panes are present.
  • @PreviewScreenSizes and @Preview(device = "spec:width=1280dp,height=800dp,dpi=240") for quick Compose preview coverage.
  • Automated tests — Compose UI tests with explicit window sizes; androidx.window:window-testing to publish fake FoldingFeatures; Firebase Test Lab for tablet / foldable devices.

7. Pitfalls & Production Bugs

1. Hardcoding dp widths instead of using WindowSizeClass

A 360.dp-wide card or if (screenWidthDp > 600) scattered through UI code works on the test phone and fails in split-screen, on foldables (inner and outer displays differ) and in ChromeOS windows.

// ❌ Magic numbers, tied to configuration, not to the actual window
val isTablet = LocalConfiguration.current.screenWidthDp > 600
Box(Modifier.width(360.dp)) { Details() }

// ✅ Window-driven, with a max width so content never stretches absurdly
val widthClass = currentWindowAdaptiveInfo().windowSizeClass.windowWidthSizeClass
Box(Modifier.widthIn(max = 640.dp).fillMaxWidth()) { Details(twoColumn = widthClass == WindowWidthSizeClass.EXPANDED) }

2. Not handling IME insets

Symptom: user taps a field, keyboard opens, the field and the Send button are hidden. Fix: imePadding() (after consuming Scaffold padding), adjustResize, and make sure scrollable forms use verticalScroll/LazyColumn. Use WindowInsets.isImeVisible to react.

3. Wrong window-info API

Use WindowInfoTracker for fold state and hinge bounds; WindowMetricsCalculator / currentWindowAdaptiveInfo() for window size. Do not use Display.getSize(), getRealMetrics() or Resources.displayMetrics for layout: they describe the display, not the window, and many are deprecated. Also remember WindowMetricsCalculator is a one-shot measurement, not a fold source; it won't tell you the posture.

4. OnBackPressedCallback / onBackPressed conflicts with predictive back

Overridden onBackPressed() never fires with the flag on; always-enabled callbacks disable system animations. Move to scoped, state-driven callbacks (see section 5).

5. Navigation bar color doesn't match on edge-to-edge

With 3-button navigation the system draws a translucent scrim; on gesture navigation it's transparent. Mismatch usually shows as a solid white/black strip under a dark/light app, or low-contrast icons. Use enableEdgeToEdge() with a matching SystemBarStyle, draw your own background under the bar (don't pad it away), and if the scrim looks wrong for your design set window.isNavigationBarContrastEnforced = false (only when your background guarantees contrast).

6. Testing only on phones

Layout works on a Pixel, ships, then crashes or looks broken on a tablet: stretched buttons, lists centered with huge gaps, dialogs wider than the screen, portrait-locked activity letterboxed. Add tablet/foldable/desktop AVDs to CI and to the manual release checklist.

The 30-Second Answer

"Edge-to-edge is mandatory from API 35 — handle WindowInsets. For adaptive layouts, use WindowSizeClass: Compact=single pane, Expanded=two panes. For foldables, detect FoldingFeature with WindowInfoTracker."

The 2-Minute Expansion

1
Edge-to-edge: enableEdgeToEdge() before super.onCreate; use safeDrawing / Scaffold padding / imePadding(); consume insets once to avoid double padding.

9. Flash Cards

Read the question, answer out loud, then check the card.

1 · Edge-to-edge mandatory from?

Apps targeting API 35 on Android 15+. Opt-out attribute is temporary/deprecated. Use enableEdgeToEdge() and handle insets.

2 · safeDrawing vs safeContent vs navigationBars?

navigationBars = nav bar only. safeDrawing = systemBars + ime + displayCutout (nothing visible is hidden). safeContent = safeDrawing + safeGestures (also avoids gesture-conflict zones).

3 · WindowSizeClass breakpoints?

Width: Compact <600, Medium 600–839, Expanded ≥840dp. Height: Compact <480, Medium 480–899, Expanded ≥900dp.

4 · SupportingPaneScaffold vs ListDetailPaneScaffold?

ListDetail: selecting a list item changes the detail. SupportingPane: a main pane plus supporting content (filters, related, comments). Both build on ThreePaneScaffold.

5 · Predictive back opt-in flag?

android:enableOnBackInvokedCallback="true" on <application> or <activity>. Default-on when targeting API 36.

6 · FoldingFeature states?

FLAT and HALF_OPENED; orientation HORIZONTAL (tabletop) or VERTICAL (book). Also isSeparating and occlusionType.

7 · The canonical layouts?

List-Detail, Supporting Pane, Feed.

8 · How do you handle IME insets?

Modifier.imePadding() after consumeWindowInsets(scaffoldPadding); keep adjustResize; not adjustPan.

9 · OnBackInvokedDispatcher?

Platform (API 33+) back dispatcher. registerOnBackInvokedCallback(priority, cb); OnBackAnimationCallback (API 34+) gives progress events. AndroidX OnBackPressedCallback sits on top of it.

10 · How to test adaptive UI?

Resizable emulator (phone / foldable / tablet / desktop), @PreviewScreenSizes, Layout Inspector, window-testing fake folds, Firebase Test Lab.

10. Interview Questions
Q1. Your team bumps targetSdk to 35. What changes about the UI and what do you do?
Easy ⌄

On Android 15+, apps targeting API 35 are laid out edge-to-edge: the window extends behind the transparent status bar and the (gesture or translucent 3-button) navigation bar. Content that used to be auto-padded is now overlapped.

Plan:

  • Call enableEdgeToEdge() in every activity (before super.onCreate) with proper SystemBarStyle.
  • Audit top bars, bottom bars, FABs, dialogs and bottom sheets for insets. Use Scaffold inner padding, safeDrawing, imePadding().
  • Check landscape for displayCutout.
  • Don't rely on windowOptOutEdgeToEdgeEnforcement: it's a temporary escape hatch that stops working when you target API 36.
Q2. Name the WindowSizeClass width breakpoints and what you'd change in navigation at each.
Easy ⌄

Compact (<600dp): bottom NavigationBar, single pane. Medium (600–839dp): NavigationRail, usually still single pane, optionally two. Expanded (≥840dp): rail (or permanent drawer on very wide windows), list + detail side by side.

Height has its own breakpoints (480dp / 900dp) and matters mainly for landscape phones and tabletop mode. The size class belongs to the window, so split-screen on a tablet can yield Compact. NavigationSuiteScaffold automates this switch.

Q3. How do you detect that a foldable is in tabletop posture, and what would you do with that information?
Medium ⌄

Collect WindowInfoTracker.getOrCreate(activity).windowLayoutInfo(activity), find the FoldingFeature in displayFeatures, and check state == HALF_OPENED && orientation == HORIZONTAL. (Book posture is the same with VERTICAL.)

val fold = info.displayFeatures.filterIsInstance<FoldingFeature>().firstOrNull()
val isTabletop = fold?.state == FoldingFeature.State.HALF_OPENED &&
                  fold.orientation == FoldingFeature.Orientation.HORIZONTAL

In tabletop, put the viewport (video, camera preview, product 3D view) on the top half and controls on the bottom half, aligned to fold.bounds.top. Keep the collection lifecycle-aware (collectAsStateWithLifecycle) and keep state in the ViewModel.

Q4. An app overrides onBackPressed() everywhere. How do you migrate to predictive back?
Medium ⌄
  1. Inventory every onBackPressed() override, KEYCODE_BACK handler, and root-level BackHandler.
  2. Replace with OnBackPressedCallback (or BackHandler in Compose) whose isEnabled mirrors actual state — dialog open, unsaved edits, drawer open.
  3. Where the in-app UI should animate with the gesture (bottom sheet, search, drawer), use PredictiveBackHandler / handleOnBackProgressed or Material components that support it.
  4. Upgrade Navigation (2.8+) and Fragment (1.7+) so screen transitions follow the gesture.
  5. Set android:enableOnBackInvokedCallback="true" and test with the "Predictive back animations" developer option on Android 14/15.

Tip: do the migration before targeting API 36, where the behaviour is on by default.

Q5. Spot the bug: on a phone, tapping the message field hides the field and the Send button behind the keyboard.
Hard ⌄ 
@Composable
fun ChatScreen(messages: List<Message>, onSend: (String) -> Unit) {
    Scaffold { _ ->
        Column(Modifier.fillMaxSize()) {
            LazyColumn(Modifier.weight(1f)) { items(messages) { MessageRow(it) } }
            MessageInput(onSend)
        }
    }
}

Bugs:

  • The Scaffold innerPadding is discarded (_), so the input sits under the navigation bar, and the top bar inset is ignored.
  • There is no imePadding(), so nothing lifts the input above the keyboard. With edge-to-edge the window no longer resizes the content for you.
  • (Also check the manifest isn't using adjustPan.)

Fix:

Scaffold { inner ->
    Column(
        Modifier
            .fillMaxSize()
            .padding(inner)
            .consumeWindowInsets(inner)
            .imePadding()
    ) {
        LazyColumn(Modifier.weight(1f)) { items(messages, key = { it.id }) { MessageRow(it) } }
        MessageInput(onSend)
    }
}

consumeWindowInsets(inner) prevents the nav bar height from being added twice (once from the Scaffold, once inside the IME inset).

Q6. Design the navigation for a shopping app that must work on phones, foldables and tablets. What do you build?
Medium ⌄

One navigation graph, one set of screens, with a presentation layer that adapts:

  • Top-level destinations in NavigationSuiteScaffold (bottom bar → rail by window size).
  • Catalog uses ListDetailPaneScaffold; the selected product id is nav state, so deep links work and the selection survives fold/rotate.
  • Product detail uses SupportingPaneScaffold (reviews / recommendations as supporting pane).
  • Home feed uses LazyVerticalGrid(GridCells.Adaptive(...)).
  • Fold-specific tweaks (tabletop media viewer) isolated behind a posture model from WindowInfoTracker.
  • Back: closes detail first on Compact; predictive back opted in.
Q7. When would you choose each canonical layout: List-Detail, Supporting Pane, Feed?
Medium ⌄
  • List-Detail: the user picks an item from a collection and the rest of the screen shows that item — email, chat, orders, settings. Selection drives content.
  • Supporting Pane: there's one primary task and the secondary content aids it — document + comments, video + related videos, product + recommendations. The supporting pane is optional context.
  • Feed: many equal-weight cards the user browses and scans — news, social, discovery, home screens. Use adaptive grid columns, not panes.

Test: "If I remove the right pane, can the user still do the task?" Yes → Supporting Pane. No (they can't see the item) → List-Detail.

Q8. How do you test that an adaptive UI actually works before you ship?
Hard ⌄
  • Manual: Android Studio Resizable emulator (phone / unfolded / tablet / desktop), plus split-screen and window resizing. Use Layout Inspector to inspect the actual composition and padding at each size.
  • Previews: @PreviewScreenSizes and custom @Preview(device=…) specs for Compact/Medium/Expanded and landscape.
  • Automated: Compose UI tests parameterised by window size; androidx.window:window-testing (WindowLayoutInfoPublisherRule, TestWindowLayoutInfo) to fake FoldingFeature states; screenshot tests per size class.
  • Behavioural: rotate/fold/resize mid-flow to verify selection, scroll position and text input are preserved; IME open at each size; back gesture on Compact vs Expanded.
  • Device farm: Firebase Test Lab with tablets and foldables; check Play Console's large-screen quality reports.
