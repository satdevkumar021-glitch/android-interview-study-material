23A — Gradle / Build System

Gradle lifecycle, Android Gradle Plugin, build types, product flavors, version catalogs, KAPT vs KSP, and build performance — everything a senior Android engineer must know about the build system.

1. Overview

What this unit covers

  • Gradle lifecycle: initialization → configuration → execution phases
  • Android Gradle Plugin (AGP): what it adds on top of Gradle
  • Build files: build.gradle.kts, settings.gradle.kts, libs.versions.toml
  • Build types & product flavors: debug/release, free/paid, variants
  • Annotation processing: KAPT vs KSP
  • Build performance: build cache, incremental builds, common tasks
Senior Mental Model
Gradle is a programmatic build system, not declarative like Make. Every build.gradle.kts is Kotlin code executed at configuration time. Understanding the three phases (init → config → exec) is essential for writing correct, fast build scripts and debugging mysterious build failures.

2. Gradle Lifecycle

Three Phases

PhaseWhat happensWhen it runs
InitializationGradle reads settings.gradle.kts; discovers which projects existEvery build
ConfigurationAll build.gradle.kts scripts execute top-to-bottom; task graph builtEvery build (even ./gradlew help)
ExecutionOnly the requested tasks run in dependency orderOnly needed tasks
Common Mistake
Code at the top level of build.gradle.kts runs at configuration time — even if you never run that task. Heavy I/O or network calls in configuration scripts slow every single Gradle invocation. Always put work inside task actions.

3. AGP & Build Files

Android Gradle Plugin (AGP)

AGP is a Gradle plugin (applied as com.android.application or com.android.library) that adds Android-specific tasks: resource merging, manifest merging, DEX compilation, signing, and more. It wraps D8 (dexer) and R8 (shrinker/minifier).

// build.gradle.kts (app module)
plugins {
    alias(libs.plugins.android.application)
    alias(libs.plugins.kotlin.android)
    alias(libs.plugins.hilt)
    alias(libs.plugins.ksp)
}
android {
    namespace = "com.example.myapp"
    compileSdk = 35
    defaultConfig {
        applicationId = "com.example.myapp"
        minSdk = 26; targetSdk = 35
        versionCode = 1; versionName = "1.0.0"
    }
}

4. Build Variants & Signing

Build Types

buildTypes {
    debug {
        applicationIdSuffix = ".debug"
        isDebuggable = true
        isMinifyEnabled = false
    }
    release {
        isMinifyEnabled = true       // enables R8 shrinking + obfuscation
        isShrinkResources = true
        proguardFiles(
            getDefaultProguardFile("proguard-android-optimize.txt"),
            "proguard-rules.pro"
        )
        signingConfig = signingConfigs.getByName("release")
    }
}

Product Flavors

flavorDimensions += "env"
productFlavors {
    create("dev") {
        dimension = "env"
        applicationIdSuffix = ".dev"
        buildConfigField("String", "BASE_URL", "\"https://dev.api.example.com\"")
    }
    create("prod") {
        dimension = "env"
        buildConfigField("String", "BASE_URL", "\"https://api.example.com\"")
    }
}
// Variants: devDebug, devRelease, prodDebug, prodRelease

Signing Configuration

signingConfigs {
    create("release") {
        // Read from environment variables or local.properties (NEVER commit keystore)
        storeFile = file(System.getenv("KEYSTORE_PATH") ?: "keystore/debug.jks")
        storePassword = System.getenv("STORE_PASSWORD")
        keyAlias = System.getenv("KEY_ALIAS")
        keyPassword = System.getenv("KEY_PASSWORD")
    }
}
Security Warning
Never commit your .jks keystore or plaintext passwords to version control. Use environment variables (for CI) or local.properties (gitignored) for local development.

KAPT vs KSP

FeatureKAPTKSP
SpeedSlow — converts Kotlin to Java stubs first~2× faster — processes Kotlin symbols directly
Language awareJava-centric (annotation processing API)Kotlin-native, understands suspend, sealed, etc.
IncrementalLimited incremental supportFull incremental processing
SupportDeprecated in AGP 8+Recommended going forward
UsersHilt (old), Room (old), MoshiHilt, Room, Retrofit KSP, Moshi KSP
// build.gradle.kts — switching from KAPT to KSP
plugins {
    id("com.google.devtools.ksp") version "2.0.0-1.0.21"
}
dependencies {
    // KAPT (old):
    // kapt(libs.hilt.compiler)
    // kapt(libs.room.compiler)

    // KSP (new):
    ksp(libs.hilt.compiler)
    ksp(libs.room.compiler)
}

Build Cache

# gradle.properties — enable build cache
org.gradle.caching=true
org.gradle.parallel=true
org.gradle.configureondemand=true
org.gradle.jvmargs=-Xmx4g -XX:+UseG1GC

# Local build cache: ~/.gradle/caches/build-cache/
# Remote build cache: configure in settings.gradle.kts
buildCache {
    remote(HttpBuildCache::class) {
        url = uri("https://your-build-cache-server/")
        isPush = System.getenv("CI") != null   // only push from CI
    }
}

Incremental Builds

Gradle tracks task inputs and outputs. If inputs haven't changed since last run, tasks are UP-TO-DATE and skipped. KSP supports incremental annotation processing — only re-processes files that changed.

Performance Tips
Use ./gradlew assembleDebug --scan to get a build scan URL showing which tasks are slow. Common culprits: KAPT on large projects, full recompilation due to ABI changes, and disabled build cache.

6. Pitfalls & Best Practices

Common Pitfalls

  • Slow configuration: network/file I/O at top level of build script — wrap in task actions
  • api vs implementation: using api() leaks transitive dependencies to consumers, increasing compilation scope. Use implementation() by default.
  • Not using Version Catalog: version duplication across modules causes drift. Adopt libs.versions.toml.
  • Committed keystore or passwords: security risk. Use environment variables or Gradle secrets plugins.
  • KAPT in new projects: adds ~30–60 sec to large project builds. Migrate to KSP.
  • Missing proguard rules: R8 may strip classes used via reflection (Retrofit, Gson, Moshi). Add keep rules.

Best Practices

Use libs.versions.tomlSingle source of truth for all versions
Prefer KSP over KAPT2× faster, incremental, Kotlin-native
Enable build cache + parallelDramatically reduces CI build time
Use implementation not apiReduces recompilation scope across modules
Put signing creds in env varsSecurity — never commit credentials
Profile with --scanIdentify slow tasks before optimizing

30-Second Answer

"Gradle has three phases: initialization reads settings.gradle, configuration executes all build scripts and builds the task graph, execution runs only the requested tasks. AGP adds Android-specific tasks on top. For performance I use KSP instead of KAPT — roughly 2× faster — along with build cache and parallel execution enabled in gradle.properties. Dependencies are centralized in libs.versions.toml."

2-Minute Answer

"The Gradle lifecycle is init → config → execute. A critical detail is that configuration runs on every Gradle invocation, so heavy work in build scripts always hurts. AGP wraps D8 and R8: D8 converts bytecode to DEX, R8 shrinks and obfuscates for release builds. I structure build variants with build types (debug/release) and product flavors (dev/staging/prod), giving me a matrix of variants. For annotation processing, KSP is the modern choice — it processes Kotlin symbols directly without the Java stub generation step KAPT requires. For large multi-module projects, enabling org.gradle.caching=true and parallel=true in gradle.properties can cut CI build time by 40–60% when combined with a remote build cache. Signing credentials never go in the repository; they come from environment variables in CI and local.properties locally."

9. Interview Questions
1. What are the three phases of Gradle's build lifecycle?
Basic⌄
Initialization (reads settings.gradle, discovers projects), Configuration (executes all build scripts, builds the task graph — runs every time), Execution (runs only the requested tasks in dependency order). Key point: configuration always runs, so heavy work there slows every Gradle invocation.
2. What is a build variant and how is it formed?
Basic⌄
A build variant is the cross-product of a product flavor and a build type. If you have flavors [dev, prod] and types [debug, release], you get four variants: devDebug, devRelease, prodDebug, prodRelease. Each variant can have its own source set, resources, and BuildConfig values.
3. What is the Version Catalog (libs.versions.toml) and why use it?
Basic⌄
A TOML file in the gradle/ directory that centralizes all dependency versions, library coordinates, and plugin IDs. Modules reference them as libs.hilt.android or libs.plugins.ksp. Benefits: single source of truth for versions, no drift across modules, IDE auto-complete, and bundle grouping.
4. What is the difference between KAPT and KSP?
Intermediate⌄
KAPT (Kotlin Annotation Processing Tool) converts Kotlin source to Java stubs before running Java annotation processors — this stub generation adds significant overhead. KSP (Kotlin Symbol Processing) processes Kotlin symbols directly, making it ~2× faster, fully incremental, and Kotlin-aware (understands suspend functions, sealed classes, etc.). KAPT is deprecated in AGP 8+. Migrate Room and Hilt to KSP.
5. What does R8 do and when does it run?
Intermediate⌄
R8 is Google's code shrinker/obfuscator. It runs in a single pass doing tree-shaking (removes unused classes/methods), obfuscation (renames symbols to short names), and bytecode optimization. It only runs when isMinifyEnabled = true, typically for release builds. D8 converts bytecode to DEX; R8 is an enhanced D8 that also shrinks.
6. What is the difference between api() and implementation() in Gradle dependencies?
Intermediate⌄
api() exposes the dependency on the compile classpath of consumers — it leaks transitively. implementation() hides it from consumers — they can't see or reference that dependency. In modules: use implementation by default to minimize recompilation scope. Use api only when the dependency is part of your module's public API surface (e.g., a library module returning types from that dependency).
7. How do you handle release signing securely in CI?
Intermediate⌄
Store the keystore as a base64-encoded secret in CI (e.g. GitHub Secrets). In the CI pipeline, decode it to a file, then pass keystore path, alias, and passwords as environment variables. In build.gradle.kts, read them via System.getenv(). Never commit the .jks file or plain-text credentials. Alternatively, use the Gradle Secrets Plugin which reads from local.properties (gitignored) for local dev.
8. Your CI build takes 12 minutes. How do you diagnose and fix it?
Senior⌄
1) Run ./gradlew assembleDebug --scan to get a build scan — shows per-task timings. 2) Check if build cache is enabled (org.gradle.caching=true) and whether tasks are UP-TO-DATE or FROM-CACHE. 3) Identify KAPT tasks — evaluate KSP for supported processors and measure the result. 4) Enable parallel execution (org.gradle.parallel=true). 5) Set up a remote build cache server so CI agents share cached task outputs. 6) Use configuration cache when the project’s Gradle version and plugins support it to skip configuration phase on unchanged builds. Measure the impact on your own project; no fixed speedup is guaranteed.
9. Why does configuration time matter even when you're not building?
Senior⌄
Configuration runs on every Gradle invocation — for task graph calculation unless a compatible configuration-cache entry is reused. IDE sync is separate and does not use the configuration cache. If build scripts do file I/O, network calls, or expensive computation at the top level (outside task actions), they slow every developer interaction. This is why lazy task configuration (tasks.register instead of tasks.create) and configuration cache exist. The configuration cache serializes the task graph and skips re-configuration when inputs are unchanged.
10. How does the Gradle build cache differ from UP-TO-DATE checks?
Scenario⌄
UP-TO-DATE: task skipped because its inputs/outputs haven't changed on the same machine since last run — it checks the local output directory. Build cache: task outputs stored by a hash of the inputs — can be reused across machines (remote cache) or after a clean. After ./gradlew clean, UP-TO-DATE won't help, but the build cache will still restore outputs FROM-CACHE. Remote build cache is essential for CI where workspaces are fresh each run.
10. Practical Lab: Diagnose a Slow Build

Goal: explain a build failure or performance change with measurements, not assumed speedups. Use a sample Android project and record its Gradle, AGP, Kotlin and JDK versions before changing anything.

1. Reproduce with the project's wrapper

./gradlew --version
./gradlew :app:assembleDebug --profile
./gradlew :app:assembleDebug --profile
./gradlew :app:dependencyInsight --dependency kotlinx-coroutines --configuration debugRuntimeClasspath

Compare first and warm builds in the same environment. Record configuration time, slow tasks, and UP-TO-DATE or FROM-CACHE outcomes. The local profile report is under build/reports/profile. A Build Scan can provide more detail but publishes build information to a service; review what your organization permits before using --scan.

2. Compare the caches correctly

MechanismWhat it reusesWhat to inspect
UP-TO-DATEExisting task outputs in this workspaceDid task inputs or outputs change?
Build cacheCacheable task outputsAre inputs declared correctly and outputs reusable?
Configuration cacheConfigured task graphAre plugins and build logic compatible? Why was the entry invalidated?
./gradlew :app:assembleDebug --configuration-cache
./gradlew :app:assembleDebug --configuration-cache

Read any compatibility report and fix the cause before enabling this permanently. Configuration cache does not accelerate IDE sync. Avoid measuring every run after clean, which removes workspace outputs and changes the comparison.

3. Reproducibility and dependency trust

Commit the wrapper and reviewed dependency versions. Check the AGP/Gradle/JDK compatibility matrix rather than upgrading each independently. A version catalog centralizes declarations; dependency locking and dependency verification solve different problems. A wrapper distribution checksum protects the downloaded distribution; verification metadata checks dependency artifacts. Review generated checksums against trusted upstream information before committing them.

Practice and interview checkpoint

  1. Capture two baseline timings and make one change.
  2. Compare timings and correctness; do not promise a universal percentage improvement.
  3. Explain why a cache miss happened and how you would detect it in CI.
  4. Describe how you would investigate a dependency-version conflict with dependencyInsight.
