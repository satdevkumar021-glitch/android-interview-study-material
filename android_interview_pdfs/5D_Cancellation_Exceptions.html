5D — Cancellation & Exceptions

Cooperative cancellation, CancellationException, isActive/ensureActive/yield, NonCancellable, exception propagation, CoroutineExceptionHandler, SupervisorJob — everything about keeping coroutines safe.

ID: 5D ⭐ Tier 1
🔍
1. Overview

Cooperative cancellation

Coroutines can only be cancelled at suspension points. Code between suspension points runs to completion — you cannot interrupt a tight CPU loop from outside. The coroutine must actively check for cancellation.

  • isActive — check in tight loops: while (isActive) { ... }
  • ensureActive() — throws CancellationException if not active; use at loop top
  • yield() — checks cancellation AND yields control to other coroutines (fairness)
  • delay() — any suspension point, checks cancellation automatically

CancellationException is special

CancellationException is a subclass of IllegalStateException but is treated specially — it is not a failure from the structured concurrency perspective. It propagates downward only and does NOT cancel the parent. Catch it carefully.

⚙
2. How It Works

Cancellation check mechanisms

// 1. isActive — manual check, no exception thrown
while (isActive) {
    processItem(queue.poll())
}

// 2. ensureActive() — throws CancellationException if cancelled
for (item in items) {
    ensureActive()           // check at top of loop
    processItem(item)
}

// 3. yield() — checks + gives up thread for other coroutines
for (item in items) {
    yield()                   // check + fairness
    processItem(item)
}

// 4. Any suspend function (delay, withContext) checks automatically
for (item in items) {
    delay(0)                  // zero-delay still checks cancellation
    processItem(item)
}

NonCancellable — for cleanup work

// Problem: finally blocks run in cancelled coroutine context
// Suspend calls in finally fail with CancellationException
try {
    doWork()
} finally {
    // This throws if coroutine is cancelled:
    delay(100)            // ❌ CancellationException thrown
    db.closeConnection()  // ❌ Never reached
}

// Fix: withContext(NonCancellable) for cleanup
try {
    doWork()
} finally {
    withContext(NonCancellable) {
        delay(100)           // ✅ runs even if cancelled
        db.closeConnection() // ✅ cleanup completes
    }
}

CoroutineExceptionHandler

val handler = CoroutineExceptionHandler { context, exception ->
    Timber.e(exception, "Unhandled in ${context[CoroutineName]}")
    // Log to Crashlytics, show error UI, etc.
}

// Handler must be on the ROOT coroutine (not a child)
val scope = CoroutineScope(SupervisorJob() + Dispatchers.Main + handler)
scope.launch {              // root — handler fires here
    launch {               // child — handler does NOT fire here
        throw IOException()  // propagates to root launch
    }
}

// ⚠️ Handler does NOT catch exceptions from async { }.await()
// Those must be caught with try/catch around await()

Exception propagation rules

ScenarioBehaviour
launch throws, regular Job parentException propagates to parent → cancels all siblings → crashes scope
launch throws, SupervisorJob parentException goes to CoroutineExceptionHandler → siblings unaffected
async throws, not awaitedException stored in Deferred — nothing happens yet
async throws, .await() calledException re-thrown at await() site — catch it there
CancellationException thrownNever treated as failure — scope NOT cancelled

4. Production Example

E-commerce: resilient order processing

class OrderProcessor(
    private val ioDispatcher: CoroutineDispatcher = Dispatchers.IO
) {
    private val exceptionHandler = CoroutineExceptionHandler { _, e ->
        if (e is CancellationException) return@CoroutineExceptionHandler
        Crashlytics.log(e)
        alertOpsTeam(e)
    }

    private val scope = CoroutineScope(
        SupervisorJob() + ioDispatcher + exceptionHandler
    )

    fun processOrders(orders: List<Order>) {
        scope.launch {
            for (order in orders) {
                ensureActive()  // check before each order
                try {
                    processOrder(order)
                } catch (e: OrderException) {
                    markFailed(order, e)   // one failure → next order
                }
            }
        }
    }

    private suspend fun processOrder(order: Order) {
        try {
            withContext(ioDispatcher) {
                paymentService.charge(order)
                inventoryService.reserve(order)
            }
        } finally {
            // Cleanup runs even if this coroutine is cancelled
            withContext(NonCancellable) {
                auditLog.record(order)    // audit must complete
            }
        }
    }

    fun cancel() = scope.cancel()
}

try/catch and CancellationException — critical rule

// ❌ WRONG: catching Exception swallows CancellationException
try {
    longRunningOp()
} catch (e: Exception) {
    log(e)  // CancellationException caught and dropped!
    // Coroutine continues running after cancel() — LEAK
}

// ✅ CORRECT: re-throw CancellationException
try {
    longRunningOp()
} catch (e: CancellationException) {
    throw e   // always re-throw
} catch (e: Exception) {
    handleError(e)
}

runCatching Gotcha
runCatching { suspendFn() } catches ALL exceptions including CancellationException. This is dangerous: the coroutine appears to have been cancelled but the exception is trapped in a Result.Failure. Always check: result.exceptionOrNull()?.let { if (it is CancellationException) throw it }

6. Pitfalls & Best Practices
Pitfall 1 — Tight loop without cancellation check
A CPU-intensive loop with no suspension points is not cancellable. Even if you call job.cancel(), the coroutine keeps running until the loop finishes. Fix: add ensureActive() or yield() inside the loop.
Pitfall 2 — Catching CancellationException
Catching Exception or Throwable and not re-throwing will swallow CancellationException, breaking cooperative cancellation — the coroutine continues running after cancel() is called.
Pitfall 3 — Using CoroutineExceptionHandler on child coroutines
CoroutineExceptionHandler only fires on root coroutines (those whose parent is a Job without a coroutine parent, e.g. scope.launch). Adding it to a child launch { } has no effect — exceptions still propagate to the parent.
Best Practice — Always use NonCancellable for critical cleanup
Any suspend call in a finally block needs withContext(NonCancellable) { }. This includes: closing network connections, committing database transactions, writing audit logs, sending analytics events.

7. Interview Framework

30-second answer

"Coroutine cancellation is cooperative — it only happens at suspension points. The coroutine receives a CancellationException which must be propagated, not swallowed. For non-cancellable cleanup like closing connections, wrap suspend calls in withContext(NonCancellable) inside finally blocks. For unhandled exceptions from root coroutines, use CoroutineExceptionHandler."

2-minute answer

"Cancellation works by marking the Job as cancelling and throwing CancellationException at the next suspension point. This means a tight CPU loop without suspension is not cancellable — you need to add ensureActive() or yield() checks. CancellationException is special: it's not treated as a failure by the parent Job, so cancellation is a clean lifecycle event, not an error.

The most dangerous mistake is catching Exception and not re-throwing CancellationException — this breaks cancellation entirely, causing coroutine leaks.

For cleanup after cancellation, wrap suspend calls in withContext(NonCancellable) — this creates a context that ignores cancellation, allowing your cleanup to complete. For application-level error handling, put a CoroutineExceptionHandler on your root scope — not on child coroutines, where it has no effect."

Follow-up Q&A

Q: "What is the difference between ensureActive() and yield()?"

A: Both throw CancellationException if the coroutine is cancelled. ensureActive() only checks — no suspension, no thread switch. yield() also suspends briefly, giving other coroutines a chance to run — provides fairness in the thread pool. Use ensureActive() for tight loops where you just want cancellability; use yield() when the work is heavy and you want to be a good citizen in the coroutine pool.

Q: "Where does CoroutineExceptionHandler fit vs try/catch?"

A: CoroutineExceptionHandler is the "last resort" for exceptions that escape the coroutine hierarchy — like an UncaughtExceptionHandler for threads. It's for logging/reporting, not for recovery. For recoverable errors, use try/catch locally. For async results, use try/catch around .await(). The handler only fires on root coroutines inside a scope.

Senior insight

Senior Insight
In an automotive app processing continuous sensor streams, every processing loop must have ensureActive(). When the car park scenario ends, the system scope is cancelled — without this check, the sensor processor would continue consuming CPU and battery on a dead screen. This is the difference between a battery-draining app and a well-behaved one.

9. Interview Questions
What does "cooperative cancellation" mean in coroutines?
Basic⌄
Cancellation is cooperative — the coroutine is not forcefully stopped; instead, calling cancel() marks the Job as cancelling and throws CancellationException at the next suspension point. Code between suspension points runs to completion. If a coroutine has no suspension points (e.g., a tight CPU loop), it cannot be cancelled unless you add explicit checks like ensureActive().
What is CancellationException and how should you handle it?
Basic⌄
CancellationException is a subclass of IllegalStateException used to signal cooperative cancellation. It should always be re-thrown when caught. Catching it with a broad catch (e: Exception) and not rethrowing breaks cancellation — the coroutine continues running after being cancelled. Rule: catch (e: CancellationException) { throw e } always comes first.
When would you use withContext(NonCancellable)?
Basic⌄
When you need to run suspend calls inside a finally block after a coroutine has been cancelled. Normally, any suspension inside a cancelled coroutine throws CancellationException immediately, preventing cleanup. withContext(NonCancellable) overrides this, letting cleanup code (close connections, audit logs, commit transactions) complete even in a cancelled coroutine.
A tight data processing loop is not responding to cancel(). Why and how do you fix it?
Intermediate⌄
The loop has no suspension points — cancellation can only happen at suspension points. Fix: add ensureActive() at the top of each iteration (checks and throws CancellationException if cancelled) or yield() (also yields the thread to other coroutines). For example: for (item in items) { ensureActive(); process(item) }. Both options make the loop respect cancellation.
Where should you place CoroutineExceptionHandler — on the scope, root coroutine, or child coroutine?
Intermediate⌄
On the scope or root coroutine — never on a child coroutine. The handler only fires when an exception has propagated all the way up to the root of the coroutine hierarchy (a coroutine whose parent context is a bare Job, not another coroutine). Adding it to a child launch has no effect — the exception still propagates to the parent.
Does CoroutineExceptionHandler catch exceptions from async { }.await()?
Intermediate⌄
No. The handler only catches exceptions from launch-based coroutines. Exceptions from async { }.await() are re-thrown at the await() call site and must be caught with try/catch there. This is a common misconception — developers add a handler expecting it to catch all errors, but async failures still require local handling.
What is the danger of using runCatching with suspend functions?
Intermediate⌄
runCatching catches ALL exceptions, including CancellationException. If used inside a coroutine, it may silently trap a cancellation signal, breaking cooperative cancellation. The coroutine would continue executing as if nothing happened. Workaround: after calling runCatching, check if the result contains a CancellationException and re-throw it: result.exceptionOrNull()?.let { if (it is CancellationException) throw it }.
Design cancellation-safe order processing for a banking app that must always write an audit log, even when cancelled.
Senior⌄
Structure the processing as: try { processPayment(order) } catch (e: CancellationException) { markOrderCancelled(order); throw e } catch (e: Exception) { markOrderFailed(order, e) } finally { withContext(NonCancellable) { auditLog.write(order) } }. The finally with NonCancellable guarantees the audit log is written regardless of outcome. Re-throwing CancellationException after marking the order cancelled ensures structured concurrency still works. The catch for Exception handles business failures gracefully without breaking cancellation.
Explain why a coroutine can appear "stuck" even after calling scope.cancel().
Senior⌄
Three root causes: (1) The coroutine is in a tight loop with no suspension points — cancellation can't be delivered. Fix: add ensureActive(). (2) The code caught CancellationException and didn't rethrow — the coroutine thinks it's still running normally. Fix: always rethrow CancellationException. (3) The coroutine holds a NonCancellable context from a misused withContext(NonCancellable) not just in finally — if wrapped around a long operation, cancellation is indefinitely blocked. Fix: use NonCancellable only in finally blocks.
What is the difference between ensureActive() and yield() and when would you choose each?
Senior⌄
ensureActive() only checks the cancellation flag and throws CancellationException if cancelled — no suspension, no thread yield. It has minimal overhead and is ideal for high-speed loops that must remain cancellable but should not voluntarily give up the CPU. yield() also throws on cancellation but additionally suspends the coroutine, allowing other coroutines on the same dispatcher to run. Use yield() in CPU-heavy loops that run on a limited pool (Default) where fairness matters — without it, a single heavy coroutine can starve others on the same thread.
