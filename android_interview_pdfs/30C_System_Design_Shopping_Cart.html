30C — Shopping Cart

Design an Android shopping cart: local Room persistence, server sync, optimistic updates, guest-to-auth migration, conflict resolution, promo codes, and order placement flow.

ID: 30C ★ Senior Differentiator
🔍
1. Problem Statement

Requirements

Functional

  • Add, remove, update item quantity in cart
  • Cart persists across app restarts and device reboots
  • Cart syncs with backend for cross-device access
  • Guest cart (not logged in) → migrates to authenticated cart on login
  • Apply discount/promo codes
  • Place order from cart

Non-Functional

  • Instant UI feedback — optimistic updates (don't wait for network)
  • Cart badge count visible on bottom nav
  • Handle concurrent edits (phone + web)
  • No duplicate items — quantity update, not double-add

3. Data Flow

Add to Cart — Optimistic Update

User taps "Add to Cart"
  → CartViewModel.onAddItem(product)
  → AddToCartUseCase.invoke(product)
  → CartRepository.addItem(product)
      1. Write to Room immediately (syncStatus = PENDING)
         → UI updates instantly via Flow (optimistic)
      2. Enqueue SyncCartWorker in background
      3. SyncCartWorker calls CartApi.addItem()
      4. On success: update Room (syncStatus = SYNCED)
      5. On failure: mark FAILED, show retry banner

Cart Badge Count

// Always from Room — instant, no network needed
val cartItemCount: Flow<Int> = cartDao.getTotalItemCount()
// Collect in AppViewModel (singleton) → display on bottom nav badge

Guest Cart → Auth Cart Migration

Guest user adds items → stored in Room with userId = "guest"
User logs in:
  → AuthRepository emits LoginSuccess event
  → CartRepository.migrateGuestCart()
      1. Read all guest cart items from Room
      2. POST /cart/guest-merge with all items + auth token
      3. Server merges: sum quantities for duplicate items,
         or overwrite with auth cart if server is source of truth
      4. Receive merged cart from server
      5. Clear guest items in Room
      6. Save merged cart in Room (userId = authenticated userId)
  → UI shows merged cart

Promo Code Flow

User enters promo code → taps Apply
  → CartViewModel.onApplyPromo(code)
  → ApplyPromoUseCase.invoke(code)
  → CartApi.applyPromo(cartId, code)
  → Response: { discount_amount, discount_type, error? }
  → On success: save promo to Room, recalculate CartSummary
  → On failure: show "Invalid code" error in UiState
  → CartSummary = subtotal - discount + tax

Order Placement

User taps "Place Order"
  → Validate: cart not empty, items still in stock (server check)
  → Show payment selection (Stripe/PayPal intent)
  → POST /orders with: cart_id, payment_method_id, address
  → Response: { order_id, status: "PROCESSING" }
  → Clear local cart (Room.clearAll())
  → Navigate to OrderConfirmationScreen(orderId)
  → Track order status via GET /orders/{id} polling or WebSocket

4. Key Design Decisions

1. Optimistic Updates Pattern

Update Room immediately, sync in background. Users see instant feedback — the cart count and items update without waiting for the server. If the sync fails: show a non-intrusive error banner ("Some changes couldn't sync — tap to retry").

suspend fun addItem(item: CartItem) {
    // 1. Optimistic: update local immediately
    cartDao.insertOrUpdate(item.toEntity(SyncStatus.PENDING))

    // 2. Background sync (don't await — fire and forget)
    val syncWork = OneTimeWorkRequestBuilder<SyncCartWorker>().build()
    workManager.enqueue(syncWork)
}

2. Conflict Resolution

StrategyDescriptionWhen to use
Server winsServer state always overrides local on syncSimple; good for high-trust server-side inventory
Last-write-winsMost recent update (by timestamp) winsMulti-device sync with timestamps
Merge / unionGuest cart + auth cart quantities are summedGuest cart migration

Recommendation: Use server wins for quantity conflicts (prevents overselling inventory). Use merge for guest → auth migration (users expect their guest items to survive login).

3. Debounced Quantity Updates

// Stepper: +/- rapid taps should not fire 10 API calls
private val quantityUpdateFlow = MutableSharedFlow<Pair<String, Int>>()

init {
    quantityUpdateFlow
        .debounce(500)       // wait 500ms after last tap
        .flatMapLatest { (productId, qty) ->
            cartRepository.updateQuantity(productId, qty)
        }
        .launchIn(viewModelScope)
}

6. Scalability

Real-time Cart Updates

For cross-device sync (phone + web): use WebSocket or Server-Sent Events to push cart changes. CartViewModel subscribes to websocket flow; when server emits a cart update event, merge with local Room data (server wins for conflicts).

// WebSocket cart update handler
webSocketFlow
    .filterIsInstance<CartUpdatedEvent>()
    .onEach { event ->
        // Server data overrides local for server-authoritative fields
        cartDao.merge(event.items)
    }
    .launchIn(viewModelScope)

Item Quantity Limits

// Validate client-side AND server-side
fun onUpdateQty(productId: String, newQty: Int) {
    if (newQty > MAX_QUANTITY_PER_ITEM) {
        _uiState.update { it.copy(error = "Max $MAX_QUANTITY_PER_ITEM per item") }
        return
    }
    if (newQty <= 0) { onRemoveItem(productId); return }
    quantityUpdateFlow.tryEmit(productId to newQty)
}

7. Interview Framework

30-Second Answer

"The cart uses Room as local storage with a sync_status field. When users add/update/remove items, Room updates immediately (optimistic update) — the UI responds instantly. A WorkManager job syncs PENDING items to the backend. Server wins on conflicts to prevent inventory overselling. Guest cart items migrate to the authenticated cart on login. Debounced quantity updates prevent API spam from rapid taps."

2-Minute Answer

"Architecture: CartScreen → CartViewModel → CartUseCase → CartRepository → Room + Retrofit. The key design is optimistic updates: user taps '+1' → Room updates immediately with syncStatus = PENDING → WorkManager enqueues a background sync → CartApi call → on success mark SYNCED. This gives instant UI without waiting for the network. For quantity stepper: debounce 500ms so rapid taps don't generate 10 API calls — only the final quantity syncs. Guest cart: items stored in Room with userId='guest'. On login, migrateGuestCart() merges guest items with the server cart (quantities summed for duplicate products). Conflict resolution: server wins for inventory-sensitive fields to prevent overselling; we use last-write-wins (localUpdatedAt timestamp) for ordering non-inventory details. For order placement: validate stock with server → payment intent → POST /orders with idempotency key (prevents duplicate orders from retries) → clear cart only on success → navigate to confirmation."

9. Interview Questions
1. What are optimistic updates and why use them for a cart?
Basic⌄
Optimistic updates means updating the local UI immediately (as if the server accepted the change) and then syncing in the background. For a cart: user taps "+1" → quantity shows 3 instantly → network sync happens asynchronously. This feels snappy and responsive. If sync fails, show an error and optionally roll back. Contrast with pessimistic updates: wait for server confirmation before updating UI — laggy, especially on poor connections.
2. How do you migrate a guest cart to an authenticated cart?
Basic⌄
Store guest cart in Room with userId="guest". On successful login: read all guest items from Room, call POST /cart/guest-merge with items + auth token. Server applies merge strategy: sum quantities for duplicate products (product in both guest + existing auth cart), keep auth-only items, keep guest-only items. Response: merged cart. Client: clear guest items in Room, save merged cart as authenticated user's cart. Show "Your cart has been merged" notification.
3. What is an idempotency key and why is it critical for order placement?
Basic⌄
An idempotency key is a unique identifier (UUID) that the client generates before placing an order and includes in the request header (X-Idempotency-Key). If the same key is sent twice, the server returns the existing response instead of creating a duplicate. This handles the "network dropped after server processed but before client received response" scenario — client retries, server detects duplicate key → returns existing order → no double charge. Generate the UUID when the user confirms the order, not on button tap (to survive navigation).
4. How do you prevent API spam from a quantity stepper?
Intermediate⌄
Debounce: each stepper tap emits to a SharedFlow. Use .debounce(500ms) to wait 500ms after the last tap before calling the API. If the user taps + five times in 400ms, only one API call fires. Additionally: cancel the previous pending request if a new one arrives before it completes (flatMapLatest). This is the standard pattern for quantity inputs, search fields, and any rapid-fire user input.
5. How do you handle a "product is now out of stock" error during checkout?
Intermediate⌄
Server returns HTTP 409 Conflict with a payload indicating which products are out of stock. Client: don't clear the cart. Show inline errors on the affected cart items ("No longer available"). Offer options: remove item from cart, or save to wishlist for later. Don't place the order until the problematic items are resolved. Consider a "Validate Cart" step before showing the checkout button — call GET /cart/validate to check stock before showing the payment screen.
6. How do you handle cart badge count across the entire app?
Intermediate⌄
CartCountRepository provides Flow<Int> from Room's cartDao.getTotalItemCount(). This query returns the sum of quantities instantly from the local database. Inject CartCountRepository into a Hilt-scoped ViewModel or share it via the Application's Hilt SingletonComponent. In MainActivity's composable root: collect cartCount and pass to BottomNavigation badge. Because it's Room, it updates reactively whenever items are added/removed — no manual refresh needed.
7. How do you design the sync mechanism for PENDING cart items?
Intermediate⌄
SyncCartWorker (WorkManager) with constraints: requires network. On run: query Room for all items where syncStatus = PENDING. For each: call the appropriate API (add/update/delete based on operation type — add an operation enum to the entity). On success: update syncStatus = SYNCED. On failure: increment retryCount, WorkManager's retry/backoff handles re-runs. After max retries: mark FAILED, show persistent sync error banner. Use FAILED status to prevent infinite retry loops.
8. How would you handle real-time cart updates across devices?
Senior⌄
WebSocket or Server-Sent Events (SSE) connection per authenticated session. Server pushes CartUpdatedEvent when the cart changes from any device. Client receives event, applies server-wins merge to local Room data (update quantities, add new items, remove deleted items). Use a version number or timestamp per cart to detect stale updates. Show brief "Cart updated from another device" snackbar. Handle reconnection with exponential backoff and replay last event to avoid missing updates during reconnection gap.
9. Design the order placement flow with payment integration.
Senior⌄
Flow: (1) "Checkout" tapped → validate cart (stock check). (2) Show address selection + payment method. (3) Request payment intent from backend (POST /payment/create-intent) → returns client_secret. (4) Present Stripe/PayPal SDK with client_secret. (5) On payment confirmation: POST /orders { cart_id, payment_intent_id, idempotency_key, address_id }. (6) On 200: clear cart from Room, navigate to OrderConfirmationScreen. (7) On failure: keep cart, show error, allow retry with same idempotency_key. Never process payment entirely client-side — always via server-issued payment intents.
10. What would change in your design if the cart required strict consistency (no optimistic updates)?
Scenario⌄
Drop local Room as source of truth. Each cart action calls the API first and waits for confirmation: show loading indicator, then update UI with server response. UiState has explicit Loading/Error states for each operation. Pros: always consistent, no conflicts, no sync complexity. Cons: poor UX on slow connections, unusable offline. This model is appropriate for high-value items (luxury goods, limited edition) where overselling risk outweighs UX concerns. You could also use a hybrid: optimistic updates but with server-side locks that reject conflicting changes and trigger a cart refresh.
