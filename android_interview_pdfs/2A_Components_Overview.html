2A — Android Components Overview

Tier 2 Activity · Fragment · Service · BroadcastReceiver · ContentProvider · Application · Context

1 · Overview

Android apps are not traditional programs with a single main() entry point. Instead, the OS selects and instantiates discrete components on demand. This allows the system to optimise memory, lifecycle, and inter-app collaboration without the app running as a monolithic process.

Activity

A single, focused screen with a UI. The entry point for user interaction. Managed by the Activity back stack.

Fragment

A reusable UI/logic portion hosted inside an Activity. Has its own lifecycle, view lifecycle, and back stack entry.

Service

Long-running background operation, no UI. Three types: Started, Bound, Foreground.

BroadcastReceiver

Listens for system-wide or app-scoped intents (events). Very short-lived — no UI, minimal work.

ContentProvider

Structured data sharing across apps/processes via a URI-based CRUD API backed by SQLite / file / network.

Application

Singleton that exists for the process lifetime. Global init (DI graph, logging). Extended via Application subclass.

Context

Context is the bridge to the Android system: access resources, start components, get system services. Every component is a Context (or wraps one). Two main flavours:

  • Application Context — process lifetime, safe for singletons, DI graphs, database instances.
  • Activity/Fragment Context — tied to UI lifecycle; use only for UI operations (inflate views, show dialogs).

2 · How It Works

AndroidManifest.xml — The Registry

Every component must be declared (or exported) in AndroidManifest.xml. The PackageManagerService reads this at install time to build a component registry.

<!-- Activity: visible screen -->
<activity android:name=".MainActivity"
           android:exported="true">
    <intent-filter>
        <action android:name="android.intent.action.MAIN" />
        <category android:name="android.intent.category.LAUNCHER" />
    </intent-filter>
</activity>

<!-- Service: background work -->
<service android:name=".sync.SyncService"
          android:exported="false" />

<!-- BroadcastReceiver: event listener -->
<receiver android:name=".receiver.BootReceiver"
            android:exported="false">
    <intent-filter>
        <action android:name="android.intent.action.BOOT_COMPLETED" />
    </intent-filter>
</receiver>

<!-- ContentProvider: structured data sharing -->
<provider android:name=".provider.ContactsProvider"
            android:authorities="com.example.app.contacts"
            android:exported="false" />

3 · Why and When to Use Each

ComponentUse when…Do NOT use when…
Activity You need a distinct full-screen user interaction point; app entry points; launcher screens You have a single-activity app (prefer Fragments/Compose for sub-screens)
Fragment Reusable UI segments; tablet dual-pane; modal bottom sheets; navigation destinations Logic-only modules with no UI (use ViewModel / UseCase instead)
Service (started) Long-running work decoupled from UI (legacy); background music (foreground service) One-off background tasks — use WorkManager / Coroutine instead
Service (bound) IPC to another app or process; MediaBrowser; Bluetooth In-process communication — use ViewModel/Repository instead
BroadcastReceiver React to system events (network change, boot, battery); app-global events between components Ongoing processing — receivers must finish in <10 s; no long work here
ContentProvider Expose structured data to other apps (Contacts, Media); share data with widgets Internal-only data access — use Room/DataStore directly
Application Process-level singletons: DI init (Hilt), analytics setup, crash reporting init Storing UI state or large objects — will cause memory leaks
Application Context Singletons, Room database, Retrofit, DataStore, WorkManager Inflating views, showing dialogs — causes WindowManager leaks

4 · Production Example (Banking App)

Multi-module banking app: :app → single Activity, Navigation Compose, Hilt, Room, WorkManager. Each component plays its proper role.

Application — DI + Crash Init

@HiltAndroidApp
class BankingApp : Application() {
    override fun onCreate() {
        super.onCreate()
        // Hilt builds the DI graph here — process-scoped singletons created
        // Crashlytics, Timber, StrictMode init in debug builds
        if (BuildConfig.DEBUG) StrictMode.enableDefaults()
    }
}

Single Activity — Navigation Host

@AndroidEntryPoint
class MainActivity : ComponentActivity() {
    override fun onCreate(savedInstanceState: Bundle?) {
        super.onCreate(savedInstanceState)
        setContent {
            BankingTheme {
                // NavHost owns back stack; all screens are Composables
                AppNavHost()
            }
        }
    }
}

BroadcastReceiver — Network Change

// Registered dynamically (API 26+: static receivers restricted for most actions)
class NetworkReceiver : BroadcastReceiver() {
    override fun onReceive(context: Context, intent: Intent) {
        // Must exit quickly — no coroutines, no blocking IO here
        // Use goAsync() + coroutine only if you MUST; prefer WorkManager
        val isConnected = NetworkUtils.isOnline(context)
        SyncManager.onNetworkChanged(isConnected)   // triggers WorkManager enqueue
    }
}

// In Activity.onStart / ViewModel init:
private val networkReceiver = NetworkReceiver()
registerReceiver(networkReceiver, IntentFilter(ConnectivityManager.CONNECTIVITY_ACTION))

Foreground Service — Transaction Sync

class SyncForegroundService : LifecycleService() {

    @Inject lateinit var syncUseCase: SyncTransactionsUseCase

    override fun onStartCommand(intent: Intent?, flags: Int, startId: Int): Int {
        startForeground(NOTIF_ID, buildNotification())   // must call within 5 s
        lifecycleScope.launch {
            syncUseCase.invoke()
            stopSelf()                                    // stop when done
        }
        return START_NOT_STICKY
    }
}

Context — Safe Usage

// ✅ ApplicationContext for long-lived singletons
@Singleton
class AppDatabase @Inject constructor(
    @ApplicationContext context: Context   // Hilt qualifier — no leaks
) {
    val db = Room.databaseBuilder(context, BankDatabase::class.java, "bank.db").build()
}

// ❌ Never store Activity context in a singleton — causes memory leak
object BadSingleton {
    var ctx: Context? = null  // LEAK if ctx is an Activity
}

5 · Alternatives and Trade-offs

ApproachProsConsWhen to pick
Multiple Activities Clean separation, independent back stacks, deep-link targets Cross-activity communication is hard; more boilerplate; harder to share ViewModels Legacy codebases; distinct user flows that rarely share state
Single Activity + Fragments Shared ViewModel, Navigation Component, easy transitions Fragment lifecycle complexity, FragmentManager bugs in older APIs Standard modern Android pre-Compose
Single Activity + Compose No Fragment lifecycle; composable back stack; simplest model Requires migration effort; less mature tooling for very large apps New projects / greenfield
Service for background Always-running, flexible IPC Background execution restrictions (API 26+); battery drain; complex lifecycle Foreground service (audio, location); IPC to other processes

DataStore instead of ContentProvider Type-safe, coroutine-native, simpler API No cross-app sharing App-internal preferences/proto data

6 · Pitfalls and Best Practices

Context Leaks

❌ Bad

// Stores Activity context in a long-lived object
class ImageLoader(val ctx: Context)

// Passed from Fragment — leaks Fragment/Activity
ImageLoader(requireContext())

✅ Good

// Use applicationContext for singletons
class ImageLoader(val ctx: Context)

ImageLoader(requireContext().applicationContext)

BroadcastReceiver — Long Work

❌ Bad

override fun onReceive(ctx: Context, intent: Intent) {
    // Blocking network call — ANR risk
    apiClient.syncNow()
}

✅ Good

override fun onReceive(ctx: Context, intent: Intent) {
    // Enqueue WorkManager — fast, non-blocking
    WorkManager.getInstance(ctx).enqueue(syncRequest)
}

Other Critical Pitfalls

  • Static Activity reference: companion object { var activity: Activity? } — will leak. Never do this.
  • Starting Activity from Application context: requires FLAG_ACTIVITY_NEW_TASK — avoid unless necessary (notifications, deep links from services).
  • Fragment over-creation: Not using findFragmentByTag before add leads to duplicate fragments after rotation.
  • Service not stopped: Started services that never call stopSelf() or stopService() drain battery.
  • Exported components without permission: android:exported="true" without android:permission exposes your components to any app (security hole).
  • Application class bloat: Heavy sync init in Application.onCreate() slows cold start. Use App Startup library or lazy init.
  • ContentProvider in multi-process: Accessing your own ContentProvider from multiple processes leads to unexpected instantiation. Prefer single-process with explicit initialization order.
API 26+ Background Restrictions: Apps in background cannot start Services. Use startForegroundService() + call startForeground() within 5 seconds, or use WorkManager for deferrable tasks.

7 · Interview Answer Framework

30-Second Answer

"Android apps are component-based rather than having a single entry point. The four main components — Activity, Service, BroadcastReceiver, and ContentProvider — each have a distinct lifecycle and purpose. On top of that, Fragment gives you reusable UI inside an Activity, Application provides process-level initialisation, and Context is the bridge to the Android system. In modern apps I typically use a single Activity with Compose or Fragments for navigation, Services only when truly needed for IPC or foreground work, and WorkManager instead of started Services for background tasks."

2-Minute Structured Answer

What they are: Android's app model is component-based. PackageManagerService reads AndroidManifest.xml at install time, and ActivityManagerService instantiates components on demand. The four main component types are Activity (UI screen), Service (background work), BroadcastReceiver (system/app events), and ContentProvider (structured data sharing).

Key distinctions: Activities are UI-centric and managed in a task back stack. Fragments are hosted by Activities, with their own view lifecycle. Services run without UI; post-API-26, background services are heavily restricted, so foreground services + WorkManager are the production choices. BroadcastReceivers must finish fast — any heavy work goes to WorkManager. ContentProviders are for cross-app data sharing; for internal data I use Room + DataStore directly.

Context: Application context is safe for singletons; Activity context is needed only for UI operations — using it in long-lived objects causes memory leaks. With Hilt, I use @ApplicationContext qualifier to inject the right context automatically.

Modern pattern: Single Activity + Navigation Compose/Fragments; Hilt for DI bootstrapped in Application; WorkManager for background; foreground service only for ongoing user-aware operations like audio playback or live location.

Must-Mention Points

  1. Four app components declared in AndroidManifest; AMS instantiates them on demand.
  2. Activity = UI + back stack; Fragment = reusable UI inside Activity with own view lifecycle.
  3. Service types: Started (no UI, fire-and-forget), Bound (IPC), Foreground (ongoing, visible notification).
  4. BroadcastReceiver is ephemeral — onReceive() must finish fast; post-API-26 most static receivers are restricted.
  5. ContentProvider is for cross-app data sharing; internal apps should use Room / DataStore directly.
  6. Application context vs Activity context: lifespan and leak implications.
  7. Modern recommendation: Single Activity + Compose + WorkManager + Foreground Service only when necessary.
  8. Background execution restrictions since API 26 changed the Service usage pattern fundamentally.

Do Not Go Deeper Unless Asked

  • AIDL / Binder internals for IPC (wait for 3C)
  • ContentProvider cursor implementations
  • IntentService (deprecated) — just note it's replaced by WorkManager
  • Specific Fragment backstack transactions

Likely Follow-up Questions

QuestionShort Answer
What's the difference between Application context and Activity context?Lifespan: Application lives for the process; Activity lives until destroyed. Use Activity context only for UI operations to avoid leaks.
When would you use a bound Service vs WorkManager?Bound Service for IPC / ongoing connection with another process (e.g., MediaBrowser, Bluetooth). WorkManager for deferrable, constraint-aware, persisted background tasks.
Why are static BroadcastReceivers restricted in API 26+?Background execution restrictions. Apps were abusing implicit broadcasts to wake up in background and drain battery. Google restricted most implicit broadcasts to dynamic registration only.
Why single-activity architecture?Simplifies back stack, enables shared ViewModels, works natively with Navigation Component / Compose NavHost, reduces Activity transition complexity.

Senior-Level Insight

"The shift to single-activity architecture isn't just a style preference — it aligns with the process model. Sharing a ViewModel across screens requires a common scope (the Activity's ViewModelStore). Multiple Activities create multiple ViewModelStores, making shared state hard. Compose NavHost takes this further: there's no Fragment back stack at all — the Composable function call stack IS the UI tree, which means no lifecycle edge cases from Fragment transactions. This directly improves testability because screens are just Composable functions with no component lifecycle boilerplate."

Context Golden Rules

  • Singleton / long-lived object → applicationContext (never Activity context)
  • Inflate view / show dialog → Activity/Fragment context
  • Hilt DI → use @ApplicationContext qualifier for non-UI injection
  • Never store Activity in static / companion object field

Background Restrictions (API 26+)

  • Cannot call startService() from background → use startForegroundService() + startForeground() within 5 s
  • Most implicit broadcasts cannot have static receivers → register dynamically
  • Deferrable work → WorkManager

Component Security

  • Set android:exported="false" unless cross-app access is needed
  • Add android:permission for exported components that should be restricted
  • Required: android:exported must be explicit on API 31+ for components with intent-filters

9 · Interview Questions (Self-Check)

Try to answer before expanding each card.

Basic What are the four main Android app components?
Activity, Service, BroadcastReceiver, ContentProvider. All must be declared in AndroidManifest.xml. Each has a distinct lifecycle and purpose managed by the Android system (ActivityManagerService).
Basic What is the difference between Application context and Activity context?
Application context lives for the process lifetime; Activity context lives until the Activity is destroyed. Use Application context for long-lived singletons (databases, Retrofit, DI). Use Activity context only for UI operations (inflate views, show dialogs, start activities). Storing Activity context in a singleton causes memory leaks because the Activity cannot be GC'd.
Basic What restrictions apply to BroadcastReceivers?
onReceive() must complete quickly (ideally <10 s). No long-running or async work. Post-API 26, most implicit broadcasts cannot use statically declared receivers in the manifest — use dynamic registration. If work is needed, enqueue a WorkManager task inside onReceive().
Intermediate Explain the difference between a started Service, bound Service, and foreground Service.
Started: Launched via startService(); runs until stopSelf() is called; no IPC interface. Mostly obsolete for pure background work.
Bound: Launched via bindService(); client-server relationship; provides IBinder for IPC; stops when all clients unbind.
Foreground: Started via startForegroundService(); must show a persistent notification; survives background restrictions; used for ongoing user-aware operations (music, navigation, workout tracking).
Intermediate Why is single-activity architecture preferred in modern Android?
Single Activity means one ViewModelStore, enabling easy state sharing across screens. Navigation Component / Compose NavHost manage the back stack without inter-Activity complexity. Transitions are smoother (within one window). Fragment / Composable lifecycles are simpler than Activity-to-Activity transitions. Deep links are easier to handle in one NavGraph. No need to pass data via Intent extras across Activity boundaries.
Intermediate When should you use ContentProvider for internal data access?
You generally should NOT use ContentProvider for internal-only access. ContentProvider adds overhead (URI resolver, cursor conversion) and was designed for cross-app data sharing. For internal storage use Room (SQL), DataStore (preferences/proto), or files directly. ContentProvider is appropriate when: sharing data with other apps, exposing data to Search/Android Auto/widgets, or implementing SyncAdapter integration.
Intermediate What is the correct way to start a Service on API 26+ from the background?
You cannot call startService() from a background app — it throws IllegalStateException. Use startForegroundService() instead, then call startForeground(notifId, notification) within 5 seconds or the system throws ForegroundServiceDidNotStartInTimeException. For deferrable work, use WorkManager instead of a service entirely.
Senior/Scenario You have a foreground service that syncs banking transactions. It must stop if the user logs out, even if it's mid-sync. How do you architect this?
Use LifecycleService so the service has a lifecycleScope. Expose a cancellation signal — e.g., a SharedFlow in a singleton SyncCoordinator. The sync coroutine collects this flow: if a logout event arrives, cancel the job and call stopSelf(). The ViewModel (or logout UseCase) emits to the SharedFlow. This decouples the logout trigger from the service without needing to call stopService() directly, and the coroutine cooperatively cancels. Also enqueue a WorkManager task post-logout to do any cleanup that must survive process death.
Senior/Scenario [Coding] Register and unregister a BroadcastReceiver safely in a Fragment. Write the code. 
class DashboardFragment : Fragment() {
    private val networkReceiver = object : BroadcastReceiver() {
        override fun onReceive(ctx: Context, intent: Intent) {
            viewModel.onNetworkChanged(NetworkUtils.isOnline(ctx))
        }
    }

    override fun onStart() {
        super.onStart()
        // Register when Fragment is visible
        requireContext().registerReceiver(
            networkReceiver,
            IntentFilter(ConnectivityManager.CONNECTIVITY_ACTION)
        )
    }

    override fun onStop() {
        super.onStop()
        // Unregister symmetric to onStart — prevents leaks
        requireContext().unregisterReceiver(networkReceiver)
    }
}
Key: register/unregister in symmetric lifecycle callbacks (onStart/onStop). Never in onCreate/onDestroy for a dynamic receiver — Fragment view may exist longer than needed.
Senior/Scenario [Debug] Your app throws "Context is not an Activity" when inflating a view inside a ViewModel. What happened and how do you fix it?
The ViewModel was injected with Application context (correct for non-UI work), but the code tried to use it to inflate a View — which requires an Activity context (a ContextThemeWrapper with a window). Fix: Never inflate views in ViewModel. Move inflation to Fragment/Activity. If creating a custom View programmatically for testing, pass Activity context explicitly. Alternatively, if absolutely necessary, wrap applicationContext in a ContextThemeWrapper with the app theme, but this is a code-smell — views belong in the UI layer.
