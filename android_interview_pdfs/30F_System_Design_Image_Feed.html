30F — System Design: Image-heavy Feed

Design an infinite-scroll image feed for Android — Paging 3, Coil, three-level cache, offline support, 60fps smoothness. Senior differentiator unit.

ID: 30F ⭐ Senior Differentiator
🔍
1. Problem Statement

Scenario

Design an Android client for an image-heavy social feed (think Instagram-style) that scrolls infinitely, loads images fast, works offline, and maintains 60fps throughout.

Functional Requirements

  • Infinite scroll — load next page as user approaches end of list
  • Fast image loading with progressive reveal (no pop-in jank)
  • Offline support — users must see cached content with no internet
  • Smooth 60fps / 120fps scroll under load
  • Like/comment counts update in real-time (WebSocket or polling)

Non-Functional Requirements

  • Performance: image load <100ms from cache, <500ms from CDN
  • Memory: no OOM on 2GB RAM devices; evict images when not visible
  • Battery: batch network requests; cancel requests when item scrolls off screen
  • Bandwidth: serve thumbnails first, full-res on demand / WiFi
Clarifying Questions to Ask
(1) Is the feed real-time or pull-to-refresh? (2) What image sizes — fixed aspect ratio or variable? (3) Is there a CDN? (4) Do we need Stories/Reels or just feed? (5) What's the p50/p99 feed latency from backend?

2. Architecture

Layer Breakdown

┌─────────────────────────────────────────────────────┐ │ UI Layer (Compose) │ │ FeedScreen (LazyColumn) ← PagingData<FeedItem> │ └──────────────────────┬──────────────────────────────┘ │ collectAsLazyPagingItems() ┌──────────────────────▼──────────────────────────────┐ │ ViewModel Layer │ │ FeedViewModel → Pager(config, remoteMediator) │ └──────────────────────┬──────────────────────────────┘ │ Flow<PagingData<FeedItem>> ┌──────────────────────▼──────────────────────────────┐ │ Domain Layer │ │ GetFeedUseCase (optional) │ └──────────────────────┬──────────────────────────────┘ │ ┌──────────────────────▼──────────────────────────────┐ │ Data Layer │ │ FeedRepository ← FeedRemoteMediator │ │ ↓ Room (FeedItemEntity) │ │ ↓ Retrofit (FeedItemDto) │ └─────────────────────────────────────────────────────┘ Image Loading (Coil): AsyncImage → MemoryCache (LRU) → DiskCache → Network (CDN)

Key Components

  • FeedScreen — Compose LazyColumn with items(lazyPagingItems); stable key = { it.id } for scroll position preservation
  • FeedViewModel — creates Pager, exposes Flow<PagingData> cached with .cachedIn(viewModelScope)
  • FeedRemoteMediator — Paging 3's offline-first bridge: loads from network, saves to Room, Room is single source of truth
  • FeedRepository — returns @PagingSource from Room; mediator handles network boundary
  • Coil — Compose-native, coroutine-based, handles memory + disk cache automatically

// ViewModel — Pager setup
class FeedViewModel @Inject constructor(
    private val repository: FeedRepository
) : ViewModel() {

    val feedPagingData: Flow<PagingData<FeedItem>> = Pager(
        config = PagingConfig(
            pageSize = 20,
            prefetchDistance = 5,       // start loading 5 items before end
            enablePlaceholders = false
        ),
        remoteMediator = repository.remoteMediator(),
        pagingSourceFactory = { repository.pagingSource() }
    ).flow().cachedIn(viewModelScope)   // survive rotation
}

3. Data Flow

Paging 3 + RemoteMediator Flow

User scrolls near end │ ▼ PagingSource exhausted (no more local data) │ ▼ RemoteMediator.load(LoadType.APPEND, state) │ ├─── Fetch page from Retrofit API │ (cursor = lastItem.cursor) │ ├─── Map Dto → Entity │ ├─── Room.withTransaction { │ if REFRESH: delete old rows │ insert new FeedItemEntity rows │ } │ └─── return MediatorResult.Success(endOfPaginationReached) │ ▼ Room PagingSource automatically invalidated → emits new data → UI updates

Image Loading Flow

AsyncImage(model = item.imageUrl) │ ▼ MemoryCache (LRU, ~20% heap by default in Coil) │ MISS ▼ DiskCache (up to 250MB on disk, LRU) │ MISS ▼ Network request to CDN URL │ ▼ Decode in background thread (IO dispatcher) │ ▼ Store in Disk + Memory cache │ ▼ Display with crossfade animation

Cursor-based Pagination

Real-time feeds should use cursor-based pagination (not offset-based). Reason: if 3 new items are inserted at top while user is on page 2, offset-based pagination skips or duplicates items. Cursor points to a specific item ID/timestamp — always consistent.

4. Key Decisions

Why Coil over Glide / Picasso?

  • Compose-native — AsyncImage composable with no XML
  • Coroutine-based cancellation — image load auto-cancels when composable leaves composition
  • Kotlin-first API, same coroutine dispatcher as the rest of the app
  • Built-in SVG, GIF, video frame support

Why Room as single source of truth?

  • Offline support is free — Room emits cached data even with no network
  • Paging 3 + RemoteMediator is purpose-built for this pattern
  • Single source of truth prevents UI/data inconsistency

Thumbnail vs Full-resolution Strategy

  • Feed row: load thumbnail URL (CDN resized to 400px width) — fast, cheap
  • Detail view: load full-res on demand
  • On WiFi: pre-fetch next 3 full-res images in background
  • On metered: thumbnail only unless user taps

Memory Pressure Trade-off

Coil evicts memory cache under low-memory conditions automatically (respects onLowMemory / ComponentCallbacks2). Disk cache persists across memory pressure — ensures images reload from disk not network after eviction.

Common Mistake
Loading full-resolution images (2000×2000px) into feed thumbnails. Coil's .size() modifier or ImageRequest.size() should be set to the display size. Decoding a 4K image into a 400px thumbnail wastes 10× memory and CPU.

60fps Checklist

  • Stable key in LazyColumn — prevents full recomposition on data update
  • Use @Immutable or @Stable on FeedItem to tell Compose it won't change unexpectedly
  • Avoid allocating lambdas inside composable functions — hoist them to top level or remember
  • Fixed item height where possible — avoids measure passes
  • Pre-fetch distance = 5 items — network request starts before user reaches end
  • Avoid notifyDataSetChanged() equiv — Paging uses diffing internally

9. Quiz
Why is cursor-based pagination preferred over offset-based for a real-time feed?
Medium▼
Offset-based pagination (page=2&size=20) breaks when new items are inserted at the top — page 2 now contains items that were on page 1. Cursor-based pagination points to a specific item (cursor = lastItem.id or timestamp), so the next page always starts after that item regardless of insertions above it.
What does cachedIn(viewModelScope) do and why is it critical?
Medium▼
It caches the PagingData Flow in the ViewModel's scope, so when the screen rotates (Fragment/Activity recreated), the new collector gets the same in-memory pages immediately — no network re-fetch and no scroll position loss. Without it, rotation triggers a full reload from RemoteMediator.
Describe Coil's three-level cache and when each level is hit.
Easy▼
1) MemoryCache — LRU in-process heap (~20% by default); fastest, cleared on process death. 2) DiskCache — stored as files on device (default 250MB); survives process restart, cleared by OS under storage pressure. 3) Network — CDN fetch; slowest, billed against data. Coil checks each level in order.
How does RemoteMediator enable offline-first behaviour?
Hard▼
The PagingSource always reads from Room. The RemoteMediator's job is to fill Room with data from the network. If the network is unavailable, load() returns MediatorResult.Error — but Room already has cached items, so the PagingSource keeps serving them. The UI shows stale data + an error banner. No blank screen.
Why use stable keys in LazyColumn and what happens without them?
Medium▼
Without stable keys (key = { item.id }), Compose uses list position as the key. When Paging 3 inserts items or the list is refreshed, items shift positions — causing Compose to recompose and re-measure all visible items, which causes jank. Stable keys let Compose diff by identity and only recompose changed items.
How does Coil automatically cancel image loads when items scroll off screen?
Medium▼
AsyncImage is a Composable that binds its image request to the composition lifecycle. When the composable leaves composition (item scrolled off screen and recycled by LazyColumn), the coroutine backing the image load is automatically cancelled. This prevents wasted network bandwidth and decoding CPU on off-screen items.
What image format would you use for a CDN serving an Android feed and why?
Easy▼
WebP — supported since Android 4.0, 25–35% smaller than JPEG at the same quality, lossless and lossy modes available. The CDN should serve WebP to Android clients (via Accept header negotiation) and fall back to JPEG for unsupported clients. AVIF offers even better compression but decoding is slow and Android 12+ only.
What is the role of @Immutable on FeedItem and how does it affect performance?
Hard▼
@Immutable tells the Compose compiler that none of FeedItem's public properties will change after construction. This enables "skippable" recomposition — if a FeedItem composable's parameters haven't changed (by reference), Compose skips recomposing it. Without @Immutable (or @Stable), Compose conservatively recomposes all items whenever the parent recomposes, causing jank.
How would you handle a user tapping "Like" while offline?
Hard▼
Optimistic update: immediately update Room (which flows to UI via PagingSource) and enqueue a WorkManager background task to sync the like to the server when network is available. If the server rejects the like, roll back the Room update and show an error. This gives instant feedback and survives app restart before sync.
What is prefetchDistance in PagingConfig and what value would you use?
Easy▼
prefetchDistance is how many items before the end of the loaded list Paging 3 starts loading the next page. A value of 5 means "start loading the next page when the user is 5 items from the bottom." Too small causes visible load indicators; too large wastes bandwidth. 3–10 is typical; tune based on network latency and scroll speed.
