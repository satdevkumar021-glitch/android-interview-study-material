19A — Data & Network Security

Android Sandbox, Hardware-Backed Keystore, EncryptedSharedPreferences, SQLCipher, TLS enforcement, Certificate Pinning, Network Security Config, and secrets handling.

ID: 19A ⭐ Tier 2 (Security Architecture)
🚀
1. Overview & Android Security Model

Android security relies on the Linux Application Sandbox. Each app runs with a distinct Linux User ID (UID) in its own process. By default, apps cannot access other apps' private data directories (/data/data/<package_name>).

Core Android Security Pillars
  • Hardware-Backed Keystore: Private keys and symmetric keys reside in a Secure Element / TEE (Trusted Execution Environment). Key material never enters the Android OS user space memory.
  • EncryptedSharedPreferences: AES-256 GCM encryption for key-value storage backed by a Keystore master key.
  • Network Security Config: Declarative XML rules enforcing HTTPS, disabling cleartext traffic, and configuring custom trust anchors.
  • Certificate Pinning: Restricts accepted TLS certificates to specific cryptographic public key hashes (SHA-256 pins).

2. How It Works Under the Hood

1. Android Keystore System

The Android Keystore lets apps create and use cryptographic keys without exposing key bytes to the app process or RAM. Operations (signing, decryption) are executed inside the secure hardware (TEE/StrongBox):

val keyGenerator = KeyGenerator.getInstance(
    KeyProperties.KEY_ALGORITHM_AES,
    "AndroidKeyStore"
)
val spec = KeyGenParameterSpec.Builder(
    "MyMasterKeyAlias",
    KeyProperties.PURPOSE_ENCRYPT or KeyProperties.PURPOSE_DECRYPT
)
    .setBlockModes(KeyProperties.BLOCK_MODE_GCM)
    .setEncryptionPaddings(KeyProperties.ENCRYPTION_PADDING_NONE)
    .setKeySize(256)
    .build()

keyGenerator.init(spec)
keyGenerator.generateKey()

2. EncryptedSharedPreferences (Jetpack Security)

Uses a two-tier key scheme: A Master Key stored in the Android Keystore encrypts keyset subkeys (using Tink), which encrypt the SharedPreferences values via AES-256 GCM and keys via AES-256 SIV.

3. Network Security & Certificate Pinning

1. Network Security Config (res/xml/network_security_config.xml)

<!-- Disallow all cleartext HTTP and enforce TLS -->
<network-security-config>
    <base-config cleartextTrafficPermitted="false">
        <trust-anchors>
            <certificates src="system" />
        </trust-anchors>
    </base-config>
    <domain-config>
        <domain includeSubdomains="true">api.bank.com</domain>
        <pin-set expiration="2026-12-31">
            <pin digest="SHA-256">k2v657xBsOwg11+/sgYDnU542/gGHPQFiXZq5PCmj0=</pin>
            <!-- Backup pin required for certificate rotation -->
            <pin digest="SHA-256">0Z/WvNvqA9oPj1m12Y2F4Q1aK0bFqW8lG5E4Q3P2A1=</pin>
        </pin-set>
    </domain-config>
</network-security-config>

2. OkHttp CertificatePinner

val certPinner = CertificatePinner.Builder()
    .add("api.bank.com", "sha256/k2v657xBsOwg11+/sgYDnU542/gGHPQFiXZq5PCmj0=")
    .add("api.bank.com", "sha256/0Z/WvNvqA9oPj1m12Y2F4Q1aK0bFqW8lG5E4Q3P2A1=") // Backup pin
    .build()

val okHttpClient = OkHttpClient.Builder()
    .certificatePinner(certPinner)
    .build()

4. Production Example (Secure Auth Token Storage)
class SecureTokenStorage(context: Context) {

    private val masterKey = MasterKey.Builder(context)
        .setKeyScheme(MasterKey.KeyScheme.AES256_GCM)
        .build()

    private val sharedPreferences = EncryptedSharedPreferences.create(
        context,
        "secure_bank_prefs",
        masterKey,
        EncryptedSharedPreferences.PrefKeyEncryptionScheme.AES256_SIV,
        EncryptedSharedPreferences.PrefValueEncryptionScheme.AES256_GCM
    )

    fun saveAuthToken(token: String) {
        sharedPreferences.edit().putString("AUTH_JWT", token).apply()
    }

    fun getAuthToken(): String? = sharedPreferences.getString("AUTH_JWT", null)

    fun clear() = sharedPreferences.edit().clear().apply()
}

6. Pitfalls & Best Practices
Pitfall 1: Hardcoding API Secrets & Private Keys in Kotlin Code

Strings in Kotlin source code or BuildConfig are trivially extracted in seconds via jadx-gui or strings classes.dex. Sensitive backend secrets must live on a backend proxy server; client-side keys should be obfuscated with NDK C++ JNI and protected via API gateway authentication.

Pitfall 2: Single Certificate Pin Brick Hazard

Pinning a single leaf certificate without configuring a backup pin (intermediate CA or backup public key) means your app will permanently fail to connect to your backend if your production certificate expires or is revoked, requiring an emergency Play Store update.

Pitfall 3: Sensitive Logging in Release Builds (Timber)

Logging user PII, credit card details, or auth tokens via Log.d() exposes them to Android Logcat. In production, use Timber with a release tree that strips debug and sensitive logs.

7. Interview Framework

30-Second Elevator Pitch

"Android security follows defense-in-depth: the Linux UID sandbox isolates private app storage, the hardware-backed Android Keystore generates and stores cryptographic keys inside the TEE/StrongBox so raw keys never enter RAM, and EncryptedSharedPreferences protects local auth tokens. Over the wire, Network Security Config enforces TLS, and OkHttp CertificatePinner prevents Man-in-the-Middle attacks."

2-Minute Deep Dive

"At rest, sensitive tokens and keys must never be stored in plain SharedPreferences. We use Jetpack Security's EncryptedSharedPreferences, which uses a 2-tier key model: a Keystore MasterKey encrypts keyset encryption subkeys via AES-256 GCM. For relational datasets, SQLCipher encrypts SQLite databases at the page level.

In transit, Android disables cleartext HTTP by default via Network Security Config. For high-security banking endpoints, we enforce Certificate Pinning on the SPKI public key hash. To prevent app brinking during certificate rotation, we always include primary and backup pins. In code, secrets are never hardcoded; Timber release trees strip Logcat logs, and sensitive crypto operations require biometric user presence."

Must-Mention Checklist

1
Android Keystore / TEE: Keys generated and stored in secure hardware; never leave TEE.
2
EncryptedSharedPreferences: MasterKey + AES-256 GCM / SIV.
3
Certificate Pinning: Public key SHA-256 pinning + mandatory backup pins.
4
Network Security Config: cleartextTrafficPermitted="false".

9. Interview Questions (Self-Check)

Basic Questions

B1 — How does the Android Application Sandbox isolate app data?
Easy▼
Android assigns each installed application a unique Linux User ID (UID) and runs it in an isolated process. File system permissions ensure that private directories (/data/data/<package_name>) can only be read and written by that specific UID, preventing other apps from accessing private files.
B2 — What is the primary advantage of storing keys in the Android Keystore?
Easy▼
The Android Keystore protects key material from being extracted. Keys are generated and stored inside hardware-backed secure enclaves (TEE or StrongBox). Cryptographic operations (signing, decryption) are performed inside the hardware module; raw key bytes are never exposed in the application's RAM.
B3 — What is Certificate Pinning and why is it used?
Easy▼
Certificate Pinning is a security technique where the client app hardcodes or verifies the exact cryptographic public key hash (SPKI SHA-256) of the server's certificate. This protects against Man-in-the-Middle (MitM) attacks where a compromised or rogue Certificate Authority (CA) issues fraudulent certificates.

Intermediate Questions

I1 — How does EncryptedSharedPreferences work under the hood?
Medium▼
It uses Google's Tink crypto library with a 2-tier key architecture: A hardware-backed MasterKey in the Android Keystore encrypts a local keyset. Key names are deterministically encrypted using AES-256 SIV (so keys can be queried), and key values are encrypted using AES-256 GCM authenticated encryption.
I2 — Why must you always configure a backup pin when using Certificate Pinning?
Medium▼
If you pin only one certificate/key and that certificate expires, is revoked, or the server rotates keys due to a compromise, your mobile app will reject the new server certificate and permanently fail all network calls. A backup pin ensures smooth rotation without breaking existing client apps.
I3 — What is SQLCipher and how does it differ from standard Room DB?
Medium▼
Standard Room DB stores SQLite database files in plaintext on disk. SQLCipher is an open-source extension providing transparent 256-bit AES page-level encryption for the entire SQLite database file, headers, and journal data. It integrates with Room using SupportFactory(passphrase).
I4 — How do you prevent sensitive screens from appearing in Android Recents / App Switcher?
Medium▼
Call window.setFlags(WindowManager.LayoutParams.FLAG_SECURE, WindowManager.LayoutParams.FLAG_SECURE) in the Activity's onCreate(). This instructs the OS to treat the window surface as secure, blocking screenshots, screen recordings, and masking the window preview in the recent apps task switcher.

Senior & Scenario Questions

S1 — How do you protect a third-party payment gateway API secret in a mobile client?
HardScenario▼
Never store master payment gateway private keys in the client app code or APK. The only secure architecture is a Backend-for-Frontend (BFF) proxy: The Android client authenticates against your own secure backend with a user JWT, your backend communicates with the payment gateway using the secret key, and passes a short-lived, scoped client token/intent back to the Android app.
S2 — How would you implement biometric-bound encryption for high-value banking transactions?
HardScenario▼
1. Generate an AES key in Keystore with setUserAuthenticationRequired(true) and setUserAuthenticationParameters(0, AUTH_BIOMETRIC_STRONG).
2. Initialize a Cipher in ENCRYPT_MODE.
3. Wrap the cipher in BiometricPrompt.CryptoObject(cipher).
4. Present BiometricPrompt.authenticate(promptInfo, cryptoObject).
5. In onAuthenticationSucceeded(), obtain the authenticated cipher from result.cryptoObject.cipher and encrypt transaction payload.
S3 — What happens to Keystore keys when the user changes or removes their device lock screen PIN/biometrics?
HardScenario▼
If a key is generated with setInvalidatedByBiometricEnrollment(true) or bound to user authentication, enrolling a new fingerprint or disabling the lock screen permanently invalidates the key in the TEE. Attempting to use the key throws a KeyPermanentlyInvalidatedException. The app must detect this exception, clear local credentials, and force the user to re-authenticate with server credentials.
