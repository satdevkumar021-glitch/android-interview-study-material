8B — Clean Architecture

Three concentric layers, the Dependency Rule, and the art of keeping your domain pure. The architecture standard for production Android apps.

ID: 8B ⭐ Tier 1
🔍
1. Overview

What is Clean Architecture?

Clean Architecture (Robert C. Martin, 2012) organises code into concentric layers where dependencies only point inward. The innermost layer (Domain) has zero knowledge of Android, databases, or network — it is pure Kotlin business logic. Each outer layer depends on the layer inside it, never the reverse.

┌──────────────────────────────────────────────────────┐ │ PRESENTATION LAYER │ │ ViewModel · UI State · Composable / Fragment │ │ │ │ ┌──────────────────────────────────────────────┐ │ │ │ DOMAIN LAYER (pure Kotlin) │ │ │ │ UseCase · Repository Interface │ │ │ │ Domain Models · Business Rules │ │ │ │ │ │ │ │ ┌────────────────────────────────────────┐ │ │ │ │ │ DATA LAYER │ │ │ │ │ │ Repository Impl · Remote DS │ │ │ │ │ │ Local DS · DTO · Mapper │ │ │ │ │ └────────────────────────────────────────┘ │ │ │ └──────────────────────────────────────────────┘ │ └──────────────────────────────────────────────────────┘ Dependencies flow INWARD only ──►

The Three Layers

LayerContentsDependencies
PresentationViewModel, UI State, Composables/Fragments/ActivitiesDomain layer only
DomainUseCases, Repository interfaces, Domain models, Business rulesNone — pure Kotlin
DataRepository implementations, Remote/Local data sources, DTOs, MappersDomain layer (implements interfaces)
Senior Mental Model
The Domain layer is the most stable part of your app. It should compile without any Android SDK, Retrofit, or Room imports. If your UseCase imports retrofit2.Response, you have violated the Dependency Rule.
⚙
2. How It Works

The Dependency Rule

Source code dependencies must point inward only. A class in the Data layer can implement a Domain interface, but the Domain layer never imports anything from Data. This is enforced at compile time by structuring them as separate Gradle modules.

Dependency Inversion in Practice

The Domain layer defines the PaymentRepository interface. The Data layer implements it. The Domain UseCase receives it via constructor injection — it never knows whether it's talking to Room or Retrofit.

// domain/repository/PaymentRepository.kt  (pure Kotlin interface)
interface PaymentRepository {
    suspend fun processPayment(request: PaymentRequest): Result<PaymentReceipt>
    fun getTransactionHistory(accountId: String): Flow<List<Transaction>>
}

// domain/model/PaymentRequest.kt  (Domain model — no JSON annotations)
data class PaymentRequest(
    val fromAccountId: String,
    val toAccountId: String,
    val amount: BigDecimal,
    val currency: Currency
)

// domain/usecase/ProcessPaymentUseCase.kt
class ProcessPaymentUseCase @Inject constructor(
    private val repository: PaymentRepository,  // interface, not impl
    private val validator: PaymentValidator
) {
    suspend operator fun invoke(request: PaymentRequest): Result<PaymentReceipt> {
        validator.validate(request).getOrElse { return Result.failure(it) }
        return repository.processPayment(request)
    }
}

DTO → Domain Model Mapper

DTOs carry network/database-specific concerns (JSON field names, nullable API fields). Mappers convert them to clean domain models at the boundary.

// data/remote/dto/TransactionDto.kt
data class TransactionDto(
    @SerializedName("txn_id") val txnId: String,
    @SerializedName("amount_cents") val amountCents: Long,
    @SerializedName("status_code") val statusCode: Int?
)

// data/mapper/TransactionMapper.kt
fun TransactionDto.toDomain(): Transaction = Transaction(
    id = txnId,
    amount = BigDecimal(amountCents).movePointLeft(2),
    status = TransactionStatus.fromCode(statusCode ?: 0)
)

Repository Implementation (Data Layer)

// data/repository/PaymentRepositoryImpl.kt
class PaymentRepositoryImpl @Inject constructor(
    private val remoteDataSource: PaymentRemoteDataSource,
    private val localDataSource: PaymentLocalDataSource
) : PaymentRepository {

    override suspend fun processPayment(request: PaymentRequest) =
        runCatching {
            remoteDataSource.processPayment(request.toDto()).toDomain()
        }

    override fun getTransactionHistory(accountId: String): Flow<List<Transaction>> =
        localDataSource.getTransactions(accountId).map { list ->
            list.map { it.toDomain() }
        }
}
Unidirectional Data Flow
UI → ViewModel → UseCase → Repository → DataSource. Data flows back up via Flow/StateFlow. No circular dependencies. Each step is independently testable with mocks.

3. When to Use

Use Clean Architecture when:

  • Team size > 2: clear boundaries prevent merge conflicts and ownership disputes
  • Long-lived app: the separation pays off over months, not weeks
  • Multiple data sources: combining Room + Retrofit + third-party SDKs
  • High test coverage requirement: UseCases are pure Kotlin — unit tests need no Android framework
  • Feature parity across platforms: domain module can be shared with KMM (Kotlin Multiplatform Mobile)

Consider a simpler approach when:

  • Prototype or throwaway code — the boilerplate overhead isn't worth it
  • Single-feature, single-developer, short-lived app
  • Simple CRUD app with no business logic (a ViewModel directly calling a Repository may suffice)
Pragmatic Note
Many teams skip the UseCase layer for trivial screens (e.g., a settings toggle) and only introduce UseCases when business logic accumulates. That's fine — Clean Architecture is a spectrum, not a binary.

Module Structure (Gradle)

:app (Android module — Hilt entry point, navigation) :feature:payments :presentation (Android module — ViewModel, Composables) :domain (pure Kotlin module — UseCases, interfaces, models) :data (Android module — Room, Retrofit, repositories) :core:network (shared Retrofit/OkHttp setup) :core:database (shared Room setup)

4. Production Example

Banking App — Transfer Money Feature

A complete vertical slice through all three layers for a funds transfer flow:

// ── DOMAIN LAYER ──────────────────────────────────────────────

// domain/model/TransferResult.kt
sealed class TransferResult {
    data class Success(val receipt: TransferReceipt) : TransferResult()
    data class InsufficientFunds(val available: BigDecimal) : TransferResult()
    data class DailyLimitExceeded(val limit: BigDecimal) : TransferResult()
    data class Error(val cause: Throwable) : TransferResult()
}

// domain/usecase/TransferFundsUseCase.kt
class TransferFundsUseCase @Inject constructor(
    private val accountRepo: AccountRepository,
    private val transferRepo: TransferRepository,
    private val limitsRepo: LimitsRepository
) {
    suspend operator fun invoke(params: TransferParams): TransferResult {
        val balance = accountRepo.getBalance(params.fromAccountId)
        if (balance < params.amount) return TransferResult.InsufficientFunds(balance)

        val dailyLimit = limitsRepo.getDailyTransferLimit(params.fromAccountId)
        val usedToday = transferRepo.getTodayTransferTotal(params.fromAccountId)
        if (usedToday + params.amount > dailyLimit)
            return TransferResult.DailyLimitExceeded(dailyLimit)

        return runCatching { transferRepo.execute(params) }
            .fold(
                onSuccess = { TransferResult.Success(it) },
                onFailure = { TransferResult.Error(it) }
            )
    }
}
// ── PRESENTATION LAYER ────────────────────────────────────────

@HiltViewModel
class TransferViewModel @Inject constructor(
    private val transferFunds: TransferFundsUseCase
) : ViewModel() {

    private val _uiState = MutableStateFlow<TransferUiState>(TransferUiState.Idle)
    val uiState = _uiState.asStateFlow()

    fun onTransfer(params: TransferParams) {
        viewModelScope.launch {
            _uiState.emit(TransferUiState.Loading)
            val result = transferFunds(params)
            _uiState.emit(when (result) {
                is TransferResult.Success          -> TransferUiState.Success(result.receipt)
                is TransferResult.InsufficientFunds -> TransferUiState.InsufficientFunds
                is TransferResult.DailyLimitExceeded -> TransferUiState.LimitExceeded
                is TransferResult.Error              -> TransferUiState.Error(result.cause.message)
            })
        }
    }
}

5. Alternatives & Trade-offs
ArchitectureLayersProsCons
Clean Architecture3 (Presentation/Domain/Data)Testable, scalable, platform-agnostic domainBoilerplate, learning curve
MVI + Repository2 (UI/Data)Simpler, less filesBusiness logic bleeds into ViewModel
MVVM (no UseCase)2 (ViewModel/Repository)Quick to set up, Google's starter recommendationRepos become god objects over time
MVC (Activity)1No boilerplateUntestable, spaghetti code

Clean Architecture vs "MVVM with Repository"

Google's official guide shows MVVM + Repository without a Domain layer. That works for simple apps. As business rules grow, UseCases act as an extraction point — each one has a single responsibility, is independently testable, and prevents the ViewModel from becoming a god object.

KMM Advantage
If you structure the Domain layer as a pure Kotlin module, it can be shared between Android and iOS via Kotlin Multiplatform. Business logic is written once; only the Presentation and Data layers differ per platform.

6. Pitfalls & Best Practices

Common Violations

Anti-Pattern: Domain importing Android/Retrofit
import retrofit2.Response or import android.content.Context inside a UseCase or domain model instantly breaks the Dependency Rule and makes the domain untestable without Robolectric.
Anti-Pattern: Repository returning DTOs
If UserRepository.getUser() returns UserDto (with JSON annotations), the mapping responsibility leaks into the Presentation layer. Always map to domain models at the Data/Domain boundary.

Best Practices

  • One UseCase per action: GetUserUseCase, UpdateProfileUseCase — not a UserUseCase with ten methods
  • Domain models have no annotations: no @SerializedName, no @ColumnInfo, no @Parcelize (those belong in Data/Presentation)
  • UseCases are operator fun invoke: the idiomatic Kotlin style allows calling them like a function: getUser(userId)
  • Mappers as extension functions: fun UserDto.toDomain() keeps mapping code co-located with the DTO
  • Repository interface in Domain, impl in Data: enforced by separate Gradle modules so you cannot accidentally import the wrong one
  • Test UseCases with pure unit tests: no Mockk Android extensions needed — just mock the repository interface

7. Interview Framework

30-Second Answer

"Clean Architecture splits an Android app into three layers: Presentation (ViewModel + UI), Domain (UseCases + Repository interfaces + domain models), and Data (Repository implementations + Room + Retrofit). The key rule is that dependencies only point inward — the Domain layer knows nothing about Android, databases, or network. This makes business logic independently testable and swappable."

2-Minute Deep Dive

"On top of the three layers, I apply the Dependency Inversion Principle: the Domain layer defines repository interfaces, and the Data layer implements them. This means if we swap Retrofit for a GraphQL client, the Domain and Presentation layers don't change at all. I use the Mapper pattern to convert DTOs (which have JSON annotations) into clean domain models at the Data/Domain boundary — the domain model is annotation-free and testable without Android. UseCases are single-responsibility interactors — they orchestrate business rules, validate inputs, and delegate to repositories. The ViewModel only talks to UseCases and exposes a StateFlow of sealed UI states. The whole flow is unidirectional: UI → ViewModel → UseCase → Repository → DataSource, with data flowing back up via Flow."

Must-Mention Points

1
Dependency Rule: source code dependencies only point inward — outer layers depend on inner, never the reverse
2
Domain layer is pure Kotlin: no Android SDK, no Retrofit, no Room — compiles standalone
3
DIP: Domain defines interface PaymentRepository; Data implements it. ViewModel/UseCase depend on abstraction
4
Mapper pattern: DTO (data concern) → Domain Model (business concern) at the Data layer boundary
5
UseCase = single responsibility: operator fun invoke, one business action, independently unit testable
6
Unidirectional data flow: UI → ViewModel → UseCase → Repository → DS, results via Flow/StateFlow
7
Gradle modules: enforced at compile time — cannot import Data classes into Domain module

Do NOT Go Deeper On

  • Hexagonal Architecture / Ports and Adapters (same idea, different name — mention only if asked)
  • The full Gradle multi-module setup syntax (mention the concept, not the Gradle DSL)
  • KMM shared domain module (mention as a benefit, don't deep-dive unless asked)

Follow-up Q&A

QuestionAnswer
"Why not just use ViewModel + Repository?"Works for simple apps, but repos become god objects. UseCases isolate business logic, making it testable and reusable across features.
"Isn't it too much boilerplate?"The layers pay dividends in large teams: parallel development, isolated testing, and swappable data sources.
"What if a UseCase just delegates to a repository?"That's fine — a passthrough UseCase still provides a stable interface and a place to add logic later without touching the ViewModel.
"How do you enforce the Dependency Rule?"Separate Gradle modules: :domain is a pure Kotlin module with no Android dependencies. Any bad import causes a compile error.

Senior Insight

Senior Signal
Mention that the real value of Clean Architecture isn't the layers themselves — it's that it creates natural seams for testing. A UseCase with a mocked repository interface can be tested in <1ms with no emulator. At scale, this means thousands of fast unit tests instead of slow integration tests. That's the business case for the boilerplate.

9. Interview Questions
Basic What are the three layers of Clean Architecture and what goes in each? ⌄
Presentation: ViewModel, UI State, Composables/Fragments — handles display logic and user events.

Domain: UseCases, Repository interfaces, Domain models, business rules — pure Kotlin, no Android imports.

Data: Repository implementations, DTOs, Mappers, Room DAOs, Retrofit API interfaces — bridges the domain to external systems.
Basic What is the Dependency Rule and why does it matter? ⌄
Source code dependencies must point inward only. Outer layers (Data, Presentation) can depend on inner layers (Domain), but Domain can never import anything from Data or Presentation. This means the business logic is decoupled from framework details, making it independently testable and replaceable.
Basic Why should Domain models be free of JSON/Room annotations? ⌄
Annotations like @SerializedName and @ColumnInfo are data concerns tied to specific frameworks. If you put them on domain models, your business logic becomes coupled to Gson and Room. When you switch serialisation libraries or databases, you'd have to modify domain models — violating OCP and the Dependency Rule. The solution is separate DTOs in the Data layer with mappers at the boundary.
Intermediate Explain the Mapper pattern with a concrete example. ⌄
A mapper converts between layers' models. A UserDto from Retrofit has @SerializedName annotations and potentially nullable fields due to API inconsistency. The domain User has validated, non-null fields. An extension function fun UserDto.toDomain(): User in the Data layer performs this conversion — handling nulls, renaming fields, and transforming types — so the Domain and Presentation layers work with clean, safe models.
Intermediate When would you skip the UseCase layer? ⌄
For screens with no business logic — like a settings toggle that just calls repository.saveTheme(theme) — a passthrough UseCase adds ceremony without benefit. In those cases, having the ViewModel call the repository directly is fine. The UseCase layer pays off when there's real orchestration: validating inputs, combining data from multiple repositories, handling business-specific error cases, or reusing the same logic across ViewModels.
Intermediate How does Dependency Inversion work between Domain and Data? ⌄
The Domain layer defines a interface ProductRepository with methods the UseCase needs. The Data layer provides class ProductRepositoryImpl : ProductRepository. Hilt binds the implementation to the interface via @Binds. The UseCase only knows about the interface — it never imports or instantiates the implementation. This means swapping Room for SQLDelight only requires changing the Data module; Domain and Presentation are untouched.
Intermediate How do you handle errors across the layers? ⌄
The Data layer catches network/database exceptions and converts them into domain errors — either via Kotlin's Result<T> or a custom sealed class. The UseCase propagates or transforms these into business-meaningful sealed results (e.g., InsufficientFunds instead of HttpException(402)). The ViewModel maps these to UI states. The Presentation layer never sees raw IOException — it sees domain-specific failure cases it can display meaningfully.
Senior How do you enforce Clean Architecture boundaries at scale? ⌄
Gradle modules are the primary enforcement mechanism — the :domain module declares no Android or framework dependencies, so any bad import fails the build. For monolithic single-module projects, tools like ArchUnit (via JVM tests) can assert that no class in the domain package imports anything from data or presentation. On large teams, a custom Lint rule or a modularisation guide in the team wiki prevents drift. The key is making violations visible at CI time, not code review time.
Senior Design a Clean Architecture structure for an e-commerce app with offline support. ⌄
Domain: ProductRepository interface with getProducts(): Flow<List<Product>>, GetFeaturedProductsUseCase, domain models Product, Cart, Order.

Data: ProductRepositoryImpl that first emits Room data (instant), then fetches from Retrofit, maps DTOs, saves to Room — so the Flow automatically re-emits the updated list. Room is the single source of truth. TTL-based cache invalidation triggers background refresh.

Presentation: ProductListViewModel collects the Flow, emits UiState.Loading / UiState.Success(products) / UiState.Offline(cachedProducts).

The offline-first pattern works naturally because Room's Flow re-emits whenever the local DB updates, regardless of whether the update came from the network or a local action.
Senior A colleague says UseCases are just "extra classes that call repository methods". How do you respond? ⌄
They're right for trivial cases, and that's fine — not every UseCase needs to justify its existence. The value emerges when:

1. Multiple ViewModels need the same logic — without a UseCase, you'd duplicate it or put it in the repository (wrong layer).
2. Business rules accumulate — a "place order" flow that started as a single repo call now involves inventory check, payment processing, loyalty points, and audit logging. A UseCase is the right seam for that.
3. Testing — a UseCase with mocked repos tests business logic at <1ms, no emulator needed.

The pragmatic approach: start without UseCases, extract them when ViewModels grow beyond display logic. The architecture supports that evolution.
