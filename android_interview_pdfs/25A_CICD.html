1. Overview

What is CI/CD for Android?

Continuous Integration (CI): every code change triggers automated lint, tests, and builds — catching regressions before they reach main. Continuous Delivery (CD): tested builds are automatically packaged and distributed to testers or the Play Store.

  • Pipeline stages: push → lint → unit tests → build → UI tests → sign → distribute
  • GitHub Actions: YAML-based workflow files in .github/workflows/
  • Fastlane: Ruby-based automation for building, testing, and deploying iOS and Android apps
  • AAB: Android App Bundle — required for Play Store; Google generates optimized APKs per device
Senior Mental Model
CI/CD is a quality gate, not just automation. Every merge to main should be guaranteed to be shippable. The pipeline should fail fast — lint and unit tests first (cheap), then build, then UI tests (expensive). Never merge red builds.

Trunk-BasedEveryone commits to main (or short-lived branches <1 day)High-velocity teams, feature flags for incomplete work

Pull Request Best Practices

  • Small PRs: <400 LOC changed — easier to review, less likely to break things
  • Required CI pass: lint + unit tests must pass before merge
  • Required reviewers: at least 1–2 approvals from team members
  • Automated checks: lint, test coverage threshold, static analysis
  • Branch protection: protect main from direct pushes
Android Team Recommendation
Most Android teams use a trunk-based approach with feature flags for incomplete features. Release branches are cut when preparing a Play Store submission. Hotfixes are cherry-picked from the release branch back to main.

3. GitHub Actions Pipeline

Android Pull Request Verification Example

Adapt the JDK, SDK packages and action versions to your project. Tags below are illustrative; pin reviewed production actions to full commit SHAs. Signing and publishing belong in a separate protected release workflow.

# .github/workflows/android-ci.yml
name: Android CI
permissions:
  contents: read
on:
  push:
    branches: [ main, develop ]
  pull_request:
    branches: [ main ]

jobs:
  lint-and-test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

      - name: Set up JDK 17
        uses: actions/setup-java@v4
        with:
          java-version: '17'
          distribution: 'temurin'

      - name: Setup Gradle
        uses: gradle/actions/setup-gradle@v3
        with:
          cache-encryption-key: ${{ secrets.GRADLE_ENCRYPTION_KEY }}

      - name: Run Lint
        run: ./gradlew lintDebug

      - name: Run Unit Tests
        run: ./gradlew testDebugUnitTest

      - name: Upload Test Results
        if: always()
        uses: actions/upload-artifact@v4
        with:
          name: test-results
          path: '**/build/reports/tests/'

  build:
    needs: lint-and-test
    runs-on: ubuntu-latest
    permissions:
      contents: read
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-java@v4
        with: { java-version: '17', distribution: 'temurin' }
      - uses: gradle/actions/setup-gradle@v3
      - name: Build Debug APK
        run: ./gradlew :app:assembleDebug
      - uses: actions/upload-artifact@v4
        with:
          name: debug-apk
          path: app/build/outputs/apk/debug/*.apk
Key Actions
gradle/actions/setup-gradle@v3 provides Gradle caching out of the box — it caches the Gradle wrapper, dependencies, and build cache between runs, dramatically reducing CI build time.

4. Signing & Distribution

Secure Signing in CI

  1. Base64-encode your keystore: base64 -i release.jks | pbcopy
  2. Add to GitHub Secrets: KEYSTORE_BASE64, STORE_PASSWORD, KEY_ALIAS, KEY_PASSWORD
  3. In CI: decode keystore to a temp file, pass path + creds as env vars to Gradle
  4. Delete temp keystore file after signing (or use tmpfs)
Security Rules
Never commit .jks files to the repo. Never log credentials. Never print env vars. Use GitHub Secrets (encrypted at rest, masked in logs). Rotate keys if accidentally exposed.

5. Fastlane & Play Store

Fastlane for Android

Fastlane is a Ruby-based automation tool. Its Fastfile defines lanes — sequences of actions for building, testing, and deploying.

# fastlane/Fastfile
default_platform(:android)

platform :android do
  lane :test do
    gradle(task: "test", build_type: "Debug")
  end

  lane :beta do
    gradle(
      task: "bundle",
      build_type: "Release",
      properties: {
        "android.injected.signing.store.file" => ENV["KEYSTORE_PATH"],
        "android.injected.signing.store.password" => ENV["STORE_PASSWORD"],
        "android.injected.signing.key.alias" => ENV["KEY_ALIAS"],
        "android.injected.signing.key.password" => ENV["KEY_PASSWORD"],
      }
    )
    upload_to_play_store(
      track: "internal",
      aab: "app/build/outputs/bundle/release/app-release.aab"
    )
  end

  lane :deploy do
    upload_to_play_store(
      track: "beta",
      track_promote_to: "production",
      rollout: "0.1"   # 10% rollout
    )
  end
end

6. Pitfalls & Best Practices

Common Pitfalls

  • Committing keystore/passwords: irreversible security breach. Use GitHub Secrets only.
  • Slow CI due to no caching: always use gradle/actions/setup-gradle for Gradle caching
  • Running UI tests on every PR: expensive. Run unit tests on PR, UI tests only on merge to main or nightly
  • No branch protection: developers can push broken code directly to main. Enforce CI pass + reviews.
  • Uploading APK to Play Store: Play Store requires AAB since August 2021 for new apps
  • Forgetting versionCode increment: Play Store rejects uploads with duplicate versionCode. Automate with CI build number.

Best Practices

PracticeWhy
Fail fast: lint before buildCatch cheap issues early, don't waste build minutes
Cache Gradle dependenciesSaves 3–5 min per CI run
Use GitHub EnvironmentsRequire manual approval before deploying to production
Automate versionCode from CIUse GITHUB_RUN_NUMBER as versionCode to avoid duplicates
Use AAB for Play Store20–30% smaller downloads vs APK
Stage production rolloutStart at 1–10%, monitor crash rate, then expand

30-Second Answer

"Our CI pipeline runs on GitHub Actions: every PR triggers lint and unit tests, merge to main triggers a full build, signs an AAB with credentials from GitHub Secrets, and distributes to Firebase App Distribution for QA. Production deployments go through Fastlane with a staged rollout. Signing credentials are stored as base64-encoded secrets — the keystore is never committed."

2-Minute Answer

"For branching I prefer trunk-based development with short-lived feature branches and feature flags for incomplete work. The CI pipeline has two stages: lint + unit tests run on every PR (fast, catches most issues), and the full build + UI tests run on merge to main. GitHub Actions with gradle/actions/setup-gradle provides Gradle caching so dependencies and build cache are shared between runs, keeping build times under 5 minutes. For release: the AAB is built with R8 minification enabled, signed using a keystore decoded from base64-encoded GitHub Secret, and uploaded to Play Store's internal track via Fastlane. Production uses a staged rollout starting at 10%. I also set up JaCoCo coverage reports uploaded to Codecov to track test coverage trends over time."

Must-Mention Points

1
Signing credentials from GitHub Secrets — keystore base64-encoded, never committed
2
Fail fast: lint → unit tests → build → UI tests — don't run expensive steps before cheap ones pass
3
AAB for Play Store — 20–30% smaller, Google generates per-device APKs
4
Gradle caching in CI via gradle/actions/setup-gradle — saves minutes per run
5
Staged rollout — 10% → monitor crash rate → expand, can halt if issues found

Senior Differentiator

Also mention monitoring post-deploy: Firebase Crashlytics alerts on spike in crash rate within hours of a new rollout.

9. Interview Questions
1. What is the difference between an APK and an AAB?
Basic⌄
An APK (Android Package) contains all resources for all device configurations in one file — large download. An AAB (Android App Bundle) contains split code and resources for all configurations; Google Play generates device-specific APKs from it at download time, reducing install size by 20–30%. Play Store requires AAB for new apps since August 2021. APKs are still used for direct installs and Firebase App Distribution.
2. How do you securely handle the release keystore in CI?
Basic⌄
Base64-encode the keystore file and store it as a CI secret (e.g. KEYSTORE_BASE64 in GitHub Secrets). In the CI workflow, decode it: echo "$KEYSTORE_BASE64" | base64 -d > keystore.jks. Pass the path and credentials (STORE_PASSWORD, KEY_ALIAS, KEY_PASSWORD) as environment variables to the Gradle build. Never commit the .jks file or print env vars in logs.
3. What Play Store tracks are available for staged deployment?
Basic⌄
Internal testing (up to 100 testers, instant publish), Closed testing / Alpha (specific user groups), Open testing / Beta (any opted-in user), Production (all users, supports gradual rollout percentage). Standard flow: Internal → Alpha → Beta → Production at 10% → 50% → 100%.
4. What GitHub Actions steps are essential for an Android CI pipeline?
Intermediate⌄
actions/checkout (clone repo), actions/setup-java with JDK 17 (Temurin distribution), gradle/actions/setup-gradle (Gradle wrapper + dependency + build cache), then Gradle tasks: lintDebug, testDebugUnitTest, bundleRelease. For UI tests: need Android emulator action. Caching via gradle/actions/setup-gradle saves 3–5 min per run.
5. Compare GitFlow, GitHub Flow, and trunk-based development.
Intermediate⌄
GitFlow: main + develop + feature/* + release/* + hotfix/* — structured, good for scheduled releases. GitHub Flow: main + short-lived feature branches, deploy from main — simpler, continuous deployment. Trunk-based: everyone commits to main (or branches <1 day old), incomplete features hidden behind feature flags — best for high-velocity teams, minimizes merge conflicts. Most Android teams use trunk-based or GitHub Flow with Play Store release branches cut periodically.
6. How would you prevent a duplicate versionCode upload to Play Store in CI?
Intermediate⌄
Use the CI build number as the versionCode: in GitHub Actions, GITHUB_RUN_NUMBER is a monotonically increasing integer. Inject it into Gradle: android { defaultConfig { versionCode = System.getenv("GITHUB_RUN_NUMBER")?.toIntOrNull() ?: 1 } }. This guarantees each CI-built AAB has a unique versionCode. Local developer builds use 1 as the fallback.
7. Your CI pipeline takes 20 minutes. How do you optimize it?
Intermediate⌄
1) Enable gradle/actions/setup-gradle for dependency and build cache. 2) Split pipeline into parallel jobs: lint, unit tests, and instrumented tests can run simultaneously. 3) Run UI tests only on main merges, not every PR. 4) Use larger GitHub Actions runners for faster hardware. 5) Enable Gradle configuration cache. 6) Migrate KAPT to KSP. 7) Modularize so only changed modules recompile. Targeting 5–8 min for PR builds is reasonable.
8. What is a staged rollout and why is it important?
Senior⌄
A staged rollout releases a new version to a percentage of users first. Start at 1–10%, monitor crash rates in Firebase Crashlytics and ANR rates in Play Console for 24–48 hours, then expand to 50% then 100%. If crash rate spikes, halt the rollout and the previous version remains for un-updated users. This limits blast radius of production bugs. Always have monitoring set up BEFORE initiating a rollout — you need real-time crash alerts.
9. How does Fastlane's supply action work with Play Store?
Senior⌄
Fastlane's supply uses the Google Play Android Developer API. You create a service account in Google Cloud Console, grant it access to Play Console, download the JSON key, and store it as a secret. upload_to_play_store uses this JSON to authenticate and upload AABs. It supports specifying track (internal/alpha/beta/production), rollout percentage, changelogs, and screenshots. Can also promote between tracks without uploading a new binary.
10. How do you set up test coverage enforcement in CI?
Scenario⌄
Enable JaCoCo in Android build config. Run ./gradlew jacocoTestReport in CI. Upload the XML report to Codecov or SonarQube. In SonarQube, configure a quality gate that fails if coverage drops below the threshold (e.g., 75%). In GitHub Actions, the Codecov action posts coverage % as a PR comment and can fail the check on coverage decrease. This creates a ratchet — coverage can only stay the same or improve over time.
10. Practical Lab: Design a Reliable Android Pipeline

Goal: draw the path from a pull request to a releasable artifact, including failures and recovery. Apply the commands to a sample Android repository; this study website itself is not an Android build.

Separate verification from release

StageChecks and outputsTrust boundary
Pull requestLint, JVM tests, debug build; preserve reports even after failureNo signing or publishing credentials; read-only repository permissions
IntegrationEmulator/device tests for important journeys; defined API levelsUse synthetic test accounts and controlled services
ReleaseApproved commit, signed AAB, version checks, staged rolloutProtected environment and reviewed approval policy
./gradlew :app:lintDebug :app:testDebugUnitTest :app:assembleDebug
# Requires a running emulator or attached test device:
./gradlew :app:connectedDebugAndroidTest

Passing a debug build does not prove release behavior: test the release variant's shrinking, manifests and configuration before distribution. Retain lint/test reports, commit identity and artifact provenance. Choose report retention deliberately instead of keeping artifacts indefinitely.

Diagnose failures, not just retry them

  • Works locally, fails on CI: compare the wrapper, JDK, SDK packages, environment variables and task names.
  • Fork pull request fails to sign: signing does not belong in its verification job. Keep release credentials in the trusted release workflow.
  • Flaky emulator test: collect logs and failure evidence; replace fixed sleeps with synchronization. Track flakiness rather than rerunning until green.
  • Cache makes an incorrect build pass: compare against a fresh run, inspect inputs and restrict who can write shared caches.
  • Rollout regression: halt expansion, investigate crash/ANR and functional signals, and prepare a tested replacement. Do not assume users can automatically downgrade an installed version.

Pipeline safety and efficiency

Use pull_request for untrusted PR checks. Do not execute untrusted PR code in a privileged pull_request_target workflow. Review action sources and pin production actions to reviewed full commit SHAs. Set bounded job timeouts, cancel superseded verification runs, and upload diagnostics with if: always(). Gradle's setup action manages Gradle caching; avoid stacking multiple cache owners for the same directory.

Interview exercise

A team has a 15-minute pipeline and frequent release incidents. Propose measurable improvements: fail fast on cheap checks, identify the slowest stage, split verification and publishing, define release gates, and track queue time, duration, flake rate and escaped defects. Explain the trade-off before adding parallel jobs or broad caches.
