1. Overview

What is Room?

Room is Google's ORM (Object-Relational Mapping) library built on top of SQLite. It provides compile-time query verification, type-safe access to the database, and seamless integration with Kotlin Flow and coroutines.

ComponentAnnotationResponsibility
Entity@Entity(tableName = "orders")Defines a database table — maps a data class to a table row
DAO@DaoData Access Object — interface with query methods
Database@Database(entities=[...], version=1)Creates/manages the SQLite database file
Senior Mental Model
Room's biggest advantage over raw SQLite: compile-time query verification. If your SQL has a typo, references a non-existent column, or returns the wrong type, the build fails. This catches data access bugs before they reach production. The Flow integration turns a static SQL query into a live, reactive data source.

2. How It Works

@Entity — Table Definition

@Entity(
    tableName = "transactions",
    indices = [Index(value = ["account_id"]),  // speed up queries by accountId
               Index(value = ["transaction_date"])]
)
data class TransactionEntity(
    @PrimaryKey val id: String,
    @ColumnInfo(name = "account_id") val accountId: String,
    @ColumnInfo(name = "amount_cents") val amountCents: Long,
    @ColumnInfo(name = "transaction_date") val date: LocalDate,  // needs TypeConverter
    @ColumnInfo(name = "status") val status: TransactionStatus  // needs TypeConverter
)

@TypeConverter — Custom Types

class Converters {
    @TypeConverter
    fun fromLocalDate(date: LocalDate): String = date.toString()  // ISO-8601
    @TypeConverter
    fun toLocalDate(value: String): LocalDate = LocalDate.parse(value)

    @TypeConverter
    fun fromStatus(status: TransactionStatus) = status.name
    @TypeConverter
    fun toStatus(value: String) = TransactionStatus.valueOf(value)
}

@Dao — Data Access Object

@Dao
interface TransactionDao {
    // Flow — re-emits automatically when table changes
    @Query("SELECT * FROM transactions WHERE account_id = :accountId ORDER BY transaction_date DESC")
    fun getTransactions(accountId: String): Flow<List<TransactionEntity>>

    // Suspend — for one-shot operations
    @Query("SELECT * FROM transactions WHERE id = :transactionId")
    suspend fun getTransaction(transactionId: String): TransactionEntity?

    @Insert(onConflict = OnConflictStrategy.REPLACE)
    suspend fun insertAll(transactions: List<TransactionEntity>)

    @Update
    suspend fun update(transaction: TransactionEntity): Int  // returns rows affected

    @Delete
    suspend fun delete(transaction: TransactionEntity)

    @Query("DELETE FROM transactions WHERE account_id = :accountId")
    suspend fun deleteByAccount(accountId: String)

    // @Transaction — multiple queries in one atomic operation
    @Transaction
    @Query("SELECT * FROM transactions WHERE account_id = :accountId")
    fun getTransactionsWithDetails(accountId: String): Flow<List<TransactionWithDetails>>
}

@Relation — One-to-Many and Many-to-Many

// One-to-Many: Account has many Transactions
data class AccountWithTransactions(
    @Embedded val account: AccountEntity,
    @Relation(parentColumn = "id", entityColumn = "account_id")
    val transactions: List<TransactionEntity>
)
// Must mark DAO query as @Transaction — Room fetches both in one atomic operation
@Transaction
@Query("SELECT * FROM accounts WHERE id = :accountId")
suspend fun getAccountWithTransactions(accountId: String): AccountWithTransactions?

// Many-to-Many: Order can have many Products; Product can be in many Orders
@Entity(primaryKeys = ["order_id", "product_id"])
data class OrderProductCrossRef(
    @ColumnInfo(name = "order_id") val orderId: String,
    @ColumnInfo(name = "product_id") val productId: String
)
data class OrderWithProducts(
    @Embedded val order: OrderEntity,
    @Relation(parentColumn = "id", entityColumn = "product_id",
              associateBy = Junction(OrderProductCrossRef::class))
    val products: List<ProductEntity>
)

@Database and Migrations

@Database(
    entities = [TransactionEntity::class, AccountEntity::class, OrderProductCrossRef::class],
    version = 3,
    exportSchema = true  // exports schema JSON to assets — track in git
)
@TypeConverters(Converters::class)
abstract class AppDatabase : RoomDatabase() {
    abstract fun transactionDao(): TransactionDao
    abstract fun accountDao(): AccountDao
}

// Migration 2→3: add index on transaction_date
val MIGRATION_2_3 = object : Migration(2, 3) {
    override fun migrate(database: SupportSQLiteDatabase) {
        database.execSQL("CREATE INDEX index_transactions_transaction_date ON transactions (transaction_date)")
    }
}

// Database builder — in Hilt module
Room.databaseBuilder(context, AppDatabase::class.java, "app.db")
    .addMigrations(MIGRATION_1_2, MIGRATION_2_3)
    .fallbackToDestructiveMigration()  // ⚠️ dev only — wipes data if migration missing
    .build()

Full-Text Search (FTS)

// FTS4 virtual table — enables fast full-text search
@Fts4(contentEntity = ProductEntity::class)
@Entity(tableName = "products_fts")
data class ProductFtsEntity(
    @PrimaryKey @ColumnInfo(name = "rowid") val rowId: Int,
    val name: String,
    val description: String
)

// FTS search query — MATCH operator
@Query("SELECT * FROM products JOIN products_fts ON products.rowid = products_fts.rowid WHERE products_fts MATCH :query")
suspend fun searchProducts(query: String): List<ProductEntity>

3. When to Use

Room is the Right Choice for

  • Any structured relational data that must be queried, filtered, or sorted
  • Offline-first apps where the database is the single source of truth
  • Large data sets with millions of rows where query performance matters
  • Complex relationships between entities (one-to-many, many-to-many)

Use @Transaction When

  • Fetching a parent entity and its related child entities — prevents inconsistent reads
  • Writing multiple related records atomically — either all succeed or all fail
  • Any multi-step operation that must be atomic (e.g., delete then re-insert)

Room + Flow

Reactive Database
When a DAO method returns Flow<List<T>>, Room automatically observes the table for changes. Every INSERT, UPDATE, or DELETE to the observed table triggers a new emission. This is what makes the offline-first pattern work — the UI never polls; it just reacts to database changes.

4. Production Example

E-Commerce App — Orders with Products

// ── Entities ─────────────────────────────────────────────────
@Entity(tableName = "orders", indices = [Index("user_id"), Index("created_at")])
data class OrderEntity(
    @PrimaryKey val id: String,
    @ColumnInfo(name = "user_id") val userId: String,
    @ColumnInfo(name = "total_cents") val totalCents: Long,
    @ColumnInfo(name = "status") val status: String,
    @ColumnInfo(name = "created_at") val createdAt: Instant  // TypeConverter needed
)

// ── DAO ───────────────────────────────────────────────────────
@Dao
interface OrderDao {
    @Transaction
    @Query("SELECT * FROM orders WHERE user_id = :userId ORDER BY created_at DESC")
    fun getOrdersWithProducts(userId: String): Flow<List<OrderWithProducts>>

    @Transaction
    suspend fun upsertOrderWithItems(order: OrderEntity, items: List<OrderItemEntity>) {
        upsertOrder(order)
        deleteOrderItems(order.id)
        insertOrderItems(items)
    }

    @Insert(onConflict = OnConflictStrategy.REPLACE)
    suspend fun upsertOrder(order: OrderEntity)

    @Query("DELETE FROM order_items WHERE order_id = :orderId")
    suspend fun deleteOrderItems(orderId: String)

    @Insert
    suspend fun insertOrderItems(items: List<OrderItemEntity>)
}

// ── Repository using the DAO ──────────────────────────────────
class OrderRepositoryImpl @Inject constructor(
    private val dao: OrderDao,
    private val api: OrderApi
) : OrderRepository {

    override fun getOrders(userId: String): Flow<List<Order>> =
        dao.getOrdersWithProducts(userId).map { it.map(OrderWithProducts::toDomain) }
            .onStart { refreshOrders(userId) }

    private suspend fun refreshOrders(userId: String) {
        runCatching { api.getOrders(userId) }
            .onSuccess { orders ->
                orders.forEach { dto ->
                    dao.upsertOrderWithItems(dto.toEntity(), dto.items.map(OrderItemDto::toEntity))
                }
            }
    }
}

6. Pitfalls & Best Practices

Common Mistakes

Querying on Main Thread
Room throws IllegalStateException: Cannot access database on the main thread if you call a non-Flow, non-suspend DAO method on the main thread. Always use suspend fun or Flow. Never call .allowMainThreadQueries() in production — it blocks UI rendering.
@Relation without @Transaction
Loading a parent + its children requires at least two SQL queries. Without @Transaction, another thread could modify a child between the two queries, giving you an inconsistent result. Always add @Transaction to any DAO method that returns a type with @Relation.

Database Migration Best Practices

  • Set exportSchema = true — tracks the schema JSON file in git. This lets you verify migrations haven't missed columns
  • Write migration tests using MigrationTestHelper from Room's test dependency
  • Never use fallbackToDestructiveMigration() in production builds
  • Always run migrations on a background thread (Room handles this, but ensure you're not blocking the main thread during startup)

@Index Best Practices

  • Add indexes on foreign key columns (e.g., account_id on the transactions table)
  • Add indexes on columns used in WHERE clauses in frequent queries
  • Indexes slow down INSERT/UPDATE/DELETE — don't index every column

7. Interview Framework

30-Second Answer

"Room is Android's SQLite ORM with three main components: @Entity maps a data class to a database table, @Dao is an interface with annotated query methods, and @Database ties everything together and provides DAO instances. The key advantage over raw SQLite: queries are verified at compile time — a typo in your SQL is a build error, not a runtime crash. Returning Flow<List<T>> from a DAO makes it reactive — the Flow re-emits whenever the underlying table changes."

2-Minute Deep Dive

"For relations: @Relation maps a one-to-many or many-to-many relationship. Always pair it with @Transaction — loading a parent and its children requires two queries, and without a transaction another thread could modify the children between queries giving you an inconsistent result. For custom types like LocalDate or enums, use @TypeConverter to convert to/from a SQLite-supported type. For migrations: write explicit Migration objects for every version bump — never use fallbackToDestructiveMigration in production. For performance: add @Index on foreign key columns and frequently queried columns. For FTS: @Fts4 creates a virtual table that enables fast full-text search with the MATCH operator."

Must-Mention Points

1
Compile-time query verification: SQL typos and type mismatches are build errors
2
Flow reactive queries: Room auto-re-emits when the queried table changes
3
@Transaction required with @Relation: prevents inconsistent reads across multiple queries
4
@TypeConverter: converts non-primitive types (LocalDate, enums, BigDecimal)
5
Migration objects: never fallbackToDestructiveMigration in production
6
@Index on foreign keys: critical for query performance on large tables

Do NOT Go Deeper On

  • Paging 3 + Room integration (separate topic — PagingSource)
  • Room's code generation internals (just say "annotation processing")
  • WAL mode details (mention it exists for multi-process access if asked)

Follow-up Q&A

QuestionAnswer
"How does Room emit Flow updates?"Room registers an InvalidationTracker.Observer on the queried tables. When a write occurs to any tracked table, Room posts an update, and the Flow collector re-runs the query and emits the new result.
"What is @Embedded used for?"Flattens a nested object's fields into the parent table. Unlike @Relation (separate query), @Embedded is part of the same row. Used for ValueObjects like Address embedded in a UserEntity.
"What happens if a migration is missing?"Room throws IllegalStateException: A migration from version X to Y was required but not found on database open. Without fallbackToDestructiveMigration, the app crashes. With it, the database is wiped and recreated.

Senior Insight

Senior Signal
The @Transaction-with-@Relation requirement is the most commonly missed Room concept. Room's relation loading is not a JOIN — it's multiple separate queries. Without a transaction wrapping them, you have a TOCTOU (time-of-check-to-time-of-use) race condition. Mentioning this demonstrates real-world Room knowledge beyond the happy path.

9. Interview Questions
Basic What are the three main components of Room and what does each do? ⌄
@Entity: annotates a data class to define a database table. Fields map to columns. @PrimaryKey defines the primary key; @ColumnInfo customises column names.

@Dao: interface that defines methods to interact with the table. Methods are annotated with @Query, @Insert, @Update, or @Delete. Room generates the implementation at compile time.

@Database: abstract class extending RoomDatabase. Declares all entities, the database version, and abstract methods returning DAO instances. Built via Room.databaseBuilder().
Basic How does Room's Flow integration work? ⌄
When a DAO method returns Flow<List<T>>, Room wraps the query in an InvalidationTracker observer. Whenever a row in the queried table is inserted, updated, or deleted, Room marks the table as invalid and re-runs the query. The new result is emitted to all active collectors. This makes Room queries reactive — the UI doesn't need to manually refresh; it just collects the Flow and reacts to emissions.
Basic What is a TypeConverter and when do you need one? ⌄
SQLite natively supports: INTEGER, REAL, TEXT, BLOB, and NULL. For any other type — LocalDate, Instant, BigDecimal, enums, List<String> — you need a TypeConverter. A TypeConverter class has two methods: one converting FROM the Kotlin type TO a SQLite-supported type, and one converting back. Register it with @TypeConverters(Converters::class) on the @Database class.
Intermediate Why must @Relation DAO methods be annotated with @Transaction? ⌄
Room's @Relation is NOT a SQL JOIN. It executes multiple SQL queries: one to fetch the parent entities, then one (or more) separate queries to fetch the related children. Between these two queries, another thread could write to the child table — you might get a parent with outdated children or missing children. @Transaction wraps all these queries in a single SQLite transaction, ensuring you get a consistent snapshot of the database at a single point in time.
Intermediate How do you add a column to a Room table in an existing production app? ⌄
1. Add the new column to the @Entity data class. If nullable: val notes: String? = null; if non-nullable, provide a default.
2. Increment the @Database(version = N+1).
3. Write a Migration: val MIGRATION_N_N1 = object : Migration(N, N+1) { override fun migrate(db) { db.execSQL("ALTER TABLE my_table ADD COLUMN notes TEXT") } }.
4. Register: Room.databaseBuilder(...).addMigrations(MIGRATION_N_N1).build().
5. Test with MigrationTestHelper to verify migration works on the old schema.
Never use fallbackToDestructiveMigration in production — it destroys all user data.
Intermediate What is @Fts4 and when would you use it? ⌄
@Fts4 creates an SQLite FTS (Full-Text Search) virtual table. Regular SQL LIKE '%query%' performs a full table scan — O(n) on every search. FTS creates an inverted index, enabling fast token-based searches with the MATCH operator. Use it when: users type search queries against large text content (product descriptions, notes, messages), you need relevance ranking, or you need prefix matching. Trade-off: FTS tables don't support standard SQL operations like JOIN directly — you typically JOIN back to the original table via rowid.
Intermediate Explain the difference between @Embedded and @Relation. ⌄
@Embedded: flattens a nested object's fields directly into the same table row. @Embedded val address: Address means Address's fields (street, city, zip) are columns in the parent table. One row, one query. Good for value objects that belong to one entity.

@Relation: represents a relationship between two different tables. Room runs separate queries for parent and children. Requires @Transaction. Good for one-to-many or many-to-many associations where children are stored in a separate table with a foreign key.
Senior Design the Room schema for a banking app with accounts, transactions, and categories. ⌄
AccountEntity: PK=id, userId, name, type (CHECKING/SAVINGS), balanceCents. Index on userId.

TransactionEntity: PK=id, FK=accountId, FK=categoryId (nullable), amountCents, type (DEBIT/CREDIT), description, date (Instant→TypeConverter), status. Index on accountId, date.

CategoryEntity: PK=id, name, iconName, color.

Relations: AccountWithTransactions(@Embedded account, @Relation transactions). TransactionWithCategory(@Embedded transaction, @Relation category). Both DAOs methods annotated with @Transaction.

Indexes: account_id on transactions (FK queries), date on transactions (sort/filter), userId on accounts.

TypeConverters: Instant, TransactionType enum, TransactionStatus enum.
Senior What happens at compile time when Room processes your DAO annotations? ⌄
Room uses an annotation processor (KSP or kapt). For each DAO interface, Room:

1. Parses SQL strings: validates syntax, resolves column names against the @Entity field names, checks that return types match query result types. A SELECT * FROM orders WHERE uer_id = :id typo is caught here.
2. Generates a concrete implementation class: e.g., OrderDao_Impl. For Flow methods, the generated code wraps the query in RoomTrackingLiveData / CoroutinesRoom.createFlow() with the table invalidation tracker.
3. Generates the Database implementation: AppDatabase_Impl that creates tables, runs migrations, and returns DAO instances.
4. Validates relationships: ensures @Relation column names exist in the referenced entities.
Any error (bad SQL, missing column, type mismatch) is a compile error — not a runtime crash.
Senior A query that was fast in development is slow in production with 100k rows. How do you investigate? ⌄
1. EXPLAIN QUERY PLAN: run the SQL with EXPLAIN QUERY PLAN prefix on the production database (copy it to dev). Look for "SCAN TABLE" (full scan) vs "SEARCH TABLE USING INDEX" (fast). Full scans on large tables = missing index.

2. Add @Index: on the column(s) in the WHERE clause. Re-run EXPLAIN QUERY PLAN to verify it uses the index.

3. Check query complexity: multiple JOINs or nested SELECT → consider a denormalised view or restructuring the query.

4. Room profiling: enable SQLite WAL mode and use Android Studio's Database Inspector to trace query execution times.

5. Paging: if the query returns large lists, paginate with Paging 3 — never load 100k rows at once.
