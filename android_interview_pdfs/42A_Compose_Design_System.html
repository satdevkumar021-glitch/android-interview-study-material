42A — Compose Design System & Multi-Brand Theming

CompositionLocal, design tokens, MaterialTheme customisation, and how to support multiple brands from a single Compose codebase — the architecture behind scalable UI systems.

ID: 42A ⭐ Tier 1 🔥 Hot
🔍
1. Overview

What Is a Design System?

A design system is a shared language between designers and engineers consisting of three interlocking layers:

  • Design Tokens — the raw primitives: colors, typography scales, spacing values, corner radii. These are pure data, not UI code.
  • Component Library — reusable Composables that consume tokens. A PrimaryButton reads buttonBackground from the token set; it never hardcodes Color(0xFF6200EE).
  • Screen Compositions — product screens assembled from components. They contain layout and business logic, not visual decisions.

Why Multi-Brand Matters

Enterprise products increasingly deliver one codebase, multiple visual identities. Examples from production:

  • Acme Corp — two product lines have different brand colours, logo assets, and typographic tone but share all checkout, account, and loyalty screens.
  • Automotive super-app — 14 vehicle brands (each with distinct primary colour, logo, typography, and tone) running from a single Compose codebase. Each brand supplies its own token set as a data object injected at startup — zero UI code duplication.
  • Banking super-apps — white-label banking apps where each bank provides its colour palette and font; the underlying transaction, card, and KYC flows are identical.

The Three-Layer Architecture

LayerContentsBrand-specific?
Design TokensColorTokens, TypographyTokens, SpacingTokens data classes✅ Yes — each brand has its own instance
Component LibraryPrimaryButton, Card, AppBar, TextField composables❌ No — reads tokens via CompositionLocal
Screen CompositionsHomeScreen, CheckoutScreen, ProfileScreen❌ No — assembles components
Senior Mental Model
The key insight is that brand identity is data, not code. Your composables never know which brand they're rendering for — they just consume tokens from CompositionLocal. Swapping brands is swapping the data, not rewriting components. A component that reads LocalBrandColors.current.primary works for all 14 brands without a single if (brand == BRAND_X) branch.

Real-World Scale

In a real-world multi-brand automotive app, a single :design-system module maintains ~80 composable components. Each of the 14 brand modules contributes a 400-line Kotlin file that is entirely data: colours, fonts, spacing, icon drawables. No UI code is duplicated across brands. A new brand launch is a new data file + Gradle flavour — the entire app is production-ready in days, not months.

2. CompositionLocal API

What Is CompositionLocal?

CompositionLocal is Compose's mechanism for implicit parameter passing. Instead of threading a value through every function signature, you provide it once at a high level and any descendant composable can read it. Think of it as a typed, scoped global that is safe to use in the composition tree.

Compose's own MaterialTheme, LocalContext, LocalDensity, and LocalFocusManager are all built on this exact mechanism.

Two Factory Functions

FactoryRecomposition ScopeWhen to Use
compositionLocalOf { }Only composables that read the value recompose on changeValues that change during a session (e.g. dark/light mode toggle, locale)
staticCompositionLocalOf { }Entire subtree below the provider recomposes on changeStable values set once at startup (e.g. entire brand config object)
Performance Note
staticCompositionLocalOf causes the entire subtree to recompose when the value changes. For brand config (set once at startup and never changed), this is perfectly fine — the cost is paid once. For frequently changing values (e.g. scroll offset), always use compositionLocalOf instead.

Reading and Providing Values

  • Reading: LocalSomething.current — reads the nearest provided value in the composition tree.
  • Providing: CompositionLocalProvider(LocalSomething provides value) { content() } — scopes the value to all descendants in the content lambda.

Full Example: Brand Color CompositionLocal

// 1. Define the token data class
data class BrandColors(
    val primary: Color,
    val secondary: Color,
    val surface: Color,
    val onPrimary: Color,
    val onSurface: Color,
    val error: Color,
    val logo: Int // drawable resource ID
)

// 2. Create the CompositionLocal with a sensible default (fallback / preview)
val LocalBrandColors = staticCompositionLocalOf {
    BrandColors(
        primary    = Color(0xFF1C1C1E),
        secondary  = Color(0xFF56CFB2),
        surface    = Color(0xFF0F1117),
        onPrimary  = Color.White,
        onSurface  = Color(0xFFE2E4F0),
        error      = Color(0xFFFF6B6B),
        logo       = R.drawable.logo_default
    )
}

// 3. Read the token anywhere in the composition tree
@Composable
fun PrimaryButton(text: String, onClick: () -> Unit) {
    val colors = LocalBrandColors.current  // no parameter needed
    Button(
        onClick = onClick,
        colors = ButtonDefaults.buttonColors(
            containerColor = colors.primary,
            contentColor   = colors.onPrimary
        )
    ) { Text(text) }
}

// 4. Provide a brand-specific value at the root
@Composable
fun BrandARoot(content: @Composable () -> Unit) {
    val brandAColors = BrandColors(
        primary   = Color(0xFFE63946), // Brand A primary
        secondary = Color(0xFF457B9D), // Brand A secondary
        surface   = Color(0xFFFFFFFF),
        onPrimary = Color.White,
        onSurface = Color(0xFF1C1C1E),
        error     = Color(0xFFD32F2F),
        logo      = R.drawable.logo_brand_a
    )
    CompositionLocalProvider(LocalBrandColors provides brandAColors) {
        content()
    }
}

Overriding in Subtrees (Nested Providers)

CompositionLocal scoping is hierarchical. You can narrow a scope within a larger tree — for example, a dark-mode preview card inside a light-mode screen can wrap its content in a new provider:

@Composable
fun DarkPreviewCard(content: @Composable () -> Unit) {
    val current = LocalBrandColors.current
    // Override only surface/onSurface for the dark preview
    CompositionLocalProvider(
        LocalBrandColors provides current.copy(
            surface   = Color(0xFF1C1C1E),
            onSurface = Color.White
        )
    ) { content() }
}
Interview Tip
Interviewers love to ask: "How does a deeply nested composable get a value without prop-drilling?" The answer is CompositionLocal. Know the API, know when to use static vs dynamic, and give a concrete example like brand theming.

3. Brand Token Architecture

Three-Level Token Hierarchy

The industry-standard approach (from the W3C Design Token Community Group, adopted by Figma, Salesforce Lightning, and Material Design 3) uses three levels:

LevelDescriptionExample
Global tokensRaw palette values — all possible colors in the systemColor(0xFFC8102E), Color(0xFFFFFFFF)
Alias tokensSemantic meaning mapped to globalsprimary = brandRed, surface = white
Component tokensComponent-specific slots mapped to alias tokensbuttonBackground = primary, cardBorderColor = border
Why This Hierarchy Matters
When the design team changes "primary = #C8102E" to "#B50024" in one place, every button, header, and active state that uses the primary alias automatically updates across all 80 components — no search-and-replace, no missed spots.

4. MaterialTheme Deep Dive

MaterialTheme Is Just CompositionLocal

Internally, MaterialTheme is nothing magical — it's a composable that provides several CompositionLocals:

// Simplified internals of MaterialTheme (actual Compose source)
@Composable
fun MaterialTheme(
    colorScheme: ColorScheme = MaterialTheme.colorScheme,
    typography:  Typography  = MaterialTheme.typography,
    shapes:      Shapes      = MaterialTheme.shapes,
    content:     @Composable () -> Unit
) {
    CompositionLocalProvider(
        LocalColorScheme  provides colorScheme, // → MaterialTheme.colorScheme
        LocalTypography   provides typography,  // → MaterialTheme.typography
        LocalShapes       provides shapes,       // → MaterialTheme.shapes
        content = content
    )
}

This means you can feed your BrandTheme tokens directly into MaterialTheme and every Material component (Button, Card, TextField, TopAppBar) automatically respects your brand colours.

Mapping BrandTheme → Material ColorScheme

fun BrandTheme.toColorScheme(): ColorScheme = darkColorScheme(
    primary          = colors.primary,
    onPrimary        = colors.onPrimary,
    primaryContainer = colors.primaryVariant,
    secondary        = colors.secondary,
    onSecondary      = colors.onSecondary,
    background       = colors.background,
    onBackground     = colors.onBackground,
    surface          = colors.surface,
    onSurface        = colors.onSurface,
    surfaceVariant   = colors.surfaceVariant,
    error            = colors.error,
    onError          = colors.onError,
    outline          = colors.outline
)

fun BrandTheme.toMaterialTypography(): Typography = Typography(
    displayLarge   = typography.displayLarge,
    headlineMedium = typography.headlineMedium,
    titleLarge     = typography.titleLarge,
    bodyMedium     = typography.bodyMedium,
    labelSmall     = typography.labelSmall
)

fun BrandTheme.toMaterialShapes(): Shapes = Shapes(
    small  = shapes.small,
    medium = shapes.medium,
    large  = shapes.large
)

The Full Root Composable

@Composable
fun MultiApp(brand: Brand = Brand.BRAND_A) {

Custom Token Access Pattern

Always provide a type-safe accessor object so callsites are ergonomic:

// Accessor object — mirrors MaterialTheme's API style
object BrandTheme {
    val colors: ColorTokens
        @Composable
        @ReadOnlyComposable
        get() = LocalBrandColors.current

    val typography: TypographyTokens
        @Composable
        @ReadOnlyComposable
        get() = LocalBrandTypography.current

    val spacing: SpacingTokens
        @Composable
        @ReadOnlyComposable
        get() = LocalBrandSpacing.current
}

// Usage inside any composable — clean and discoverable:
@Composable
fun ProductCard(name: String, price: String) {
    Card(
        colors = CardDefaults.cardColors(containerColor = BrandTheme.colors.surface),
        modifier = Modifier.padding(BrandTheme.spacing.md)
    ) {
        Text(name,  style = BrandTheme.typography.titleLarge)
        Text(price, style = BrandTheme.typography.bodyMedium)
    }
}

5. Multi-Brand in Practice

Runtime Brand Switching

Some apps allow the user to switch brand context mid-session (e.g., a dealer app that shows inventory for multiple vehicle brands). The pattern is:

  1. Hold the active Brand in a StateFlow inside a ViewModel
  2. Collect it in the root composable with collectAsStateWithLifecycle()
  3. Pass it to the root theme wrapper — Compose re-runs the provider with the new token set
// BrandViewModel.kt
@HiltViewModel
class BrandViewModel @Inject constructor(
    private val brandPrefs: BrandPreferences
) : ViewModel() {

    private val _activeBrand = MutableStateFlow(brandPrefs.getSavedBrand())
    val activeBrand: StateFlow<Brand> = _activeBrand.asStateFlow()

    fun switchBrand(brand: Brand) {
        _activeBrand.value = brand
        brandPrefs.saveBrand(brand)
    }
}

// MainActivity.kt
class MainActivity : ComponentActivity() {
    private val brandVm: BrandViewModel by viewModels()

    override fun onCreate(savedInstanceState: Bundle?) {
        super.onCreate(savedInstanceState)
        setContent {
            val brand by brandVm.activeBrand.collectAsStateWithLifecycle()
            MultiApp(brand = brand)
        }
    }
}

Build Flavour Approach (Static Brand Selection)

When each AAB is always for a single brand (e.g. "BrandA App" on Play Store vs "BrandB App"), use product flavours:

// build.gradle.kts (app module)
android {
    flavorDimensions("brand")
    productFlavors {
        create("brand-b") {
            dimension("brand")
            applicationId = "com.example.branda"
            buildConfigField("String", "BRAND_ID", "\"BRAND_C\"")
        }
        create("brand-d") {
            dimension("brand")
            applicationId = "com.example.brandb"
            buildConfigField("String", "BRAND_ID", "\"BRAND_D\"")
        }
    }
}

// In MainActivity — brand is statically determined at build time
val brand = Brand.valueOf(BuildConfig.BRAND_ID)
setContent { BrandApp(brand = brand) }

Hilt Dependency Injection Approach

For maximum flexibility, inject the BrandTheme directly via Hilt. The brand module provides its own Hilt module:

// In :brand-b module
@Module
@InstallIn(SingletonComponent::class)
object BrandBThemeModule {
    @Provides
    @Singleton
    fun provideBrandTheme(): BrandTheme = brandBTheme()
}

// Root composable reads the injected theme
@HiltViewModel
class ThemeViewModel @Inject constructor(
    val brandTheme: BrandTheme
) : ViewModel()

@Composable
fun AppRoot(themeVm: ThemeViewModel = hiltViewModel()) {
    val theme = themeVm.brandTheme
    CompositionLocalProvider(
        LocalBrandColors     provides theme.colors,
        LocalBrandTypography provides theme.typography,
        LocalBrandSpacing    provides theme.spacing
    ) {
        MaterialTheme(
            colorScheme = theme.toColorScheme(),
            typography  = theme.toMaterialTypography()
        ) { AppNavHost() }
    }
}

"In a multi-brand app I worked on, the base app module had no brand knowledge whatsoever. Each brand module (e.g. :brand-premium, :brand-economy) injected its token set via Hilt at app startup. The NavHost wrapped everything in CompositionLocalProvider with that brand's tokens. We could build brand-specific AABs from the same source tree with just a Gradle flavour switch. CI produced all brand APKs from one pipeline run."

Why Separate :design-system-tokens from :design-system-components?

  • Compile isolation: Brand token modules have zero Compose transitive dependencies. Pure Kotlin JVM modules compile in milliseconds and can be unit-tested without Robolectric.
  • Designer handoff: Designers export Figma tokens as JSON, a script generates ColorTokens data classes, and the change lands in :tokens only — no component code is touched.
  • Testability: Token correctness is testable as pure Kotlin assertions: assertEquals(Color(0xFFC8102E), brandATheme().colors.primary).

The Catalog App (Storybook for Android)

A :catalog module is a standalone debug APK that renders every component in every brand theme side by side. Benefits:

  • QA and designers can review all brand permutations without running the full app
  • Catches token mismatches at design-review time, not production
  • Can be used for automated screenshot tests: render every component × every brand, compare to golden images
@Composable
fun CatalogScreen() {
    LazyColumn {
        Brand.entries.forEach { brand ->
            val theme = BrandRegistry.get(brand)
            item {
                Text(brand.name, style = MaterialTheme.typography.titleLarge,
                     modifier = Modifier.padding(16.dp))
            }
            item {
                CompositionLocalProvider(
                    LocalBrandColors     provides theme.colors,
                    LocalBrandTypography provides theme.typography,
                    LocalBrandSpacing    provides theme.spacing
                ) {
                    MaterialTheme(colorScheme = theme.toColorScheme()) {
                        ComponentShowcase() // renders buttons, cards, inputs
                    }
                }
            }
        }
    }
}

Component Contract

Every component in :design-system-components must satisfy this contract:

  • ❌ No hardcoded Color values in the component body
  • ❌ No direct reference to MaterialTheme.colorScheme.primary for brand-differentiated visuals
  • ✅ All visual values read from LocalBrandColors.current, LocalBrandTypography.current, LocalBrandSpacing.current
  • ✅ Component is @Preview-able with an explicit brand provider (no ambient magic needed for previews)

7. Pitfalls & Best Practices

Common Mistakes

❌ Pitfall 1 — Hardcoded Colors in Components

Writing Color.Red or Color(0xFFFF0000) directly inside a component body silently breaks brand theming. The component will ignore whatever the brand token says for error.

// ❌ WRONG — hardcoded, brand-unaware
fun ErrorText(msg: String) = Text(msg, color = Color.Red)

// ✅ CORRECT — brand-aware
fun ErrorText(msg: String) = Text(msg, color = LocalBrandColors.current.error)
❌ Pitfall 2 — Reading MaterialTheme.colorScheme.primary When You Need Brand Primary

If you use MaterialTheme.colorScheme.primary in a custom component and the brand adds a custom brandPrimary that diverges from M3's primary (e.g. for a gradient button), the component silently shows the wrong colour. Always read from your own LocalBrandColors.current.primary in custom components.

❌ Pitfall 3 — staticCompositionLocalOf for Frequently Changing Values

Using staticCompositionLocalOf for a value that changes frequently (e.g. a scroll position, a counter, a dark/light toggle that users can flip 10 times per minute) will cause the entire subtree below the provider to recompose every time. For volatile values, use compositionLocalOf — only the composables that actually read the value recompose.

❌ Pitfall 4 — Forgetting to Test Each Brand Theme

Token mismatches only appear at runtime — a brand might accidentally set onPrimary = Color.Black when the button background is also dark, making text invisible. Without brand-specific screenshot tests, this ships to production. Write a parameterised screenshot test that covers all brands for every component.

Best Practices

✅ Always Read From Your CompositionLocal
Every component reads LocalBrandColors.current (or your BrandTheme.colors accessor). Never cache it outside the composable scope — let Compose handle recomposition correctly.
✅ Static for Brand Identity, Dynamic for Session Values
staticCompositionLocalOf for the full brand config object (changes once: at app startup or brand switch). compositionLocalOf for dark mode, locale, or any value that changes during a user session.
✅ Brand-Agnostic Screenshot Tests
Write one screenshot test per component that iterates over all brand themes: 
@RunWith(Parameterized::class)
class PrimaryButtonScreenshotTest(private val brand: Brand) {
    companion object {
        @JvmStatic @Parameterized.Parameters
        fun brands() = Brand.entries.toList()
    }
    @Test
    fun screenshotMatchesGolden() {
        val theme = BrandRegistry.get(brand)
        composeTestRule.setContent {
            CompositionLocalProvider(LocalBrandColors provides theme.colors) {
                PrimaryButton(text = "Order Now") {}
            }
        }
        composeTestRule.onRoot().captureRoboImage("golden/button_${brand.name}.png")
    }
}
✅ Keep Token Data Classes in Pure Kotlin Module
Token data classes must have zero Android framework dependencies. ColorTokens should use Compose's androidx.compose.ui.graphics.Color (which is multiplatform-ready), but no Context, no Resources, no @DrawableRes integers if you want maximum portability. Test them as fast JVM unit tests.

8. Interview Framework

30-Second Answer

"A design system in Compose is built on CompositionLocal. You define design tokens — colors, typography, spacing — as plain Kotlin data classes. Each brand provides its own token set. CompositionLocalProvider injects the correct tokens at the root of the composition tree. Every component reads LocalBrandColors.current — it has zero knowledge of which brand it's running under. Swapping brands means swapping one data object, not touching any component code."

2-Minute Answer (Expanded)

Build from the 30-second base and layer in:

  1. Token hierarchy: "We use three levels — global palette → semantic alias tokens → component tokens. This means a single change to primary propagates to every consumer automatically."
  2. staticCompositionLocalOf vs compositionLocalOf: "Brand config uses static because it's set once. Dark mode toggle uses dynamic because only the reading composables should recompose, not the whole tree."
  3. MaterialTheme integration: "We map our BrandTheme tokens into MaterialTheme's ColorScheme and Typography, so all Material components like Button and TextField automatically use brand colours without any extra wiring."
  4. Module structure: ":design-system-tokens is pure Kotlin — no Android deps. :design-system-components holds the composables. Each brand lives in its own :brand-X module that's just a data file + optional Hilt module."
  5. Build approach: "We use Gradle product flavours for static brand selection — each AAB is for one brand. For apps that support runtime switching, a ViewModel holds the active brand in a StateFlow and the root composable collects it with collectAsStateWithLifecycle."
  6. Testing: "We have a parameterised screenshot test for every component that iterates over all brand themes. Token mismatches show up as golden file diffs in CI, not in production."

Must-Mention Checklist

CompositionLocal / staticCompositionLocalOf for stable brand config — know why static is appropriate and when to use the dynamic variant instead.

Q1. What is CompositionLocal and why is it used for theming in Compose?
Easy⌄

What to say: CompositionLocal is Compose's mechanism for passing values implicitly down the composition tree without threading them through every function parameter. It's like a scoped, typed ambient value.

For theming, it's ideal because the theme affects hundreds of composables across many layers of the tree. Without it, you'd need to pass colors: ColorTokens as a parameter to every single composable — including ones that just pass it through without using it (prop drilling). CompositionLocalProvider injects the value once at the root; any descendant reads it with LocalSomething.current.

"CompositionLocal provides implicit parameters to the composition tree. For theming, this avoids prop-drilling brand colors through every composable. The theme is provided once at the root, and any component anywhere in the tree reads it via LocalBrandColors.current. It's how MaterialTheme itself works under the hood."
Q2. What is the difference between compositionLocalOf and staticCompositionLocalOf?
Easy⌄

Key difference: recomposition scope.

  • compositionLocalOf { } — When the value changes, only the composables that read the local recompose. More granular and efficient for values that change during a session.
  • staticCompositionLocalOf { } — When the value changes, the entire subtree below the provider recomposes. The word "static" means Compose doesn't track individual read points — it assumes the value is stable.

When to use each: Use static for brand config (set once at startup, stable for the app lifetime). Use dynamic for dark/light mode, locale, or anything a user can toggle mid-session.

"staticCompositionLocalOf recomposes the whole subtree on change — acceptable for brand config that's set once. compositionLocalOf only recomposes the composables that actually read the value, so it's better for volatile data like dark mode state."
Q3. How would you support two brands with different primary colours from a single Compose codebase?
Medium⌄

Step-by-step answer:

  1. Define a ColorTokens data class with a primary: Color field (and all other tokens).
  2. Create a staticCompositionLocalOf<ColorTokens> with a default value.
  3. Create one instance of ColorTokens per brand with brand-specific values.
  4. At the root of the composition, wrap in CompositionLocalProvider(LocalColorTokens provides brandColors).
  5. In every component, read LocalColorTokens.current.primary — never hardcode colours.

For build-time selection use Gradle flavours; for runtime switching use a ViewModel StateFlow feeding the root provider.

"Define a ColorTokens data class, create staticCompositionLocalOf for it, instantiate one per brand, and provide the correct instance at the composition root. Components read LocalColorTokens.current.primary. Swapping brands is swapping the data object, no component code changes."
Q4. Where in the composition tree would you place CompositionLocalProvider for a multi-brand app?
Medium⌄

As high as possible — ideally wrapping the NavHost or the outermost content composable inside setContent { }.

It must be above any component that reads the local. If you place it inside a feature screen, only that screen's composables get the brand colours; the rest of the app falls back to the default value. In a multi-module app, the provider sits in the :app module's root composable, above the navigation graph.

Typically: Activity.setContent → BrandTheme wrapper → MaterialTheme → NavHost → screens

"At the very root — in setContent in MainActivity, wrapping MaterialTheme and NavHost. This ensures every screen and every component in the navigation graph inherits the brand tokens without any composable needing to know where the tokens came from."
Q5. A component deep in the tree needs a brand-specific logo drawable. How does it get it without passing a parameter through 10 composables?
Hard⌄

This is exactly the problem CompositionLocal solves. Include the logo drawable resource ID inside your BrandColors (or a dedicated BrandAssets) data class:

data class BrandColors(..., val logo: Int /* @DrawableRes */)

// Deep component — no parameter needed
@Composable
fun BrandLogo() {
    val logoRes = LocalBrandColors.current.logo
    Image(painterResource(logoRes), contentDescription = null)
}

The token set provided at the root includes the drawable resource. The deep component reads it without a single caller needing to thread the parameter. For more complex asset sets, create a separate BrandAssets data class provided via its own LocalBrandAssets.

"Include the logo drawable ID in the BrandColors token set. LocalBrandColors is already provided at the root, so any composable at any depth reads LocalBrandColors.current.logo — zero prop drilling, zero parameter threading."
Q6. Your design team adds a new token (errorSecondary). What's the safest way to roll it out without breaking existing brand implementations?
Hard⌄

Add the field with a default value in the data class. Because it's a data class with a Kotlin default, existing brand instantiations that don't yet specify errorSecondary will compile without changes:

data class ColorTokens(
    val error: Color,
    // New token — defaults to a safe fallback derived from existing token
    val errorSecondary: Color = error.copy(alpha = 0.6f)
)

Rollout plan:

  1. Add errorSecondary with a default to ColorTokens in :design-system-tokens.
  2. Use it in the new component in :design-system-components. All existing brands compile — they get the default.
  3. Each brand team progressively overrides the default with their correct brand value in their own :brand-X module.
  4. When all brands have explicitly set it, the default can optionally be removed (breaking change — communicate in advance).
"Add the token with a sensible default value derived from existing tokens — e.g., error.copy(alpha=0.6f). All existing brand implementations compile immediately. Each brand team can then explicitly set the correct value in their own module at their own pace, without a big-bang migration."
Q7. How does MaterialTheme relate to your custom brand token system? Should they coexist or replace each other?
Hard⌄

They should coexist, with your brand tokens feeding into MaterialTheme.

MaterialTheme provides LocalColorScheme, LocalTypography, LocalShapes — the same CompositionLocal mechanism. Material components (Button, Card, TextField, TopAppBar) read from MaterialTheme.colorScheme. If you completely bypass MaterialTheme, every Material component needs manual colour overrides — that's hundreds of lines of boilerplate.

The correct architecture:

  • Your custom LocalBrandColors is the source of truth for brand tokens.
  • You map brand tokens → ColorScheme via an extension function and pass them to MaterialTheme.
  • Material components automatically pick up brand colours via MaterialTheme.colorScheme.
  • Custom components read from LocalBrandColors.current directly, so they can use brand-specific tokens that M3 has no equivalent for (e.g. logo, errorSecondary).
"They coexist. Our brand tokens are the source of truth — they feed into MaterialTheme via a toColorScheme() mapping. Material components use MaterialTheme automatically. Our custom components read from LocalBrandColors.current directly for brand-specific tokens that M3 doesn't have a concept for."
Q8. How would you test that each brand theme renders correctly without writing 14 copies of every UI test?
Hard⌄

Parameterised screenshot tests using Roborazzi (or Paparazzi for pure JVM):

@RunWith(ParameterizedRobolectricTestRunner::class)
class PrimaryButtonTest(private val brand: Brand) {

    @get:Rule val composeRule = createComposeRule()

    companion object {
        @JvmStatic
        @ParameterizedRobolectricTestRunner.Parameters(name = "{0}")
        fun brands() = Brand.entries.toList()
    }

    @Test
    fun primaryButton_matchesGolden() {
        val theme = BrandRegistry.get(brand)
        composeRule.setContent {
            CompositionLocalProvider(LocalBrandColors provides theme.colors) {
                MaterialTheme(colorScheme = theme.toColorScheme()) {
                    PrimaryButton("Order Now") {}
                }
            }
        }
        composeRule.onRoot().captureRoboImage("golden/PrimaryButton_${brand.name}.png")
    }
}

One test class covers all 14 brands via the @Parameters list. Golden images are stored in the repo. Any token mismatch surfaces as a visual diff in CI. New brands automatically get coverage by being added to the Brand enum — no new test code needed.

"Parameterised screenshot tests with Roborazzi. One test class iterates over all Brand enum values, wraps each component in the correct CompositionLocalProvider, and compares against golden images. New brands are covered automatically by being added to the Brand enum — zero additional test code."
