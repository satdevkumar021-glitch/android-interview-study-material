1. Problem Statement

Scenario

Design the Android client architecture for a large-scale consumer app (banking / e-commerce / social) with millions of active users, 10+ independent feature teams, fast build times, A/B testing, staged rollouts, and a 99.5% crash-free session SLA.

Requirements

  • 10+ feature teams working independently without blocking each other
  • Fast local builds (<3 min incremental, <15 min clean build)
  • A/B testing and Feature Flags for gradual rollout
  • Multi-variant builds: free/premium, debug/staging/production
  • 99.5% crash-free session rate SLA
  • Startup time <2 seconds cold start
  • CI/CD pipeline with parallel testing, automated releases
Clarifying Questions
(1) Monorepo or multiple repos? (2) Is Jetpack Compose already adopted or migrating? (3) Do teams own backend APIs too? (4) What's the current crash-free rate and startup time? (5) Any existing DFM (Dynamic Feature Modules) usage?

2. Architecture

Module Graph

:app (thin shell, only navigation + DI graph wiring) │ ├── :feature:home (Home feed) ├── :feature:checkout (Checkout flow) ├── :feature:profile (User profile) ├── :feature:search (Search & discovery) │ each feature: UI + ViewModel + UseCases (no data layer) │ ├── :core:data (Repositories, Room, Retrofit, DataStore) ├── :core:domain (Use cases, domain models — pure Kotlin, no Android) ├── :core:ui (Design system: components, theme, typography) ├── :core:network (OkHttp, interceptors, auth token refresh) ├── :core:analytics (event tracking abstraction) ├── :core:featureflags (Remote Config wrapper, local fallback) └── :core:testing (test utilities, fakes, test rules) Dependency Rule: feature → core only. Features NEVER depend on other features.

Strict Dependency Rules

  • :feature:X can depend on any :core:Y
  • :feature:X must never depend on :feature:Z
  • :core:domain has NO Android dependencies — pure Kotlin/Java
  • :app depends on all features (for DI wiring) but features don't depend on :app
  • Enforce with forbiddenDependencies in Gradle scripts or Dependency Guard plugin

Dynamic Feature Modules (DFMs)

Optional heavy features (AR try-on, large onboarding flows) live in DFMs — they are not installed until needed, reducing APK size for users who never use them. DFMs are downloaded on demand via SplitInstallManager.

BFF Pattern (Backend for Frontend)

Each mobile platform (Android, iOS) has a dedicated BFF API gateway that aggregates multiple microservice calls and returns a single mobile-optimised response. The Android app doesn't call 5 microservices directly — it calls /mobile/v1/home and gets everything for the home screen in one request.

4. Key Decisions

Why Strict Modularization?

  • Build speed: Gradle only recompiles modules that changed. If :feature:profile changes, :feature:checkout doesn't recompile.
  • Team isolation: Teams own their module, set their own API surface. No merge conflicts with unrelated teams.
  • Testability: Each module tested in isolation with fake implementations of core modules.
  • Play Feature Delivery: Modules can become DFMs for optional delivery.

Feature Flags Strategy

interface FeatureFlagProvider {
    fun isEnabled(flag: FeatureFlag): Boolean
    fun getVariant(experiment: Experiment): String
}

// Production: backed by Firebase Remote Config
class RemoteConfigFlagProvider @Inject constructor(
    private val remoteConfig: FirebaseRemoteConfig
) : FeatureFlagProvider {
    override fun isEnabled(flag: FeatureFlag): Boolean =
        remoteConfig.getBoolean(flag.key)
}

// Test / debug: local override
class LocalFlagProvider(
    private val overrides: Map<FeatureFlag, Boolean> = emptyMap()
) : FeatureFlagProvider {
    override fun isEnabled(flag: FeatureFlag) = overrides[flag] ?: flag.defaultValue
}

CI/CD at Scale

  • Parallel test shards: split 2000 unit tests across 8 workers → 4× faster CI
  • Gradle Build Cache: remote cache (Gradle Enterprise) shares task outputs across machines
  • Incremental compile: only changed modules recompile
  • Automated version code: CI sets versionCode = CI_BUILD_NUMBER
  • Staged rollout: internal → alpha → beta → production 10% → 100%

API layerBFF patternDirect microservice callsReduces round trips, mobile-optimised response shape, less client logic

Build Time vs Modularity Trade-off

Too many small modules can slow Gradle's configuration phase. Optimal: 15–30 modules at this scale. Group small utilities into a single :core:utils module rather than one module per utility.

Common Anti-patterns
(1) :app module contains business logic — makes testing impossible. (2) Feature modules depend on each other — creates tight coupling. (3) Feature flags checked directly in ViewModel — should be injected via abstraction. (4) Remote Config fetched synchronously at startup — blocks main thread.

Emergency Halt

  • If a new release causes crash spike: Play Console → staged rollout halt → revert to previous version
  • Feature flags provide a kill switch: disable a feature remotely without a new release
  • Crashlytics alerts: if crash-free rate drops below 99%, PagerDuty alert fires

Startup Optimization

  • App Startup library: lazy-initialize SDKs that don't need to be ready at t=0
  • Baseline Profiles: ship pre-compiled code paths for critical user journeys (startup, checkout)
  • No blocking I/O in Application.onCreate() — defer to background coroutines
  • Splash screen API (Android 12+): smooth handoff from OS splash to app content

9. Quiz
Why must feature modules never depend on other feature modules?
Medium▼
Feature-to-feature dependencies create tight coupling — changing :feature:profile breaks :feature:checkout. It also creates potential circular dependency cycles which Gradle cannot build. Cross-feature communication should go through :core:domain shared models or navigation events. This ensures teams can release independently.
What is a Baseline Profile and how does it reduce cold start time?
Hard▼
A Baseline Profile is a list of critical code paths (startup, key user journeys) that are pre-compiled to native code (AOT) during app installation. Without it, the JIT compiler compiles code at runtime during first run — causing slow startup. With Baseline Profiles, the critical path is already native code, reducing cold start by 30–40%.
How would you use Firebase Remote Config as a kill switch?
Easy▼
Define a boolean flag like "new_payment_ui_enabled = true". Wrap the new feature: if (flags.isEnabled(FeatureFlag.NEW_PAYMENT_UI)) { showNewUI() } else { showOldUI() }. If the new UI causes crashes in production, flip the flag to false in Remote Config console — takes effect within minutes without a Play Store release. Always have a local default (false) for offline scenarios.
What is the BFF pattern and why is it valuable for mobile?
Medium▼
Backend for Frontend (BFF) is a dedicated API gateway layer for each client type (Android, iOS, web). Instead of the mobile app calling 5 microservices to render a screen, the BFF aggregates those calls server-side and returns one mobile-optimised response. Benefits: fewer network round trips, response shape designed for mobile consumption, backend changes don't break mobile APIs directly.
How does the App Startup library help cold start time?
Medium▼
The App Startup library provides a single ContentProvider that initializes multiple SDKs sequentially or concurrently, replacing the pattern of each SDK having its own ContentProvider (which adds startup overhead). It allows lazy initialization — defer SDK initialization until it's first needed rather than blocking app startup. Especially important for analytics, crash reporting, and image loaders.
How do Dynamic Feature Modules (DFMs) reduce APK size?
Medium▼
DFMs are Gradle modules that are NOT bundled in the initial install. They're downloaded on demand via SplitInstallManager when the user accesses that feature for the first time. This keeps the initial download small. Good candidates: AR features, large PDF viewers, rarely-used admin tools. Poor candidates: core functionality users need immediately.
Describe the staged rollout process from internal to production.
Easy▼
Internal track → Alpha (opted-in testers) → Beta (larger group) → Production 10% rollout → Production 50% → Production 100%. Monitor crash-free rate and ANR rate at each stage. If crash-free rate drops below threshold at 10%, halt rollout and investigate before proceeding. Emergency halt is instant; revert to previous version if needed.
Why should :core:domain have no Android dependencies?
Hard▼
Pure Kotlin/Java modules compile faster (no Android toolchain) and can be tested with plain JUnit without an Android emulator or Robolectric. Domain use cases and models are business logic — they have no reason to depend on Android Context, Activity, or Android-specific APIs. This also makes the domain layer portable to other platforms (KMP).
How would you enforce module dependency rules automatically?
Hard▼
Use the Dependency Guard Gradle plugin — it generates a baseline of allowed dependencies and fails CI if any module adds a new unexpected dependency. Alternatively, write custom Gradle tasks that parse the dependency graph and assert no :feature:X → :feature:Y edges. Pair with PR review guidelines. Some teams use lint rules or the ArchUnit library for architectural constraint verification.
An A/B test shows variant B has 10% higher conversion but 2% higher crash rate. What do you recommend?
Hard▼
Do not ship variant B as-is. A 2% higher crash rate is unacceptable — if crash-free rate was 99.5%, this would drop it to 97.5%. First, identify the crash root cause from Crashlytics. Fix the crash in variant B. Re-run the A/B test with the fixed variant. Only ship when both metrics are satisfied: higher conversion AND same or better crash-free rate.
