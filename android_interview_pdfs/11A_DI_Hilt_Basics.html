11A — DI & Hilt Basics

Why dependency injection, constructor vs field injection, and Hilt's core annotations: @Inject, @Module, @Provides, @Binds, @InstallIn, scopes, and qualifiers.

ID: 11A ⭐ Tier 1
🔍
1. Overview

Why Dependency Injection?

Dependency Injection (DI) is the practice of providing a class with its dependencies from outside rather than having the class create them. This produces three critical benefits:

  • Testability: swap real implementations with fakes/mocks without modifying production code
  • Loose coupling: classes depend on interfaces, not concrete types (DIP)
  • Single source of truth: one place creates and configures dependencies — a Hilt module, not scattered new calls throughout the codebase

DI Without Framework (Manual DI)

// Manual DI — valid for small apps, but scales poorly
class AppContainer(context: Context) {
    val database = AppDatabase.getInstance(context)
    val orderDao = database.orderDao()
    val retrofit = Retrofit.Builder().baseUrl("https://api.example.com").build()
    val orderApi = retrofit.create(OrderApi::class.java)
    val orderRepo: OrderRepository = OrderRepositoryImpl(orderApi, orderDao)
    val getOrders = GetOrdersUseCase(orderRepo)
    fun orderViewModelFactory() = OrderViewModelFactory(getOrders)
}
// Problem: tedious, error-prone, no lifecycle management
Senior Mental Model
Hilt is Dagger with an opinionated, Android-aware setup. Dagger does the heavy lifting (compile-time code generation, validated dependency graph); Hilt provides the Android-specific component hierarchy and @AndroidEntryPoint so you don't write boilerplate component code. Understanding Hilt = understanding Dagger's core concepts + Android lifecycle.

2. How It Works

Constructor Injection (Preferred)

The cleanest form — dependencies are declared in the constructor, making them visible, testable, and immutable.

// @Inject on constructor — Hilt knows how to create this class
class GetOrdersUseCase @Inject constructor(
    private val repository: OrderRepository  // interface — resolved by Hilt
) {
    suspend operator fun invoke(): Flow<List<Order>> = repository.getOrders()
}

@Provides — Providing Third-Party Classes

When you can't annotate a class with @Inject (e.g., OkHttpClient, Retrofit, Room), use @Provides in a module.

@Module
@InstallIn(SingletonComponent::class)
object NetworkModule {

    @Singleton
    @Provides
    fun provideOkHttpClient(
        tokenStore: TokenStore  // Hilt injects this parameter automatically
    ): OkHttpClient = OkHttpClient.Builder()
        .addInterceptor(AuthInterceptor(tokenStore))
        .build()

    @Singleton
    @Provides
    fun provideRetrofit(client: OkHttpClient): Retrofit =
        Retrofit.Builder()
            .baseUrl("https://api.commerce.com/")
            .client(client)
            .addConverterFactory(MoshiConverterFactory.create())
            .build()
}

@Binds — Interface Binding (Preferred over @Provides for interfaces)

@Binds is more efficient than @Provides for binding an interface to its implementation — no code is generated for the function body, it's purely a Dagger hint.

@Module
@InstallIn(SingletonComponent::class)
abstract class RepositoryModule {  // must be abstract for @Binds

    @Singleton
    @Binds
    abstract fun bindOrderRepository(
        impl: OrderRepositoryImpl  // Hilt injects the impl, returns as interface
    ): OrderRepository

    @Singleton
    @Binds
    abstract fun bindPaymentRepository(impl: PaymentRepositoryImpl): PaymentRepository
}

Scopes

AnnotationScopeLifetime
@SingletonSingletonComponentApplication lifetime
@ActivityRetainedScopedActivityRetainedComponentActivity lifetime across config changes

@ActivityScopedActivityComponentActivity instance (destroyed on config change)

class CartSessionManager @Inject constructor() { /* ... */ }

@HiltViewModel
class CartViewModel @Inject constructor(
    private val session: CartSessionManager  // same instance throughout ViewModel lifetime
) : ViewModel()

Qualifiers — Distinguishing Multiple Bindings

// Custom qualifier annotations
@Qualifier @Retention(AnnotationRetention.BINARY)
annotation class AuthenticatedOkHttpClient

@Qualifier @Retention(AnnotationRetention.BINARY)
annotation class UnauthenticatedOkHttpClient

@Module
@InstallIn(SingletonComponent::class)
object NetworkModule {
    @AuthenticatedOkHttpClient
    @Provides
    fun provideAuthClient(store: TokenStore) =
        OkHttpClient.Builder().addInterceptor(AuthInterceptor(store)).build()

    @UnauthenticatedOkHttpClient
    @Provides
    fun providePublicClient() = OkHttpClient.Builder().build()
}

// Injection site — specify which binding you want
class TokenRefreshService @Inject constructor(
    @UnauthenticatedOkHttpClient private val client: OkHttpClient
)

Entry Points — Injecting into Non-Hilt-Managed Classes

// For classes Hilt can't inject directly (e.g., ContentProvider, custom View)
@EntryPoint
@InstallIn(SingletonComponent::class)
interface SyncWorkerEntryPoint {
    fun syncService(): SyncService
}

// Use in a non-Hilt class
class DataSyncWorker(context: Context, params: WorkerParameters) : Worker(context, params) {
    private val syncService = EntryPointAccessors
        .fromApplication(applicationContext, SyncWorkerEntryPoint::class.java)
        .syncService()
}

3. When to Use

Constructor Injection vs Field Injection

TypeSyntaxProsCons
Constructor injection@Inject constructor(val dep: Dep)Immutable, visible, testable without DI frameworkRequires a non-Android class or @HiltViewModel
Field injection@Inject lateinit var dep: DepRequired for Activity/Fragment (system-instantiated)Mutable, not visible in constructor, needs @AndroidEntryPoint
Rule of Thumb
Use constructor injection everywhere possible. Use field injection only for Activities, Fragments, and Views — classes that Android instantiates via reflection and where you can't control the constructor call.

When to Use @Provides vs @Binds

  • @Provides: when you need to call a constructor or configure the object (Retrofit, Room, OkHttp). The function body creates the instance.
  • @Binds: when you have an interface and an @Inject-annotated implementation. No function body — just tells Dagger which type to use. More efficient (generates less code).

4. Production Example

Banking App — Full DI Setup

// ── Application setup ─────────────────────────────────────────
@HiltAndroidApp
class BankApplication : Application()

// ── Database module ───────────────────────────────────────────
@Module
@InstallIn(SingletonComponent::class)
object DatabaseModule {
    @Singleton
    @Provides
    fun provideDatabase(@ApplicationContext context: Context): BankDatabase =
        Room.databaseBuilder(context, BankDatabase::class.java, "bank.db")
            .addMigrations(MIGRATION_1_2, MIGRATION_2_3)
            .build()

    @Provides
    fun provideTransactionDao(db: BankDatabase) = db.transactionDao()
}

// ── Repository binding module ─────────────────────────────────
@Module
@InstallIn(SingletonComponent::class)
abstract class RepositoryModule {
    @Singleton
    @Binds
    abstract fun bindTransactionRepository(
        impl: TransactionRepositoryImpl
    ): TransactionRepository

    @Singleton
    @Binds
    abstract fun bindAccountRepository(impl: AccountRepositoryImpl): AccountRepository
}

// ── ViewModel (auto-injected via @HiltViewModel) ──────────────
@HiltViewModel
class TransactionHistoryViewModel @Inject constructor(
    private val getTransactions: GetTransactionHistoryUseCase
) : ViewModel() {
    val transactions = getTransactions()
        .stateIn(viewModelScope, SharingStarted.WhileSubscribed(5000), emptyList())
}

// ── Fragment — field injection via @AndroidEntryPoint ─────────
@AndroidEntryPoint
class TransactionHistoryFragment : Fragment() {
    private val viewModel: TransactionHistoryViewModel by viewModels()
    // No @Inject needed — viewModels() delegate works via Hilt ViewModel injection
}

5. Alternatives & Trade-offs
ApproachProsCons
HiltCompile-time validation, Android component hierarchy, minimal boilerplateBuild-time annotation processing, steep learning curve
Manual DI (AppContainer)No framework dependency, easy to understandManual lifetime management, no compile-time validation
KoinPure Kotlin, simpler setup, runtime resolutionRuntime errors (not compile-time), slower for large graphs
KodeinKotlin DSL, lightweightLess popular, runtime resolution

Hilt vs Koin

The critical difference: Hilt/Dagger validates the entire dependency graph at compile time. A missing binding is a compile error, not a runtime crash. Koin resolves at runtime — a missing binding crashes on the first use. For production apps with large dependency graphs, Hilt's compile-time safety is the decisive advantage.

6. Pitfalls & Best Practices

Scope Mismatch

Scope Mismatch — Most Common Hilt Bug
Injecting a @ActivityScoped dependency into a @Singleton component. The Singleton lives longer than the Activity — Dagger catches this at compile time with a "cannot be provided without an @Singleton scope" error. Always match the scope to the shortest-lived component that needs the dependency.

Field Injection and Lateinit

Accessing Field-Injected Property Before Injection
@Inject lateinit var service: MyService — accessing service before super.onCreate() in an Activity (where Hilt performs injection) causes a UninitializedPropertyAccessException. Always access injected fields after super.onCreate().

@Provides vs @Binds

  • Prefer @Binds for interface-to-implementation bindings — it's a compile-time hint, not a function call
  • Never have both @Binds and @Provides for the same type in the same module
  • @Binds requires an abstract class for the module; @Provides can be in an object

@ApplicationContext vs Context

// ✅ Use @ApplicationContext qualifier for Context in Singleton-scoped modules
@Provides
fun provideDatabase(@ApplicationContext ctx: Context): AppDatabase = /* ... */

// ✅ Use @ActivityContext for Activity-scoped components
@Provides
fun provideNavigator(@ActivityContext ctx: Context): Navigator = /* ... */

7. Interview Framework

30-Second Answer

"Hilt is Android's dependency injection framework built on Dagger. The three main benefits: testability (inject a fake instead of a real implementation), loose coupling (depend on interfaces, not concrete classes), and single source of truth (one Hilt module creates and configures each dependency). You annotate the Application with @HiltAndroidApp, Activities/Fragments with @AndroidEntryPoint, ViewModels with @HiltViewModel, and constructor dependencies with @Inject. For third-party types you can't annotate, you use @Module + @Provides or @Binds."

2-Minute Deep Dive

"The key distinction between @Provides and @Binds: use @Provides when you need to instantiate the object yourself (Retrofit, OkHttp, Room). Use @Binds when you're mapping an interface to its implementation — it's a pure Dagger hint with no function body, more efficient. Scopes control object lifetime: @Singleton = one instance for the app's lifetime, @ViewModelScoped = one per ViewModel. A scope mismatch — injecting a shorter-lived dependency into a longer-lived scope — is a compile error in Hilt, which is the critical advantage over runtime DI like Koin. For qualifiers: when two OkHttpClient instances exist (authenticated and unauthenticated), custom qualifier annotations tell Hilt which one to inject at each injection site."

Must-Mention Points

1
Why DI: testability (swap fakes), loose coupling (interfaces), single source of truth
2
Constructor injection preferred; field injection only for Android-system-instantiated classes
3
@Binds for interface → impl (abstract module, no body); @Provides for construction logic
4
Scopes: @Singleton app-wide; @ViewModelScoped per ViewModel; scope mismatch = compile error
5
Qualifiers: distinguish multiple bindings of the same type (two OkHttpClients)
6
Compile-time validation: Hilt/Dagger catches missing bindings at build time; Koin at runtime
7
@HiltAndroidApp / @AndroidEntryPoint / @HiltViewModel: three required entry-point annotations

Do NOT Go Deeper On

  • Raw Dagger 2 component boilerplate (Hilt handles it)
  • SubComponent vs Component dependencies details (covered in 11B)
  • Koin/Kodein implementation details

Follow-up Q&A

QuestionAnswer
"What's the difference between @Singleton and object in Kotlin?"Kotlin object is a static, untestable global. Hilt @Singleton is a single instance managed by the DI graph — injectable and replaceable in tests via a test module.
"How do you inject into a WorkManager Worker?"Use @HiltWorker on the Worker class and @AssistedInject on the constructor. Hilt generates the required WorkerFactory that WorkManager uses.
"What happens if a binding is missing?"The build fails with a "cannot be provided without an @Provides-annotated method" error. This is the key advantage — you find it at build time, not in production.

Senior Insight

Senior Signal
The compile-time graph validation is Hilt/Dagger's most underappreciated feature. In a large app with 200 classes in the DI graph, adding a new dependency and getting a build error is a feature, not a bug. It means you find missing bindings before the QA team does. The extra build time annotation processing pays for itself in prevented runtime crashes in production.

9. Interview Questions
Basic What are the three main benefits of Dependency Injection? ⌄
1. Testability: inject a fake or mock implementation instead of the real one — test the class in isolation. 2. Loose coupling: classes depend on interfaces, not concrete types — changing the implementation doesn't require changing the consumer. 3. Single source of truth: dependency creation is centralised in Hilt modules — no scattered new SomeClass() calls, consistent configuration everywhere.
Basic What is the difference between constructor injection and field injection? ⌄
Constructor injection: class Foo @Inject constructor(val dep: Bar) — dependencies are declared in the constructor, immutable, visible, and testable by passing them directly. Preferred everywhere possible.

Field injection: @Inject lateinit var dep: Bar — Hilt sets the field after the object is created. Required for Activities, Fragments, and Views because Android's system creates them using the no-arg constructor and you can't inject via constructor. Fields are mutable and can be accessed before injection.
Basic What is @Binds and when do you use it over @Provides? ⌄
@Binds tells Dagger to use a specific implementation class when a given interface is requested. It's in an abstract module method with no body: @Binds abstract fun bindRepo(impl: RepoImpl): Repository. Use it when the implementation has its own @Inject constructor and you just need to map the interface to it.

Use @Provides when you need to execute code to create the object — calling a builder, configuring a client, or using a constructor with non-injectable parameters. @Binds generates less code and is preferred for pure interface bindings.
Intermediate What does @ViewModelScoped mean and how does it differ from @Singleton? ⌄
@Singleton: one instance per Application component — lives as long as the app process. All ViewModels and classes in the app share the same instance.

@ViewModelScoped: one instance per ViewModel — lives as long as the ViewModel. Different ViewModel instances get different instances. The ViewModel's onCleared() destroys the scoped dependency. Use this for dependencies that logically belong to one ViewModel's operation (e.g., a cart session manager, a paging data source).
Intermediate How do qualifiers solve the "multiple bindings of the same type" problem? ⌄
When you have two OkHttpClient instances — one with auth interceptor, one without — Hilt/Dagger can't distinguish them by type alone. Qualifier annotations act as labels. You define @Qualifier annotation class AuthClient and @Qualifier annotation class PublicClient, annotate each @Provides method with the appropriate qualifier, and annotate the injection site: @AuthClient @Inject val client: OkHttpClient. Dagger matches the qualifier at compile time.
Intermediate How do you inject into a class that Hilt doesn't manage (e.g., a custom View)? ⌄
Use @EntryPoint. Define an interface annotated with @EntryPoint and @InstallIn(SingletonComponent::class) that exposes the dependencies you need. In the custom View or ContentProvider, retrieve the entry point via EntryPointAccessors.fromApplication(context, MyEntryPoint::class.java) and call the accessor methods. This is the "manual injection" escape hatch — use it sparingly, as it's more fragile than normal injection.
Intermediate Why is Hilt preferred over Koin in large production apps? ⌄
Compile-time validation: Hilt/Dagger validates the entire dependency graph during compilation. Missing bindings, scope mismatches, and circular dependencies are build errors. Koin resolves at runtime — a missing dependency crashes the first time the code path is hit in production. For a banking or e-commerce app with hundreds of dependencies, finding a missing binding in CI (build failure) rather than in production (crash report) is critical.
Senior How do you write a unit test for a ViewModel that has Hilt-injected dependencies? ⌄
For a pure unit test, don't use Hilt at all — just instantiate the ViewModel directly with constructor injection, passing fakes:
val fakeRepo = FakeOrderRepository(); val vm = OrderViewModel(GetOrdersUseCase(fakeRepo))

For integration tests using Hilt (e.g., @HiltAndroidTest): create a test module annotated with @TestInstallIn that replaces the production module with fakes. The test Hilt component uses the test module. Use @UninstallModules(ProductionModule::class) on the test class to exclude the real module.

Prefer the first approach (no Hilt in unit tests) — it's faster and requires no instrumentation.
Senior Explain a scope mismatch error and how to fix it. ⌄
Scenario: @Singleton class UserDashboard @Inject constructor(val activityNav: Navigator) where Navigator is @ActivityScoped. Dagger error: "Navigator cannot be provided without an @ActivityScoped scope".

Why: A Singleton lives forever; an ActivityScoped dependency lives only while the Activity is alive. The Singleton would hold a reference to a dead Navigator after the Activity is destroyed — memory leak and crash.

Fix options: (1) Make Navigator also @Singleton if it doesn't truly require Activity context. (2) Move UserDashboard to @ActivityScoped if it logically belongs to an Activity. (3) Use Provider<Navigator> to defer Navigator creation and always get the current Activity's instance.
Senior How would you migrate a large app from manual DI (AppContainer pattern) to Hilt? ⌄
Incremental migration strategy:

1. Add Hilt to the project; annotate Application with @HiltAndroidApp.
2. Start with leaf nodes of the dependency graph — classes with no dependencies of their own. Add @Inject constructor.
3. Work up the graph: for each class whose dependencies are now injectable, add @Inject constructor. For third-party classes, create Hilt modules.
4. For interfaces, add @Binds modules.
5. Once a subsystem is fully in Hilt, annotate the consuming Activity/Fragment with @AndroidEntryPoint and annotate ViewModels with @HiltViewModel.
6. Remove the corresponding AppContainer code for that subsystem.

Key: don't try to migrate everything at once. The AppContainer and Hilt can coexist during migration — keep the old container for unmigrated parts.
