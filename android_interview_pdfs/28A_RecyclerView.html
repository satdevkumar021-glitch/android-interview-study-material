1. Overview

RecyclerView Architecture

RecyclerView
  ├── LayoutManager       — decides where items go (linear, grid, staggered)
  ├── Adapter             — creates and binds ViewHolders
  │   └── ViewHolder      — wraps a single item View
  ├── RecycledViewPool    — cache of recycled ViewHolders by viewType
  ├── ItemDecoration      — draws dividers, spacing, overlays
  └── ItemAnimator        — animates add/remove/change
Senior Mental Model
RecyclerView's core innovation is view recycling. Instead of inflating a new View for every list item, it reuses off-screen ViewHolders (via the RecycledViewPool). The ViewHolder caches view references — no findViewById in onBindViewHolder. DiffUtil calculates minimal diff on a background thread, delivering smooth animations without full dataset reloads.
⚙
2. Architecture & ViewHolder Pattern

Adapter Lifecycle

class ProductAdapter : RecyclerView.Adapter<ProductAdapter.ProductViewHolder>() {

    private val items = mutableListOf<Product>()

    // 1. inflate — called only when no recycled view available
    override fun onCreateViewHolder(parent: ViewGroup, viewType: Int): ProductViewHolder {
        val binding = ItemProductBinding.inflate(
            LayoutInflater.from(parent.context), parent, false
        )
        return ProductViewHolder(binding)
    }

    // 2. bind — called every time a ViewHolder is (re)used for an item
    // NEVER do findViewById here — use ViewBinding instead
    override fun onBindViewHolder(holder: ProductViewHolder, position: Int) {
        holder.bind(items[position])
    }

    override fun getItemCount() = items.size

    // ViewHolder — view references cached as constructor properties
    class ProductViewHolder(
        private val binding: ItemProductBinding
    ) : RecyclerView.ViewHolder(binding.root) {

        fun bind(product: Product) {
            binding.nameText.text = product.name
            binding.priceText.text = product.formattedPrice()
            Glide.with(binding.root)
                .load(product.imageUrl)
                .into(binding.productImage)
        }
    }
}
ViewHolder Pattern
The ViewHolder pattern avoids repeated findViewById() calls during scrolling. With ViewBinding, view references are auto-generated as properties of the binding class and cached in the ViewHolder instance. onBindViewHolder is called frequently during scroll — keep it fast.

3. DiffUtil & ListAdapter

DiffUtil.Callback

class ProductDiffCallback : DiffUtil.ItemCallback<Product>() {

    // Are these the same item? (same identity — used for move animations)
    override fun areItemsTheSame(oldItem: Product, newItem: Product): Boolean =
        oldItem.id == newItem.id

    // Are the contents identical? (used to decide if binding is needed)
    override fun areContentsTheSame(oldItem: Product, newItem: Product): Boolean =
        oldItem == newItem  // data class equals() compares all fields

    // Optional: return specific changed payload for partial binding
    override fun getChangePayload(oldItem: Product, newItem: Product): Any? {
        return if (oldItem.price != newItem.price) "PRICE_CHANGED" else null
    }
}

ListAdapter — the recommended approach

// ListAdapter wraps DiffUtil with AsyncListDiffer
// Diff calculation happens on a background thread
class ProductAdapter : ListAdapter<Product, ProductAdapter.ProductViewHolder>(
    ProductDiffCallback()
) {
    override fun onCreateViewHolder(parent: ViewGroup, viewType: Int) = ...
    override fun onBindViewHolder(holder: ProductViewHolder, position: Int) {
        holder.bind(getItem(position))  // use getItem(), not external list
    }
}

// Submit a new list — diff calculated in background, then dispatched
// Only items that actually changed get animated/rebound
adapter.submitList(newProducts)

// Important: always submit a NEW list, not mutate the existing one
// DiffUtil compares old vs new — mutating in place skips the diff
Common Mistake
Never call adapter.submitList(list) with the same list reference you mutated. AsyncListDiffer compares the new list object to the internally stored one — if it's the same reference, it skips the diff. Always create a new list: submitList(currentList.toMutableList().also { it.add(item) }) or work with immutable state.

5. ItemDecoration & Nested RecyclerViews

ItemDecoration

// Add spacing between items
class SpaceItemDecoration(private val spacing: Int) : RecyclerView.ItemDecoration() {
    override fun getItemOffsets(
        outRect: Rect, view: View,
        parent: RecyclerView, state: RecyclerView.State
    ) {
        val position = parent.getChildAdapterPosition(view)
        if (position != RecyclerView.NO_ID) {
            outRect.bottom = spacing
            if (position == 0) outRect.top = spacing
        }
    }
}
recyclerView.addItemDecoration(SpaceItemDecoration(spacing = 16))

Nested RecyclerViews with RecycledViewPool

// Problem: each horizontal RV inside a vertical RV has its own ViewPool
// → ViewHolders are not shared, causing excessive inflation

// Solution: share RecycledViewPool between all nested horizontal RVs
val sharedPool = RecyclerView.RecycledViewPool()
sharedPool.setMaxRecycledViews(VIEW_TYPE_PRODUCT, 20)  // pool 20 items

// In the outer adapter's onCreateViewHolder:
class CategoryViewHolder(binding: ItemCategoryBinding) : RecyclerView.ViewHolder(binding.root) {
    val productsRV: RecyclerView = binding.productsRecyclerView

    fun bind(category: Category, sharedPool: RecyclerView.RecycledViewPool) {
        productsRV.setRecycledViewPool(sharedPool)
        productsRV.setHasFixedSize(true)
        (productsRV.layoutManager as? LinearLayoutManager)
            ?.initialPrefetchItemCount = 4
    }
}

7. Interview Framework

30-Second Answer

"RecyclerView uses the ViewHolder pattern to cache view references and recycle off-screen views. I use ListAdapter built on DiffUtil's AsyncListDiffer — it calculates the diff on a background thread and dispatches minimal updates with animations. For performance: setHasFixedSize(true), use stable IDs, share RecycledViewPool for nested RecyclerViews, and avoid expensive work in onBindViewHolder."

2-Minute Answer

"RecyclerView separates concerns: the LayoutManager decides positioning, the Adapter creates and binds ViewHolders, and the RecycledViewPool caches off-screen ViewHolders for reuse. The ViewHolder pattern caches view references — with ViewBinding, references are typed properties so no findViewByld is ever needed in bind(). For efficient updates I use ListAdapter, which wraps AsyncListDiffer. DiffUtil requires implementing areItemsTheSame (identity check — usually ID) and areContentsTheSame (equality check — data class equals works). The diff runs on a background thread and dispatches precise insert/remove/change/move animations. Critical mistake: never submit a mutated list — always submit a new list instance. For nested RecyclerViews (e.g. horizontal carousels inside vertical feed), sharing a RecycledViewPool dramatically reduces inflation overhead. And setHasFixedSize(true) skips unnecessary layout passes when item count changes but container size doesn't."

Must-Mention Points

1
ViewHolder pattern — caches view refs; onCreateViewHolder (inflate once), onBindViewHolder (bind frequently)
2
ListAdapter + DiffUtil — async diff on background thread, minimal updates, smooth animations
3
areItemsTheSame (identity/ID) vs areContentsTheSame (data equality)
4
Never submit the same list reference mutated — DiffUtil compares references first
5
Shared RecycledViewPool for nested RVs — prevents excessive inflation

Senior Insight

Senior Differentiator
Know the full RecycledViewPool hierarchy: scrap cache (just off screen, rebind happens but not reinflate) → RecycledViewPool (pooled by viewType, must rebind). For nested RecyclerViews, understand that without a shared pool, each row creates its own pool — if 20 rows each inflate 5 items that's 100 inflations vs sharing a pool of 20. Also know when NOT to use RecyclerView — for <10 static items, a simple Column in Compose or LinearLayout is cheaper.

9. Interview Questions
1. Why is the ViewHolder pattern important?
Basic⌄
ViewHolder caches view references. Without it, onBindViewHolder would call findViewById() on every scroll event — an expensive tree traversal. The ViewHolder stores all view references as properties, created once in onCreateViewHolder. With ViewBinding, references are auto-generated as typed properties — cleaner and null-safe. The key insight: onCreateViewHolder is called rarely (only when no recycled view is available), but onBindViewHolder is called on every visible item during scroll.
2. What is the difference between areItemsTheSame and areContentsTheSame?
Basic⌄
areItemsTheSame checks identity — are these two items representing the same entity? Usually compares unique IDs. areContentsTheSame checks equality — do both items have the same data to display? Usually uses data class equals() or field-by-field comparison. If areItemsTheSame is false: item is added/removed (insert/delete animation). If true but areContentsTheSame is false: item is updated (change animation). Both true: no change, skip rebind.
3. What is ListAdapter and how does it improve on plain RecyclerView.Adapter?
Basic⌄
ListAdapter wraps AsyncListDiffer which runs DiffUtil.calculateDiff() on a background thread. Plain adapter requires calling notifyDataSetChanged() (expensive — rebinds everything) or manually calling notifyItemInserted/Removed (error-prone). ListAdapter.submitList() automatically diffs old vs new list and dispatches precise updates with animations. It also stores the current list internally — use getItem(position) in onBindViewHolder.
4. Why can't you submit the same mutated list to ListAdapter?
Intermediate⌄
AsyncListDiffer stores a reference to the last submitted list. When submitList is called, it first checks if oldList === newList (same reference). If yes, it bails out without diffing — even if you mutated the contents. This is why you must always create a new list: currentList.toMutableList().also { it.add(item) }. Functional/immutable state management (like Kotlin's plus operator on lists) naturally avoids this problem.
5. When would you use multiple view types in an adapter?
Intermediate⌄
When list items have different layouts: header + items, loading footer, ads between items, different item styles in the same feed. Override getItemViewType() to return a unique Int per type. Create separate ViewHolder classes per type. In onCreateViewHolder, inflate based on viewType. In onBindViewHolder, cast to the correct ViewHolder type. Each viewType gets its own RecycledViewPool bucket — ViewHolders are never reused across types.
6. How do shared RecycledViewPool and prefetching help nested RecyclerViews?
Intermediate⌄
In a vertical RV where each row has a horizontal RV (e.g. category rows): by default each horizontal RV has its own ViewPool — ViewHolders aren't shared. Shared RecycledViewPool lets all horizontal RVs share one pool, dramatically reducing inflation when scrolling vertically. Set initialPrefetchItemCount on the horizontal LinearLayoutManager so the RenderThread prefetches items for new rows before they appear, reducing jank.
7. What does setHasFixedSize(true) do?
Intermediate⌄
When set to true, RecyclerView skips calling requestLayout() on the parent when the adapter notifies data changes. requestLayout() is an expensive re-measure/re-layout pass. If your RecyclerView's size doesn't change when items are added/removed (e.g., it's match_parent in both dimensions), this is always safe to enable and avoids unnecessary layout work during updates.
8. Your list has janky scrolling. How do you diagnose and fix it?
Senior⌄
1) Use Android Studio's CPU Profiler to find which methods are slow. 2) Check onBindViewHolder — is it doing heavy work? (bitmap decode, network, JSON parsing) Move to Glide/background. 3) Check for synchronous notifyDataSetChanged() calls — switch to ListAdapter. 4) Check overdraw with "Show GPU Overdraw" in developer options. 5) Check if views have complex layouts — flatten with ConstraintLayout. 6) Add setHasFixedSize(true) and stable IDs. 7) For nested RVs, add shared RecycledViewPool and initialPrefetchItemCount.
9. How does getChangePayload() improve partial binding?
Senior⌄
When areItemsTheSame is true but areContentsTheSame is false, DiffUtil calls getChangePayload() to return a description of what changed. This payload is passed to onBindViewHolder(holder, position, payloads). Instead of rebinding the entire item, you can update only the changed views. Example: if only the price changed, update just the price TextView instead of rebinding the image and name. Reduces unnecessary Glide reloads and prevents image flicker on partial updates.
10. How does RecyclerView's recycling work internally?
Scenario⌄
RecyclerView has multiple caches: (1) Attached/detached scrap — ViewHolders that are still in the layout but being re-laid out; retrieved without rebinding. (2) Cache (default size 2) — recently off-screen ViewHolders cached by position; retrieved without rebinding if the same position comes back. (3) RecycledViewPool — typed ViewHolders for reuse; must rebind when retrieved. (4) ViewCacheExtension — custom cache layer. Order of retrieval: scrap → cache → pool → onCreateViewHolder. setItemViewCacheSize increases the size of the cache layer, reducing rebinds for recently-off-screen items.
