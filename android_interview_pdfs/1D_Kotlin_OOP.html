1D — Kotlin OOP

Classes, constructors, init, inheritance, interfaces, abstract classes, visibility modifiers, and open/final/abstract — how Kotlin's OOP differs from Java and why it matters for Android architecture.

ID: 1D ⭐ Tier 1
🔍
1. Overview

What it is

Kotlin's OOP system is a safer, more concise evolution of Java's. Key differences: classes are final by default (must opt-in to inheritance with open), constructors are inline in the class header, interfaces can have default implementations and properties, and visibility modifiers have Android-relevant scoping differences.

Why it matters for Android

  • Every Activity, Fragment, ViewModel, Repository, UseCase is a class — OOP fundamentals underpin every layer.
  • Clean Architecture is built on interfaces (abstractions) and classes (implementations) — understanding visibility and inheritance is mandatory.
  • Hilt DI relies on constructor injection — understanding primary constructors and @Inject is critical.
  • Compose uses open/abstract sparingly — final-by-default aligns with the immutability preference in reactive code.
Key Kotlin vs Java Difference
In Java, classes are open (extensible) by default. In Kotlin, classes are final by default. You must explicitly mark a class open to allow subclassing. This is a deliberate design choice — it enforces the Effective Java principle "design and document for inheritance, or else prohibit it."

2. How It Works

Classes and Primary Constructor

// Primary constructor in class header — no separate constructor block needed
class UserRepository @Inject constructor(   // @Inject on primary constructor
    private val api: UserApi,
    private val dao: UserDao
) {
    // class body
}

init block

class TokenManager(private val prefs: SharedPreferences) {
    private val encryptionKey: String

    init {
        // Runs after primary constructor, before secondary constructors
        encryptionKey = prefs.getString("enc_key", "") ?: generateKey()
        require(encryptionKey.isNotBlank()) { "Encryption key must not be blank" }
    }
}
// Multiple init blocks run top-to-bottom in declaration order

Secondary Constructors

class ApiException(val code: Int, message: String) : Exception(message) {
    // Secondary constructor — must delegate to primary via this()
    constructor(code: Int) : this(code, "HTTP error $code")
}
// Prefer default arguments over secondary constructors in most cases

Inheritance

// Base class MUST be 'open' to be subclassed
open class BaseViewModel : ViewModel() {
    open fun onError(e: Throwable) {  // also 'open' for override
        Timber.e(e)
    }
}

class PaymentViewModel @Inject constructor(
    private val useCase: ProcessPaymentUseCase
) : BaseViewModel() {
    override fun onError(e: Throwable) {
        super.onError(e)              // call super explicitly
        _uiState.value = UiState.Error(e.message)
    }
}

Interfaces

// Kotlin interfaces can have: abstract methods, default implementations, properties
interface PaymentRepository {
    // Abstract — must be implemented
    suspend fun initiatePayment(request: PaymentRequest): Result<PaymentResponse>

    // Default implementation — can be overridden but doesn't have to be
    suspend fun cancelPayment(id: String): Result<Unit> =
        Result.failure(UnsupportedOperationException("Cancel not supported"))

    // Property in interface (no backing field)
    val maxRetries: Int get() = 3
}

Abstract Classes

// abstract class: cannot be instantiated, can have state (fields), constructors
abstract class BaseUseCase<P, R> {
    protected abstract suspend fun execute(params: P): R

    suspend operator fun invoke(params: P): Result<R> = try {
        Result.success(execute(params))
    } catch (e: Exception) {
        Result.failure(e)
    }
}

class GetUserProfileUseCase @Inject constructor(
    private val repo: UserRepository
) : BaseUseCase<String, UserProfile>() {
    override suspend fun execute(params: String) = repo.getUser(params)
}

3. Why and When to Use It

Interface vs Abstract Class — Decision Guide

UseWhenAndroid Example
InterfaceDefine a contract with no state; multiple implementations; testability (mock/fake); DI abstraction layerUserRepository, AuthService, AnalyticsTracker
Abstract classShare state + behaviour across subclasses; template method pattern; partial implementationBaseViewModel, BaseUseCase<P,R>, BaseFragment
Open classAllow subclassing but provide a complete default implementationCustom view base class, library classes that need extension
Final class (default)Implementation classes that should not be subclassed (most use cases, use cases, ViewModels)LoginUseCase, ProductRepositoryImpl

Visibility in Multi-Module Architecture

Production Rule
In a multi-module app, internal is your friend. Mark implementation classes internal so the :feature-payment module cannot directly instantiate PaymentRepositoryImpl from :data. Only the interface (PaymentRepository) is public. Hilt binds them — the consumer never sees the implementation class.

When NOT to Use Inheritance

Do NOT
  • Use inheritance for code reuse alone — prefer composition or extension functions
  • Mark every class open "just in case" — final-by-default is a safety feature
  • Use abstract classes for pure contracts — that's what interfaces are for
  • Deep inheritance hierarchies — 2 levels max; beyond that, extract shared logic differently

4. Production Example
Scenario
Automotive app — a Clean Architecture payment module demonstrating interface, abstract class, open class, visibility modifiers, constructors, and init blocks together.

Interface — contract for DI

// domain/repository/PaymentRepository.kt  (public — crosses module boundary)
interface PaymentRepository {
    suspend fun initiatePayment(req: PaymentRequest): Result<PaymentResponse>
    suspend fun getPaymentStatus(id: String): Result<PaymentStatus>
}

Abstract Base UseCase — template method pattern

// domain/usecase/BaseUseCase.kt  (internal to :domain module)
internal abstract class BaseUseCase<in P, out R> {
    protected abstract suspend fun execute(params: P): R

    // Template method: wraps execute() with error handling
    suspend operator fun invoke(params: P): Result<R> = try {
        Result.success(execute(params))
    } catch (e: CancellationException) {
        throw e   // never swallow cancellation
    } catch (e: Exception) {
        Result.failure(e)
    }
}

Concrete UseCase — final (default)

// domain/usecase/ProcessPaymentUseCase.kt
class ProcessPaymentUseCase @Inject constructor(
    private val repo: PaymentRepository,       // depends on interface, not impl
    private val validator: PaymentValidator
) : BaseUseCase<PaymentRequest, PaymentResponse>() {

    override suspend fun execute(params: PaymentRequest): PaymentResponse {
        validator.validate(params)          // throws on invalid — caught by base
        return repo.initiatePayment(params).getOrThrow()
    }
}

Repository Implementation — internal, hides from other modules

// data/repository/PaymentRepositoryImpl.kt
internal class PaymentRepositoryImpl @Inject constructor(
    private val api: PaymentApi,
    private val dao: PaymentDao
) : PaymentRepository {

    private val cache = HashMap<String, PaymentStatus>()  // private state

    override suspend fun initiatePayment(req: PaymentRequest) =
        safeApiCall { api.pay(req.toDto()).toDomain() }

    override suspend fun getPaymentStatus(id: String) =
        safeApiCall { cache.getOrPut(id) { api.getStatus(id).toDomain() } }
}

ViewModel — open base class pattern

// presentation/base/BaseViewModel.kt
open class BaseViewModel : ViewModel() {
    protected val _error = MutableSharedFlow<String>()
    val error = _error.asSharedFlow()

    protected open fun handleError(e: Throwable) {
        viewModelScope.launch { _error.emit(e.message ?: "Unknown error") }
    }
}

// presentation/payment/PaymentViewModel.kt
@HiltViewModel
class PaymentViewModel @Inject constructor(
    private val processPayment: ProcessPaymentUseCase
) : BaseViewModel() {

    private val _state = MutableStateFlow<PaymentUiState>(PaymentUiState.Idle)
    val state = _state.asStateFlow()

    fun pay(req: PaymentRequest) {
        viewModelScope.launch {
            _state.value = PaymentUiState.Loading
            processPayment(req)
                .onSuccess { _state.value = PaymentUiState.Success(it) }
                .onFailure { handleError(it) }  // calls base class method
        }
    }
}

Key Architecture Points

  • PaymentRepository is a public interface — crosses module boundaries; consumers depend on abstraction.
  • PaymentRepositoryImpl is internal — hidden from feature modules; only Hilt wires it.
  • BaseUseCase is internal abstract — template method pattern; error handling once, reused across all use cases.
  • BaseViewModel is open with protected open fun handleError — subclasses can override but get sensible defaults.
  • No !!, no mutable public state, constructor injection throughout.

6. Pitfalls & Best Practices

Forgetting open on a class that needs to be subclassed

// ❌ BAD — Hilt proxy / Mockito subclassing will fail at runtime
class BaseViewModel : ViewModel()  // final — cannot mock or proxy
// ✅ GOOD
open class BaseViewModel : ViewModel()

Leaking implementation through public visibility

// ❌ BAD — implementation class is public; other modules can depend on it directly
class UserRepositoryImpl : UserRepository { ... }  // public by default
// ✅ GOOD — internal hides it from other modules; only Hilt module sees it
internal class UserRepositoryImpl : UserRepository { ... }

init block ordering trap

class Foo(val x: Int) {
    val doubled = x * 2   // ✅ property initializers run top-to-bottom

    init {
        // ❌ BAD: if 'tripled' is declared AFTER this init block,
        // accessing it here throws UninitializedPropertyAccessException
        println(tripled)
    }

    val tripled = x * 3   // declared AFTER init — not yet initialized when init runs
}

Property initializers and init blocks run in declaration order. Never access a property in an init block that is declared after it.

Abstract class vs interface — wrong choice

// ❌ BAD — abstract class used as a pure contract (no state, no constructors)
abstract class UserRepository {
    abstract suspend fun getUser(id: String): User
}
// ✅ GOOD — interface is the right tool for a pure contract
interface UserRepository {
    suspend fun getUser(id: String): User
}
// Benefit: implementation can implement multiple interfaces; can be mocked

Production Best Practices

  1. Classes are final by default — only add open when inheritance is deliberately designed and documented.
  2. Keep implementation classes internal in multi-module apps — expose only interfaces across module boundaries.
  3. Prefer interfaces for cross-layer contracts (Repository, Service); abstract classes for shared state (BaseViewModel).
  4. Use protected for base class helpers intended only for subclasses — don't make them public.
  5. Prefer constructor injection — Hilt's @Inject constructor documents all dependencies explicitly.
  6. Declare properties before the init block that needs them — or initialize them in the init block itself.
  7. Prefer composition over inheritance beyond 1–2 levels deep.

7. Interview Answer Framework

30-Second Answer

"Kotlin's OOP differs from Java in one critical way: classes are final by default. You must explicitly mark a class open to allow subclassing. This enforces 'design for inheritance or prohibit it.' For contracts, I use interfaces — they support multiple implementations, default methods, and are mockable. For shared state and behaviour, I use abstract classes. Visibility-wise, I use internal heavily in multi-module apps to hide implementation classes from other modules, exposing only the interface."

2-Minute Structured Answer

"Three areas stand out in Kotlin OOP compared to Java.

First, final-by-default. In Java, any class can be subclassed unless you mark it final. In Kotlin it's the opposite — you have to opt-in with open. This is an intentional design decision that aligns with Clean Architecture: use cases, repository implementations, and most concrete classes should not be extended — they should be replaced or wrapped.

Second, interface vs abstract class. I use interfaces for cross-layer contracts — UserRepository, AnalyticsTracker — because they're mockable, support multiple implementations, and implementations can implement multiple interfaces. I use abstract classes when I need shared state: a BaseViewModel with a protected _error: SharedFlow, or a BaseUseCase<P,R> that wraps execute() with error handling once for all use cases.

Third, visibility in multi-module apps. internal is the key modifier. Repository implementations are internal — the feature module only sees the interface. Only Hilt's module sees the implementation. This enforces the Dependency Inversion Principle at the module level."

Likely Follow-up Questions

QuestionShort Answer
Why are Kotlin classes final by default?Enforces "design and document for inheritance, or prohibit it" (Effective Java Item 19). Prevents accidental subclassing that breaks invariants. Aligns with Kotlin's philosophy of explicit opt-in for unsafe operations.
Can an interface have a constructor in Kotlin?No. Interfaces cannot have constructors or backing fields. If you need constructor parameters, use an abstract class. Interface properties are abstract getters (or have custom getters) — no stored state.
What's the difference between internal and private?private on a class member = visible only within that class. private on a top-level declaration = visible only within that file. internal = visible within the same Gradle module — used to hide implementation classes from other modules.
Can a Kotlin class implement multiple interfaces?Yes — unlike abstract classes, a class can implement multiple interfaces. If two interfaces have the same default method, the implementing class must override it and explicitly call which super it wants.
What happens if two interfaces both provide a default for the same method?Compile error — the implementing class must override the method and call super<InterfaceName>.method() to disambiguate.

Senior-Level Insight (Stand Out)

Say This
"In a multi-module Clean Architecture, I combine Kotlin's visibility system with Hilt's DI to enforce the Dependency Inversion Principle at the build-system level. The :data module exposes only public interface UserRepository. The implementation UserRepositoryImpl is internal — literally impossible for the :feature module to reference it directly. Hilt's module in :data binds them. This means you get compile-time enforcement of 'depend on abstractions, not concretions' — not just a convention. That's a stronger guarantee than any code review."

9. Interview Questions (Self-Check)
How to use
Answer first, then reveal.

Basic

B1 — What is the default visibility of a Kotlin class and its members? How does it differ from Java?
Easy▼
In Kotlin, the default visibility is public (unlike Java where it's package-private). However, classes in Kotlin are final by default (unlike Java where they're open/extensible). To allow subclassing in Kotlin you must mark the class open. Java requires final to prohibit subclassing — the opposite approach.
B2 — What is the init block? When does it run?
Easy▼
The init block is a body of code that runs as part of the primary constructor, immediately after property initializers. Multiple init blocks are allowed — they run in top-to-bottom declaration order, interleaved with property initializers. Use it for validation (require()), complex initialization that can't be expressed in a single expression, or initialization that depends on constructor parameters.
B3 — What is the difference between interface and abstract class in Kotlin?
Easy▼
Interface: no constructors, no backing fields (only abstract getters), can have default method implementations, a class can implement multiple interfaces.

Abstract class: can have constructors, backing fields (actual state), both abstract and concrete methods. A class can only extend one abstract class.

Use interface for pure contracts (testability, DI); use abstract class when shared state or constructor parameters are needed.

Intermediate

I1 — What does internal mean? How is it different from private? Give an Android multi-module example.
Medium▼
internal means visible within the same Gradle module. private on a class member means visible only within that class; on a top-level declaration it means visible only within that file.

Multi-module example: In :data module, UserRepositoryImpl is marked internal. The :feature-profile module cannot reference it directly even though it depends on :data. It can only use the public interface UserRepository. Hilt's module in :data (which is in the same module as the impl) binds the interface to the implementation.
I2 — (Coding) What is wrong with this code and how do you fix it?
MediumCoding▼
class Config(val env: String) {
    init {
        println(label)   // ❌ — 'label' declared AFTER this init block
    }
    val label = "$env config"
}
Problem: Property initializers and init blocks run in declaration order. label is declared after the init block, so when init runs, label has not been initialized yet → UninitializedPropertyAccessException at runtime.

Fix: Move label before the init block, or access it in a later init block: 
class Config(val env: String) {
    val label = "$env config"  // declared first
    init { println(label) }    // ✅ now initialized
}
I3 — Can a Kotlin class implement two interfaces that both define a default implementation for the same method? What happens?
Medium▼
Yes, a class can implement two such interfaces, but if both provide a default implementation for the same method, the implementing class must override that method — otherwise it's a compile error. Inside the override, you can delegate to either interface's default with super<InterfaceName>.method(): 
interface A { fun greet() = println("Hello from A") }
interface B { fun greet() = println("Hello from B") }
class C : A, B {
    override fun greet() { super<A>.greet() }  // must disambiguate
}
I4 — When would you use a secondary constructor vs default arguments in Kotlin?
Medium▼
Almost always prefer default arguments — they're more concise, idiomatic, and work with named arguments. Secondary constructors should be used when: (1) the class needs completely different initialization paths that can't be captured by defaults (e.g., constructing from a JSON string vs individual fields); (2) interoperability with Java requires overloaded constructors (@JvmOverloads is the cleaner alternative); (3) you're subclassing a Java class with multiple constructors and need to delegate to different parent constructors.

Senior / Scenario

S1 — (Scenario) A teammate made UserRepositoryImpl public. What are the risks? How do you enforce the right pattern?
HardScenario▼
Risks: (1) Feature modules can depend directly on the implementation — violating DIP. If the implementation changes (e.g., adding a constructor parameter), every direct user breaks. (2) Tests may use the concrete class instead of the interface, making them harder to fake. (3) The implementation's internal details (caching, retries) are now part of the "public API" — any refactor becomes a breaking change.

Fix: Mark UserRepositoryImpl as internal. The Hilt module that binds it is in the same module so it still works. Add a lint rule or ArchUnit test to prevent cross-module direct usage of impl classes. In code review, flag any import of an Impl class in a feature module.
S2 — Design a BaseUseCase abstract class that wraps all use cases in a Result with correct CancellationException handling.
HardCoding▼
abstract class BaseUseCase<in P, out R> {
    // Subclasses implement this — business logic only
    protected abstract suspend fun execute(params: P): R

    // Callers use invoke() — gets error handling for free
    suspend operator fun invoke(params: P): Result<R> = try {
        Result.success(execute(params))
    } catch (e: CancellationException) {
        throw e  // CRITICAL: never swallow coroutine cancellation
    } catch (e: Exception) {
        Result.failure(e)
    }
}

// Usage:
class GetUserUseCase @Inject constructor(
    private val repo: UserRepository
) : BaseUseCase<String, User>() {
    override suspend fun execute(params: String) = repo.getUser(params)
}
Key point: CancellationException must be rethrown — swallowing it breaks coroutine cancellation throughout the scope.
S3 — When would you choose composition over inheritance for a ViewModel scenario? Give a concrete example.
HardScenario▼
Scenario: You have BaseViewModel with error handling, and now you need two orthogonal concerns: pagination logic and analytics tracking. You could add both to the base class or create a deep hierarchy — but that couples all ViewModels to pagination and analytics whether they need it or not.

Composition approach: 
// Each concern is a separate class injected via constructor
class PaginationController(private val pageSize: Int = 20) {
    fun nextPage() = ...
}

class AnalyticsDelegate @Inject constructor(private val tracker: Tracker) {
    fun trackScreen(name: String) = tracker.track(name)
}

@HiltViewModel
class ProductListViewModel @Inject constructor(
    private val pagination: PaginationController,  // composed
    private val analytics: AnalyticsDelegate        // composed
) : ViewModel() { ... }
This is testable (mock each dependency independently), avoids a bloated base class, and each concern is independently reusable. Kotlin's by delegation can make this even cleaner by auto-delegating interface calls.
