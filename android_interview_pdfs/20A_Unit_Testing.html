20A — Unit Testing

JUnit 4 vs JUnit 5, MockK (Kotlin-first mocking, coEvery, slots, relaxed mocks) vs Mockito, Fake vs Mock vs Stub, Testing Pyramid, and Clean Architecture testability.

ID: 20A ⭐ Tier 2 (Testing & QA)
🚀
1. Overview & Testing Pyramid

Unit tests run entirely on the local JVM (under src/test/java), executing in milliseconds with zero Android emulator or device overhead. They form the base (~70%) of the Android Testing Pyramid.

The Testing Pyramid Breakdown
  • Unit Tests (~70%): Fast, isolated JVM tests for ViewModels, UseCases, Repositories, and Mappers. Uses MockK / Fakes.
  • Integration Tests (~20%): Validates interactions between components (e.g. Room DB queries via in-memory SQLite, OkHttp MockWebServer).
  • End-to-End / UI Tests (~10%): Runs on device/emulator (Compose UI Test, Espresso, UI Automator). Slowest and most brittle.

2. How It Works: Test Doubles & MockK

1. Fake vs Mock vs Stub vs Spy

Double TypeDefinitionWhen to Use
FakeWorking lightweight implementation (e.g., in-memory map repository)Best for stateful repositories & DAOs
StubProvides predefined hardcoded answers to method callsSimple data providers where interaction count doesn't matter
MockObject registered with expectations (calls verified via verify {})Verifying side-effects (e.g., analytics track event called)
SpyWraps a real object, delegating calls unless explicitly stubbedPartial mocking of legacy classes

2. MockK Kotlin DSL

val repo = mockk<UserRepository>()

// Stubbing suspend function:
coEvery { repo.getUser("123") } returns User(id = "123", name = "Alice")

// Verifying call happened exactly once:
coVerify(exactly = 1) { repo.getUser("123") }

// Capturing argument with Slot:
val slot = slot<User>()
coEvery { repo.saveUser(capture(slot)) } just Runs
assertEquals("Alice", slot.captured.name)

3. Designing Architecture for Testability
Golden Rules for Testable Clean Code
  • Constructor Injection: Inject all dependencies (Repositories, Dispatchers, APIs) via constructor rather than instantiating them inside classes.
  • Inject Coroutine Dispatchers: Never hardcode Dispatchers.IO or Dispatchers.Default. Inject a CoroutineDispatcherProvider interface or @IoDispatcher so unit tests can swap in StandardTestDispatcher.
  • Zero Android SDK Imports in Domain Layer: Keep UseCases and Domain entities 100% pure Kotlin with zero Android framework dependencies (no Context, TextUtils, Bundle).
  • Favour Fakes over Heavy Mocks: Fakes reduce test maintenance burden when method signatures change.

4. Production Example (ViewModel & UseCase Test)
class TransferMoneyViewModelTest {

    private val transferUseCase: TransferMoneyUseCase = mockk()
    private val testDispatcher = StandardTestDispatcher()
    private lateinit var viewModel: TransferMoneyViewModel

    @Before
    fun setUp() {
        Dispatchers.setMain(testDispatcher)
        viewModel = TransferMoneyViewModel(transferUseCase, testDispatcher)
    }

    @After
    fun tearDown() {
        Dispatchers.resetMain()
    }

    @Test
    fun transferSuccess_updatesUiStateToSuccess() = runTest(testDispatcher) {
        // Given
        coEvery { transferUseCase("ACC_1", "ACC_2", 500.0) } returns Result.success(Unit)

        // When
        viewModel.onTransferClicked(from = "ACC_1", to = "ACC_2", amount = 500.0)
        advanceUntilIdle()

        // Then
        val state = viewModel.uiState.value
        assertTrue(state is TransferUiState.Success)
        coVerify(exactly = 1) { transferUseCase("ACC_1", "ACC_2", 500.0) }
    }
}

6. Pitfalls & Best Practices
Pitfall 1: Over-Mocking and Fragile Tests

Mocking every single internal collaborator makes tests tightly coupled to implementation details rather than behavior. When refactoring internal code, tests break even if output remains correct. Prefer state verification using Fakes.

Pitfall 2: Forgetting to Reset Main Dispatcher

Calling Dispatchers.setMain(testDispatcher) without calling Dispatchers.resetMain() in an @After method leaves the static Main dispatcher corrupted, causing flaky downstream test failures.

Pitfall 3: Mocking Data Classes

Never mock Kotlin data class or value objects. Instantiate them directly with actual test data (or create test fixture factory functions).

7. Interview Framework

30-Second Elevator Pitch

"Unit testing in Android focuses on verifying domain and presentation logic on the local JVM without emulator dependencies. We use JUnit with MockK for Kotlin-first mocking (supporting coroutine suspend functions via coEvery/coVerify) or in-memory Fakes for repositories. Clean architecture and constructor injection are the core design enablers for testability."

2-Minute Deep Dive

"In modern Android, unit tests should cover ~70% of the testing pyramid. To maximize execution speed, we isolate tests from Android framework classes.

When mocking, MockK is superior to Mockito in Kotlin because all Kotlin classes are final by default, and MockK seamlessly mocks suspend functions via coEvery/coVerify and captures arguments via slot(). However, to avoid brittle tests caused by over-mocking, we prefer using lightweight in-memory Fakes for repositories.

For coroutine testing, we replace Dispatchers.Main with StandardTestDispatcher using Dispatchers.setMain(), and execute tests inside runTest {}. We inject dispatchers into ViewModels so tests can precisely control virtual time advancement."

Must-Mention Checklist

1
Testing Pyramid: 70% Unit (JVM), 20% Integration, 10% E2E / UI.
2
Fake vs Mock: In-memory working implementation vs expectation verification.
3
MockK Coroutines: coEvery, coVerify, slot, relaxed = true.
4
Dispatcher Injection: Replacing hardcoded Dispatchers for deterministic testing.

9. Interview Questions (Self-Check)

Basic Questions

B1 — Where do Android unit tests run and why are they fast?
Easy▼
Unit tests live in src/test/java and run on the local host development machine's Java Virtual Machine (JVM). Because they do not require packaging an APK, booting an Android emulator, or interacting with a physical device, they execute in milliseconds.
B2 — What is the difference between a Mock and a Fake?
Easy▼
A Fake is a real, working lightweight implementation of an interface (e.g. an in-memory FakeUserRepository with a MutableList). A Mock is a simulated object created by a mocking library (MockK/Mockito) where return values are programmed (every {}) and interactions are verified (verify {}).
B3 — Why is MockK preferred over Mockito for Kotlin codebases?
Easy▼
MockK is built natively for Kotlin. It mocks final classes and methods by default (which Kotlin classes are), provides first-class support for coroutine suspending functions (coEvery / coVerify), supports Kotlin object / singleton mocking, and offers idiomatic Kotlin DSL syntax.

Intermediate Questions

I1 — What is a relaxed mock in MockK?
Medium▼
Created via mockk<MyClass>(relaxed = true), a relaxed mock provides simple default values (0, empty string, false, empty list) for all methods that haven't been explicitly stubbed with every {}. This avoids throwing MockKException: no answer found for... during test execution.
I2 — Why should you avoid hardcoding Dispatchers.IO in ViewModels?
Medium▼
Hardcoding Dispatchers.IO causes coroutines to run on real background thread pools during unit tests. This makes tests non-deterministic, introduces race conditions, and bypasses virtual time control in runTest. Injecting dispatchers allows tests to inject StandardTestDispatcher for deterministic control.
I3 — What is the purpose of slot<T> in MockK?
Medium▼
A slot<T>() captures the argument passed to a mocked function during execution. Inside every { mock.method(capture(slot)) } or verify { ... }, the slot stores the parameter so you can perform detailed assertions on its internal properties via slot.captured.
I4 — How does spyk differ from mockk in MockK?
Medium▼
mockk() creates a completely fake object where all method calls must be stubbed or return default values. spyk(realObject) wraps an existing real instance, delegating all method calls to the real implementation unless a specific method is explicitly overridden with every {}.

Senior & Scenario Questions

S1 — Why is over-mocking considered an anti-pattern and how do Fakes solve it?
HardScenario▼
Over-mocking ties unit tests to the exact private implementation details (which methods were invoked and in what order) rather than verifying behavioral outcomes. When refactoring code, over-mocked tests break even when the business logic is preserved. Fakes replicate contract behaviors with real state in memory, allowing true behavioral testing and easier refactoring.
S2 — How do you unit test a pure UseCase that validates user input before calling a repository?
HardScenario▼
1. Create a FakeUserRepository or mock with MockK.
2. Instantiate ValidateAndSubmitUseCase(fakeRepository).
3. Test invalid input: assert that it returns Result.failure(InvalidInputException) and verify that repository methods were NEVER invoked.
4. Test valid input: assert that it returns Result.success() and verify the repository received sanitized parameters.
S3 — You inherit legacy code where a ViewModel instantiates Room and Retrofit directly inside its constructor. How do you refactor it for unit testing?
HardScenario▼
1. Extract an interface DataRepository representing the required data contracts.
2. Implement DataRepositoryImpl that takes Room DAO and Retrofit API via constructor injection.
3. Refactor ViewModel to accept DataRepository and CoroutineDispatcher via its primary constructor.
4. Provide Hilt/Koin bindings in the DI module.
5. In the unit test, pass a FakeDataRepository and StandardTestDispatcher to instantiate the ViewModel cleanly on JVM.
