10B — Structural Patterns

Adapter, Decorator, Facade, and Proxy — how Android and its libraries compose objects to build larger structures without tight coupling.

ID: 10B ◈ Tier 2
🔍
1. Overview

What are Structural Patterns?

Structural patterns deal with object composition — how to assemble classes and objects into larger structures while keeping those structures flexible and efficient. They answer: "How do we make these two incompatible things work together?" or "How do we add behaviour without modifying a class?"

PatternIntentAndroid Example
AdapterMake incompatible interfaces work togetherRecyclerView.Adapter, Retrofit converters
DecoratorAdd behaviour to an object without changing its classOkHttp interceptors, caching repository wrapper
FacadeSimplify a complex subsystem with a unified interfaceRepository pattern, Retrofit over HTTP
ProxyControl access to an objectViewModel as data access proxy, lazy loading proxy
Senior Mental Model
Structural patterns are the most recognisable in Android because they appear in the framework itself. You use Adapter every time you build a RecyclerView, Decorator every time you add an OkHttp interceptor, and Facade every time you write a Repository. Knowing the formal names lets you reason about and communicate these decisions precisely.
⚙
2. How It Works

1. Adapter Pattern

Converts the interface of a class into another interface that clients expect. Allows classes to work together that otherwise couldn't due to incompatible interfaces.

// RecyclerView.Adapter adapts a List<Order> to RecyclerView's ViewHolder interface
class OrderAdapter(
    private val onClick: (Order) -> Unit
) : ListAdapter<Order, OrderAdapter.ViewHolder>(OrderDiffCallback()) {

    inner class ViewHolder(private val binding: ItemOrderBinding) :
        RecyclerView.ViewHolder(binding.root) {
        fun bind(order: Order) {
            binding.orderId.text = order.id
            binding.amount.text = order.formattedAmount
            binding.root.setOnClickListener { onClick(order) }
        }
    }
    override fun onCreateViewHolder(parent: ViewGroup, viewType: Int) =
        ViewHolder(ItemOrderBinding.inflate(LayoutInflater.from(parent.context), parent, false))

    override fun onBindViewHolder(holder: ViewHolder, position: Int) =
        holder.bind(getItem(position))
}

// Moshi converter adapter — adapts JSON to domain model
class BigDecimalAdapter {
    @FromJson fun fromJson(value: String) = BigDecimal(value)
    @ToJson   fun toJson(value: BigDecimal) = value.toPlainString()
}

2. Decorator Pattern

Attaches additional responsibilities to an object dynamically. Decorators provide a flexible alternative to subclassing for extending functionality.

OkHttp Interceptor Chain (each interceptor wraps the next): Request ──► AuthInterceptor │ ▼ RetryInterceptor │ ▼ LoggingInterceptor │ ▼ Network (actual HTTP call) │ ▼ (Response flows back up, each interceptor can modify it) 
// Each interceptor decorates the call — adds behaviour without changing OkHttpClient
class AuthInterceptor(private val tokenStore: TokenStore) : Interceptor {
    override fun intercept(chain: Interceptor.Chain): Response {
        val token = tokenStore.getAccessToken()
        val request = chain.request().newBuilder()
            .addHeader("Authorization", "Bearer $token")
            .build()
        return chain.proceed(request)  // delegates to next interceptor in chain
    }
}

// Caching Repository Decorator — wraps a repository without changing it
class CachedProductRepository(
    private val delegate: ProductRepository,  // same interface
    private val cache: LruCache<String, Product>
) : ProductRepository by delegate {  // delegates all other methods

    override suspend fun getProduct(id: String): Product {
        return cache.get(id) ?: delegate.getProduct(id).also { cache.put(id, it) }
    }
}

3. Facade Pattern

Provides a simplified interface to a complex subsystem. The subsystem remains accessible for advanced use, but the facade makes the common case easy.

// Repository is a facade over Room (local) + Retrofit (remote) + DataStore (prefs)
class ProductRepositoryImpl @Inject constructor(
    private val productDao: ProductDao,           // Room subsystem
    private val productApi: ProductApi,           // Retrofit subsystem
    private val prefsStore: DataStore<Preferences>  // DataStore subsystem
) : ProductRepository {

    // Callers just call getProducts() — they don't know about the 3 subsystems
    override fun getProducts(): Flow<List<Product>> =
        productDao.getAllProducts().map { it.map(ProductEntity::toDomain) }
            .onStart { refreshIfStale() }

    private suspend fun refreshIfStale() {
        val lastRefresh = prefsStore.data.first()[LAST_REFRESH_KEY] ?: 0L
        if (System.currentTimeMillis() - lastRefresh > CACHE_TTL) {
            val products = productApi.getProducts()
            productDao.replaceAll(products.map(ProductDto::toEntity))
        }
    }
}

4. Proxy Pattern

Provides a surrogate or placeholder for another object to control access to it. Three common proxy types: Remote (controls access to a remote object), Virtual (lazy loading), Protection (access control).

// ViewModel as Proxy — controls access to data, manages lifecycle, caches last value
@HiltViewModel
class OrderViewModel @Inject constructor(
    private val getOrders: GetOrdersUseCase
) : ViewModel() {
    // The UI never accesses the UseCase directly — the ViewModel proxies access
    val orders: StateFlow<UiState<List<Order>>> = getOrders()
        .map { UiState.Success(it) }
        .stateIn(viewModelScope, SharingStarted.Lazily, UiState.Loading)
}

// Lazy loading proxy using Kotlin's lazy delegate
class HeavyAnalyticsEngine {
    private val model: MLModel by lazy {
        MLModel.load("assets/model.tflite")  // only loaded when first accessed
    }
    fun predict(input: FloatArray) = model.run(input)
}

3. When to Use
PatternUse whenAvoid when
AdapterIntegrating third-party libraries with incompatible interfaces; RecyclerView alwaysWhen the interface can be changed at source
DecoratorAdding optional behaviour (logging, caching, auth) without subclassing; OkHttp interceptorsWhen there are too many decorators — deep chains become hard to debug
FacadeHiding complexity of subsystem combinations — Repository over Room+RetrofitWhen the subsystem is simple enough that the facade adds no value
ProxyLazy loading expensive resources; ViewModel lifecycle boundary; access controlWhen direct access is fine and no control is needed

4. Production Example

Automotive App — Vehicle Data Pipeline

An automotive app that reads sensor data via a Bluetooth SDK, adapts it, caches it, and facades the complexity from the ViewModel:

// ── ADAPTER: Bluetooth SDK → Domain interface ─────────────────
interface VehicleDataSource {
    fun getSpeed(): Flow<Int>
    fun getBatteryLevel(): Flow<Float>
}

class BluetoothVehicleAdapter(private val sdk: OBD2BluetoothSdk) : VehicleDataSource {
    override fun getSpeed(): Flow<Int> =
        sdk.readPid(OBD2Pid.VEHICLE_SPEED).map { it.toInt() }  // adapt SDK type
    override fun getBatteryLevel(): Flow<Float> =
        sdk.readPid(OBD2Pid.BATTERY_VOLTAGE).map { it / 12f }
}

// ── DECORATOR: add logging to any VehicleDataSource ───────────
class LoggingVehicleDataSource(
    private val delegate: VehicleDataSource,
    private val logger: Logger
) : VehicleDataSource by delegate {
    override fun getSpeed(): Flow<Int> =
        delegate.getSpeed().onEach { logger.d("Speed: $it km/h") }
}

// ── FACADE: VehicleRepository hides BT + Room + OBD2 details ──
class VehicleRepository @Inject constructor(
    private val liveSource: VehicleDataSource,   // bluetooth adapter (decorated)
    private val tripDao: TripDao                  // Room for history
) {
    fun getLiveSpeed() = liveSource.getSpeed()
    fun getTripHistory() = tripDao.getAllTrips().map { trips -> trips.map(TripEntity::toDomain) }
    suspend fun saveTrip(trip: Trip) = tripDao.insert(trip.toEntity())
}

// ── PROXY: ViewModel controls access and manages lifecycle ─────
@HiltViewModel
class DashboardViewModel @Inject constructor(
    private val repo: VehicleRepository
) : ViewModel() {
    val speed = repo.getLiveSpeed()
        .stateIn(viewModelScope, SharingStarted.WhileSubscribed(5000), 0)
}

5. Alternatives & Trade-offs

Decorator vs Subclassing

ApproachProsCons
DecoratorComposable — chain multiple behaviours; doesn't modify base classMany small classes; long chains can be hard to trace
SubclassingSimpler for single extensionRigid — can't swap decorators at runtime; violates OCP if base changes

Facade vs Exposing All Dependencies

Without a Repository facade, a ViewModel would need to know about Room DAO, Retrofit API, DataStore, and cache TTL logic. The facade collapses complexity to a single, stable interface. The trade-off: the facade can become a "God Repository" if it grows too large — consider splitting into feature-specific facades.

Kotlin by Delegation

Kotlin Advantage
Kotlin's by keyword implements the Decorator and Proxy patterns at the language level. class CachedRepo(val delegate: Repo) : Repo by delegate — every method is automatically delegated. You only override the methods you want to add behaviour to. This eliminates boilerplate delegation code.
⚠
6. Pitfalls & Best Practices

Decorator / Interceptor Pitfalls

Order Matters in Interceptor Chains
In OkHttp, Application Interceptors run before the network; Network Interceptors run after the connection is established. Placing the AuthInterceptor as a Network Interceptor means it won't run for cached responses. Auth should be an Application Interceptor. Order also matters for retry logic — the retry interceptor must wrap the auth interceptor.

Facade Anti-Pattern: God Repository

God Repository
A UserRepository with 30 methods covering profile, authentication, notifications, preferences, analytics, and billing is a Facade that has become a god object. Split by bounded context: UserProfileRepository, AuthRepository, NotificationRepository.

Adapter Best Practices

  • Use ListAdapter with DiffUtil.ItemCallback over plain RecyclerView.Adapter — diffing on a background thread, smooth animations
  • Adapter should not contain business logic — just binds data to views. Logic belongs in ViewModel or UseCase
  • Use custom Moshi/Gson adapters for non-standard types (BigDecimal, LocalDate, enums) instead of raw String parsing in the ViewModel

7. Interview Framework

30-Second Answer

"Structural patterns are about composing objects. Android uses all four constantly: Adapter — RecyclerView.Adapter bridges a List to RecyclerView's ViewHolder interface. Decorator — OkHttp interceptors chain together, each decorating the request without changing OkHttpClient. Facade — the Repository pattern hides Room, Retrofit, and DataStore behind one simple interface. Proxy — the ViewModel proxies data access for the UI, managing lifecycle and caching."

2-Minute Deep Dive

"The Decorator pattern in OkHttp is particularly elegant — each interceptor implements the same Interceptor interface and calls chain.proceed() to delegate to the next. You can add auth, logging, retry, or compression without touching any existing code. Kotlin's by delegation keyword makes it even cleaner — class CachedRepo(val delegate: Repo) : Repo by delegate auto-delegates all methods; you only override the ones that need caching. The Repository as Facade is the most universally applicable — it ensures the ViewModel never knows whether data came from Room or Retrofit, making offline-first strategies transparent to the caller."

Must-Mention Points

1
Adapter: RecyclerView.Adapter is the canonical Android example — converts data list to ViewHolder interface
2
Decorator: OkHttp interceptors — each wraps the next, adds behaviour without modifying OkHttpClient
3
Facade: Repository hides Room + Retrofit + DataStore — single interface for all data access
4
Proxy: ViewModel proxies data for the UI — controls access, survives configuration changes, caches last value
5
Kotlin by delegation: implements Decorator/Proxy idiomatically — auto-delegates, override only what changes

Do NOT Go Deeper On

  • Flyweight and Composite patterns (not commonly asked in Android interviews)
  • Bridge pattern (rarely relevant)
  • OkHttp internal chain mechanics unless asked specifically

Follow-up Q&A

QuestionAnswer
"What's the difference between Decorator and Proxy?"Decorator adds behaviour; Proxy controls access. The ViewModel proxy doesn't add new behaviour to the UseCase — it controls when and how the UI accesses it (lifecycle, caching). An auth interceptor decorator adds behaviour (the auth header) to every request.
"Is Retrofit itself a pattern?"Yes — it's a Facade over OkHttp, which is itself a Facade over Java's HttpURLConnection. Retrofit further uses Proxy (it creates proxy implementations of your API interface at runtime via reflection).
"How does ListAdapter improve on Adapter?"ListAdapter uses DiffUtil on a background thread to calculate the diff between old and new lists, then applies smooth animations automatically. No manual notifyDataSetChanged() needed.

Senior Insight

Senior Signal
Structural patterns reveal themselves when you trace dependencies. Draw the object graph: if you see a chain (A → B → C → D where each calls the next), it's Decorator. If multiple objects converge to one (A, B, C → Facade → callers), it's Facade. If one object stands in front of another (UI → Proxy → real data), it's Proxy. Recognising these patterns in code reviews is a senior engineering skill.

9. Interview Questions
Basic What design pattern does RecyclerView.Adapter implement? ⌄
The Adapter pattern. RecyclerView knows only about ViewHolders — it doesn't know what data you have or how it should be displayed. The Adapter bridges the gap by converting List<Order> (or any data) into the ViewHolder interface RecyclerView expects. The onBindViewHolder() method is the core adaptation — it maps a data item to a view.
Basic How does the Repository pattern relate to the Facade pattern? ⌄
The Repository pattern is the Facade pattern applied to data access. A Repository hides the complexity of multiple data sources (Room database, Retrofit API, DataStore, in-memory cache, third-party SDKs) behind a single, clean interface. Callers — ViewModel, UseCase — call repository.getProducts() without knowing whether data is being fetched from network, served from cache, or loaded from the local database.
Basic What is an OkHttp interceptor and which pattern does it implement? ⌄
An OkHttp interceptor implements the Decorator pattern (also called Chain of Responsibility in GoF terms). Each interceptor receives a Chain object, optionally modifies the request, calls chain.proceed(request) to pass to the next interceptor, and optionally modifies the response. Common interceptors: Auth (adds Bearer token), Logging (logs request/response), Retry (retries on failure), Cache (adds Cache-Control headers).
Intermediate Implement a caching repository decorator in Kotlin using the by keyword. ⌄
class CachedProductRepository(private val delegate: ProductRepository, private val cache: LruCache<String, Product>) : ProductRepository by delegate { override suspend fun getProduct(id: String): Product = cache.get(id) ?: delegate.getProduct(id).also { cache.put(id, it) } }

The by delegate clause auto-generates delegation for every method in ProductRepository. We only override getProduct to add caching behaviour. This is the Decorator pattern — we added behaviour without modifying or subclassing ProductRepositoryImpl.
Intermediate What's the difference between Application Interceptors and Network Interceptors in OkHttp? ⌄
Application Interceptors (added via addInterceptor()): run before OkHttp's core mechanics. They run even for cached responses, see the full original URL (before any redirects), and are called once per call. Best for: auth headers, retry logic, logging business-level requests.

Network Interceptors (added via addNetworkInterceptor()): run after OkHttp decides a real network request is needed. They see the wire-level request, including headers added by OkHttp itself. They are NOT called for cache hits. Best for: modifying gzip compression, low-level traffic analysis.
Intermediate How does ViewModel implement the Proxy pattern? ⌄
ViewModel acts as a Protection Proxy and Virtual Proxy: (1) The UI never directly accesses the UseCase or Repository — it only talks to the ViewModel. (2) The ViewModel controls when data is fetched (lazy init, only when UI subscribes), who can observe it (via StateFlow), and what lifecycle-sensitive cleanup happens. (3) Across configuration changes (screen rotation), the ViewModel survives while the Activity dies and recreates — the UI reconnects to the same proxy and gets the last cached state immediately.
Intermediate How would you use the Adapter pattern to integrate a third-party analytics SDK? ⌄
Define an interface AnalyticsTracker in your domain with methods like track(event: AnalyticsEvent). Create a FirebaseAnalyticsAdapter(val firebase: FirebaseAnalytics) : AnalyticsTracker that translates domain events to Firebase-specific calls. Inject AnalyticsTracker everywhere — never import FirebaseAnalytics in business code. If you switch to Mixpanel, you write a new adapter, not change 50 call sites. This also makes testing trivial — inject a fake adapter that records events.
Senior Design an OkHttp interceptor chain for a banking app with auth, retry, and certificate pinning. ⌄
Application Interceptors (outer to inner): (1) RetryInterceptor — catches network exceptions, retries up to 3 times with exponential backoff, but NOT for payment endpoints (idempotency concern). (2) AuthInterceptor — adds Bearer token; on 401, refreshes token once then retries original request using a Mutex to prevent concurrent refresh. Network Interceptor (none needed for this case). Separately: CertificatePinner — set on the OkHttpClient, not as an interceptor. It validates the server certificate against pinned hashes before any interceptor runs, preventing MITM even if a user installs a rogue CA.
Senior How does Retrofit use the Proxy pattern internally? ⌄
When you call retrofit.create(ApiService::class.java), Retrofit uses Java's Proxy.newProxyInstance() to create a dynamic proxy that implements your API interface. The proxy's InvocationHandler intercepts every method call, reads the Retrofit annotations (@GET, @POST, @Path, etc.) to build an HTTP request, executes it via OkHttp, and passes the response through your converter factory to return the typed result. This is why your API interface has no implementation — Retrofit generates it at runtime via reflection-based proxying.
Senior A Repository has grown to 40 methods. How do you refactor it using structural patterns? ⌄
A 40-method Repository is a "God Facade" — it has violated SRP. Refactor strategy:

1. Identify bounded contexts: group the 40 methods by feature domain (e.g., product listing, cart, orders, user profile). Each group becomes its own facade interface.
2. Apply ISP: split into ProductReader, CartRepository, OrderRepository, UserRepository.
3. Decorator for cross-cutting concerns: caching, logging, and auth are implemented as decorators wrapping the base implementations.
4. Aggregate facade if needed: if some callers legitimately need access to all domains, a thin ShoppingFacade can compose the smaller repositories — without duplicating logic.
