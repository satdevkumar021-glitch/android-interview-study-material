1. Overview

Permission Types

TypeGrant mechanismExamples
NormalAuto-granted at install timeINTERNET, ACCESS_NETWORK_STATE, VIBRATE, RECEIVE_BOOT_COMPLETED
DangerousRequires runtime request from userCAMERA, RECORD_AUDIO, READ_CONTACTS, ACCESS_FINE_LOCATION
SignatureAuto-granted if same signing certUsed for inter-app communication between your own apps
Key Rule
Always declare permissions in AndroidManifest.xml regardless of type. Normal permissions are auto-granted — you don't need to request them at runtime. Dangerous permissions must be requested at runtime on API 23+ (Android 6.0). Always check before use with ContextCompat.checkSelfPermission().

2. Normal vs Dangerous

Normal Permissions (auto-granted)

<!-- AndroidManifest.xml — declare, no runtime request needed -->
<uses-permission android:name="android.permission.INTERNET" />
<uses-permission android:name="android.permission.ACCESS_NETWORK_STATE" />
<uses-permission android:name="android.permission.VIBRATE" />
<uses-permission android:name="android.permission.WAKE_LOCK" />

Dangerous Permissions — must declare AND request

<!-- AndroidManifest.xml -->
<uses-permission android:name="android.permission.CAMERA" />
<uses-permission android:name="android.permission.RECORD_AUDIO" />
<uses-permission android:name="android.permission.ACCESS_FINE_LOCATION" />
<uses-permission android:name="android.permission.READ_CONTACTS" />
<uses-permission android:name="android.permission.POST_NOTIFICATIONS" /> <!-- API 33+ -->

Permission Groups

Dangerous permissions belong to groups. Granting one permission in a group may auto-grant others in the same group. However, always request each individual permission — don't rely on group behavior.

3. Runtime Permissions Flow

Complete Permission Request Flow

class CameraFragment : Fragment() {

    // Register launcher BEFORE fragment/activity is created
    private val requestPermissionLauncher = registerForActivityResult(
        ActivityResultContracts.RequestPermission()
    ) { isGranted ->
        if (isGranted) {
            openCamera()
        } else {
            showPermissionDeniedMessage()
        }
    }

    fun checkAndRequestCamera() {
        when {
            // 1. Already granted — proceed
            ContextCompat.checkSelfPermission(
                requireContext(), Manifest.permission.CAMERA
            ) == PackageManager.PERMISSION_GRANTED -> openCamera()

            // 2. Show rationale — user previously denied
            shouldShowRequestPermissionRationale(Manifest.permission.CAMERA) -> {
                showRationaleDialog {
                    requestPermissionLauncher.launch(Manifest.permission.CAMERA)
                }
            }

            // 3. Request permission — first time or after "don't ask again"
            else -> requestPermissionLauncher.launch(Manifest.permission.CAMERA)
        }
    }
}

shouldShowRequestPermissionRationale()

StateReturnsMeaning
First time askingfalseShow dialog directly, no rationale needed
User denied oncetrueShow rationale explaining why permission is needed
User checked "Don't ask again"falseDirect to Settings — can't request again programmatically
Permission grantedfalseAlready have permission

Multiple Permissions

private val multiplePermissionsLauncher = registerForActivityResult(
    ActivityResultContracts.RequestMultiplePermissions()
) { permissions ->
    val cameraGranted = permissions[Manifest.permission.CAMERA] == true
    val audioGranted = permissions[Manifest.permission.RECORD_AUDIO] == true
    if (cameraGranted && audioGranted) startVideoRecording()
}
multiplePermissionsLauncher.launch(arrayOf(
    Manifest.permission.CAMERA,
    Manifest.permission.RECORD_AUDIO
))

Location Permission Levels

PermissionAccuracyAPINotes
ACCESS_COARSE_LOCATION~1 km (cell/WiFi)1+Low precision, minimal privacy impact

// Android 10+ (API 29+): background location is a SEPARATE permission
// Step 1: request foreground location first
requestPermissionLauncher.launch(Manifest.permission.ACCESS_FINE_LOCATION)

// Step 2: ONLY after foreground is granted, request background
// This shows a different system dialog on Android 11+
requestPermissionLauncher.launch(Manifest.permission.ACCESS_BACKGROUND_LOCATION)
// Android 11: system redirects user to Settings for background permission

Notification Permission (POST_NOTIFICATIONS — API 33+)

<!-- AndroidManifest.xml -->
<uses-permission android:name="android.permission.POST_NOTIFICATIONS" />

// Runtime request on Android 13+ (API 33+)
// On Android 12 and below: notifications are auto-granted
if (Build.VERSION.SDK_INT >= Build.VERSION_CODES.TIRAMISU) {
    requestPermissionLauncher.launch(Manifest.permission.POST_NOTIFICATIONS)
}

// One-time permissions (Android 11+)
// User can grant camera/mic/location "only this time"
// App loses permission when it goes to background
// No code change needed — system handles it; just check permission before use
One-Time Permissions (API 30+)
Android 11 introduced "Only this time" for CAMERA, RECORD_AUDIO, and location. The permission is automatically revoked when the app goes to background. You don't need to handle this specially — just always call checkSelfPermission() before using sensitive features, even if you thought you had permission.

Modern Storage Approach

// Modern approach: scoped storage (Android 10+)
// Apps can read/write their own files WITHOUT permissions
// To access OTHER apps' media: request specific media permission

// Android 13+ granular media permissions
val mediaPermissions = if (Build.VERSION.SDK_INT >= 33) {
    arrayOf(
        Manifest.permission.READ_MEDIA_IMAGES,
        Manifest.permission.READ_MEDIA_VIDEO
    )
} else {
    arrayOf(Manifest.permission.READ_EXTERNAL_STORAGE)
}
multiplePermissionsLauncher.launch(mediaPermissions)

// SAF — user picks file, you get a Uri (no storage permission needed)
val openDocument = registerForActivityResult(ActivityResultContracts.OpenDocument()) { uri ->
    uri?.let { /* process the file */ }
}
openDocument.launch(arrayOf("application/pdf", "image/*"))

6. Android Version Evolution
Android VersionAPIPermission Changes
Android 6.0 Marshmallow23Runtime permissions introduced — dangerous perms must be requested at runtime
Android 10 Q29Scoped storage; background location separate permission; ACCESS_BACKGROUND_LOCATION added
Android 11 R30One-time permissions (camera, mic, location); background location: system redirects to Settings; MANAGE_EXTERNAL_STORAGE added; auto-reset permissions for unused apps
Android 12 S31/32Approximate vs precise location: user can grant coarse instead of fine; Bluetooth permissions split (BLUETOOTH_SCAN, BLUETOOTH_CONNECT)
Android 13 T33POST_NOTIFICATIONS required at runtime; granular media permissions (READ_MEDIA_IMAGES, READ_MEDIA_VIDEO, READ_MEDIA_AUDIO) replace READ_EXTERNAL_STORAGE; nearby WiFi permission

Senior Mental Model
Android permissions have evolved toward granularity and transparency. Each version restricts more and gives users more control. Always check the target API level and use Build.VERSION.SDK_INT to handle different permission models. Compile against the latest targetSdk so your app gets the new privacy features.

7. Interview Framework

30-Second Answer

"Normal permissions are auto-granted at install. Dangerous permissions require runtime requests via ActivityResultContracts.RequestPermission. The flow is: check if granted → show rationale if previously denied (shouldShowRequestPermissionRationale) → request → handle result. Always check before use, especially with one-time permissions on Android 11+."

2-Minute Answer

"Permissions split into normal (auto-granted, like INTERNET) and dangerous (require runtime request, like CAMERA). The modern way is ActivityResultContracts — register the launcher before the fragment starts, then when needed: check if already granted, check shouldShowRequestPermissionRationale to decide whether to show rationale UI, then launch the request. For location: coarse and fine are one-step; background location is a SEPARATE request on API 29+ and must happen after foreground is granted. Android 11 added one-time permissions — apps lose access when backgrounded. API 33 added POST_NOTIFICATIONS as a required runtime permission, so notification apps must request it on Android 13+. For storage: scoped storage on API 29+, granular media permissions on API 33+, and SAF for user-picked files with no permission needed."

Must-Mention Points

1
ActivityResultContracts.RequestPermission — modern API; must register before fragment/activity created
2
shouldShowRequestPermissionRationale() — shows rationale after first denial, returns false after "don't ask again"
3
Background location (API 29+) — SEPARATE request, must have foreground first
4
POST_NOTIFICATIONS required on API 33+ — needs runtime request
5
One-time permissions (API 30+) — revoked when app goes background; always check before use

Senior Insight

Senior Differentiator
Understand that "don't ask again" can never be detected directly (shouldShowRationale returns false for both first-time and permanently denied). The pattern to detect "permanently denied": track whether you've asked before using SharedPreferences. If you asked before AND shouldShowRationale is false AND permission is denied → permanently denied → direct to Settings via Intent(Settings.ACTION_APPLICATION_DETAILS_SETTINGS).

9. Interview Questions
1. What is the difference between normal and dangerous permissions?
Basic⌄
Normal permissions (like INTERNET, VIBRATE) are automatically granted at install time — no user interaction needed. Dangerous permissions (like CAMERA, LOCATION, READ_CONTACTS) can access sensitive user data or device features, so they must be declared in the manifest AND explicitly requested at runtime on Android 6+ (API 23). The user must grant them; they can be revoked at any time.
2. What does shouldShowRequestPermissionRationale() return in each state?
Basic⌄
First time asking: false (no rationale needed, show dialog). User denied once: true (show rationale UI explaining why you need it). User checked "Don't ask again": false (same as first time — can't distinguish programmatically). Permission already granted: false. The key gotcha: false doesn't tell you whether it's first-time or permanently denied — you must track "has the user been asked before" separately.
3. What changed about notifications in Android 13?
Basic⌄
Android 13 (API 33) made POST_NOTIFICATIONS a dangerous permission requiring a runtime request. On Android 12 and below, apps could post notifications without permission. Apps targeting API 33+ must declare the permission in the manifest and request it at runtime. The user can deny it, in which case all notifications from the app are blocked. Apps upgraded from lower target SDK get a one-time automatic grant prompt.
4. How do you request background location on Android 10+?
Intermediate⌄
Two separate requests: Step 1: request ACCESS_FINE_LOCATION (or COARSE). Wait for it to be granted. Step 2: only after foreground is granted, request ACCESS_BACKGROUND_LOCATION. On Android 11+, the system dialog for background location has no "Allow all the time" option — it redirects the user to Settings where they manually select "Allow all the time." Request both permissions in separate user actions, not simultaneously. Play Store requires a declaration explaining why you need background location.
5. What are one-time permissions and how do they affect your app?
Intermediate⌄
Introduced in Android 11. Users can grant CAMERA, RECORD_AUDIO, and location permissions "Only this time." The permission is automatically revoked when the app goes to background or the user switches away. No code change required — your app doesn't know it's a one-time grant. The implication: always call checkSelfPermission() before using these features, even mid-session. If the user put your app in background while recording, you might lose the permission when returning.
6. What is scoped storage and which permissions does it affect?
Intermediate⌄
Scoped storage (Android 10+) gives each app its own private storage area it can read/write without permissions, and limits access to shared storage. Apps can access their own app-specific directory (getFilesDir()) freely. For shared media: use MediaStore API. For arbitrary files: use SAF (user picks via system file picker, no permission needed). MANAGE_EXTERNAL_STORAGE grants broad access but requires Play Store justification. On API 33+, READ_EXTERNAL_STORAGE is split into READ_MEDIA_IMAGES, READ_MEDIA_VIDEO, READ_MEDIA_AUDIO.
7. How do you handle the "permanently denied" (Don't ask again) case?
Intermediate⌄
You can't directly detect "don't ask again" since shouldShowRationale returns false for both first-time and permanently denied. Pattern: store a boolean (e.g., "hasAskedForCamera") in SharedPreferences. If hasAskedForCamera is true AND shouldShowRationale returns false AND permission is DENIED → permanently denied. Show a dialog explaining the situation and open Settings: Intent(Settings.ACTION_APPLICATION_DETAILS_SETTINGS, Uri.parse("package:" + packageName)).
8. Walk through the full permission request flow for a camera feature in a Compose app.
Senior⌄
In Compose, use rememberLauncherForActivityResult(ActivityResultContracts.RequestPermission()). On button tap: 1) Check ContextCompat.checkSelfPermission — if GRANTED, open camera. 2) Check shouldShowRequestPermissionRationale — if true, show rationale dialog with "OK" button that triggers launcher.launch(CAMERA). 3) Otherwise, launch directly. In result callback: if granted → open camera; if denied → check if permanently denied (using stored pref), if so show Settings dialog. Handle lifecycle correctly — the launcher must be registered at composition time, not in a click handler.
9. What is the Storage Access Framework (SAF) and when do you use it?
Senior⌄
SAF lets users pick files from any location (local storage, Google Drive, Dropbox) via the system file picker. The app receives a content URI — no storage permissions needed. Use SAF when users need to select arbitrary file types (PDFs, documents, custom formats). Use ActivityResultContracts.OpenDocument for single file, OpenMultipleDocuments for multiple. The returned URI has persisted permissions (take persistable URI permission for across-session access). Contrast with MediaStore (media collections only) and direct file access (app-private directory only).
10. How does Android 12's approximate location affect your app?
Scenario⌄
Android 12 (API 31) lets users grant only approximate location (COARSE) even when your app requests precise (FINE). The permission dialog shows "Precise" vs "Approximate" options. Your app must handle receiving COARSE when it requested FINE. Design: if the feature genuinely requires precise GPS, check that ACCESS_FINE_LOCATION is granted — don't just check that any location permission is granted. If the user chose approximate, show UI explaining why precise is needed for this specific feature, or degrade gracefully to coarse-based functionality.
