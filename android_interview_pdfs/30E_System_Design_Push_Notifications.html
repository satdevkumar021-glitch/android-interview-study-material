30E — Push Notification System

Design a complete Android push notification system: FCM architecture, token management, data vs notification messages, custom notification channels, deep link handling, grouping, foreground handling, and delivery receipts.

ID: 30E ★ Senior Differentiator
🔍
1. Problem Statement

Requirements

Functional

  • Transactional alerts: order shipped, payment confirmed, security alerts
  • Marketing / promotional: new deals, personalized recommendations
  • Deep link handling: notification tap opens the correct in-app screen
  • Notification grouping: multiple messages bundled under one summary
  • Handle notification when app is in foreground (don't show system notification)
  • Delivery receipts: know whether the user received/tapped the notification

Non-Functional

  • No notification for revoked consent (POST_NOTIFICATIONS permission denied)
  • Token refresh handled automatically — server always has valid token
  • Correct channel importance — transactional uses HIGH, marketing uses DEFAULT
  • Works on all Android versions from API 26+

3. Data Flow

FCM Token Registration Flow

App starts for first time
  → FirebaseMessaging.getInstance().getToken()
  → Token generated by Firebase
  → FirebaseMessagingService.onNewToken(token) called
  → Store token in SharedPreferences (local)
  → POST /notifications/register { token, deviceId, platform: "android" }
  → Server stores: userId → [token1(phone), token2(tablet)]

Token refresh (rare, but must handle):
  → FCM rotates token if: app reinstalled, data cleared, new device
  → onNewToken() called again with new token
  → Same flow: POST /notifications/register with new token
  → Server upserts token for this deviceId

Notification Message Delivery

Backend sends order shipped notification:
  → FCM HTTP v1 POST with { token, notification: {title, body}, data: {...} }

Case 1: App in BACKGROUND
  → System shows notification automatically (from `notification` field)
  → User taps notification
  → Intent with data payload delivered to MainActivity
  → NavController.handleDeepLink(intent)

Case 2: App in FOREGROUND
  → System does NOT show notification (if `notification` field present)
  → onMessageReceived() called
  → App shows in-app snackbar / banner
  → OR: build and show notification manually from onMessageReceived()

Case 3: Data-only message (no `notification` field)
  → onMessageReceived() always called (foreground AND background)
  → App handles display entirely — full control
  → This is the RECOMMENDED pattern for apps wanting full control

4. Key Design Decisions

1. Data Message vs Notification Message

TypeWhen deliveredWho shows notificationUse when
Notification messageBackground: always. Foreground: onMessageReceived onlySystem (background), App (foreground)Simple notifications, don't need foreground handling
Data messageAlways (foreground + background)App always (onMessageReceived)Full control, rich notifications, foreground handling needed
Both (data + notification)System shows notification in backgroundSystem (background), App (foreground)Fallback behavior in background, custom in foreground
Recommendation
Use data-only messages for full control. Always show notifications manually in onMessageReceived(). This ensures consistent behavior in foreground and background, and allows custom notification styling.

2. Notification Channels

// Create channels in Application.onCreate() — idempotent
fun createNotificationChannels(context: Context) {
    if (Build.VERSION.SDK_INT < Build.VERSION_CODES.O) return
    val manager = context.getSystemService(NotificationManager::class.java)

    // Transactional: HIGH importance — makes sound, pops up
    manager.createNotificationChannel(NotificationChannel(
        "transactional", "Orders & Payments",
        NotificationManager.IMPORTANCE_HIGH
    ).apply { description = "Order updates, payment confirmations, security alerts" })

    // Marketing: DEFAULT importance — silent, no popup
    manager.createNotificationChannel(NotificationChannel(
        "marketing", "Promotions",
        NotificationManager.IMPORTANCE_DEFAULT
    ).apply { description = "Deals, offers, and personalized recommendations" })
}

6. Scalability

Delivery Receipts

// When notification is delivered:
override fun onMessageReceived(message: RemoteMessage) {
    val notifId = message.data["notification_id"] ?: return
    // Send delivery receipt to backend
    CoroutineScope(Dispatchers.IO).launch {
        notificationApi.sendReceipt(DeliveryReceipt(
            notificationId = notifId,
            status = "DELIVERED",
            timestamp = System.currentTimeMillis()
        ))
    }
    showNotification(message)
}

// When user taps notification — track "opened"
// In the Activity/Composable that receives the deep link intent:
intent.extras?.getString("notification_id")?.let { notifId ->
    notificationApi.sendReceipt(DeliveryReceipt(notifId, "OPENED", ...))
}

7. Interview Framework

30-Second Answer

"The system uses FCM for delivery. The app registers its FCM token on launch and whenever onNewToken() fires — token sent to the backend and stored per userId+deviceId. I use data-only messages so onMessageReceived() always runs, giving full control in foreground and background. Notification channels separate transactional (IMPORTANCE_HIGH) from marketing (IMPORTANCE_DEFAULT). Deep links use NavDeepLinkBuilder + TaskStackBuilder for correct back stack. Groups bundle related notifications with a summary notification."

2-Minute Answer

"FCM architecture: app → Firebase → FCM → device. Token lifecycle: onNewToken() sends the token to our backend. Always re-register on every app start (server upserts) to handle reinstalls. For message types: data-only messages are preferred over notification messages — onMessageReceived() fires regardless of app state, giving us full rendering control. For importance: transactional notifications (orders, security alerts) use NotificationChannel with IMPORTANCE_HIGH — they pop over other apps and make sound. Marketing uses IMPORTANCE_DEFAULT — delivered silently to the notification shade. For deep links: NavDeepLinkBuilder creates an intent that navigates to the right screen with proper arguments, and TaskStackBuilder ensures back button works correctly. For notification grouping: set the same GROUP_KEY on individual notifications and add a summary notification with setGroupSummary(true). To handle notifications in foreground: detect in onMessageReceived() whether the chat screen is currently visible — if yes, show an in-app banner instead of a system notification. Delivery receipts: POST /notifications/{id}/receipt when onMessageReceived fires (DELIVERED) and again when the user taps (OPENED). Handle invalid tokens: FCM returns INVALID_REGISTRATION for uninstalled devices — server must delete that token."

Must-Mention Points

1
FCM flow: app → Firebase → FCM → device; token registered per userId+deviceId on server
2
Data-only messages → onMessageReceived always fires; full app control in all states
3
Notification channels: IMPORTANCE_HIGH (transactional) vs IMPORTANCE_DEFAULT (marketing)
4
Deep links: NavDeepLinkBuilder + TaskStackBuilder for correct back stack
5
Handle INVALID_REGISTRATION → delete stale token from server to prevent sending to uninstalled apps

Senior Insight

Senior Differentiator
Know that notification messages in the background are shown by the system — your onMessageReceived() is NOT called if the app is in the background and the payload has a notification field. The data in the data field is put in the activity's intent when the user taps. This is the #1 source of confusion in FCM integration: developers assume onMessageReceived always fires, but it doesn't for notification messages in the background. Use data-only to avoid this asymmetry.

9. Interview Questions
1. What is an FCM token and when does it change?
Basic⌄
An FCM token is a unique identifier for an app installation on a specific device. FCM uses it to route messages. The token changes when: app is uninstalled and reinstalled, user clears app data, app is restored to a new device. When it changes, onNewToken(newToken) is called — you must send the new token to your server. Always call FirebaseMessaging.getInstance().getToken() on app launch and register it (server upserts) to ensure the server has the current token.
2. What is the difference between notification messages and data messages in FCM?
Basic⌄
Notification messages: have a "notification" JSON field (title, body). In background: system shows the notification automatically. onMessageReceived is NOT called when in background. In foreground: onMessageReceived is called, system does NOT show notification. Data messages: only have a "data" field. onMessageReceived is ALWAYS called regardless of app state. App handles all display logic. Recommendation: use data-only messages for consistent behavior — always goes through onMessageReceived in all app states.
3. What are notification channels and why were they introduced?
Basic⌄
NotificationChannels (API 26+) let users control notification behavior per category instead of per app. Apps define channels with importance levels: IMPORTANCE_HIGH (heads-up, sound), DEFAULT (sound only), LOW (silent), MIN (no visual). Users can disable specific channels without disabling all notifications. Required since API 26 — notifications without a valid channel are silently dropped. Create channels in Application.onCreate() — creation is idempotent (safe to call multiple times).
4. How do you handle a notification tap that should open a specific screen?
Intermediate⌄
Use NavDeepLinkBuilder to create a PendingIntent pointing to a specific NavGraph destination with arguments. Wrap with TaskStackBuilder to ensure the back stack is correct (Back button returns to the parent screen, not exits the app). Attach this PendingIntent to the notification's setContentIntent(). When the user taps: PendingIntent fires, MainActivity opens (or resumes), NavController navigates to the destination. Handle the case where MainActivity was already running: check getIntent() in onNewIntent() for the deep link data.
5. How do you handle a notification when the app is in the foreground?
Intermediate⌄
With data-only messages, onMessageReceived() fires in foreground. Decide based on context: if the user is already on the chat screen where the notification applies, show a subtle in-app banner (Snackbar, custom composable toast) rather than interrupting with a system notification. If they're on a different screen, show a normal notification or an in-app heads-up. Implement by: checking the current NavDestination ID against the notification's target screen. If match → show in-app UI. If not → show system notification.
6. How do you implement notification grouping?
Intermediate⌄
Set .setGroup(GROUP_KEY) on each notification with a consistent group key per category (e.g., per chat conversation). Create a separate summary notification with .setGroup(GROUP_KEY) and .setGroupSummary(true). Style the summary with NotificationCompat.InboxStyle(). Android bundles all notifications with the same GROUP_KEY under the summary. Required: show the summary notification alongside individual notifications. On Android 7+, system auto-groups if there are 4+ notifications with the same group key, but explicitly setting the summary ensures control over the summary text.
7. How do you handle stale/invalid FCM tokens?
Intermediate⌄
FCM HTTP API returns error codes for invalid tokens: INVALID_REGISTRATION (token format invalid), NOT_REGISTERED (app uninstalled or token revoked). Server must: detect these error codes in FCM API responses, immediately delete the corresponding token from the database, not retry sending to that token. If sending to multiple tokens for a user (multi-device), remove only the failed token — not all tokens. Also: prune tokens not active in 60+ days as a maintenance policy. Client: always re-register on launch to replace stale tokens.
8. How do you implement notification delivery receipts?
Senior⌄
Two events to track: DELIVERED (device received it) and OPENED (user tapped). DELIVERED: POST receipt in onMessageReceived() with notification_id from the data payload. Fire and forget — use a background coroutine. OPENED: attach the notification_id to the PendingIntent's data. When MainActivity receives the intent (from notification tap), extract notification_id and POST OPENED receipt. Be careful: if the app is killed and relaunched from the notification, handle this in onCreate() too. Store receipts locally if offline (Room) and flush when connected.
9. How does POST_NOTIFICATIONS permission on Android 13+ affect your system?
Senior⌄
Android 13 (API 33) requires POST_NOTIFICATIONS runtime permission. On API 33+: must declare <uses-permission android:name="android.permission.POST_NOTIFICATIONS"/> and request at runtime. Without permission: NotificationManager.notify() silently does nothing. FCM still delivers the data message (onMessageReceived fires) — the permission only affects showing system notifications. Approach: request permission on first launch or when the user first accesses a feature that needs notifications. Show rationale explaining value. If denied: suppress all notification display, but FCM data messages still arrive for in-app banners.
10. Design a notification system that distinguishes transactional from marketing pushes.
Scenario⌄
Server: tag every notification with a type field in the data payload (type: "ORDER_SHIPPED" vs "PROMO_DEAL"). Client: in onMessageReceived(), route to the correct channel based on type. Transactional → channel "transactional" (IMPORTANCE_HIGH: heads-up notification, sound, vibration). Marketing → channel "marketing" (IMPORTANCE_DEFAULT: silent). Users can disable the "marketing" channel in Settings without losing order updates. Backend: respect opt-out preferences — don't send marketing to users who unsubscribed (check marketing_consent before sending). Include campaign_id in data payload for analytics tracking.
