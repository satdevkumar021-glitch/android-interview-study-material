38A — Kotlin Multiplatform (KMP/KMM)

Sharing Kotlin code across Android, iOS, Web, and Desktop using expect/actual, shared modules, and platform-specific implementations.

ID: 38A ⭐ Tier 2 — Senior Differentiator
🔍
1. Overview

What is KMP?

Kotlin Multiplatform (KMP) allows you to share Kotlin code across multiple platforms — Android, iOS, Web, and Desktop — while retaining full access to native APIs and native UI on each platform. You write business logic once in Kotlin and compile it to the appropriate target format per platform.

KMP vs KMM

KMM (Kotlin Multiplatform Mobile) is a subset of KMP focused specifically on Android and iOS mobile development. KMM is now stabilised under the broader KMP umbrella. When interviewers say "KMM", they mean KMP applied to mobile.

How the Shared Module Compiles

Desktop (JVM)JVM bytecodeJVM

What IS Shared

  • Domain layer — use cases, business logic, domain models
  • Data layer — repositories, data sources, API clients (Ktor), database (SQLDelight)
  • Networking logic — request/response mapping, error handling
  • Coroutines & Flow — kotlinx.coroutines-core is fully multiplatform
  • Serialization — kotlinx.serialization is multiplatform

What is NOT Shared

  • UI layer — Jetpack Compose is Android-only; iOS uses SwiftUI or UIKit
  • Platform-specific APIs — camera, GPS, biometrics — abstracted via expect/actual
  • DI frameworks — Hilt is Android-only; iOS uses manual DI or Koin
  • Navigation — Navigation Compose (Android) vs NavigationStack (iOS)
Senior Mental Model
KMP is not "write once run anywhere" (that's Flutter). It is "share logic, native UI". You eliminate duplicate business logic (~60% of codebase) while each platform retains its native look, feel, and performance. The correct mental model is: shared kernel + native shell per platform.

2. How It Works

expect / actual — The Core Mechanism

The expect / actual mechanism is how KMP handles platform-specific code. You declare an expect declaration in commonMain and provide an actual implementation in each platform source set.

// commonMain — declare the contract
expect class PlatformLogger() {
    fun log(message: String)
}

// androidMain — Android implementation
actual class PlatformLogger actual constructor() {
    actual fun log(message: String) = Log.d("KMP", message)
}

// iosMain — iOS implementation
actual class PlatformLogger actual constructor() {
    actual fun log(message: String) = NSLog(message)
}

Shared Repository Pattern

// commonMain — shared domain + data
class UserRepository(
    private val apiClient: UserApiClient,  // Ktor

iOS Integration

KMP generates an .xcframework from the shared module. iOS app adds it via Xcode or CocoaPods, then consumes Kotlin classes directly in Swift:

// Swift (iOS) — consuming KMP shared module
import shared

let repo = UserRepository(apiClient: apiClient, database: database)
let user = try await repo.getUser(id: "u_123")
// Kotlin suspend functions become async/await in Swift automatically

3. When to Use It

Use KMP When

Good Fit
  • Same business logic needed on Android AND iOS — account management, transaction processing, validation rules
  • Team has strong Kotlin expertise — KMP is Kotlin-first; no new language to learn for Android devs
  • New projects — far easier to start KMP-first than to retrofit it
  • You want native UI performance — no bridge overhead, native rendering
  • You need platform-specific features — camera, push, biometrics stay native
  • You want to keep separate Android/iOS teams — both teams consume the shared module as a library

Do NOT Use KMP When

Poor Fit
  • UI-heavy apps where most complexity is in animation, custom UI — little shareable logic
  • Small teams without iOS experience — KMP generates native iOS code that someone must integrate and test on iOS
  • Legacy apps with deep Java integration — retrofitting KMP is complex; not worth it for maintenance projects
  • Team is primarily React/JS — consider React Native instead
  • Tight delivery timelines with no KMP experience — initial setup and iOS toolchain adds friction

KMP vs Flutter Decision Matrix

FactorKMPFlutter
UI sharingNo — native UI per platformYes — single UI (Canvas-rendered)
Native feelFull native (Compose / SwiftUI)Very close but not native widgets
LanguageKotlin (Android team strength)Dart (new language to learn)
Code sharingLogic only (~60%)Logic + UI (~90%)
iOS team involvementStill needs Swift dev for UIFlutter dev handles both
Ecosystem maturityStable (JetBrains, JetBrains-backed)Mature (Google-backed)

4. Production Example
Scenario
Banking app: shared account balance and transaction domain layer. The KMP shared module is consumed by the Android app (Hilt + Compose) and the iOS app (SwiftUI), eliminating duplicate repository and API code.

1. build.gradle.kts — Shared KMP Module

// shared/build.gradle.kts
plugins {
    kotlin("multiplatform")
    id("com.android.library")
    kotlin("plugin.serialization")
    id("app.cash.sqldelight")
}

kotlin {
    androidTarget {
        compilations.all {
            kotlinOptions { jvmTarget = "17" }
        }
    }

    val iosTargets = listOf(
        iosX64(), iosArm64(), iosSimulatorArm64()
    )
    iosTargets.forEach { target ->
        target.binaries.framework {
            baseName = "shared"
            isStatic = true
        }
    }

    sourceSets {
        val commonMain by getting {
            dependencies {
                implementation("io.ktor:ktor-client-core:2.3.7")
                implementation("io.ktor:ktor-client-content-negotiation:2.3.7")
                implementation("io.ktor:ktor-serialization-kotlinx-json:2.3.7")
                implementation("app.cash.sqldelight:runtime:2.0.1")
                implementation("org.jetbrains.kotlinx:kotlinx-coroutines-core:1.7.3")
                implementation("org.jetbrains.kotlinx:kotlinx-serialization-json:1.6.2")
            }
        }
        val androidMain by getting {
            dependencies {
                implementation("io.ktor:ktor-client-android:2.3.7")
                implementation("app.cash.sqldelight:android-driver:2.0.1")
            }
        }
        val iosMain by creating {
            dependsOn(commonMain)
            dependencies {
                implementation("io.ktor:ktor-client-darwin:2.3.7")
                implementation("app.cash.sqldelight:native-driver:2.0.1")
            }
        }
    }
}

sqldelight {
    databases {
        create("BankingDatabase") {
            packageName.set("com.banking.db")
        }
    }
}

2. Shared Domain Model + Repository Interface (commonMain)

// commonMain/domain/model/Account.kt
data class Account(
    val id: String,
    val accountNumber: String,
    val balance: Double,
    val currency: String
)

data class Transaction(
    val id: String,
    val amount: Double,
    val description: String,
    val timestamp: Long,
    val type: TransactionType
)

enum class TransactionType { CREDIT, DEBIT }

// commonMain/domain/repository/AccountRepository.kt
interface AccountRepository {
    suspend fun getAccount(id: String): Result<Account>
    fun observeTransactions(accountId: String): Flow<List<Transaction>>
    suspend fun transferFunds(fromId: String, toId: String, amount: Double): Result<Unit>
}

// commonMain/data/repository/AccountRepositoryImpl.kt
class AccountRepositoryImpl(
    private val apiClient: AccountApiClient,
    private val localDb: BankingDatabase
) : AccountRepository {

    override suspend fun getAccount(id: String): Result<Account> =
        runCatching { apiClient.fetchAccount(id) }

    override fun observeTransactions(accountId: String): Flow<List<Transaction>> =
        localDb.transactionQueries.selectByAccount(accountId).asFlow().mapToList()

    override suspend fun transferFunds(
        fromId: String, toId: String, amount: Double
    ): Result<Unit> = runCatching {
        apiClient.transfer(TransferRequest(fromId, toId, amount))
    }
}

3. Android-Specific Driver Implementation (androidMain)

// androidMain/di/DatabaseDriverFactory.kt
actual class DatabaseDriverFactory actual constructor(
    private val context: Context
) {
    actual fun createDriver(): SqlDriver =
        AndroidSqliteDriver(BankingDatabase.Schema, context, "banking.db")
}

// androidMain/di/NetworkModule.kt (Hilt)
@Module
@InstallIn(SingletonComponent::class)
object KmpModule {

    @Provides @Singleton
    fun provideAccountRepository(
        @ApplicationContext context: Context
    ): AccountRepository {
        val driver = DatabaseDriverFactory(context).createDriver()
        val database = BankingDatabase(driver)
        val httpClient = HttpClient(Android) {
            install(ContentNegotiation) { json() }
        }
        return AccountRepositoryImpl(
            AccountApiClient(httpClient),
            database
        )
    }
}

4. Android ViewModel Consuming Shared Module

// androidApp/presentation/AccountViewModel.kt
@HiltViewModel
class AccountViewModel @Inject constructor(
    private val repository: AccountRepository  // from KMP shared module
) : ViewModel() {

    private val _account = MutableStateFlow<AccountUiState>(AccountUiState.Loading)
    val account: StateFlow<AccountUiState> = _account.asStateFlow()

    val transactions: StateFlow<List<Transaction>> =
        repository.observeTransactions("acc_001")  // KMP Flow → StateFlow
            .stateIn(viewModelScope, SharingStarted.WhileSubscribed(5000), emptyList())

    fun loadAccount(id: String) {
        viewModelScope.launch {
            repository.getAccount(id)
                .onSuccess { _account.value = AccountUiState.Success(it) }
                .onFailure { _account.value = AccountUiState.Error(it.message) }
        }
    }
}

6. Pitfalls & Best Practices

iOS Binary Size Increase

Kotlin/Native includes the Kotlin runtime in the generated .xcframework, increasing binary size by 2–5 MB. Mitigate with:

  • Use isStatic = true (static framework) to allow Xcode linker to dead-strip unused code
  • Enable linkerOpts("-dead_strip") in release builds
  • Measure with xcrun bitcode_strip and monitor size in CI

Coroutine Threading on iOS (Legacy Issue)

⚠ Known Pitfall
In older Kotlin/Native (pre-1.6), objects passed between threads had to be frozen (immutable), which broke standard coroutine patterns. Since Kotlin 1.6+ with the new memory model (kotlin.native.binary.memoryModel=experimental / default since 1.7.20), this is resolved. If you see InvalidMutabilityException or FreezingException, upgrade Kotlin and enable the new memory model. 
// gradle.properties — new memory model (required pre-1.7.20)
kotlin.native.binary.memoryModel=experimental

expect/actual Boilerplate

Every platform-specific class needs an expect declaration plus actual implementations for every target. With many targets (Android, iOS, Web, Desktop), this multiplies quickly. Strategies:

  • Minimise expect/actual surface: push platform code to the edges, share as much as possible
  • Use interfaces in commonMain + factory pattern rather than expect/actual classes
  • Use expect fun for simple utilities rather than whole classes

SQLDelight is More Complex than Room

SQLDelight uses SQL schema files (.sq) and generates typed Kotlin queries — more explicit than Room annotations. Setup gotchas:

  • Driver must be provided per-platform via expect/actual or DI — not automatic
  • Migrations must be written in SQL, not Kotlin DSL like Room
  • Debugging SQL is done via the generated code, not Room's easy @Database inspector

Ktor Requires More Configuration than Retrofit

// commonMain — Ktor client (more verbose than Retrofit)
val client = HttpClient {
    install(ContentNegotiation) {
        json(Json { ignoreUnknownKeys = true })
    }
    install(HttpTimeout) {
        requestTimeoutMillis = 30_000
    }
    install(Logging) {
        level = LogLevel.ALL
    }
}

// vs Retrofit — @GET, @POST annotations generate everything
// Ktor: manual request building, explicit endpoint calls

Memory Management — Kotlin/Native GC

Kotlin/Native uses a different garbage collector than JVM. With the new memory model (Kotlin 1.7.20+), it is a tracing GC that runs concurrently. Key differences:

  • No generational GC — full heap traversal; can pause on large heaps
  • Cycle detection is not automatic in all cases with the new MM; avoid reference cycles in long-lived objects
  • Finalizers behave differently — do not rely on finalize() for cleanup; use explicit resource management

Best Practices

  1. Keep commonMain pure — no platform imports, no Android/iOS-specific APIs
  2. Use interfaces in commonMain, expect/actual only for primitives (date, UUID, dispatcher)
  3. Use Dispatchers.Default in shared code — not Dispatchers.Main (platform-specific)
  4. Test commonMain with kotlin.test — runs on both JVM and native
  5. Wrap coroutine scopes for iOS consumption (KMP-NativeCoroutines or SKIE library helps)
  6. Measure iOS binary size in CI — set a size budget and fail builds that exceed it

7. Interview Answer Framework

30-Second Answer

"KMP lets you share business logic — domain models, repositories, networking, and data layers — across Android and iOS using a single Kotlin codebase. The expect/actual mechanism handles platform differences. On Android it compiles to JVM bytecode, on iOS it generates an xcframework via Kotlin/Native. The UI stays native — Compose on Android, SwiftUI on iOS. You share roughly 60% of the codebase while keeping full native performance."

2-Minute Structured Answer

"KMP is Kotlin's multiplatform build system. You define a shared module with three main source sets: commonMain holds the platform-agnostic code — domain models, use cases, repositories — and androidMain / iosMain hold platform-specific implementations.

The core mechanism is expect/actual: in commonMain you declare an expect class or function — a contract — and each platform source set provides the actual implementation. This is how you abstract things like logging, date formatting, and database drivers.

For networking, we use Ktor instead of Retrofit — it's multiplatform and uses OkHttp on Android and NSURLSession on iOS under the hood. For persistence, SQLDelight replaces Room and compiles to platform-native SQLite drivers. Coroutines and Flow work on all platforms, which means shared repositories can expose reactive streams that both Android ViewModels and iOS Swift code can observe.

The iOS side: KMP generates an .xcframework. The iOS app adds it and consumes Kotlin classes directly in Swift — Kotlin suspend functions map to Swift async/await automatically. The trade-off is that you still need an iOS developer for the SwiftUI layer and for iOS CI/CD integration. KMP is the right choice when the team is Kotlin-first and needs iOS without a full Flutter rewrite."

Must-Mention Points (Show Deep Knowledge)

1
commonMain / androidMain / iosMain source sets — the fundamental structure of any KMP project
2
expect/actual — how platform-specific implementations are declared and provided; the contract mechanism
3
Ktor + SQLDelight — the standard multiplatform networking and database stack replacing Retrofit + Room
4
Flow works cross-platform — kotlinx.coroutines-core is multiplatform; reactive streams shared in commonMain
5
iOS generates .xcframework — consumed by iOS app via Xcode or CocoaPods; Kotlin suspend → Swift async/await
6
UI is NOT shared — Compose is Android-only; iOS uses SwiftUI. KMP is "shared logic, native UI"

Senior-Level Insight (Stand Out)

Say This
"KMP is the pragmatic choice for teams that are Kotlin-first and need iOS without a full Flutter rewrite — you keep native performance and UI while eliminating roughly 60% of duplicate business logic. The key architectural decision is where to draw the expect/actual boundary: I prefer pushing it to infrastructure primitives only — database drivers, platform dispatchers, UUID generation — and keeping all domain and data logic truly shared in commonMain. The biggest footgun is treating KMP as a way to avoid iOS expertise entirely; you still need a Swift developer for the SwiftUI shell and for navigating Xcode toolchain issues."

9. Interview Questions (Self-Check)
How to use
Try to answer each question before revealing the answer. Click the arrow to reveal.

Basic

B1 — What is the difference between KMP and KMM?
Easy▼
KMP (Kotlin Multiplatform) is the broad technology for sharing Kotlin code across Android, iOS, Web, and Desktop targets. KMM (Kotlin Multiplatform Mobile) was the name for the mobile-focused subset (Android + iOS only), which JetBrains has since merged back under the KMP umbrella. In 2023, JetBrains officially stabilised KMP and retired the KMM branding — they are now the same thing. When interviewers say KMM they mean KMP targeting Android and iOS.
B2 — What is the purpose of the expect / actual mechanism?
Easy▼
expect declares a contract in commonMain — a class or function that the compiler knows must exist on every platform, but whose implementation differs. Each platform source set (androidMain, iosMain) provides an actual implementation. The compiler enforces that every declared expect has a matching actual on every declared target — if one is missing, it is a compile error. This allows commonMain to call platform-specific APIs (logging, date, UUID) without knowing the platform.
B3 — What is shared in a KMP project? What is NOT shared?
Easy▼
Shared (commonMain): domain models, use cases, repositories, networking (Ktor), database access (SQLDelight), coroutines, Flow, serialization, business logic, validation rules.

NOT shared: UI (Compose is Android-only; iOS uses SwiftUI), dependency injection (Hilt is Android-only), platform-specific APIs (camera, GPS, biometrics), navigation, platform lifecycle management. These stay native and either have an expect/actual abstraction or live entirely in the platform-specific app.

Intermediate

I1 — Why is Ktor used instead of Retrofit in KMP? Why is SQLDelight used instead of Room?
Medium▼
Ktor vs Retrofit: Retrofit is built on OkHttp which is JVM/Android-only. Ktor is multiplatform by design — it uses OkHttp as its engine on Android and NSURLSession (Darwin engine) on iOS. Since commonMain must compile to both JVM and Kotlin/Native, only Ktor works there. Retrofit would fail to compile on iOS targets.

SQLDelight vs Room: Room uses annotation processing and Android-only SQLite APIs. SQLDelight is multiplatform — it generates platform-typed Kotlin code from SQL schema files, and uses platform-appropriate drivers: AndroidSqliteDriver on Android and NativeSqliteDriver on iOS. Room would fail on Kotlin/Native targets.
I2 — How does an iOS app consume a KMP shared module? How do Kotlin coroutines work from Swift?
Medium▼
KMP generates an .xcframework (or .framework) from the shared module during the Gradle build. The iOS team adds this framework to the Xcode project either directly or via CocoaPods/SPM. Kotlin classes and functions are exposed to Swift as Objective-C interop — Kotlin data classes become Swift structs/classes, Kotlin interfaces become Swift protocols.

Kotlin suspend functions are not directly callable from Swift (which has no concept of Kotlin coroutines). The recommended solutions:
• KMP-NativeCoroutines library: generates Swift async/await wrappers automatically
• SKIE (Swift Kotlin Interface Enhancer) by Touchlab: produces idiomatic Swift API
• Manual: wrap suspend functions in a CoroutineScope with a callback/completion handler

With modern libraries, suspend fun getUser(): User becomes async func getUser() async throws -> User in Swift.
I3 — What is the new Kotlin/Native memory model and why does it matter for KMP?
Medium▼
Before Kotlin 1.6, Kotlin/Native used a "frozen" memory model — objects passed between threads had to be explicitly frozen (made immutable), and mutable state was not allowed to be shared across threads. This broke coroutine patterns that rely on shared mutable state between withContext switches and was a major source of InvalidMutabilityException and FreezingException crashes on iOS.

Since Kotlin 1.7.20, the new memory model is the default. It uses a concurrent tracing garbage collector and allows mutable state to be shared across threads (same as JVM semantics). This makes standard coroutine patterns, StateFlow, and mutable ViewModel-like classes work correctly on iOS. Migration: ensure Kotlin 1.7.20+ and remove any .freeze() calls from your shared code.
I4 — [Coding] Write an expect / actual for getting the current platform's date as a formatted string (yyyy-MM-dd). Provide commonMain, androidMain, and iosMain.
MediumCoding▼
// commonMain/PlatformDate.kt
expect fun currentDateString(): String

// androidMain/PlatformDate.kt
import java.text.SimpleDateFormat
import java.util.Date
import java.util.Locale

actual fun currentDateString(): String =
    SimpleDateFormat("yyyy-MM-dd", Locale.getDefault()).format(Date())

// iosMain/PlatformDate.kt
import platform.Foundation.NSDate
import platform.Foundation.NSDateFormatter

actual fun currentDateString(): String {
    val formatter = NSDateFormatter()
    formatter.dateFormat = "yyyy-MM-dd"
    return formatter.stringFromDate(NSDate())
}
Note: in production you would prefer kotlinx.datetime library which is multiplatform and handles this in commonMain without expect/actual: Clock.System.now().toLocalDateTime(TimeZone.currentSystemDefault()).date.toString()

Senior / Scenario

S1 — [Scenario] An iOS engineer reports: app crashes with FreezingException: freezing of kotlin.coroutines.CancellableContinuation when calling a shared Flow from Swift. What is happening and how do you fix it?
HardScenario▼
What is happening: This is the old Kotlin/Native memory model issue. When code tries to pass a CancellableContinuation (internal coroutine state) across threads — which Kotlin/Native's old model requires to be frozen/immutable before crossing thread boundaries — the freeze operation fails because coroutine internals are mutable.

Root causes:
1. The project is using Kotlin < 1.7.20 (old memory model default)
2. Or: using old coroutines-native-mt version instead of standard coroutines

Fix:
1. Upgrade to Kotlin 1.7.20+ — new memory model is default, this exception class is gone
2. Use standard kotlinx.coroutines-core (not the deprecated -native-mt variant)
3. Use KMP-NativeCoroutines or SKIE to generate safe Swift wrappers
4. If temporarily stuck on older Kotlin: wrap the Flow collection in @OptIn(ExperimentalCoroutinesApi::class) and use flowOn(Dispatchers.Main) to ensure single-thread execution

Long-term: Standardise on Kotlin 1.9+ and the new memory model — the old model is removed.
S2 — A senior engineer wants to add KMP to an existing 3-year-old Android app that has a large Java legacy codebase. What is your advice? Is it worth it?
Hard▼
Honest assessment — it depends:

Arguments for: If the team needs to deliver an iOS app, KMP avoids rewriting the entire business logic. The shared layer can be extracted incrementally — start with domain models and repository interfaces, then migrate implementations one by one.

Arguments against:
1. Java interop with KMP is imperfect — Java classes can be used from commonMain only if they're pure JVM targets; Kotlin/Native can't use Java directly
2. Legacy Java code must be converted to Kotlin before moving to commonMain
3. Room, Retrofit, Hilt — all Android-only — must be replaced or abstracted
4. Significant iOS infrastructure investment (xcframework builds, iOS CI, Swift team)

Recommended approach if proceeding:
1. Audit what is truly shareable (pure domain + data logic) vs. Android-specific
2. Convert Java domain/data layer to Kotlin first
3. Extract shared module incrementally — start with domain models only
4. Replace Room with SQLDelight and Retrofit with Ktor one module at a time
5. Set a 6-month migration target with clear milestones

If there is no immediate iOS requirement: do not add KMP to a legacy Java app for its own sake — the migration cost exceeds the benefit.
S3 — How do you test shared KMP code? What test frameworks are available in commonMain?
Hard▼
kotlin.test is the multiplatform test framework — it provides @Test, assertEquals, assertTrue, assertFails. Tests in commonTest run on all platforms:
• ./gradlew testDebugUnitTest — runs on JVM (Android unit tests)
• ./gradlew iosX64Test — runs on Kotlin/Native (iOS simulator)

For coroutines testing: kotlinx.coroutines.test (TestScope, runTest) is multiplatform since coroutines 1.6.

For mocking: Mockito and MockK do not work on Kotlin/Native. Use either:
• Manual fakes/stubs (recommended for shared code)
• Mockative — a KMP-compatible mocking library using KSP

Best practice: Test use cases and repositories with fake data sources in commonTest. Platform-specific tests (database driver, HTTP engine) go in androidTest / iosTest. This keeps the most important business logic tested cross-platform.
