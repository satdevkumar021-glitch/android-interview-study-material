3D — Android Process Model & Lifecycle

Tier 1 · Senior Architecture Process Priority · oom_adj / oom_score_adj · LMK · Application Sandbox · UID · ANR Internals

1 · Overview

In standard desktop operating systems, an application's process lifetime is directly tied to the user opening and closing windows. In Android, process lifecycle is completely detached from application component lifecycle. Android keeps processes in memory as long as possible and reclaims them silently when system RAM runs low.

The Core Problem Solved: Mobile devices operate under strict physical RAM constraints without swap space. To maintain high responsiveness, Android assigns a dynamic OOM adjustment score (oom_score_adj) to every process based on what the user is currently seeing or interacting with. When RAM thresholds are breached, the Low Memory Killer daemon (lmkd) kills processes with the highest score instantly (SIGKILL).

Key Pillars of Android Process Architecture:
  • Linux UID Sandbox: Every app is assigned a unique Linux User ID (e.g. u0_a142). Files created by this app cannot be accessed by other UIDs without explicit file permissions.
  • OOM Adjustment Hierarchy: Processes transition dynamically from Foreground (Score 0) to Cached Background (Score 900–1000).
  • Process Death vs State Restoration: When a background process is killed, Android preserves the back stack record and Bundle state in ActivityTaskManagerService. Upon return, a new process is spawned and the UI is restored from the saved bundle.

How Process Death Occurs (The LMK Pipeline)

  1. Memory Pressure Event: Free system RAM falls below predefined kernel watermarks (e.g., low_wmark).
  2. LMKD Evaluation: The user-space lmkd (Low Memory Killer Daemon) reads /proc/[pid]/oom_score_adj for all candidate processes.
  3. SIGKILL Execution: lmkd selects the process with the highest oom_score_adj (e.g. 999) that frees the required memory pages, and issues an immediate uncatchable SIGKILL (9).
  4. No Callbacks Run: Neither Activity.onDestroy() nor Application.onTerminate() is invoked! The process memory space vanishes immediately.

ANR (Application Not Responding) Internals

An ANR dialog is displayed when the application fails to respond to a system event within a hard deadline:

  • Input Events (Key/Touch): 5 seconds without finishing the touch dispatch.
  • Foreground BroadcastReceiver: 10 seconds to return from onReceive().
  • Background BroadcastReceiver: 60 seconds.
  • Foreground Service: 200 seconds without calling startForeground().

When the timeout expires, ATMS sends SIGQUIT (3) to the process. The ART runtime dumps all thread stack traces into /data/anr/traces.txt.

3 · Multi-Process Architecture: When to Use & Avoid

Architecture Use Case Trade-Offs & Pitfalls
Single Process (Default) 99% of applications (Banking, E-Commerce, Social). Single heap; simple state sharing via ViewModel/Singletons.
Separate Process (:remote / :sync) Independent heavy tasks (e.g. continuous audio playback, WebView isolation, core IPC daemon). Duplicates Application.onCreate() memory (~20–40MB overhead per process); memory cannot be shared; Singletons do not sync across processes.

4 · Production Example: Handling Process Death & SavedStateHandle

Production Banking transfer flow resilient to process death, preserving multi-step transaction drafts with Jetpack SavedStateHandle.

package com.enterprise.banking.transfer

import androidx.lifecycle.SavedStateHandle
import androidx.lifecycle.ViewModel
import androidx.lifecycle.viewModelScope
import kotlinx.coroutines.flow.StateFlow
import kotlinx.coroutines.launch
import java.math.BigDecimal

/**
 * Transfer ViewModel resilient to OS Process Death.
 * SavedStateHandle automatically survives process termination via ATMS Bundle.
 */
class TransferViewModel(
    private val savedStateHandle: SavedStateHandle,
    private val transferRepository: TransferRepository
) : ViewModel() {

    // Automatically restored when process is resurrected!
    val targetIban: StateFlow<String> = savedStateHandle.getStateFlow(KEY_IBAN, "")
    val transferAmount: StateFlow<String> = savedStateHandle.getStateFlow(KEY_AMOUNT, "0.00")

    fun onIbanEntered(iban: String) {
        savedStateHandle[KEY_IBAN] = iban
    }

    fun onAmountEntered(amount: String) {
        savedStateHandle[KEY_AMOUNT] = amount
    }

    fun submitTransfer() {
        val iban = targetIban.value
        val amount = BigDecimal(transferAmount.value)

        viewModelScope.launch {
            transferRepository.executeTransfer(iban, amount)
            // Clear saved state on success
            savedStateHandle.remove<String>(KEY_IBAN)
            savedStateHandle.remove<String>(KEY_AMOUNT)
        }
    }

    companion object {
        private const val KEY_IBAN = "key_transfer_target_iban"
        private const val KEY_AMOUNT = "key_transfer_amount"
    }
}

6 · Pitfalls & Common Mistakes

1. Relying on Static Singletons for Transient State: A common architectural mistake is storing authentication tokens or user drafts in global Kotlin object Singletons. When the app is in the background and the OS kills the process, the user returns and the Activity restarts with null Singleton fields, resulting in NullPointerException or silent logout.
2. Expecting onDestroy() to Run Before Process Death: Never write cleanup or database commits inside onDestroy() expecting them to execute during low memory termination. onDestroy() is skipped entirely during LMK SIGKILL. Commit important state in onPause() / onStop() or write to disk.
3. Multi-Process Application.onCreate() Duplication: Adding android:process=":remote" to a Service causes the entire Application.onCreate() to run twice (once per process). If you initialize Firebase, Room, or DI graphs globally in Application.onCreate() without checking the current process name, you waste memory and cause database lock conflicts.

7 · Interview Framework (Senior Differentiator)

30-Second Answer (Elevator Pitch)

"Android decouples process lifecycle from component lifecycle. Every process is assigned an oom_score_adj score from -1000 (system) to 1000 (cached background). When system RAM drops below kernel watermarks, the lmkd daemon issues a SIGKILL to the highest-scoring cached processes without invoking onDestroy(). When the user returns, Android spawns a new process and restores the UI hierarchy from the SavedStateHandle bundle preserved in ATMS."

2-Minute Structured Answer

  1. Linux Sandbox & UID: Android assigns a unique Linux UID per application package, isolating file access and memory spaces at the kernel level.
  2. OOM Adjustment Hierarchy (oom_score_adj):
    • Foreground (Score 0): Active visible Activity with user focus.
    • Perceptible / Foreground Service (Score 200): Playing audio, active GPS navigation with notification.
    • Service Process (Score 500): Background services.
    • Cached Background (Score 900–1000): No active components; killed first by LMK.
  3. Process Death vs State Restoration:
    • When killed by LMK, ATMS retains the Activity back-stack metadata and onSaveInstanceState() Bundles.
    • Upon relaunch, ATMS forks a fresh process and passes the saved Bundle into onCreate(savedInstanceState) or Jetpack SavedStateHandle.
  4. ANR Watchdog Architecture: ATMS tracks a timer for input events (5s) and broadcasts (10s/60s). If unhandled, it sends SIGQUIT to dump thread traces into /data/anr/traces.txt.

Must-Mention Points (Key Vocabulary)

  • oom_score_adj (OOM adjustment score) and lmkd (Low Memory Killer Daemon).
  • Instant SIGKILL (no onDestroy() or onTerminate() is called).
  • Difference between Configuration Change (ViewModel survives) vs Process Death (only SavedStateHandle / Disk survives).
  • ANR timeouts: 5s for input touches, 10s/60s for BroadcastReceivers, 200s for Foreground Services.
  • Application Sandbox: Unique Linux UID per app.

Likely Follow-Up Questions & Short Answers

Q: How can you simulate Process Death in Android Studio?

1. Put the app in the background (Home button).
2. In Android Studio's Logcat / Terminal, run: adb shell am kill com.enterprise.banking or click "Stop Process" in the Device File Explorer.
3. Reopen the app from the Recent Apps screen to verify if it restores correctly from SavedStateHandle.

Q: Does ViewModel survive process death?

No. ViewModel instances reside entirely in the process's JVM heap. When the process is killed, the heap is destroyed. Only state explicitly saved in SavedStateHandle or persistent storage (Room/DataStore) survives.

Q: What is the purpose of shareUserId in Android manifest?

Historically, android:sharedUserId allowed two apps signed with the same certificate to share the same Linux UID and access each other's data sandbox. It is now deprecated due to security risks and migration complexity.

Senior-Level Insight: "Junior engineers test their apps against screen rotation; senior engineers test against Process Death. If your app crashes or loses form inputs when the user leaves to take a phone call and returns 10 minutes later, your state architecture is flawed. Always bind critical transient UI state to SavedStateHandle."

8 · Revision Sheet (Quick Memory Anchors)

  • Sandbox: Linux UID per app; files in /data/data/<package> restricted by OS permissions.
  • oom_score_adj: -1000 (System) to 1000 (Cached background). High score killed first.
  • LMKD: User-space daemon sending SIGKILL when RAM is low. No lifecycle callbacks execute.
  • State Survives Death: SavedStateHandle, onSaveInstanceState, Room/DataStore.
  • ANR Timeouts: 5s (Input), 10s (Foreground Broadcast), 60s (Background Broadcast), 200s (Foreground Service).
  • Multi-Process (android:process): Re-runs Application.onCreate(); no shared memory; isolated heaps.

9 · Quiz (10 Questions)

BASIC 1. What determines which process Android terminates when RAM is low?
The Low Memory Killer daemon (lmkd) uses the process's oom_score_adj value. Processes with higher scores (such as cached background apps with no visible components, score 900–1000) are killed first.
BASIC 2. Does Activity.onDestroy() run when an app is killed due to low memory?
No. When LMK kills a background process, the kernel sends an immediate SIGKILL. The process terminates instantly without executing any cleanup or lifecycle callbacks like onDestroy() or Application.onTerminate().
BASIC 3. What is the ANR timeout for user touch input?
5 seconds. If the Main thread fails to process an input event (such as a tap or keypress) within 5 seconds, an ANR dialog is triggered.
INTERMEDIATE 4. What is the difference between ViewModel and SavedStateHandle regarding process death?
ViewModel survives configuration changes (like screen rotations) because the ViewModelStore is retained in memory, but it does NOT survive process death. SavedStateHandle survives both configuration changes AND process death because its state bundle is transmitted to and retained by the system process (ActivityTaskManagerService).
INTERMEDIATE 5. What happens when an app declares android:process=":sync" in its manifest?
The declared component runs in a new, separate Linux process. Android executes Application.onCreate() again for this new process. Memory, static variables, and Singletons are completely isolated between the two processes.
INTERMEDIATE 6. How does the Android sandbox isolate apps using Linux UIDs?
During installation, PackageManagerService assigns a unique Linux User ID (e.g. UID 10142) to the app. Linux kernel file system permissions restrict the app's files (/data/data/pkg) so that other UIDs cannot read or modify them without explicit inter-app sharing permissions.
INTERMEDIATE 7. What are the timeout thresholds for BroadcastReceivers before an ANR occurs?
Foreground broadcasts have a timeout of 10 seconds. Background broadcasts have a timeout of 60 seconds.
SENIOR 8. Explain how the system restores an app's UI after process death.
1. Before killing the background process, the system calls onSaveInstanceState(Bundle) and transfers the serialized Bundle to ATMS via Binder.
2. When the user taps the app in Recents, ATMS detects no active process and forks a new process via Zygote.
3. The process runs ActivityThread.main(), initializes Application, and ATMS sends the saved Bundle.
4. The Activity is recreated with onCreate(savedInstanceState), passing the bundle to View hierarchies and SavedStateHandle.
SENIOR 9. How do you analyze an ANR trace file generated in /data/anr/traces.txt?
1. Open the trace file and locate the main thread entry ("main" prio=5 tid=1).
2. Check the thread state: BLOCKED (waiting on a monitor/lock held by another thread), WAITING / TIMED_WAIT (waiting on I/O or sleep), or RUNNABLE (executing an infinite loop or heavy CPU task).
3. Inspect the stack trace to locate the exact class and line number causing the stall.
4. Check other background threads if the main thread is blocked waiting for a synchronized lock.
SENIOR 10. Why is android:sharedUserId deprecated in modern Android?
sharedUserId caused serious security vulnerabilities (a compromised app could access all apps sharing the UID), broke Package Manager signature enforcement, prevented granular permission isolation, and created deadlocks during app updates. Google deprecated it in API 29 and recommends using ContentProviders or AIDL for secure inter-app data sharing.
