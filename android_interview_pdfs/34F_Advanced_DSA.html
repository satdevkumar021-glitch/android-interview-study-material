34F — Advanced DSA: Graphs, DP & Monotonic Structures

The three pattern families that separate L4 from L5 in coding rounds: graph algorithms (BFS/DFS, topological sort, Dijkstra), dynamic programming (state machines, LIS, edit distance), and monotonic stack/deque — all in production Kotlin.

1. Overview

In Plain Words

Topics 34A–34E cover the core patterns. This topic covers the three families that Android senior/staff candidates consistently underestimate: graphs (model relationships), dynamic programming (optimize decisions by remembering results), and monotonic structures (answer "nearest larger/smaller" in O(n)). These appear in FAANG-style rounds as both standalone algorithmic problems and embedded in Android-flavored design questions.

Pattern Decision Tree

// When you see this in the problem → think this pattern:
// "shortest path between two nodes"    → BFS (unweighted) or Dijkstra (weighted)
// "all possible orderings / scheduling" → Topological Sort (Kahn's or DFS)
// "connected components / reachability" → BFS or DFS
// "optimal substructure + overlapping subproblems" → Dynamic Programming
// "next greater / previous smaller element" → Monotonic Stack
// "maximum in a sliding window"          → Monotonic Deque

In Android interviews, these patterns appear as: dependency resolution between Gradle modules (topological sort), feature flag dependency graphs (Dijkstra/BFS), RecyclerView item animations (monotonic stack for "previous smaller height"), and diff computation (edit distance DP for DiffUtil). Know the pattern AND its Android-flavored equivalent.

2. Graph Algorithms

BFS — Shortest Path (Unweighted)

// Time: O(V + E)  Space: O(V)
// Use: shortest path in unweighted graph, level-order traversal
fun bfsShortestPath(
    graph: Map<Int, List<Int>>,
    start: Int,
    end: Int
): Int {
    val visited = mutableSetOf(start)
    val queue = ArrayDeque<Pair<Int, Int>>()  // (node, distance)
    queue.addLast(start to 0)

    while (queue.isNotEmpty()) {
        val (node, dist) = queue.removeFirst()
        if (node == end) return dist
        graph[node]?.forEach { neighbor ->
            if (visited.add(neighbor)) {
                queue.addLast(neighbor to dist + 1)
            }
        }
    }
    return -1  // unreachable
}
// ✅ Kotlin: use ArrayDeque — faster than java.util.LinkedList for BFS

DFS — Connected Components & Cycle Detection

// Cycle detection in directed graph using color marking
// WHITE=0 (unvisited), GRAY=1 (in progress), BLACK=2 (done)
fun hasCycle(graph: Map<Int, List<Int>>): Boolean {
    val color = mutableMapOf<Int, Int>()

    fun dfs(node: Int): Boolean {
        color[node] = 1  // GRAY — currently exploring
        graph[node]?.forEach { neighbor ->
            if (color[neighbor] == 1) return true  // back edge = cycle
            if (color[neighbor] == 0 || color[neighbor] == null) {
                if (dfs(neighbor)) return true
            }
        }
        color[node] = 2  // BLACK — fully explored
        return false
    }

    graph.keys.forEach { node ->
        if (color[node] == null && dfs(node)) return true
    }
    return false
}

Topological Sort — Kahn's Algorithm (BFS-based)

// Time: O(V + E)  Space: O(V)
// Use: task scheduling with dependencies, Gradle module build order
// Prerequisite: graph must be a DAG (no cycles)
fun topologicalSort(numNodes: Int, edges: List<Pair<Int, Int>>): List<Int> {
    val inDegree = IntArray(numNodes)
    val adj = Array(numNodes) { mutableListOf<Int>() }

    edges.forEach { (from, to) ->
        adj[from].add(to)
        inDegree[to]++
    }

    val queue = ArrayDeque(inDegree.indices.filter { inDegree[it] == 0 })
    val result = mutableListOf<Int>()

    while (queue.isNotEmpty()) {
        val node = queue.removeFirst()
        result.add(node)
        adj[node].forEach { neighbor ->
            if (--inDegree[neighbor] == 0) queue.addLast(neighbor)
        }
    }

    // If result.size != numNodes, there is a cycle in the graph
    return if (result.size == numNodes) result else emptyList()
}

Dijkstra — Weighted Shortest Path

// Time: O((V + E) log V) with binary heap  Space: O(V)
// Use: shortest path with positive weights, feature flag dependency costs
fun dijkstra(
    graph: Map<Int, List<Pair<Int, Int>>>,  // node → [(neighbor, weight)]
    start: Int,
    numNodes: Int
): IntArray {
    val dist = IntArray(numNodes) { Int.MAX_VALUE }
    dist[start] = 0
    // PriorityQueue of (distance, node) — min-heap by distance
    val pq = PriorityQueue(compareBy<Pair<Int, Int>> { it.first })
    pq.offer(0 to start)

    while (pq.isNotEmpty()) {
        val (d, node) = pq.poll()
        if (d > dist[node]) continue  // stale entry
        graph[node]?.forEach { (neighbor, weight) ->
            val newDist = dist[node] + weight
            if (newDist < dist[neighbor]) {
                dist[neighbor] = newDist
                pq.offer(newDist to neighbor)
            }
        }
    }
    return dist
}
// ⚠️ Dijkstra requires non-negative weights — use Bellman-Ford for negative weights.

3. Dynamic Programming

The 5-Step DP Framework

  1. Define state: What does dp[i] or dp[i][j] represent? Be precise.
  2. Identify base cases: What are the smallest sub-problems you can answer trivially?
  3. Write the recurrence relation: How does dp[i] relate to dp[i-1], dp[i-2], etc.?
  4. Choose top-down (memoization) or bottom-up (tabulation): Top-down is easier to derive; bottom-up is faster and avoids stack overflow.
  5. Optimize space: Can you reduce O(n²) space to O(n) or O(1) by only keeping the last row/column?

Coin Change — Classic 1D DP

// State: dp[amount] = minimum coins needed for this amount
// Recurrence: dp[a] = min(dp[a], dp[a - coin] + 1) for each coin
// Time: O(amount × coins.size)  Space: O(amount)
fun coinChange(coins: IntArray, amount: Int): Int {
    val dp = IntArray(amount + 1) { amount + 1 }  // sentinel = impossible
    dp[0] = 0

    for (a in 1..amount) {
        for (coin in coins) {
            if (coin <= a) {
                dp[a] = minOf(dp[a], dp[a - coin] + 1)
            }
        }
    }
    return if (dp[amount] > amount) -1 else dp[amount]
}

Longest Increasing Subsequence (LIS) — O(n log n)

// Patience sorting approach — O(n log n) time, O(n) space
// tails[i] = smallest tail element of all LIS of length i+1
fun lengthOfLIS(nums: IntArray): Int {
    val tails = mutableListOf<Int>()
    for (num in nums) {
        var lo = 0; var hi = tails.size
        while (lo < hi) {          // binary search for insertion point
            val mid = (lo + hi) / 2
            if (tails[mid] < num) lo = mid + 1 else hi = mid
        }
        if (lo == tails.size) tails.add(num) else tails[lo] = num
    }
    return tails.size
}

Edit Distance (Levenshtein) — 2D DP

// Basis for DiffUtil's difference algorithm
// dp[i][j] = min edits to transform word1[0..i-1] to word2[0..j-1]
// Time: O(m×n)  Space: O(m×n) → can optimize to O(min(m,n))
fun minDistance(word1: String, word2: String): Int {
    val m = word1.length; val n = word2.length
    val dp = Array(m + 1) { i -> IntArray(n + 1) { j -> if (i == 0) j else if (j == 0) i else 0 } }

    for (i in 1..m) {
        for (j in 1..n) {
            dp[i][j] = if (word1[i-1] == word2[j-1]) dp[i-1][j-1]
            else minOf(dp[i-1][j], dp[i][j-1], dp[i-1][j-1]) + 1
        }
    }
    return dp[m][n]
}

4. Monotonic Stack & Deque

Monotonic Stack — Next Greater Element

// Invariant: stack is always monotonically decreasing (top = smallest seen so far)
// When current element breaks the invariant: pop and record the "next greater"
// Time: O(n)  Space: O(n)  — each element pushed/popped at most once
fun nextGreaterElement(nums: IntArray): IntArray {
    val result = IntArray(nums.size) { -1 }
    val stack = ArrayDeque<Int>()  // stores INDICES

    for (i in nums.indices) {
        while (stack.isNotEmpty() && nums[stack.last()] < nums[i]) {
            result[stack.removeLast()] = nums[i]  // i is the next greater for popped idx
        }
        stack.addLast(i)
    }
    return result
}
// Android use: "what is the next frame that's taller than this one?" (animation height stack)

Sliding Window Maximum — Monotonic Deque

// Maintain a deque of indices in decreasing order of their values
// Front of deque is always the max of current window
// Time: O(n)  Space: O(k)
fun maxSlidingWindow(nums: IntArray, k: Int): IntArray {
    val result = IntArray(nums.size - k + 1)
    val deque = ArrayDeque<Int>()  // stores indices

    for (i in nums.indices) {
        // Remove indices outside this window
        if (deque.isNotEmpty() && deque.first() < i - k + 1) deque.removeFirst()
        // Remove indices whose values are smaller than current (they can never be max)
        while (deque.isNotEmpty() && nums[deque.last()] < nums[i]) deque.removeLast()
        deque.addLast(i)
        if (i >= k - 1) result[i - k + 1] = nums[deque.first()]
    }
    return result
}
// Android use: "max frame render time in last k frames" for jank detection

5. Android-Flavored DSA Problems

Task Scheduler with Dependencies (Topological Sort)

// Problem: given a list of tasks and their dependencies,
// return a valid execution order (or detect circular dependencies)
data class Task(val id: String, val dependsOn: List<String>)

fun scheduleTasks(tasks: List<Task>): List<String>? {
    val inDegree = mutableMapOf(*tasks.map { it.id to 0 }.toTypedArray())
    val adj = mutableMapOf(*tasks.map { it.id to mutableListOf<String>() }.toTypedArray())

    tasks.forEach { task ->
        task.dependsOn.forEach { dep ->
            adj[dep]!!.add(task.id)
            inDegree[task.id] = inDegree[task.id]!! + 1
        }
    }

    val queue = ArrayDeque(inDegree.filter { it.value == 0 }.keys)
    val order = mutableListOf<String>()

    while (queue.isNotEmpty()) {
        val task = queue.removeFirst()
        order.add(task)
        adj[task]!!.forEach { next ->
            if (--inDegree[next]!! == 0) queue.addLast(next)
        }
    }
    return if (order.size == tasks.size) order else null  // null = cycle detected
}

Sliding Window Rate Limiter

// Allow at most maxRequests in the last windowMs milliseconds
// Uses monotonic deque of timestamps
class RateLimiter(private val maxRequests: Int, private val windowMs: Long) {
    private val timestamps = ArrayDeque<Long>()

    fun tryAcquire(now: Long = System.currentTimeMillis()): Boolean {
        val windowStart = now - windowMs
        while (timestamps.isNotEmpty() && timestamps.first() < windowStart) {
            timestamps.removeFirst()
        }
        return if (timestamps.size < maxRequests) {
            timestamps.addLast(now)
            true
        } else false
    }
}

Kotlin Hidden Costs to Avoid

Performance Pitfalls in Kotlin DSA
  • String concatenation in loops: "a" + "b" creates a new String each time → O(n²). Use StringBuilder.
  • List<Int> vs IntArray: List<Int> boxes integers into java.lang.Integer objects. For large arrays use IntArray (primitive array, no boxing).
  • List.contains() is O(n): Use Set.contains() which is O(1) amortized.
  • LinkedList vs ArrayDeque: ArrayDeque is faster for both stack and queue operations due to cache locality. Prefer it always.
  • Sequence laziness pitfall: sequence.toList() materializes eagerly — if you chain terminal operations, sequences add overhead. For small collections, direct list operations are faster.
  • Mutable collection copies: list.sortedBy { } returns a new list. For in-place sort use list.sortBy { } on a MutableList.

7. Interview Framework

Pattern Recognition Guide

1
"Shortest path" + unweighted graph → BFS. "Shortest path" + weighted → Dijkstra. "Minimum cost path" + grid → Dijkstra or 2D DP.
2
"Dependencies" or "prerequisites" or "order" → Topological sort. First check: is it a DAG? (Cycle = impossible ordering.)
3
"Count / optimize over subsets" with overlapping sub-problems → Dynamic programming. First question: "What is the state?"
4
"Next greater/smaller element" → Monotonic stack. "Maximum/minimum in sliding window" → Monotonic deque.
5
"All paths" or "can we reach" → DFS or BFS. DFS for all-paths (backtracking); BFS for shortest-path guarantees.

8. Flash Cards
FC1 — BFS vs DFS: when to choose each?
Core⌄
BFS: shortest path in unweighted graph, level-order traversal, "minimum steps" problems. DFS: all paths, connected components, cycle detection, topological sort (recursive). Key difference: BFS guarantees shortest path for uniform-cost edges; DFS does not.
FC2 — Topological sort precondition and Kahn's algorithm summary
Core⌄
Precondition: graph must be a DAG (Directed Acyclic Graph). If it has a cycle, topological sort is impossible. Kahn's: (1) compute in-degree for all nodes, (2) enqueue nodes with in-degree 0, (3) process queue: add node to result, decrement in-degree of neighbors, enqueue those reaching 0. If result.size != numNodes → cycle exists.
FC3 — Dijkstra's key insight and its limitation
Critical⌄
Key insight: always process the unvisited node with the smallest known distance first (greedy). This works because all edge weights are non-negative — you can never find a shorter path to an already-processed node. Limitation: does NOT work with negative weights (use Bellman-Ford instead).
FC4 — The 5 steps to define a DP solution
Core⌄
(1) Define state: what does dp[i] mean? (2) Base cases: trivially solvable sub-problems. (3) Recurrence: how does dp[i] depend on smaller sub-problems? (4) Top-down vs bottom-up: memoization (recursive, easier) vs tabulation (iterative, faster). (5) Space optimization: can you keep only the last row?
FC5 — Monotonic stack invariant for "next greater element"
Critical⌄
Stack is maintained in decreasing order (top = smallest). When current element nums[i] is greater than stack's top: pop the top (its "next greater" is nums[i], record it). Push nums[i]. Iteration completes: any remaining elements in stack have no next greater element. Store indices, not values — needed to record answers.
FC6 — Why use ArrayDeque instead of Stack or LinkedList in Kotlin?
Core⌄
ArrayDeque (kotlin.collections.ArrayDeque) is backed by a resizable array with O(1) amortized add/remove at both ends. Stack is a legacy Java class (synchronized, slow). LinkedList has poor cache performance. ArrayDeque is the idiomatic Kotlin choice for both stack (addLast/removeLast) and queue (addLast/removeFirst) operations.
FC7 — LIS in O(n log n): the key insight
Senior⌄
Maintain a "tails" array where tails[i] = smallest tail element of all increasing subsequences of length i+1. For each new number: binary search for its insertion position in tails. If it's larger than all → extend LIS (add to end). Otherwise → replace the first element ≥ it (keeps tails as small as possible for future extensions). Final tails.size = LIS length.
FC8 — Edit distance recurrence relation
Senior⌄
dp[i][j] = min edits to transform word1[0..i-1] to word2[0..j-1]. If word1[i-1] == word2[j-1]: dp[i][j] = dp[i-1][j-1] (no edit needed). Else: dp[i][j] = min(dp[i-1][j] + 1 [delete], dp[i][j-1] + 1 [insert], dp[i-1][j-1] + 1 [replace]). Base: dp[i][0] = i, dp[0][j] = j.
FC9 — Hidden O(n²) in Kotlin: List.contains() pitfall
Critical⌄
List.contains() is O(n) linear scan. Inside a loop this becomes O(n²). Fix: convert to a Set first. val seen = nums.toHashSet() then seen.contains(x) is O(1). Common interview mistake: using a list as a "visited" set in BFS/DFS. Always use HashSet for visited tracking.
FC10 — Cycle detection: directed vs undirected graphs
Senior⌄
Directed graph: use 3-color DFS (WHITE/GRAY/BLACK). A cycle exists if you encounter a GRAY node during DFS (back edge). Undirected graph: during DFS, track the parent; a cycle exists if you encounter a visited node that is NOT the parent. Union-Find also works for undirected graphs: if two nodes are already in the same component, adding an edge creates a cycle.

9. Quick Revision Sheet

Graph Algorithms

BFS  → shortest unweighted, O(V+E)
DFS  → all paths, cycle, O(V+E)
Kahn → topological sort, DAG only
Dijkstra → weighted shortest, +ve only
         → O((V+E)logV) with heap

DP Patterns

1D: dp[i] = f(dp[i-1], dp[i-2])
2D: dp[i][j] = f(dp[i-1][j], dp[i][j-1])
LIS: O(n log n) patience sort
Edit dist: min(del, ins, replace)+1
Space opt: keep only prev row

Monotonic Structures

Stack: next greater/smaller O(n)
  → maintain decreasing order
  → pop when invariant breaks
Deque: sliding window max/min O(n)
  → remove front (out of window)
  → remove back (smaller than curr)

Kotlin Gotchas

Use IntArray not List<Int> (no boxing)
Use ArrayDeque not Stack/LinkedList
Use HashSet not List for visited
StringBuilder not + in loops
sortBy{} in-place, sortedBy{} copy

10. Interview Questions
Why can't you use Dijkstra's algorithm with negative edge weights?
Basic⌄
Dijkstra's greedy assumption is: once a node is processed (finalized), its shortest distance is known and will never decrease. With negative edges, a later-discovered longer path could produce a shorter total via a negative edge — violating the assumption. A finalized node might actually have a shorter path we haven't discovered yet. Fix: use Bellman-Ford (O(VE)) which relaxes all edges V-1 times, handling negative weights.
Design a build system that detects circular module dependencies. What algorithm, what data structure, what is returned?
Intermediate⌄
Model modules as nodes, dependencies as directed edges. Use Kahn's topological sort: (1) build adjacency list and in-degree map from the dependency graph, (2) enqueue all nodes with in-degree 0, (3) process queue, decrement in-degrees, enqueue nodes reaching 0, (4) if result.size != total modules → cycle exists. Return: the ordered build sequence (topological order) or the cycle-causing modules (DFS 3-color can identify the back edge for better error messages).
Implement coin change with DP. What is the state, recurrence, and time complexity?
Intermediate⌄
State: dp[amount] = minimum coins to make exactly this amount. Base: dp[0] = 0, dp[i] = ∞ (impossible) for i > 0 initially. Recurrence: for each amount a, for each coin c ≤ a: dp[a] = min(dp[a], dp[a - c] + 1). Time: O(amount × numCoins). Space: O(amount). Return dp[amount] or -1 if still ∞. Common mistake: initializing dp with 0 instead of a sentinel like amount+1.
Spot the bug: this BFS finds shortest path but sometimes returns wrong results. Why?
Senior — Spot the Bug⌄
val visited = mutableSetOf<Int>()
val queue = ArrayDeque<Pair<Int,Int>>()
queue.addLast(start to 0)
// BUG: visited.add(start) is missing here!
Bug: the start node is not added to visited before entering the loop. If the start node appears as a neighbor of another node early in BFS, it gets re-added to the queue with a larger distance, causing incorrect results or infinite loops in graphs with back-edges. Fix: always mark the start node as visited before entering the BFS loop.
How does edit distance relate to DiffUtil in Android RecyclerView?
Senior⌄
DiffUtil uses a variant of the Myers diff algorithm, which is conceptually similar to edit distance DP — it finds the minimum number of insertions and deletions to transform one list into another. Unlike plain edit distance (which also counts substitutions), DiffUtil treats each item as equal or not-equal (via areItemsTheSame and areContentsTheSame), then computes the minimal change set. For RecyclerView, it then translates these changes into notifyItemInserted/Removed/Moved calls, enabling smooth animations.
What is the time complexity of this Kotlin code and how would you fix it?
Senior — Kotlin Specific⌄
fun hasDuplicate(list: List<Int>): Boolean {
    val seen = mutableListOf<Int>()
    for (n in list) { if (seen.contains(n)) return true; seen.add(n) }
    return false
}
O(n²) — List.contains() is O(n). Fix: use HashSet instead. val seen = mutableSetOf<Int>(). HashSet.contains() is O(1) amortized → overall O(n). An even more idiomatic Kotlin fix: return list.size != list.toHashSet().size — but this always iterates the full list, so the early-return version with a set is better for large inputs with early duplicates.
Implement a sliding window rate limiter allowing max N requests per T milliseconds. What data structure, what time complexity?
Senior — Android Flavored⌄
Use an ArrayDeque of timestamps (monotonically increasing). On each tryAcquire(now): (1) remove from front any timestamps older than now - windowMs, (2) if queue size < maxRequests: add now to back and return true, else return false. Time: O(1) amortized per call (each timestamp is added and removed at most once). Space: O(maxRequests). This is the sliding window approach — more precise than fixed window (which can allow 2× the limit at window boundaries).
Graph representation: adjacency list vs adjacency matrix — when to use each?
Intermediate⌄
Adjacency list (Map<Int, List<Int>>): O(V+E) space — best for sparse graphs (few edges relative to nodes). Edge lookup O(degree). Iteration over neighbors O(degree). Best for most Android problems (feature graphs, dependency graphs — typically sparse). Adjacency matrix (Array(V){BooleanArray(V)}): O(V²) space — best for dense graphs or when edge lookup must be O(1). Wasted space if sparse. For interview problems: default to adjacency list unless the problem mentions dense connections or O(1) edge lookup is explicitly required.
