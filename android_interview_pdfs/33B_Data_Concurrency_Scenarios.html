2. Two APIs Run Simultaneously
1
Fetch user profile AND order history simultaneously, show both when both complete
Naive (Wrong) Approach
// ❌ Sequential — second call waits for first. 600ms total instead of 300ms
val user = api.getUser(userId)     // 300ms
val orders = api.getOrders(userId) // 300ms — waits for user to complete
Correct: async/await
// ✅ Parallel — both start immediately, total ~300ms (whichever is slower)
suspend fun loadProfilePage(userId: String): ProfilePage = coroutineScope {
    val userDeferred  = async(Dispatchers.IO) { api.getUser(userId) }
    val ordersDeferred = async(Dispatchers.IO) { api.getOrders(userId) }
    
    // Both start immediately; await blocks until each completes
    val user   = userDeferred.await()
    val orders = ordersDeferred.await()
    ProfilePage(user, orders)
}

// Or with awaitAll for a list of deferred values
val results = listOf(d1, d2, d3).awaitAll()  // waits for all, fails fast if any fails
Failure Handling (Senior differentiator)
// What if orders fails but user succeeds? Show partial data
suspend fun loadProfilePagePartial(userId: String): ProfilePage = coroutineScope {
    val userDeferred   = async(Dispatchers.IO) {
        runCatching { api.getUser(userId) }
    }
    val ordersDeferred = async(Dispatchers.IO) {
        runCatching { api.getOrders(userId) }
    }
    ProfilePage(
        user   = userDeferred.await().getOrNull(),
        orders = ordersDeferred.await().getOrNull() ?: emptyList()
    )
}

3. API B Depends on API A Result
2
Fetch product details, then use productId to fetch recommendations
// ✅ Sequential — await result of A before calling B
suspend fun loadProductWithRecs(productId: String): ProductPageData =
    withContext(Dispatchers.IO) {
        val product = api.getProduct(productId)          // Step 1: fetch product
        val recs    = api.getRecommendations(product.category) // Step 2: uses category from step 1
        ProductPageData(product, recs)
    }

// Error propagation: if getProduct() throws, getRecommendations is never called
// Exception propagates up to the caller — handle at ViewModel level

// In ViewModel:
fun loadProduct(productId: String) {
    viewModelScope.launch {
        uiState.value = UiState.Loading
        uiState.value = runCatching {
            repository.loadProductWithRecs(productId)
        }.fold(
            onSuccess = { UiState.Success(it) },
            onFailure = { UiState.Error("Failed to load product: ${it.message}") }
        )
    }
}
Partial failure variant
// Recommendations are optional — show product even if recs fail
suspend fun loadProductWithOptionalRecs(productId: String): ProductPageData =
    withContext(Dispatchers.IO) {
        val product = api.getProduct(productId)   // must succeed
        val recs = runCatching {
            api.getRecommendations(product.category)
        }.getOrDefault(emptyList())              // optional — empty on failure
        ProductPageData(product, recs)
    }

4. Token Refresh Race Condition
3
5 coroutines make API calls simultaneously. Token expires. All 5 get 401. How do you prevent 5 concurrent token refreshes?
Problem

Without coordination, all 5 coroutines call refreshToken() simultaneously. This causes: multiple refresh requests to the server, race conditions on token storage, previous tokens invalidated mid-request.

Solution: Mutex
// In your TokenManager / AuthRepository
class TokenManager @Inject constructor(private val api: AuthApi) {

    private val mutex = Mutex()   // Only ONE coroutine refreshes at a time
    private var cachedToken: String? = null

    suspend fun getValidToken(): String {
        cachedToken?.let { if (!isExpired(it)) return it }

        // Lock: only one coroutine enters; others wait
        mutex.withLock {
            // Double-check: another coroutine may have refreshed while we waited
            cachedToken?.let { if (!isExpired(it)) return it }

            // Actually refresh
            val newToken = api.refreshToken()
            cachedToken = newToken.accessToken
            return newToken.accessToken
        }
    }
}
OkHttp Authenticator Pattern
class TokenAuthenticator @Inject constructor(
    private val tokenManager: TokenManager
) : Authenticator {

    override fun authenticate(route: Route?, response: Response): Request? {
        // Called by OkHttp when it receives a 401
        if (response.responseCount() >= 2) return null  // stop after 1 retry
        
        val newToken = runBlocking {          // OkHttp is sync; runBlocking here is ok
            tokenManager.getValidToken()    // Mutex ensures only 1 refresh
        }
        
        return response.request.newBuilder()
            .header("Authorization", "Bearer $newToken")
            .build()
    }

    private fun Response.responseCount(): Int {
        var result = 1
        var prior = priorResponse
        while (prior != null) { result++; prior = prior.priorResponse }
        return result
    }
}

5. Room Has Stale Data but API Fails
4
User has cached data in Room. Network request fails. What should the UI show?
Wrong Behaviour

Show a blank error screen, discarding the cached data. This is the worst UX — user sees nothing instead of slightly-stale data.

Correct UiState Design
// UiState models all combinations
sealed class FeedUiState {
    object Loading : FeedUiState()
    data class Success(val items: List<FeedItem>, val isStale: Boolean = false) : FeedUiState()
    data class Error(val message: String, val cachedItems: List<FeedItem>? = null) : FeedUiState()
}

// Repository: emit cache first, then try network
fun getFeed(): Flow<FeedUiState> = flow {
    // 1. Emit cached data immediately (fast)
    val cached = db.feedDao().getAllItems()
    if (cached.isNotEmpty()) {
        emit(FeedUiState.Success(cached, isStale = true))
    } else {
        emit(FeedUiState.Loading)
    }
    
    // 2. Try to refresh from network
    runCatching { api.getFeed() }
        .onSuccess { fresh ->
            db.withTransaction { db.feedDao().replaceAll(fresh) }
            emit(FeedUiState.Success(fresh, isStale = false))
        }
        .onFailure { error ->
            // Network failed — show stale data with error indicator
            emit(FeedUiState.Error(
                message = error.message ?: "Failed to refresh",
                cachedItems = cached.ifEmpty { null }
            ))
        }
}.flowOn(Dispatchers.IO)
UI Rendering
when (val state = uiState) {
    is FeedUiState.Loading  -> ShowShimmer()
    is FeedUiState.Success  -> {
        FeedList(state.items)
        if (state.isStale) StaleDataBanner()   // subtle "Last updated 5 min ago"
    }
    is FeedUiState.Error -> {
        state.cachedItems?.let { FeedList(it) }   // show stale data if available
        ErrorBanner(state.message)                 // "Couldn't refresh — pull to retry"
    }
}

6. RecyclerView with 10,000 Items
5
A list of 10,000 items needs to update efficiently. Scrolling is janky.
Anti-patterns to avoid
  • notifyDataSetChanged() — rebinds ALL items, O(n) work even if 1 item changed
  • Holding all 10,000 items in memory at once without pagination
  • Complex item view that measures multiple times (nested weights, wrap_content chains)
Efficient Solutions
// 1. DiffUtil + ListAdapter (for manageable lists)
class FeedAdapter : ListAdapter<FeedItem, FeedViewHolder>(
    object : DiffUtil.ItemCallback<FeedItem>() {
        override fun areItemsTheSame(old: FeedItem, new: FeedItem) = old.id == new.id
        override fun areContentsTheSame(old: FeedItem, new: FeedItem) = old == new
    }
) { ... }

// 2. Paging 3 — don't load all 10,000 at once
// Load 20 at a time, Room + RemoteMediator pattern (see 30F)

// 3. LazyColumn with stable keys (Compose)
LazyColumn {
    items(items, key = { it.id }) { item ->   // stable key = no recompose on unrelated changes
        FeedItemRow(item)
    }
}

// 4. Fixed item size — avoid remeasuring every scroll
// RecyclerView: setHasFixedSize(true) if item heights are uniform
// Compose: use height(Dp) instead of wrapContentHeight() where possible
DiffUtil Algorithm

DiffUtil uses Eugene Myers' diff algorithm (O(N+D²) where D = number of changes). For large lists (>1000 items), compute the diff on a background thread and submit to the adapter on main thread — ListAdapter does this automatically.

7. Interview Framework
Concurrency Question Framework
When asked "how do you make two API calls", always address: 1) The happy path (async/await) → 2) What if one fails? (runCatching, partial result) → 3) Cancellation (coroutineScope auto-cancels siblings on failure). This shows senior-level thinking.

Token Refresh: The Key Insight

The critical insight is the double-check pattern inside the Mutex: when 5 coroutines are waiting for the lock and coroutine #1 refreshes the token, the other 4 should NOT refresh again. After acquiring the lock, check if the token is now valid — if so, return immediately without refreshing.

Stale Cache: The Golden Rule

"Never show a blank screen when you have cached data." Always prefer showing stale data with an error indicator over an empty screen. The user's goal is to see data — stale data with a "refresh failed" banner is far better than nothing.

9. Practice Questions
Write Kotlin code to fetch user profile and orders in parallel. Handle the case where orders fail but user succeeds.
Hard▼
coroutineScope { val userD = async(IO) { runCatching { api.getUser(id) } }; val ordersD = async(IO) { runCatching { api.getOrders(id) } }; ProfilePage(user = userD.await().getOrThrow(), orders = ordersD.await().getOrDefault(emptyList())) }. Key: wrap each async in runCatching for independent failure handling. userD.await().getOrThrow() propagates user failure; ordersD.await().getOrDefault(emptyList()) shows empty orders on failure.
Why is the double-check pattern inside a Mutex critical for token refresh?
Hard▼
When 5 coroutines all find the token expired and race to acquire the Mutex, only one enters the lock first and refreshes the token. When the remaining 4 acquire the lock sequentially, the token is now valid. Without the double-check, all 4 would refresh again unnecessarily (and potentially invalidate the token refreshed by #1). The double-check: if (!isExpired(cachedToken)) return cachedToken — exit early after acquiring lock if already fresh.
What is the difference between async + awaitAll vs coroutineScope + launch + join?
Medium▼
async{} returns a Deferred which carries the result — you call await() to get the value. awaitAll(d1, d2) waits for all and returns a List of results. launch{} + join() only synchronizes completion — launch doesn't return a value. Use async/await when you need results. Use launch/join when you just need completion (fire and forget side effects). awaitAll() also fails fast — if any async throws, awaitAll throws immediately.
Design a UiState sealed class that handles loading, success, stale success, and error with partial data.
Medium▼
sealed class UiState<T> { object Loading : UiState<Nothing>(); data class Success(val data: T, val isStale: Boolean = false) : UiState<T>(); data class Error(val message: String, val partialData: T? = null) : UiState<T>() }. The Error state carries partialData so the UI can show stale content + error banner simultaneously. isStale on Success allows a subtle "last updated" indicator without hiding data.
Why should you never call notifyDataSetChanged() for large list updates?
Easy▼
notifyDataSetChanged() tells RecyclerView that every item has potentially changed. RecyclerView then rebinds all visible items — O(visible items) work even if only 1 item changed. It also destroys all recycled views, losing scroll state. DiffUtil computes the minimal diff (which items changed, added, removed) and only rebinds changed items. For a 10,000-item list where 1 item changed, DiffUtil rebinds 1 item; notifyDataSetChanged() rebinds ~15 visible items and invalidates the full internal state.
When would you use coroutineScope{} vs supervisorScope{} for parallel calls?
Hard▼
coroutineScope{}: if any child fails, ALL siblings are cancelled immediately. Use when all results are required — a failure in one means the whole operation fails. supervisorScope{}: children fail independently — one failure doesn't cancel others. Use when children are independent and partial results are acceptable (e.g., loading 5 widgets on a dashboard where each is independent). For the profile page example: if user fetch is required but orders are optional, use supervisorScope + runCatching on the optional async.
How does DiffUtil's areItemsTheSame differ from areContentsTheSame?
Easy▼
areItemsTheSame: checks if two items represent the same entity (same ID). This determines the structural diff — moves, insertions, deletions. Returns true if it's the "same item" even if the content changed. areContentsTheSame: only called when areItemsTheSame returns true. Checks if the item's visual content has changed — determines whether to call onBindViewHolder. Return old == new (data class equality). Example: areItemsTheSame(old, new) = old.id == new.id; areContentsTheSame(old, new) = old == new.
What happens if you call await() on a Deferred that threw an exception?
Medium▼
Calling await() on a failed Deferred re-throws the exception at the await() call site. This is the mechanism for propagating errors from async back to the parent. If you call awaitAll() on a list that contains a failed Deferred, it throws the first exception it encounters. Wrap in runCatching { deferred.await() } to handle per-request errors without cancelling the parent scope.
How would you implement a "refresh" button in a stale-data scenario?
Medium▼
Add a refresh() function in the ViewModel that: (1) Sets state to Loading (or Success(stale=true) to keep showing data), (2) Calls the repository network refresh explicitly, (3) Updates state on success/failure. Use a MutableStateFlow for the refresh trigger or just call a suspend function. Don't re-collect the repository Flow — call a dedicated refresh method that bypasses cache and goes straight to network, then updates Room, which triggers the existing Flow from Room.
How do you prevent a user from rapidly tapping a button to trigger multiple concurrent API calls?
Medium▼
In the ViewModel, check for an in-progress state before launching: if (_uiState.value is Loading) return. This prevents concurrent launches. Alternatively, use a loading flag: private var isLoading = false; fun onSubmit() { if (isLoading) return; isLoading = true; viewModelScope.launch { try { ... } finally { isLoading = false } } }. In Compose, disable the button when loading: Button(enabled = uiState !is Loading, onClick = {...}).
