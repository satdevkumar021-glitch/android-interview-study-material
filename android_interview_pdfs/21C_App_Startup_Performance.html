Overview — Startup Types

Three Startup Types

TypeProcess StateActivity StateTimeline StepsTypical DurationOptimisation Levers
Cold Start Does not exist Does not exist Zygote fork → JVM init → Application.onCreate() → ContentProviders → Activity.onCreate() → layout inflate → first frame 300ms–3000ms Baseline Profile, lazy init, App Startup library, reduce ContentProviders

Why Startup Matters

  • Play Store ranking: Google Play considers startup performance in app quality signals and ranking algorithms.
  • Retention impact: Users who experience >5 second cold starts have a 29% higher uninstall rate within 30 days.
  • Revenue: E-commerce studies show each additional 100ms of startup latency correlates with ~1% drop in conversion.

TTID vs TTFD

TTID (Time to Initial Display): Time from launch intent to first frame rendered on screen. Measured automatically by the system. Check with adb shell am start -W → ThisTime.

TTFD (Time to Full Display): Time until your content is fully loaded and useful. You control this by calling reportFullyDrawn(). Without this call, Macrobenchmark cannot measure TTFD accurately.

Key Distinction
TTID can look great (fast skeleton/splash) while TTFD is terrible (data loads slowly). Users see TTFD. Always optimise and measure both — and always call reportFullyDrawn() when your real content is visible.

The Startup Timeline

Full annotated cold start sequence from process creation to first rendered frame:

1
System forks from Zygote
Android's Zygote process pre-warms a JVM and pre-loads common classes. Your app process is forked from this. Not optimisable by the app developer.
2
JVM initialised, DEX classes loaded
Class loading begins. With a Baseline Profile, startup-path classes are already AOT-compiled. Partially optimisable via Baseline Profiles.
3
ContentProviders initialised ⚠️ HIDDEN BOTTLENECK
Every registered ContentProvider is initialised before Application.onCreate() runs. Many SDKs use the ContentProvider trick for auto-init: Firebase, WorkManager, Lifecycle, CameraX. Each CP holds the Application Context lock. With 5–8 SDKs, this can consume 50–150ms.
4
Application.attachBaseContext() → Application.onCreate()
DI graph, logging, analytics, crash reporting initialised here. Major optimisation opportunity. Move non-critical SDK init off main thread. Use lazy init and App Startup library.
5
Activity created — setContentView() / Compose setContent()
Layout inflation (XML) or initial composition (Compose). Complex layouts with deep hierarchies or custom views inflate slowly. Optimise with ViewStub, Compose, constraint-flat hierarchies.
6
Layout measured, laid out, drawn → TTID
First frame rendered to screen. This is TTID — what adb shell am start -W reports as ThisTime. The system records this automatically.
7
Async data loads complete → UI updates → reportFullyDrawn() → TTFD
Network calls, database queries, image loading finish. UI transitions from skeleton/loading state to full content. Call reportFullyDrawn() here. This is TTFD.

App Startup Library

Problem: N SDKs registering N ContentProviders for auto-init creates N separate ContentProvider instantiations, each holding the Application Context lock on the main thread during startup.

Solution: The App Startup library provides a single ContentProvider (InitializationProvider) that orchestrates all registered Initializers in dependency order.

✅ Impact
App Startup replaces N ContentProviders with 1. For an app with 5 auto-init SDKs, this eliminates 4 unnecessary ContentProvider creations — each of which holds an Application Context lock during initialisation. Typical saving: 20–60ms of cold start time.

Dependency

// build.gradle.kts
implementation("androidx.startup:startup-runtime:1.1.1")

Writing Initializers

// WorkManager initializer
class WorkManagerInitializer : Initializer<WorkManager> {
    override fun create(context: Context): WorkManager {
        WorkManager.initialize(context, Configuration.Builder().build())
        return WorkManager.getInstance(context)
    }
    override fun dependencies(): List<Class<out Initializer<*>>> = emptyList()
}

// Timber initializer (no dependencies)
class TimberInitializer : Initializer<Unit> {
    override fun create(context: Context) {
        if (BuildConfig.DEBUG) Timber.plant(Timber.DebugTree())
    }
    override fun dependencies(): List<Class<out Initializer<*>>> = emptyList()
}

// Crashlytics initializer — depends on Timber being ready first
class CrashlyticsInitializer : Initializer<Unit> {
    override fun create(context: Context) {
        FirebaseCrashlytics.getInstance().setCrashlyticsCollectionEnabled(!BuildConfig.DEBUG)
    }
    override fun dependencies() = listOf(TimberInitializer::class.java)
}

Cold Start Optimisation

Optimisation Checklist — Ranked by Impact

1. Move Heavy Init Out of Application.onCreate()

// ❌ BEFORE: blocking main thread at startup
class MyApplication : Application() {
    override fun onCreate() {
        super.onCreate()
        HeavyAnalyticsSdk.initialize(this)        // 80ms on main thread
        ImageLoader.setup(this, diskCacheSize = 500_000_000) // 40ms
    }
}

// ✅ AFTER: defer to background thread
class MyApplication : Application() {
    override fun onCreate() {
        super.onCreate()
        // Only critical-path init on main thread
        Timber.plant(Timber.DebugTree())
        // Defer heavy init
        AppScope.launch(Dispatchers.IO) {
            HeavyAnalyticsSdk.initialize(this@MyApplication)
        }
    }
}

2. SplashScreen API — Instant Perceived Start

// themes.xml
<style name="Theme.App.Starting" parent="Theme.SplashScreen">
    <item name="windowSplashScreenBackground">@color/brand_bg</item>
    <item name="windowSplashScreenAnimatedIcon">@drawable/ic_logo</item>
    <item name="postSplashScreenTheme">@style/Theme.App</item>
</style>

// MainActivity.kt
override fun onCreate(savedInstanceState: Bundle?) {
    val splashScreen = installSplashScreen()
    super.onCreate(savedInstanceState)
    // Keep splash visible until data is ready
    splashScreen.setKeepOnScreenCondition { !viewModel.isReady }
    setContentView(R.layout.activity_main)
}

3. Reduce ContentProviders — Use App Startup Library

See Section 3 for full implementation. Replace N SDK ContentProviders with a single InitializationProvider.

4. Lazy-load Non-Critical Dependencies

// Hilt lazy injection — AnalyticsManager not created until first access
@AndroidEntryPoint
class MainActivity : AppCompatActivity() {
    @Inject lateinit var analyticsManager: Lazy<AnalyticsManager>

    override fun onCreate(savedInstanceState: Bundle?) {
        super.onCreate(savedInstanceState)
        // analyticsManager.get() called here — not at startup
    }

    fun onUserAction() {
        analyticsManager.get().track("user_action") // Created on first use
    }
}

5. Enable R8 / Code Shrinking

Smaller DEX files mean faster class loading. Enable R8 in release builds and write effective ProGuard rules. Unused classes removed = faster startup.

6. Add Baseline Profile

See module 21B. AOT-compiles startup-critical code. Typically the highest single-step improvement at 20–40%.

class HomeViewModel @Inject constructor(
    private val repo: ProductRepository

    init {

AtomicReference Background Singleton Init

object HeavySingleton {
    private val instance = AtomicReference<HeavyService?>(null)

    fun initInBackground(context: Context) {
        Thread {
            instance.set(HeavyService(context)) // background thread
        }.start()
    }

    fun get(): HeavyService? = instance.get() // null until ready
}

                onContentReady = {

                    reportFullyDrawn()

            )
        }
    }

Custom Trace Sections

Add named sections to your code — they appear as labelled spans in Perfetto's timeline:

class MyApplication : Application() {
    override fun onCreate() {
        Trace.beginSection("App.onCreate")
        super.onCreate()

        Trace.beginSection("App.initTimber")
        Timber.plant(Timber.DebugTree())
        Trace.endSection()

        Trace.beginSection("App.initDatabase")
        Room.databaseBuilder(this, AppDatabase::class.java, "app.db")
            .build()
        Trace.endSection()

        Trace.endSection() // App.onCreate
    }
}

What to Look for in a Startup Trace

  • Main thread blocking work: Any long spans on the main thread before first frame. Should be <16ms each.
  • ContentProvider init time: Look for bindApplication → ContentProvider: [name] sections. Identify which SDKs are slowest.
  • Large class loads: Look for ClassLoad events — indicates classes not in Baseline Profile being JIT-compiled for first time.
  • Synchronous I/O: Look for disk read/write on main thread. Even small SharedPreferences reads can block 5–20ms.
  • Blocking coroutines: runBlocking on main thread appears as a blocked main thread span.

Pitfalls & Common Mistakes
❌ SharedPreferences in Application.onCreate()
SharedPreferences.getString() triggers a synchronous disk read on the main thread. On a cold device with fragmented storage, this can take 10–50ms.
✅ Fix: Migrate to DataStore and read asynchronously. If you must use SharedPreferences, move the read to a background thread and use a LiveData/StateFlow to observe the result.
❌ Too Many ContentProviders for Auto-Init
Each SDK registering its own ContentProvider adds ~5–15ms of main-thread overhead per ContentProvider at startup.
✅ Fix: Use the App Startup library to consolidate all SDK init into a single ContentProvider with ordered, dependency-aware Initializers.
❌ Initialising Analytics/Crash/Push on Main Thread
Firebase Analytics, Crashlytics, and push notification SDKs often do file I/O and network calls during init. Calling these on the main thread adds 50–150ms.
✅ Fix: Check SDK docs for thread safety — most modern SDKs support background-thread init. Use AppScope.launch(Dispatchers.IO).
❌ Large Static Initialiser Blocks
Kotlin companion object and object declarations with heavy static initialisation run when the class is first loaded — which can be during startup.
✅ Fix: Profile with Perfetto to identify expensive class load events. Convert static-init work to lazy properties.
❌ Not Calling reportFullyDrawn()
Without reportFullyDrawn(), Macrobenchmark cannot measure TTFD accurately — it falls back to a heuristic that may not match real user-perceived loading time.
✅ Fix: Call reportFullyDrawn() (or the Compose ReportDrawn/ReportDrawnWhen modifiers) precisely when your first screen's meaningful content is fully visible.
❌ Measuring Startup on a Device with a Cold JIT Cache
First launch on a freshly installed build is always slow (JIT not yet warmed). Measuring only the first launch gives a misleadingly bad number.
✅ Fix: Use Macrobenchmark's StartupMode.COLD which kills and restarts the app process for each iteration, giving statistically valid cold-start numbers with correct ART state.

Interview Framework

30-Second Answer

"Cold start is the full path: Zygote fork → ContentProviders init → Application onCreate → Activity created → first frame drawn. The two main optimisation levers are: (1) Baseline Profiles for AOT compilation — 20–40% faster without code changes. (2) Moving heavy work out of Application.onCreate() — use the App Startup library to merge ContentProviders and enable lazy initialisation of non-critical SDKs. I measure with adb am start -W and Macrobenchmark's StartupTimingMetric, and I always call reportFullyDrawn() for accurate TTFD."

  1. Define startup types: Cold (full process creation) / Warm (Activity recreated) / Hot (resume) — different optimisation levers for each

  4. Application.onCreate(): Move non-critical SDK init to background thread; use Hilt Lazy for deferred DI
  5. Measurement: adb am start -W for quick checks; Macrobenchmark for CI-grade measurement; Perfetto for detailed profiling
  6. Baseline Profiles: AOT-compile the startup path — the highest-impact single optimisation

Interview Questions
What is the difference between cold start, warm start, and hot start?
Easy▾
  • Cold start: The app process does not exist. Android forks from Zygote, creates the Application, initialises ContentProviders, runs Application.onCreate(), creates the Activity, inflates/composes the layout, and draws the first frame. Slowest — full initialization path runs.
  • Warm start: The app process still exists in memory, but the Activity was destroyed (user pressed back, or system killed the Activity under memory pressure). The system recreates only the Activity — Application.onCreate() does NOT run again. Faster than cold, but layout still inflated.
  • Hot start: Both process and Activity still exist. The Activity was merely paused (user switched apps, received a call). It's just brought back to the foreground. Fastest — nearly instant.

Why it matters for interviews: Most startup optimisation questions are about cold start. Warm start is optimised differently (fast Activity recreation, saved state efficiency). Hot start rarely needs optimisation.

What is the difference between TTID and TTFD? How do you measure each?
Easy▾

TTID (Time to Initial Display): The time from launch intent to the first frame rendered on screen. Measured automatically by the system — even a blank/skeleton frame counts. Reported by adb shell am start -W as ThisTime. Also measured by Macrobenchmark's StartupTimingMetric automatically.

TTFD (Time to Full Display): The time until your app's content is actually useful — data loaded, images showing, interactive. You must signal this by calling reportFullyDrawn() (or the Compose equivalents ReportDrawn/ReportDrawnWhen). Without this call, Macrobenchmark cannot measure TTFD accurately.

Why the distinction matters: An app can show a fast skeleton screen (good TTID) while the actual data loads slowly (bad TTFD). Users experience TTFD — the screen isn't useful until data appears. You should optimise and monitor both metrics.

Why are ContentProviders a startup bottleneck, and how does the App Startup library solve this?
Medium▾

The Problem: Android initialises all registered ContentProviders on the main thread before Application.onCreate() runs. Many popular SDKs (Firebase, WorkManager, Lifecycle, CameraX, etc.) use the ContentProvider trick for auto-initialisation: they register a ContentProvider in their manifest, and its onCreate() triggers their SDK init. With 5–8 SDKs, you can have 5–8 ContentProviders each blocking the main thread for 5–20ms each = 50–150ms hidden startup cost.

App Startup Solution:

  1. Replaces all SDK ContentProviders with a single InitializationProvider
  2. Each SDK implements the Initializer<T> interface instead of a ContentProvider
  3. Initializers declare their dependencies — App Startup topologically sorts and runs them in order
  4. Supports lazy initialisation: mark an initializer to not run at startup, call manually when needed

Net result: 1 ContentProvider creation instead of N. The remaining init code still runs, but the ContentProvider overhead is eliminated 4+ times.

How do you measure cold start time on Android? Name at least two methods.
Medium▾
  1. adb shell am start -W: Quick command-line measurement. Force-stop the app first (am force-stop), then run. Returns ThisTime (Activity launch time = TTID) and TotalTime. Good for quick checks but not statistically rigorous — single measurement, not averaged.
  2. Macrobenchmark with StartupTimingMetric: Production-quality measurement. Runs multiple iterations, kills the process between each (for COLD mode), reports P50/P90/P99 percentiles of timeToInitialDisplay and timeToFullDisplay. Requires physical device or Firebase Test Lab.
  3. Perfetto / System Trace: Not a timing tool per se, but gives the full startup flame graph — lets you see why startup is slow: which ContentProviders, which method calls, which class loads. Essential for diagnosis after you've identified there's a problem.
  4. Android Studio Profiler — App Startup template: GUI-based automated startup trace. Provides flame graph of the full startup call stack directly in AS.
What is the relationship between Baseline Profiles and cold start performance?
Medium▾

Without Baseline Profiles, ART starts in interpreted mode on cold start — every method in the startup path runs as bytecode first, then JIT-compiles "hot" methods after ~30–60 executions. This means the very first cold start (and subsequent ones until the JIT warms up, which happens over days) is 20–40% slower than it could be.

Baseline Profiles pre-populate the ART profile cache at install time. ProfileInstaller reads baseline-prof.txt from the AAB, converts it to binary ART format, and ART's background compiler AOT-compiles all listed methods. On next cold start, those methods execute at native speed — no interpretation overhead, no JIT delay.

Typical measured impact:

  • Cold start TTID: 30–80ms reduction (15–40%)
  • First scroll jank: significantly reduced for the first few seconds
  • First navigation: faster as Fragments/composables are pre-compiled

Key point for interviews: Baseline Profiles are purely additive and risk-free. They improve performance with zero code changes — just a text file shipped in your AAB.

What lazy initialisation patterns do you use in Android, and when should you use each?
Hard▾
  • Kotlin by lazy: For class properties that are expensive to construct but not always needed. Thread-safe by default (SYNCHRONIZED mode). Best for repositories, parsers, validators that may not be used in every code path.
  • Hilt Lazy<T> (dagger.Lazy): For injected dependencies in Activities/Fragments that aren't needed until after first user interaction. The DI graph constructs the object on first .get() call rather than at injection time.
  • Deferred coroutine init: For initialisation that involves I/O or network. Launch a coroutine in viewModelScope or lifecycleScope using Dispatchers.IO. Expose a StateFlow that the UI observes — shows loading state until ready.
  • Background thread with AtomicReference: For low-level singleton services that must be thread-safe and initialised exactly once on a background thread. Set the reference when done; callers check for null before use.
  • App Startup library lazy mode: Mark SDK initializers as lazy in the manifest; call AppInitializer.getInstance(context).initializeComponent() at the appropriate time (e.g., after first frame, or when user first triggers a feature).

General rule: Anything taking >5ms that isn't needed before the first frame should be deferred. Profile with Perfetto first — don't guess what's slow.

A Perfetto trace of your app's cold start shows 400ms of main thread blocking before the first frame. How do you diagnose and fix this?
Hard▾

Step 1 — Identify the blocking sections in the trace:

  • Expand the main thread lane in Perfetto. Look for the bindApplication event and zoom into it.
  • Identify ContentProvider initialisation spans — these appear before your code. Sum their durations.
  • Find Application.onCreate() span. Expand to see child spans (if you added Trace.beginSection() calls).
  • Look for any disk I/O events on the main thread (typically SharedPreferences, database opens).
  • Look for long class-load events — large DEX sections being JIT-compiled on first use.

Step 2 — Fix by category:

  • ContentProvider bottleneck (100ms+): Migrate all SDK auto-inits to App Startup library. Identify which SDK's ContentProvider is slowest by checking individual CP spans.
  • Application.onCreate() work (100ms+): Move all non-critical SDK init to background thread via AppScope.launch(Dispatchers.IO).
  • Disk I/O on main thread: Replace SharedPreferences with DataStore. Open databases on background thread.
  • Class loading overhead: Add Baseline Profile — lists the startup-path classes for AOT compilation, eliminating first-launch JIT.

Step 3 — Verify: Add Trace.beginSection() calls around each fixed section, re-capture Perfetto, confirm each section is now <16ms or moved off main thread. Validate final TTID improvement with Macrobenchmark.

You must design startup for a new app that must show first frame in under 300ms on a mid-range device. What is your strategy?
Hard▾

300ms cold start on mid-range hardware is aggressive (equivalent to flagship targets on budget devices). Requires a systematic approach from day one:

Architecture decisions:

  • No synchronous work in Application.onCreate(): Only fire-and-forget coroutines for non-critical SDKs. Logging library only.
  • App Startup library from day 1: Zero extra ContentProviders — all SDK inits go through a single Initializer dependency graph.
  • SplashScreen API: System shows splash immediately (before your code runs) — perceived start is faster than TTID.

First screen design:

  • First screen must be renderable from static/cached data — no blocking network call before first frame.
  • Use a skeleton/shimmer layout that displays instantly. Call reportFullyDrawn() only when real content loads.
  • Prefer Compose for the first screen — Compose's lazy composition model is generally faster to first frame than deep XML hierarchies.

Compilation strategy:

  • Baseline Profile from day 1: Generate covering the full startup path. Regenerate on every release. This alone typically saves 60–100ms on cold start.
  • R8 full mode: Maximum code shrinking = smallest DEX = fastest class loading.

Measurement strategy:

  • Set up Macrobenchmark in CI from day 1. Fail the build if cold start TTID exceeds 280ms (10ms buffer).
  • Test on target hardware (mid-range device, not flagship).
  • Measure with Perfetto at each milestone to catch regressions early — it's far harder to fix a 600ms startup than to maintain a 250ms one.
