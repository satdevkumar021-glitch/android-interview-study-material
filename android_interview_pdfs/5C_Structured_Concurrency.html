5C — Structured Concurrency & Key Differences

The hierarchy: CoroutineScope → CoroutineContext → Job → children. Plus the most-asked comparison questions: launch vs async, coroutineScope vs supervisorScope, Job vs SupervisorJob, delay vs Thread.sleep.

ID: 5C ⭐ Tier 1 🔥 Highest Priority
🔍
1. Overview

In Plain Words

Think of coroutines like employees in a company with a strict org chart. Every employee (coroutine) reports to a manager (scope). When the manager leaves (scope is cancelled), every direct report is let go too — automatically, with no manual cleanup. No one can "go rogue" and keep working after their manager is gone.

Before structured concurrency this was like hiring freelancers with no manager: you'd launch work in an Activity, the Activity would be destroyed, but the coroutine kept billing — holding a reference to the dead Activity, causing NPEs and memory leaks. Structured concurrency makes orphan coroutines architecturally impossible.

The hierarchy

Structured concurrency is the guarantee that every coroutine belongs to a scope, and no coroutine outlives its scope. The hierarchy is:

CoroutineScope
  └─ CoroutineContext  // type-indexed immutable map of Element subtypes (Key → Element)
       ├─ Dispatcher    // which thread pool
       ├─ Job           // lifecycle + parent-child links  ← this is the heart of SC
       ├─ CoroutineName // debug only
       └─ ExceptionHandler // uncaught-error last resort

// CoroutineContext is NOT a tree — it is a flat map keyed by element type.
// The TREE is formed by the Job hierarchy inside that context.
// When you launch a child coroutine:
// - Child gets a NEW Job registered as a child of the parent Job
// - Child INHERITS everything else (Dispatcher, name, handler) from the parent context
// - Cancelling the parent Job → sends CancellationException DOWN to all children
// - Parent Job only completes after ALL child Jobs complete

Three guarantees of structured concurrency

  • No leaks — coroutines auto-cancel when their scope is cancelled; no coroutine outlives its parent
  • Error propagation — child failures propagate UP to parent (unless the parent has a SupervisorJob)
  • Completion guarantee — a parent waits for ALL children before it completes; a suspend function that launches coroutines inside coroutineScope { } won't return until all of them are done
Why It Matters for Senior Interviews
Interviewers test whether you know the mechanism, not just the rule. The key mechanism: when you call launch { }, the new Job object is attached to the parent's Job via Job.attachChild(). Cancellation is cooperative — the child must call isActive, ensureActive(), or hit a suspension point for the CancellationException to actually terminate the coroutine.

2. How It Works

Job hierarchy in code

val scope = CoroutineScope(SupervisorJob() + Dispatchers.Main)

val parentJob = scope.launch {              // child of scope's SupervisorJob
    val child1 = launch { doWork1() }       // child of parentJob
    val child2 = launch { doWork2() }       // child of parentJob
    // parentJob won't complete until child1 AND child2 complete
}
// Cancelling parentJob → cancels child1 AND child2
// Cancelling scope → cancels parentJob → cascades

coroutineScope vs supervisorScope

// coroutineScope: any child failure cancels ALL siblings + parent
suspend fun loadAll() = coroutineScope {
    launch { fetchA() }   // if this throws…
    launch { fetchB() }   // …this is cancelled too
}                          // and exception propagates to caller

// supervisorScope: child failures are independent — siblings survive
suspend fun loadDashboard() = supervisorScope {
    launch { fetchUser() }         // if this throws…
    launch { fetchRecommend() }    // …this still completes
}                                   // partial results possible

Cooperative cancellation — how it actually works

Cancellation in coroutines is cooperative, not preemptive. Sending a cancel signal does not immediately stop the coroutine — the coroutine must reach a cancellation checkpoint. Three ways to cooperate:

suspend fun heavyWork() {
    for (i in 1..1_000_000) {
        // Option 1: ensureActive() — throws CancellationException if cancelled
        ensureActive()
        doUnitOfWork(i)
    }
}

suspend fun heavyWorkYield() {
    for (i in 1..1_000_000) {
        // Option 2: yield() — checks cancellation AND gives up the thread
        yield()
        doUnitOfWork(i)
    }
}

fun checkActiveManually(scope: CoroutineScope) {
    // Option 3: isActive — for non-suspend contexts (callbacks, loops)
    while (scope.isActive) {
        doUnitOfWork()
    }
}

// ⚠️ A CPU-bound loop with NO checkpoint will NOT cancel:
suspend fun uncancellable() {            // ❌ BAD
    var i = 0
    while (i++ < 1_000_000) { doWork() }  // cancel() has no effect here
}

withContext(NonCancellable) — cleanup that must not be interrupted

suspend fun uploadWithCleanup() {
    try {
        uploadFile()
    } finally {
        // If we're here because of cancellation, this coroutine is already in
        // "cancelling" state — calling a suspend function would throw immediately.
        // Wrap cleanup in NonCancellable to allow suspending in finally:
        withContext(NonCancellable) {
            uploadRepo.markUploadFailed()   // suspend call safe here
            tempFileRepo.deleteTempFile()   // suspend call safe here
        }
    }
}
// ⚠️ Only use NonCancellable in finally blocks — never as a scope for entire operations.

3. Key Differences (Interview Goldmine)

delay() vs Thread.sleep()

delay()Thread.sleep()
TypeSuspend function (coroutine-aware)Blocking function
ThreadFrees the thread for other coroutinesBlocks the OS thread entirely
CancellationRespects cooperative cancellationCannot be cancelled cooperatively
TestingWorks with virtual clock in runTestAlways waits real time

suspend vs blocking

// suspend: cooperative, frees thread at suspension points
suspend fun fetchData(): Data {
    return withContext(Dispatchers.IO) { api.call() }
}

// blocking: holds the thread, must be wrapped in withContext(IO)
fun fetchDataBlocking(): Data = api.callBlocking()  // ❌ on Main

// Making blocking safe:
suspend fun safeBlocking() = withContext(Dispatchers.IO) {
    fetchDataBlocking()  // ✅ blocking on IO thread, safe
}

withContext vs async/await

// withContext: sequential, inline switch — use for single result
val user = withContext(Dispatchers.IO) { repo.getUser() }

// async/await: concurrent new coroutine — use for parallel work
val userDef = async(Dispatchers.IO) { repo.getUser() }
val ordersDef = async(Dispatchers.IO) { repo.getOrders() }
val user = userDef.await()
val orders = ordersDef.await()
// Both fetched simultaneously!

launch vs async — exception handling (CRITICAL INTERVIEW TRAP)

// launch: exception immediately propagates to parent Job
viewModelScope.launch {
    throw IOException("network error")
    // Reaches CoroutineExceptionHandler (if set), then crashes the app
}

// async under SupervisorJob (viewModelScope): exception STORED in Deferred
// Only thrown when you call .await()
val deferred = viewModelScope.async {
    throw IOException("network error")
}
try { deferred.await() }          // ✅ exception thrown here — catchable
catch (e: IOException) { /* handled */ }
⚠️ Critical Difference: async inside coroutineScope vs supervisorScope

The try/catch on await() above works because viewModelScope uses SupervisorJob. Inside a regular coroutineScope { }, async exceptions behave differently:

// ❌ TRAP: async inside coroutineScope — exception does NOT wait for await()
coroutineScope {
    val d = async { throw IOException() }
    // IOException propagates IMMEDIATELY to the coroutineScope
    // The scope is cancelled. When you call d.await(), the scope
    // is already done — your try/catch may NEVER execute.
    try { d.await() } catch (e: IOException) { }  // ← may miss the exception
}

// ✅ CORRECT: use supervisorScope when you want async exceptions on await() only
supervisorScope {
    val d = async { throw IOException() }
    try { d.await() } catch (e: IOException) { }  // ✅ reliably caught here
}

// Senior rule: async exception behaviour depends on the PARENT's Job type.
// Under SupervisorJob → stored until await().
// Under regular Job   → propagates immediately (even before await()).

CancellationException — the rule you must know

// CancellationException is special. Rules:
// 1. It extends IllegalStateException (not RuntimeException)
// 2. It is used as the cooperative cancellation signal
// 3. NEVER swallow it — always re-throw:

suspend fun bad() {
    try { delay(1000) }
    catch (e: Exception) { /* ❌ swallows CancellationException! */ }
}

suspend fun good() {
    try { delay(1000) }
    catch (e: CancellationException) { throw e }  // ✅ always re-throw CE
    catch (e: Exception) { /* handle other errors */ }
}

// runCatching ALSO swallows CancellationException — use safeRunCatching:
suspend fun <T> safeRunCatching(block: suspend () -> T): Result<T> =
    runCatching { block() }
        .onFailure { if (it is CancellationException) throw it }

4. Production Example

Banking: funds transfer — all-or-nothing (coroutineScope)

Two real-world patterns side by side: a funds transfer (all-or-nothing) and a dashboard (partial results ok).

// ═══ PATTERN 1: All-or-nothing — use coroutineScope ═══
// coroutineScope is a CONCURRENCY boundary, NOT a transaction boundary.
// For true atomicity you still need a database transaction around the ledger ops.
suspend fun TransferService.transfer(
    from: Account, to: Account, amount: BigDecimal
): TransferResult = coroutineScope {
    // Parallel validation — if EITHER throws, the other is cancelled too
    val fromOk = async { accountRepo.validateSufficientFunds(from, amount) }
    val toOk   = async { accountRepo.validateAccountActive(to) }

    if (!fromOk.await() || !toOk.await()) {
        return@coroutineScope TransferResult.Rejected
    }

    // Sequential — debit must happen before credit.
    // ⚠️ If process dies between debit and credit, coroutineScope won't roll it back.
    // In production: wrap in a database transaction or use outbox/saga pattern.
    withContext(Dispatchers.IO) {
        ledgerRepo.debit(from, amount)   // if this throws, credit never runs
        ledgerRepo.credit(to, amount)
    }
    TransferResult.Success
}

// ═══ PATTERN 2: Partial results OK — use supervisorScope ═══
// Note: use safeRunCatching (re-throws CancellationException).
// Plain runCatching would swallow CE and break cooperative cancellation.
suspend fun loadDashboard(): DashboardState = supervisorScope {
    val balanceDef = async { safeRunCatching { accountRepo.getBalance() } }
    val txnsDef    = async { safeRunCatching { txnRepo.getRecent() } }
    val offersDef  = async { safeRunCatching { offersRepo.getOffers() } }

    DashboardState(
        balance      = balanceDef.await().getOrNull(),      // null = show error widget
        transactions = txnsDef.await().getOrNull() ?: emptyList(),
        offers       = offersDef.await().getOrNull() ?: emptyList()
    )
}

// ═══ PATTERN 3: Full-stack ViewModel → UseCase → Repository ═══
// How structured concurrency flows through Clean Architecture layers
class DashboardViewModel(
    private val loadDashboard: LoadDashboardUseCase
) : ViewModel() {

    private val _uiState = MutableStateFlow<DashboardUiState>(DashboardUiState.Loading)
    val uiState: StateFlow<DashboardUiState> = _uiState.asStateFlow()

    fun load() {
        viewModelScope.launch {
            _uiState.emit(DashboardUiState.Loading)
            _uiState.emit(loadDashboard())
        }
    }
}

// Domain layer — no Android imports, pure Kotlin
class LoadDashboardUseCase(
    private val accountRepo: AccountRepository,
    private val txnRepo: TransactionRepository,
    private val offersRepo: OffersRepository
) {
    suspend operator fun invoke(): DashboardUiState = supervisorScope {
        val balanceDef = async { safeRunCatching { accountRepo.getBalance() } }
        val txnsDef    = async { safeRunCatching { txnRepo.getRecent() } }
        val offersDef  = async { safeRunCatching { offersRepo.getOffers() } }

        val balance = balanceDef.await()
        if (balance.isFailure) return@supervisorScope DashboardUiState.Error("Balance unavailable")

        DashboardUiState.Success(
            balance      = balance.getOrThrow(),
            transactions = txnsDef.await().getOrNull() ?: emptyList(),
            offers       = offersDef.await().getOrNull() ?: emptyList()
        )
    }
}

Cancellation vs exception propagation

Key Rule
Cancellation (via job.cancel()) uses CancellationException — it propagates down to children but NOT up to the parent. The parent continues. Non-cancellation exceptions propagate up AND cancel siblings. This asymmetry is by design. 
// Cancellation: downward only
val parent = scope.launch {
    val child = launch { longWork() }
    child.cancel()           // only child cancelled, parent continues
    doOtherWork()            // still runs
}

// Exception: upward + siblings
val parent = scope.launch {
    launch { throw IOException() }  // sibling also cancelled
    launch { otherWork() }           // CANCELLED due to sibling failure
}

6. Pitfalls & Best Practices
Pitfall 1 — Breaking hierarchy with a new Job()

launch(Job()) { } — adding a raw Job() to the context replaces the parent Job, disconnecting this coroutine from the parent scope. Cancelling the scope will NOT cancel this child — it becomes an orphan coroutine. Production symptom: coroutines survive Activity/ViewModel destruction, causing memory leaks and stale callbacks.

Fix: Never pass a raw Job() or SupervisorJob() to a builder. Use supervisorScope { } instead.

Pitfall 2 — launch(SupervisorJob()) creates an orphan too

viewModelScope.launch(SupervisorJob()) { } is just as dangerous as launch(Job()). The SupervisorJob replaces the parent job, creating an orphan that survives viewModelScope.cancel(). Developers write this thinking it gives child-isolation — it doesn't; it gives orphan coroutines.

// ❌ ORPHAN — survives viewModelScope.cancel()
viewModelScope.launch(SupervisorJob()) { /* still running after VM cleared */ }

// ✅ CORRECT — child isolation without orphaning
viewModelScope.launch {
    supervisorScope {
        launch { fetchA() }  // isolated from each other
        launch { fetchB() }  // but both still scoped to viewModelScope
    }
}
Pitfall 3 — Swallowing CancellationException

Catching Exception or using runCatching { } without re-throwing CancellationException breaks cooperative cancellation. The scope appears to cancel but the coroutine keeps running.

// ❌ Breaks cancellation:
try { doWork() } catch (e: Exception) { log(e) }

// ❌ runCatching also catches CE silently:
runCatching { doWork() }

// ✅ Always re-throw CE:
try { doWork() }
catch (e: CancellationException) { throw e }  // must come first
catch (e: Exception) { log(e) }
Pitfall 4 — Silent exception swallowing with un-awaited async

If you use async { } inside a supervisorScope and never call .await(), the exception is silently discarded — no crash, no log, no indication anything failed. This is especially dangerous for fire-and-forget analytics or event tracking.

// ❌ SILENT FAILURE — exception disappears forever
supervisorScope {
    async { analyticsRepo.track("event") }  // never awaited = exception gone
}

// ✅ Use launch instead if you don't need the return value:
supervisorScope {
    launch { analyticsRepo.track("event") }  // exception goes to CEH or crashes
}
Best Practice — coroutineScope for all suspend functions with concurrency

Any suspend fun that launches multiple coroutines should use coroutineScope { } or supervisorScope { } as its boundary. This makes the function's concurrency visible, safe, and lifecycle-aware. A caller can cancel the enclosing scope and know that all work inside the function stops.

Best Practice — Default to coroutineScope, not supervisorScope

supervisorScope is not the "safe default." Use coroutineScope by default (fail-fast, catch bugs early). Upgrade to supervisorScope only when you have a conscious architectural decision that partial results are acceptable for the user.

7. Interview Framework

30-second answer

"Structured concurrency means every coroutine belongs to a scope, and no coroutine outlives that scope. The hierarchy is CoroutineScope → CoroutineContext → Job → children. Cancelling a parent cancels all children; a parent waits for all children before completing; child failures propagate up unless you use SupervisorJob which isolates failures."

2-minute answer

"The key distinction between coroutineScope and supervisorScope is failure isolation. coroutineScope uses a regular Job: any child failure cancels all siblings and propagates to the caller. supervisorScope uses a SupervisorJob: each child is independent, so a failure in one doesn't affect others. viewModelScope uses SupervisorJob by default — so one failed launch doesn't crash all others.

For delay vs Thread.sleep: delay is a suspend function — it frees the thread for other coroutines during the wait and can be cancelled cooperatively. Thread.sleep blocks the OS thread entirely and ignores cancellation.

For withContext vs async: withContext is sequential — it's an inline context switch, no concurrency. async starts a new concurrent coroutine and returns a Deferred you later await. Use withContext when you need one result from a different dispatcher; use async when you want true parallelism."

Must-mention points

coroutineScope = Job (all-or-nothing) vs supervisorScope = SupervisorJob (partial ok)
2

3
launch(Job()) breaks hierarchy — never add a raw Job to a builder
4

Level 1–3 Follow-up Q&A (what the interviewer asks next)

Level 1 — "Why does viewModelScope use SupervisorJob?"

ViewModels orchestrate multiple parallel UI operations (user profile, orders, recommendations). A regular Job would mean one failed network call crashes all coroutines in the ViewModel. SupervisorJob isolates failures — each launch { } is independent. This matches the UX expectation: a failed ads call should not blank out the user's order history.

Level 2 — "What happens when a supervisorScope child throws with no handler?"

The exception is not propagated to siblings or the parent scope's Job. With launch: the exception goes to a CoroutineExceptionHandler if one is in the child's context, otherwise to Thread.defaultUncaughtExceptionHandler — crash on Android. With async: the exception is stored in the Deferred until .await() is called. If .await() is never called, the exception is silently discarded — this is a production silent failure pattern.

Level 2 — "What is CancellationException and why must you never swallow it?"

CancellationException is the cooperative signal that tells a coroutine to stop. It extends IllegalStateException (not RuntimeException). When you catch Exception broadly, you intercept it too, breaking cooperative cancellation — the scope believes it cancelled, but the coroutine's work keeps running, causing leaks and stale state. Always re-throw it, or catch it separately before other exceptions.

Level 3 — "How does async exception behavior differ under Job vs SupervisorJob parent?"

Under a regular Job parent (e.g., inside coroutineScope { }): an async exception propagates immediately when the async block throws — it cancels the scope before you even call .await(). Under a SupervisorJob parent: the exception is stored in the Deferred and only surfaces when you call .await(). The senior answer: "async exception behavior is determined by the parent's Job type, not by async itself."

Level 3 — "Walk me through what happens internally when job.cancel() is called"

1. The Job transitions to CANCELLING state. 2. A CancellationException is delivered to the coroutine at its next suspension point (or immediately if it checks ensureActive()/isActive). 3. The cancellation propagates downward to all child Jobs. 4. When all children finish their cancellation (including any finally blocks), the Job transitions to CANCELLED state. The parent is only notified (and itself transitions) after all children are done. This is the "completion guarantee" in action.

Expert Take

Expert Take — Chief Editor

The most common mistake I see in senior interviews: treating supervisorScope as the "safe default" and sprinkling it everywhere. It's not safe — it hides failures. Use coroutineScope by default; it's the one that surfaces bugs early. Upgrade to supervisorScope only with a deliberate architectural decision that partial results are acceptable to the user.

The second mistake: confusing structured concurrency's concurrency boundary with a transaction boundary. coroutineScope ensures all concurrent work is completed or cancelled together. It does NOT roll back database writes. For true atomicity, you still need a database transaction or a saga pattern around your use case.

What's changing: the Kotlin coroutines team continues to add tooling around structured concurrency — Flow.cancellable(), improvements to runTest, and structured concurrency in KMP. The concepts in this topic are the most stable part of the coroutines API; they won't change. Master the reasoning, not the syntax.

Architectural Senior Insight

Production Decision Framework

Choose coroutineScope when: all operations must succeed together (checkout, upload pipeline, multi-step form submit), or when a partial result is undefined or dangerous (e.g., debit without credit).

Choose supervisorScope when: you're composing independent data sources for a single screen, failures in one source have a sensible fallback (empty list, cached value, hidden widget), and showing partial data is strictly better than showing nothing.

Never use GlobalScope in Android apps. It has no parent, ignores lifecycle, and is effectively "unstructured concurrency" — the exact problem structured concurrency was designed to eliminate.

9. Flash Cards

Click each card to reveal the answer. Study these until you can answer without hesitation.

FC1 — What are the 3 guarantees of structured concurrency?
Core⌄
(1) No leaks — no coroutine outlives its scope. (2) Error propagation — child failures propagate to parent (unless SupervisorJob). (3) Completion guarantee — parent waits for all children before completing.
FC2 — What is a CoroutineContext?
Core⌄
A type-indexed immutable map of Element subtypes. Each element type (Dispatcher, Job, CoroutineName, ExceptionHandler) has a unique Key. You access elements by key: coroutineContext[Job], coroutineContext[CoroutineDispatcher.Key]. You combine contexts with +: later entries override earlier ones.
FC3 — coroutineScope vs supervisorScope: one-line answer
Core⌄
coroutineScope: one child fails → all siblings cancelled, exception propagates to caller. supervisorScope: one child fails → siblings unaffected, you handle failure per-child.
FC4 — delay() vs Thread.sleep(): two key differences
Core⌄
1. Thread blocking: delay() suspends the coroutine and frees the thread; Thread.sleep() blocks the OS thread. 2. Cancellation: delay() throws CancellationException if the coroutine is cancelled; Thread.sleep() ignores cancellation entirely.
FC5 — What does viewModelScope use internally?
Core⌄
SupervisorJob() + Dispatchers.Main.immediate. This means: (1) independent failures per launch, (2) coroutines start on the Main thread immediately if already on Main, (3) the scope is cancelled when ViewModel.onCleared() is called.
FC6 — Why must you NEVER pass Job() or SupervisorJob() to launch/async?
Critical⌄
Passing a Job to a builder replaces the parent Job in the context, disconnecting the new coroutine from the parent scope. Cancelling the scope will NOT cancel this orphan. Both launch(Job()) and launch(SupervisorJob()) create orphan coroutines — use supervisorScope { } inside a launch instead.
FC7 — Cancellation direction: which way does cancel() flow? Which way do exceptions flow?
Critical⌄
cancel() (CancellationException): flows DOWN to children only — parent continues. Non-cancellation exceptions: flow UP to parent and cancel ALL siblings. This asymmetry is intentional — cancellation is a normal lifecycle event; exceptions are unexpected failures.
FC8 — async exception behavior under SupervisorJob vs regular Job
Senior⌄
Under SupervisorJob (viewModelScope): exception stored in Deferred, surfaces only on .await() — catchable with try/catch. Under regular Job (coroutineScope): exception propagates immediately and cancels the scope — your try/catch on .await() may never execute because the scope is already cancelled.
FC9 — What is cooperative cancellation and what three APIs provide cancellation checkpoints?
Critical⌄
Cancellation is cooperative — the coroutine must reach a checkpoint. Three checkpoints: (1) ensureActive() — throws CancellationException if cancelled (suspension point in coroutine). (2) yield() — checks cancellation AND gives up the thread temporarily. (3) isActive — boolean check for non-suspend contexts (loops, callbacks). All suspension points (delay, withContext, await) are also implicit checkpoints.
FC10 — When and why do you use withContext(NonCancellable)?
Senior⌄
In a finally block when the coroutine is already in CANCELLING state. In that state, any suspension call would throw CancellationException immediately, aborting your cleanup. Wrapping cleanup in withContext(NonCancellable) allows suspension during the cleanup. Rule: only use it in finally blocks — never as a scope for normal operations.
FC11 — Why does runCatching break cooperative cancellation, and what is the fix?
Senior⌄
runCatching catches ALL throwables including CancellationException, wrapping it in a Result.failure(). The coroutine then continues past the cancellation signal as if nothing happened, breaking cooperative cancellation. Fix: use a safeRunCatching wrapper that re-throws CancellationException: .onFailure { if (it is CancellationException) throw it }.
FC12 — coroutineScope is a "concurrency boundary." What is it NOT?
Senior⌄
It is NOT a transaction boundary. coroutineScope ensures that all concurrent work inside it either completes or is cancelled together. It does NOT provide atomicity — if the process dies between a debit and a credit, the coroutine scope will not roll back the debit. For true atomicity, you need a database transaction (Room's @Transaction, SQLiteDatabase transaction) or a saga/outbox pattern.

10. Testing Structured Concurrency

runTest and TestScope

runTest (kotlinx-coroutines-test) runs your suspending test body in a TestScope with a virtual clock — delay() calls advance the virtual time instantly, so tests with delays don't take real time.

import kotlinx.coroutines.test.*
import kotlinx.coroutines.test.runTest

class DashboardViewModelTest {

    private val fakeAccountRepo = FakeAccountRepository()
    private val fakeTxnRepo     = FakeTransactionRepository()
    private val fakeOffersRepo  = FakeOffersRepository()

    @Test
    fun `loads all sources in parallel`() = runTest {
        // Fake repos add artificial delay to verify parallelism
        fakeAccountRepo.delay = 300
        fakeTxnRepo.delay     = 200
        fakeOffersRepo.delay  = 250

        val useCase = LoadDashboardUseCase(fakeAccountRepo, fakeTxnRepo, fakeOffersRepo)

        val startTime = currentTime
        useCase.invoke()
        val elapsed = currentTime - startTime

        // Sequential would take 300+200+250 = 750ms.
        // Parallel takes max(300, 200, 250) = 300ms.
        assertTrue(elapsed <= 350, "Expected parallel execution, got ${elapsed}ms")
    }

    @Test
    fun `balance failure returns error state`() = runTest {
        fakeAccountRepo.throwError = IOException("Network error")

        val useCase = LoadDashboardUseCase(fakeAccountRepo, fakeTxnRepo, fakeOffersRepo)
        val result = useCase.invoke()

        assertIs<DashboardUiState.Error>(result)
    }

    @Test
    fun `offers failure still shows balance and transactions`() = runTest {
        fakeOffersRepo.throwError = IOException("Offers unavailable")

        val useCase = LoadDashboardUseCase(fakeAccountRepo, fakeTxnRepo, fakeOffersRepo)
        val result = useCase.invoke()

        assertIs<DashboardUiState.Success>(result)
        assertTrue((result as DashboardUiState.Success).offers.isEmpty())
    }

    @Test
    fun `cancellation stops all in-flight work`() = runTest {
        val scope = TestScope()
        var fetchCalled = false
        fakeAccountRepo.onFetch = { fetchCalled = true }
        fakeAccountRepo.delay = 1000

        val job = scope.launch {
            LoadDashboardUseCase(fakeAccountRepo, fakeTxnRepo, fakeOffersRepo).invoke()
        }
        scope.advanceTimeBy(100)  // start the coroutines
        job.cancel()              // cancel before they finish
        scope.runCurrent()

        assertTrue(job.isCancelled)
    }
}

11. Interview Questions
What is structured concurrency and why does it matter?
Basic⌄
Structured concurrency is the guarantee that every coroutine belongs to a scope and cannot outlive it. When a scope is cancelled, all coroutines inside are cancelled too. This prevents coroutine leaks — the most common async bug before structured concurrency, where coroutines would hold references to destroyed UI components.
What is the difference between delay() and Thread.sleep()?
Basic⌄
delay() is a suspend function: it suspends the coroutine, freeing the thread to run other coroutines, and resumes after the specified time. It also respects cancellation — if the coroutine is cancelled during a delay, a CancellationException is thrown. Thread.sleep() blocks the OS thread entirely for the duration — other coroutines on that thread can't run, and it cannot be cancelled cooperatively.
What is the difference between coroutineScope and supervisorScope?
Basic⌄
coroutineScope uses a regular Job: if any child fails, all siblings are cancelled and the exception propagates to the caller. supervisorScope uses a SupervisorJob: each child is independent; a failure in one does not affect others. Use coroutineScope for all-or-nothing (transactions), supervisorScope for partial-results-ok (dashboard loading).
What is the difference between launch and async in terms of exception handling?
Intermediate⌄
With launch, exceptions propagate immediately to the parent Job. With async, the exception is stored in the Deferred and only re-thrown when .await() is called. This means you can use try/catch around await(). However, in a coroutineScope, even async exceptions cancel siblings when the scope is cancelled — the storage is temporary until you await.
Why does adding a new Job() to a launch call break structured concurrency?
Intermediate⌄
When you do scope.launch(Job()) { }, the new Job replaces the parent Job in the context — disconnecting the child from the parent's lifecycle. Cancelling the scope no longer cancels this child. It becomes an orphaned coroutine. The fix is to never pass a raw Job to builders. If you need isolation, use supervisorScope at the scope level instead.
How does cancellation propagation differ from exception propagation?
Intermediate⌄
Cancellation (via cancel()) sends a CancellationException downward — it cancels children but not the parent. The parent continues after cancelling a child. Non-cancellation exceptions propagate upward — they cancel the parent and all siblings. This asymmetry is deliberate: cancellation is a normal lifecycle event (user navigated away), while exceptions indicate unexpected failures that should abort the whole operation.
When would you choose supervisorScope over coroutineScope in a ViewModel?
Intermediate⌄
Use supervisorScope when loading multiple independent data sources for the same screen (e.g., user profile + recommendations + ads). If recommendations fail, you still want to show the profile. Use coroutineScope when the data is interdependent (e.g., first get an auth token, then use it to fetch data — token failure should abort the whole flow).
A coroutine throws an unhandled exception inside supervisorScope but there's no CoroutineExceptionHandler. What happens?
Senior⌄
In a supervisorScope, the failed child's exception is not propagated to siblings or the parent scope. However, it still needs to be handled. If the child was created with launch and has no handler, the exception reaches the global uncaught exception handler — on Android this means a crash. With async, the exception is stored in the Deferred until await(). The correct pattern inside supervisorScope: wrap each child's logic in try/catch, or add a CoroutineExceptionHandler to the child's context.
Explain the 3 guarantees of structured concurrency and how each prevents a common production bug.
Senior⌄
(1) No leaks: coroutines auto-cancel with their scope — prevents callbacks firing after Activity destroy, preventing NPEs and outdated UI updates. (2) Error propagation: failures are never silently dropped — in coroutineScope, a silent failure in one operation doesn't leave the app in an inconsistent partial state. (3) Completion guarantee: parent waits for all children — a function that returns only after all its spawned work is done, preventing data races where callers assume work is complete when it isn't.
Design the concurrency model for a banking dashboard that must show balance (critical), recent transactions (important), and promotional offers (optional). Handle failures gracefully.
Senior⌄
Use supervisorScope for isolation with safeRunCatching (re-throws CancellationException) per source. Balance is critical — return an error state if it fails. Transactions show an empty list on failure. Offers are silently omitted. All three run in parallel: total latency = max(individual latencies) instead of sum. Critically: use safeRunCatching, not plain runCatching, to avoid swallowing CancellationException on scope cancel.
What are the three cooperative cancellation checkpoints in Kotlin coroutines? When would you choose each?
Senior⌄
ensureActive(): throws CancellationException immediately if cancelled — best for tight CPU loops where you want the coroutine to stop ASAP. yield(): checks cancellation AND gives up the current thread to let other coroutines run — best when your loop is both CPU-intensive and should share the dispatcher fairly. isActive: boolean check — best in non-suspending callbacks or JNI callbacks where you can't throw, only return early. Note: all standard suspension points (delay, withContext, await) are also implicit checkpoints.
Spot the bug: Why does this code silently fail to handle errors?
Senior — Spot the Bug⌄
supervisorScope {
    async { analyticsRepo.track("purchase") }  // no await
    async { experimentRepo.log("variant_b") }  // no await
}
Bug: Both async calls are never awaited. If either throws, the exception is stored in the Deferred but never retrieved — it is silently discarded. No crash, no log. Fix: Use launch { } instead of async { } when you don't need the return value. With launch, an unhandled exception goes to a CoroutineExceptionHandler or crashes — giving you visibility into the failure.
