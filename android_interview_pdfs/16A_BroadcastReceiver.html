16A — BroadcastReceiver

Inter-process and system event messaging: Static vs Dynamic receivers, modern API 26+ broadcast limits, receiver security permissions, ordered broadcasts, and goAsync().

ID: 16A ⭐ Tier 3 (System Components)
🚀
1. Overview & Receiver Types

A BroadcastReceiver is an Android system component that listens for system-wide broadcast announcements (e.g. battery low, screen on, boot completed) or custom inter-app / intra-app intents.

Static vs Dynamic Receivers
  • Static (Manifest-Declared): Declared in AndroidManifest.xml. The OS will instantiate the app process if needed to deliver the broadcast. Severely restricted since Android 8.0 (API 26) to prevent battery drain.
  • Dynamic (Context-Registered): Registered at runtime via context.registerReceiver() and tied to the lifecycle of the registering component (Activity, Service, or Application). Required on API 33+ to specify RECEIVER_EXPORTED or RECEIVER_NOT_EXPORTED.
⚙
2. How It Works Under the Hood

1. onReceive() Execution & Threading

BroadcastReceiver.onReceive(context, intent) runs synchronously on the Main Thread. The Android OS imposes a strict 10-second timeout before flagging the receiver with an ANR.

2. goAsync() for Background Work

If work cannot finish synchronously within milliseconds, call goAsync():

class HeavyBroadcastReceiver : BroadcastReceiver() {
    override fun onReceive(context: Context, intent: Intent) {
        val pendingResult: PendingResult = goAsync()
        CoroutineScope(Dispatchers.IO).launch {
            try {
                performShortWork()
            } finally {
                pendingResult.finish() // Must be called to release the WakeLock/receiver
            }
        }
    }
}

3. Ordered Broadcasts (sendOrderedBroadcast)

Broadcasts sent via sendOrderedBroadcast() are delivered to one receiver at a time in order of android:priority. A higher-priority receiver can:

  • Mutate broadcast extras via setResultData() or setResultExtras().
  • Completely terminate propagation via abortBroadcast().
🖈
3. Modern Restrictions & Security

Android 8.0 (API 26+) Implicit Broadcast Exceptions

Apps targeting API 26+ cannot register manifest receivers for implicit broadcasts, with few exceptions (e.g., ACTION_BOOT_COMPLETED, ACTION_LOCALE_CHANGED, ACTION_MY_PACKAGE_REPLACED). Broadcasts like CONNECTIVITY_ACTION must be registered dynamically or replaced with ConnectivityManager.NetworkCallback.

Android 13 (API 33+) Exported Receiver Flag

When calling registerReceiver(), you MUST pass either Context.RECEIVER_EXPORTED or Context.RECEIVER_NOT_EXPORTED. Omitting this flag throws a SecurityException.

Securing Broadcasts

  • Receiver Permission: Add android:permission="com.example.MY_PERMISSION" to restrict who can send intents to your receiver.
  • Sender Permission: Pass a permission string to sendBroadcast(intent, "com.example.MY_PERMISSION") to ensure only authorized apps receive it.
  • Intra-App State: For purely in-app events, replace broadcasts with Kotlin SharedFlow or Channel.
💻
4. Production Example (Dynamic Network / Airplane Mode Listener)
class ConnectivityMonitorActivity : ComponentActivity() {

    private val airplaneModeReceiver = object : BroadcastReceiver() {
        override fun onReceive(context: Context, intent: Intent) {
            val isAirplaneModeOn = intent.getBooleanExtra("state", false)
            updateAirplaneModeBanner(isAirplaneModeOn)
        }
    }

    override fun onStart() {
        super.onStart()
        val filter = IntentFilter(Intent.ACTION_AIRPLANE_MODE_CHANGED)
        if (Build.VERSION.SDK_INT >= Build.VERSION_CODES.TIRAMISU) {
            registerReceiver(airplaneModeReceiver, filter, Context.RECEIVER_EXPORTED)
        } else {
            registerReceiver(airplaneModeReceiver, filter)
        }
    }

    override fun onStop() {
        super.onStop()
        unregisterReceiver(airplaneModeReceiver)
    }
}

6. Pitfalls & Best Practices
Pitfall 1: Leaking Dynamic Receivers

Registering in onStart() without unregistering in onStop() (or onResume() / onPause()) causes an IntentReceiverLeaked error and keeps the surrounding Activity in memory.

Pitfall 2: Launching Async Coroutines without goAsync()

Once onReceive() returns, the Android OS considers the broadcast handled and reduces the process priority. Any background thread launched inside without goAsync() may be abruptly killed by the OS low memory killer.

Pitfall 3: Using LocalBroadcastManager (Deprecated)

LocalBroadcastManager was deprecated in Jetpack. For internal app messaging, use Kotlin Coroutines (SharedFlow, Channel, or EventBus pattern).

7. Interview Framework

30-Second Elevator Pitch

"BroadcastReceiver is an Android component for receiving system-wide or cross-app Intent broadcasts. Static receivers are declared in the manifest but restricted since API 26, while dynamic receivers are registered at runtime with mandatory RECEIVER_EXPORTED/NOT_EXPORTED flags in API 33+. onReceive runs on the main thread with a 10s timeout, extendable via goAsync()."

2-Minute Deep Dive

"BroadcastReceivers enable loosely coupled publish-subscribe messaging in Android. Under API 26 background execution limits, implicit broadcasts cannot be registered statically in the manifest, except for exempted actions like ACTION_BOOT_COMPLETED. For dynamic registration, API 33 requires explicitly specifying RECEIVER_EXPORTED or RECEIVER_NOT_EXPORTED for security.

onReceive() executes on the Main thread. If async work is needed, goAsync() returns a PendingResult, keeping the process alive until pendingResult.finish() is called. For ordered broadcasts, receivers process intents sequentially based on priority, allowing modifications via setResultData() or cancellation via abortBroadcast(). For intra-app communication, we favor Kotlin SharedFlow over deprecated LocalBroadcastManager."

9. Interview Questions (Self-Check)

Basic Questions

B1 — What is the execution time limit for BroadcastReceiver.onReceive()?
Easy▼
The execution time limit is 10 seconds on the main thread. If onReceive() blocks for more than 10 seconds, the Android OS flags the receiver with an Application Not Responding (ANR) dialog.
B2 — What is the difference between static and dynamic receivers?
Easy▼
Static receivers are declared in AndroidManifest.xml and can wake up a cold process when the broadcast fires. Dynamic receivers are registered at runtime using context.registerReceiver() and are only active during the lifecycle of the registering component.
B3 — What flag is required when dynamically registering a receiver on Android 13 (API 33)+?
Easy▼
You must pass either Context.RECEIVER_EXPORTED (if other apps can send broadcasts to it) or Context.RECEIVER_NOT_EXPORTED (if restricted to your app and the system). Omitting this parameter throws a runtime SecurityException.

Intermediate Questions

I1 — How does goAsync() work and why is it needed?
Medium▼
goAsync() returns a PendingResult object and informs the OS that the receiver intends to complete its work asynchronously on a background thread. This prevents the OS from considering the broadcast completed immediately upon onReceive() return and lowering process priority. Once work finishes, the worker must call pendingResult.finish().
I2 — Why can't you register a static receiver for CONNECTIVITY_ACTION on Android 8.0+?
Medium▼
Android 8.0 (API 26) introduced Background Execution Limits to prevent battery drain. Because network changes occur frequently, waking up hundreds of apps via static broadcast receivers caused severe battery depletion. Apps must use dynamic registration or ConnectivityManager.registerNetworkCallback() instead.
I3 — How do Ordered Broadcasts work?
Medium▼
Sent via sendOrderedBroadcast(), intents are delivered sequentially to receivers based on priority (defined in android:priority). Each receiver can read/modify results via getResultExtras() and setResultData(), or stop further delivery entirely by invoking abortBroadcast().
I4 — How do you restrict a broadcast so that only specific apps can receive it?
Medium▼
1. Define a custom permission in the sender app manifest (e.g. signature protection level).
2. Call sendBroadcast(intent, "com.example.CUSTOM_PERMISSION").
3. Receiver apps must declare <uses-permission android:name="com.example.CUSTOM_PERMISSION" /> signed with the same developer certificate.

Senior & Scenario Questions

S1 — How do you handle ACTION_BOOT_COMPLETED to schedule alarms in an Android 14 app?
HardScenario▼
1. Declare RECEIVE_BOOT_COMPLETED permission in manifest.
2. Register static receiver for android.intent.action.BOOT_COMPLETED.
3. In onReceive(), call goAsync() or enqueue a WorkManager OneTimeWorkRequest to read scheduled alarms from Room DB and register them with AlarmManager. (WorkManager is preferred to avoid ANRs during heavy post-boot device load).
S2 — Why was LocalBroadcastManager deprecated and what is the modern Kotlin replacement?
HardScenario▼
LocalBroadcastManager was deprecated because it relied on global Intent serialization and Context references for what is fundamentally an in-process pub-sub pattern. The modern replacement is Kotlin Coroutines using MutableSharedFlow (or Channel for single-subscriber events), which provides compile-time type safety, zero IPC serialization overhead, and seamless lifecycle awareness.
S3 — An app receives an SMS broadcast via an ordered receiver to parse 2FA OTP. How do you prevent other apps from reading it?
HardScenario▼
Historically, apps used high-priority ordered receivers and called abortBroadcast(), but modern Android restricts SMS broadcast manipulation. The modern, secure Google-recommended solution is the SMS Retriever API (or SMS User Consent API), which delivers the 2FA SMS exclusively to your app without requiring the sensitive RECEIVE_SMS permission.
