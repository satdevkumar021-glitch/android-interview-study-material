15A — Services

Started Services, Bound Services, Foreground Services (API 34+ types), IntentService deprecation, Background Execution Limits (API 26+), and LifecycleService.

ID: 15A ⭐ Tier 2 (Core Architecture)
🚀
1. Overview & Service Anatomy

An Android Service is an application component that can perform long-running operations in the background and does NOT provide a user interface. Crucially, a Service runs on the application's Main (UI) thread by default unless explicitly dispatched to background threads or coroutines.

The Three Primary Types of Services
  • Foreground Service: Performs operations noticeable to the user (e.g., media playback, audio recording, GPS). Requires an ongoing Status Bar Notification and explicit foregroundServiceType on API 34+.
  • Background / Started Service: Triggered via startService() for background work. Severely restricted since Android 8.0 (API 26+) — modern apps must use WorkManager instead.
  • Bound Service: Offers a client-server interface (via IBinder / AIDL / Messenger) that allows components to bind, send requests, and receive responses. Active only while clients remain bound.
⚙
2. How It Works Under the Hood

1. Started Service Lifecycle & onStartCommand Return Flags

When started via startService(Intent), the lifecycle is: onCreate() → onStartCommand() → (runs until stopSelf() or stopService()) → onDestroy().

The integer returned from onStartCommand() instructs the OS how to handle process kills under memory pressure:

  • START_STICKY: OS recreates the service after killing it and calls onStartCommand(null, 0, startId). Ideal for explicit start/stop services (e.g. music players).
  • START_NOT_STICKY: OS does NOT recreate the service unless pending start intents exist. Ideal for one-off operations.
  • START_REDELIVER_INTENT: OS recreates the service and redelivers the exact original Intent. Ideal for file downloads that must resume with original arguments.

2. Bound Service Lifecycle (ServiceConnection & IBinder)

Client components bind using bindService(intent, connection, BIND_AUTO_CREATE):

class LocalAudioService : Service() {
    private val binder = LocalBinder()

    inner class LocalBinder : Binder() {
        fun getService(): LocalAudioService = this@LocalAudioService
    }

    override fun onBind(intent: Intent?): IBinder = binder
}

When the last client unbinds via unbindService(), onUnbind() is called followed by onDestroy() unless the service was also started via startService().

3. LifecycleService (Jetpack)

LifecycleService extends Service and implements LifecycleOwner, allowing you to use lifecycleScope and collect Flows or observe LiveData safely without manual lifecycle cleanup.

3. When to Use & Modern OS Restrictions

Android 8.0 (API 26+) Background Limits

Apps in the background cannot create background services. Calling startService() while in the background throws an IllegalStateException. Apps must call startForegroundService() and call startForeground() within 5 seconds, or use WorkManager.

Android 14 (API 34+) Foreground Service Types

Google mandates that every foreground service must declare one or more specific types in AndroidManifest.xml and possess corresponding runtime permissions:

  • camera — Accessing camera while backgrounded.
  • connectedDevice — Interacting with external Bluetooth/USB devices.
  • dataSync — Data transfer (heavily restricted; Google recommends WorkManager).
  • health — Fitness/health tracking (wearables).
  • location — GPS navigation / ride sharing.
  • mediaPlayback — Audio/Video playback.
  • mediaProjection — Screen recording/casting.
  • phoneCall — Ongoing VoIP/telephony.
  • specialUse — Custom cases needing Google Play Store justification.

4. Production Example (Media Playback Service)
class AudioStreamingService : LifecycleService() {

    private val binder = AudioBinder()
    private var isPlaying = false

    inner class AudioBinder : Binder() {
        fun getService(): AudioStreamingService = this@AudioStreamingService
    }

    override fun onCreate() {
        super.onCreate()
        createNotificationChannel()
    }

    override fun onStartCommand(intent: Intent?, flags: Int, startId: Int): Int {
        super.onStartCommand(intent, flags, startId)
        val notification = buildNotification()

        if (Build.VERSION.SDK_INT >= Build.VERSION_CODES.Q) {
            startForeground(
                1001,
                notification,
                ServiceInfo.FOREGROUND_SERVICE_TYPE_MEDIA_PLAYBACK
            )
        } else {
            startForeground(1001, notification)
        }

        lifecycleScope.launch(Dispatchers.IO) {
            startStreamingEngine()
        }

        return START_STICKY
    }

    override fun onBind(intent: Intent): IBinder {
        super.onBind(intent)
        return binder
    }

    override fun onDestroy() {
        super.onDestroy()
        stopStreamingEngine()
    }
}

6. Pitfalls & Best Practices
Pitfall 1: Blocking the Main Thread in onStartCommand

Services run on the Main Thread. Doing file I/O or network requests directly inside onStartCommand() will trigger an ANR (Application Not Responding) within 5 seconds. Always launch work in a coroutine or background thread.

Pitfall 2: Missing startForeground() within 5 Seconds

Calling startForegroundService() creates a 5-second OS timer. If the service does not call startForeground(id, notification) within that window, the OS throws an ANR / RemoteServiceException: Context.startForegroundService() did not then call Service.startForeground() and crashes the app.

Pitfall 3: Leaking ServiceConnection via Unbind Omission

Every bindService() in an Activity or Fragment MUST have a matching unbindService() in onStop() or onDestroy(). Failure to unbind causes memory leaks and keeps the Service alive indefinitely in memory.

7. Interview Framework

30-Second Elevator Pitch

"An Android Service is a non-UI component for running tasks. It runs on the main thread by default. Services come in three forms: Started (runs until stopped), Bound (client-server IPC via IBinder), and Foreground (user-aware task with ongoing notification). In modern Android, background services are replaced by WorkManager, while Foreground Services strictly require foregroundServiceType declarations on Android 14."

2-Minute Deep Dive

"Historically, Started Services were used for background tasks, but API 26 Background Execution Limits made launching background services from the background illegal. Today, Foreground Services are reserved for user-noticeable work like media playback and GPS navigation. On Android 14 (API 34), apps must declare explicit foregroundServiceType attributes in the manifest and specify them in startForeground().

For lifecycle management, onStartCommand returns START_STICKY, START_NOT_STICKY, or START_REDELIVER_INTENT to control restart behavior after low-memory kills. For Bound Services, components connect via ServiceConnection and communicate using an IBinder. Jetpack's LifecycleService enables coroutine lifecycleScope integration."

Must-Mention Checklist

1
Main Thread Default: Services run on UI thread unless dispatched explicitly.
2
Foreground Service 5s Rule: Must call startForeground() within 5s of startForegroundService().
3
onStartCommand Flags: START_STICKY vs START_NOT_STICKY vs START_REDELIVER_INTENT.
4
Android 14 Requirements: Manifest foregroundServiceType and runtime permissions.

9. Interview Questions (Self-Check)

Basic Questions

B1 — On which thread does an Android Service run by default?
Easy▼
An Android Service runs on the Main (UI) Thread of the hosting process by default. Performing heavy calculations, database queries, or network requests directly inside a Service will freeze the UI and cause an ANR (Application Not Responding) error. Background work must be offloaded using coroutines or background threads.
B2 — What is the purpose of START_STICKY in onStartCommand()?
Easy▼
START_STICKY tells the Android OS that if the service process is killed due to low memory, the OS should recreate the service when resources become available and call onStartCommand() with a null Intent. It is ideal for continuous background operations like music streaming services.
B3 — Why was IntentService deprecated?
Easy▼
IntentService was deprecated in API 30 because it does not conform to Android 8.0+ (API 26) Background Execution Limits. It cannot be launched from the background without throwing exceptions. Google officially recommends replacing IntentService with WorkManager (via CoroutineWorker) or Jetpack JobIntentService.

Intermediate Questions

I1 — What happens if startForeground() is not called within 5 seconds of startForegroundService()?
Medium▼
If an app calls startForegroundService() and does not invoke startForeground(notificationId, notification) inside the service within 5 seconds, the system throws a RemoteServiceException: Context.startForegroundService() did not then call Service.startForeground(), causing an immediate fatal app crash.
I2 — What is the lifecycle difference between a Started Service and a Bound Service?
Medium▼
A Started Service is started via startService(), runs indefinitely until it calls stopSelf() or another component calls stopService(). A Bound Service is started when a client binds via bindService() and is automatically destroyed by the OS when all clients have called unbindService() (unless it was also started with startService()).
I3 — Explain the difference between START_NOT_STICKY and START_REDELIVER_INTENT.
Medium▼
START_NOT_STICKY tells the OS not to recreate the service if killed under memory pressure, unless new start intents are queued. START_REDELIVER_INTENT tells the OS to recreate the service AND redeliver the exact original Intent (with all extras) that was being processed at the time of the kill.
I4 — What is a LifecycleService and why is it preferred in modern Android?
Medium▼
LifecycleService is an androidx.lifecycle component extending Service that implements LifecycleOwner. It gives the service access to lifecycleScope, allowing coroutines to be launched and automatically cancelled when the service's onDestroy() fires, avoiding coroutine leaks.

Senior & Scenario Questions

S1 — How do you build a multi-process Bound Service using AIDL?
HardScenario▼
1. Define an .aidl file specifying interface methods.
2. Android SDK generates a Java interface with an internal Stub abstract class extending Binder.
3. In the Service, implement the Stub and return it in onBind().
4. In the Client app, implement ServiceConnection; in onServiceConnected(), call IMyAidlInterface.Stub.asInterface(service).
5. Handle RemoteException on all IPC method calls.
S2 — What changes are required to adapt a Foreground Location Service for Android 14 (API 34)?
HardScenario▼
1. Declare <uses-permission android:name="android.permission.FOREGROUND_SERVICE_LOCATION" /> and ACCESS_FINE_LOCATION in the manifest.
2. In manifest <service> tag, add android:foregroundServiceType="location".
3. In code, pass ServiceInfo.FOREGROUND_SERVICE_TYPE_LOCATION to startForeground().
4. Request runtime permissions before starting the service; otherwise a SecurityException will be thrown.
S3 — How would you communicate state from a Foreground Service to a Compose UI?
HardScenario▼
Expose a singleton StateFlow repository or shared domain model injected into both the ForegroundService and the ViewModel via Hilt. The Service updates the MutableStateFlow in the repository, and the ViewModel exposes it as a read-only StateFlow collected in Jetpack Compose using collectAsStateWithLifecycle(). This decouples the Service from the UI and eliminates complex Binder connection boilerplate.
