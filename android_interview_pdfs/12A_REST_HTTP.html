1. Overview

REST Principles

REST (Representational State Transfer) is an architectural style for distributed hypermedia systems. Six constraints make an API RESTful:

  • Client-Server: UI and data storage are separated
  • Stateless: each request contains all information needed; no server-side session state
  • Cacheable: responses can be cached with appropriate headers
  • Uniform Interface: standard HTTP verbs, resource URIs, representation (JSON/XML)
  • Layered System: client can't tell if it's talking to the actual server or an intermediary
  • Code on Demand (optional): server can send executable code
HTTP Request Structure: POST /api/v1/payments HTTP/1.1 Host: api.bank.com Content-Type: application/json Authorization: Bearer eyJhbGci... Accept: application/json { "amount": 100.00, "currency": "GBP", "toAccountId": "ACC-456" } HTTP Response Structure: HTTP/1.1 201 Created Content-Type: application/json Location: /api/v1/payments/PAY-789 ETag: "abc123def" Cache-Control: no-store { "paymentId": "PAY-789", "status": "PENDING" }

Retry with Exponential Backoff

suspend fun <T> retryWithBackoff(
    maxAttempts: Int = 3,
    initialDelayMs: Long = 1000,
    maxDelayMs: Long = 8000,
    factor: Double = 2.0,
    block: suspend () -> T
): T {
    var currentDelay = initialDelayMs
    repeat(maxAttempts - 1) { attempt ->
        try { return block() }
        catch (e: IOException) {
            delay(currentDelay + Random.nextLong(0, 500))  // jitter
            currentDelay = minOf((currentDelay * factor).toLong(), maxDelayMs)
        }
    }
    return block()  // final attempt, let exception propagate
}

3. When to Use

Choosing the Right HTTP Verb

  • GET: any read operation — always safe to repeat
  • POST: creating a resource where the server assigns the ID, or non-idempotent actions (submit payment)
  • PUT: full replacement; the client supplies the final representation
  • PATCH: partial updates — prefer when you only want to change one field
  • DELETE: removal — safe to retry (idempotent)

When to Retry

  • Retry: 429 (rate limit — wait for Retry-After), 500, 503, network timeouts (connect/read), SocketTimeoutException, UnknownHostException
  • Do NOT retry: 400 (bad request — same request will fail again), 401 (need new token first), 403, 404, 409, 422
  • Conditionally retry: POST payments — only retry if the API has idempotency keys
Idempotency Keys for Payments
POST is not idempotent. For payment APIs, send an Idempotency-Key: {uuid} header. The server will return the same response for duplicate requests with the same key, preventing double charges on retry.

4. Production Example

Banking App — API Error Mapping + Retry

// Sealed API result type — maps HTTP status codes to domain errors
sealed class ApiResult<out T> {
    data class Success<T>(val data: T) : ApiResult<T>()
    sealed class Failure : ApiResult<Nothing>() {
        data class HttpError(val code: Int, val message: String) : Failure()
        data class NetworkError(val cause: IOException) : Failure()
        object Unauthorized : Failure()
        data class ValidationError(val errors: List<String>) : Failure()
    }
}

// Map HTTP response to ApiResult
fun <T> Response<T>.toApiResult(): ApiResult<T> = when {
    isSuccessful    -> ApiResult.Success(requireNotNull(body()))
    code() == 401  -> ApiResult.Failure.Unauthorized
    code() == 422  -> {
        val errors = errorBody()?.string().parseValidationErrors() ?: emptyList()
        ApiResult.Failure.ValidationError(errors)
    }
    else            -> ApiResult.Failure.HttpError(code(), message())
}

// Repository using ApiResult
class PaymentRepositoryImpl @Inject constructor(
    private val api: PaymentApi
) : PaymentRepository {
    override suspend fun processPayment(request: PaymentRequest): ApiResult<PaymentReceipt> =
        retryWithBackoff(maxAttempts = 3) {
            api.processPayment(request.toDto(),
                idempotencyKey = request.idempotencyKey)  // prevents double charge on retry
        }.toApiResult()
}

Pagination: Offset vs Cursor

For social feeds and real-time content, cursor-based pagination prevents the "page drift" problem: if a new item is inserted at the top while the user is on page 2, offset-based pagination would show the same item twice. Cursor-based pagination always continues from the last seen item regardless of insertions.

6. Pitfalls & Best Practices

Status Code Pitfalls

401 vs 403 Confusion
401 = authentication problem (not logged in or token expired). 403 = authorisation problem (logged in but no permission). Handle them differently: 401 triggers token refresh; 403 shows "permission denied" and does NOT trigger a retry or refresh — the token is valid, the user just doesn't have access.
Retrying non-idempotent requests
Never blindly retry POST requests for financial operations. A retry after a timeout on POST /payments could charge the user twice. Always use idempotency keys for payment POST requests, and only retry with the same key.

Caching Sensitive Data

Never Cache Sensitive Responses
Account balances, transaction details, PII — always return Cache-Control: no-store, private. OkHttp respects this header and will not write the response to disk cache.

Best Practices

  • Version your API: /api/v1/ — never make breaking changes without a version bump
  • Use meaningful 4xx codes — don't return 500 for a validation error
  • Always set appropriate Content-Type on requests and responses
  • Add jitter to retry delays (random 0–500ms added to calculated backoff) to prevent thundering herd
  • Log request/response in debug only; never log Authorization headers or request bodies containing PII

7. Interview Framework

30-Second Answer

"REST uses standard HTTP verbs — GET to retrieve, POST to create, PUT to replace, PATCH to partially update, DELETE to remove. The most important status codes: 200 success, 201 created, 400 bad request, 401 trigger token refresh, 403 no permission, 404 not found, 429 rate limited, 500/503 retry with backoff. Caching uses ETags — server sends ETag with response, client sends If-None-Match on next request, server returns 304 Not Modified if unchanged, saving bandwidth."

2-Minute Deep Dive

"For retry strategy: retry 500, 503, 429 (respect Retry-After), and network errors like SocketTimeoutException with exponential backoff plus jitter. Never retry POST payments without idempotency keys — you'd charge users twice. The distinction between 401 and 403 is critical: 401 means unauthenticated — trigger token refresh and retry. 403 means authenticated but unauthorised — show error, don't retry. For caching: OkHttp supports disk cache with ETag-based conditional GETs automatically. For sensitive data like account balances, the server must send Cache-Control: no-store. For pagination, cursor-based is superior to offset for real-time feeds — offset pagination has a page drift problem when items are inserted during pagination."

Must-Mention Points

1
Verb semantics: idempotent = GET/PUT/DELETE; non-idempotent = POST/PATCH (usually)
2
401 vs 403: 401 = unauthenticated (refresh token); 403 = unauthorised (show error, don't retry)
3
ETag caching: server sends ETag; client sends If-None-Match; 304 = use cache
4
Retry strategy: exponential backoff + jitter for 5xx/429/network errors; idempotency key for POST payments
5
Timeouts: connectTimeout (TCP), readTimeout (data), writeTimeout (body) — set all three
6
Cursor pagination: no page drift; preferred over offset for real-time feeds

  • Full OAuth 2.0 flow details (covered in 12C)

Follow-up Q&A

QuestionAnswer
"What's an idempotency key?"A UUID sent in a request header (e.g., Idempotency-Key). If the same request is sent twice with the same key, the server returns the same response without processing it again — preventing duplicate actions on retry.
"When would you use PATCH vs PUT?"PATCH for partial updates (change one field without sending the whole object). PUT for full replacement (client sends the complete representation). PUT is safer for conflict resolution — you always know the full state being set.
"What is a thundering herd?"When many clients all retry at the same time after a failure, overwhelming the server again. Jitter (random delay added to backoff) spreads retry attempts over time to prevent this.

Senior Insight

Senior Signal
In a banking or e-commerce app, the most dangerous HTTP mistake is blindly retrying POST requests. Network timeout doesn't mean the server didn't process the request — it might have. Always use idempotency keys for any non-idempotent operation that has real-world consequences (payments, orders, bookings). This is the difference between robust production code and code that occasionally charges users twice.

9. Interview Questions
Basic What is the difference between GET and POST? ⌄
GET is safe (no side effects), idempotent (same result every call), and cacheable. Parameters go in the URL query string. POST is unsafe (may cause side effects like creating a record), not idempotent, and not cached by default. Body carries the payload. GET for reading; POST for creating or triggering non-idempotent actions.
Basic What should an app do when it receives a 401 response? ⌄
401 means the request lacked valid authentication — typically an expired JWT. The app should: (1) Pause the current request. (2) Attempt to refresh the access token using the refresh token. (3) If refresh succeeds, retry the original request with the new token. (4) If refresh fails (e.g., refresh token expired), redirect the user to the login screen. This logic lives in an OkHttp Authenticator or AuthInterceptor to avoid duplicating it everywhere.
Basic What does Cache-Control: no-store mean and when should you use it? ⌄
Cache-Control: no-store means the response must not be stored in any cache — not memory cache, not disk cache, not intermediary proxy cache. The entire response is discarded after use. Use it for sensitive data: account balances, transaction history, authentication tokens, personal information. no-cache is different — it allows caching but requires re-validation with the server before each use.
Intermediate Explain ETag-based conditional GET and its benefit. ⌄
The server includes an ETag: "version_hash" header with its response. The client caches the response and the ETag. On the next request, the client adds If-None-Match: "version_hash". If the resource hasn't changed, the server returns 304 Not Modified with no body — saving bandwidth and processing. If the resource changed, the server returns 200 with the new body and a new ETag. The benefit: freshness check happens every time (no stale data), but bandwidth is only used when the data actually changed.
Intermediate Describe a correct retry strategy for a mobile banking app. ⌄
1. Only retry transient failures: 500, 503, 429, SocketTimeoutException, ConnectException, UnknownHostException.
2. Exponential backoff + jitter: 1s, 2s, 4s ± random(0-500ms) to spread load.
3. Respect Retry-After: for 429/503, wait the specified duration.
4. Max 3 attempts: beyond that, fail and show the user an actionable error.
5. Idempotency keys for payments: generate a UUID before the first attempt; use the same key for all retries of the same payment.
6. Do NOT retry: 400, 401, 403, 404, 422 — retrying won't help.
Intermediate What is the difference between connectTimeout and readTimeout in OkHttp? ⌄
connectTimeout: how long OkHttp waits to establish a TCP connection to the server. A slow DNS lookup or an unresponsive server will trigger this. Typically 10–15 seconds.

readTimeout: how long OkHttp waits between receiving consecutive bytes from the server during data transfer. A server that starts responding but then stalls mid-response will trigger this. Typically 30 seconds for APIs; may need to be longer for large file downloads.

writeTimeout: how long OkHttp waits to finish sending the request body. Important for file uploads on slow connections.
Intermediate Compare cursor-based and offset-based pagination. ⌄
Offset: ?offset=20&limit=10 — skip the first 20 records. Simple to implement. Problem: if a new item is inserted at the top while the user is on page 2, page 3 will show one item they already saw on page 2 (page drift). Also slow for large offsets (database must scan rows to skip them).

Cursor: ?after=eyJpZCI6MTAwfQ&limit=10 — start from after the item with that cursor. The cursor encodes the position (usually last item's ID + sort field). No page drift — you always get items after your last position, regardless of insertions. DB query is efficient (WHERE id > cursor instead of OFFSET). No random access. Best for infinite scroll/feed content.
Senior A payment POST times out. How do you handle it correctly to avoid double charges? ⌄
Network timeout doesn't mean the payment failed — the server may have processed it and the response was lost. Strategy:

1. Before the first POST, generate a UUID as an idempotency key and store it (DataStore/SharedPreferences) alongside the payment state.
2. Add the key to the request: Idempotency-Key: {uuid}.
3. On timeout, retry the same POST with the same idempotency key. The payment API returns the original response (e.g., 200 with the receipt) if already processed.
4. On success: clear the idempotency key.
5. If all retries fail: show a "payment pending" state. Check payment status via a separate GET endpoint using the idempotency key as a reference.
6. On app restart: check for any pending idempotency keys and resolve their status via GET before allowing new payments.
Senior How do you design API error handling that works across the full Android stack? ⌄
Layered error handling:

Data layer (Repository): wraps raw Response<T> in a sealed ApiResult type. Maps status codes: 401 → Unauthorized, 422 → ValidationError with parsed field errors, 5xx → ServerError, IOException → NetworkError.

Domain layer (UseCase): maps ApiResult to domain-specific results: InsufficientFunds, AccountFrozen, etc. The ViewModel never sees HTTP concepts.

Presentation layer (ViewModel): maps domain errors to UI states: UiState.Error("Insufficient balance"). Provides user-visible strings, not error codes.

Benefit: the API's error model can change without touching the ViewModel; the ViewModel's error display can change without touching the repository.
Senior How would you implement HTTP caching for a product catalogue in a Retrofit/OkHttp app? ⌄
1. Add an OkHttp Cache object: Cache(File(cacheDir, "http"), 10 * 1024 * 1024).
2. Set it on the OkHttpClient: .cache(cache).
3. Server must send Cache-Control: max-age=300 (5 min) and ETag: "v5abc".
4. For offline mode, add a network interceptor: if no network, override the request's Cache-Control to only-if-cached, max-stale=86400 — OkHttp will serve stale cache rather than failing.
5. Combine with a Room single source of truth for offline-first: on network response, update Room; UI observes Room's Flow. Even with cache miss, the user sees stale data from Room rather than an error.
