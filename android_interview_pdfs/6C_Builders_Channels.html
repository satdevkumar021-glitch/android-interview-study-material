6C — Builders & Channels

flow{}, flowOn, callbackFlow, channelFlow. Channel types: Rendezvous, Buffered, Conflated, Unlimited. Backpressure strategies.

ID: 6C ⭐ Tier 1
🔍
1. Overview

Flow builders

  • flow { } — simplest builder; cold; sequential; cannot emit from a different coroutine
  • flowOf(vararg) — emit a fixed set of values
  • callbackFlow { } — bridge callback-based APIs (location, sensors, WebSocket) to Flow
  • channelFlow { } — like callbackFlow but allows multiple concurrent emissions from different coroutines
  • flowOn(dispatcher) — change the upstream context; does NOT affect the collector

Channels

A Channel is a communication primitive between coroutines — like a queue with suspend-aware send/receive. Unlike Flow, channels are hot and stateful. They're the foundation of channelFlow and callbackFlow internally.

Senior Mental Model
Use callbackFlow to bridge legacy callback APIs (Bluetooth, location, Firebase) into the reactive Flow world. Use flowOn to change the dispatcher for upstream work without changing where the collector runs. Channels are low-level — in most Android code you don't need raw Channels; prefer Flow.
⚙
2. Flow Builders

flow { } — basic cold builder

// Simple cold flow — sequential emissions
fun countdownFlow(): Flow<Int> = flow {
    for (i in 10 downTo 0) {
        emit(i)
        delay(1000)
    }
}
// Constraint: cannot call emit() from a different coroutine inside flow{}

flowOn — change upstream context

// flowOn affects ONLY the upstream operators — NOT the collector
repo.getItems()                    // runs on IO (set by flowOn)
    .map { it.toUiModel() }          // also runs on IO
    .flowOn(Dispatchers.IO)          // sets context for above ops
    .collect { renderItem(it) }       // runs on collector's context (Main)

// Multiple flowOn: each applies to everything above it
flow.map { /* on Default */ }
    .flowOn(Dispatchers.Default)
    .map { /* on IO */ }
    .flowOn(Dispatchers.IO)
    .collect { /* on Main */ }

callbackFlow — bridge callbacks to Flow

// Bridge LocationManager callback to Flow
fun locationFlow(context: Context): Flow<Location> = callbackFlow {
    val manager = context.getSystemService(LocationManager::class.java)

    val listener = LocationListener { location ->
        trySend(location)  // non-suspend send (from callback thread)
    }

    manager.requestLocationUpdates(
        LocationManager.GPS_PROVIDER, 1000L, 0f, listener
    )

    // awaitClose: runs when flow is cancelled / collector stops
    awaitClose {
        manager.removeUpdates(listener)  // cleanup!
    }
}

// Usage
locationFlow(context)
    .collect { location -> updateMap(location) }
// When collector cancels, awaitClose removes the listener

channelFlow — concurrent emissions

// channelFlow: allows emission from different coroutines
fun parallelFetch(ids: List<String>): Flow<Item> = channelFlow {
    ids.forEach { id ->
        launch {                    // multiple coroutines emit concurrently
            val item = api.fetchItem(id)
            send(item)               // suspend-aware send
        }
    }
}
// Regular flow{} would throw: "Flow invariant is violated"

4. Backpressure Strategies

Backpressure occurs when the producer emits faster than the consumer can process. Flow operators to handle it:

// buffer: add a coroutine boundary between producer and consumer
// Producer and consumer run concurrently
fastSensorFlow
    .buffer(64)              // up to 64 items buffered while consumer processes
    .collect { slowProcess(it) }

// conflate: keep only the latest value, drop intermediate
// Consumer always gets freshest data
locationFlow
    .conflate()              // if consumer is busy, old locations are dropped
    .collect { updateMap(it) }

// collectLatest: cancel current processing when new value arrives
priceFlow
    .collectLatest { price ->
        delay(1000)          // simulate slow rendering
        renderPrice(price)   // if new price arrives, this is cancelled
    }

5. Production Example

Automotive: GPS sensor to location service via callbackFlow

// Bridge Android FusedLocationProvider to Flow
fun FusedLocationProviderClient.locationFlow(): Flow<Location> = callbackFlow {
    val request = LocationRequest.create()
        .setInterval(1000)
        .setPriority(PRIORITY_HIGH_ACCURACY)

    val callback = object : LocationCallback() {
        override fun onLocationResult(result: LocationResult) {
            result.lastLocation?.let { location ->
                trySend(location)  // non-blocking send from callback
            }
        }
    }

    requestLocationUpdates(request, callback, Looper.getMainLooper())

    awaitClose { removeLocationUpdates(callback) }
}

// Processing pipeline with backpressure + context switch
class NavigationViewModel(
    private val client: FusedLocationProviderClient
) : ViewModel() {

    val route: StateFlow<RouteState> = client.locationFlow()
        .conflate()                          // only latest GPS position
        .map { location ->                   // heavy route calculation
            routeEngine.calculate(location)
        }
        .flowOn(Dispatchers.Default)         // route calc on CPU pool
        .map { route -> RouteState.Active(route) }
        .catch { emit(RouteState.Error(it)) }
        .stateIn(viewModelScope, SharingStarted.WhileSubscribed(5000), RouteState.Idle)
}

Banking: WebSocket price feed via callbackFlow

fun priceFlow(symbol: String): Flow<Price> = callbackFlow {
    val ws = webSocketClient.connect(symbol)

    ws.onMessage { msg ->
        val price = parsePrice(msg)
        trySend(price)  // may drop if buffer full
    }
    ws.onError { e -> close(e) }

    awaitClose { ws.disconnect() }
}
    .buffer(Channel.CONFLATED)   // only latest price if consumer is slow

6. Pitfalls & Best Practices
Pitfall 1 — Missing awaitClose in callbackFlow
If you don't call awaitClose { } in a callbackFlow, the flow completes immediately after the block ends — before any callbacks fire. You also miss the chance to unregister the callback, causing memory leaks.
Pitfall 2 — emit() from different coroutine inside flow{}
flow { } is single-coroutine only. Calling emit() from a coroutine launched inside flow { } throws "Flow invariant violated". Use channelFlow { } instead for concurrent emissions.
Pitfall 3 — flowOn affects upstream, not downstream
A common mistake: putting flowOn(IO) after collect { }. flowOn only applies to operators above it. The collector always runs on the coroutine that called collect (e.g., viewModelScope's Main dispatcher).
Best Practice — trySend vs send in callbackFlow
Use trySend(value) in callbacks — it's non-suspending and returns a ChannelResult. send(value) suspends until there's space in the buffer, which is not valid in a regular (non-suspending) callback. If you need to know if the send was dropped, check the result.

7. Interview Framework

30-second answer

"callbackFlow is the standard way to bridge legacy callback APIs like location, sensors, or WebSocket to Kotlin Flow. It provides trySend() for non-suspending emission from callbacks and awaitClose() for cleanup. flowOn changes the upstream context without affecting the collector. Channels are the underlying mechanism — Rendezvous (no buffer), Buffered, Conflated (latest only), Unlimited."

2-minute answer

"callbackFlow solves a fundamental problem: callback-based APIs (LocationManager, Bluetooth, Firebase Realtime) don't fit the sequential coroutine model. callbackFlow creates a Channel internally — trySend() puts values into it from callback threads, and collect() reads from it. awaitClose() is critical: it runs when the flow collector cancels, unregistering the callback to prevent leaks.

flowOn is more subtle than it appears: it only affects operators upstream (above it). Multiple flowOn operators create separate coroutine boundaries between sections. The collector always runs in its calling context — usually Main in a ViewModel.

For backpressure: buffer(n) allows the producer to run ahead by n items. conflate() drops intermediate values, keeping only the latest. For sensor data, conflate is usually right — processing stale GPS readings is wasteful. For financial transactions, buffer is right — you don't want to lose any transaction events."

callbackFlow + awaitClose — always cleanup in awaitClose, never skip it

3

4

Follow-up Q&A

Q: "What's the difference between callbackFlow and channelFlow?"

A: callbackFlow and channelFlow are nearly identical in implementation. Both create a Channel and allow concurrent emissions. The key difference: callbackFlow checks that awaitClose() is called and throws a runtime error if it's missing. channelFlow does not enforce this. In practice, always use callbackFlow when bridging callbacks (the enforcement helps catch bugs), and channelFlow for internal concurrent producers.

Q: "What does trySend return when the buffer is full?"

A: It returns a ChannelResult — a failure result if the channel is full or closed. You can check trySend(value).isFailure. For a conflated channel, it never fails — it overwrites the old value. The caller in a callback should decide: log the drop, increment a dropped-events counter, or simply ignore it depending on the use case.

Senior insight

Senior Insight
In an automotive app with 10+ sensor streams (GPS, accelerometer, LIDAR), use callbackFlow for each sensor and merge them with merge(). Apply conflate() on each sensor stream to drop stale readings, then flowOn(Dispatchers.Default) for sensor fusion processing. This gives you one clean reactive stream that always processes the freshest sensor data available.

9. Interview Questions
What is callbackFlow and when would you use it?
Basic⌄
callbackFlow is a Flow builder that creates a Channel internally, allowing you to bridge callback-based APIs (GPS, Bluetooth, WebSocket, Firebase) to the Kotlin Flow world. Callbacks call trySend(value) (non-suspending) to put values in the channel, and awaitClose { } handles cleanup when the flow is cancelled.
What is the purpose of awaitClose in callbackFlow?
Basic⌄
awaitClose { } does two things: (1) it keeps the callbackFlow alive — without it, the flow would complete immediately after the block, before any callbacks fire; (2) its lambda runs when the flow collector cancels, providing the cleanup hook to unregister the callback. Missing awaitClose causes both premature completion and listener leaks.
What does flowOn do and where does it apply?
Basic⌄
flowOn(dispatcher) changes the dispatcher for all operators upstream (above it in the chain). It does NOT affect the collector — the collector always runs on the coroutine that called collect(). It creates a coroutine boundary between the upstream and downstream sections, allowing them to run on different threads concurrently.
What are the 4 channel capacity types and when would you use each?
Intermediate⌄
Rendezvous (0): strict handshake — sender and receiver must be ready simultaneously. Good for controlled producer-consumer pairs. Buffered: N items queued; sender suspends when full. Good for bursty producers that outpace consumers temporarily. Conflated: 1-element buffer, overwrites; sender never suspends. Good for state updates where only the latest matters (sensor data, UI state). Unlimited: unbounded queue; sender never suspends. Use carefully — can OOM with fast producers.
Why can't you call emit() from a different coroutine inside flow { }?
Intermediate⌄
flow { } is a sequential cold flow builder — it enforces that emissions come from a single coroutine, preserving sequential guarantees. Calling emit() from a launched coroutine inside flow{} would violate this contract, potentially causing concurrent emission which is not safe for all collectors. The runtime throws "Flow invariant violated" to catch this. Use channelFlow { } for concurrent emissions.
What is the difference between buffer() and conflate() for backpressure?
Intermediate⌄
buffer(n) allows the producer to run ahead of the consumer by up to n items — both run concurrently with a queue between them. No items are lost; sender suspends when buffer is full. conflate() is a special case: the producer and consumer run concurrently, but intermediate values are dropped — the consumer only ever processes the most recent value. Use buffer() when you need all items (events, orders); use conflate() when only the latest matters (GPS updates, price ticks).
How do you bridge a Bluetooth LE scan callback to a Flow in Android?
Intermediate⌄
fun bleScanFlow(scanner: BluetoothLeScanner): Flow<ScanResult> = callbackFlow { val callback = object : ScanCallback() { override fun onScanResult(callbackType: Int, result: ScanResult) { trySend(result) } override fun onScanFailed(errorCode: Int) { close(BleScanException(errorCode)) } }; scanner.startScan(callback); awaitClose { scanner.stopScan(callback) } }. Key points: use trySend() (not send()), call close() on error, and always stopScan in awaitClose.
A GPS flow emitting 10 updates/second is connected to a route calculation that takes 500ms. What happens and how do you handle it?
Senior⌄
Without backpressure handling: the callbackFlow's internal channel buffers updates (default 64); once full, trySend() starts dropping updates silently. The route calculation falls further and further behind, processing stale GPS data. Fix: callbackFlow { ... }.conflate() — the producer runs at full speed but only the latest GPS update is processed by the route calculator. Since route calculation needs the current position, dropping intermediate positions is correct. Add .flowOn(Dispatchers.Default) to move the heavy calculation off Main.
Explain how flowOn creates a coroutine boundary and what happens to backpressure at that boundary.
Senior⌄
flowOn creates a Channel between the upstream (new coroutine on the specified dispatcher) and the downstream (existing collector coroutine). This channel acts as a buffer between the two. By default, the channel is buffered (64 items). If the upstream produces faster than the downstream consumes, the buffer fills and the upstream suspends. This is similar to calling .buffer(64).flowOn(dispatcher) explicitly. You can control the buffer size using buffer(n) placed before flowOn.
When would you use a raw Channel instead of Flow?
Senior⌄
Raw Channel is appropriate when: (1) you need bidirectional communication between exactly two coroutines (producer-consumer pair, not broadcast); (2) you need to close the channel explicitly from the producer side with a result or error; (3) you're implementing a work queue where multiple producers send to one consumer (fan-in pattern). In most Android code, Flow provides a better abstraction with operators, lifecycle support, and backpressure. Use Channels for internal coroutine-to-coroutine communication; expose Flow for the outside world.
