21A — Android Performance

ANR detection and prevention, StrictMode, Cold vs Warm vs Hot startup optimization, Baseline Profiles, 16ms frame jank budgeting, Macrobenchmark, and Compose stability.

ID: 21A ⭐ Tier 2 (Core System Optimization)
🚀
1. Overview & The Vitals Metrics

Android app quality is measured through Google Play Android Vitals: ANR rate, crash rate, slow rendering frames (>16ms), frozen frames (>700ms), and excessive background wakeups/WiFi scans.

Core Performance Pillars
  • ANR (Application Not Responding): Triggered when main thread blocks >5s for user input, >10s in BroadcastReceiver, or >20s in Service.
  • App Startup Time: Cold Start (process creation + Application.onCreate + Activity render), Warm Start, Hot Start.
  • UI Rendering / Jank: 60Hz displays give a 16.6ms frame budget (8.3ms on 120Hz). Exceeding this causes Choreographer to drop frames.
  • Tooling: StrictMode, Android Studio Profiler, Perfetto / Systrace, Macrobenchmark, and Baseline Profiles.

2. How It Works Under the Hood

1. App Startup Spectrum (Cold vs Warm vs Hot)

Startup TypeOS Process StatusWhat Executes?Target Budget
Cold Start Process must be created (forked from Zygote) Load classes → Application.onCreate() → ContentProviders → Activity.onCreate() → Layout/Measure/Draw < 500 ms (Critical < 2s)
Warm Start Process is already alive in memory Recreates Activity from saved state; skips Application init < 200 ms
Hot Start Process and Activity are in memory (background stack) Brings Activity to foreground (onStart() → onResume()); zero inflation < 100 ms

2. Baseline Profiles & ART Compilation

Android Ahead-of-Time (AOT) compiler pre-compiles DEX bytecode into native machine code. Baseline Profiles specify critical user journeys (cold start, list scrolling) so the OS pre-compiles them during app installation via Google Play, boosting cold startup by 30-40% and eliminating first-run JIT interpretation jank.

3. ANR Prevention & StrictMode

1. StrictMode Setup (Debug Only)

if (BuildConfig.DEBUG) {
    StrictMode.setThreadPolicy(
        StrictMode.ThreadPolicy.Builder()
            .detectDiskReads()
            .detectDiskWrites()
            .detectNetwork()
            .penaltyLog()
            .penaltyFlashScreen()
            .build()
    )
    StrictMode.setVmPolicy(
        StrictMode.VmPolicy.Builder()
            .detectLeakedSqlLiteObjects()
            .detectLeakedClosableObjects()
            .penaltyLog()
            .build()
    )
}

2. Compose Recomposition Stability

Unstable parameters force composables to recompose even when inputs have not changed:

  • Classes with var properties are unstable. Make all properties val.
  • Standard List<T> is considered unstable by Compose compiler because it might be a mutable ArrayList. Use Kotlinx ImmutableList<T> or annotate class with @Immutable / @Stable.
  • Use lambda references (onItemClick = viewModel::onSelect) or remember lambdas to prevent recreating function instances.

6. Pitfalls & Best Practices
Pitfall 1: Heavy Synchronous Initialization in Application.onCreate()

Initializing analytics SDKs, crash reporters, push notification engines, and local databases synchronously inside Application.onCreate() directly delays the first frame and degrades cold start metrics. Use Jetpack App Startup and offload non-critical SDKs to coroutines.

Pitfall 2: Loading Unscaled Bitmaps into ImageViews

Loading full 4K (4096x2160 ARGB_8888) camera photos directly into memory consumes ~35 MB RAM per image, quickly causing OutOfMemoryError (OOM). Always decode downsampled bitmaps matching the View dimensions using inSampleSize or Coil/Glide.

Pitfall 3: Reading SharedPreferences Synchronously during Startup

Calling sharedPreferences.getString() causes a synchronous disk read on the Main Thread. If SharedPreferences XML is large, it blocks the main thread and can trigger ANRs.

9. Interview Questions (Self-Check)

Basic Questions

B1 — What is an ANR and what are the primary thresholds that trigger it?
Easy▼
An ANR (Application Not Responding) occurs when the application's Main (UI) thread is blocked and cannot process system messages. Thresholds:
• 5 seconds: No response to user input (touch, key press).
• 10 seconds: BroadcastReceiver.onReceive() fails to return.
• 20 seconds: Service.onStartCommand() blocks.
B2 — What is the frame rendering time budget on a 60Hz vs 120Hz Android screen?
Easy▼
On a standard 60Hz display, the system must render each frame in under 16.6 milliseconds (1000ms / 60 frames). On high refresh rate 120Hz displays, the budget shrinks to 8.3 milliseconds per frame. Exceeding this budget causes Choreographer to skip a VSYNC pulse, resulting in visible UI jank/stutter.
B3 — What is the difference between a Cold Start and a Hot Start?
Easy▼
A Cold Start creates a new Linux OS process from scratch, initializes the Application class, and inflates the first Activity (slowest). A Hot Start simply brings an already running Activity from the background back to the foreground with zero view inflation or process creation (fastest).

Intermediate Questions

I1 — What is StrictMode and how does it help catch performance bugs?
Medium▼
StrictMode is a developer tool that detects accidental disk I/O, network requests, and SQLite operations executed on the application's Main Thread. It can log warnings, flash the screen, or crash the app in debug builds to catch ANR bottlenecks before releasing to production.
I2 — What are Baseline Profiles and how do they improve app startup time?
Medium▼
Baseline Profiles are rules bundled with an APK that specify classes and methods used during critical user paths (cold start, first screen rendering). Google Play and the Android Runtime (ART) use them to Ahead-of-Time (AOT) pre-compile DEX bytecode into native machine code upon app installation, eliminating JIT compilation stalls and speeding up cold start by ~30-40%.
I3 — Why is List<T> considered unstable by the Jetpack Compose compiler?
Medium▼
In Kotlin, List<T> is an interface that can be backed by a mutable implementation like ArrayList. Because the Compose compiler cannot guarantee that the underlying collection items haven't been mutated, it flags standard List<T> as unstable, forcing the Composable to recompose on every recomposition cycle. Fix: Use kotlinx.collections.immutable.ImmutableList or @Immutable.
I4 — What is derivedStateOf in Jetpack Compose and when should you use it?
Medium▼
derivedStateOf { } creates a state object that calculates its value from other Compose states, emitting a new state ONLY when the calculated result actually changes. It is essential when observing fast-changing states (e.g. lazyListState.firstVisibleItemIndex > 0 for a "scroll to top" button) to prevent hundreds of unnecessary recompositions per second during scrolling.

Senior & Scenario Questions

S1 — An e-commerce app experiences dropped frames while scrolling a complex product grid in Compose. How do you diagnose and fix it?
HardScenario▼
1. Diagnose: Run Android Studio Layout Inspector to check Recomposition Count / Skipped Count per item. Use Perfetto / Systrace to check Choreographer VSYNC overruns.
2. Fix Stability: Wrap product list in ImmutableList<Product> to make items skippable.
3. Item Keys: Provide stable key = { it.productId } in items().
4. Image Loading: Ensure Coil uses hardware bitmap configs and downsamples images to exact grid dimensions.
5. Avoid Reallocations: Extract lambdas out of item composition scopes.
S2 — How would you reduce cold start time in an enterprise banking app with 15+ third-party SDKs?
HardScenario▼
1. Profile Startup: Use Android Studio CPU Profiler (Traceview) on Application.onCreate() to identify slowest SDK initializers.
2. App Startup Library: Consolidate initialization into Jetpack App Startup to eliminate ContentProvider startup overhead.
3. Lazy Init: Defer non-critical SDKs (analytics, feedback, in-app messaging) to background coroutines after the first Activity draws its first frame.
4. Baseline Profiles: Generate and bundle a Baseline Profile for the cold start journey.
5. R8 Optimization: Enable full R8 shrinking and dex desugaring.
S3 — How do you use Macrobenchmark to write automated CI performance regression tests?
HardScenario▼
Create a dedicated :macrobenchmark module using MacrobenchmarkRule. Write tests measuring StartupTimingMetric() (measuring timeToInitialDisplayMs) and FrameTimingMetric() during automated UI scrolls. Run the benchmark on physical test devices in CI against release builds with CompilationMode.Partial(BaselineProfileMode.Require), asserting that startup remains below agreed SLA thresholds (e.g. <600ms).
