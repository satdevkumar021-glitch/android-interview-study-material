Overview

Why Compose Testing Is Different from Espresso

Traditional Espresso tests navigate a View hierarchy — finding widgets by their resource ID (R.id.submit_button), casting to typed subclasses, and asserting on View properties. Jetpack Compose has no View hierarchy at all. There are no View objects, no XML layout IDs, no ViewGroup trees to traverse.

Instead Compose builds a semantics tree — a separate, lightweight tree that runs in parallel with the composition tree. Every composable that participates in accessibility or testing emits a semantics node. That node holds properties: text content, content description, role, enabled state, click action, and so on. Both the Android accessibility framework (TalkBack) and Compose's test framework consume this same semantics tree. Your test never touches a composable directly; it finds a semantics node and interacts with it.

Three Layers of Compose Testing

LayerWhat it testsSpeedTool
UnitPure logic — ViewModel state, UseCases, mappersVery fast (<1 ms)JUnit + MockK / Turbine
IntegrationComposable + ViewModel with fake repositoryMedium (emulator/device)createComposeRule()
End-to-EndFull NavHost flow, real ActivitySlow (full app launch)createAndroidComposeRule<MainActivity>()

The Testing Pyramid in Compose

The classic pyramid still applies, but the layers map differently than in View-based apps:

  • 70% Unit tests — ViewModel logic, UseCase rules, state machines, mappers. Zero UI. Fastest feedback loop.
  • 20% Integration tests — Composable renders correctly, responds to state changes, emits correct events. Uses createComposeRule() with fake dependencies.
  • 10% E2E tests — Full navigation flows with real Activity. Validates happy paths and critical error paths from the user's perspective.

Key Dependency

The entire Compose test API lives in one artifact: androidx.compose.ui:ui-test-junit4. It provides:

  • createComposeRule() and createAndroidComposeRule()
  • All finder functions (onNodeWithText, onNodeWithTag, etc.)
  • All interaction functions (performClick, performTextInput, etc.)
  • All assertion functions (assertIsDisplayed, assertTextEquals, etc.)
  • waitUntil{} for async assertions

Senior Mental Model

"In Compose tests you're testing the semantics tree, not the View tree. A Text composable emits a semantics node with a text property. Your test finds it via onNodeWithText(). This means your UI can be completely restructured — move composables around, extract components, rename internal functions — and your tests still pass as long as semantics are preserved. The test is coupled to behaviour, not implementation."

Test Setup & Dependencies

Gradle Dependencies

// build.gradle.kts (app module)
dependencies {
    // Core Compose test library — provides ComposeTestRule, finders, interactions
    androidTestImplementation("androidx.compose.ui:ui-test-junit4:$compose_version")

    // Required: provides a stub Activity for createComposeRule() in debug builds
    debugImplementation("androidx.compose.ui:ui-test-manifest:$compose_version")

    // Recommended: mock dependencies in integration tests
    androidTestImplementation("io.mockk:mockk-android:1.13.5")

    // Recommended: test coroutines (StateFlow, suspend fns, TestCoroutineDispatcher)
    androidTestImplementation("org.jetbrains.kotlinx:kotlinx-coroutines-test:1.7.3")

    // Optional: Hilt testing support
    androidTestImplementation("com.google.dagger:hilt-android-testing:$hilt_version")
    kaptAndroidTest("com.google.dagger:hilt-android-compiler:$hilt_version")
}

Why ui-test-manifest?

createComposeRule() needs a real Activity to host the Compose content, but it shouldn't need your Activity. The ui-test-manifest artifact ships a minimal ComponentActivity in your debug APK. Without it you get: "No activities found" or "No compose hierarchies found" at runtime.

Basic Test Class Structure

@RunWith(AndroidJUnit4::class)
class LoginScreenTest {

    @get:Rule
    val composeTestRule = createComposeRule()

    @Test
    fun loginScreen_displaysEmailAndPasswordFields() {
        composeTestRule.setContent {
            AppTheme {
                LoginScreen(onLoginSuccess = {})
            }
        }
        composeTestRule
            .onNodeWithText("Email")
            .assertIsDisplayed()
        composeTestRule
            .onNodeWithText("Password")
            .assertIsDisplayed()
    }
}

Using createAndroidComposeRule for Navigation Tests

@RunWith(AndroidJUnit4::class)
class NavigationTest {

    // Launches the REAL MainActivity — use only for nav/back/deep link testing
    @get:Rule
    val composeTestRule = createAndroidComposeRule<MainActivity>()

    @Test
    fun homeToDetail_navigation_works() {
        composeTestRule.onNodeWithTag("product_0").performClick()
        composeTestRule.onNodeWithTag("product_detail_screen").assertIsDisplayed()
    }
}

Injecting Fake ViewModels (No Hilt Required)

For isolated composable tests, the cleanest approach is to pass dependencies directly to the composable rather than using the DI framework. Compose composables that accept a ViewModel as a parameter (rather than creating one internally) are trivially testable:

// Production composable — ViewModel as default parameter
@Composable
fun ProductListScreen(
    viewModel: ProductListViewModel = viewModel()
) { /* ... */ }

// In test — inject fake directly:
val fakeRepo = FakeProductRepository()
val fakeViewModel = ProductListViewModel(GetProductsUseCase(fakeRepo))
composeTestRule.setContent {
    ProductListScreen(viewModel = fakeViewModel)
}
Best Practice

Always use createComposeRule() — no Activity — for isolated composable tests. Only upgrade to createAndroidComposeRule<MainActivity>() when you genuinely need the full Activity: testing Jetpack Navigation, system back button behaviour, or Activity-level theming. The Activity-backed rule is slower and harder to isolate.

ComposeTestRule & Finders

The Full Finder API

// ── By text ────────────────────────────────────────────────────────────
onNodeWithText("Submit")
onNodeWithText("Submit", ignoreCase = true)
onNodeWithText("ubmi", substring = true)  // partial match

// ── By content description ─────────────────────────────────────────────
onNodeWithContentDescription("Close dialog")
onNodeWithContentDescription("close", ignoreCase = true, substring = true)

// ── By test tag (most stable) ──────────────────────────────────────────
onNodeWithTag("login_button")
onNodeWithTag("email_field", useUnmergedTree = true)

// ── By semantics matcher ───────────────────────────────────────────────
onNode(hasRole(Role.Button))
onNode(hasSetTextAction())       // any text input field
onNode(hasClickAction())         // any clickable node
onNode(hasScrollAction())        // scrollable container
onNode(isDialog())               // dialog popups
onNode(isPopup())                // dropdowns / menus
onNode(isFocused())              // currently focused field
onNode(isEnabled())
onNode(isNotEnabled())

// ── Combining matchers (and / or) ─────────────────────────────────────
onNode(hasText("Email") and hasSetTextAction())
onNode(hasTag("btn") or hasText("Submit"))

// ── Multiple nodes ─────────────────────────────────────────────────────
onAllNodesWithText("Delete")           // SemanticsNodeInteractionCollection
onAllNodesWithTag("list_item")[2]      // index into collection
onAllNodesWithContentDescription("Star")

Adding testTag to Composables

// In your composable:
Button(
    onClick = onSubmit,
    modifier = Modifier.testTag("submit_button")
) { Text("Submit") }

TextField(
    value = email,
    onValueChange = onEmailChange,
    modifier = Modifier.testTag("email_field")
)

// In your test:
composeTestRule.onNodeWithTag("submit_button").performClick()
composeTestRule.onNodeWithTag("email_field").performTextInput("user@example.com")

waitUntil for Async Content

When a composable loads data asynchronously (e.g., via a LaunchedEffect or collectAsState()), the node may not exist in the semantics tree immediately. Use waitUntil to poll:

// Wait until at least one product_item node appears
composeTestRule.waitUntil(timeoutMillis = 5_000) {
    composeTestRule
        .onAllNodesWithTag("product_item")
        .fetchSemanticsNodes()
        .isNotEmpty()
}
// Now safe to assert on individual items
composeTestRule.onAllNodesWithTag("product_item")[0].assertIsDisplayed()

Finder Function Reference

FunctionFinds byBest use caseLocale-safe?
onNodeWithTag()Developer-set testTagAny testable UI element✅ Yes
onNodeWithText()Visible text contentStatic strings in tests❌ No
onNodeWithContentDescription()Accessibility labelIcons and images❌ No
onNode(matcher)Any SemanticsMatcherRole, state, combined conditionsDepends
onAllNodesWithTag()Shared testTagLazyColumn items, repeated elements✅ Yes
onAllNodes(matcher)Any SemanticsMatcherChecking count, bulk assertionsDepends
Best Practice

testTag is the most robust finder. Text and contentDescription can change with localisation or copy changes. testTag is a developer-controlled stable identifier. In production apps, wrap tag constants in a TestTags object so tests and composables share the same source of truth: object TestTags { const val LOGIN_BUTTON = "login_button" }.

Full Interaction API

// ── Click actions ──────────────────────────────────────────────────────
.performClick()
.performLongClick()
.performDoubleClick()

// ── Text input ─────────────────────────────────────────────────────────
.performTextInput("user@example.com")   // appends to current text
.performTextClearance()                  // clears the field

.performImeAction()                      // keyboard Done/Next/Search

.performScrollToNode(hasText("Item 12")) // scroll until child matches

// ── Touch gestures ─────────────────────────────────────────────────────
.performTouchInput {

    swipeLeft()
    swipeRight()
    swipeDown()

    longClick(Offset(100f, 200f))

}

Full Assertion API

// ── Visibility ─────────────────────────────────────────────────────────
.assertIsDisplayed()           // visible AND on screen
.assertIsNotDisplayed()        // exists in tree but not visible
.assertExists()                // in semantics tree (may be off-screen)
.assertDoesNotExist()          // NOT in tree at all

// ── State ──────────────────────────────────────────────────────────────
.assertIsEnabled()
.assertIsDisabled()
.assertIsSelected()
.assertIsNotSelected()
.assertIsFocused()

.assertIsOff()

// ── Content ────────────────────────────────────────────────────────────
.assertTextEquals("Expected text")
.assertTextContains("partial")
.assertContentDescriptionEquals("Close")
.assertContentDescriptionContains("close")

// ── Actions ────────────────────────────────────────────────────────────
.assertHasClickAction()

// ── Collection ─────────────────────────────────────────────────────────

Testing a Complete Login Flow

@Test
fun loginFlow_validCredentials_navigatesToHome() {
    composeTestRule.setContent {
        AppTheme { AppNavHost() }
    }

    // Fill email field
    composeTestRule
        .onNodeWithTag("email_field")
        .performTextInput("user@example.com")

    // Fill password field
    composeTestRule
        .onNodeWithTag("password_field")
        .performTextInput("password123")

    // Submit
    composeTestRule
        .onNodeWithTag("login_button")
        .performClick()

    // Verify navigation occurred
    composeTestRule
        .onNodeWithTag("home_screen")
        .assertIsDisplayed()
}

@Test
fun loginFlow_invalidEmail_showsError() {
    composeTestRule.setContent {
        AppTheme { LoginScreen(onLoginSuccess = {}) }
    }

    composeTestRule.onNodeWithTag("email_field").performTextInput("notanemail")
    composeTestRule.onNodeWithTag("login_button").performClick()

    // Error message should appear
    composeTestRule.onNodeWithTag("email_error").assertIsDisplayed()
    composeTestRule.onNodeWithTag("email_error").assertTextContains("invalid", ignoreCase = true)
}
Important Distinction

assertIsDisplayed() fails if the node exists in the tree but is not visible — scrolled off screen, alpha = 0, or hidden behind another layout. Use assertExists() if you only want to verify the node is in the tree regardless of visibility. Use assertDoesNotExist() when you need to confirm an element was removed from the tree entirely (e.g., a dialog was dismissed).

Semantics & Accessibility

What Is the Semantics Tree?

When Compose lays out your UI, it builds two trees simultaneously: the composition tree (which composables produce which layout nodes) and the semantics tree (which nodes have accessibility meaning). The semantics tree is a filtered, simplified view of your UI that exposes only the information needed by accessibility services and tests.

Every composable that calls Modifier.semantics{} — directly or implicitly through Material components — contributes a node. Text contributes its text. Button contributes a click action and role. TextField contributes text, set-text action, and editing state. You test the semantics tree, not the composition tree.

mergeDescendants — Compound Components

// WITHOUT mergeDescendants: two separate semantics nodes
// → screen reader reads icon and text separately
// → test must find each node independently
Row {
    Icon(Icons.Default.Star, contentDescription = null)
    Text("4.5 stars")
}

// WITH mergeDescendants: one unified semantics node
// → screen reader reads "4.5 stars" as a single unit
// → test: onNodeWithText("4.5 stars") finds the merged node
Row(
    modifier = Modifier.semantics(mergeDescendants = true) {}
) {
    Icon(Icons.Default.Star, contentDescription = null)
    Text("4.5 stars")
}

// Accessing unmerged tree in tests when needed:
composeTestRule.onNodeWithTag("rating", useUnmergedTree = true)

Custom Semantic Properties

// Define a custom semantics property
val SelectedKey = SemanticsPropertyKey<Boolean>("Selected")
var SemanticsPropertyReceiver.selected by SelectedKey

// Apply in composable
@Composable
fun SelectableListItem(text: String, isSelected: Boolean, ...) {
    Row(
        modifier = Modifier
            .testTag("list_item")
            .semantics { selected = isSelected }
            .clickable(onClick = onClick)
    ) { Text(text) }
}

// Test it:
composeTestRule
    .onNode(SemanticsMatcher.expectValue(SelectedKey, true))
    .assertIsDisplayed()

contentDescription Best Practices

// ✅ Dynamic description reflecting actual state
Icon(
    imageVector = Icons.Default.Favorite,
    contentDescription = if (isFavorite) "Remove from favourites" else "Add to favourites"
)

// ✅ Null contentDescription for purely decorative icons
Icon(
    imageVector = Icons.Default.ChevronRight,
    contentDescription = null   // decorative — screen reader skips
)

// In test — assert correct description based on state
composeTestRule
    .onNodeWithContentDescription("Add to favourites")
    .assertHasClickAction()

composeTestRule
    .onNodeWithContentDescription("Add to favourites")
    .performClick()

composeTestRule
    .onNodeWithContentDescription("Remove from favourites")
    .assertIsDisplayed()   // state changed correctly

Testing Invisible Content (Screen Reader Only)

// Assert loading indicator has correct content description
composeTestRule
    .onNodeWithContentDescription("Loading products")
    .assertIsDisplayed()

// Assert icon has accessible label and is clickable
composeTestRule
    .onNode(hasContentDescription("Delete item"))
    .assertHasClickAction()

// Verify error is readable by screen reader even if hidden visually
composeTestRule
    .onNodeWithTag("error_message")
    .assertExists()   // in tree (screen reader can read)
Key Concept

mergeDescendants = true is critical for compound components like rating bars, checkboxes with labels, and list items. Without it, screen readers and tests see multiple disconnected nodes. With it, they see one meaningful unit. If your test fails with "multiple nodes found", check whether a parent container has mergeDescendants = true causing nodes to collapse — use useUnmergedTree = true in the finder to bypass merging.

Testing Patterns (State, Navigation, Screenshot)

Pattern 1 — Testing State Changes

Drive state via mutableStateOf held in the test, then assert that the composable reflects changes:

@Test
fun counter_incrementButton_updatesDisplayedCount() {
    var count by mutableStateOf(0)

    composeTestRule.setContent {
        CounterScreen(
            count = count,
            onIncrement = { count++ },
            onDecrement = { count-- }
        )
    }

    // Initial state
    composeTestRule.onNodeWithTag("count_text").assertTextEquals("0")

    // Increment once
    composeTestRule.onNodeWithTag("increment_button").performClick()
    composeTestRule.onNodeWithTag("count_text").assertTextEquals("1")

    // Increment again
    composeTestRule.onNodeWithTag("increment_button").performClick()
    composeTestRule.onNodeWithTag("count_text").assertTextEquals("2")

    // Decrement
    composeTestRule.onNodeWithTag("decrement_button").performClick()
    composeTestRule.onNodeWithTag("count_text").assertTextEquals("1")
}

Pattern 2 — Integration Test with Real ViewModel + Fake Repo

@Test
fun productList_loadsAndDisplaysItems() {
    val fakeProducts = listOf(
        Product("1", "Espresso Machine", "$299"),
        Product("2", "Milk Frother", "$49")
    )
    val fakeRepo = FakeProductRepository(fakeProducts)
    val viewModel = ProductListViewModel(GetProductsUseCase(fakeRepo))

    composeTestRule.setContent {
        AppTheme { ProductListScreen(viewModel = viewModel) }
    }

    // Wait for coroutine to emit products
    composeTestRule.waitUntil(timeoutMillis = 3_000) {
        composeTestRule
            .onAllNodesWithTag("product_item")
            .fetchSemanticsNodes()
            .size == 2
    }

    composeTestRule.onNodeWithText("Espresso Machine").assertIsDisplayed()
    composeTestRule.onNodeWithText("Milk Frother").assertIsDisplayed()
    composeTestRule.onNodeWithText("$299").assertIsDisplayed()
}

@Test
fun productList_emptyState_showsEmptyMessage() {
    val fakeRepo = FakeProductRepository(emptyList())
    val viewModel = ProductListViewModel(GetProductsUseCase(fakeRepo))

    composeTestRule.setContent {
        AppTheme { ProductListScreen(viewModel = viewModel) }
    }

    composeTestRule.waitUntil(3_000) {
        composeTestRule.onAllNodesWithTag("loading_indicator")
            .fetchSemanticsNodes().isEmpty()
    }
    composeTestRule.onNodeWithTag("empty_state_message").assertIsDisplayed()
}

Pattern 3 — Screenshot Testing with Paparazzi

Paparazzi renders composables on the JVM — no emulator or device needed. It snapshots the rendered bitmap and compares it against a golden image on each test run. Perfect for component library regression testing.

dependencies {

Pitfalls & Best Practices

Common Pitfalls

❌ Using onNodeWithText() for Localised Strings

Hard-coding translated strings in tests breaks when the device language changes or copy is updated.

// ❌ Breaks with language changes
composeTestRule.onNodeWithText("Submit").performClick()

// ✅ Use testTag — stable across all locales
composeTestRule.onNodeWithTag("submit_button").performClick()

❌ Not Waiting for Async State

// ❌ Asserts before LaunchedEffect completes — flaky!
composeTestRule.setContent { ProductListScreen(viewModel) }
composeTestRule.onNodeWithText("Espresso Machine").assertIsDisplayed()

// ✅ Wait for state to settle first
composeTestRule.waitUntil(3_000) {
    composeTestRule.onAllNodesWithTag("product_item")
        .fetchSemanticsNodes().isNotEmpty()
}
composeTestRule.onNodeWithText("Espresso Machine").assertIsDisplayed()

❌ Thread.sleep() for Async Waits

// ❌ Never do this — slow, unreliable, causes CI timeouts
Thread.sleep(2000)
composeTestRule.onNodeWithTag("result").assertIsDisplayed()

// ✅ Use waitUntil — polls with timeout
composeTestRule.waitUntil(timeoutMillis = 3_000) {
    composeTestRule.onAllNodesWithTag("result")
        .fetchSemanticsNodes().isNotEmpty()
}

❌ Forgetting ui-test-manifest

// ❌ Missing dependency → "No activities found" crash

// ✅ Add to build.gradle.kts:
debugImplementation("androidx.compose.ui:ui-test-manifest:$compose_version")

❌ assertIsDisplayed() on Off-Screen LazyColumn Items

// ❌ Item exists in tree but is not on screen — fails
composeTestRule.onNodeWithText("Item 50").assertIsDisplayed()

// ✅ Scroll to it first
composeTestRule.onNodeWithTag("product_list")
    .performScrollToIndex(49)
composeTestRule.onNodeWithText("Item 50").assertIsDisplayed()

Best Practices

✅ Control Animations with mainClock

// Pause automatic clock advancement
composeTestRule.mainClock.autoAdvance = false

// Trigger animation
composeTestRule.onNodeWithTag("expand_button").performClick()

// Advance exactly 300ms (half of a 600ms animation)
composeTestRule.mainClock.advanceTimeBy(300)

// Assert mid-animation state
composeTestRule.onNodeWithTag("panel").assertIsDisplayed()

// Complete the animation
composeTestRule.mainClock.advanceTimeBy(300)

✅ Debug the Semantics Tree with printToLog

// When a finder fails — print the full semantics tree to Logcat
composeTestRule.onRoot().printToLog("SemanticTree")

// Also works on sub-trees
composeTestRule.onNodeWithTag("product_list").printToLog("ListTree")

✅ Async Test with MainCoroutineRule + waitUntil

@RunWith(AndroidJUnit4::class)
class ProductListScreenTest {

    @get:Rule(order = 0)
    val mainCoroutineRule = MainCoroutineRule()  // sets Dispatchers.Main

    @get:Rule(order = 1)
    val composeTestRule = createComposeRule()

    @Test
    fun products_loadSuccessfully() = mainCoroutineRule.runTest {
        val fakeRepo = FakeProductRepository(listOf(Product("1", "Espresso Machine")))
        val viewModel = ProductListViewModel(GetProductsUseCase(fakeRepo))

        composeTestRule.setContent {
            AppTheme { ProductListScreen(viewModel = viewModel) }
        }

        composeTestRule.waitUntil(3_000) {
            composeTestRule.onAllNodesWithTag("product_item")
                .fetchSemanticsNodes().isNotEmpty()
        }

        composeTestRule.onNodeWithText("Espresso Machine").assertIsDisplayed()
    }
}

Interview Framework

30-Second Answer

"Compose UI testing uses the semantics tree, not the View hierarchy. You write tests using ComposeTestRule — set content with setContent{}, find nodes with onNodeWithTag() or onNodeWithText(), interact with performClick() and performTextInput(), and assert with assertIsDisplayed() and assertTextEquals(). For async content I use waitUntil{}. I prefer testTag over text finders for stability across locales and copy changes."

2-Minute Answer — Expand With

  • Two test rules: createComposeRule() for isolated composable tests (fast, no Activity), createAndroidComposeRule<MainActivity>() only for navigation/back/deep link tests that require the real Activity.
  • Semantics tree: Compose tests interact with a semantics tree — a lightweight parallel tree containing accessibility metadata. This is why tests survive UI refactors as long as semantics are preserved.
  • Screenshot testing: Use Paparazzi for offline JVM snapshot regression — renders on the JVM with no emulator, compares golden bitmaps. Fast CI feedback for component library changes.
  • Integration pattern: Use a real ViewModel with a fake repository. Don't mock the ViewModel — test the real one. This gives confidence that the ViewModel + composable integration actually works.
  • Navigation testing: For NavHost flows, use createAndroidComposeRule<MainActivity>(). For unit-testing navigation graph routes, use TestNavHostController with createComposeRule().
  • Async: waitUntil{} polls the semantics tree until a condition is met or the timeout expires. For coroutine-driven tests, combine with MainCoroutineRule and runTest{}.

Must-Mention Checklist

1
ComposeTestRule — createComposeRule() for isolated tests vs createAndroidComposeRule<Activity>() for navigation/Activity-level tests.
2
Semantic finders — onNodeWithTag() preferred over onNodeWithText() for locale stability. Tags are developer-controlled, text/descriptions change with copy.
3
Interactions — performClick(), performTextInput(), performScrollTo(), performScrollToIndex(), performTouchInput{}.
4
Assertions — assertIsDisplayed(), assertTextEquals(), assertDoesNotExist(), assertIsEnabled(), assertCountEquals().
5
Async handling — waitUntil{} with a timeout condition. Never Thread.sleep(). For animations, use mainClock.autoAdvance = false + advanceTimeBy().
6
ui-test-manifest — debugImplementation("androidx.compose.ui:ui-test-manifest") is required. Without it, createComposeRule() crashes with "No activities found".

Interview Questions
Q1 — What is the difference between createComposeRule() and createAndroidComposeRule()?
Easy▾

createComposeRule() creates a ComposeContentTestRule that uses a minimal stub ComponentActivity provided by the ui-test-manifest dependency. No real Activity from your app is launched. It's fast, isolated, and ideal for testing individual composables or ViewModel integration.

createAndroidComposeRule<MainActivity>() actually launches your MainActivity. The full Activity lifecycle runs. Use this only when the test genuinely requires the Activity — navigation with NavHost, system back handling, or themes/resources that come from the Activity context.

// Isolated — no Activity needed
@get:Rule
val composeTestRule = createComposeRule()

// Full Activity — for navigation tests
@get:Rule
val composeTestRule = createAndroidComposeRule<MainActivity>()

Rule of thumb: start with createComposeRule(). Only escalate to createAndroidComposeRule when your test fails specifically because it needs the Activity.

Q2 — How do you find a composable node in a Compose test?
Easy▾

You use semantic finder functions on the ComposeTestRule. The primary finders are:

// By testTag — most stable, locale-independent
composeTestRule.onNodeWithTag("login_button")

// By visible text
composeTestRule.onNodeWithText("Submit")

// By accessibility content description
composeTestRule.onNodeWithContentDescription("Close")

// By semantics matcher (role, state, actions)
composeTestRule.onNode(hasRole(Role.Button) and hasText("Submit"))

Prefer testTag. Add it via Modifier.testTag("my_tag") on your composable. This is the most stable identifier — it never changes with copy updates or locale changes.

Q3 — Your test fails with "No matching node found" — how do you debug it?
Medium▾

Step-by-step debugging process:

1. Print the semantics tree to Logcat and read what nodes actually exist:

composeTestRule.onRoot().printToLog("DEBUG")

2. Check for async issues — is your content loaded yet? If the screen shows a loading spinner when the test runs, the product nodes don't exist. Fix: add waitUntil{} before the assertion.

3. Check for merged semantics — if a parent uses mergeDescendants = true, child nodes are absorbed. Your finder may need useUnmergedTree = true:

composeTestRule.onNodeWithText("4.5 stars", useUnmergedTree = true)

4. Check for off-screen nodes — in a LazyColumn, items outside the visible window are not in the semantics tree. Use performScrollToIndex() first.

5. Verify testTag is set — check that the composable actually has the tag in the code path being exercised. A conditional can mean the tag is not applied in certain states.

Q4 — How do you test a LazyColumn that loads data asynchronously from a ViewModel?
Medium▾

Use a fake repository, inject it into a real ViewModel, and use waitUntil{} to poll until the data appears:

@Test
fun productList_async_loadsAndDisplaysItems() {
    val fakeRepo = FakeProductRepository(
        listOf(Product("1", "Espresso Machine"))
    )
    val viewModel = ProductListViewModel(GetProductsUseCase(fakeRepo))

    composeTestRule.setContent {
        AppTheme { ProductListScreen(viewModel = viewModel) }
    }

    // Poll until the product item tag appears
    composeTestRule.waitUntil(timeoutMillis = 5_000) {
        composeTestRule
            .onAllNodesWithTag("product_item")
            .fetchSemanticsNodes()
            .isNotEmpty()
    }

    composeTestRule.onNodeWithText("Espresso Machine").assertIsDisplayed()
}

For tests that need coroutine dispatch control, combine with @get:Rule val mainCoroutineRule = MainCoroutineRule() and use runTest{}. The fake repository can be a simple in-memory implementation returning the provided data via a Flow.

Q5 — What is the semantics tree and why does Compose testing use it instead of the View hierarchy?
Hard▾

The semantics tree is a parallel tree built by Compose alongside the layout/composition tree. Each composable that calls Modifier.semantics{} — directly or through Material components — contributes a semantics node. That node holds structured metadata: text content, content description, role (Button, Image, etc.), state (enabled, checked, focused), and available actions (click, set-text, scroll).

Why not the View hierarchy? In Compose there is no View hierarchy. Composables are functions that emit layout instructions — there are no View objects, no ViewGroup trees, no R.id identifiers. There is nothing for a View-level testing framework to inspect.

The key advantage: The semantics tree is decoupled from implementation structure. You can restructure your composables completely — extract components, rearrange layouts, rename composable functions — and your tests still pass as long as the semantic meaning (text, tags, actions) is preserved. Tests are coupled to behaviour, not implementation:

// This test passes regardless of whether "Submit" is a Button,
// a TextButton, a custom composable, or wrapped in 10 Box containers
composeTestRule.onNodeWithTag("submit_button")
    .assertIsEnabled()
    .performClick()

The semantics tree is also what accessibility services (TalkBack, Switch Access) read — so tests that pass are also a strong signal that the UI is accessible.

Q6 — How do you test a composable that uses LaunchedEffect to trigger a side effect?
Hard▾

LaunchedEffect launches a coroutine tied to the composition lifecycle. In tests, the Compose test framework controls the clock. The coroutine runs on the test's coroutine dispatcher.

Pattern 1 — Simply waitUntil for the observable outcome:

// Composable uses LaunchedEffect to load and show a snackbar after 2s
@Test
fun screen_launchedEffect_showsSnackbar() {
    composeTestRule.setContent {
        MyScreen(viewModel = fakeViewModel)
    }
    composeTestRule.waitUntil(timeoutMillis = 5_000) {
        composeTestRule.onAllNodesWithTag("snackbar")
            .fetchSemanticsNodes().isNotEmpty()
    }
    composeTestRule.onNodeWithTag("snackbar").assertIsDisplayed()
}

Pattern 2 — Advance the clock for time-based effects:

composeTestRule.mainClock.autoAdvance = false
composeTestRule.setContent { MyScreen() }

// Advance past the LaunchedEffect delay
composeTestRule.mainClock.advanceTimeBy(3_000)

composeTestRule.onNodeWithTag("result").assertIsDisplayed()

Pattern 3 — Use TestCoroutineDispatcher via MainCoroutineRule for full coroutine control:

@get:Rule(order = 0) val coroutineRule = MainCoroutineRule()
@get:Rule(order = 1) val composeTestRule = createComposeRule()

@Test
fun test() = coroutineRule.runTest {
    composeTestRule.setContent { MyScreen() }
    advanceUntilIdle()  // drains all pending coroutines
    composeTestRule.onNodeWithTag("result").assertIsDisplayed()
}
Q7 — Describe how you would implement screenshot regression testing for a component library.
Hard▾

Screenshot regression testing catches unintended visual changes. The standard approach for Compose component libraries is Paparazzi (offline JVM rendering).

Setup:

// build.gradle.kts
plugins { id("app.cash.paparazzi") version "1.3.4" }
dependencies { testImplementation("app.cash.paparazzi:paparazzi:1.3.4") }

Write tests for each visual state:

class ButtonScreenshotTest {
    @get:Rule
    val paparazzi = Paparazzi(
        deviceConfig = DeviceConfig.PIXEL_5,
        theme = "android:Theme.Material.Light.NoActionBar"
    )

    @Test fun button_enabled() {
        paparazzi.snapshot { AppTheme { PrimaryButton("Submit", enabled = true, onClick = {}) } }
    }
    @Test fun button_disabled() {
        paparazzi.snapshot { AppTheme { PrimaryButton("Submit", enabled = false, onClick = {}) } }
    }
    @Test fun button_dark_theme() {
        paparazzi.snapshot { AppTheme(darkTheme = true) { PrimaryButton("Submit", onClick = {}) } }
    }
}

Workflow:

  • Record goldens: ./gradlew recordPaparazziDebug — generates PNG golden files committed to source control
  • Verify in CI: ./gradlew verifyPaparazziDebug — compares rendered output to goldens; fails if pixel diff exceeds threshold
  • Update after intentional changes: re-run record, review diffs in PR, commit updated goldens

Coverage strategy: test every component in every documented state — default, disabled, loading, error, hover, dark theme, different screen densities. Use @TestParameter for parameterised snapshot tests if you have many variants.

Q8 — Your Compose test is flaky — it sometimes passes and sometimes fails on the same code. What are the likely causes and how do you fix them?
Hard▾

Flaky Compose tests almost always have one of these root causes:

1. Race condition — asserting before async state settles

// ❌ Flaky: sometimes the coroutine hasn't emitted yet
composeTestRule.setContent { ProductListScreen(viewModel) }
composeTestRule.onNodeWithTag("product_item").assertIsDisplayed()

// ✅ Fix: wait until the node exists
composeTestRule.waitUntil(5_000) {
    composeTestRule.onAllNodesWithTag("product_item")
        .fetchSemanticsNodes().isNotEmpty()
}

2. Animation not complete — asserting during transition

// ✅ Fix: disable auto-advance and control the clock
composeTestRule.mainClock.autoAdvance = false
// ... trigger action ...
composeTestRule.mainClock.advanceTimeBy(1_000)  // skip past animation

3. Shared mutable state between tests — a static field or singleton retains state from a previous test run. Fix: reset state in @Before / @After, or use a fresh instance per test.

4. Test-order dependency — test A leaves the app in a state that test B depends on. Fix: each test must be fully self-contained — set its own content in setContent{}.

5. Timing sensitivity on slow CI machines — waitUntil timeout is too short. Fix: increase the timeout or replace polling with a deterministic condition that doesn't depend on wall-clock time.

6. LazyColumn item not in semantics tree — an item was scrolled off-screen between one test run and the next due to different initial scroll positions. Fix: always performScrollToIndex() before asserting off-screen items.

Diagnostic approach: run the test 20 times in a row (adb shell am instrument -e numRuns 20), capture Logcat, look for "No matching node" or assertion errors. Print the semantics tree on failure with printToLog().
