10C — Behavioral Patterns

Observer, Strategy, Command, and State — the behavioral patterns that govern communication and responsibility assignment in Android apps.

ID: 10C ◈ Tier 2
🔍
1. Overview

What are Behavioral Patterns?

Behavioral patterns deal with communication between objects — how they interact, share responsibilities, and pass information. They answer: "How do objects collaborate to complete a task?" without coupling them tightly.

PatternIntentAndroid Example
ObserverOne-to-many notification when state changesLiveData, StateFlow, Flow — UI reacts to data changes
StrategyDefine a family of algorithms, encapsulate each, make them interchangeableSorting strategies, payment method selection, compression algorithms
CommandEncapsulate a request as an object (enables undo/redo, queuing)WorkManager tasks, menu actions, undo in text editors
StateAllow an object to alter behaviour when its internal state changesSealed class UI states (Loading/Success/Error), order state machine
Senior Mental Model
Behavioral patterns are about managing complexity in communication. In modern Android (MVI/MVVM), Observer and State are the foundation — everything flows through StateFlow. Strategy and Command appear in domain logic. Recognising them helps you reason about testability: a Strategy can be swapped in tests; a Command can be replayed or logged.

2. How It Works

1. Observer Pattern

Defines a one-to-many dependency between objects so that when one object changes state, all its dependents are notified automatically.

Subject (Observable) Observers ┌──────► UI Composable StateFlow<UiState> ─┼──────► Analytics collector └──────► Test assertion Observers subscribe/unsubscribe independently. Subject doesn't know who is observing. 
// StateFlow — the modern Android observer
class AccountViewModel @Inject constructor(
    private val getBalance: GetAccountBalanceUseCase
) : ViewModel() {

    val balance: StateFlow<BalanceUiState> = getBalance()
        .map { BalanceUiState.Success(it) }
        .catch { emit(BalanceUiState.Error(it.message)) }
        .stateIn(viewModelScope, SharingStarted.WhileSubscribed(5000), BalanceUiState.Loading)
}

// Composable observer — reacts to state changes automatically
@Composable
fun BalanceScreen(vm: AccountViewModel = hiltViewModel()) {
    val state by vm.balance.collectAsStateWithLifecycle()
    when (state) {
        is BalanceUiState.Loading -> CircularProgressIndicator()
        is BalanceUiState.Success -> BalanceCard(state.balance)
        is BalanceUiState.Error   -> ErrorCard(state.message)
    }
}

2. Strategy Pattern

Defines a family of algorithms, encapsulates each one, and makes them interchangeable. The strategy pattern lets the algorithm vary independently from clients that use it.

// Strategy interface — different sorting algorithms for product lists
fun interface SortStrategy<T> {
    fun sort(items: List<T>): List<T>
}

val byPriceAsc = SortStrategy<Product> { items -> items.sortedBy { it.price } }
val byNameAsc  = SortStrategy<Product> { items -> items.sortedBy { it.name } }
val byRating   = SortStrategy<Product> { items -> items.sortedByDescending { it.rating } }

// Context — uses whatever strategy is injected
class ProductListViewModel @Inject constructor(
    private val getProducts: GetProductsUseCase
) : ViewModel() {
    private var sortStrategy: SortStrategy<Product> = byPriceAsc

    fun sortBy(strategy: SortStrategy<Product>) {
        sortStrategy = strategy
        // re-emit sorted list
    }
}

3. Command Pattern

Encapsulates a request as an object, parameterises clients with different requests, and supports undoable operations.

// Command interface
interface Command {
    suspend fun execute()
    suspend fun undo()
}

// Concrete command — add item to cart
class AddToCartCommand(
    private val cartRepository: CartRepository,
    private val item: CartItem
) : Command {
    override suspend fun execute() = cartRepository.addItem(item)
    override suspend fun undo()    = cartRepository.removeItem(item.id)
}

// Command history — supports undo/redo
class CommandExecutor {
    private val history = ArrayDeque<Command>()
    suspend fun execute(command: Command) { command.execute(); history.addLast(command) }
    suspend fun undo() { history.removeLastOrNull()?.undo() }
}

// WorkManager as Command — work request is a command object
val uploadWork = OneTimeWorkRequestBuilder<UploadTransactionWorker>()
    .setInputData(workDataOf("txn_id" to transactionId))
    .setConstraints(Constraints.Builder().setRequiredNetworkType(NetworkType.CONNECTED).build())
    .build()
WorkManager.getInstance(context).enqueue(uploadWork)  // enqueue = execute(command)

4. State Pattern

Allows an object to alter its behaviour when its internal state changes. In Kotlin, sealed classes represent the states; the object transitions between them explicitly.

// Sealed class UI state — each state is a first-class object
sealed class OrderUiState {
    object Idle                                      : OrderUiState()
    object Loading                                    : OrderUiState()
    data class Success(val orders: List<Order>)      : OrderUiState()
    data class Error(val message: String)            : OrderUiState()
    object Empty                                      : OrderUiState()
}

// State machine for order lifecycle
sealed class OrderStatus {
    object Pending                                    : OrderStatus()
    object Confirmed                                  : OrderStatus()
    data class Shipped(val trackingId: String)      : OrderStatus()
    data class Delivered(val deliveredAt: Instant)  : OrderStatus()
    data class Cancelled(val reason: String)        : OrderStatus()
}

// Valid transitions enforced by the state machine
fun OrderStatus.canTransitionTo(next: OrderStatus): Boolean = when (this) {
    is OrderStatus.Pending    -> next is OrderStatus.Confirmed || next is OrderStatus.Cancelled
    is OrderStatus.Confirmed  -> next is OrderStatus.Shipped   || next is OrderStatus.Cancelled
    is OrderStatus.Shipped    -> next is OrderStatus.Delivered
    is OrderStatus.Delivered,
    is OrderStatus.Cancelled  -> false  // terminal states
}

4. Production Example

E-Commerce App — Cart Feature

// ── STATE: Cart UI state sealed class ─────────────────────────
sealed class CartUiState {
    object Loading                                : CartUiState()
    data class Success(val cart: Cart)           : CartUiState()
    object Empty                                  : CartUiState()
    data class Error(val message: String)        : CartUiState()
    data class CheckingOut(val cart: Cart)       : CartUiState()
}

// ── OBSERVER: ViewModel emits state, Composable observes ──────
@HiltViewModel
class CartViewModel @Inject constructor(
    private val cartRepo: CartRepository,
    private val commandExecutor: CommandExecutor,
    private var sortStrategy: SortStrategy<CartItem> = sortCartByAdded
) : ViewModel() {

    val uiState: StateFlow<CartUiState> = cartRepo.observeCart()
        .map { cart ->
            if (cart.items.isEmpty()) CartUiState.Empty
            else CartUiState.Success(cart.copy(items = sortStrategy.sort(cart.items)))
        }
        .catch { emit(CartUiState.Error(it.message ?: "Unknown error")) }
        .stateIn(viewModelScope, SharingStarted.WhileSubscribed(5000), CartUiState.Loading)

    // COMMAND: add/remove with undo support
    fun addItem(item: CartItem) {
        viewModelScope.launch {
            commandExecutor.execute(AddToCartCommand(cartRepo, item))
        }
    }
    fun undoLastAction() { viewModelScope.launch { commandExecutor.undo() } }

    // STRATEGY: change sort at runtime
    fun sortBy(strategy: SortStrategy<CartItem>) { sortStrategy = strategy }
}

5. Alternatives & Trade-offs

Observer: LiveData vs StateFlow vs SharedFlow

TypeBehaviourUse case
LiveDataLifecycle-aware, replays last value, Dispatchers.MainLegacy; avoid in new code
StateFlowAlways has a value, replays to new collectors, distinctUntilChangedUI state — current state always available
SharedFlowConfigurable replay buffer, hot, one-shot eventsNavigation events, Snackbars, one-shot side effects

Strategy vs when/if-else

For 2-3 static cases, a when expression is perfectly fine. Strategy pays off when: the algorithm is chosen at runtime, changes frequently, or must be independently tested. In Kotlin, a fun interface + lambda is the lightweight Strategy implementation — no extra class hierarchy needed.

State Pattern vs Boolean Flags

Anti-Pattern: Boolean Flag Explosion
var isLoading: Boolean; var hasError: Boolean; var isEmpty: Boolean — these are 8 possible combinations, most of which are invalid. A sealed UiState restricts to only the valid states, making invalid combinations unrepresentable.

6. Pitfalls & Best Practices

Observer Pitfalls

Collecting in the Wrong Lifecycle
lifecycleScope.launch { viewModel.flow.collect { ... } } continues collecting even when the app is in the background, wasting resources and potentially processing stale data. Use repeatOnLifecycle(Lifecycle.State.STARTED) or collectAsStateWithLifecycle() in Compose, which automatically pauses and resumes collection with the lifecycle.
Using SharedFlow for UI State
SharedFlow doesn't have a current value — a new subscriber (e.g., after screen rotation) gets nothing. Always use StateFlow for UI state, and SharedFlow only for one-shot events (navigation, Snackbar).

State Pattern Best Practices

  • Use object for stateless states and data class for states carrying data
  • Transitions should be explicit: a canTransitionTo() method on the state prevents invalid transitions in the domain model
  • One ViewModel → one UiState sealed class: don't have separate isLoading, error, data properties — unify into a single state

Command Pattern Best Practices

  • For WorkManager: use unique work names (enqueueUniqueWork) to prevent duplicate background tasks
  • Ensure commands are idempotent when they can be retried (WorkManager retries on failure)
  • Separate the command from its executor — the executor manages history and concurrency, the command encapsulates only the action

7. Interview Framework

30-Second Answer

"Behavioral patterns govern object communication. In Android: Observer is the foundation — StateFlow and Flow let the UI react to state changes without polling. State is how we model UI screen states and domain lifecycles — sealed classes make all valid states explicit. Strategy lets us swap algorithms at runtime, like sorting or payment method selection. Command encapsulates an action as an object — enabling undo, queuing, and WorkManager's deferred execution."

2-Minute Deep Dive

"Observer is built into Android's reactive stack. The key distinction: StateFlow for UI state (always has a current value — safe after rotation), SharedFlow for one-shot events like navigation. The State pattern with sealed classes is the modern replacement for boolean flag combinations — var isLoading; var hasError gives 4 possible states, many invalid. A sealed UiState restricts to exactly the valid ones. For Command: WorkManager is essentially a distributed command queue — each WorkRequest is a command object with constraints, input data, retry policy, and the ability to chain. For Strategy: using fun interface SortStrategy in Kotlin means any lambda is a strategy — you don't need a class hierarchy."

Must-Mention Points

1
Observer: StateFlow for state (has current value), SharedFlow for one-shot events — collect with lifecycle awareness
2
State: sealed class UI states (Loading/Success/Error/Empty) — invalid combinations are unrepresentable
3
Strategy: Kotlin fun interface + lambda = lightweight strategy; swap algorithms without modifying context
4
Command: WorkManager tasks are command objects — encapsulate work, defer, queue, retry
5
Boolean flag anti-pattern: replaced by sealed UiState — always mention this when asked about State pattern
6
collectAsStateWithLifecycle: lifecycle-safe observer — stops collection in background, resumes on STARTED

Do NOT Go Deeper On

  • Iterator, Visitor, Mediator patterns (not commonly asked in Android)
  • Full GoF Command implementation details — keep it at WorkManager/undo pattern level

Follow-up Q&A

QuestionAnswer
"LiveData vs StateFlow?"StateFlow is coroutine-native, works on any dispatcher, doesn't need lifecycle on the data side. LiveData is lifecycle-aware at collection but couples to Dispatchers.Main. Use StateFlow in new code.
"How do you handle one-shot events (navigation, Snackbar)?"SharedFlow with replay=0 (no cached value). Collect in a LaunchedEffect or repeatOnLifecycle(STARTED) block. Avoid Channel-based events — they have different cancellation semantics.
"What's the Strategy pattern in Kotlin?"A fun interface with a single method. Any lambda conforming to that signature is a strategy — no class needed. This is Kotlin's idiomatic approach to the classic GoF Strategy pattern.

Senior Insight

Senior Signal
MVI (Model-View-Intent) is the synthesis of Observer + State + Command. The View emits Intent (Command), the ViewModel reduces it to a new State (State pattern), and the View observes the State (Observer). Recognising that MVI is three behavioral patterns composed together demonstrates deep understanding of both patterns and modern Android architecture.

9. Interview Questions
Basic What is the Observer pattern and where does Android use it? ⌄
Observer defines a one-to-many dependency: when a subject changes state, all observers are notified. In Android: StateFlow is the subject — ViewModels emit state, Composables and Fragments observe it. Clicking "Collect" registers as an observer; unsubscribing (leaving the screen) removes it. Room's Flow<List<T>> from DAO queries is also Observer — the database is the subject, the ViewModel is the observer, and Room notifies it automatically when the underlying table changes.
Basic Why use a sealed class for UI state instead of multiple boolean flags? ⌄
Multiple booleans (isLoading, hasError, isEmpty) create 8 possible combinations (2³), but most are invalid — e.g., isLoading=true AND hasError=true is nonsensical. A sealed class UiState with subclasses Loading, Success, Error, Empty has exactly 4 valid states. The compiler exhausts all cases in a when expression, ensuring every state is handled. Invalid state combinations are unrepresentable at compile time.
Basic How does WorkManager implement the Command pattern? ⌄
A WorkRequest is a Command object — it encapsulates the work to be done (ListenableWorker subclass), the constraints (network type, charging state), input data, retry policy, and backoff criteria. WorkManager.enqueue(request) is the execute. WorkManager persists commands to a SQLite database and executes them when constraints are met — even across app restarts. This gives you deferred, reliable, persistent command execution.
Intermediate What is the difference between StateFlow and SharedFlow? ⌄
StateFlow: always holds a current value (initial value required); new collectors immediately receive the current value; uses distinctUntilChanged — identical consecutive values are not re-emitted. Best for UI state.

SharedFlow: configurable replay buffer (default 0 — no replay); supports multiple simultaneous emissions; doesn't require an initial value. Best for one-shot events: navigation, Snackbar messages, error popups. A new collector with replay=0 doesn't get past events, which is exactly what you want for "show once" notifications.
Intermediate Implement the Strategy pattern for a text search algorithm in Kotlin. ⌄
fun interface SearchStrategy { fun search(query: String, items: List<Product>): List<Product> }
val exactMatch = SearchStrategy { q, items -> items.filter { it.name == q } }
val fuzzyMatch = SearchStrategy { q, items -> items.filter { it.name.contains(q, ignoreCase = true) } }
val ftsMatch = SearchStrategy { q, items -> ftsEngine.search(q) }

The ViewModel holds a var searchStrategy: SearchStrategy and the UI calls viewModel.setSearchStrategy(fuzzyMatch). The search logic never changes — only the strategy does.
Intermediate How do you implement undo functionality using the Command pattern? ⌄
Define interface Command { suspend fun execute(); suspend fun undo() }. Implement commands like DeleteItemCommand(repo, item) where execute() deletes and undo() re-inserts. A CommandExecutor holds an ArrayDeque<Command> as history. Every executed command is pushed to the deque. undo() pops the last command and calls its undo(). In the UI: show a Snackbar with "Undo" after deletion; the button calls viewModel.undo(). This is exactly how Gmail's "Undo send" or Android's swipe-to-delete work.
Intermediate What lifecycle-aware way should you use to collect a Flow in a Fragment? ⌄
Use viewLifecycleOwner.repeatOnLifecycle(Lifecycle.State.STARTED) inside onViewCreated:

viewLifecycleOwner.lifecycleScope.launch { viewLifecycleOwner.repeatOnLifecycle(STARTED) { viewModel.state.collect { render(it) } } }

This automatically stops the collector when the Fragment moves to the STOPPED state (backgrounded) and resumes when it returns to STARTED. Without this, the coroutine runs even when the Fragment is invisible, wasting resources and potentially crashing on updates to destroyed views.
Senior MVI architecture uses multiple behavioral patterns. Identify them and explain how they compose. ⌄
MVI (Model-View-Intent) is three behavioral patterns composed:

1. Command: User interactions produce "Intents" (UserIntent.AddToCart, UserIntent.Search) — each Intent is a Command describing what the user wants to do. They're dispatched to the ViewModel, not executed inline.

2. State: The ViewModel maintains a single sealed UiState that represents all possible screen states. A "reducer" function takes (currentState, intent) and produces the next state — this is a pure State pattern transition function.

3. Observer: The View observes the single StateFlow<UiState> and re-renders entirely when it changes. The View is a passive observer — it never reads state directly, only reacts to emissions.

The composition provides: testable transitions (test the reducer with no Android context), unidirectional data flow (commands → state → view, never backwards), and deterministic replay.
Senior Design a state machine for an automotive app's vehicle connection lifecycle. ⌄ 
sealed class ConnectionState {
    object Disconnected : ConnectionState()
    object Scanning : ConnectionState()
    data class Connecting(val device: BluetoothDevice) : ConnectionState()
    data class Connected(val device: BluetoothDevice, val session: Session) : ConnectionState()
    data class Error(val cause: Throwable) : ConnectionState()
}

fun ConnectionState.canTransitionTo(next: ConnectionState) = when (this) {
    is Disconnected -> next is Scanning
    is Scanning     -> next is Connecting || next is Disconnected
    is Connecting   -> next is Connected || next is Error || next is Disconnected
    is Connected    -> next is Disconnected || next is Error
    is Error        -> next is Disconnected
}
State machine enforces legal transitions, making it impossible to jump from Disconnected to Connected without going through Scanning → Connecting. The ViewModel emits this as a StateFlow; the dashboard UI maps each state to different UI: spinner for Scanning, progress for Connecting, live data for Connected.
Senior How would you test a Strategy pattern implementation in isolation? ⌄
Strategy's key testability benefit: each strategy is an isolated, stateless function — no Android framework needed. Tests:

1. Unit test each strategy: val result = byPriceAsc.sort(sampleList); assertEquals(sortedByPrice, result) — pure Kotlin test, sub-millisecond.
2. Test the context with a fake strategy: inject a SortStrategy { it } (identity — returns items unchanged) when testing the ViewModel. This isolates the ViewModel test from sorting logic.
3. Test strategy switching: verify that calling viewModel.sortBy(byRating) causes the StateFlow to emit a re-sorted list.

This is exactly why Strategy + DIP together produce the highest testability: each algorithm is a function, the context is tested with fakes.
