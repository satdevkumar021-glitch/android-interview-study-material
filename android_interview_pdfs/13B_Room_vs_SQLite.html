1. Overview

Room Abstracts SQLite

Room is not a replacement for SQLite — it is an abstraction layer on top of it. Under the hood, Room generates code that calls the Android SQLiteOpenHelper APIs. The generated code is equivalent to what you'd write manually with raw SQLite, but Room adds compile-time verification, type mapping, and reactive integration.

Senior Mental Model
"Room vs SQLite" is often a false dichotomy. Room IS SQLite — it's compiled into efficient SQLiteOpenHelper calls. The question is really: "Do you need the safety and productivity of Room's abstractions, or do you need the raw control that only direct SQLite access provides?" In 2024, the answer is Room for 95% of cases.

2. How It Works

Compile-Time Query Verification Side by Side

// ── Room ─────────────────────────────────────────────────────
@Query("SELECT * FROM orders WHERE user_id = :userId AND staus = 'ACTIVE'")
//                                              ^^^^^ typo
// BUILD ERROR: There is a problem with the query: [SQLITE_ERROR] SQL error or missing database
// (no such column: staus) → caught at COMPILE TIME

// ── Raw SQLite ───────────────────────────────────────────────
val cursor = db.rawQuery(
    "SELECT * FROM orders WHERE user_id = ? AND staus = 'ACTIVE'",
    arrayOf(userId)
)
// Cursor is empty at runtime — no exception, just silently wrong results
// Typo discovered in production via user bug report 😢

Type Safety

// ── Room — type-safe, auto-mapped ────────────────────────────
@Query("SELECT * FROM orders WHERE id = :orderId")
suspend fun getOrder(orderId: String): OrderEntity?
// Room maps columns to OrderEntity fields automatically, with type checking

// ── Raw SQLite — manual, error-prone ─────────────────────────
val cursor = db.rawQuery("SELECT * FROM orders WHERE id = ?", arrayOf(orderId))
return if (cursor.moveToFirst()) {
    OrderEntity(
        id = cursor.getString(cursor.getColumnIndexOrThrow("id")),
        userId = cursor.getString(cursor.getColumnIndexOrThrow("user_id")),
        totalCents = cursor.getLong(cursor.getColumnIndexOrThrow("total_cents")),
        status = cursor.getString(cursor.getColumnIndexOrThrow("status"))
    ).also { cursor.close() }
} else {
    cursor.close(); null
}

Migration DSL vs onUpgrade

// ── Room Migration ───────────────────────────────────────────
val MIGRATION_2_3 = object : Migration(2, 3) {
    override fun migrate(database: SupportSQLiteDatabase) {
        database.execSQL("ALTER TABLE orders ADD COLUMN delivery_notes TEXT")
    }
}
// Room validates the resulting schema against the @Entity definition

// ── Raw SQLiteOpenHelper ─────────────────────────────────────
override fun onUpgrade(db: SQLiteDatabase, oldVersion: Int, newVersion: Int) {
    if (oldVersion < 3) {
        db.execSQL("ALTER TABLE orders ADD COLUMN delivery_notes TEXT")
    }
    // No automatic schema validation — must manually verify correctness
    // Easy to forget an if-block for a new version jump
}

@RawQuery — Dynamic Queries in Room

// @RawQuery for dynamic query construction (e.g., user-configurable filters)
@Dao
interface ProductDao {
    @RawQuery(observedEntities = [ProductEntity::class])
    fun getProductsDynamic(query: SupportSQLiteQuery): Flow<List<ProductEntity>>
}

// Build the query dynamically
fun buildProductQuery(
    categoryId: String?,
    minPrice: Long?,
    sortBy: String
): SupportSQLiteQuery {
    val sb = StringBuilder("SELECT * FROM products")
    val args = mutableListOf<Any>()
    val conditions = mutableListOf<String>()
    if (categoryId != null) { conditions.add("category_id = ?"); args.add(categoryId) }
    if (minPrice != null) { conditions.add("price_cents >= ?"); args.add(minPrice) }
    if (conditions.isNotEmpty()) sb.append(" WHERE ${conditions.joinToString(" AND ")}")
    sb.append(" ORDER BY $sortBy")
    return SimpleSQLiteQuery(sb.toString(), args.toTypedArray())
}
@RawQuery and SQL Injection
Never concatenate user input directly into a RawQuery string — use positional arguments (?) to prevent SQL injection. The SimpleSQLiteQuery(sql, args) constructor uses parameterised queries safely.

3. When to Use

Use Room when:

  • Building any new Android feature that needs local data persistence
  • You want compile-time safety, type safety, and reactive queries
  • The schema is known at compile time (covers 95% of use cases)
  • You need coroutine-based APIs and Flow integration
  • The team has mixed experience — Room prevents common SQLite mistakes

Consider Raw SQLite when:

  • Multi-process access: Room's locking isn't designed for concurrent access from multiple processes (e.g., app + ContentProvider + background service in separate processes). Raw SQLite with WAL mode handles this better.
  • Existing legacy code: migrating an existing SQLiteOpenHelper that works correctly is only worthwhile if there's a benefit to the migration
  • Complex dynamic SQL that Room's annotation model can't express — though @RawQuery covers most of these
  • Minimal dependency requirements in an SDK/library where adding Room's dependencies is undesirable
The Answer in Most Interviews
"Room in 95% of cases. Raw SQLite only for multi-process access, legacy code with no benefit to migration, or SDK development where dependencies must be minimal."

4. Production Example

Same Feature: Room vs Raw SQLite

Get all active orders for a user, sorted by date descending:

// ── ROOM (10 lines, type-safe, compile-verified, reactive) ────
@Query("SELECT * FROM orders WHERE user_id = :userId AND status = 'ACTIVE' ORDER BY created_at DESC")
fun getActiveOrders(userId: String): Flow<List<OrderEntity>>

// ── RAW SQLITE (30+ lines, manual, error-prone, no reactivity) ─
fun getActiveOrders(userId: String): List<OrderEntity> {
    val db = readableDatabase
    val orders = mutableListOf<OrderEntity>()
    var cursor: Cursor? = null
    try {
        cursor = db.rawQuery(
            "SELECT * FROM orders WHERE user_id = ? AND status = 'ACTIVE' ORDER BY created_at DESC",
            arrayOf(userId)
        )
        while (cursor.moveToNext()) {
            orders.add(OrderEntity(
                id = cursor.getString(cursor.getColumnIndexOrThrow("id")),
                userId = cursor.getString(cursor.getColumnIndexOrThrow("user_id")),
                totalCents = cursor.getLong(cursor.getColumnIndexOrThrow("total_cents")),
                status = cursor.getString(cursor.getColumnIndexOrThrow("status")),
                createdAt = cursor.getString(cursor.getColumnIndexOrThrow("created_at"))
                    .let { Instant.parse(it) }
            ))
        }
    } finally {
        cursor?.close()  // must not forget this
    }
    return orders
    // No reactivity — caller must re-call this manually to get updates
}

@RawQuery for Advanced Search

// E-commerce app: user selects any combination of category, price, rating filters
// Static @Query cannot express this — @RawQuery with SimpleSQLiteQuery is the solution
class ProductSearchRepository @Inject constructor(
    private val dao: ProductDao
) {
    fun searchProducts(filters: ProductFilters): Flow<List<Product>> =
        dao.getProductsDynamic(buildProductQuery(filters))
            .map { it.map(ProductEntity::toDomain) }
}

Room Performance vs Raw SQLite

Room's overhead is negligible for normal usage. Since Room generates code at compile time (not reflection at runtime), the generated DAO implementation is nearly identical to hand-written SQLite code. The only overhead is the InvalidationTracker for Flow queries — which adds a small observer registration on writes. For most apps this is unmeasurable.

6. Pitfalls & Best Practices

SQL Injection in @RawQuery

Never Concatenate User Input into SQL Strings
SimpleSQLiteQuery("SELECT * FROM products WHERE name = '$userInput'") is vulnerable to SQL injection. Always use parameterised queries: SimpleSQLiteQuery("SELECT * FROM products WHERE name = ?", arrayOf(userInput)). Room's static @Query methods are automatically safe — Room never concatenates parameters into the SQL string.

Cursor Leaks in Raw SQLite

Always Close Cursors
Unclosed Cursors leak file descriptors. Always close them in a finally block or use Kotlin's use extension: cursor.use { ... }. Room never has this problem — it manages Cursor lifecycle in generated code. This is one of the most common raw SQLite bugs in production apps.

Best Practices for @RawQuery

  • Always specify observedEntities on @RawQuery — Room needs to know which tables to watch for Flow invalidation
  • Validate the sortBy column name against a whitelist before passing to SimpleSQLiteQuery — don't let users inject column names directly
  • Test @RawQuery methods with Room's test database using real data — static analysis can't verify dynamic queries

7. Interview Framework

30-Second Answer

"Room is an abstraction layer on top of SQLite with three key advantages: compile-time query verification — a SQL typo is a build error, not a runtime crash; type safety — no manual Cursor reading; and reactive queries via Flow — the UI auto-updates when the database changes. Raw SQLite gives full control and zero overhead, but you write 3x more code with no compile-time safety. I'd use Room for virtually all production Android work. The only exceptions are multi-process access, existing legacy code that works correctly, or library/SDK development where dependencies must be minimal."

2-Minute Deep Dive

"Room's compile-time verification is worth emphasising: when you write @Query('SELECT * FROM orders WHERE user_id = :userId'), Room's annotation processor verifies the SQL against the schema before the .class files are generated. A typo in a column name, a type mismatch between the return type and the SELECT columns, or referencing a non-existent table — all are build errors. With raw SQLite, these produce silent bugs (wrong data) or runtime crashes. For dynamic queries that Room's static annotation model can't express, @RawQuery with SimpleSQLiteQuery preserves the Flow reactive behaviour while allowing runtime query construction. Always use parameterised queries to prevent SQL injection. Room's migration DSL is also safer than SQLiteOpenHelper.onUpgrade() — Room validates the schema after migration against the @Entity definition."

9. Interview Questions
Basic What is the main advantage of Room over raw SQLite? ⌄
Compile-time query verification. Room's annotation processor validates your SQL queries against the database schema during compilation. Typos in table/column names, type mismatches between the query result and the return type, and invalid SQL syntax are all build errors — not runtime crashes. Raw SQLite discovers these errors in production via user bug reports or crash logs.
Basic What is a Cursor in raw SQLite and why is it error-prone? ⌄
A Cursor is the result of a raw SQLite query — a pointer into the result set that you iterate manually with cursor.moveToNext(). Pitfalls: (1) you access columns by string name or integer index — typos compile fine but throw IllegalArgumentException at runtime. (2) Cursors are file descriptor resources that must be explicitly closed — forgetting cursor.close() leaks file descriptors and eventually crashes the app. (3) There's no automatic type mapping — you manually call getString(), getLong(), etc., and must cast correctly. Room eliminates all of these.
Basic What is @RawQuery and when would you use it? ⌄
@RawQuery lets you execute a dynamically-constructed SQL query through Room's DAO, while still retaining Room's type mapping and Flow reactive capabilities. Use it when the query can't be expressed as a static @Query annotation — e.g., a search screen where users can select any combination of filters (category, price range, rating, sort order). The observedEntities parameter tells Room which tables to watch for Flow invalidation.
Intermediate Room is built on SQLite, so why doesn't it add performance overhead? ⌄
Room uses annotation processing (KSP or kapt) to generate DAO implementations at compile time — not reflection at runtime. The generated code in OrderDao_Impl is essentially the same boilerplate you'd write manually: open database, build the SQL string, create a Cursor, iterate it, close it. There's no reflection, no dynamic dispatch, no serialisation layer. The only runtime overhead is the InvalidationTracker for Flow queries, which registers a lightweight observer on table writes — this overhead is typically under 1ms.
Intermediate Describe a scenario where you'd choose raw SQLite over Room. ⌄
Multi-process access: If a ContentProvider in one process, the main app in another, and a background service in a third all need database access, Room's locking assumptions may not hold. Raw SQLite with WAL (Write-Ahead Logging) mode handles multi-reader, single-writer access more predictably across processes.

SDK/library development: A library that embeds SQLite doesn't want to force its consumers to add Room as a dependency — especially if they already use Room for their own data and might get version conflicts.

Legacy working code: Migrating a 5-year-old SQLiteOpenHelper that works correctly provides no user-visible benefit and carries migration risk.
Intermediate How does Room's migration approach differ from SQLiteOpenHelper.onUpgrade()? ⌄
SQLiteOpenHelper.onUpgrade(): called with old and new version numbers; you write nested if (oldVersion < N) checks. No automatic schema validation — if your migration is incorrect, Room won't tell you (unless you test it). Easy to miss a version jump when adding new migrations over time.

Room Migration objects: each Migration(fromVersion, toVersion) is registered separately via .addMigrations(). Room chains them automatically for large version jumps (e.g., 1→3 runs MIGRATION_1_2 then MIGRATION_2_3). With exportSchema = true, Room saves the schema JSON to disk — you can use MigrationTestHelper to verify that your migration produces the exact expected schema.
Intermediate How do you prevent SQL injection with @RawQuery? ⌄
Use SimpleSQLiteQuery with positional parameters (?) instead of string concatenation:

SAFE: SimpleSQLiteQuery("SELECT * FROM products WHERE name = ?", arrayOf(userInput))
UNSAFE: SimpleSQLiteQuery("SELECT * FROM products WHERE name = '$userInput'")

The parameterised form escapes the user input before embedding it in the query. Additionally, validate any user-controlled column names (e.g., sort order) against a whitelist of allowed column names before including them in the SQL string — column names cannot be parameterised.
Senior A colleague argues "Room is unnecessary overhead — our app should use raw SQLite for performance." How do you respond? ⌄
The performance argument is incorrect: Room generates identical code to hand-written SQLite at compile time — no reflection, no runtime overhead. Benchmark data from Google confirms this.

The real trade-offs are: (1) Safety: Room catches SQL errors at build time; raw SQLite at runtime in production. In a banking app, a wrong column reference that silently returns null instead of throwing means incorrect data displayed to users — far worse than a build failure. (2) Productivity: 3 lines of Room vs 30 lines of raw SQLite for a basic query. Over a codebase of 500 queries, that's 13,500 fewer lines of boilerplate. (3) Maintainability: when a column is renamed, Room gives a compile error at every affected query. With raw SQLite, you do a global text search and hope you didn't miss anything.

The only legitimate performance concern: Room's InvalidationTracker for Flow queries adds minimal overhead on writes. If you're doing millions of writes per second (atypical), this might matter. Otherwise, it's a non-issue.
Senior How would you migrate a 50,000-line legacy app from raw SQLiteOpenHelper to Room? ⌄
Incremental migration — never big-bang:

1. Assess first: is migration worth it? Identify which tables are most active, have the most bugs, or would benefit most from Flow reactivity.
2. Keep existing SQLiteOpenHelper: create Room entities and DAOs for one table only. Configure Room to use the same database file as the existing helper: Room.databaseBuilder(...).openHelperFactory(...) or use a separate database for new tables.
3. Write migration scripts: Room's schema must be compatible with the existing SQLite schema. Set the database version to the current version; add a Migration that does nothing (schema is already correct).
4. Migrate table by table: replace each SQLiteOpenHelper access with Room DAO calls. Run the full test suite after each table migration.
5. Export schema from the start: version control the JSON — it becomes the audit trail of schema changes.
6. Remove SQLiteOpenHelper once all tables are migrated.
Senior How does Room handle multi-threaded writes and reads? ⌄
Room configures SQLite in WAL (Write-Ahead Logging) mode by default on Android (API 16+). WAL allows: multiple concurrent readers, one concurrent writer, and readers don't block writers. Room's generated DAO code uses SupportSQLiteDatabase, which handles transaction management. Suspend DAO functions run on Room's Dispatchers.IO dispatcher — they're safe to call from multiple coroutines simultaneously.

Room uses ThreadLocal-based transaction management for @Transaction-annotated functions, ensuring all operations within a transaction block use the same database connection. For Flow queries, Room's InvalidationTracker uses a background thread to coalesce invalidation events and re-run queries. This is safe for single-process apps. For multi-process access, Room's documentation explicitly states it's not designed for that use case — use raw SQLite with explicit locking.
