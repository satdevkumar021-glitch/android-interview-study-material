1. Overview

The Legacy UI Toolkit

Android's original UI toolkit uses XML layout files inflated into View objects. Jetpack Compose is the modern replacement, but legacy UI knowledge is essential for maintaining existing apps and understanding the limitations Compose was designed to solve.

TechnologyPurposeStatus
ViewBindingType-safe view access — replaces findViewById✅ Recommended when not using Compose
DataBindingTwo-way binding between XML and data⚠️ Works but adds complexity — prefer ViewModel + ViewBinding
ConstraintLayoutFlat, flexible layout✅ Best XML layout manager
Custom ViewsFully custom rendering via Canvas✅ Still needed for complex custom components
ViewStub/merge/includeLayout optimization techniques✅ Still used in XML-based apps
Senior Mental Model
Know legacy UI well enough to maintain and migrate it. In interviews, acknowledge that Compose solves the fundamental problems of XML UI (no type safety, manual state management, complex custom rendering) while still demonstrating mastery of the legacy stack for the millions of existing Android apps.

2. ViewBinding & DataBinding

ViewBinding

// Enable in build.gradle.kts:
android { buildFeatures { viewBinding = true } }

// Fragment — proper lifecycle management
class ProductFragment : Fragment(R.layout.fragment_product) {

    private var _binding: FragmentProductBinding? = null
    private val binding get() = _binding!!

    override fun onCreateView(inflater: LayoutInflater, container: ViewGroup?, savedInstanceState: Bundle?) =
        FragmentProductBinding.inflate(inflater, container, false).also { _binding = it }.root

    override fun onDestroyView() {
        super.onDestroyView()
        _binding = null  // IMPORTANT: prevent memory leak
    }
}
Memory Leak Warning
In Fragments, the View can be destroyed while the Fragment instance lives on (e.g., in the back stack). Always null out the binding reference in onDestroyView() to prevent the binding (and all its view references) from leaking.

DataBinding

// Enable:
android { buildFeatures { dataBinding = true } }

<!-- XML layout wrapped in <layout> tag -->
<layout>
    <data>
        <variable name="product" type="com.example.Product" />
        <variable name="viewModel" type="com.example.ProductViewModel" />
    </data>
    <TextView
        android:text="@{product.name}"
        android:onClick="@{() -> viewModel.onProductClicked(product)}" />
    <!-- Two-way binding: -->
    <EditText android:text="@={viewModel.searchQuery}" />
</layout>
FeatureViewBindingDataBinding
Type safety✅ Full✅ Full
Build speedFaster (no annotation processing)Slower (KSP/KAPT needed)
XML expressions❌ No✅ @{}, @={} expressions
Two-way binding❌ No✅ @={}
Kotlin syntheticsDeprecated — removed in Kotlin 1.8

Recommendation: Use ViewBinding for simple view access. DataBinding for two-way binding — but be aware of hidden complexity (hard-to-debug XML expressions, build time overhead). Prefer ViewModel + ViewBinding + manual observation over DataBinding expressions.

3. ConstraintLayout

ConstraintLayout produces a flat view hierarchy — all views at the same level with positional relationships defined by constraints. This eliminates deeply nested LinearLayouts/RelativeLayouts, reducing measure/layout passes.

Key Concepts

ConceptDescription
ConstraintsAttach view edges to parent, other views, or guidelines
ChainsLinked group of views sharing space — spread, packed, or weighted
BarrierVirtual guide that tracks the extremity of multiple views
GuidelineFixed or percentage-based position line for alignment
GroupControl visibility of multiple views together
MotionLayoutSubclass for complex animations between two ConstraintSets
<!-- Typical ConstraintLayout card -->
<androidx.constraintlayout.widget.ConstraintLayout>

    <ImageView
        android:id="@+id/avatar"
        app:layout_constraintTop_toTopOf="parent"
        app:layout_constraintStart_toStartOf="parent" />

    <TextView
        android:id="@+id/nameText"
        app:layout_constraintTop_toTopOf="@id/avatar"
        app:layout_constraintStart_toEndOf="@id/avatar"
        app:layout_constraintEnd_toEndOf="parent" />

    <!-- Barrier — follows the longer of name or subtitle -->
    <androidx.constraintlayout.widget.Barrier
        android:id="@+id/textBarrier"
        app:barrierDirection="bottom"
        app:constraint_referenced_ids="nameText,subtitleText" />

</androidx.constraintlayout.widget.ConstraintLayout>

ConstraintSet for Programmatic Changes

val constraintSet = ConstraintSet()
constraintSet.clone(constraintLayout)
constraintSet.connect(R.id.view, ConstraintSet.TOP, R.id.anchor, ConstraintSet.BOTTOM, 16)
// Apply with animation:
TransitionManager.beginDelayedTransition(constraintLayout)
constraintSet.applyTo(constraintLayout)

4. Custom Views

Custom View Lifecycle

class CircleProgressView @JvmOverloads constructor(
    context: Context,
    attrs: AttributeSet? = null,
    defStyleAttr: Int = 0
) : View(context, attrs, defStyleAttr) {

    private val paint = Paint(Paint.ANTI_ALIAS_FLAG).apply {
        color = Color.BLUE
        style = Paint.Style.STROKE
        strokeWidth = 8f
    }
    private val oval = RectF()
    var progress: Float = 0f
        set(value) { field = value.coerceIn(0f, 1f); invalidate() }

    // onMeasure: define the view's size
    override fun onMeasure(widthMeasureSpec: Int, heightMeasureSpec: Int) {
        val size = resolveSize(200, widthMeasureSpec).coerceAtLeast(
            resolveSize(200, heightMeasureSpec)
        )
        setMeasuredDimension(size, size)
    }

    // onLayout: position children (for ViewGroups only)

    // onDraw: render to Canvas — called every invalidate()
    override fun onDraw(canvas: Canvas) {
        val padding = paint.strokeWidth / 2
        oval.set(padding, padding, width - padding, height - padding)
        canvas.drawArc(oval, -90f, progress * 360f, false, paint)
    }
}

Custom XML Attributes

<!-- res/values/attrs.xml -->
<declare-styleable name="CircleProgressView">
    <attr name="progressColor" format="color" />
    <attr name="strokeWidth" format="dimension" />
</declare-styleable>

// Read in constructor:
init {
    context.obtainStyledAttributes(attrs, R.styleable.CircleProgressView).use { ta ->
        paint.color = ta.getColor(R.styleable.CircleProgressView_progressColor, Color.BLUE)
        paint.strokeWidth = ta.getDimension(R.styleable.CircleProgressView_strokeWidth, 8f)
    }
}
Performance Warning
Never allocate Paint, RectF, or other objects inside onDraw() — it runs 60+ times per second and triggers GC pressure. Create all objects in the constructor or as class fields.

5. XML Layout Techniques

include — reuse layout files

<!-- Reuse a common toolbar layout -->
<include
    layout="@layout/toolbar_main"
    android:id="@+id/toolbar"
    android:layout_width="match_parent"
    android:layout_height="wrap_content" />

merge — eliminate root ViewGroup

<!-- Without merge: include adds toolbar_main's root FrameLayout into parent -->
<!-- With merge: children merge directly into include location -->
<merge xmlns:android="...">
    <!-- Children are merged into the parent container directly -->
    <TextView android:id="@+id/label" ... />
    <ImageView android:id="@+id/icon" ... />
</merge>
<!-- Use when the included layout's root type matches the parent container -->

ViewStub — lazy inflation

<!-- ViewStub: 0x0 placeholder — not inflated until needed -->
<ViewStub
    android:id="@+id/errorStub"
    android:layout="@layout/layout_error"
    android:inflatedId="@+id/errorView"
    android:layout_width="match_parent"
    android:layout_height="wrap_content" />

// Inflate on demand:
val stub = binding.errorStub
if (stub.parent != null) {  // check not already inflated
    stub.inflate()
}
// After inflation, stub is removed from hierarchy and replaced by the layout
// Ideal for error states, onboarding screens, rare UI paths
TechniqueWhen to useBenefit
includeReusing common layouts (toolbar, footer)DRY, maintainability
mergeWhen included layout root matches parentRemoves extra nesting level
ViewStubLayouts used conditionally (error, empty, overlay)Reduces initial inflation cost

6. Migration to Compose

Why Compose Replaces All of This

Legacy ProblemCompose Solution
Manual state management (setText, setVisibility)State-driven UI — recompose on state change automatically
No type safety in XML attributesPure Kotlin — compile-time type checking everywhere
Complex two-way binding with DataBindingrememberSaveable + ViewModel.uiState — simple and explicit
onMeasure/onDraw boilerplate for custom renderingCanvas in DrawScope, Modifier.drawBehind — Kotlin DSL
Nested layouts causing measure overheadIntrinsic measurements, single-pass layout

Incremental Migration Strategy

// Step 1: Add Compose to a Fragment with ComposeView
class ProductFragment : Fragment() {
    override fun onCreateView(...) = ComposeView(requireContext()).apply {
        setViewCompositionStrategy(ViewCompositionStrategy.DisposeOnViewTreeLifecycleDestroyed)
        setContent {
            MyAppTheme { ProductScreen(viewModel = hiltViewModel()) }
        }
    }
}

// Step 2: Embed legacy View in Compose with AndroidView
@Composable
fun LegacyMapView() {
    AndroidView(factory = { context -> MapView(context).apply { ... } })
}

7. Interview Framework

30-Second Answer

"For legacy XML-based UI: ViewBinding for type-safe view access (replacing kotlin synthetics which are removed), ConstraintLayout for flat hierarchies, ViewStub for lazy inflation of conditional UI. DataBinding is an option for two-way binding but I prefer ViewModel + ViewBinding due to lower complexity. Custom Views use onMeasure → onDraw with Canvas. Compose replaces all of this with state-driven, type-safe, declarative UI."

2-Minute Answer

"ViewBinding generates a typed binding class from each XML layout — fragment_product.xml becomes FragmentProductBinding. The critical Fragment pattern is nulling out the binding in onDestroyView() to prevent memory leaks since the Fragment lives longer than its View. DataBinding adds @{} XML expressions and @={} two-way binding — it works but adds build overhead and hard-to-debug XML logic; I prefer keeping logic in the ViewModel and using ViewBinding for view access. ConstraintLayout produces flat hierarchies via constraints, barriers, and chains — it's the best XML layout manager. For custom rendering, Custom Views override onMeasure (size) and onDraw (Canvas rendering) — never allocate objects in onDraw or you'll cause GC pressure during animation. ViewStub defers inflation until needed — useful for error/empty states. Compose replaces all of this: state-driven recomposition instead of manual setText/setVisibility, pure Kotlin type safety, and intrinsic measurements instead of multi-pass layout."

Must-Mention Points

1
ViewBinding: null _binding in onDestroyView() — Fragment View lifecycle is shorter than Fragment lifecycle
2
Kotlin synthetics removed in Kotlin 1.8 — ViewBinding is the replacement
3
Custom Views: no object allocation in onDraw — 60fps means Paint/RectF in constructor
4
ViewStub: lazy inflation — 0 cost until inflate() called
5
ComposeView + AndroidView — the bridge for incremental migration

Senior Insight

Senior Differentiator
Understand the View measurement system: measure() → onMeasure() → layout() → onLayout() → draw() → onDraw(). Every parent calls measure on all children before laying them out. Deeply nested layouts cause O(n²) measure passes. ConstraintLayout reduces this to O(n) by solving constraints in one pass. Compose's Intrinsics API provides similar benefits with explicit opt-in.

9. Interview Questions
1. What is ViewBinding and how does it differ from DataBinding?
Basic⌄
ViewBinding generates a typed class for each XML layout file — provides null-safe, type-safe access to views. It replaces findViewByld and Kotlin synthetics. DataBinding also generates typed classes but additionally supports @{} expressions in XML for data binding and @={} for two-way binding. ViewBinding is faster to compile (no annotation processing), simpler to debug (no XML expressions), and preferred for most cases. Use DataBinding only when two-way XML binding is genuinely needed.
2. Why must you null the binding reference in Fragment.onDestroyView()?
Basic⌄
Fragments have two lifetimes: the Fragment itself (created to destroyed) and the Fragment's View (onCreateView to onDestroyView). When the Fragment is on the back stack, its View is destroyed but the Fragment instance lives on. The binding holds references to all Views in the destroyed layout. If not nulled, this constitutes a memory leak — the Fragment keeps the entire View hierarchy alive. Always: onDestroyView() { super.onDestroyView(); _binding = null }.
3. What are the key advantages of ConstraintLayout over LinearLayout/RelativeLayout?
Basic⌄
Flat hierarchy — all views at one level, no nested containers. This reduces measure/layout passes (nested LinearLayouts require O(n²) measurement). ConstraintLayout can express any layout that would require nested LinearLayouts + RelativeLayouts in a single flat structure. Additional features: chains (spread/pack weight distribution), barriers (dynamic alignment), groups (visibility control), guidelines, and MotionLayout for animations.
4. What is ViewStub and when is it useful?
Intermediate⌄
ViewStub is a zero-size, zero-draw placeholder in the layout hierarchy. It takes up no memory or draw time until inflate() is called. On inflate, the ViewStub is replaced in the view tree by the specified layout. Useful for: error states (only shown when network fails), onboarding overlays (shown once), premium features UI (shown only to paid users), complex UI that's rarely needed. It reduces initial inflation and layout costs for these conditional views.
5. What are the lifecycle methods of a Custom View and when does each run?
Intermediate⌄
onMeasure(widthSpec, heightSpec): called by parent to determine this View's size. Must call setMeasuredDimension(). onLayout(changed, l, t, r, b): called to position children (ViewGroups only). onDraw(canvas): render the view. Called on every invalidate() — runs at 60fps during animations. invalidate(): schedules a redraw (calls onDraw). requestLayout(): schedules re-measure + re-layout + redraw. Call invalidate() for visual changes, requestLayout() when size might change.
6. Why shouldn't you allocate objects in onDraw()?
Intermediate⌄
onDraw() runs 60+ times per second during animations and scrolling. Allocating Paint, RectF, Path, or other objects in onDraw() creates thousands of objects per second. Each allocation eventually triggers garbage collection — GC pauses can cause visible jank (frame drops). Allocate all drawing objects in the constructor or as class-level fields. Reuse and update them (e.g., rect.set() instead of new RectF()). Android Lint has a "DrawAllocation" check that flags this pattern.
7. How does the merge tag work with include?
Intermediate⌄
Normally, <include> embeds the entire XML including its root ViewGroup. A <FrameLayout> wrapper in the included file becomes an extra nested view. Using <merge> as the root of the included layout tells the inflater to merge the children directly into the parent at the include insertion point — the <merge> tag itself is not a View. This removes one level of nesting. Use merge when the included layout's content type matches the parent container (e.g., including into a LinearLayout when merge contains LinearLayout children).
8. How do you incrementally migrate XML-based UI to Compose?
Senior⌄
Strategy: start with new screens in Compose, don't rewrite working screens. For existing screens: use ComposeView inside Fragment.onCreateView() — the Fragment container becomes a thin shell hosting Compose UI. Set ViewCompositionStrategy.DisposeOnViewTreeLifecycleDestroyed for correct lifecycle. Use AndroidView for embedding legacy Views that have no Compose equivalent (MapView, WebView). Gradually replace Fragment-by-Fragment, then remove Fragment dependencies as screens become fully Compose. The ViewModel layer remains untouched throughout migration.
9. When would you still write a Custom View in a Compose-first project?
Senior⌄
Custom Views are still warranted for: third-party SDKs that provide custom View subclasses (Maps, AR, camera preview), extremely complex custom rendering that's better expressed with Canvas API than Compose's DrawScope, and integration with accessibility frameworks that work better with View. In Compose, Canvas {} composable and Modifier.drawBehind cover 95% of custom drawing needs. For the remaining 5%, use AndroidView to embed the custom View in Compose with full lifecycle management.
10. What are ConstraintLayout chains and when do you use them?
Scenario⌄
A chain is a group of views linked bi-directionally. Chain styles: spread (equal spacing between views), spread_inside (equal spacing but no outer margin), packed (views clustered together with bias). Weighted chains allow LinearLayout-style weight distribution in ConstraintLayout. Use chains when multiple views share horizontal or vertical space and need to distribute it. Example: three buttons sharing the bottom of a form — create a horizontal chain with spread_inside to space them evenly without nested LinearLayout.
