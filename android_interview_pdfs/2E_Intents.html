2E — Intents

Tier 2 Explicit · Implicit · Intent Filters · PendingIntent · Deep Links · App Links

1 · Overview

An Intent is a messaging object used to request an action from another component — within your app or from the system/other apps. It is the primary mechanism for inter-component and inter-app communication on Android.

What problem it solves: Android's sandboxed process model means apps cannot call each other's code directly. Intents provide a declarative, system-mediated way to say "I want to do X" without needing to know which app or component will handle it. The OS routes the Intent to the correct recipient based on intent filters declared in the manifest.

Three uses of Intents:
  • Start an Activity (screen navigation)
  • Start or bind to a Service
  • Deliver a Broadcast (system or app-wide event)

2 · How It Works

Explicit Intent

Specifies the exact component (class) to start. Used for in-app navigation.

// Start a specific Activity in the same app
val intent = Intent(this, OrderDetailActivity::class.java).apply {
    putExtra("orderId", "ORD-123")
    putExtra("amount", 99.99)
}
startActivity(intent)

// Start a Service explicitly
val serviceIntent = Intent(this, SyncService::class.java)
startService(serviceIntent)

Implicit Intent

Does not specify a component. Declares an action; the OS resolves which app/component can handle it based on intent filters.

// Share text — OS shows chooser of apps that handle ACTION_SEND
val intent = Intent(Intent.ACTION_SEND).apply {
    type = "text/plain"
    putExtra(Intent.EXTRA_TEXT, "Check out this product!")
}
// ✅ Always check if a handler exists before starting
if (intent.resolveActivity(packageManager) != null) {
    startActivity(Intent.createChooser(intent, "Share via"))
}

// Dial a phone number
val dialIntent = Intent(Intent.ACTION_DIAL, Uri.parse("tel:+1234567890"))
startActivity(dialIntent)

Intent Filters

Declared in the manifest; tell the system what types of Intents a component can handle (for implicit Intents).

<activity android:name=".ShareReceiverActivity" android:exported="true">
    <intent-filter>
        <action android:name="android.intent.action.SEND" />
        <category android:name="android.intent.category.DEFAULT" />
        <data android:mimeType="text/plain" />
    </intent-filter>
</activity>

PendingIntent

A PendingIntent is a token that grants another app (Notification system, AlarmManager, widget host) the ability to fire your Intent at a future time, with your app's permissions and identity — even if your app is not running.

Your App Android System Notification Manager │ │ │ ├─ createPendingIntent ──────────────────────►│ │ (stores Intent + your identity) │ │ │ │ │ [User taps notification] │ │ │◄───────────────────────┤ │ │ fires PendingIntent │ ├◄───────────────────┤ │ │ Activity started with your permissions │
// PendingIntent for notification tap — API 31+ requires FLAG_IMMUTABLE or FLAG_MUTABLE
val intent = Intent(this, OrderDetailActivity::class.java).apply {
    putExtra("orderId", orderId)
    flags = Intent.FLAG_ACTIVITY_SINGLE_TOP
}
val pendingIntent = PendingIntent.getActivity(
    context,
    orderId.hashCode(),       // requestCode — uniquely identifies this PendingIntent
    intent,
    PendingIntent.FLAG_UPDATE_CURRENT or PendingIntent.FLAG_IMMUTABLE
)

// Use in Notification
NotificationCompat.Builder(context, CHANNEL_ID)
    .setContentIntent(pendingIntent)
    .setAutoCancel(true)
    .

3 · Why and When to Use Each

TypeUse when…Do NOT use when…
Explicit Intent In-app navigation between known components; starting your own Service Cross-app actions where you don't know the target — use implicit
Implicit Intent System actions (share, dial, map, camera); letting user choose which app handles the action In-app navigation — use explicit (security risk to expose your internals)
PendingIntent Notifications, AlarmManager, widgets — any deferred Intent fired by another process Immediate in-app navigation — use startActivity() directly
Deep Link Custom URL scheme for your app; marketing links; sharing app content When you need guaranteed single-app routing — use App Links
App Link HTTPS links that should always open your app (no chooser); bank account links; purchase confirmations If you can't serve the verification JSON at the domain — use deep link

4 · Production Example (Banking App)

FCM Notification with PendingIntent + TaskStackBuilder

// Notification for incoming payment — tap opens TransactionDetailActivity
// with correct back stack (Home → Transactions → Detail)
fun buildPaymentNotification(context: Context, txId: String): Notification {
    // TaskStackBuilder creates synthetic back stack for notification deep link
    val pendingIntent = TaskStackBuilder.create(context).apply {
        addNextIntentWithParentStack(
            Intent(context, TransactionDetailActivity::class.java).apply {
                putExtra("transactionId", txId)
            }
        )
    }.getPendingIntent(
        txId.hashCode(),
        PendingIntent.FLAG_UPDATE_CURRENT or PendingIntent.FLAG_IMMUTABLE
    )

    return NotificationCompat.Builder(context, CHANNEL_PAYMENTS)
        .setSmallIcon(R.drawable.ic_payment)
        .setContentTitle("Payment received")
        .setContentText("Transaction #$txId")
        .setContentIntent(pendingIntent)
        .setAutoCancel(true)
        .build()
}

App Links — HTTPS Deep Link Handling

// Manifest: android:autoVerify="true" + HTTPS scheme + your domain
// Server: /.well-known/assetlinks.json must return your app's SHA256 fingerprint

// In Activity (or Navigation Component handles this automatically)
override fun onCreate(savedInstanceState: Bundle?) {
    super.onCreate(savedInstanceState)
    val action = intent.action
    val data = intent.data

    if (Intent.ACTION_VIEW == action && data != null) {
        when {
            data.path?.startsWith("/account") == true -> navigateToAccount()
            data.path?.startsWith("/transactions") == true -> {
                val txId = data.lastPathSegment
                navigateToTransaction(txId)
            }
        }
    }
}

// With Navigation Compose — declare deep links in NavGraph instead
composable(
    route = "transaction/{id}",
    deepLinks = listOf(navDeepLink {
        uriPattern = "https://mybank.com/transactions/{id}"
    })
) { backStackEntry ->
    val id = backStackEntry.arguments?.getString("id")
    TransactionDetailScreen(id)
}

Implicit Intent — Share Bank Statement

fun shareStatement(fileUri: Uri) {
    val intent = Intent(Intent.ACTION_SEND).apply {
        type = "application/pdf"
        putExtra(Intent.EXTRA_STREAM, fileUri)
        // Grant temporary read permission to the receiving app
        addFlags(Intent.FLAG_GRANT_READ_URI_PERMISSION)
    }
    // ✅ Use createChooser — always show picker even if one app handles it
    startActivity(Intent.createChooser(intent, "Share statement"))
}

6 · Pitfalls and Best Practices

Implicit Intent with No Handler — Crash

❌ Bad — ActivityNotFoundException

// On devices without an email app — crashes
val intent = Intent(Intent.ACTION_SENDTO)
intent.data = Uri.parse("mailto:support@bank.com")
startActivity(intent)  // CRASH if no handler

✅ Good — check first

val intent = Intent(Intent.ACTION_SENDTO)
intent.data = Uri.parse("mailto:support@bank.com")
if (intent.resolveActivity(packageManager) != null) {
    startActivity(intent)
} else {
    showToast("No email app found")
}

PendingIntent — Missing FLAG_IMMUTABLE (API 31+)

API 31+ requires PendingIntent to explicitly specify FLAG_IMMUTABLE or FLAG_MUTABLE. Omitting this throws IllegalArgumentException. Almost always use FLAG_IMMUTABLE unless the PendingIntent needs to be modified by the receiving app (e.g. Android Auto inline replies).

Other Critical Pitfalls

  • Passing large objects via Intent extras: Intents go through the Binder IPC buffer (1 MB limit). Passing large Bitmaps or lists causes TransactionTooLargeException. Pass IDs and load data in the target component.
  • Receiving implicit Intents in unexported components: On API 31+, any component with an intent-filter must declare android:exported="true|false" explicitly or the app won't install.
  • Not using FLAG_GRANT_READ_URI_PERMISSION: When sharing files via FileProvider, the receiving app needs temporary permission to read the URI. Missing this causes permission denied on the target app.
  • Deep link not handled after process death: If the Activity is killed and relaunched via a deep link, intent.data must be parsed in onCreate — not just in onNewIntent. Both paths must be handled.
  • PendingIntent requestCode collision: Using the same requestCode for different PendingIntents causes FLAG_UPDATE_CURRENT to overwrite the previous one's extras. Use unique requestCodes (e.g., notification ID or entity ID hashCode).
Security best practice for implicit Intents received: Validate all data received via Intent. An implicit Intent can be sent by any app. Never trust extras without validation — especially in components marked android:exported="true".

7 · Interview Answer Framework

30-Second Answer

"Intents are the messaging system for starting Android components. Explicit Intents specify the exact component — used for in-app navigation. Implicit Intents declare an action and let the OS find an app to handle it — used for share, dial, open URL. PendingIntent wraps an Intent with your app's identity and permissions so another process can fire it later — used for notifications, AlarmManager, widgets. Deep links and App Links let external URLs open specific screens, with App Links requiring HTTPS domain verification to avoid the disambiguation chooser."

2-Minute Structured Answer

Explicit vs Implicit: Explicit Intent targets a specific class — used for in-app navigation. Implicit Intent declares an action (ACTION_SEND, ACTION_VIEW) — the OS resolves it via intent filters in the manifest. Always check resolveActivity() before firing an implicit Intent to avoid ActivityNotFoundException.

Intent filters: Declared in manifest; specifies what action + category + data MIME type a component can handle. For security, components that should not be accessed externally must be android:exported="false".

PendingIntent: A deferred Intent that another process (notification manager, alarm manager) can fire with your app's identity. API 31+ requires FLAG_IMMUTABLE or FLAG_MUTABLE explicitly. Use TaskStackBuilder to create a proper back stack when the PendingIntent opens a deep-linked screen.

Deep links vs App Links: Deep links use custom schemes or HTTPS but may show a chooser if multiple apps match. App Links use HTTPS with domain verification via assetlinks.json — no chooser, opens your app directly. For production push notification flows and marketing links, I always implement App Links.

Must-Mention Points

  1. Explicit (known component) vs Implicit (declared action, OS resolves).
  2. Intent filters in manifest — how implicit Intent routing works.
  3. PendingIntent — deferred Intent, fired by another process, carries your identity.
  4. FLAG_IMMUTABLE required on API 31+ for PendingIntent.
  5. TransactionTooLargeException — never pass large data via extras; pass IDs.
  6. Deep link vs App Link — HTTPS verification, no chooser with App Links.
  7. TaskStackBuilder for synthetic back stack on notification deep links.
  8. Always validate data received via exported components — any app can send Intents.

9 · Interview Questions (Self-Check)

Basic What is the difference between an explicit and an implicit Intent?
Explicit Intent specifies the exact component (Activity/Service class name) to start. Used for in-app navigation. Implicit Intent specifies an action (e.g. ACTION_SEND) and optional data type/category. The OS resolves which app/component can handle it based on manifest intent-filters. The system shows a chooser if multiple apps match.
Basic What is a PendingIntent and when is it used?
A PendingIntent is a token wrapping an Intent that grants another process the ability to execute it with your app's permissions, even when your app is not running. Used for: notification taps (NotificationCompat), scheduled alarms (AlarmManager), widget interactions, and deferred system actions. API 31+ requires FLAG_IMMUTABLE or FLAG_MUTABLE explicitly.
Basic What happens if you try to start an implicit Intent with no handler?
ActivityNotFoundException is thrown at runtime, crashing the app. Fix: always call intent.resolveActivity(packageManager) first and handle the null case gracefully. Note: On Android 11+ (API 30), resolveActivity() requires a <queries> element in the manifest for non-system apps to be visible.
Intermediate What is the difference between a deep link and an App Link?
Deep link: any URI scheme (custom myapp:// or https://). No domain verification. The OS may show a disambiguation chooser if multiple apps match. Simple to implement.
App Link: HTTPS URI only. Requires digital asset links verification — a JSON file at https://domain/.well-known/assetlinks.json that contains your app's SHA256 signing certificate. On verified devices, the OS opens your app directly with no chooser. Required: android:autoVerify="true" in the intent-filter.
Intermediate Why do you use TaskStackBuilder for notification PendingIntents?
When a user taps a notification that opens a deep screen (e.g. TransactionDetailActivity), the app may not have a back stack. Without TaskStackBuilder, pressing Back would exit the app instead of going to the expected parent screen. TaskStackBuilder.create(context).addNextIntentWithParentStack(targetIntent) constructs a synthetic back stack based on the Activity's parentActivityName in the manifest. This creates the full stack [HomeActivity → TransactionsActivity → TransactionDetailActivity] even if the app was cold-started from the notification.
Intermediate What security risk exists with exported Activities that have intent-filters?
Any app on the device can send an Intent to any exported component. If your exported Activity reads Intent extras and uses them (SQL queries, file paths, URLs), a malicious app can send crafted extras to cause SQL injection, path traversal, or open unintended URLs (deep link hijacking). Fix: always validate and sanitize data received from Intents. Use android:permission to restrict access. Keep non-public components exported="false". Audit all intent-filter declarations.
Intermediate What is FLAG_GRANT_READ_URI_PERMISSION and when is it needed?
When you share a file via FileProvider (content:// URI), the receiving app doesn't normally have permission to read from your app's content provider. FLAG_GRANT_READ_URI_PERMISSION grants the target app temporary read access to that specific URI. Without it, the receiving app gets "Permission Denied". Used in ACTION_SEND with EXTRA_STREAM for file sharing, and when opening files in third-party viewers.
Senior/Scenario [Scenario] Your FCM notification deep link opens the correct screen but pressing Back takes the user to an empty app/Home screen instead of the expected parent screens. How do you fix it?
Use TaskStackBuilder to construct a proper back stack for the notification PendingIntent. Declare parentActivityName in the manifest for each Activity's logical parent.
// Manifest
<activity android:name=".TransactionDetailActivity"
          android:parentActivityName=".TransactionsListActivity" />

// PendingIntent creation
val pendingIntent = TaskStackBuilder.create(context).apply {
    addNextIntentWithParentStack(
        Intent(context, TransactionDetailActivity::class.java)
            .putExtra("txId", txId)
    )
}.getPendingIntent(
    txId.hashCode(),
    PendingIntent.FLAG_UPDATE_CURRENT or PendingIntent.FLAG_IMMUTABLE
)
Now pressing Back from TransactionDetailActivity goes to TransactionsListActivity (which goes to HomeActivity), matching the expected navigation flow.
Senior/Scenario [Coding] Implement file sharing via FileProvider in a banking app (share PDF statement). 
// 1. Provider declared in manifest
<provider
    android:name="androidx.core.content.FileProvider"
    android:authorities="com.mybank.app.fileprovider"
    android:exported="false"
    android:grantUriPermissions="true">
    <meta-data
        android:name="android.support.FILE_PROVIDER_PATHS"
        android:resource="@xml/file_paths" />
</provider>

// 2. res/xml/file_paths.xml
// <files-path name="statements" path="statements/" />

// 3. Sharing code
fun shareStatement(statementFile: File) {
    val uri = FileProvider.getUriForFile(
        context,
        "com.mybank.app.fileprovider",
        statementFile
    )
    val intent = Intent(Intent.ACTION_SEND).apply {
        type = "application/pdf"
        putExtra(Intent.EXTRA_STREAM, uri)
        addFlags(Intent.FLAG_GRANT_READ_URI_PERMISSION)  // ✅ critical
    }
    context.startActivity(Intent.createChooser(intent, "Share statement"))
}
Senior/Scenario [Debug] Your app crashes with TransactionTooLargeException when navigating to a product detail screen. What is the root cause and fix?
Root cause: An oversized object (likely a Bitmap, large List, or Parcelable with many fields) is being passed via Intent extras. Intent extras are transmitted through the Binder IPC buffer which has a ~1 MB limit across the entire transaction queue.

Fix: Never pass large objects via Intent extras. Pass only an ID or key and load the data in the destination:
// ❌ Bad
intent.putExtra("product", product)  // large Parcelable

// ✅ Good — pass only the ID
intent.putExtra("productId", product.id)
// Load full product in destination ViewModel using the ID
For shared ViewModel patterns (single-activity), the data is already in memory — no need to pass it via Intent at all.
