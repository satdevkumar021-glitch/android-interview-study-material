19C — Secrets & API Key Security

How to protect API keys, secrets, and credentials in Android apps — local.properties, BuildConfig fields, secrets-gradle-plugin, server-side proxying, and why no client-side approach is truly secure.

ID: 19C ⭐ Tier 1 🔥 Hot
🔒
1. Overview

The single most critical reality of mobile application security is that Android client applications are inherently untrusted environments. Any compiled APK or Android App Bundle (AAB) distributed to end users can be disassembled, decompiled, and analyzed using standard reverse-engineering tools like jadx, apktool, and dex2jar in under 5 minutes.

Consequently, no secret, private key, or credential embedded within an Android APK is safe from extraction. The goal of client-side secret management is not to achieve impossible mathematical secrecy on the device, but rather to:

  1. Prevent Source Code & Git Repository Leaks: Ensure keys never get committed to public or private version control systems.
  2. Enforce Defense-in-Depth & Blast Radius Reduction: Restrict client-embedded keys using provider-level policies (e.g., Google Cloud SHA-1 and package name restrictions).
  3. Architect Zero-Trust Systems: Proxy all high-value, billed, or privileged API interactions through your own authenticated backend gateway.

4 Approaches Ranked by Security

Rank Approach Security Rating Git Leak Safe? APK Decompile Safe? Recommended For
1 (Best) Server-Side Key Proxying 🟢 Absolute (Gold Standard) ✅ Yes ✅ Yes (Key never touches device) Billed APIs (OpenAI, Stripe, Twilio), database credentials, private keys
2 Runtime Dynamic Key Fetching + App Attestation 🟡 Moderate to High ✅ Yes ⚠️ High effort to hook memory / MITM Third-party SDKs requiring client-side tokens (Firebase App Check, Auth tokens)
3 local.properties + secrets-gradle-plugin 🟠 Low (Git-safe only) ✅ Yes ❌ No (Compiled directly into APK) Client-only SDK keys with strict provider restrictions (Google Maps, Analytics)
4 (Worst) Hardcoding in Source / strings.xml 🔴 Zero Security ❌ Instant leak in git ❌ Extracted in seconds via apktool NEVER USE UNDER ANY CIRCUMSTANCES
The Fundamental Axiom
There is no way to truly hide a secret in an Android app that a determined attacker cannot extract. The only truly secure approach is to never put the secret in the app — proxy all API calls through your backend.

2. The Wrong Ways

These anti-patterns are frequently found in flawed codebases and represent critical security vulnerabilities during senior engineering interviews.

1. Hardcoding Keys in Kotlin/Java Source

// ❌ WRONG: Committed directly to Git, plainly visible in decompiled DEX bytecode
object ApiConstants {
    const val STRIPE_SECRET_KEY = "sk_live_51Nz8ABC1234567890XYZ"
}

Decompilation Command: jadx app-release.apk immediately indexes strings and reveals the key across all class decompilations.

2. Storing Keys in res/values/strings.xml

<!-- ❌ WRONG: Packaged in compiled resources.arsc -->
<resources>
    <string name="api_key">AIzaSyD-ABC1234567890_XYZ</string>
</resources>

Decompilation Command: apktool d app-release.apk && cat app-release/res/values/strings.xml | grep api_key extracts the key in under 3 seconds.

3. Hardcoding in build.gradle.kts buildConfigField

// ❌ WRONG: Plaintext secret committed to build scripts and generated into BuildConfig.java
android {
    defaultConfig {
        buildConfigField("String", "OPENAI_KEY", "\"sk-proj-abc123456\"")
    }
}

4. "Security Through Obscurity": Base64, XOR, or C++ NDK (JNI)

// ❌ WRONG: Trivial to reverse-engineer or hook at runtime
external fun getNativeKey(): String

// Inside native-lib.cpp:
// JNIEXPORT jstring JNICALL Java_com_app_getNativeKey(JNIEnv *env, jobject) {
//     return env->NewStringUTF("sk_live_secret123");
// }

Decompilation Command: Running strings libnative-lib.so | grep sk_ exposes raw strings immediately. If encrypted inside C++, dynamic instrumentation frameworks like Frida can hook getNativeKey() and intercept the return value with one line of JavaScript.

5. Storing Secrets in assets/ Folder

// ❌ WRONG: Plaintext JSON/property files inside APK zip package
val configJson = context.assets.open("credentials.json").bufferedReader().use { it.readText() }

Decompilation Command: unzip -p app-release.apk assets/credentials.json dumps credentials without any reverse-engineering tools.

3. local.properties Approach

The local.properties file is located in the project root directory and is excluded from Git version control by default in standard Android project .gitignore files. This makes it an ideal repository for developer-machine keys to prevent accidental Git leaks.

1. Define Key in local.properties

# local.properties (Ignored by Git)
sdk.dir=/Users/developer/Library/Android/sdk
MAPS_API_KEY=AIzaSyD-YOUR_ACTUAL_DEV_KEY_12345

2. Read and Inject into BuildConfig via build.gradle.kts

import java.util.Properties
import java.io.FileInputStream

plugins {
    id("com.android.application")
    id("org.jetbrains.kotlin.android")
}

// Load local.properties safely
val localProperties = Properties().apply {
    val localPropertiesFile = rootProject.file("local.properties")
    if (localPropertiesFile.exists()) {
        load(FileInputStream(localPropertiesFile))
    }
}

android {
    namespace = "com.example.secureapp"
    compileSdk = 34

    defaultConfig {
        // Priority: 1. CI/CD Environment Variable -> 2. local.properties -> 3. Fallback dummy
        val mapsKey = System.getenv("MAPS_API_KEY")
            ?: localProperties.getProperty("MAPS_API_KEY")
            ?: ""

        buildConfigField("String", "MAPS_API_KEY", "\"$mapsKey\"")
    }

    buildFeatures {
        buildConfig = true
    }
}

3. Access in Kotlin Code

class MapInitializer @Inject constructor() {
    fun initMap() {
        val apiKey = BuildConfig.MAPS_API_KEY
        // Use apiKey for Maps SDK setup
    }
}
Security Scope of local.properties
What local.properties achieves: Prevents secrets from being committed into Git repositories, public pull requests, and commit logs.
What local.properties does NOT achieve: Protection against APK decompilation. The injected key still compiles directly into the BuildConfig.class bytecode inside the final release APK.

4. secrets-gradle-plugin

Google developed the Secrets Gradle Plugin for Android (com.google.android.libraries.mapsplatform.secrets-gradle-plugin) to streamline reading secrets from local.properties and injecting them into both BuildConfig and AndroidManifest.xml placeholders without writing manual Groovy/Kotlin parsing scripts.

1. Setup in Root & App build.gradle.kts

// build.gradle.kts (Root Project)
plugins {
    id("com.google.android.libraries.mapsplatform.secrets-gradle-plugin") version "2.0.1" apply false
}

// build.gradle.kts (Module: app)
plugins {
    id("com.android.application")
    id("org.jetbrains.kotlin.android")
    id("com.google.android.libraries.mapsplatform.secrets-gradle-plugin")
}

secrets {
    // Point to a defaults file committed to git with empty or mock values
    defaultPropertiesFileName = "secrets.defaults.properties"
    // Point to the gitignored file containing actual production/dev keys
    propertiesFileName = "local.properties"
    // Ignore specific keys if you don't want them in BuildConfig
    ignoreList.add("sdk.dir")
}

2. Injecting into AndroidManifest.xml

Certain SDKs like Google Maps require keys to be declared directly in the manifest via <meta-data>:

<!-- AndroidManifest.xml -->
<application>
    <meta-data
        android:name="com.google.android.geo.API_KEY"
        android:value="${MAPS_API_KEY}" />
</application>

5. Server-Side Key Proxying

Server-Side Key Proxying is the industry-standard architecture for securing API keys. In this pattern, the Android client never possesses the secret third-party API key. Instead, the mobile app communicates exclusively with your own backend gateway, which validates the client request and forwards it to the third-party service using credentials stored in secure server-side vaults.

Architecture Workflow

┌─────────────────┐       1. Request + User JWT       ┌──────────────────────┐       3. Forward Request       ┌──────────────────┐
│                 │      + Play Integrity Token       │                      │      + Server-Side Secret      │                  │
│  Android Client ├──────────────────────────────────►│  Your Backend Proxy  ├───────────────────────────────►│ Third-Party API   │
│                 │                                   │                      │                                │ (OpenAI/Stripe)  │
│                 │◄──────────────────────────────────┤  (AWS / GCP Gateway) │◄───────────────────────────────┤                  │
└─────────────────┘       5. Filtered Response        └──────────┬───────────┘       4. API Response          └──────────────────┘
                                                                 │
                                                       2. Verify Integrity
                                                       & Rate Limit User
                                                                 ▼
                                                      ┌──────────────────────┐
                                                      │  Google Play Verify  │
                                                      │  / AWS Secrets Mgr   │
                                                      └──────────────────────┘

Key Capabilities of Server-Side Proxying

  • Zero Client Secrets: The third-party API key (e.g., Stripe secret, OpenAI API key) resides strictly on the server (e.g., AWS Secrets Manager or GCP Secret Manager).
  • Instant Zero-Downtime Rotation: If a key needs to be rotated or refreshed, it is updated on the server instantly without requiring a new APK release or waiting for users to update.
  • Granular Rate Limiting & Quota Enforcement: The backend can enforce per-user rate limits, billing quotas, and fraud detection algorithms before invoking paid upstream APIs.
  • App Integrity Gating (Play Integrity API): The backend verifies that incoming requests originate from a genuine, untampered app installed from Google Play on a non-rooted, certified Android device.
  • Request & Response Sanitization: The backend strips sensitive upstream internal headers and only returns data fields necessary for the mobile UI.
Production Rule of Thumb
For any API that has per-call billing (Google Maps Places API, OpenAI, Stripe, Twilio) or accesses privileged user data, server-side proxying is the only acceptable production approach. The backend cost of running a thin proxy is negligible compared to the financial and security cost of a leaked API key being abused by bots.

6. Runtime Key Fetching

In scenarios where a third-party SDK strictly requires client-side initialization (e.g., real-time streaming SDKs, mapping renderers), you should avoid hardcoding long-lived static keys. Instead, implement Runtime Ephemeral Key Fetching.

Architecture & Lifecycle

  1. The app authenticates the user and fetches a short-lived, scoped session token from your backend at runtime.
  2. The token is pinned using OkHttp Certificate Pinning to prevent Man-In-The-Middle (MITM) proxy interception.
  3. The token is held strictly in volatile RAM memory (never persisted to plaintext disk or SharedPreferences).
  4. If persistent caching across app restarts is mandatory, the token is encrypted using EncryptedSharedPreferences backed by the Android Keystore hardware.

Complete Implementation: Secure Ephemeral Key Manager

import android.content.Context
import androidx.security.crypto.EncryptedSharedPreferences
import androidx.security.crypto.MasterKey
import kotlinx.coroutines.sync.Mutex
import kotlinx.coroutines.sync.withLock
import javax.inject.Inject
import javax.inject.Singleton

data class SessionKey(
    val token: String,
    val expiresAtEpochMs: Long
)

@Singleton
class SecureKeyManager @Inject constructor(
    private val context: Context,
    private val authApiService: AuthApiService
) {
    private val mutex = Mutex()
    @Volatile
    private var inMemoryKey: SessionKey? = null

    private val encryptedPrefs by lazy {
        val masterKey = MasterKey.Builder(context)
            .setKeyScheme(MasterKey.KeyScheme.AES256_GCM)
            .build()

        EncryptedSharedPreferences.create(
            context,
            "secure_ephemeral_keys",
            masterKey,
            EncryptedSharedPreferences.PrefKeyEncryptionScheme.AES256_SIV,
            EncryptedSharedPreferences.PrefValueEncryptionScheme.AES256_GCM
        )
    }

    suspend fun getValidApiKey(): String = mutex.withLock {
        val currentTime = System.currentTimeMillis()

        // 1. Check in-memory cache
        inMemoryKey?.let {
            if (it.expiresAtEpochMs > currentTime + 60_000) {
                return it.token
            }
        }

        // 2. Check Keystore-backed encrypted storage
        val cachedToken = encryptedPrefs.getString("temp_token", null)
        val expiry = encryptedPrefs.getLong("token_expiry", 0L)
        if (cachedToken != null && expiry > currentTime + 60_000) {
            inMemoryKey = SessionKey(cachedToken, expiry)
            return cachedToken
        }

        // 3. Fetch fresh short-lived key from authenticated backend gateway
        val response = authApiService.fetchShortLivedSdkToken()
        val newKey = SessionKey(response.token, response.expiresAtEpochMs)

        inMemoryKey = newKey
        encryptedPrefs.edit()
            .putString("temp_token", newKey.token)
            .putLong("token_expiry", newKey.expiresAtEpochMs)
            .apply()

        return newKey.token
    }

    fun clearKeys() {
        inMemoryKey = null
        encryptedPrefs.edit().clear().apply()
    }
}

7. Pitfalls & Attack Vectors
Attack Vector 1: Git History Leaks
Problem: A developer accidentally commits a secret key to Git, realizes the mistake in the next commit, and removes it. The key remains permanently visible in the repository's .git/ commit history.
Remediation:
  1. Immediately Revoke and Rotate the Key: Treat the key as completely compromised.
  2. Scrub Repository History: Use git-filter-repo or BFG Repo-Cleaner to rewrite history before pushing.
  3. Install Pre-Commit Hooks: Enforce tools like git-secrets or trufflehog in local and CI pipelines.
Attack Vector 2: Unmasked Secrets in CI/CD Logs
Problem: Gradle build scripts or test runners print command line arguments or environment variables into build console logs.
Remediation: In GitHub Actions or GitLab CI, always use native secret masking (e.g. ::add-mask::$SECRET_KEY) and inject keys via repository secret managers rather than shell arguments.
Attack Vector 3: Logcat Leakage in Release Builds
Problem: Calling Log.d(TAG, "Request auth: $apiKey") or logging full HTTP headers via OkHttp HttpLoggingInterceptor.Level.BODY in production logs keys to system logcat.
Remediation: Use Timber with a custom DebugTree enabled strictly when BuildConfig.DEBUG == true. Configure ProGuard/R8 to strip all standard logging calls: 
-assumenosideeffects class android.util.Log {
    public static boolean isLoggable(java.lang.String, int);
    public static int v(...);
    public static int d(...);
}
Attack Vector 4: Unrestricted Cloud API Keys
Problem: Using an unrestricted Google Cloud or Firebase API key. Anyone who extracts the key from your APK can use it to query any Google Cloud API on your billing account.
Remediation: In Google Cloud Console, apply two-tier key restrictions:
  1. Application Restriction: Restrict usage strictly to Android apps matching your exact Package Name and SHA-1 Signing Certificate Fingerprint.
  2. API Restriction: Restrict key usage exclusively to the specific API needed (e.g. "Maps SDK for Android" only).
Attack Vector 5: ADB Backup Extraction
Problem: If android:allowBackup="true" is enabled, an attacker with physical or USB debugging access can run adb backup to extract private internal storage files and unencrypted SharedPreferences.
Remediation: Set android:allowBackup="false" in AndroidManifest.xml or explicitly exclude sensitive preferences files via android:fullBackupContent.

8. Interview Framework

30-Second Elevator Pitch

"In Android, no client-side secret is ever truly secure against reverse engineering because APK bytecode and resources can be decompiled in minutes. For client-required keys like Google Maps, we keep keys out of Git using local.properties and secrets-gradle-plugin, while restricting the key in Google Cloud Console using our app's Package Name and SHA-1 certificate fingerprint. For high-value, billed, or sensitive APIs like Stripe, OpenAI, or private databases, the gold standard is Server-Side Key Proxying combined with Play Integrity API attestation so the Android device never holds the secret key."

2-Minute Deep Dive

"When designing an API key strategy, we categorize secrets into two threat models:

1. Client-Mandatory Public Keys (Maps, Analytics): These must be included in the APK. We prevent source control leaks by loading them from local.properties at build time. To prevent abuse when the key is extracted from the APK, we configure strict provider restrictions in the cloud console—limiting requests strictly to our production release SHA-1 certificate and application package name.

2. Sensitive Private Secrets (Billed APIs, Auth, Payments): These must NEVER exist on the client. We implement a backend proxy architecture. The mobile app requests an attestation verdict from Google's Play Integrity API to prove it is a genuine, untampered build. The backend validates this verdict, applies rate limiting per user ID, and injects the actual API secret stored in AWS Secrets Manager before forwarding the request to the upstream provider.

If temporary client tokens are required, we fetch them at runtime over TLS with Certificate Pinning, hold them in memory, and optionally cache them in EncryptedSharedPreferences backed by Android Keystore hardware."

Must-Mention Points

1
Zero Client-Side Secrecy: Decompilation (jadx, apktool) and memory hooking (Frida) make client secrets discoverable.
2
Server-Side Key Proxying: The only 100% secure architecture for billed and sensitive third-party services.
3
Git Safety with local.properties: Keeps developer credentials out of version control and CI repositories.
4
Provider Restrictions (SHA-1 + Package Name): Limits blast radius of client-embedded Google Cloud API keys.
5
Play Integrity API: Gates backend API proxy access to verified, non-rooted, untampered app instances.
6
Incident Response: Immediate key revocation and rotation upon leak, followed by Git history scrubbing with git-filter-repo.

Follow-up Q&A Reference

Follow-up Question Key Takeaway
"Does NDK C++ make keys safe?" No. Running strings libnative.so reveals plaintext strings immediately. Even with XOR encryption, Frida can hook the native JNI method and intercept the decrypted return value.
"How do SHA-1 restrictions work for Google Maps?" Google's backend checks the caller's TLS connection metadata and app signature bundle. Requests without matching package name and signing certificate SHA-1 are rejected with HTTP 403.
"What is the difference between Play Integrity and Firebase App Check?" Play Integrity is Google's core device and app attestation API. Firebase App Check wraps Play Integrity (along with DeviceCheck and SafetyNet) to provide turn-key gating for Firebase and custom backend endpoints.
Senior Signal
A staff-level engineer never claims they can "encrypt keys in C++ to make them uncrackable." Instead, they articulate realistic threat models, explain defense-in-depth, demonstrate how to proxy requests through a secure backend, and implement provider-level restrictions to minimize the blast radius.

9. Interview Questions
1. Why is hardcoding API keys in Android source code dangerous even if ProGuard/R8 obfuscation is enabled?
Easy ▾

ProGuard and R8 obfuscate class names, field names, and method identifiers (e.g. renaming ApiKeyManager.getSecret() to a.b()). However, R8 does not encrypt or obfuscate string literals. String literals remain stored as cleartext UTF-8 entries in the string_ids pool of the compiled classes.dex file.

Anyone running jadx, dex2jar, or the unix command strings classes.dex | grep -E "(sk_|key_)" can extract the key in seconds. Furthermore, hardcoding keys in source code commits them to version control, making them vulnerable to Git repository leaks.

2. How does storing secrets in local.properties improve security, and what are its primary limitations?
Easy ▾

Security Improvement:

  • local.properties is excluded from version control by .gitignore, preventing keys from leaking into public Git repositories, branch diffs, commit histories, and pull requests.
  • Enables different developers and CI/CD pipelines to supply distinct API keys for debug, staging, and production environments.

Primary Limitation:

  • When Gradle reads local.properties and injects it via buildConfigField, the key value is hardcoded into the generated BuildConfig.class.
  • The compiled APK still contains the plaintext string, making it trivial to extract by decompiling the released APK. It solves Git leaks, not APK reverse engineering.
3. What does Google's secrets-gradle-plugin do, and when is it appropriate to use?
Medium ▾

secrets-gradle-plugin is an official Gradle plugin that automates reading key-value pairs from local.properties (or custom property files) and exposing them seamlessly to:

  1. BuildConfig fields in Kotlin/Java.
  2. AndroidManifest.xml placeholders using ${PROPERTY_NAME} syntax.

It provides a standardized configuration block, supports default fallback property files (secrets.defaults.properties), and avoids custom Groovy/Kotlin parsing code. It is appropriate for non-sensitive client SDK keys (like Google Maps SDK, Firebase Analytics) that must be present in the manifest and can be constrained with cloud-level SHA-1 restrictions.

4. What is Server-Side Key Proxying, and why is it considered the gold standard for high-value API keys?
Medium ▾

Server-Side Key Proxying routes all requests through your own backend server instead of having the mobile app communicate directly with third-party APIs. The secret API keys are stored exclusively in secure server-side vaults (e.g. AWS Secrets Manager, GCP Secret Manager) and never touch the mobile device.

Why it is the Gold Standard:

  • Zero Secret Exposure: Attackers cannot extract keys from the APK because they simply do not exist on the device.
  • Instant Key Rotation: If a key is compromised, you can rotate it on the server within seconds without publishing a new app release.
  • Abuse Prevention: The backend authenticates the user, validates app integrity (via Play Integrity API), and enforces per-user rate limits and billing quotas before calling expensive third-party APIs.
5. How can you restrict Google API keys (like Google Maps) if they must be included in the Android APK?
Medium ▾

In the Google Cloud Console, you configure two types of restrictions for the API key:

  1. Application Restrictions: Set to "Android apps" and add allowed package name and SHA-1 certificate fingerprint pairs:
    • Add the Debug keystore SHA-1 (keytool -list -v -keystore ~/.android/debug.keystore) for development builds.
    • Add the Production Release Keystore SHA-1 (or the Google Play App Signing key certificate SHA-1 if Play Signing is enabled).
  2. API Restrictions: Restrict the key exclusively to the APIs required (e.g. "Maps SDK for Android" only, blocking Places API, Geocoding API, and compute services).

Even if an attacker extracts the key from your APK, Google's servers will reject any request not originating from your signed application package.

6. How do you use the Play Integrity API together with a backend proxy to protect API access?
Hard ▾

End-to-End Workflow:

  1. Nonce Generation: The mobile app requests a cryptographically secure random nonce from your backend server.
  2. Integrity Request: The app invokes IntegrityManager.requestIntegrityToken(), passing the backend nonce and Google Cloud project number.
  3. Token Submission: The Play Integrity SDK communicates with Google Play services and returns an encrypted integrity token. The app sends this token alongside its business request to your backend.
  4. Server-Side Decryption & Validation: Your backend decrypts the token via Google's Play Integrity API and verifies:
    • appLicensingVerdict == LICENSED
    • appRecognitionVerdict == PLAY_RECOGNIZED and packageName / certificateSha256Digests match your official app.
    • deviceRecognitionVerdict satisfies MEETS_DEVICE_INTEGRITY (non-rooted, passed CTS checks).
    • The returned nonce matches the session nonce issued in step 1 (prevents replay attacks).
  5. Proxy Execution: If the verdict passes, the backend executes the third-party API call using its private credentials and returns the response.
7. An API key was accidentally committed to a public Git repository. What are the immediate and permanent remediation steps?
Hard ▾

Step-by-Step Remediation:

  1. Immediate Revocation & Rotation (Day 0): Immediately log in to the third-party service provider (AWS, Stripe, OpenAI) and revoke the compromised key. Generate a new key and deploy it. Simply deleting the file in a new Git commit does not revoke the active key.
  2. Audit Usage Logs: Inspect access and billing logs for the leaked key to identify unauthorized API calls, data breaches, or billing spikes.
  3. Scrub Git Repository History: Use git-filter-repo or BFG Repo-Cleaner to permanently purge the file containing the secret from all commits, tags, and reflogs across all branches: 
    git-filter-repo --invert-paths --path path/to/secret_file.properties --force
  4. Force Push & Invalidate Remote Caches: Force-push rewritten branches (git push origin --force --all) and contact GitHub/GitLab support to purge orphan commit caches.
  5. Implement Preventative CI Gating: Install pre-commit hooks (e.g. pre-commit with detect-secrets or trufflehog) and enable GitHub Secret Scanning to block future secret pushes automatically.
8. Design a complete zero-trust defense-in-depth secret management strategy for a high-security banking/fintech Android application.
Hard ▾

A comprehensive zero-trust architecture incorporates defense-in-depth across multiple layers:

  1. Zero Client Secrets Architecture: No private keys, database credentials, or payment secrets exist within the APK. All operations pass through a backend API Gateway (BFF - Backend for Frontend).
  2. Client-to-Backend Transport Security:
    • Enforce TLS 1.3 with OkHttp CertificatePinner using multiple backup SPKI pins to mitigate MITM proxy attacks.
    • Implement Mutual TLS (mTLS) with client certificates stored in Android Keystore for enterprise banking transactions.
  3. Device & App Attestation: Gate gateway access using Google's Play Integrity API to block rooted environments, emulators, debuggers, and repackaged APKs.
  4. Short-Lived Ephemeral Session Tokens: The backend issues short-lived JWTs (5-15 minute lifespan). User refresh tokens are stored using EncryptedSharedPreferences backed by hardware Keystore keys requiring biometric authorization (setUserAuthenticationRequired(true)).
  5. Build-Time Key Hygiene: Non-sensitive public SDK keys are loaded via local.properties + secrets-gradle-plugin and restricted in cloud consoles by SHA-1 fingerprint and package name.
  6. Runtime Memory & UI Protection:
    • Store sensitive strings in CharArray or byte buffers that are immediately zeroed out after cryptographic operations.
    • Set WindowManager.LayoutParams.FLAG_SECURE to prevent screen recording, task switcher snapshots, and screen sharing leaks.
    • Disable OS backup via android:allowBackup="false".
