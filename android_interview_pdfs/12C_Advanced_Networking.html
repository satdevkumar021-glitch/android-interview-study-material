2. How It Works

1. Certificate Pinning

Certificate pinning prevents MITM attacks by hardcoding the expected certificate (or its public key hash) in the app. Even if a user installs a malicious CA certificate, a pinned connection will fail.

// OkHttp CertificatePinner — pin the server's leaf or intermediate certificate
val certificatePinner = CertificatePinner.Builder()
    .add("api.bank.com", "sha256/AAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAA=")
    .add("api.bank.com", "sha256/BACKUP_PIN_HASH_HERE=")  // backup pin for rotation
    .build()

val client = OkHttpClient.Builder()
    .certificatePinner(certificatePinner)
    .build()

Network Security Config (Declarative, XML)

<!-- res/xml/network_security_config.xml -->
<network-security-config>
    <domain-config cleartextTrafficPermitted="false">
        <domain includeSubdomains="true">api.bank.com</domain>
        <pin-set expiration="2026-01-01">
            <pin digest="SHA-256">AAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAA=</pin>
            <pin digest="SHA-256">BACKUP_PIN=</pin>
        </pin-set>
    </domain-config>
</network-security-config>

<!-- AndroidManifest.xml -->
<application android:networkSecurityConfig="@xml/network_security_config" ... />

2. Token Refresh — The Concurrent Problem

When a JWT expires, multiple in-flight API calls all get 401 simultaneously. Without coordination, each call would try to refresh the token independently — causing multiple refresh requests and race conditions.

PROBLEM (no mutex): Thread 1: GET /orders → 401 → starts refresh Thread 2: GET /cart → 401 → starts refresh (duplicate!) Thread 3: GET /user → 401 → starts refresh (triplicate!) → 3 concurrent refresh calls → server confusion, possible logout SOLUTION (with Mutex): Thread 1: GET /orders → 401 → acquires Mutex → refreshes token → releases Mutex → retries Thread 2: GET /cart → 401 → waits for Mutex → (token already refreshed) → retries with new token Thread 3: GET /user → 401 → waits for Mutex → retries with new token → 1 refresh call, all requests succeed 
class TokenRefreshInterceptor @Inject constructor(
    private val tokenStore: TokenStore,
    @UnauthenticatedOkHttpClient private val refreshClient: OkHttpClient
) : Interceptor {

    private val mutex = Mutex()  // Coroutine Mutex — only one refresh at a time

    override fun intercept(chain: Interceptor.Chain): Response {
        val response = chain.proceed(chain.request())
        if (response.code != 401) return response

        response.close()

        // Synchronous token refresh with Mutex to prevent concurrent refreshes
        val newToken = runBlocking {
            mutex.withLock {
                // Check if another thread already refreshed the token while we waited
                val currentToken = tokenStore.getAccessToken()
                val requestToken = chain.request().header("Authorization")?.removePrefix("Bearer ")
                if (currentToken != requestToken) {
                    // Token was already refreshed by another thread — use the new one
                    return@withLock currentToken
                }
                // We are the first thread — perform the refresh
                val refreshResponse = refreshClient.newCall(
                    buildRefreshRequest(tokenStore.getRefreshToken())
                ).execute()
                if (!refreshResponse.isSuccessful()) {
                    tokenStore.clearTokens()  // force logout
                    return@withLock null
                }
                val newToken = refreshResponse.parseToken()
                tokenStore.saveTokens(newToken)
                newToken.accessToken
            }
        } ?: return buildUnauthorizedResponse(chain.request())

        // Retry original request with new token
        return chain.proceed(
            chain.request().newBuilder().header("Authorization", "Bearer $newToken").build()
        )
    }
}

3. Sealed Result Type + Error Mapper

sealed class NetworkResult<out T> {
    data class Success<T>(val data: T)                     : NetworkResult<T>()
    data class HttpError(val code: Int, val error: ApiError?) : NetworkResult<Nothing>()
    data class NetworkError(val exception: IOException)          : NetworkResult<Nothing>()
    object Loading                                                : NetworkResult<Nothing>()
}

// Extension function — wrap any Retrofit call in a NetworkResult
suspend fun <T> safeApiCall(call: suspend () -> Response<T>): NetworkResult<T> =
    try {
        val response = call()
        if (response.isSuccessful()) NetworkResult.Success(requireNotNull(response.body()))
        else NetworkResult.HttpError(response.code(), response.errorBody()?.parseApiError())
    } catch (e: IOException) {
        NetworkResult.NetworkError(e)
    }

4. Offline-First Networking

// Pattern: emit Room data immediately, then fetch from network and update Room
// Room's Flow re-emits when the DB updates → UI automatically shows fresh data
fun getProducts(): Flow<List<Product>> = flow {
    // 1. Emit cached data immediately (UI is usable right away)
    emitAll(productDao.getProducts().map { it.map(ProductEntity::toDomain) })
}.onStart {
    // 2. Fetch from network in parallel — updates Room, which re-emits the Flow
    refreshProductsFromNetwork()
}

private suspend fun refreshProductsFromNetwork() {
    runCatching { api.getProducts() }
        .onSuccess { dtos -> productDao.replaceAll(dtos.map(ProductDto::toEntity)) }
        .onFailure { /* silently fail — cached data is already shown */ }
}

3. When to Use

Certificate Pinning — Required for

  • Banking, payments, healthcare apps — any app handling sensitive personal or financial data
  • Apps in regulated industries (PCI-DSS, HIPAA)
  • Internal corporate apps where the server certificate is known and stable
Certificate Rotation Warning
Always include a backup pin. If the server's certificate is rotated and you've only pinned one certificate hash, all previously installed app versions will stop working until users update. With an expiration date in Network Security Config and a backup pin, you can rotate gracefully.

Mutex Token Refresh — Required when

  • The app makes multiple concurrent API calls
  • The authentication token has a TTL and can expire mid-session

Offline-First — Use when

  • Users are in areas with intermittent connectivity (mobile apps in general)
  • The app shows lists of data that should be available instantly
  • A network failure should degrade gracefully, not show an error screen

4. Production Example

Banking App — Complete Auth Interceptor with Concurrent Refresh

// TokenStore — persists tokens securely (EncryptedSharedPreferences)
interface TokenStore {
    fun getAccessToken(): String?
    fun getRefreshToken(): String?
    fun saveTokens(accessToken: String, refreshToken: String)
    fun clearTokens()
}

// Full interceptor with all production considerations
class BankingAuthInterceptor @Inject constructor(
    private val tokenStore: TokenStore,
    @UnauthenticatedOkHttpClient
    private val authClient: OkHttpClient,
    private val moshi: Moshi
) : Interceptor {

    companion object {
        private val mutex = Mutex()  // static — shared across all interceptor instances
    }

    override fun intercept(chain: Interceptor.Chain): Response {
        // 1. Add current token to request
        val token = tokenStore.getAccessToken()
        val request = if (token != null)
            chain.request().newBuilder().header("Authorization", "Bearer $token").build()
        else chain.request()

        val response = chain.proceed(request)
        if (response.code != 401) return response

        response.close()  // IMPORTANT: close before retrying

        // 2. Try to refresh token, coordinated with Mutex
        val newToken = runBlocking {
            mutex.withLock {
                // Was token already refreshed while waiting for Mutex?
                val latestToken = tokenStore.getAccessToken()
                if (latestToken != token) {
                    return@withLock latestToken  // use the already-refreshed token
                }
                // Perform the refresh
                val refreshToken = tokenStore.getRefreshToken()
                    ?: return@withLock null

                val refreshResult = runCatching {
                    authClient.newCall(
                        Request.Builder()
                            .url("https://auth.bank.com/v1/token/refresh")
                            .post(jsonBody("""{"refreshToken":"$refreshToken"}"""))
                            .build()
                    ).execute()
                }

                refreshResult.getOrNull()?.let { refreshResponse ->
                    if (refreshResponse.isSuccessful()) {
                        val tokens = refreshResponse.parseTokenResponse(moshi)
                        tokenStore.saveTokens(tokens.accessToken, tokens.refreshToken)
                        tokens.accessToken
                    } else {
                        tokenStore.clearTokens()  // session expired — force re-login
                        null
                    }
                }
            }
        }

        return if (newToken != null) {
            chain.proceed(request.newBuilder().header("Authorization", "Bearer $newToken").build())
        } else {
            // Build 401 response to propagate up to the ViewModel
            Response.Builder().request(request).protocol(Protocol.HTTP_1_1)
                .code(401).message("Unauthorized")
                .body("".toResponseBody()).build()
        }
    }
}

6. Pitfalls & Best Practices

Certificate Pinning Pitfalls

Forgotten Backup Pin = App Broken on Certificate Rotation
If you pin only the production certificate and the server rotates to a new cert, every installed version of the app breaks until the user updates. Always pin the production certificate AND a backup certificate (can be a pre-generated cert you haven't deployed yet). Include an expiration date in Network Security Config so Trustpilot/Google Play's review catches stale pins.

Token Refresh Pitfalls

Infinite Refresh Loop
If the refresh endpoint itself returns 401 (e.g., refresh token expired), and your interceptor retries on 401, you'll loop infinitely. Always check: if the request is already to the refresh endpoint, don't retry — propagate the 401 up and force re-login.

Offline-First Pitfalls

Not Closing Response Bodies
When you call chain.proceed(), OkHttp returns a Response with an open body stream. If you check the status code and decide to retry without calling response.close(), you leak the connection. Always call response.close() before retrying or returning a different response.

Best Practices

  • Store the Mutex as a companion object property — shared across all interceptor instances
  • Use EncryptedSharedPreferences (or DataStore with encryption) to store refresh tokens — never plain SharedPreferences
  • Seal the NetworkResult type — forces callers to handle all cases at compile time
  • Room as single source of truth: always write network data to Room first; let Room's Flow deliver it to the UI

7. Interview Framework

30-Second Answer

"For production Android networking: certificate pinning pins the server's certificate hash in the app so MITM attacks fail even with a rogue CA — OkHttp's CertificatePinner or Network Security Config XML handles this. Token refresh: when a JWT expires, multiple concurrent 401s can trigger multiple refresh calls — use a Mutex so only one refresh happens; others wait and reuse the new token. Offline-first: Room is the single source of truth; the repository emits Room's Flow immediately, then fetches from network and writes to Room — the Flow re-emits automatically with fresh data."

2-Minute Deep Dive

"The concurrent token refresh problem is a race condition: if 5 API calls are in-flight and the token expires, all 5 get 401 simultaneously and would each try to refresh — potentially logging the user out. The fix: a Mutex in the auth interceptor. Thread 1 acquires the Mutex and refreshes. Threads 2–5 wait. When they finally acquire the Mutex, they check if the token changed since their 401 — it has, so they skip the refresh and retry with the new token directly. Always store the Mutex as a companion object property — a new interceptor instance per request would have different Mutexes and the protection fails. For pinning: always include a backup pin to survive certificate rotation, and set an expiration date so you remember to update it."

Must-Mention Points

1
Certificate pinning: OkHttp CertificatePinner or Network Security Config XML; always include backup pin
2
Concurrent 401 problem: Mutex ensures only one refresh call happens; others reuse the result
3
Check token changed before refreshing: avoids redundant refresh when waiting on Mutex
4
Never loop on refresh endpoint 401: detect and force re-login
5
Offline-first: Room as single source of truth; emit cache immediately, update from network
6
Always close Response before retrying: prevents OkHttp connection leaks

Do NOT Go Deeper On

  • Full OAuth 2.0 PKCE flow (mention if asked, don't volunteer)
  • TLS handshake mechanics (just say "certificate pinning validates the server cert")
  • Network Security Config for debug builds (mention only if asked about proxy debugging)

Follow-up Q&A

QuestionAnswer
"What's the difference between CertificatePinner and Network Security Config?"Both pin certificates. CertificatePinner is in code — works for one host at a time, easy to update with app release. NSC is XML — declarative, also controls cleartext traffic and custom CAs, applied at OS level.
"What is stale-while-revalidate?"Serve the cached response immediately, then fetch fresh data in the background. The UI sees instant data; if the background fetch differs, the UI updates. This is essentially the offline-first pattern described above.
"How do you store tokens securely?"EncryptedSharedPreferences (wraps Android Keystore) for access and refresh tokens. Never plain SharedPreferences or files. Never in-memory only — tokens are lost on process death.

Senior Insight

Senior Signal
The subtle part of the Mutex solution is the "check if token changed" step. Without it, threads 2–5 wake up after Thread 1's refresh and each also try to refresh — the Mutex prevents parallel refreshes, but without the stale-token check, you'd refresh N times sequentially. The check makes the solution O(1) refreshes regardless of how many calls failed with 401. This is the kind of detail that separates a correct implementation from a production-ready one.

9. Interview Questions
Basic What is certificate pinning and why is it needed? ⌄
Certificate pinning hardcodes the expected server certificate (or its public key hash) in the app. Standard TLS trusts any certificate signed by a trusted CA. If an attacker installs a rogue CA certificate on the device (or does a corporate MITM), they can intercept TLS traffic. Certificate pinning rejects any certificate not matching the pinned hash — even if it's signed by a "trusted" CA. This is required for apps handling financial or health data where MITM attacks must be prevented.
Basic What is the concurrent token refresh problem? ⌄
When a JWT expires, multiple in-flight API calls all receive 401 simultaneously. Without coordination, each call would attempt to refresh the token independently — potentially making 5 simultaneous refresh calls, overwhelming the auth server, causing race conditions (which refresh response is "correct"?), and possibly invalidating other refresh tokens in the process. The solution: a Mutex that serialises refresh attempts. The first thread refreshes; subsequent threads wait, then reuse the new token without refreshing again.
Basic What does "offline-first" mean in Android development? ⌄
Offline-first means the app is designed to work without network connectivity. The architecture uses Room as the single source of truth: the UI always reads from Room (never directly from the network), so data is instantly available even without a network. When the network is available, the repository fetches fresh data and writes it to Room — Room's Flow automatically re-emits the update to the UI. The user never sees "no connection" errors for data that was previously loaded; they see slightly stale data, which is preferable to a blank screen.
Intermediate Why must the Mutex be in a companion object in the token refresh interceptor? ⌄
OkHttp creates a new interceptor invocation context per call — but if the Mutex is an instance property, each call could potentially use a different Mutex instance if new interceptor instances are created. The Mutex must be shared across all concurrent calls to the same interceptor. Declaring it in companion object makes it a class-level (static) property, so all instances share the same Mutex. Even if multiple interceptors of the same type exist (which shouldn't happen in production, but might in tests), they share the lock.
Intermediate How does the "check if token changed" optimisation work in the Mutex refresh pattern? ⌄
When Thread 1 acquires the Mutex and refreshes the token, Threads 2–5 are waiting. When they each acquire the Mutex (one at a time), they check: "Is the current token in the token store different from the token that was in my 401 request?" If yes — Thread 1 already refreshed — they skip the refresh and return the new token immediately. Without this check, Threads 2–5 would each perform a sequential refresh, refreshing the token 5 times and invalidating previously issued refresh tokens. The check makes it so only Thread 1 does real work; the rest benefit from it.
Intermediate What should happen when the token refresh request itself returns 401? ⌄
A 401 on the refresh endpoint means the refresh token itself has expired (or been revoked). The session is invalid and cannot be recovered silently. The interceptor should: (1) Call tokenStore.clearTokens() — remove all stored credentials. (2) Return null from the refresh logic. (3) Build a 401 response to propagate up the call chain. (4) The ViewModel observes the 401 state and navigates to the login screen.

Critical: guard against infinite loops — if the request URL is the refresh endpoint, skip the 401 retry logic entirely and propagate the 401 immediately.
Intermediate What is the difference between OkHttp CertificatePinner and Network Security Config? ⌄
CertificatePinner (code-based): configured in OkHttpClient builder. Per-host configuration. Checked by OkHttp on every request to the pinned hostname. More flexible — can be dynamically updated (e.g., via remote config, though that defeats the purpose). Easy to test.

Network Security Config (XML): declared in res/xml/network_security_config.xml, referenced in AndroidManifest. Applied at the OS networking layer — affects all connections from the app including those not using OkHttp. Also controls cleartext traffic (cleartextTrafficPermitted), custom CAs for debug builds, and domain-specific policies. Has an expiration date feature. Verified by Google Play on upload.
Senior Design the full offline-first architecture for a banking transaction history feature. ⌄
Room: TransactionEntity with all fields. TransactionDao returns Flow<List<TransactionEntity>>.

Repository: getTransactions() returns a Flow that: (1) immediately emits Room data (mapped to domain models). Separately, a background refresh: (2) fetches from Retrofit, writes to Room via dao.replaceAll(). Room's Flow auto-re-emits the fresh data.

Stale data handling: each transaction has a server-assigned timestamp. On Room insert, also store a fetchedAt timestamp. Show a "last updated X minutes ago" label in the UI based on this. If fetchedAt is older than 5 minutes and no network is available, show a "data may be outdated" banner.

Balance (accuracy-critical): do NOT use offline-first for balance. Always fetch from network. Show a loading state until fresh data arrives. Cache for display only during temporary connection loss, with a clear "as of [time]" label.
Senior A user's token refresh is failing intermittently in production. How would you debug it? ⌄
Debugging strategy:

1. Add logging (to a secure backend — not Logcat in production): log refresh request timestamps, HTTP status codes, and whether the token-changed check triggered. Never log token values.
2. Check for clock skew: JWT expiry is time-based. If the device's clock is ahead/behind the server's, tokens may appear expired before they are. Check the token's exp claim vs system time at the point of 401.
3. Check for Mutex deadlock: if the Mutex is never released (exception in the refresh block), all calls will hang. Ensure withLock is used (auto-releases on exception).
4. Verify single Mutex instance: check if the Mutex is actually in companion object — a test configuration change could have moved it to an instance property.
5. Server logs: check if multiple refresh requests are hitting the server from the same device — indicating the Mutex isn't working as expected.
Senior How would you handle certificate pinning when using a CDN that rotates certificates frequently? ⌄
CDNs like CloudFront rotate leaf certificates frequently (every 30–90 days), making leaf certificate pinning impractical. Solution: pin the intermediate CA certificate instead. CDN providers control which intermediate CA they use, and these rotate far less frequently (years). This gives you MITM protection without breaking on every leaf cert rotation.

Alternative: use the public key hash (sha256/ of the SubjectPublicKeyInfo) rather than the certificate hash. The public key is stable even when the certificate is renewed — same public key, new certificate = same pin hash.

Also: implement a remote kill-switch — a mechanism to disable pinning for a specific version via a remote config, in case a pin break in production requires an emergency bypass while an app update propagates.
