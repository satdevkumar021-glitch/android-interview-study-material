1B — Kotlin Functions

Default & named arguments, vararg, extension functions, infix, higher-order functions, lambdas, function references, and SAM conversions — the full Kotlin function toolkit.

ID: 1B ⭐ Tier 1
🔍
1. Overview

What it is

Kotlin's function system goes well beyond Java methods. It adds default/named arguments (eliminating builder boilerplate), extension functions (add behaviour to existing types without inheritance), higher-order functions and lambdas (functions as first-class values), infix notation (DSL-friendly syntax), and SAM conversions (interop with Java functional interfaces).

Why it exists

  • Java forces overloaded methods or Builder patterns for optional parameters — Kotlin uses defaults.
  • Java requires subclassing or utility classes to add behaviour — Kotlin uses extension functions.
  • Java lambdas are verbose and limited — Kotlin's functional features are first-class, concise, and composable.

Problems it solves

  • Boilerplate constructors and builders
  • Utility class proliferation (StringUtils, CollectionUtils)
  • Callback hell — lambdas and higher-order functions make callbacks clean
  • Java SAM verbosity — Runnable { } vs anonymous inner classes
Senior Mental Model
In Kotlin, functions are values. A lambda is an instance of a function type ((T) -> R). This enables the entire functional programming style — passing behaviour, not just data.

2. How It Works

Default & Named Arguments

fun createRequest(
    url: String,
    method: String = "GET",        // default argument
    timeout: Int = 30,
    retries: Int = 3
): Request { ... }

// Callers only specify what they need:
createRequest("https://api.bank.com/balance")
createRequest("https://api.bank.com/pay", method = "POST", retries = 1)
createRequest(url = "https://api.bank.com/pay", timeout = 60)  // named — order-independent

Named arguments make call sites self-documenting and order-independent. Eliminates the Builder pattern for simple data objects.

vararg

fun log(tag: String, vararg messages: String) {
    messages.forEach { Log.d(tag, it) }
}

log("Auth", "Token refreshed", "Session extended")  // any number of args

val msgs = arrayOf("a", "b")
log("Auth", *msgs)  // spread operator to pass array as vararg

vararg is compiled to an array. Use the spread operator * to pass an existing array.

Extension Functions

// Adds .toFormattedAmount() to Double — no subclassing needed
fun Double.toFormattedAmount(currency: String = "INR"): String =
    "$currency ${this.toBigDecimal().setScale(2, RoundingMode.HALF_UP)}"

val display = 1234.567.toFormattedAmount()  // "INR 1234.57"

// Extension on nullable receiver:
fun String?.orEmpty(): String = this ?: ""  // stdlib example
Internals
Extension functions are statically dispatched — compiled to static methods in JVM bytecode. They do NOT override member functions. If a member and extension have the same signature, the member always wins.

Infix Functions

// Single parameter, member or extension, marked infix
infix fun Int.times(action: () -> Unit) = repeat(this) { action() }

3 times { Log.d("tag", "ping") }   // reads like English

// Stdlib: to, until, step, downTo, and, or...
val pair = "key" to "value"  // infix Pair creation

Higher-Order Functions

// Takes a function as parameter
fun <T> retry(times: Int, block: () -> T): T {
    repeat(times - 1) {
        try { return block() } catch (e: Exception) { /* retry */ }
    }
    return block()  // last attempt — propagate exception
}

// Returns a function
fun multiplier(factor: Int): (Int) -> Int = { it * factor }
val double = multiplier(2)
double(5)  // 10

Lambdas

// Lambda syntax: { params -> body }
val sum: (Int, Int) -> Int = { a, b -> a + b }

// Single parameter: implicit 'it'
val square: (Int) -> Int = { it * it }

// Trailing lambda convention (last param is lambda → outside parens)
listOf(1,2,3).filter { it > 1 }.map { it * 2 }

// Lambda with receiver (used in DSLs / scope functions)
fun buildQuery(init: StringBuilder.() -> Unit): String =
    StringBuilder().apply(init).toString()

Function References

// :: refers to a function by name instead of calling it
fun isValid(s: String) = s.isNotBlank()

val names = listOf("Alice", "", "Bob")
names.filter(::isValid)          // top-level function ref
names.filter(String::isNotBlank)  // member function ref

// Constructor reference
val makeUser: (String) -> User = ::User
val users = names.map(::User)

SAM Conversions

// Java SAM (Single Abstract Method) interface:
// interface Runnable { void run(); }

// Java-style (verbose):
executor.execute(object : Runnable { override fun run() { doWork() } })

// SAM conversion — Kotlin converts lambda to Runnable automatically:
executor.execute { doWork() }

// Kotlin fun interface (SAM-compatible Kotlin interface):
fun interface Validator<T> { fun validate(value: T): Boolean }
val nonBlank = Validator<String> { it.isNotBlank() }  // SAM conversion

Real Android Use Cases

FeatureAndroid Use Case

varargLogging helpers, analytics event properties, route arguments

When NOT to Use

Do NOT
  • Use extension functions to add core business logic to domain models — put that in use cases
  • Capture Activity/Context in a lambda stored beyond its lifecycle
  • Use infix for non-obvious operations — reduces readability for teams
  • Mark every function infix just because it takes one argument
  • Use vararg with reified — separate concern; use inline instead

4. Production Example
Scenario
E-commerce app — product listing. A safe API call wrapper uses higher-order functions; product mappers use function references; UI extensions clean up View code.

Safe API Call Wrapper (Higher-Order Function)

// data/remote/NetworkUtils.kt
suspend fun <T> safeApiCall(
    dispatcher: CoroutineDispatcher = Dispatchers.IO,
    apiCall: suspend () -> T  // function param — behaviour injected
): Result<T> = withContext(dispatcher) {
    try {
        Result.success(apiCall())
    } catch (e: HttpException) {
        Result.failure(ApiException(e.code(), e.message()))
    } catch (e: IOException) {
        Result.failure(NetworkException(e))
    }
}

Repository Using the Wrapper + Function Reference in Mapper

// data/repository/ProductRepositoryImpl.kt
class ProductRepositoryImpl @Inject constructor(
    private val api: ProductApi,
    private val dao: ProductDao
) : ProductRepository {

    override suspend fun getProducts(
        category: String,
        page: Int = 1,            // default arg — callers omit for first page
        pageSize: Int = 20
    ): Result<List<Product>> = safeApiCall {
        api.getProducts(category, page, pageSize)
            .products
            .map(ProductDto::toDomain)  // function reference to extension on DTO
    }
}

DTO Extension Function (Mapper)

// data/mapper/ProductMapper.kt
fun ProductDto.toDomain() = Product(
    id = id,
    name = name,
    price = price,
    imageUrl = imageUrl.orEmpty(),   // stdlib extension on String?
    inStock = stockCount > 0
)

// Extension on List for batch mapping
fun List<ProductDto>.toDomainList() = map(ProductDto::toDomain)

View Extension Functions (Presentation Layer)

// presentation/extensions/ViewExtensions.kt
fun View.visible() { visibility = View.VISIBLE }
fun View.gone()    { visibility = View.GONE }
fun View.invisible() { visibility = View.INVISIBLE }

// Higher-order + lambda: debounced click listener
fun View.setDebouncedClickListener(
    debounceMs: Long = 300L,        // default arg
    onClick: (View) -> Unit          // function param
) {
    var lastClick = 0L
    setOnClickListener {              // SAM conversion
        val now = SystemClock.elapsedRealtime()
        if (now - lastClick > debounceMs) {
            lastClick = now
            onClick(it)
        }
    }
}

Key Lines Explained

  • safeApiCall { api.getProducts(...) } — trailing lambda; function param injects the network call behaviour.
  • .map(ProductDto::toDomain) — function reference replaces .map { it.toDomain() }; cleaner and compiler-verified.
  • page: Int = 1 — callers who only want the first page don't need to pass it; named args make intent clear.
  • setOnClickListener { } — SAM conversion; Kotlin lambda satisfies the Java OnClickListener interface.
  • onClick: (View) -> Unit — function type as parameter — the entire debounce logic is reusable, behaviour is injected.

Common Interviewer Comparisons

Expect These
  • Extension function vs member function — member always wins on same signature; extension is static dispatch
  • Lambda vs anonymous object — lambda for SAM; anonymous object for multi-method interfaces
  • Default args vs overloads — default args are idiomatic Kotlin; overloads needed for Java interop
  • Higher-order function vs interface — HOF is more concise; interface provides stronger contract with a name
  • Function reference vs lambda — equivalent at runtime; references are more concise when no transformation needed

6. Pitfalls & Best Practices

Extension Function Shadowed by Member

class Foo { fun bar() = "member" }
fun Foo.bar() = "extension"  // ❌ never called — member always wins
Foo().bar()  // "member"

Context Leak in Lambda

// ❌ BAD — Activity captured in a long-lived lambda
class MyActivity : AppCompatActivity() {
    private val handler = Handler(Looper.getMainLooper())
    override fun onCreate(...) {
        handler.postDelayed({ updateUI() }, 5000)  // captures Activity
    }
}
// ✅ GOOD — use WeakReference or cancel in onDestroy
private val weakActivity = WeakReference(this)
handler.postDelayed({ weakActivity.get()?.updateUI() }, 5000)

Default Args and Java Interop

// ❌ BAD — Java can't use default args without @JvmOverloads
fun connect(host: String, port: Int = 443) { }
// Java: connect("host", 443) only — no default available
// ✅ GOOD — generates overloaded methods for Java
@JvmOverloads
fun connect(host: String, port: Int = 443) { }

Lambda Allocation in Hot Paths

// ❌ BAD — new lambda object created on every RecyclerView bind
override fun onBindViewHolder(holder: VH, position: Int) {
    holder.itemView.setOnClickListener { onItemClick(position) }  // allocation
}
// ✅ GOOD — pass listener reference; set once in onCreateViewHolder
override fun onCreateViewHolder(parent: ViewGroup, viewType: Int): VH {
    val holder = VH(inflate(parent))
    holder.itemView.setOnClickListener { onItemClick(holder.bindingAdapterPosition) }
    return holder
}

Overusing Extension Functions

// ❌ BAD — business logic in an extension on a primitive
fun String.isValidBankAccountNumber(): Boolean = matches(Regex("^[0-9]{9,18}$"))
// Business rule leaks into a generic utility layer
// ✅ GOOD — keep in domain validator / use case
class AccountNumberValidator {
    fun isValid(accountNumber: String): Boolean = accountNumber.matches(Regex("^[0-9]{9,18}$"))
}

Production Best Practices

  1. Use default + named args instead of Builder pattern for data config objects.
  2. Put extension functions in a dedicated file matching the extended type (ViewExtensions.kt, StringExtensions.kt).
  3. Prefer function references over lambdas in mapper chains — they're compiler-verified.
  4. Use inline for higher-order functions called in performance-sensitive code (see 1I).
  5. Never capture long-lived references (Activity, Fragment) in lambdas stored beyond their lifecycle.
  6. Add @JvmOverloads on functions with defaults when the module is consumed by Java code.
  7. Keep extension functions stateless and pure — no side effects, no dependencies on external state.

7. Interview Answer Framework

30-Second Answer

"Kotlin's function system has several layers. Default and named arguments eliminate builder boilerplate. Extension functions let you add behaviour to existing types without subclassing — they're statically dispatched and don't require modifying the original class. Higher-order functions and lambdas treat functions as first-class values, which is fundamental to how Flow operators, coroutine builders, and scope functions work. SAM conversions make Java interop clean — a lambda automatically satisfies a single-abstract-method interface."

2-Minute Structured Answer

"I'll cover the most practically important ones. Default and named arguments: instead of overloaded methods or a Builder, I declare one function with defaults and callers only specify what differs. This is how I design API call wrappers and UseCase signatures — clean, readable, no boilerplate.

Extension functions: I use these heavily for mappers (ProductDto.toDomain()), View utilities (.gone(), .visible()), and String formatting. The key thing to know: they're statically dispatched — compiled to static methods. If a member and extension have the same signature, the member always wins. So extensions can't override behaviour — they extend it.

Higher-order functions: this is how safeApiCall { } wrappers work — the network call is injected as a function parameter. The caller owns the 'what', the wrapper owns the 'how' (error handling, dispatching). This is the Strategy pattern, implemented cleanly without an interface.

SAM conversions: Kotlin lambdas automatically satisfy Java single-abstract-method interfaces. setOnClickListener { } works because OnClickListener has one method. For Kotlin-defined interfaces, I use fun interface to get the same benefit."

Must-Mention Points

1
Default args eliminate overloads; named args make call sites self-documenting and order-independent
2
Extension functions are statically dispatched — compiled to static methods; member always wins on same signature
3
Higher-order functions accept or return functions — the basis of Strategy pattern, coroutine builders, Flow operators
4
Trailing lambda convention: if last param is a function, lambda can be moved outside parentheses
5
Function references (::fn) are equivalent to lambdas but compiler-verified and more concise in mapper chains
6
SAM conversion: Kotlin lambda → Java SAM interface automatically; use fun interface for Kotlin SAMs
7
Lambdas capture variables from enclosing scope — beware lifecycle/context leaks in long-lived lambdas

Do NOT Go Deeper Unless Asked

  • Bytecode compilation details of lambdas (invokedynamic, FunctionN interfaces)
  • inline functions and how they eliminate lambda allocation (covered in 1I)
  • Kotlin coroutine builders as higher-order functions internals

Likely Follow-up Questions

QuestionShort Answer
Can extension functions access private members?No. They're compiled outside the class — they only see public/internal members.
What's the difference between a lambda and an anonymous function?Lambda uses implicit return (returns from enclosing function). Anonymous function uses explicit return (returns from itself). Lambda return inside a non-inline HOF requires a label.
When does a lambda cause an object allocation?Every time a non-inline higher-order function is called with a lambda argument, a new function object is allocated. Inline functions eliminate this.
What is a lambda with receiver?A lambda where this refers to the receiver object — used in DSLs and scope functions. Example: StringBuilder.() -> Unit

Senior-Level Insight (Stand Out)

Say This
"In production, I use higher-order functions to implement a safeApiCall { } wrapper in the data layer. The caller passes the actual Retrofit call as a lambda; the wrapper owns retry, dispatcher, and error-mapping logic. This is the Strategy pattern with zero interface boilerplate. It's also trivially testable — in unit tests I pass a lambda that throws, or one that returns a fixture — no mocking needed. The key senior insight: Kotlin's function types are named contracts — suspend () -> T is as clear as an interface with one method, but with zero ceremony."

9. Interview Questions (Self-Check)
How to use
Answer mentally first, then click to reveal.

Basic

B1 — What are named arguments? Why are they useful?
Easy▼
Named arguments let you specify parameters by name at the call site, making the order irrelevant. They're useful when a function has many parameters (especially booleans), making the call self-documenting. Example: createRequest(url = "...", timeout = 60) — the reader immediately knows what each value is without checking the function signature.
B2 — What is an extension function? What can it NOT do?
Easy▼
An extension function lets you add a new function to an existing class without modifying or inheriting from it. It's called with dot notation as if it's a member. What it CANNOT do: (1) access private/protected members — it only sees the public API; (2) override existing member functions — member always takes precedence on same signature; (3) modify the class's state in any privileged way.
B3 — What is a SAM conversion?
Easy▼
SAM (Single Abstract Method) conversion allows a Kotlin lambda to be used wherever a Java interface with a single abstract method is expected. Kotlin automatically wraps the lambda in an anonymous class implementing the interface. Example: setOnClickListener { handleClick() } — the lambda is converted to View.OnClickListener automatically. For Kotlin interfaces, use fun interface to enable the same behavior.

Intermediate

I1 — What is the difference between a higher-order function and a regular function? Give a real Android example.
Medium▼
A higher-order function either takes a function as a parameter, returns a function, or both. A regular function only works with data. Real Android example: safeApiCall { api.getUser(id) } — the lambda is the network call. The wrapper function owns error handling, dispatcher, and Result wrapping. This is the Strategy pattern without an interface — the behaviour is injected as a value.
I2 — What is the difference between a function reference and a lambda? When would you use each?
Medium▼
They're equivalent at runtime. A function reference (::fn or Class::fn) refers to an existing named function. A lambda is an inline anonymous function. Use function reference when: (1) a named function already exists that does exactly what you need — .map(::toDomain); (2) it's more readable. Use a lambda when: you need to write the logic inline, or there are transformations the existing function doesn't cover.
I3 — What is a "lambda with receiver" and where is it used in Android?
Medium▼
A lambda with receiver is a lambda where this inside the block refers to the receiver object rather than the outer class. Type: T.() -> R. Used in: (1) Kotlin scope functions — apply { }, run { }, with { }; (2) DSL builders — e.g., buildString { append("...") }; (3) Jetpack Compose implicit receiver lambdas. This is what makes apply { visibility = VISIBLE } work — inside the lambda, this is the View.
I4 — (Coding) Rewrite using an extension function and function reference: list.map { it.name.trim().lowercase() }
MediumCoding▼
// Extension on User
fun User.normalizedName(): String = name.trim().lowercase()

// Usage with function reference
list.map(User::normalizedName)

// Or top-level extension + reference
fun normalizedName(user: User) = user.name.trim().lowercase()
list.map(::normalizedName)

Senior / Scenario

S1 — (Scenario) A junior dev wrote 6 overloaded fetchProducts() methods to support optional filters. You're reviewing the PR. How do you refactor?
HardScenario▼
Consolidate into one function with default arguments. Identify all the varying parameters across the 6 overloads and make each one a named parameter with a sensible default: 
// Before: 6 overloaded methods

// After: 1 function, default args
suspend fun fetchProducts(
    category: String? = null,
    minPrice: Double? = null,
    maxPrice: Double? = null,
    inStockOnly: Boolean = false,
    sortBy: SortOrder = SortOrder.DEFAULT,
    page: Int = 1
): Result<List<Product>>
If the module is also consumed by Java code, add @JvmOverloads. If the filter combinations grow to a large data class, consider a ProductFilter data class as a single parameter — but that's only warranted at high complexity.
S2 — Extension functions vs utility class: which do you prefer and why? What's the trade-off?
Hard▼
Prefer extension functions in Kotlin — they're idiomatic, discoverable via IDE autocomplete on the type, and don't require an instance of a utility class. Trade-offs: Extensions: statically dispatched (no polymorphism), can't access private members, may scatter logic across files if not organized. Utility class: testable as a unit (can be mocked/injected), centralizes logic, needed when logic requires injected dependencies. Rule: pure transformations (formatting, parsing, mapping) → extension. Logic with dependencies (business validation, formatting with locale from DI) → use case or injected service.
S3 — (Debug) A ViewModel function captures this (the ViewModel) in a lambda passed to a repository. The repository stores the lambda. What's the risk? How do you fix it?
HardScenario▼
Risk: The repository is typically a singleton (Hilt @Singleton). It now holds a reference to the ViewModel through the stored lambda. When the user navigates away and the ViewModel is supposed to be destroyed, the repository's reference keeps it alive → memory leak. The ViewModel holds a reference to Compose state or Fragment context → entire screen kept in memory.

Fix: (1) Don't store lambdas that capture ViewModel state in longer-lived components. (2) Use a callback interface that can be set to null in onCleared(). (3) Better: use Flow — the repository emits data via Flow; the ViewModel collects it. No lambda stored, lifecycle handled by viewModelScope.
