1. Overview

The Hilt Component Hierarchy

Hilt generates a hierarchy of Dagger components that mirror the Android lifecycle. Each component can access bindings from its parent (they form a parent-child tree). A component is created when its corresponding Android object is created and destroyed when that object is destroyed.

SingletonComponent (Application lifetime) └── ActivityRetainedComponent (survives config changes) ├── ViewModelComponent (ViewModel lifetime) └── ActivityComponent (Activity instance) ├── FragmentComponent (Fragment instance) │ └── ViewComponent (Fragment) └── ViewComponent (Activity) ServiceComponent (Service lifetime, parallel to Activity)
ComponentScope AnnotationCreated WhenDestroyed When
SingletonComponent@SingletonApplication.onCreate()Application destroyed
ActivityRetainedComponent@ActivityRetainedScopedActivity.onCreate()Activity.onDestroy() (NOT on rotation)
ViewModelComponent@ViewModelScopedViewModel createdViewModel.onCleared()
ActivityComponent@ActivityScopedActivity.onCreate()Activity.onDestroy() (INCLUDING rotation)
FragmentComponent@FragmentScopedFragment.onAttach()Fragment.onDestroy()
Senior Mental Model
ActivityRetainedComponent survives configuration changes — it's the component backing the ViewModel lifecycle. That's why @ViewModelScoped dependencies don't re-create on rotation. ActivityComponent does NOT survive rotation — never inject something that holds a reference to an Activity View into ActivityRetainedComponent.

2. How It Works

Dagger Code Generation

Dagger is an annotation processor that runs at compile time. It reads your @Inject, @Module, @Provides, @Binds annotations and generates concrete Java/Kotlin classes: a Factory for each injectable class, and a Component implementation for each component.

// Your code
class GetOrdersUseCase @Inject constructor(
    val repo: OrderRepository
)

// Dagger generates (simplified):
class GetOrdersUseCase_Factory(val repoProvider: Provider<OrderRepository>) : Factory<GetOrdersUseCase> {
    override fun get() = GetOrdersUseCase(repoProvider.get())
    companion object { fun create(repoProvider: Provider<OrderRepository>) = GetOrdersUseCase_Factory(repoProvider) }
}

@HiltViewModel — What Dagger Generates

// Your code
@HiltViewModel
class OrderViewModel @Inject constructor(
    val getOrders: GetOrdersUseCase
) : ViewModel()

// Dagger generates a Factory class:
class OrderViewModel_HiltModules_KeyModule_ProvideFactory
// + registers it in the ViewModelComponent
// Hilt's DefaultViewModelFactories uses the generated factory to create ViewModel instances

Compile-Time Graph Validation

When Dagger processes annotations, it builds a complete dependency graph. It performs several compile-time checks:

  • Missing binding: A type is requested but no @Provides/@Binds/injectable constructor provides it → "cannot be provided without an @Provides-annotated method"
  • Scope mismatch: A shorter-lived dependency injected into a longer-lived component → compile error
  • Circular dependency: A depends on B, B depends on A → compile error (can be broken with Provider<T> lazy injection)
  • Duplicate bindings: Two @Provides methods return the same type without qualifiers
// Example compile error: AnalyticsService is not provided anywhere
@HiltViewModel
class DashboardViewModel @Inject constructor(
    val analytics: AnalyticsService  // ← no @Inject on AnalyticsService, no @Provides
) : ViewModel()
// Build error: AnalyticsService cannot be provided without an @Provides-annotated method

SubComponents vs Component Dependencies

ApproachAccess to parent bindingsHow specifiedHilt equivalent
SubComponentFull access to all parent bindings@Subcomponent declared inside parentAll Hilt components are subcomponents of their parent
Component dependencyOnly explicitly exposed bindings@Component(dependencies=[ParentComponent::class])Not used in standard Hilt (Hilt uses subcomponents)

In Hilt's hierarchy, all components are SubComponents — each child has full access to the bindings of its parent (e.g., ActivityComponent can use Singleton-scoped bindings). This is why a @Singleton-scoped dependency can be injected into an Activity-scoped class.

Provider<T> — Breaking Circular Dependencies and Deferring Creation

// Provider<T> defers creation — the dependency is retrieved lazily on each get() call
class LoginFlowCoordinator @Inject constructor(
    private val authViewModelProvider: Provider<AuthViewModel>  // lazy + fresh instance each call
) {
    fun createAuthViewModel() = authViewModelProvider.get()
}

// Lazy<T> — like Provider but caches the first result
class FeatureFlagService @Inject constructor(
    private val remoteConfig: Lazy<FirebaseRemoteConfig>  // first access initialises, then cached
)

3. When to Use

Choosing the Right Component Scope

ScenarioComponentScope
HTTP client, Room database, token storeSingletonComponent@Singleton
Shared state that must survive rotationActivityRetainedComponent@ActivityRetainedScoped
Dependency used by one ViewModel onlyViewModelComponent@ViewModelScoped
Navigator that needs Activity contextActivityComponent@ActivityScoped
Screen-specific analytics trackerFragmentComponent@FragmentScoped
Key Decision Criterion
Ask: "What is the shortest lifecycle that ALL consumers of this dependency have in common?" Use that component's scope. When in doubt, scope to @Singleton for stateless services (they're cheap to share) and @ViewModelScoped for stateful per-screen state.

4. Production Example

E-Commerce App — Scoped Dependencies Across Components

// ── Singleton (app-wide) ───────────────────────────────────────
@Singleton
class ProductCatalogCache @Inject constructor(
    private val clock: Clock
) {
    private val cache = LruCache<String, Product>(200)
    // Shared across the entire app — cache is populated once, used everywhere
}

// ── ActivityRetained (survives rotation, not Activity death) ──
@ActivityRetainedScoped
class CheckoutSessionManager @Inject constructor() {
    var selectedAddress: Address? = null
    var paymentMethod: PaymentMethod? = null
    // Survives screen rotation — user's checkout state is preserved
}

// ── ViewModelScoped (lives with one ViewModel) ─────────────────
@ViewModelScoped
class CartPagingSourceFactory @Inject constructor(
    private val dao: CartDao
) {
    fun create() = CartPagingSource(dao)
    // New factory per ViewModel instance — scoped to avoid stale sources
}

@HiltViewModel
class CheckoutViewModel @Inject constructor(
    private val session: CheckoutSessionManager,    // ActivityRetainedScoped
    private val cache: ProductCatalogCache,          // Singleton
    private val pagingFactory: CartPagingSourceFactory // ViewModelScoped
) : ViewModel() {
    // Hilt injects the correct scoped instance for each dependency
}

5. Alternatives & Trade-offs

SubComponents vs Component Dependencies

Hilt uses SubComponents exclusively. Raw Dagger offers both: SubComponents have full access to the parent's bindings (tighter coupling, simpler configuration). Component dependencies are explicit — the child only sees what the parent exposes (looser coupling, better for library modules or multi-project setups). Hilt's choice of SubComponents simplifies usage at the cost of slightly less control over what's visible.

Eager vs Lazy Injection

TypeSyntaxBehaviour
Regular injection@Inject val dep: DepDep is created when the parent is created
Provider<T>@Inject val depProvider: Provider<Dep>Dep is created on each call to get()
Lazy<T>@Inject val dep: Lazy<Dep>Dep is created once, on first get() call

6. Pitfalls & Best Practices

ActivityRetainedScoped vs ActivityScoped Confusion

Most Common Scope Confusion
@ActivityRetainedScoped survives rotation — it's the scope backing the ViewModel. @ActivityScoped does NOT survive rotation — it's a new instance every time the Activity is recreated. Never put something that holds a View reference into ActivityRetainedScoped; Views don't survive rotation and you'll leak the old Activity.

Build Errors — Common Dagger Error Messages

Error messageRoot causeFix
"cannot be provided without an @Provides"Type has no binding in the graphAdd @Inject constructor or @Provides method
"is bound multiple times"Two modules provide the same typeAdd qualifiers or remove duplicate binding
"depends on scoped components"Scope mismatchMatch scope to the shortest-lived consumer
"found a dependency cycle"A → B → A circular dependencyUse Provider<T> to break the cycle

@HiltViewModel vs SavedStateHandle

// SavedStateHandle is automatically available in @HiltViewModel constructors
@HiltViewModel
class ProductDetailViewModel @Inject constructor(
    private val savedStateHandle: SavedStateHandle,  // injected by Hilt — no @Provides needed
    private val getProduct: GetProductUseCase
) : ViewModel() {
    private val productId = requireNotNull(savedStateHandle.get<String>("product_id"))
}

7. Interview Framework

30-Second Answer

"Hilt has a predefined component hierarchy that mirrors the Android lifecycle: SingletonComponent (app lifetime), ActivityRetainedComponent (survives rotation), ViewModelComponent (ViewModel lifetime), ActivityComponent (Activity instance), FragmentComponent. Dagger generates Factory classes at compile time for each injectable type, validates the entire graph, and catches missing bindings as build errors. When you annotate a ViewModel with @HiltViewModel, Dagger generates a Factory for it that the ViewModelProvider uses to create instances with injected dependencies."

2-Minute Deep Dive

"The key lifecycle insight: ActivityRetainedComponent survives configuration changes — that's the component behind ViewModel's survival. ActivityComponent does not survive rotation. So @ActivityRetainedScoped dependencies persist through rotation; @ActivityScoped ones don't. A scope mismatch — injecting an ActivityScoped dependency into an ActivityRetainedScoped class — is a compile-time error, not a runtime bug. Under the hood, Dagger runs as an annotation processor (kapt or KSP), reads all the annotations, and emits Java classes: a Factory per injectable class, an implementation class for each component. The factory pattern means every instantiation is explicit and traceable. For ViewModel injection specifically, Dagger generates a ViewModelFactory entry into the ViewModelComponent, and Hilt's DefaultViewModelFactories bridges that to Android's ViewModelProvider."

Must-Mention Points

1
Component hierarchy: Singleton → ActivityRetained → ViewModel → Activity → Fragment — child can access parent bindings
2
ActivityRetained ≠ Activity: survives rotation; ActivityScoped does not
3
Compile-time generation: Dagger (kapt/KSP) generates Factory classes and Component impls at build time
4
@HiltViewModel generates a Factory: registered in ViewModelComponent, used by Hilt's DefaultViewModelFactories
5
Graph validation at compile time: missing bindings, scope mismatches, circular deps = build errors
6
All Hilt components are SubComponents: full parent binding access — no explicit exposure needed

Do NOT Go Deeper On

  • Raw Dagger SubComponent annotation syntax (Hilt abstracts it away)
  • kapt vs KSP implementation details (just say "annotation processing")

Follow-up Q&A

QuestionAnswer
"Why does Hilt use SubComponents instead of Component dependencies?"SubComponents have full access to parent bindings — simpler for Android where components naturally nest (Fragment inside Activity inside Application). Component dependencies require explicit exposure of each binding, which is more verbose for the standard hierarchy.
"How does SavedStateHandle work with Hilt?"Hilt automatically provides SavedStateHandle in the ViewModelComponent — no @Provides needed. It's created from the Activity's or Fragment's saved state bundle.
"What's the difference between Provider<T> and Lazy<T>?"Provider<T>: new instance on each get() call. Lazy<T>: first get() creates the instance and caches it — same instance on subsequent calls.

Senior Insight

Senior Signal
Understanding what Dagger generates is what separates Hilt users from Hilt practitioners. When you add @Singleton to a class, you're not adding concurrency safety — you're telling Dagger to reuse one instance in the SingletonComponent. If the class has mutable state, you still need synchronisation. The scope only controls how many instances Dagger creates; you're responsible for thread safety inside the instance.

9. Interview Questions
Basic List the Hilt component hierarchy from outermost to innermost. ⌄
SingletonComponent (Application) → ActivityRetainedComponent → ViewModelComponent and ActivityComponent (siblings) → FragmentComponent (child of Activity) → ViewComponent. ServiceComponent runs parallel to the Activity hierarchy, created/destroyed with a Service.
Basic What does Dagger generate when you annotate a class with @Inject constructor? ⌄
Dagger generates a Foo_Factory class that implements Factory<Foo>. The factory has a get() method that creates an instance of Foo by calling its constructor with the required dependencies (obtained from their own Providers). The factory is also used by Dagger to respect scope — if Foo is @Singleton, the component wraps the factory with a DoubleCheck to create only one instance.
Basic What is the difference between @ActivityScoped and @ActivityRetainedScoped? ⌄
@ActivityRetainedScoped: the instance lives inside ActivityRetainedComponent, which is preserved across configuration changes (rotation). One instance per Activity "logical session".

@ActivityScoped: the instance lives inside ActivityComponent, which is destroyed and recreated on rotation. A new instance is created every time the Activity is recreated. Use ActivityScoped for things that depend on the specific Activity instance (e.g., a Navigator using startActivity()).
Intermediate What does Dagger generate for a @HiltViewModel-annotated ViewModel? ⌄
Dagger generates: (1) A ViewModel_Factory that creates the ViewModel with all its injected constructor parameters. (2) A module that provides this factory, installed in the ViewModelComponent. (3) An entry point that Hilt's DefaultViewModelFactories can query to obtain the factory for a specific ViewModel class. When you call viewModels(), Android's ViewModelProvider asks Hilt's factory for the ViewModel type; Hilt looks up the generated factory and creates the ViewModel with injected dependencies.
Intermediate Explain how a child component accesses parent bindings. ⌄
In Hilt, all components are SubComponents. A SubComponent holds a reference to its parent component instance. When a binding is requested in a child component, Dagger first looks in the child's own modules. If not found, it looks in the parent's modules, then the grandparent's, up the hierarchy. This is why a FragmentComponent can inject a @Singleton-scoped OkHttpClient defined in the SingletonComponent — the request propagates up until it's satisfied. This is implicit in Hilt; with raw Dagger Component dependencies, you'd need to explicitly expose each binding.
Intermediate How does Hilt validate the dependency graph at compile time? ⌄
Dagger runs as an annotation processor (kapt or KSP). During the processing phase, it reads all @Module, @Provides, @Binds, @Inject annotations and builds an in-memory graph. Before generating any code, it validates: (1) every requested type has exactly one binding, (2) scope annotations are consistent (no parent-scope type in child component), (3) no cycles, (4) no duplicate bindings. Any violation produces a compiler error with a clear message pointing to the offending class. This happens before .class files are generated, so no runtime overhead.
Intermediate When would you use Provider<T> vs regular injection? ⌄
Use Provider<T> when: (1) You need a fresh instance on each call (not a singleton). (2) The dependency is expensive and may not always be needed — defer creation until first use. (3) You have a circular dependency — Provider<T> breaks the cycle because Dagger doesn't resolve T immediately on component creation. (4) The dependency comes from a child scope and you need to access the current instance at call time (e.g., getting the current Activity's Navigator from a longer-lived class).
Senior How does @Singleton scope work at the Dagger level — what code is generated? ⌄
When you scope a binding with @Singleton, Dagger wraps the generated Factory with a DoubleCheck wrapper in the component implementation. The simplified generated code:

private volatile Object myService = UNINITIALIZED;
On get(): checks if myService == UNINITIALIZED. If so, synchronized(this) check again, then create and store. Otherwise return the cached instance. This is the classic double-checked locking pattern.

Important: @Singleton does NOT make the class thread-safe internally. It only guarantees that Dagger creates one instance. If the class has mutable state accessed from multiple threads, you still need synchronisation inside the class.
Senior A Hilt build fails with "cannot be provided without an @Provides-annotated method" for a class that does have @Inject constructor. What are the possible causes? ⌄
1. One of the constructor's parameters is the missing binding — not the annotated class itself. Read the full error: Dagger traces the chain from the requesting site down to the unresolved leaf.
2. The class is in a Gradle module that isn't visible to the Hilt component module — transitive dependency not configured.
3. The class is abstract or an interface — @Inject constructor doesn't work on interfaces; you need @Binds.
4. Module is not installed — the @Module class exists but @InstallIn is missing or uses the wrong component.
5. Qualifier mismatch — the requesting site has a qualifier annotation but no binding with that qualifier exists.
Senior Design a multi-module Hilt setup for a feature module that needs to register its own bindings. ⌄
In a multi-module app, each feature module can define its own Hilt modules. Hilt aggregates them automatically at compile time via the app module's Hilt component:

:feature:payments module: @Module @InstallIn(SingletonComponent::class) abstract class PaymentModule { @Binds abstract fun bindPaymentRepo(impl: PaymentRepositoryImpl): PaymentRepository }

:app module: just needs @HiltAndroidApp on the Application class. Hilt's annotation processing scans all included modules and their transitive dependencies, finds all @InstallIn modules, and includes them in the generated component.

Key rule: the feature module must be on the compile-time classpath of the app module. Dynamic feature modules (DFM) require a separate Hilt component since they're loaded at runtime — use @DefineComponent for custom components in DFMs.
