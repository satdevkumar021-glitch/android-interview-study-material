30A — Offline-First Product Catalog

Design an Android product catalog with offline browsing, search, pagination, and background sync — a complete senior-level system design answer covering architecture, data flow, trade-offs, and failure handling.

ID: 30A ★ Senior Differentiator
🔍
1. Problem Statement

Requirements

Functional

  • Browse product catalog with infinite scroll / pagination
  • Search products by name, category, or price range
  • View product detail (images, description, price, availability)
  • Offline access: catalog usable without internet connection
  • Push catalog updates: price changes, new arrivals visible on next launch

Non-Functional

  • Fast initial load — no blank screen while fetching
  • No duplicate products on pagination
  • Battery efficient background sync
  • Handle device variety: low-end phones with limited storage

Constraints & Assumptions

  • REST API for product catalog (cursor-based pagination)
  • ~10,000 products total, 20 per page
  • Catalog updated daily by backend team
  • Users expected to browse offline in areas with poor connectivity

3. Data Flow

Online Flow — First Launch

App launch
  → CatalogViewModel creates Flow<PagingData>
  → Pager emits initial load request
  → RemoteMediator.load(REFRESH)
      → Fetch products/page=1 from API
      → Insert into Room (transaction: clear + insert)
  → Room PagingSource auto-invalidates
  → UI receives PagingData from Room → displays products
  → User scrolls near end
  → RemoteMediator.load(APPEND)
      → Fetch page 2 from API → insert into Room
  → UI updates with new items

Offline Flow

App launch (no internet)
  → RemoteMediator.load(REFRESH) fails
  → Returns MediatorResult.Error(NetworkException)
  → Room PagingSource serves existing cached data immediately
  → UI shows: "Showing cached data" banner
  → NetworkConnectivityObserver emits true (connected)
  → App triggers refresh() on PagingData
  → RemoteMediator.load(REFRESH) succeeds → fresh data

Background Sync Flow

WorkManager PeriodicWorkRequest (every 6 hours, on WiFi + charging)
  → CatalogSyncWorker.doWork()
      → Fetch updated catalog from API
      → Insert/update products in Room
      → Room invalidates PagingSource
      → If app is in foreground: UI auto-updates
      → If app is in background: fresh cache ready on next launch

Search Flow

User types in search box
  → searchQuery StateFlow debounced (300ms)
  → flatMapLatest: new Pager with search query param
  → ProductApi.search(query, page) → new RemoteMediator
  → OR: local Room FTS5 search for offline search

4. Key Design Decisions

1. Single Source of Truth = Room

The UI never reads directly from the network. Retrofit data goes to Room, and Room feeds the UI via PagingSource. This ensures offline reads are seamless and the UI always has consistent data regardless of network state.

2. Stale-While-Revalidate Pattern

Show cached data immediately on launch, then fetch fresh data in background. Users see content instantly — the catalog updates underneath. Implemented via: Room PagingSource loads immediately while RemoteMediator refreshes asynchronously.

3. WorkManager for Background Sync

val constraints = Constraints.Builder()
    .setRequiredNetworkType(NetworkType.CONNECTED)
    .setRequiresBatteryNotLow(true)
    .build()

val syncWork = PeriodicWorkRequestBuilder<CatalogSyncWorker>(6, TimeUnit.HOURS)
    .setConstraints(constraints)
    .setBackoffCriteria(BackoffPolicy.EXPONENTIAL, 30, TimeUnit.SECONDS)
    .build()

WorkManager.getInstance(context).enqueueUniquePeriodicWork(
    "catalog_sync",
    ExistingPeriodicWorkPolicy.KEEP,
    syncWork
)

4. NetworkConnectivityObserver

class NetworkConnectivityObserver @Inject constructor(
    @ApplicationContext context: Context
) {
    private val connectivityManager =
        context.getSystemService(ConnectivityManager::class.java)

    val isConnected: Flow<Boolean> = callbackFlow {
        val callback = object : ConnectivityManager.NetworkCallback() {
            override fun onAvailable(network: Network) { trySend(true) }
            override fun onLost(network: Network) { trySend(false) }
        }
        connectivityManager.registerDefaultNetworkCallback(callback)
        awaitClose { connectivityManager.unregisterNetworkCallback(callback) }
    }.distinctUntilChanged()
}

6. Scalability & Failure Handling

Scaling to Larger Catalogs

  • Storage pruning: Don't store entire 10K catalog on device. Store last N pages viewed (keep 100 most recent items, prune on sync). Use Room entity with last_accessed timestamp.
  • Partial sync: API supports ?updated_after=timestamp — sync only changed products, not full catalog
  • Category-based prefetch: Pre-sync only the category the user most recently viewed
  • Image caching: Coil's disk cache handles product images; set max disk cache size per available storage

Multi-Module Architecture

:feature:catalog  → CatalogScreen, CatalogViewModel
:feature:search   → SearchScreen, SearchViewModel
:core:product     → ProductRepository, ProductApi, ProductDao, RemoteMediator
:core:database    → Room setup, AppDatabase
:core:network     → Retrofit, OkHttp, interceptors
:core:sync        → CatalogSyncWorker, NetworkConnectivityObserver

Testing Strategy

  • Unit tests: ProductRepository with FakeProductApi + in-memory Room
  • PagingSource tests: TestPagingDataDiffer to collect paginated items
  • RemoteMediator tests: Mock API responses, verify Room state after each LoadType
  • E2E tests: Maestro or Espresso for offline catalog browsing flow

7. Interview Framework

30-Second Answer

"I'd use an offline-first architecture with Room as the single source of truth. Retrofit fetches from the API via a RemoteMediator, writes to Room, and the UI reads from Room via Paging 3's PagingSource — so it always has data even offline. Background sync runs via WorkManager on a 6-hour schedule when connected. Network state is observed as a Flow to show offline banners and trigger re-sync when reconnected."

2-Minute Answer

"The key insight is stale-while-revalidate: show cached data immediately, refresh in the background. Architecture: Compose UI → CatalogViewModel → GetProductsUseCase → ProductRepository. The repository creates a Pager with a RemoteMediator and Room's auto-generated PagingSource. RemoteMediator handles network: on REFRESH it clears Room and loads page 1; on APPEND it loads the next page and inserts. Room's InvalidationTracker auto-invalidates the PagingSource when RemoteMediator writes, so the UI updates automatically. For offline: if RemoteMediator fails, Room still serves the last cached data — the user sees products with an 'offline' banner. Search works both online (API query) and offline (Room FTS5). Background sync via WorkManager with constraints: connected, battery not low — keeps catalog fresh without draining battery. NetworkConnectivityObserver as a Flow<Boolean> triggers refresh when connectivity returns."

9. Interview Questions
1. What does "single source of truth" mean in offline-first architecture?
Basic⌄
Room (local database) is the only source the UI reads from. The network is a supplier of data INTO Room, not a direct source for the UI. This ensures: (a) offline works — Room always has data, (b) UI is consistent — no race between network response and cache, (c) reactivity — Room's LiveData/Flow notifies UI when data changes from any source. Network data → Room → UI (always via Room).
2. How does RemoteMediator know which page to load next after app restart?
Basic⌄
RemoteKeys table in Room stores the last fetched page key (cursor or offset). On APPEND, RemoteMediator reads the last key from RemoteKeysDao.getLastKey() to determine which page to fetch next. On REFRESH, it clears the RemoteKeys table along with the product data. Without this table, after app restart APPEND would have no idea where pagination left off and would restart from page 1.
3. What is the stale-while-revalidate pattern?
Basic⌄
Show cached (potentially stale) data immediately to the user, then fetch fresh data in the background and update the UI when it arrives. Users see content instantly — no empty screen. The catalog may be hours old on first render, but updates within seconds as the background fetch completes. This is the best pattern for catalogs: it optimizes perceived performance while ensuring data freshness.
4. How do you implement offline search?
Intermediate⌄
Room supports FTS5 (Full Text Search) virtual tables. Define a @Fts4 or @Fts5 entity and create a shadow FTS table. ProductFts entity with content relationship to Product. Room generates efficient full-text search queries using MATCH operator. For online search: use API search endpoint. Strategy: if connected, use API search for fresh results; if offline, fall back to Room FTS search on cached data. Show "searching cached data" indicator when offline.
5. How do you detect when the device goes offline and comes back online?
Intermediate⌄
Use ConnectivityManager.registerDefaultNetworkCallback() wrapped in a callbackFlow. Emit true in onAvailable, false in onLost. Use distinctUntilChanged() to avoid duplicate emissions. Expose as Flow<Boolean> from a singleton NetworkConnectivityObserver (Hilt @Singleton). In ViewModel: collect isConnected, when it transitions to true call pagingData.refresh(). In UI: show/hide offline banner based on connectivity state.
6. What WorkManager constraints would you use for catalog sync?
Intermediate⌄
setRequiredNetworkType(NetworkType.CONNECTED) — don't sync without network. setRequiresBatteryNotLow(true) — don't drain low battery. Optional: setRequiresCharging(true) for large syncs only. Use PeriodicWorkRequest with 6-hour interval for catalog freshness. Use ExistingPeriodicWorkPolicy.KEEP to prevent duplicate schedules. Add exponential backoff for retry on failure. For immediate sync on reconnect, schedule a OneTimeWorkRequest with the same worker when connectivity is restored.
7. How would you handle a product catalog of 1 million items on a mobile device?
Senior⌄
Don't cache 1M items locally — that's 100MB+. Instead: (1) Cache only recently viewed categories/pages (LRU eviction policy in Room — prune items not accessed in 7 days). (2) Use partial sync: API endpoint GET /catalog?updated_after={timestamp} — only sync changed items. (3) Use server-side search — don't build local FTS for 1M items. (4) Category-level caching: user's most-browsed categories get deeper local cache; others get minimal cache. (5) Track storage budget: check available device storage, reduce cache size if low.
8. Design the Room schema for this system.
Senior⌄
Tables: (1) products(id, name, description, price, category, image_url, last_synced_at) — main catalog. (2) remote_keys(id, prev_key, next_key) — pagination state for RemoteMediator. (3) categories(id, name) — for category filter. (4) product_fts USING fts5(content=products) — virtual FTS table for offline search. (5) sync_metadata(key, last_sync_at) — track when last sync occurred. Indices: products(category), products(last_synced_at) for pruning queries.
9. How do you show "last updated X minutes ago" to the user?
Scenario⌄
Store last_sync_at timestamp in Room (a sync_metadata table or SharedPreferences). Expose it as Flow<Long?> from a SyncMetadataRepository. In ViewModel: combine isConnected flow with lastSyncAt flow → compute age string ("Last updated 3 min ago", "Offline — last updated 2 hours ago"). Update last_sync_at in RemoteMediator after successful REFRESH. If last_sync_at is null: never synced (first install). Show "Loading..." until first sync completes.
10. Walk through what happens when a user opens the app in airplane mode for the first time.
Scenario⌄
First install, airplane mode: (1) CatalogViewModel starts flow. (2) Pager triggers RemoteMediator.load(REFRESH). (3) RemoteMediator tries API → IOException. Returns MediatorResult.Error. (4) Room PagingSource has zero items (empty database). (5) UI receives empty PagingData + loadState.refresh is Error. (6) Show empty state screen: "No internet connection. Please connect to load the catalog." with a "Retry" button. (7) User turns off airplane mode → NetworkConnectivityObserver emits true → ViewModel calls refresh() → RemoteMediator succeeds → products appear. This is the correct UX — graceful empty state, not a crash.
