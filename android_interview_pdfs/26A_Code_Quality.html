2. Android Lint

What Lint Checks

  • API level: using APIs not available on minSdk
  • Performance: unused resources, overdraw warnings
  • Security: hardcoded API keys, world-readable files
  • Correctness: wrong XML attribute usage, missing translations
  • Accessibility: missing content descriptions on ImageViews
// Running lint:
// ./gradlew lintDebug
// Report: app/build/reports/lint-results-debug.html

// Suppressing a single lint warning:
@SuppressLint("SetJavaScriptEnabled")
fun setupWebView(webView: WebView) {
    webView.settings.javaScriptEnabled = true  // intentional
}

// Suppressing in XML:
// tools:ignore="ContentDescription"

Lint Baseline File

For legacy codebases with hundreds of existing lint issues, a baseline file lets you suppress all current issues and only fail on new ones introduced after the baseline was created.

// Generate a baseline:
// ./gradlew lintDebug -Dlint.baselines.continue=true
// Creates: app/lint-baseline.xml

// Enable in build.gradle.kts:
android {
    lint {
        baseline = file("lint-baseline.xml")
        warningsAsErrors = true
        abortOnError = true
    }
}
// Now CI fails only on NEW lint issues — a ratchet pattern

Custom Lint Rules

// Custom Lint rule — detects direct use of android.util.Log in production code
class NoDirectLogDetector : Detector(), UastScanner {
    override fun getApplicableMethodNames() = listOf("d", "e", "i", "w", "v")
    override fun visitMethodCall(context: JavaContext, node: UCallExpression, method: PsiMethod) {
        if (context.evaluator.isMemberInClass(method, "android.util.Log")) {
            context.report(ISSUE, node, context.getLocation(node),
                "Use Timber instead of android.util.Log")
        }
    }
}

3. Detekt & Ktlint

Detekt — Kotlin Static Analysis

// build.gradle.kts (root)
plugins {
    id("io.gitlab.arturbosch.detekt") version "1.23.6"
}
detekt {
    config.setFrom("config/detekt.yml")
    baseline = file("config/detekt-baseline.xml")
    buildUponDefaultConfig = true
}
# config/detekt.yml — example rules
complexity:
  LongMethod:
    active: true
    threshold: 60         # fail if method > 60 lines
  ComplexMethod:
    active: true
    threshold: 15         # cyclomatic complexity
naming:
  FunctionNaming:
    active: true
style:
  MagicNumber:
    active: true
    ignoreNumbers: ['-1','0','1','2']

4. SonarQube & Coverage

SonarQube / SonarCloud

SonarQube aggregates lint, coverage, duplication, and complexity into a single dashboard with quality gates. SonarCloud is the hosted version — easier to set up for open source and small teams.

MetricWhat it measuresThreshold example
Coverage% of code covered by tests≥ 80% on new code
Duplications% of duplicated code blocks≤ 3%
Technical debtEstimated hours to fix all issuesDebt ratio ≤ 5%
Reliability ratingBug count → A/B/C/D/E≥ A (0 bugs)
Security ratingVulnerability count → A/B/C/D/E≥ A (0 vulnerabilities)

Quality Gate
A quality gate is a threshold that must pass for a build to be considered "green." SonarQube's default quality gate fails if: new code coverage < 80%, new code has any blocker/critical bugs, or reliability rating is worse than A. This is the definition of "done" for a story or PR.

5. Code Review Practices

What to Check in a Code Review

CategoryWhat to look for
Logic correctnessDoes the code do what it claims? Edge cases handled? Off-by-one errors?
NamingDescriptive names? No cryptic abbreviations? Consistent with codebase style?
Test coverageAre new code paths tested? Happy path + error path + edge cases?
PerformanceN+1 queries? Blocking main thread? Memory leaks?
SecurityHardcoded secrets? SQL injection? Insecure network? Sensitive data logged?
ArchitectureCorrect layer? ViewModel not touching View? Repository not calling ViewModel?
Android-specificContext leaks? Wrong lifecycle scope? Background work on main thread?

What NOT to do in Code Review

  • Don't debate formatting — that's Ktlint's job (automate it)
  • Don't nitpick style preferences — configure them in Detekt/Ktlint once
  • Don't approve PRs with failing CI — CI must be green before merge
  • Don't leave vague comments — be specific about what to change and why
Review Efficiency Tip
Automate everything that can be automated (formatting, lint, style) so human reviewers focus on what machines can't check: logic correctness, architecture decisions, test quality, and security.

6. Technical Debt Management

What is Technical Debt?

Technical debt is the implied cost of future rework caused by choosing a fast/easy solution now instead of the better approach. SonarQube estimates it in hours based on issue count and complexity.

Debt Prioritization

SeverityPriorityExamples
BlockerFix immediately — don't shipNullPointerException risk, data corruption
CriticalFix in current sprintSecurity vulnerability, major performance issue
MajorSchedule in backlogComplex method, code duplication, missing test
Minor/InfoFix opportunisticallyNaming issues, formatting, minor style

Managing Legacy Debt

  • Lint baseline: suppress existing issues, fail only on new ones (ratchet pattern)
  • Detekt baseline: same approach for Detekt issues
  • Boy Scout Rule: leave every file you touch slightly better than you found it
  • Refactor sprints: schedule periodic debt-reduction work alongside features
  • Debt ratio tracking: SonarQube shows debt ratio over time — ensure it trends down

7. Interview Framework

30-Second Answer

"We use a layered quality toolchain: Ktlint for formatting (no debates in PR reviews), Detekt for Kotlin static analysis, Android Lint with a baseline file for legacy issues, JaCoCo for test coverage, and SonarQube as the aggregation platform with quality gates. Every PR must pass all tools before merge."

2-Minute Answer

"Code quality tools each serve a distinct role. Ktlint enforces formatting automatically — it removes subjective style debates from code reviews. Detekt catches code smells: overly complex methods, magic numbers, naming violations. Android Lint catches Android-specific issues like missing translations, deprecated APIs, and security issues. For legacy codebases, I use Lint and Detekt baseline files — these suppress existing issues so CI only fails on new ones, creating a ratchet that prevents regression without requiring a big-bang cleanup. JaCoCo measures test coverage, and I target 80% on new code. SonarQube or SonarCloud aggregates all of this with quality gates — a PR can't merge if it introduces bugs or drops coverage below the threshold. Code reviews then focus on what tools can't check: logic correctness, architecture adherence, security, and test quality."

Each tool has a distinct role: Ktlint (format) → Detekt (code smells) → Lint (Android issues) → JaCoCo (coverage) → SonarQube (aggregate)

Senior Insight

Senior Differentiator
Custom Lint rules are a senior-level skill. When your team repeatedly makes the same mistake (e.g., calling android.util.Log directly, using hardcoded color values instead of theme attributes), write a custom Lint rule that fails CI. This is infinitely more effective than adding it to the code review checklist.

9. Interview Questions
1. What is the difference between Android Lint, Detekt, and Ktlint?
Basic⌄
Android Lint: built-in, finds Android-specific issues (wrong API level, missing translations, security). Detekt: Kotlin static analysis for code quality — complexity, naming, style, potential bugs. Ktlint: formatting ONLY — enforces the Kotlin style guide (indentation, spacing, trailing commas). All three complement each other and should run in CI.
2. What is a Lint baseline file and why is it useful?
Basic⌄
A baseline file records all existing Lint issues at a point in time. CI is then configured to suppress all baselined issues and fail only when NEW issues are introduced. This is the "ratchet" pattern — it lets you adopt strict Lint enforcement in a legacy codebase without requiring a big-bang cleanup. Over time, fix issues and regenerate the baseline to shrink it.
3. What is a SonarQube quality gate?
Basic⌄
A quality gate is a set of conditions that code must meet to be considered releasable. Default conditions: new code coverage ≥ 80%, 0 new blocker or critical issues, reliability rating A, duplication ≤ 3%. If any condition fails, the SonarQube status is "failed" and CI can be configured to block the PR merge.
4. How do you measure test coverage in Android?
Intermediate⌄
Enable JaCoCo in Android build config: enableUnitTestCoverage = true in the debug buildType. Run ./gradlew testDebugUnitTest jacocoTestReport. This generates XML + HTML reports in build/reports/jacoco/. Upload the XML report to SonarQube or Codecov for tracking and quality gate enforcement. Note: JaCoCo measures unit test coverage; instrumented test coverage requires a separate configuration.
5. What should code reviewers focus on vs what should be automated?
Intermediate⌄
Automate: formatting (Ktlint), code style (Detekt), Android-specific issues (Lint), test coverage thresholds (JaCoCo/SonarQube). Human reviewers should focus on: logic correctness, edge cases, security, architecture adherence, test quality (are the right things tested?), naming clarity, and performance pitfalls. Never debate tabs vs spaces in reviews — configure it once in Ktlint.
6. How do you manage technical debt in a large codebase?
Intermediate⌄
Use SonarQube debt ratio to track total debt over time. Prioritize: fix blockers immediately, schedule criticals this sprint, major debt goes in the backlog. Use Lint/Detekt baselines as a ratchet — prevent new debt while gradually clearing old debt. Apply the Boy Scout Rule — leave code better than you found it. Periodically schedule refactor sprints alongside feature work. Never let debt ratio increase sprint over sprint.
7. How do you write a custom Android Lint rule?
Intermediate⌄
Create a separate Java/Kotlin module with lint-api dependency. Extend Detector and implement the appropriate Scanner interface (UastScanner for Kotlin/Java code, XmlScanner for XML). Override getApplicableMethodNames() or getApplicableElements() to specify what to analyze. In visitMethodCall() or visitElement(), use context.report() to flag issues. Define an Issue object with id, description, severity, and category. Register the rule in a custom IssueRegistry. Include the module as a lintChecks dependency.
8. You join a team with 500 Lint warnings. How do you introduce strict Lint enforcement without blocking the team?
Senior⌄
1) Generate a Lint baseline file today: ./gradlew lintDebug -Dlint.baselines.continue=true. 2) Add the baseline.xml to source control. 3) Enable lint { warningsAsErrors = true; abortOnError = true } in build.gradle.kts. 4) CI now only fails on new issues — existing 500 are suppressed. 5) In backlog, schedule sprints to fix high-severity issues and shrink the baseline. 6) Track baseline issue count in SonarQube over time — ensure it trends to zero.
9. What Detekt rules are most valuable for Android Kotlin code?
Senior⌄
Most valuable: LongMethod (methods over ~40-60 lines are hard to test), ComplexMethod (cyclomatic complexity > 10 indicates need to split), MagicNumber (unexplained literals should be named constants), UnusedPrivateMember (dead code), SwallowedException (catch blocks that ignore exceptions hide bugs), ForbiddenComment (TODO/FIXME tracking), and TooManyFunctions (class doing too much — SRP violation). Configure thresholds in detekt.yml to match team standards.
10. How does code coverage differ from code quality?
Scenario⌄
Coverage measures what percentage of code is executed by tests. Quality measures whether tests are meaningful. 100% coverage can coexist with terrible tests — if tests have no assertions, every line is "covered" but nothing is verified. Good tests: test behavior not implementation, cover happy + error + edge paths, are deterministic, and fail meaningfully when production code breaks. Coverage is a necessary but not sufficient indicator of quality. Aim for high coverage AND meaningful assertions — code review of tests is as important as code review of production code.
