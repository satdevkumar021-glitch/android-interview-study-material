1. Overview

Paging 3 Architecture

Repository layer:
  PagingSource<Key, Value>  ← single data source (network OR database)
  RemoteMediator             ← network + database (offline-first)
  Pager(config, source)     ← orchestrates loading
    └── Flow<PagingData<T>> ← stream of paginated data

ViewModel layer:
  Flow<PagingData<T>>.cachedIn(viewModelScope)

UI layer:
  LazyPagingItems<T>         ← Compose
  PagingDataAdapter           ← RecyclerView
Senior Mental Model
Paging 3 is a reactive pagination library. The UI never directly requests pages — it signals loading triggers (prefetch distance reached), and the Pager + PagingSource respond asynchronously. The key design: PagingSource for single source, RemoteMediator for network+database (offline-first). Room automatically generates PagingSource from @Query — no manual implementation needed.

2. PagingSource
// PagingSource<Key, Value>
// Key: type of page key (Int for offset, String for cursor)
// Value: type of data items
class ProductPagingSource(
    private val api: ProductApiService
) : PagingSource<Int, Product>() {

    override suspend fun load(params: LoadParams<Int>): LoadResult<Int, Product> {
        val page = params.key ?: 1  // default to first page
        return try {
            val response = api.getProducts(page = page, pageSize = params.loadSize)
            LoadResult.Page(
                data = response.products,
                prevKey = if (page == 1) null else page - 1,
                nextKey = if (response.isLastPage) null else page + 1
            )
        } catch (e: Exception) {
            LoadResult.Error(e)
        }
    }

    // Called when data is invalidated (refresh signal)
    override fun getRefreshKey(state: PagingState<Int, Product>): Int? {
        // Return the page key for the anchor position (item closest to viewport center)
        return state.anchorPosition?.let { anchor ->
            state.closestPageToPosition(anchor)?.let { page ->
                page.prevKey?.plus(1) ?: page.nextKey?.minus(1)
            }
        }
    }
}

LoadResult Types

TypeMeaning
LoadResult.Page(data, prevKey, nextKey)Successful page load. null prevKey = no more previous pages. null nextKey = no more next pages.
LoadResult.Error(throwable)Load failed. Paging delivers CombinedLoadStates.append/prepend.error to the UI.
LoadResult.InvalidSource invalidated — Pager will create a new PagingSource

3. Pager & PagingData

Repository — creating the paged stream

class ProductRepository @Inject constructor(
    private val api: ProductApiService
) {
    fun getProductsPaged(): Flow<PagingData<Product>> = Pager(
        config = PagingConfig(
            pageSize = 20,             // items per page
            prefetchDistance = 5,       // load next page when 5 items from end
            initialLoadSize = 40,       // first load: 2× pageSize for faster initial display
            enablePlaceholders = false  // set true for known total count
        ),
        pagingSourceFactory = { ProductPagingSource(api) }
    ).flow
}

ViewModel — cache the flow

@HiltViewModel
class ProductViewModel @Inject constructor(
    repository: ProductRepository
) : ViewModel() {

    val products: Flow<PagingData<Product>> = repository
        .getProductsPaged()
        .cachedIn(viewModelScope)  // IMPORTANT: cache survives rotation
}
cachedIn is Required
Without .cachedIn(viewModelScope), every collector (including rotation) restarts the flow from scratch — losing loaded pages. cachedIn stores the last emitted PagingData in the ViewModel scope, surviving recomposition and configuration changes.

4. RemoteMediator (Offline-First)

Architecture: Network + Database Paging

// RemoteMediator fetches from network, stores in Room
// The UI always reads from Room (single source of truth)
// RemoteMediator is the "middleware" that keeps Room fresh

@OptIn(ExperimentalPagingApi::class)
class ProductRemoteMediator(
    private val api: ProductApiService,
    private val db: AppDatabase
) : RemoteMediator<Int, ProductEntity>() {

    override suspend fun load(
        loadType: LoadType,        // REFRESH, PREPEND, or APPEND
        state: PagingState<Int, ProductEntity>
    ): MediatorResult {
        return try {
            val page = when (loadType) {
                LoadType.REFRESH -> 1     // start from beginning
                LoadType.PREPEND -> return MediatorResult.Success(endOfPaginationReached = true)
                LoadType.APPEND -> {
                    val lastKey = db.remoteKeysDao().getLastKey()
                        ?: return MediatorResult.Success(endOfPaginationReached = true)
                    lastKey + 1
                }
            }
            val response = api.getProducts(page, state.config.pageSize)
            db.withTransaction {
                if (loadType == LoadType.REFRESH) {
                    db.productDao().clearAll()   // fresh data on refresh
                    db.remoteKeysDao().clearAll()
                }
                db.productDao().insertAll(response.products.map { it.toEntity() })
                db.remoteKeysDao().insert(RemoteKey(page))
            }
            MediatorResult.Success(endOfPaginationReached = response.isLastPage)
        } catch (e: Exception) {
            MediatorResult.Error(e)
        }
    }
}
LoadType Meanings
REFRESH: initial load or explicit refresh (e.g., swipe-to-refresh). Clear old data. PREPEND: load pages before the start. Typically return Success(endOfPaginationReached = true) for typical APIs. APPEND: load next page when user scrolls to end.

5. Room + Paging Integration

Room Auto-generates PagingSource

// Room DAO — return PagingSource directly
@Dao
interface ProductDao {
    @Query("SELECT * FROM products ORDER BY name ASC")
    fun getProductsPaged(): PagingSource<Int, ProductEntity>
    // Room generates the PagingSource implementation — no code needed
}

// Repository — combine Pager + RemoteMediator + Room
@OptIn(ExperimentalPagingApi::class)
fun getProductsPaged(): Flow<PagingData<Product>> = Pager(
    config = PagingConfig(pageSize = 20),
    remoteMediator = ProductRemoteMediator(api, db),
    pagingSourceFactory = { db.productDao().getProductsPaged() }
).flow
    .map { pagingData -> pagingData.map { it.toDomain() } }

Data Flow with RemoteMediator

User scrolls → Pager signals prefetch
  → Room PagingSource serves cached items immediately (offline)
  → RemoteMediator.load(APPEND) called
      → Fetch from API
      → Store in Room (transaction)
      → Room PagingSource auto-invalidates
      → UI receives new PagingData from Room

6. Compose & API Pagination Design

LazyPagingItems in Compose

@Composable
fun ProductListScreen(viewModel: ProductViewModel = hiltViewModel()) {
    val lazyItems = viewModel.products.collectAsLazyPagingItems()

    LazyColumn {
        items(
            count = lazyItems.itemCount,
            key = lazyItems.itemKey { it.id }
        ) { index ->
            val product = lazyItems[index]  // triggers load if null (placeholder)
            if (product != null) {
                ProductItem(product = product)
            }
        }

        // Handle load states
        when (val loadState = lazyItems.loadState.append) {
            is LoadState.Loading -> item { LoadingSpinner() }
            is LoadState.Error  -> item { ErrorRetryItem { lazyItems.retry() } }
            else -> {}
        }
    }
}

API Pagination Design

StyleKeyProsCons
Offset-basedpage=2&size=20Simple, jump to any pageData shift on insert/delete — items skipped or duplicated
Cursor-basedafter=cursor_tokenConsistent — no skips with real-time dataCan't jump to arbitrary page

For real-time feeds (chat, social, catalog updates) cursor-based is strongly preferred — an item inserted at position 5 between page requests won't cause page 2 to duplicate the item that shifted from page 1.

7. Interview Framework

30-Second Answer

"Paging 3 has three core pieces: PagingSource defines how to load a page of data, Pager orchestrates loading based on config (pageSize, prefetchDistance), and PagingData is the immutable snapshot streamed as a Flow. For offline-first, RemoteMediator fetches from network, writes to Room, and Room's auto-generated PagingSource serves the UI. The ViewModel caches the flow with cachedIn(viewModelScope) so rotation doesn't reset pagination."

2-Minute Answer

"PagingSource.load() is given LoadParams (key = current page, loadSize = how many to load) and returns LoadResult.Page(data, prevKey, nextKey) or LoadResult.Error. Pager wraps it with a PagingConfig — pageSize controls items per page, prefetchDistance triggers loading N items before the visible end, initialLoadSize is typically 2× pageSize for faster initial fill. For offline-first paging, RemoteMediator handles the network+database cycle: on REFRESH it clears Room and reloads; on APPEND it fetches the next page from API and inserts into Room. Room auto-generates PagingSource from a @Query returning PagingSource<Int, Entity> — when RemoteMediator writes new rows, Room invalidates the PagingSource and new data flows to the UI. In Compose, collectAsLazyPagingItems() + LazyColumn items(count) handles display including load state monitoring for spinners and retry buttons. Always use .cachedIn(viewModelScope) in the ViewModel — without it, every new subscriber (including orientation change) restarts paging from page 1."

Must-Mention Points

1
PagingSource.load() → LoadResult.Page(data, prevKey=null at start, nextKey=null at end)
2
cachedIn(viewModelScope) — survives rotation, prevents re-pagination
3
RemoteMediator = network + Room; pagingSourceFactory = Room's auto-generated PagingSource
4
LoadType: REFRESH (clear + reload), APPEND (next page), PREPEND (usually end-of-pagination)
5
Cursor-based pagination preferred for real-time data — offset-based causes duplicates/skips

Senior Insight

Senior Differentiator
Understand that Room's PagingSource auto-invalidates when the database changes. This is the key to RemoteMediator working: you don't need to manually signal the UI to refresh — writing new rows to Room triggers PagingSource.invalidate(), which causes Pager to create a new PagingSource and the new data flows automatically. This is the reactive backbone of offline-first paging.

9. Interview Questions
1. What are the three main components of Paging 3?
Basic⌄
PagingSource: defines how to load a single page of data — takes LoadParams (key, loadSize) and returns LoadResult.Page or LoadResult.Error. Pager: orchestrates loading, manages the RecycledViewPool, and emits Flow<PagingData<T>>. PagingData: an immutable snapshot of a page — consumed by LazyPagingItems in Compose or PagingDataAdapter in RecyclerView. RemoteMediator is optional — adds network+database (offline-first) support.
2. What does prevKey and nextKey represent in LoadResult.Page?
Basic⌄
prevKey: the key to load the page BEFORE this one. null = no more previous pages (start of data). nextKey: the key to load the page AFTER this one. null = no more next pages (end of data). For offset-based: prevKey = page - 1, nextKey = page + 1. When nextKey is null, Pager stops appending and marks endOfPaginationReached = true.
3. Why is cachedIn(viewModelScope) necessary?
Basic⌄
Without cachedIn, each new collector of the Flow starts fresh — meaning every screen rotation restarts paging from page 1. cachedIn stores the latest PagingData in the ViewModel's scope. New collectors (after rotation or recomposition) immediately receive the cached PagingData — the user stays on their position in the list. It's the equivalent of calling cachedIn that creates an ActiveFlow that survives config changes.
4. What is RemoteMediator and how does it differ from PagingSource?
Intermediate⌄
PagingSource is a single data source — either network or database. RemoteMediator is the bridge between network and local database for offline-first: it fetches from the network, stores in Room, and the PagingSource reads from Room. The UI always reads from Room (single source of truth). RemoteMediator is triggered by Pager when more data is needed (based on distance to end). Room's PagingSource auto-invalidates when RemoteMediator writes new rows.
5. How does Room auto-generate PagingSource?
Intermediate⌄
Room's annotation processor generates a PagingSource implementation when a @Query method returns PagingSource<Int, Entity>. Room's implementation wraps the query in a paging strategy that: reads one page at a time (keyed by offset), observes the database for changes using InvalidationTracker, and calls PagingSource.invalidate() when the queried table changes. This auto-invalidation is what makes RemoteMediator + Room work — no manual notification required.
6. What are the three LoadType values in RemoteMediator and when does each trigger?
Intermediate⌄
REFRESH: triggered on initial load or explicit refresh (swipe-to-refresh, invalidate()). Clear existing Room data and load page 1. APPEND: triggered when the user scrolls near the end of the list (within prefetchDistance items). Load the next page, append to Room. PREPEND: triggered when scrolling near the start. For most use cases, return MediatorResult.Success(endOfPaginationReached = true) since APIs typically don't support backward pagination.
7. How do you display loading and error states in Compose with Paging 3?
Intermediate⌄
LazyPagingItems exposes loadState: CombinedLoadStates with three properties: refresh (initial load), prepend (loading more at start), append (loading more at end). Each is a LoadState: Loading, NotLoading, or Error. In LazyColumn: observe lazyItems.loadState.refresh for initial loading spinners/errors. Add an item {} inside LazyColumn for append states — LoadState.Loading shows a spinner at the bottom; LoadState.Error shows a retry button that calls lazyItems.retry().
8. Why is cursor-based pagination better than offset-based for real-time data?
Senior⌄
Offset-based: page 2 = items 21-40. If a new item is inserted at position 5 between loading page 1 and page 2, every item shifts by 1. The old item 20 is now item 21 — the first item of page 2, duplicating it. Or if an item is deleted, page 2 skips an item. Cursor-based: page 2 = "items after cursor X" where X is the ID/timestamp of the last item on page 1. Insertions elsewhere don't affect the cursor — you always get the next items relative to the stable anchor point. Essential for chat, social feeds, and any dataset with real-time mutations.
9. How do you implement swipe-to-refresh with Paging 3?
Senior⌄
Call lazyItems.refresh() to signal REFRESH to both the PagingSource and RemoteMediator. In Compose, wrap LazyColumn with PullToRefreshBox (Material3) or SwipeRefresh, binding isRefreshing to lazyItems.loadState.refresh is LoadState.Loading. The refresh() call triggers RemoteMediator.load(LoadType.REFRESH) → clears Room → fetches page 1 from API → Room auto-invalidates PagingSource → new data flows to UI. The isRefreshing indicator should go false when loadState.refresh is not Loading.
10. What is PagingConfig.enablePlaceholders and when should you enable it?
Scenario⌄
When enablePlaceholders = true, Paging shows null items for positions that haven't loaded yet — the list appears full-length immediately with skeleton/shimmer items. Requires knowing the total item count (PagingSource must set itemsBefore/itemsAfter in LoadResult.Page). When false (default), the list grows as new pages are loaded — no placeholders. Enable placeholders when: total count is known from API, items have fixed height, and you want to show scrollbar position accurately. Disable when: total count is unknown, items have variable height, or you prefer growing lists.
