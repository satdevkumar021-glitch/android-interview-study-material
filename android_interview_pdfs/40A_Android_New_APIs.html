40A — Android New APIs (Android 12–16)

Key new APIs and behavioral changes in Android 12/13/14/15/16: Predictive Back, Photo Picker, Health Connect, per-app language, Credential Manager, edge-to-edge.

ID: 40A ⭐ Tier 1 — Current APIs
🔍
1. Overview

Why This Matters

Each Android release brings APIs and behavioral changes that break existing apps. Senior developers must know what changed, what broke, and how to adapt before bumping targetSdkVersion.

Key Releases

  • Android 12 (S) — API 31/32: Splash Screen API mandatory, exported attribute crash, exact alarms restricted
  • Android 13 (T) — API 33: POST_NOTIFICATIONS runtime permission, photo picker, per-app language, granular media permissions
  • Android 14 (U) — API 34: Foreground service type mandatory, predictive back, health connect, partial media access
  • Android 15 (V) — API 35: Edge-to-edge enforcement, PDF viewer, improved NFC, app archiving
  • Android 16 (W) — API 36 (upcoming): Further edge-to-edge hardening, adaptive refresh rate, Health & Fitness API updates

Impact Areas

AreaKey Changes
Privacy / PermissionsPOST_NOTIFICATIONS, granular media, partial photo access
UI / UXSplash Screen, edge-to-edge, predictive back gesture
Background ProcessingExact alarms restricted, foreground service types required
Securityandroid:exported required, Credential Manager
Senior Mental Model
Every targetSdk bump is a compatibility contract update. You're telling Android "my app understands the behavioral changes up to API X". Never bump targetSdk without running the full behavioral-change checklist for that release.

2. How It Works — API by API

Android 12 — API 31/32

Splash Screen API (Mandatory)

All apps launching on Android 12+ show a system splash screen. You must adopt the API to customize it; without it, the system generates a generic one from your app icon.

// build.gradle
implementation("androidx.core:core-splashscreen:1.0.1")

// themes.xml
<style name="Theme.App.Starting" parent="Theme.SplashScreen">
    <item name="windowSplashScreenBackground">@color/splash_bg</item>
    <item name="windowSplashScreenAnimatedIcon">@drawable/ic_logo</item>
    <item name="postSplashScreenTheme">@style/Theme.App</item>
</style>

// MainActivity.kt
class MainActivity : ComponentActivity() {
    override fun onCreate(savedInstanceState: Bundle?) {
        val splashScreen = installSplashScreen()
        super.onCreate(savedInstanceState)
        // keep splash visible while loading data
        splashScreen.setKeepOnScreenCondition { viewModel.isLoading.value }
        setContent { MyApp() }
    }
}

android:exported — Required (Crash Risk)

Apps targeting API 31+ with Activities, Services, or BroadcastReceivers that have Intent filters must declare android:exported explicitly. Missing it causes a build failure or install crash.

<!-- AndroidManifest.xml — must be explicit -->
<activity
    android:name=".MainActivity"
    android:exported="true">      <!-- launcher activity: true -->
    <intent-filter>...</intent-filter>
</activity>

<receiver
    android:name=".MyReceiver"
    android:exported="false">    <!-- internal: false -->
    <intent-filter>...</intent-filter>
</receiver>

Exact Alarms — SCHEDULE_EXACT_ALARM

Apps must request the SCHEDULE_EXACT_ALARM permission or use canScheduleExactAlarms() to check at runtime. Most apps should use inexact alarms instead.

Android 13 — API 33

POST_NOTIFICATIONS — Runtime Permission

// Request POST_NOTIFICATIONS before showing any notification
val notificationPermission = rememberLauncherForActivityResult(
    ActivityResultContracts.RequestPermission()
) { isGranted ->
    if (!isGranted) showPermissionRationale()
}

LaunchedEffect(Unit) {
    if (Build.VERSION.SDK_INT >= Build.VERSION_CODES.TIRAMISU) {
        notificationPermission.launch(Manifest.permission.POST_NOTIFICATIONS)
    }
}

Photo / Video Picker (System Picker)

// Uses system picker — no READ_MEDIA_* permission needed
val photoPicker = rememberLauncherForActivityResult(
    ActivityResultContracts.PickVisualMedia()
) { uri ->
    uri?.let { handleSelectedPhoto(it) }
}

photoPicker.launch(PickVisualMediaRequest(ActivityResultContracts.PickVisualMedia.ImageOnly))

Granular Media Permissions

READ_EXTERNAL_STORAGE is deprecated on API 33+. Use granular permissions instead:

  • READ_MEDIA_IMAGES — access images
  • READ_MEDIA_VIDEO — access videos
  • READ_MEDIA_AUDIO — access audio

Per-App Language

// Set per-app locale (API 33+ native, backported via AppCompat)
AppCompatDelegate.setApplicationLocales(
    LocaleListCompat.forLanguageTags("hi")  // Hindi
)
// System language picker in Settings > App language from Android 13+

Android 14 — API 34

Foreground Service Type — Required

<!-- AndroidManifest.xml — must declare type -->
<service
    android:name=".SyncService"
    android:foregroundServiceType="dataSync"
    android:exported="false" />

// Service.kt — must pass type when starting
class SyncService : Service() {
    override fun onStartCommand(intent: Intent?, flags: Int, startId: Int): Int {
        val notification = buildForegroundNotification()
        if (Build.VERSION.SDK_INT >= Build.VERSION_CODES.UPSIDE_DOWN_CAKE) {
            startForeground(NOTIF_ID, notification,
                ServiceInfo.FOREGROUND_SERVICE_TYPE_DATA_SYNC)
        } else {
            startForeground(NOTIF_ID, notification)
        }
        return START_STICKY
    }
}
Breaking Change
Missing foregroundServiceType on Android 14+ throws ForegroundServiceStartNotAllowedException or MissingForegroundServiceTypeException. This silently broke many apps upgrading to targetSdk 34.

Predictive Back Gesture

// Fragment with unsaved changes — intercept back gesture
class PaymentFragment : Fragment() {
    override fun onViewCreated(view: View, savedInstanceState: Bundle?) {
        requireActivity().onBackPressedDispatcher
            .addCallback(viewLifecycleOwner) {
                if (hasUnsavedChanges) {
                    showDiscardDialog()
                } else {
                    isEnabled = false
                    requireActivity().onBackPressedDispatcher.onBackPressed()
                }
            }
    }
}

Health Connect

// Read steps from Health Connect
val client = HealthConnectClient.getOrCreate(context)

val response = client.readRecords(
    ReadRecordsRequest(
        recordType = StepsRecord::class,
        timeRangeFilter = TimeRangeFilter.between(start, end)
    )
)
val totalSteps = response.records.sumOf { it.count }

Android 15 — API 35

Edge-to-Edge (Mandatory)

// Must call enableEdgeToEdge() — content renders behind system bars
class MainActivity : ComponentActivity() {
    override fun onCreate(savedInstanceState: Bundle?) {
        super.onCreate(savedInstanceState)
        enableEdgeToEdge()  // WindowCompat.setDecorFitsSystemWindows(window, false)
        setContent {
            MyTheme {
                Scaffold(
                    modifier = Modifier.fillMaxSize()
                ) { innerPadding ->
                    // innerPadding applies WindowInsets for system bars
                    MyApp(modifier = Modifier.padding(innerPadding))
                }
            }
        }
    }
}

// For View-based layouts — handle insets manually
ViewCompat.setOnApplyWindowInsetsListener(binding.root) { view, insets ->
    val systemBars = insets.getInsets(WindowInsetsCompat.Type.systemBars())
    view.setPadding(systemBars.left, systemBars.top, systemBars.right, systemBars.bottom)
    insets
}

3. When to Use — Migration Priority

Must Fix (Breaking / App Crash)

API / ChangeTarget SDKWhat Breaks Without It
android:exported31+App won't install or crashes on launch
foregroundServiceType34+ForegroundServiceStartNotAllowedException
Edge-to-edge insets35+UI hidden behind nav bar / status bar
POST_NOTIFICATIONS permission33+All push notifications silently dropped
Granular media permissions33+SecurityException on media access

Should Migrate (UX Degradation)

API / ChangeWhy
Splash Screen APIWithout it, system generates generic splash — no branding control
Photo PickerAvoids requesting broad storage permission; better UX
Predictive BackWithout it, no back-preview animation on Android 14+
Per-app languageUsers can set language in Settings — if not supported, setting has no effect

When to Use Each API

  • Photo Picker: Any feature requiring user to select media — use it instead of file picker + storage permission. Backported to Android 4.4.
  • Health Connect: Fitness/health features. Replaces Google Fit API. Use androidx.health.connect.
  • Credential Manager: Login flows. Replaces SmartLock, Autofill with single unified API supporting passkeys, passwords, federated login.
  • Per-app language: Any app with language selection feature. Use AppCompatDelegate.setApplicationLocales().
  • Predictive Back: Any screen with custom back handling (forms, media playback, wizards).
Senior Practice
Create a per-release migration checklist tied to your CI pipeline. Each targetSdk bump should trigger a specific test suite covering the behavioral changes of that API level.

4. Production Example — targetSdk 33→35 Migration
Scenario
E-commerce app migrating from targetSdk 33 to targetSdk 35. Shows every required change, in order of priority.

Step 1 — Update build.gradle

android {
    compileSdk = 35
    defaultConfig {
        targetSdk = 35
        minSdk = 24
    }
}

Step 2 — Fix android:exported (API 31, already done at SDK 33, verify all components)

<!-- Verify every component with an intent-filter has explicit exported -->
<activity android:name=".DeepLinkActivity" android:exported="true">
    <intent-filter>
        <action android:name="android.intent.action.VIEW"/>
        <category android:name="android.intent.category.DEFAULT"/>
        <data android:scheme="myapp"/>
    </intent-filter>
</activity>

Step 3 — Add Foreground Service Types (API 34)

<!-- Order sync service -->
<service android:name=".OrderSyncService"
         android:foregroundServiceType="dataSync"
         android:exported="false"/>

<!-- Location-tracking delivery service -->
<service android:name=".DeliveryTrackingService"
         android:foregroundServiceType="location"
         android:exported="false"/>

Step 4 — Enable Edge-to-Edge (API 35)

// MainActivity.kt
override fun onCreate(savedInstanceState: Bundle?) {
    super.onCreate(savedInstanceState)
    enableEdgeToEdge()
    setContent {
        ShopTheme {
            Scaffold(
                topBar = { ShopTopBar() },
                bottomBar = { BottomNavBar() },
                modifier = Modifier.fillMaxSize()
            ) { innerPadding ->
                NavHost(
                    navController = navController,
                    modifier = Modifier.padding(innerPadding)
                ) { ... }
            }
        }
    }
}

Step 5 — Migrate Product Image Picker to Photo Picker

// Before (Android 13 — required READ_MEDIA_IMAGES permission)
// val pickImage = registerForActivityResult(GetContent()) { uri -> ... }

// After — no storage permission needed
val photoPicker = rememberLauncherForActivityResult(
    ActivityResultContracts.PickMultipleVisualMedia(maxItems = 5)
) { uris ->
    viewModel.onProductImagesSelected(uris)
}

// Launch with image+video filter, or image only
photoPicker.launch(PickVisualMediaRequest(
    ActivityResultContracts.PickVisualMedia.ImageOnly
))

Step 6 — Request POST_NOTIFICATIONS on First Launch

// In onboarding flow or post-login
if (Build.VERSION.SDK_INT >= Build.VERSION_CODES.TIRAMISU) {
    when {
        ContextCompat.checkSelfPermission(
            context, Manifest.permission.POST_NOTIFICATIONS
        ) == PackageManager.PERMISSION_GRANTED -> {
            // Already granted — proceed
        }
        shouldShowRequestPermissionRationale(Manifest.permission.POST_NOTIFICATIONS) -> {
            showNotificationRationaleDialog()
        }
        else -> {
            notificationPermissionLauncher.launch(Manifest.permission.POST_NOTIFICATIONS)
        }
    }
}

5. Alternatives & Trade-offs
ApproachProsConsVerdict
Legacy permission model (READ_EXTERNAL_STORAGE) Familiar, one permission for all files Deprecated on API 33+; SecurityException on newer devices; poor privacy UX Migrate to granular permissions + Photo Picker
New Photo Picker No storage permission needed; system-managed UI; privacy-safe; backported to API 19 Limited to images/videos; no custom UI; multi-select capped at 100 Use for all media selection
Old splash screen (themed window background) Simple — just a color or image On Android 12+, system always shows its own splash before yours: double-splash flicker Adopt Splash Screen API
Old back handling (onBackPressed()) Simple single-method override Deprecated in API 33; no predictive back gesture preview; will be removed Use OnBackPressedCallback
Predictive Back (OnBackPressedCallback) Future-proof; supports back preview animation; lifecycle-aware Slightly more code; requires enabling gesture in developer options for preview in API 33 Adopt now
SmartLock / Credentials API (legacy) Widely deployed Deprecated; no passkey support; fragmented Migrate to Credential Manager

Common Interviewer Comparisons

Expect These
  • Photo Picker vs File Picker + READ_MEDIA_IMAGES — Photo Picker requires no permission; always prefer it for user media selection
  • onBackPressed() vs OnBackPressedCallback — callback is lifecycle-aware, handles predictive back, not deprecated
  • enableEdgeToEdge() vs fitsSystemWindows — edge-to-edge gives full control; fitsSystemWindows is a coarser tool that can conflict
  • targetSdk vs compileSdk vs minSdk — compileSdk: what APIs you can reference; targetSdk: behavioral changes you opt into; minSdk: minimum device version

6. Pitfalls & Best Practices

Pitfall 1 — Forgetting android:exported

// ❌ BAD — crashes on Android 12+ if component has intent-filter
<activity android:name=".DeepLinkActivity">
    <intent-filter>...</intent-filter>
</activity>
// ✅ GOOD — always explicit
<activity android:name=".DeepLinkActivity" android:exported="true">
    <intent-filter>...</intent-filter>
</activity>

Why it matters: Apps targeting API 31+ that have components with intent-filters but no exported attribute fail at build time or crash on install. Many third-party libraries also add receivers — check merged manifest after adding deps.

Pitfall 2 — Missing foregroundServiceType

// ❌ BAD — throws MissingForegroundServiceTypeException on API 34+
<service android:name=".UploadService"/>

class UploadService : Service() {
    override fun onStartCommand(...): Int {
        startForeground(ID, notification)  // crashes on API 34+
        ...
    }
}
// ✅ GOOD — type in manifest + type in startForeground()
<service android:name=".UploadService"
         android:foregroundServiceType="dataSync"/>

if (Build.VERSION.SDK_INT >= Build.VERSION_CODES.UPSIDE_DOWN_CAKE) {
    startForeground(ID, notification, ServiceInfo.FOREGROUND_SERVICE_TYPE_DATA_SYNC)
} else {
    startForeground(ID, notification)
}

Pitfall 3 — Not Handling Edge-to-Edge on Android 15+

// ❌ BAD — content hidden behind navigation bar on API 35+
// No inset handling → bottom content clipped

// ✅ GOOD — Scaffold handles insets in Compose
Scaffold(modifier = Modifier.fillMaxSize()) { innerPadding ->
    LazyColumn(contentPadding = innerPadding) { ... }
}

// ✅ GOOD — View-based: apply insets explicitly
ViewCompat.setOnApplyWindowInsetsListener(recyclerView) { v, insets ->
    val nav = insets.getInsets(WindowInsetsCompat.Type.systemBars())
    v.setPadding(0, 0, 0, nav.bottom)
    insets
}

Pitfall 4 — Not Requesting POST_NOTIFICATIONS

On Android 13+, all notifications are silently dropped without the runtime permission, even if the channel is created. There is no crash, no error — push messages just don't appear. Test on API 33+ emulator.

Pitfall 5 — Using READ_EXTERNAL_STORAGE on API 33+

// ❌ BAD — READ_EXTERNAL_STORAGE denied on API 33+
if (Build.VERSION.SDK_INT < Build.VERSION_CODES.TIRAMISU) {
    // you're fine on 32-
} else {
    // must use READ_MEDIA_IMAGES / READ_MEDIA_VIDEO, or Photo Picker
}

Pitfall 6 — Bumping targetSdk Without Testing

Never Do This
Bumping targetSdk to comply with Play Store requirements without running a behavioral-change test pass. Google requires targetSdk 34 from August 2024, but each release has its own breaking behaviors. Always test on a physical device or emulator running that exact API level.

Best Practices

  1. Check merged manifest after adding any dependency — third-party libs add components.
  2. Use ActivityResultContracts for all permission requests — lifecycle-safe.
  3. Always call enableEdgeToEdge() at the top of onCreate(), before setContent().
  4. Test every targetSdk bump on an emulator running that exact API level.
  5. Maintain a migration checklist document per major Android release version.
  6. Add Lint checks to CI: many of these issues are caught by AndroidLint with proper targetSdk set.

7. Interview Answer Framework

30-Second Answer

"I track each Android release for breaking changes. Key recent ones: android:exported crash on 12, notification permission on 13, foreground service type on 14, and edge-to-edge enforcement on 15. Each targetSdk bump triggers a dedicated test pass covering that release's behavioral changes."

2-Minute Structured Answer

"Android 12 introduced the mandatory splash screen API and required all components with intent-filters to declare android:exported — missing it crashes the app. Android 13 added POST_NOTIFICATIONS as a runtime permission — without it, push notifications are silently dropped. It also replaced READ_EXTERNAL_STORAGE with granular READ_MEDIA_IMAGES and introduced the system photo picker which requires no permission at all.

Android 14 was a particularly breaking release: foreground services now require a foregroundServiceType in the manifest and in the startForeground() call — missing it throws an exception. It also introduced the Predictive Back gesture, requiring apps to adopt OnBackPressedCallback instead of overriding onBackPressed().

Android 15 made edge-to-edge mandatory: app content renders behind system bars and you must use WindowInsets to prevent overlaps. In Compose, Scaffold handles this automatically via innerPadding.

I maintain a per-release migration checklist and tie targetSdk bumps to a specific test suite in CI that covers each behavioral change."

Likely Follow-up Questions

QuestionShort Answer
Difference between compileSdk and targetSdk? compileSdk: which API level you compile against (can use those APIs). targetSdk: behavioral changes you opt into. You can compileSdk 35 but targetSdk 33 to avoid behavioral changes while still accessing new APIs with version checks.
What is a foreground service type? A declaration of what the service does (location, camera, mediaPlayback, dataSync, etc.) so Android can enforce appropriate restrictions and show correct permission to users.
How do you support both old and new back gesture? Use OnBackPressedCallback via onBackPressedDispatcher — it works on all API levels, supports predictive back on 14+, and handles lifecycle automatically.
Photo Picker vs ACTION_GET_CONTENT? Photo Picker: no permission, sandboxed system UI, works for images/video, backported. GET_CONTENT: requires READ_MEDIA permission, shows all file types, not sandboxed. Prefer Photo Picker for media.

9. Interview Questions (Self-Check)
How to use
Try to answer each question before revealing the answer. Click the arrow to reveal.

Basic

B1 — What change in Android 12 most commonly crashes apps that bump to targetSdk 31?
Easy▼
The missing android:exported attribute. Android 12 requires all Activities, Services, and BroadcastReceivers that have intent-filters to explicitly declare android:exported="true" or android:exported="false". If omitted, the app fails at build time (or install time) with a manifest validation error. Many apps were broken because third-party libraries also added receivers without this attribute — check the merged manifest.
B2 — What happens if you don't request POST_NOTIFICATIONS on Android 13+?
Easy▼
All notifications from your app are silently dropped. There is no crash, no exception, no error in logcat — they simply don't appear. This includes push notifications from FCM. The user also won't see any prompt asking for permission; you must explicitly request Manifest.permission.POST_NOTIFICATIONS at runtime, just like location or camera. Apps that don't do this will have silent push failures on Android 13+ devices.
B3 — What is the advantage of using the Photo Picker over requesting READ_MEDIA_IMAGES?
Easy▼
The Photo Picker requires no storage permission at all. It's a system-managed picker where the user selects media in a sandboxed UI — your app only receives the URI(s) for the specifically selected items, not broad access to the device gallery. It's better for privacy, better UX, and is backported to Android 4.4 (API 19) via Google Play Services. READ_MEDIA_IMAGES grants access to the entire images directory which is broader than needed for a single media selection.

Intermediate

I1 — What is a foreground service type and why is it required on Android 14+?
Medium▼
A foreground service type declares what job the service is doing: location, camera, microphone, dataSync, mediaPlayback, phoneCall, connectedDevice, health. Android uses this to enforce appropriate policies — for example, a service claiming location type must hold the location permission.

On Android 14+, failing to declare the type in the manifest AND pass it to startForeground() throws MissingForegroundServiceTypeException. You must also declare the corresponding permission (e.g., FOREGROUND_SERVICE_DATA_SYNC) in the manifest. The goal is to prevent apps from abusing foreground services as a background execution workaround.
I2 — How does edge-to-edge enforcement in Android 15 differ from just calling enableEdgeToEdge() on earlier versions?
Medium▼
On Android 14 and below, enableEdgeToEdge() is opt-in — the window still fits system windows by default, so content doesn't go behind bars unless you call WindowCompat.setDecorFitsSystemWindows(window, false) or enableEdgeToEdge().

On Android 15 targeting API 35, edge-to-edge is enforced by default — setDecorFitsSystemWindows(true) no longer works. Content always extends behind system bars regardless of window flags. Apps that don't handle WindowInsets will have UI elements hidden behind the navigation bar or status bar. This is a silent visual bug, not a crash — making it dangerous in production.
I3 — What replaced READ_EXTERNAL_STORAGE on Android 13+ and how do you handle backward compatibility?
Medium▼
On Android 13+, READ_EXTERNAL_STORAGE was replaced by granular media permissions:
• READ_MEDIA_IMAGES for image access
• READ_MEDIA_VIDEO for video access
• READ_MEDIA_AUDIO for audio access

For backward compatibility:
if (Build.VERSION.SDK_INT >= Build.VERSION_CODES.TIRAMISU) {
    requestPermissions(READ_MEDIA_IMAGES, READ_MEDIA_VIDEO)
} else {
    requestPermissions(READ_EXTERNAL_STORAGE)
}
However, for media selection, prefer the Photo Picker entirely — it requires no permission on any API level and is the recommended approach.
I4 — Coding Fix this service so it works on Android 14+ without crashing:
Medium▼
Problem code: 
// AndroidManifest:
<service android:name=".FileUploadService"/>

// Service:
override fun onStartCommand(...): Int {
    startForeground(NOTIF_ID, notification)
    return START_STICKY
}
Fixed code: 
// AndroidManifest: add type + permission
<uses-permission android:name=
  "android.permission.FOREGROUND_SERVICE_DATA_SYNC"/>
<service
    android:name=".FileUploadService"
    android:foregroundServiceType="dataSync"
    android:exported="false"/>

// Service: pass type on API 34+
override fun onStartCommand(...): Int {
    val notification = buildNotification()
    if (Build.VERSION.SDK_INT >= Build.VERSION_CODES.UPSIDE_DOWN_CAKE) {
        startForeground(NOTIF_ID, notification,
            ServiceInfo.FOREGROUND_SERVICE_TYPE_DATA_SYNC)
    } else {
        startForeground(NOTIF_ID, notification)
    }
    return START_STICKY
}

Senior / Scenario

S1 — Scenario Your app has a 1-star review surge after a Play Store update: "Notifications stopped working." App targets SDK 33. What happened and how do you debug?
Hard▼
Root Cause: The app bumped targetSdk from 32 to 33 without requesting POST_NOTIFICATIONS. When targeting API 33+, existing users who installed prior to the update do not automatically get the permission — their permission state is DENIED (not granted). The app never shows a permission dialog because no code requests it.

Debug Steps:
1. Confirm on a test device running API 33+: adb shell dumpsys package <app_id> | grep POST_NOTIFICATIONS — will show DENIED
2. Check FCM delivery report in Firebase Console — messages delivered but not displayed
3. Check notification channel creation logs — channels exist but permission is denied

Fix: Add POST_NOTIFICATIONS request in the main Activity or onboarding flow. For existing users, show an in-app banner explaining why notifications were silently disabled and directing them to grant permission. Handle the case where shouldShowRequestPermissionRationale() returns false (user previously denied permanently) by linking to app Settings.
S2 — Scenario After bumping targetSdk to 35, QA reports all screen bottoms are clipped on Android 15 devices. The same build works fine on Android 14. What is the cause and fix?
Hard▼
Cause: Android 15 enforces edge-to-edge by default for apps targeting API 35. Content now renders behind the navigation bar. Previously, setDecorFitsSystemWindows(true) (the default) prevented this. On API 35, this flag is ignored — content always goes edge-to-edge regardless.

Fix Strategy:
1. Call enableEdgeToEdge() in every Activity's onCreate() before setContent()
2. In Compose: use Scaffold's innerPadding to pad all scrollable content and bottom bars
3. In View-based layouts: use ViewCompat.setOnApplyWindowInsetsListener to apply WindowInsetsCompat.Type.systemBars() padding
4. Watch for custom bottom sheets, FABs, and floating elements — they need explicit bottom inset padding
5. Run screenshot tests across all major screens against an API 35 emulator in CI

Key insight: This is a silent visual bug — it doesn't crash, won't show up in ANR/crash reports, and only appears on Android 15 devices. Screenshot regression tests are the only way to catch it systematically.
S3 — How would you design a permission request flow that handles all the POST_NOTIFICATIONS edge cases on Android 13+?
Hard▼
States to handle:
1. Already granted — do nothing, proceed
2. Not yet asked — request permission directly
3. Denied once — shouldShowRequestPermissionRationale() returns true — show rationale dialog explaining why notifications are important, then request again
4. Permanently denied — shouldShowRequestPermissionRationale() returns false AND permission denied — can't re-request; direct user to Settings > App > Notifications
5. API < 33 — permission auto-granted, skip entire flow

fun handleNotificationPermission(activity: ComponentActivity) {
    if (Build.VERSION.SDK_INT < Build.VERSION_CODES.TIRAMISU) return
    val perm = Manifest.permission.POST_NOTIFICATIONS
    when {
        checkSelfPermission(perm) == PERMISSION_GRANTED -> { /* ok */ }
        shouldShowRequestPermissionRationale(perm) ->
            showRationaleDialog(onConfirm = { launcher.launch(perm) })
        else -> launcher.launch(perm)
    }
}
Track whether the user has been asked before in SharedPreferences to distinguish "never asked" from "permanently denied."
