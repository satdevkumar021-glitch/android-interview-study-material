14A — WorkManager

Guaranteed, battery-efficient, constraint-aware, and SQLite-persisted background task scheduling on Android. Mastering CoroutineWorker, chaining, unique policies, and retry strategies.

ID: 14A ⭐ Tier 2 (Core Architecture)
🚀
1. Overview & Architecture

WorkManager is the recommended Android Jetpack library for persistent, deferrable, and guaranteed background processing. It acts as an abstraction layer above underlying platform schedulers (JobScheduler on API 23+, custom AlarmManager/BroadcastReceiver fallback on API 14-22).

Core Pillars of WorkManager
  • Guaranteed Execution: Tasks are persisted in an internal Room/SQLite database. Even if the process dies or the device restarts, execution resumes once constraints are met.
  • Constraint-Aware: Runs work only when defined conditions (network type, battery level, charging state, device idle) are satisfied.
  • Battery Efficient: Integrates with Doze mode and App Standby, executing jobs in centralized OS maintenance windows.
  • Coroutine Native: CoroutineWorker provides a first-class suspend fun doWork() with structured cancellation.

2. How It Works Under the Hood

1. CoroutineWorker & Execution Lifecycle

CoroutineWorker runs doWork() on Dispatchers.Default by default. It returns a ListenableWorker.Result:

  • Result.success(outputData): Task finished successfully. Work state becomes SUCCEEDED.
  • Result.failure(outputData): Permanent failure. Work state becomes FAILED and will not retry.
  • Result.retry(): Transient failure. WorkManager reschedules according to the defined backoff policy.

2. Internal Scheduling Pipeline

When you call WorkManager.enqueue():

  1. The request, tags, constraints, and input parameters are written to the internal Room database.
  2. The internal GreedyScheduler checks if the app is in foreground and constraints are already met to run immediately.
  3. If constraints are not met or the app is backgrounded, it delegates to JobScheduler.
  4. When the OS triggers the job, WorkManager spins up the worker class, passes input data, and invokes doWork() inside a coroutine.

3. Work Chaining (Sequential & Parallel)

WorkManager supports complex Directed Acyclic Graphs (DAGs) using beginWith() and then():

// Parallel downloads -> Parallel filters -> Final single aggregation
val downloadA = OneTimeWorkRequestBuilder<DownloadWorker>().build()
val downloadB = OneTimeWorkRequestBuilder<DownloadWorker>().build()
val filterA = OneTimeWorkRequestBuilder<FilterWorker>().build()
val filterB = OneTimeWorkRequestBuilder<FilterWorker>().build()
val upload = OneTimeWorkRequestBuilder<UploadWorker>().build()

val chainA = workManager.beginWith(downloadA).then(filterA)
val chainB = workManager.beginWith(downloadB).then(filterB)

WorkContinuation.combine(listOf(chainA, chainB))
    .then(upload)
    .enqueue()

3. When to Use & Constraint Rules

Constraints Specification

Constraints govern when WorkManager is permitted to wake up the app:

  • setRequiredNetworkType(NetworkType.UNMETERED): Requires Wi-Fi or free network.
  • setRequiresCharging(true): Device must be connected to power.
  • setRequiresBatteryNotLow(true): Device is not in low-battery state.
  • setRequiresDeviceIdle(true): Screen is off and user is inactive (API 23+).
  • setRequiresStorageNotLow(true): User storage is above threshold.

Unique Work Policies

To avoid race conditions or duplicate processing (e.g. syncing the same account twice), use enqueueUniqueWork or enqueueUniquePeriodicWork:

  • ExistingWorkPolicy.REPLACE: Cancels the running/enqueued work and starts the new one.
  • ExistingWorkPolicy.KEEP: If existing work is running or enqueued, discards the new request.
  • ExistingWorkPolicy.APPEND: Appends the new request to run after the existing work finishes.
  • ExistingWorkPolicy.APPEND_OR_REPLACE: Appends if previous succeeded; replaces if previous failed/cancelled.

4. Production Example (Banking Offline Sync)

Scenario: In a fintech application, transactions created while offline must be securely uploaded once Wi-Fi or unmetered cellular is active, with exponential backoff on server 5xx errors.

class SyncTransactionsWorker(
    appContext: Context,
    workerParams: WorkerParameters,
    private val repository: TransactionRepository
) : CoroutineWorker(appContext, workerParams) {

    override suspend fun doWork(): Result {
        val batchId = inputData.getString("KEY_BATCH_ID") ?: return Result.failure()
        
        return try {
            val pendingTx = repository.getPendingTransactions(batchId)
            if (pendingTx.isEmpty()) return Result.success()

            val syncResult = repository.uploadBatch(pendingTx)
            if (syncResult.isSuccess) {
                val output = workDataOf("SYNCED_COUNT" to pendingTx.size)
                Result.success(output)
            } else {
                // Temporary 503 or network socket error -> backoff retry
                Result.retry()
            }
        } catch (e: CancellationException) {
            // Worker cancelled because constraints (e.g. Wi-Fi dropped) failed
            throw e
        } catch (e: Exception) {
            Result.failure()
        }
    }
}

// Scheduling inside Repository / ViewModel
fun scheduleOfflineSync(context: Context, batchId: String) {
    val constraints = Constraints.Builder()
        .setRequiredNetworkType(NetworkType.CONNECTED)
        .setRequiresBatteryNotLow(true)
        .build()

    val syncRequest = OneTimeWorkRequestBuilder<SyncTransactionsWorker>()
        .setConstraints(constraints)
        .setBackoffCriteria(
            BackoffPolicy.EXPONENTIAL,
            15, TimeUnit.SECONDS
        )
        .setInputData(workDataOf("KEY_BATCH_ID" to batchId))
        .addTag("TAG_SYNC_TX")
        .build()

    WorkManager.getInstance(context).enqueueUniqueWork(
        "unique_sync_$batchId",
        ExistingWorkPolicy.KEEP,
        syncRequest
    )
}

6. Pitfalls & Best Practices
Pitfall 1: Expecting PeriodicWorkRequest to run every minute

Android enforces a hard minimum of 15 minutes for PeriodicWorkRequest (and 5 minute flex interval). Passing 5, TimeUnit.MINUTES will be clamped to 15 minutes automatically. Do not use WorkManager for high-frequency polling.

Pitfall 2: Swallowing CancellationException inside CoroutineWorker

When constraints are lost (e.g., user disables Wi-Fi), WorkManager cancels the worker's coroutine job. If your try-catch catches generic Exception or Throwable without rethrowing CancellationException, WorkManager cannot gracefully acknowledge cancellation and clean up resources.

Pitfall 3: Storing Large Payloads in Data (10 KB Limit)

The Data object (input and output) is stored in the Room DB and passed across processes. It has a strict limit of 10 KB (10,240 bytes). Attempting to pass Bitmaps, large JSON arrays, or byte arrays will throw an IllegalStateException. Store data in Room/disk and pass primary keys (IDs) instead.

Best Practice: Custom WorkerFactory with Hilt

Never construct dependencies directly inside Workers. Use @HiltWorker with @AssistedInject to inject repositories cleanly.

7. Interview Framework

30-Second Elevator Pitch

"WorkManager is Android Jetpack's standard library for guaranteed, deferrable background execution. It persists requests to an internal SQLite DB so tasks survive process death and device reboots. It is constraint-aware—waiting for network, charging, or idle states—and provides first-class CoroutineWorker support for asynchronous chains and exponential backoff retries."

2-Minute Deep Dive

"Under the hood, WorkManager abstracts JobScheduler (on API 23+) and GreedyScheduler for immediate execution. When a task is queued, WorkManager writes it to Room, inspects constraints, and delegates execution. With CoroutineWorker, doWork() runs on Dispatchers.Default and returns Result.success(), failure(), or retry().

For enterprise reliability, WorkManager provides UniqueWork with REPLACE, KEEP, and APPEND policies to eliminate duplicate work. It also supports complex dependency graphs through WorkContinuation.combine(). Key constraints include a 15-minute minimum for periodic work and a 10KB payload limit on Data objects. For Hilt integration, we use @HiltWorker with DelegatingWorkerFactory."

If foreground execution is required for long-running tasks, WorkManager supports setForeground(ForegroundInfo) on API 28+ to promote the worker to a foreground service temporarily.

9. Interview Questions (Self-Check)
How to use
Answer mentally first, then expand each card to verify your answer.

Basic Questions

B1 — What is the primary purpose of WorkManager in Android?
Easy▼
WorkManager is designed for guaranteed, deferrable background execution. Unlike standard coroutines or services, tasks are persisted in an internal SQLite database, allowing them to survive process termination and device restarts until execution constraints (like network or charging) are satisfied.
B2 — What are the 3 return options for CoroutineWorker.doWork()?
Easy▼
1. Result.success(): Task completed successfully; triggers dependent tasks in the chain.
2. Result.failure(): Permanent failure; halts execution and marks the task as FAILED.
3. Result.retry(): Transient failure; WorkManager will reschedule the task according to its backoff policy.
B3 — What is the minimum interval for PeriodicWorkRequest?
Easy▼
The minimum periodic interval is 15 minutes (defined by PeriodicWorkRequest.MIN_PERIODIC_INTERVAL_MILLIS). Any shorter interval passed to the builder will be automatically clamped to 15 minutes by the framework to preserve battery.

Intermediate Questions

I1 — Explain the difference between ExistingWorkPolicy.KEEP and ExistingWorkPolicy.REPLACE.
Medium▼
When enqueuing unique work with a specific name:
• KEEP: If work with the same name already exists in an ENQUEUED or RUNNING state, the new request is ignored.
• REPLACE: If work with that name exists, it is cancelled and deleted, and the new work request is scheduled immediately.
I2 — How does WorkManager handle task cancellation when constraints are lost?
Medium▼
When a constraint is no longer met (e.g. Wi-Fi drops), WorkManager cancels the worker coroutine's Job by throwing a CancellationException and invokes onStopped(). The worker state is rolled back to ENQUEUED so it can re-run when constraints return. Catching generic Exception without rethrowing CancellationException breaks this flow.
I3 — What is the maximum size allowed for input/output Data in WorkManager and why?
Medium▼
The maximum size is 10 KB (10,240 bytes). This limit exists because Data objects are serialized into Room database tables and passed through IPC Binder transactions. Exceeding this limit throws an IllegalStateException. Large blobs or lists should be stored in local files or Room, passing only IDs or paths in the Data object.
I4 — How do you configure exponential backoff retry criteria in WorkRequest?
Medium▼
You configure it on the WorkRequestBuilder using setBackoffCriteria(BackoffPolicy.EXPONENTIAL, initialDelay, timeUnit). Minimum initial delay is 10 seconds. On each Result.retry(), delay doubles: 10s, 20s, 40s, 80s, etc., up to a maximum capped delay.

Senior & Scenario Questions

S1 — How do you inject dependencies into a Worker using Hilt?
HardScenario▼
1. Annotate the worker class with @HiltWorker.
2. Use @AssistedInject on constructor passing @Assisted appContext: Context and @Assisted workerParams: WorkerParameters along with regular injected dependencies.
3. Inject HiltWorkerFactory into Application and implement Configuration.Provider returning Configuration.Builder().setWorkerFactory(hiltWorkerFactory).build().
4. Disable default WorkManagerInitializer in AndroidManifest.xml.

S3 — What happens if an app with scheduled WorkManager tasks is force-stopped by the user?
HardScenario▼
When an app is in the "Force Stopped" state on Android, the OS disables all its alarms, JobScheduler registrations, and broadcast receivers. WorkManager will NOT run any scheduled tasks while in this state. The tasks remain persisted in the SQLite database and will automatically reschedule and resume only after the user manually relaunches the application.
