42C — Advanced App Security: FLAG_SECURE & App Hardening

FLAG_SECURE, excludeFromRecents, task hijacking prevention, screen capture defense, exported components, and runtime self-protection — the full security hardening layer for production Android apps.

ID: 42C ⭐ Tier 1 🔥 Hot
🔒
1. Overview & Attack Surface

A production Android app — especially one handling payments, subscriptions, and user accounts — presents a large attack surface. Security is not a single feature but a property you maintain across every API surface, every component, and every runtime environment your app runs in.

The Attack Surface of a Production App

  • Screenshots & screen recording — system APIs and accessibility services can capture screen content
  • Task switcher thumbnails — Android captures live screenshots when user presses the recents button
  • Exported components — Activities, Services, Receivers, and ContentProviders accessible to other apps
  • Deep links & URI handling — crafted URIs can bypass auth flows or inject data
  • WebViews — JavaScript bridges, file access, and redirect interception
  • IPC (Binder) — unprotected inter-process communication exposes sensitive operations
  • Runtime environment — rooted devices, emulators, Frida/Xposed hooks, debugger attachment

Two Security Postures

Passive hardening prevents information leakage — FLAG_SECURE, input masking, excludeFromRecents. The goal is that even if an attacker observes the device, they learn nothing useful.

Active hardening (RASP) detects and responds to attacks at runtime — root detection, integrity verification, anti-debugging. The goal is to make the app hostile to attackers who have partial control of the device.

🌟 Senior Mental Model

"Security is not a feature you add — it's a property you maintain. Every API surface your app exposes is a potential attack vector. Your job is to minimize the surface and harden what remains. For a banking or payment app, the question is never if someone will attempt an attack — it's when. Design for the adversarial case from day one."

2. FLAG_SECURE Deep Dive

What FLAG_SECURE Does

WindowManager.LayoutParams.FLAG_SECURE is a window-level flag that tells the system this window contains sensitive content. It activates several protections simultaneously:

  • Prevents programmatic screenshots via adb shell screencap
  • Prevents capture via MediaProjection / screen recording APIs
  • Causes the window to appear as a black rectangle in the task switcher instead of a live thumbnail
  • Blocks SurfaceView capture for camera/video preview windows

What FLAG_SECURE Does NOT Do

⚠ Important Limitations
  • Does not prevent a user pointing a physical camera at the screen
  • Does not protect content in other windows (e.g. a notification shade showing a PIN)
  • Does not prevent Accessibility services from reading view content (use setImportantForAccessibility or content masking for that)

How to Set It — The Correct Way

FLAG_SECURE must be set before setContentView(). It is a Window-level property, not a View-level one. Setting it after setContentView() is a common mistake that may not apply reliably.

class PaymentActivity : AppCompatActivity() {

    override fun onCreate(savedInstanceState: Bundle?) {
        // ✅ Must be set BEFORE setContentView — this is the first line
        window.addFlags(WindowManager.LayoutParams.FLAG_SECURE)

        super.onCreate(savedInstanceState)
        setContentView(R.layout.activity_payment)
    }
}
🚫 Common Mistake

Calling window.addFlags(FLAG_SECURE) after setContentView(). At that point the window is already created and the flag may not take effect consistently. Always set it before setContentView, ideally as the very first line in onCreate. Also do not call super.onCreate() before setting the flag — the super call may trigger window creation on some base classes.

Compose Applications

In a Jetpack Compose app, FLAG_SECURE is set in the Activity, not in a Composable. It is a window-level property and has no Composable equivalent. The pattern is identical:

class PaymentActivity : ComponentActivity() {
    override fun onCreate(savedInstanceState: Bundle?) {
        window.addFlags(WindowManager.LayoutParams.FLAG_SECURE)
        super.onCreate(savedInstanceState)
        setContent {
            PaymentScreen()
        }
    }
}

Selective Application

Apply FLAG_SECURE only to screens with sensitive content: payment flows, account credential screens, PIN entry, medical records. Do not apply it to the entire application — this breaks legitimate screenshot use cases (customer support, sharing receipts) and creates a poor user experience.

3. Task & Recents Hardening

The Task Switcher Attack

When a user presses the recents/overview button, Android captures a screenshot thumbnail of every running app. This thumbnail persists in memory and on-disk cache. For a banking or payment app, this can expose PINs, account numbers, and full transaction details to anyone who picks up the device later.

This is not theoretical — researchers have extracted task switcher thumbnails from devices without unlocking them on older Android versions.

Strategy 1: FLAG_SECURE (Already Covered)

FLAG_SECURE also applies to the task switcher thumbnail — the window appears as a black rectangle in recents. This is the strongest protection but shows an opaque black card rather than a preview, which may confuse users for main screens.

Strategy 2: android:excludeFromRecents

The activity does not appear in the task switcher at all. The entire task is removed from the recents list.

Best for: one-time payment confirmation screens, sensitive deep link handlers, auth challenge screens.

Downside: bad UX for the app's main activity — users can't return to the app from recents.

<!-- AndroidManifest.xml -->
<activity
    android:name=".PaymentActivity"
    android:excludeFromRecents="true"
    android:taskAffinity=""
    android:noHistory="true"
    android:allowTaskReparenting="false" />

Strategy 3: Dynamic Thumbnail Masking in onStop()

The most user-friendly approach: in onStop(), replace sensitive content with a safe placeholder (logo, loading screen). When the user returns, restore the content in onResume(). The recents thumbnail shows the safe placeholder.

class AccountActivity : AppCompatActivity() {

    override fun onStop() {
        super.onStop()
        // Hide sensitive content — task switcher captures AFTER onStop
        binding.accountNumberText.visibility = View.INVISIBLE
        binding.balanceText.visibility = View.INVISIBLE
        binding.securityOverlay.visibility = View.VISIBLE // show logo
    }

    override fun onResume() {
        super.onResume()
        // Restore content when user comes back
        binding.accountNumberText.visibility = View.VISIBLE
        binding.balanceText.visibility = View.VISIBLE
        binding.securityOverlay.visibility = View.GONE
    }
}

android:noHistory — Back Stack Security

android:noHistory="true" removes the activity from the back stack when the user navigates away. This prevents back-navigation to sensitive screens after logout or session expiry. Critical for: login screens, payment screens, OTP screens.

android:taskAffinity="" — StrandHogg Prevention

The StrandHogg vulnerability (CVE-2020-0096) exploits Android's task management: a malicious app declares taskAffinity matching your app's package name. When the user launches your app, the malicious Activity is injected on top and presented as a login screen — a classic overlay phishing attack.

⚠ StrandHogg — High Severity

StrandHogg 1.0 (2019) affected all Android versions. StrandHogg 2.0 (CVE-2020-0096) could attack any app without requiring singleTask. Patched in Android 10+, but devices on older Android remain vulnerable.

Defense: set android:taskAffinity="" on all sensitive activities (empty string isolates the activity into its own task). Additionally set android:allowTaskReparenting="false".

<!-- Complete manifest hardening for a payment activity -->
<activity
    android:name=".PaymentFlowActivity"
    android:exported="false"
    android:excludeFromRecents="true"
    android:taskAffinity=""
    android:noHistory="true"
    android:allowTaskReparenting="false"
    android:screenOrientation="portrait" />
AttributeEffectUse When
FLAG_SECUREBlack thumbnail in recents + block screenshotAll sensitive windows

4. Screen Capture Prevention

Layered Approach to Capture Prevention

No single mechanism prevents all forms of screen capture. A production security posture combines multiple layers:

1. FLAG_SECURE — System-Level Block

Prevents MediaProjection-based screen recording, adb screencap, and task switcher thumbnails. The most effective programmatic protection. Apply to all windows containing sensitive data.

2. Secure Input Fields

Use inputType="textPassword" on PIN/password fields. This masks content at the View level independently of FLAG_SECURE. Even if FLAG_SECURE is accidentally missing from a screen, the PIN field appears as dots.

<!-- XML layout -->
<com.google.android.material.textfield.TextInputEditText
    android:id="@+id/pinInput"
    android:inputType="numberPassword"
    android:importantForAutofill="no" />

3. Jetpack Compose Secure Text Fields

// Compose — password field with visual masking
var pin by remember { mutableStateOf("") }

OutlinedTextField(
    value = pin,
    onValueChange = { pin = it },
    visualTransformation = PasswordVisualTransformation(),
    keyboardOptions = KeyboardOptions(keyboardType = KeyboardType.NumberPassword),
    // Screen readers won't announce the value
    modifier = Modifier.semantics { contentDescription = "PIN entry" }
)

4. WebView Hardening

WebViews require specific hardening to prevent capture of displayed content and to prevent malicious redirects:

fun setupSecureWebView(webView: WebView) {
    webView.settings.apply {
        // Disable file access — prevents file:// URI attacks
        allowFileAccess = false
        allowContentAccess = false
        allowFileAccessFromFileURLs = false
        allowUniversalAccessFromFileURLs = false

        // Disable JS by default — enable only if absolutely required
        javaScriptEnabled = false

        // Prevent mixed content in payment pages
        mixedContentMode = WebSettings.MIXED_CONTENT_NEVER_ALLOW

        // Enable Safe Browsing
        safeBrowsingEnabled = true
    }

    webView.webViewClient = object : WebViewClient() {
        override fun shouldOverrideUrlLoading(
            view: WebView, request: WebResourceRequest
        ): Boolean {
            // Whitelist only expected domains
            val host = request.url.host ?: return true
            val allowed = listOf("myapp.com", "www.myapp.com")
            return host !in allowed // true = block the navigation
        }
    }
}

5. Screen Recording Detection — The Hard Truth

There is no reliable way to detect screen recording on Android by design. The system intentionally does not expose this information to apps (to protect user privacy when recording tutorial videos). Mitigate by:

  • FLAG_SECURE — blocks the MediaProjection API capture path
  • Time-limited access tokens — sensitive data expires and is no longer on-screen
  • Session-aware auto-lock — return to lock screen after inactivity
  • UI masking — progressively hide sensitive data after display time expires

6. DRM-Protected Content

For video/audio content (e-books, subscription content): use ExoPlayer with Widevine DRM. DRM-protected content automatically receives FLAG_SECURE-like protection via the MediaDrm API — the system marks the output as protected and prevents capture at the hardware composition layer.

💡 Physical Camera Limitation

FLAG_SECURE does not prevent a user pointing a physical camera at the screen. For truly sensitive content (legal documents, medical records, one-time codes), combine FLAG_SECURE with time-limited access tokens (display for 30 seconds, then re-auth), session-aware access controls, and UI masking of partial data (show only last 4 digits of account number by default).

5. Activity & Component Security

The Exported Component Problem

Any component with android:exported="true" or with an implicit intent filter (pre-Android 12) is accessible to all other apps on the device. A malicious app can start your exported Activity with crafted intent extras, trigger exported Services, or query exported ContentProviders.

⚠ Android 12 Breaking Change (API 31+)

Apps targeting API 31+ must explicitly declare android:exported for every Activity, Service, and BroadcastReceiver that has an intent filter. Failing to do so causes an install-time crash: android.content.pm.PackageManager$NameNotFoundException. There is no default — you must be explicit.

Component Security Best Practices

  1. Default all components to android:exported="false" — only export what is intentionally public (share targets, deep link handlers, launcher activity).
  2. Add permission checks to exported components — use android:permission to require a signature-level permission that only your app (and apps signed with your key) can hold.
  3. Validate all deep link inputs — never trust URI parameters from deep links without validation. Deep links can be sent by any app.
  4. Use App Links for deep links — verified https:// links (via assetlinks.json) cannot be spoofed by other apps, unlike custom URI schemes (myapp://).

Deep Link Security

class DeepLinkActivity : AppCompatActivity() {
    override fun onCreate(savedInstanceState: Bundle?) {
        super.onCreate(savedInstanceState)

        val uri = intent.data ?: run { finish(); return }

        // 1. Validate host — reject anything not from your domain
        if (uri.host != "app.myapp.com") {
            finish()
            return
        }

        // 2. Validate path prefix
        if (uri.path?.startsWith("/order/") != true) {
            finish()
            return
        }

        // 3. Validate parameter format with whitelist regex
        val orderId = uri.getQueryParameter("orderId")
        if (orderId.isNullOrBlank() || !orderId.matches(Regex("[A-Z0-9]{8,16}"))) {
            finish()
            return
        }

        // 4. Never use orderId directly in SQL — use parameterized queries
        viewModel.loadOrder(orderId) // ViewModel validates server-side
    }
}

ContentProvider Security

ContentProviders are a frequent source of data leakage in Android apps. Default to android:exported="false" unless cross-app sharing is required. When sharing is required:

  • Use android:readPermission and android:writePermission separately — grant minimum necessary access
  • Use android:grantUriPermissions="true" with explicit URI grants instead of blanket export
  • Use FileProvider (from Jetpack) for file sharing — it provides scoped URI access without exposing file paths
  • Validate all query parameters and selection arguments against SQL injection — never concatenate user input into queries
<!-- Secure FileProvider declaration -->
<provider
    android:name="androidx.core.content.FileProvider"
    android:authorities="${applicationId}.fileprovider"
    android:exported="false"
    android:grantUriPermissions="true">
    <meta-data
        android:name="android.support.FILE_PROVIDER_PATHS"
        android:resource="@xml/file_paths" />
</provider>

BroadcastReceiver Security

For internal broadcasts (within your app), use LocalBroadcastManager — broadcasts stay within your process and cannot be intercepted by other apps. For system broadcasts that require an exported receiver, verify sender identity using the permission parameter on sendBroadcast() and android:permission on the receiver.

// Internal broadcast — never visible to other apps
LocalBroadcastManager.getInstance(context)
    .sendBroadcast(Intent("com.example.PAYMENT_COMPLETE"))

// For exported receiver — require signature permission
val intent = Intent("com.example.PAYMENT_COMPLETE")
sendBroadcast(intent, "com.example.permission.PAYMENT_EVENTS")

6. Runtime Application Self-Protection (RASP)

What RASP Is

Runtime Application Self-Protection is the practice of the app detecting and responding to attacks at runtime. Rather than relying solely on static hardening, RASP adds active checks: root detection, emulator detection, debugger detection, hook detection, and tampering detection.

Play Integrity API (Replaces SafetyNet — Mandatory since 2024)

The Play Integrity API provides a server-verified verdict about the app and device state. It supersedes the deprecated SafetyNet Attestation API.

Verdict LevelMeaningAction
MEETS_BASIC_INTEGRITYDevice passed basic integrity — not obviously tamperedAllow normal operations
MEETS_DEVICE_INTEGRITYCertified Android device (GMS certified), no known exploitsRequired for payment operations
MEETS_STRONG_INTEGRITYPasses all checks including bootloader lock stateRequired for highest-risk operations
 
class IntegrityVerifier(
    private val context: Context,
    private val apiBackend: BackendApi
) {
    private val integrityManager = IntegrityManagerFactory.create(context)

    /**
     * Request integrity verdict. Must be called off the main thread.
     * The nonce is server-generated and single-use to prevent replay attacks.
     */
    suspend fun verifyForPayment(paymentId: String): IntegrityResult {
        // 1. Get a fresh server-side nonce — single use, tied to this operation
        val nonce = apiBackend.getIntegrityNonce(paymentId)

        // 2. Request token from Play Integrity API
        val tokenRequest = IntegrityTokenRequest.builder()
            .setNonce(nonce)
            .setCloudProjectNumber(CLOUD_PROJECT_NUMBER)
            .build()

        val tokenResponse = integrityManager
            .requestIntegrityToken(tokenRequest)
            .await() // Coroutine-friendly extension

        // 3. Send token to YOUR server for verification — never trust client-side verdict
        return apiBackend.verifyIntegrityToken(
            token = tokenResponse.token(),
            paymentId = paymentId
        )
        // Server decrypts and verifies verdict, then proceeds or blocks
    }
}
⚠ Play Integrity API — Critical Usage Rules
  • Never call on the main thread — it makes a network request to Google's servers
  • Has a quota — do not call on every screen. Call only for specific sensitive operations: payment initiation, account changes, login
  • Nonce must be server-generated — a client-generated nonce can be replayed. The nonce ties the verdict to a specific operation
  • Verdict must be verified server-side — never make security decisions based on client-side decryption of the token

Root Detection — Multi-Signal Approach

No single root check is reliable. Combine multiple signals — a single check is trivially bypassed by Magisk modules that hook individual system calls:

object RaspChecker {

    fun isDeviceCompromised(): Boolean {
        var score = 0

        // Signal 1: su binary presence in common locations
        val suPaths = arrayOf(
            "/system/bin/su", "/system/xbin/su", "/sbin/su",
            "/data/local/su", "/data/local/bin/su"
        )
        if (suPaths.any { File(it).exists() }) score += 3

        // Signal 2: Magisk manager package
        val rootPackages = listOf(
            "com.topjohnwu.magisk", "eu.chainfire.supersu",
            "com.noshufou.android.su"
        )
        if (rootPackages.any { isPackageInstalled(it) }) score += 3

        // Signal 3: test-keys build (non-official ROM)
        val buildTags = Build.TAGS ?: ""
        if (buildTags.contains("test-keys")) score += 2

        // Signal 4: writable system partition
        try {
            val file = File("/system/test_rasp_check")
            file.createNewFile()
            file.delete()
            score += 4 // Writable /system is a strong indicator
        } catch (_: Exception) { /* expected — /system should be read-only */ }

        // Signal 5: dangerous system properties
        if (getSystemProperty("ro.debuggable") == "1") score += 2
        if (getSystemProperty("ro.secure") == "0") score += 2

        return score >= 4 // Threshold — tune based on false positive rate
    }

    fun isEmulator(): Boolean {
        return (Build.FINGERPRINT.startsWith("generic") ||
                Build.FINGERPRINT.startsWith("unknown") ||
                Build.MODEL.contains("google_sdk") ||
                Build.MODEL.contains("Emulator") ||
                Build.MODEL.contains("Android SDK built for x86") ||
                Build.HARDWARE.contains("goldfish") ||
                Build.HARDWARE.contains("ranchu") ||
                Build.PRODUCT.startsWith("sdk"))
    }

    fun isDebuggerAttached(): Boolean {
        return Debug.isDebuggerConnected() || Debug.waitingForDebugger()
    }
}
⚠ RASP — Defense in Depth, Not a Silver Bullet

RASP is defense in depth, not a guarantee. Determined attackers with Magisk + Frida can bypass individual checks. The goal is to raise the cost of attack high enough that most attackers give up. Each bypassed check requires attacker effort.

Never trust client-side security alone. Always combine RASP with server-side validation: server-verified Play Integrity tokens, server-side fraud detection, rate limiting, and anomaly detection. If a client claims to be on a clean device but shows suspicious transaction patterns, the server should still intervene.

8. Interview Framework

30-Second Answer

"For a banking or payment app, I apply security in layers. At the window level, I set FLAG_SECURE — before setContentView — to prevent screenshots and mask the task switcher thumbnail. For sensitive activities like payment and auth screens, I set excludeFromRecents and noHistory to prevent them appearing in task history and the back stack. I set taskAffinity to an empty string to isolate the task and prevent StrandHogg task hijacking. All components are android:exported=false unless explicitly public, and deep links are validated against whitelist patterns for host, path, and parameter format. At runtime, I use the Play Integrity API — server-verified, nonce-based — to confirm device integrity before allowing sensitive operations like payment initiation."

2-Minute Extended Answer

"Beyond the basics, I'd add detail on the StrandHogg vulnerability — malicious apps exploit taskAffinity to inject overlay activities, and the defense is taskAffinity='', allowTaskReparenting=false on all sensitive activities. For WebViews in payment flows, I disable file access, set MIXED_CONTENT_NEVER_ALLOW, and whitelist navigation to specific domains with a custom WebViewClient.

For component security, I use signature-level permissions on any exported component so only apps signed with my signing key can access them. Deep links use App Links (https:// verified via assetlinks.json) rather than custom schemes that can be spoofed.

For runtime protection, I combine Play Integrity with multi-signal root detection — su binary presence, Magisk manager package, test-keys build tag, writable /system partition, and dangerous system properties. No single check is reliable; the threshold scoring approach raises the cost of evasion. All of this is defense in depth — I never trust client-only security, and the server independently validates integrity tokens before authorizing any payment operation."

Must-Mention Checklist

1
FLAG_SECURE before setContentView — not after. Window must not be created yet when the flag is set.
2
excludeFromRecents + noHistory for payment/auth screens — prevents task switcher leakage and back-navigation post-logout.

9. Interview Questions
Q1. What is FLAG_SECURE and when do you use it?
Easy ⌄

FLAG_SECURE is a WindowManager.LayoutParams flag that marks a window as containing sensitive content. When set, it prevents programmatic screenshots (via adb, MediaProjection API), blocks screen recording of that window, and causes the window to appear as a black rectangle in the task switcher recents view.

When to use: Payment screens, login/PIN entry, account details pages, any screen displaying PII or credentials. Apply selectively — not to the entire app — to avoid breaking legitimate screenshot use cases.

Critical implementation detail: It must be set before setContentView():

override fun onCreate(savedInstanceState: Bundle?) {
    window.addFlags(WindowManager.LayoutParams.FLAG_SECURE) // FIRST
    super.onCreate(savedInstanceState)
    setContentView(R.layout.activity_payment)
}

What it does NOT prevent: a physical camera pointed at the screen, Accessibility services reading view content, or captures of other windows.

Q2. How do you prevent your app from appearing in the Android task switcher?
Easy ⌄

Three approaches, each with different trade-offs:

  1. android:excludeFromRecents="true" — removes the task from the recents screen entirely. Best for one-time flows (payment confirmation, auth screens). Downside: bad UX if applied to the main activity.
  2. FLAG_SECURE — the task stays in recents but shows a black rectangle instead of the live thumbnail. Useful when you want the app accessible from recents but don't want sensitive content visible.
  3. Dynamic masking in onStop() — replace sensitive views with a safe placeholder, restore in onResume(). Keeps the app in recents with a safe thumbnail. Best UX but requires more code.

For a payment Activity, the recommended combination: excludeFromRecents="true" + noHistory="true" + taskAffinity="". This removes it from recents, prevents back-navigation post-completion, and isolates the task.

Q3. What is the StrandHogg vulnerability and how do you prevent it?
Medium ⌄

StrandHogg is a class of task hijacking vulnerabilities exploiting Android's task management.

How it works: A malicious app declares android:taskAffinity equal to your app's package name and sets android:allowTaskReparenting="true". When the user launches your app, Android's task manager routes the malicious Activity to your task stack. The malicious Activity sits on top, appearing as your app's login screen — a phishing overlay. It can capture credentials before passing control back.

StrandHogg 2.0 (CVE-2020-0096) was more severe — it did not require singleTask launch mode and could attack any app without any interaction from the malicious app developer.

Defenses:

  • android:taskAffinity="" — empty string isolates the Activity into its own anonymous task. A malicious app cannot match an empty affinity.
  • android:allowTaskReparenting="false" — prevents the activity from being moved between tasks
  • Keep targetSdkVersion up to date — Android 10+ includes OS-level mitigations
  • For deep-link activities, validate the calling package using callingPackage or signed intent extras
Q4. Your banking app shows account numbers. Walk through all the screen capture attack vectors and your defenses.
Medium ⌄

Attack vectors and mitigations:

  1. adb screencap / MediaProjection API → FLAG_SECURE blocks both. The system marks the window's surface as protected, and the composition layer refuses capture requests.
  2. Task switcher thumbnail → FLAG_SECURE renders a black rectangle. Alternatively, use dynamic masking in onStop() to show a placeholder.
  3. Malicious Accessibility Service → Cannot be fully blocked (Accessibility is a user-granted privilege). Mitigate with android:importantForAccessibility="no" on sensitive views, and mask data by default (show last 4 digits only, require explicit user action to reveal).
  4. Physical camera pointed at screen → FLAG_SECURE does not help here. Mitigate with time-limited display (auto-mask after 30s), partial masking (show ••••1234), and physical display brightness/contrast warnings.
  5. Screen reader / TalkBack announcing values → Use setContentDescription() with masked values for sensitive views.
  6. Frida hook on the screenshot API → Harder to prevent. Combine RASP (hook detection, Frida port scan) with Play Integrity API before displaying sensitive data. If integrity fails, show only masked data.

Defence-in-depth summary: FLAG_SECURE + partial masking by default + time-limited reveal + Play Integrity check before showing full account number.

Q5. A security audit finds your app's ContentProvider is exported without permissions. What are the risks and how do you fix it?
Hard ⌄

Risks of an exported ContentProvider without permissions:

  • Data exfiltration: Any app can query your ContentProvider and read all data it exposes — user profiles, order history, payment methods, auth tokens stored in the database.
  • SQL injection: If the provider passes selection arguments to SQLite without parameterization, a malicious app can inject SQL to read or delete arbitrary data.
  • Data manipulation: If the provider supports insert/update/delete, a malicious app can corrupt or poison your app's data.
  • URI traversal: If the provider uses file-based URIs, path traversal attacks may expose files outside the intended directory.

Fix — in order of priority:

  1. Set android:exported="false" if the provider is only used internally. This is the complete fix for internal providers.
  2. If cross-app access is required, add android:readPermission and android:writePermission with protectionLevel="signature" so only apps from your signing key can access it.
  3. For file sharing with arbitrary apps, replace the ContentProvider with FileProvider (Jetpack) using scoped URI grants — FLAG_GRANT_READ_URI_PERMISSION on a per-share basis.
  4. Audit all query() implementations for SQL injection — use parameterized queries, never concatenate selection strings from caller input.
  5. Add query parameter validation — reject unknown projection columns, limit selection to whitelisted columns.
Q6. You need to prevent your payment activity from appearing in the user's recent apps list, but only when the user has NOT completed the payment. How do you implement this dynamically?
Hard ⌄

The manifest attribute android:excludeFromRecents is static. For dynamic control, use ActivityManager.AppTask:

class PaymentActivity : AppCompatActivity() {
    private var paymentCompleted = false

    override fun onStop() {
        super.onStop()
        if (!paymentCompleted) {
            // Payment not complete — remove from recents dynamically
            excludeFromRecentsDynamically()
        }
    }

    override fun onResume() {
        super.onResume()
        // If user returns, hide sensitive content until re-auth
        if (!paymentCompleted) {
            viewModel.requireReAuthentication()
        }
    }

    private fun excludeFromRecentsDynamically() {
        val am = getSystemService(ActivityManager::class.java) ?: return
        // Find our task in the recent tasks list and exclude it
        am.appTasks.firstOrNull {
            it.taskInfo.baseActivity?.packageName == packageName
        }?.setExcludeFromRecents(true)
    }

    fun onPaymentSuccess() {
        paymentCompleted = true
        // Allow task to appear in recents once complete (or finish it)
        getSystemService(ActivityManager::class.java)
            ?.appTasks
            ?.firstOrNull { it.taskInfo.baseActivity?.packageName == packageName }
            ?.setExcludeFromRecents(false)
        // Or: finish the activity — noHistory removes it from back stack
        finish()
    }
}

The key is ActivityManager.AppTask.setExcludeFromRecents(boolean), available since API 21. Combine with FLAG_SECURE for the intermediate "payment in progress" state.

Q7. Describe how you would implement Play Integrity API verification for a payment flow, including the nonce strategy.
Hard ⌄

The key principle: the nonce must be server-generated, single-use, and tied to a specific operation. Client-generated nonces can be replayed.

Flow:

  1. User initiates payment → app calls POST /api/payment/start on your server
  2. Server generates a cryptographically random nonce (e.g. UUID + HMAC of operation details), stores it with a 60-second TTL, returns it to the client
  3. Client calls IntegrityManager.requestIntegrityToken(nonce) — on a coroutine, never main thread
  4. Client sends the integrity token + nonce to server as part of the payment request
  5. Server calls Google's playintegrity.v1.decodeIntegrityToken API to decrypt and verify the verdict
  6. Server checks: verdict level ≥ MEETS_DEVICE_INTEGRITY, package name matches, nonce matches the stored value, token freshness within acceptable window
  7. Server marks nonce as consumed (prevents replay), then proceeds with or rejects the payment

What the server checks in the verdict:

  • appIntegrity.appRecognitionVerdict — must be PLAY_RECOGNIZED (unmodified APK from Play Store)
  • deviceIntegrity.deviceRecognitionVerdict — must include MEETS_DEVICE_INTEGRITY
  • accountDetails.appLicensingVerdict — must be LICENSED (user has legitimate copy)
  • requestDetails.nonce — must match server-stored nonce for this payment
  • requestDetails.timestampMillis — must be within the last 60 seconds

Never make the security decision client-side — the verdict JSON is encrypted for your server key, but a compromised client could substitute a pre-obtained passing verdict. The server is the source of truth.

Q8. An attacker has rooted a device and is using Frida to hook your SSL pinning code. What additional layers of protection do you have?
Hard ⌄

This is a defense-in-depth question. When SSL pinning is bypassed, your remaining protections are:

Layer 1 — Frida/Hook Detection (RASP)

  • Scan for Frida's default port (27042) being open: Socket("127.0.0.1", 27042) connecting successfully is a strong indicator
  • Inspect /proc/self/maps for Frida-related shared library names (frida-agent, gadget)
  • Check for Frida's pipe files in /tmp/frida-*
  • Detect method hooking via reflection — compare a known method's implementation address before and after a suspicious window

Layer 2 — Play Integrity API

Frida hooking SSL pinning does not spoof the Play Integrity verdict — that requires a separate attack chain. If the device has Frida and is rooted, it likely fails MEETS_DEVICE_INTEGRITY. The server refuses payment initiation entirely, regardless of what the client claims.

Layer 3 — Server-Side Request Validation

Even if the attacker can see decrypted traffic (SSL pinning bypassed), they cannot replay or forge requests that include valid HMAC signatures derived from user session tokens that expire in seconds, or one-time payment tokens. The attacker can observe but not generate valid payment requests without the user's active session.

Layer 4 — Server-Side Anomaly Detection

Even if all client-side protections are bypassed, server-side ML-based fraud detection flags unusual patterns: transaction amount outliers, unusual device fingerprint, rapid successive payments, geographic impossibility.

The senior answer: "We assume client-side protections will eventually be bypassed by a sufficiently skilled attacker. Our architecture is designed so that bypassing any single layer does not grant the ability to complete a fraudulent transaction. The server makes the final authorization decision based on multiple independent signals."
