24A — Modularization

Why to modularize, module types and responsibilities, dependency rules, api vs implementation, dynamic feature modules, build performance benefits, and inter-module communication patterns.

ID: 24A ★★ Tier 2
🔍
1. Overview

Why Modularize?

  • Build speed: Gradle can compile modules in parallel; unchanged modules are skipped (build cache)
  • Feature isolation: each feature module owns its own code, resources, and tests
  • Team scalability: teams own their modules independently — fewer merge conflicts
  • Reusability: :core:ui shared across all features; :core:network shared across all data layers
  • Dynamic delivery: Dynamic Feature Modules downloaded on demand — reduces initial APK size
Senior Mental Model
Modularization is primarily a build-time and team-scale concern, not a runtime concern. The main benefit is faster incremental builds and the ability for teams to work in parallel without blocking each other. For a 2-person team on a small app, modularization is overhead. For 20+ engineers on a large app, it's essential.
📂
2. Module Types

Recommended Module Structure

MyApp/
├── app/                      # Entry point — thin, just wires things together
├── feature/
│   ├── home/                 # Vertical feature slice — UI + ViewModel + UseCase
│   ├── product/
│   ├── cart/
│   └── checkout/
└── core/
    ├── network/              # Retrofit, OkHttp, interceptors
    ├── database/             # Room, DAOs
    ├── ui/                   # Shared composables, themes, design tokens
    ├── common/               # Utility extensions, base classes
    └── domain/               # Entities, repository interfaces, use case base
ModulePluginResponsibility
:appcom.android.applicationSingle entry point, DI graph root, navigation host
:feature:Xcom.android.libraryVertical slice: Screen + ViewModel + UseCase for feature X
:core:networkcom.android.libraryRetrofit, OkHttp, interceptors, token refresh
:core:databasecom.android.libraryRoom database, DAOs, migrations
:core:uicom.android.libraryShared Composables, themes, Material tokens
:core:commonkotlin (pure JVM)Extensions, utils, no Android deps
Tip
:core:common should ideally be a pure Kotlin module (kotlin("jvm") plugin) — no Android dependencies. This makes it fastest to compile and testable on the JVM without an emulator.

3. Dependency Rules

Dependency Direction

// Allowed dependency directions:
//   :app → :feature:home → :core:network
//   :app → :feature:cart → :core:database
//   :feature:X → :core:ui, :core:common, :core:domain
//
// FORBIDDEN:
//   :feature:home → :feature:cart   (features must NOT depend on each other)
//   :core:network → :feature:X       (core must NOT depend on features)
//   Circular dependencies            (Gradle will fail)

api vs implementation in Library Modules

// :core:network/build.gradle.kts
dependencies {
    // implementation — hidden from consumers of :core:network
    implementation(libs.retrofit)          // OK: internal detail
    implementation(libs.okhttp.logging)    // OK: internal

    // api — exposed on compile classpath of consumers
    api(libs.retrofit.converter.gson)      // Only if consumers use Gson types directly
}
// Prefer implementation — reduces recompilation scope
// When :core:network's implementation dep changes, only :core:network recompiles
// If api dep changes, ALL modules depending on :core:network must recompile
Key Rule
Use api() only when the dependency's types appear in the module's public API (function signatures, return types). Everything else uses implementation(). Incorrect api() usage is the #1 cause of unnecessarily slow incremental builds in modularized projects.
⚡
4. Build Performance Benefits

Parallel Compilation

With org.gradle.parallel=true, Gradle compiles independent modules concurrently. In a monolith, everything is sequential. In a modular app with 10 feature modules all depending on shared cores, the features can all compile in parallel after the cores finish.

# Monolith build (sequential):          Modular build (parallel):
# compile → 8 minutes                   :core:* → 2 min
#                                        :feature:* (parallel) → +2 min
#                                        :app link → +30 sec
#                                        Total: ~4.5 minutes

Build Cache Per Module

Gradle caches task outputs per module based on a hash of inputs. If you change only :feature:cart, only that module recompiles. All other module caches are valid. In a monolith, any change recompiles everything.

ABI Changes

An ABI (Application Binary Interface) change is when a module's public API changes (adding/removing/changing a public method). This forces all dependent modules to recompile. Internal (private/internal) changes are non-ABI and don't trigger downstream recompilation. This is why good encapsulation in Kotlin (using internal) directly improves build speed.

Build Speed Rule of Thumb
Changing a private or internal function → only that module recompiles. Changing a public function → all dependent modules recompile. Maximize use of internal in library modules.
🚀
5. Dynamic Feature Modules

What Are They?

Dynamic Feature Modules (DFM) are Android library modules whose code and resources are not included in the base APK. They are downloaded on demand from the Play Store using the Play Core library. This reduces initial install size.

// :feature:ar-scanner/build.gradle.kts (Dynamic Feature Module)
plugins {
    id("com.android.dynamic-feature")
}
android {
    // No applicationId — inherits from :app
    // minSdk must match :app's minSdk
}
dependencies {
    implementation(project(":app"))  // DFM depends on :app, not the other way
}
// Requesting a Dynamic Feature at runtime
val splitInstallManager = SplitInstallManagerFactory.create(context)
val request = SplitInstallRequest.newBuilder()
    .addModule("ar_scanner")
    .build()
splitInstallManager.startInstall(request)
    .addOnSuccessListener { /* navigate to AR scanner */ }
    .addOnFailureListener { e -> /* handle error */ }
FeatureDetail
On-demand deliveryDownloaded when user first accesses the feature
Install-time deliveryDownloaded at install but packaged separately (faster update)
Conditional deliveryOnly on devices meeting criteria (country, API level, hardware)
Dependency directionDFM → :app (reversed from regular modules)

6. Module Communication Patterns

The Problem

Feature modules cannot depend on each other. But they often need to communicate — e.g., :feature:cart needs to know the user logged in (event from :feature:auth). Three patterns solve this:

1. Shared ViewModel via NavBackStackEntry

// Scoped ViewModel shared across feature screens via the nav graph
// Both features define the nav graph in :app — they share a parent entry
@Composable
fun CheckoutScreen(navController: NavController) {
    val parentEntry = remember(navController) {
        navController.getBackStackEntry("checkout_graph")
    }
    val sharedVm: SharedCartViewModel = hiltViewModel(parentEntry)
}

2. SharedFlow Event Bus via :core:common

// :core:common — defines the event contract (no feature dependencies)
sealed class AppEvent {
    data class UserLoggedIn(val userId: String) : AppEvent()
    object CartCleared : AppEvent()
}

// :core:common — EventBus singleton
object AppEventBus {
    private val _events = MutableSharedFlow<AppEvent>()
    val events: SharedFlow<AppEvent> = _events.asSharedFlow()
    suspend fun emit(event: AppEvent) = _events.emit(event)
}

3. Service Interface via Hilt (Preferred)

// :core:domain — interface (no feature deps)
interface CartRepository {
    suspend fun addItem(item: CartItem)
    fun getCartFlow(): Flow<List<CartItem>>
}

// :feature:cart — implementation (depends on :core:domain, :core:database)
class CartRepositoryImpl @Inject constructor(
    private val cartDao: CartDao
) : CartRepository { ... }

// :app — Hilt binding wires interface to implementation
@Binds abstract fun bindCartRepo(impl: CartRepositoryImpl): CartRepository

7. Interview Framework

30-Second Answer

"Modularization splits the app into :app, :feature:X vertical slices, and :core:* shared layers. The main benefits are faster incremental builds through parallel compilation and Gradle's build cache, plus team scalability. Features depend on core modules but never on each other — this enforces isolation. I use implementation() not api() for dependencies to minimize recompilation scope."

2-Minute Answer

"The standard structure is :app as the thin entry point, feature modules as vertical slices owning their own UI, ViewModels, and use cases, and core modules for shared infrastructure like :core:network, :core:database, :core:ui. The dependency rule is strict: app → features → core, and features never depend on each other. For build performance, parallel compilation means independent modules build concurrently, and Gradle's build cache means unchanged modules are skipped. Using implementation() instead of api() minimizes ABI surface — only ABI changes trigger downstream recompilation. For inter-module communication, I use shared ViewModels via NavBackStackEntry for co-located screens, SharedFlow event bus in core:common for cross-feature events, or best of all — define repository interfaces in :core:domain and bind implementations in :app via Hilt, so features depend only on contracts."

Must-Mention Points

1
Dependency direction: :app → :feature → :core — features NEVER depend on each other
2
api() vs implementation(): implementation hides transitives, prevents unnecessary recompilation
3
Build performance: parallel compilation + cache — changing one feature only recompiles that feature
4
Communication: interface in :core:domain, implementation in feature, binding in :app via Hilt
5
Dynamic Feature Modules: downloaded on demand, DFM depends on :app (reversed dependency)

Do NOT Go Deeper On

  • Navigation deep links between DFMs (complex, mention it exists)
  • Gradle composite builds (advanced, separate topic)
  • Specific module counts — it depends on team/app size

Senior Insight

Senior Differentiator
The real value of modularization shows at scale. In a monolith, every developer touching any file triggers full recompilation for everyone. In a well-modularized app, a developer on the :feature:checkout module can iterate in seconds because only that module recompiles. The architecture discipline (features not depending on each other) is what enables this — and it's enforced by Gradle, not just convention.

9. Interview Questions
1. What are the main reasons to modularize an Android app?
Basic⌄
Build speed (parallel compilation, build cache), feature isolation (each feature owns its code), team scalability (teams work in independent modules), reusability (core modules shared), and dynamic delivery (Dynamic Feature Modules reduce install size).
2. What dependency direction rule must modules follow?
Basic⌄
:app → :feature:X → :core:*. Feature modules must NEVER depend on other feature modules. Core modules must never depend on feature modules. This one-way flow ensures isolation and allows parallel compilation.
3. What is an ABI change and why does it matter for build speed?
Basic⌄
An ABI (Application Binary Interface) change is a modification to a module's public API — adding, removing, or changing a public function or class. ABI changes force all dependent modules to recompile. Non-ABI changes (private/internal modifications) only recompile the changed module. Maximizing use of internal visibility directly improves build speed.
4. When would you use api() instead of implementation() in a module's dependency?
Intermediate⌄
Only when the dependency's types appear in the module's public API surface — function parameters, return types, or properties that consumers need to interact with. Example: if :core:network exposes a function returning a Retrofit Response<T>, then Retrofit needs to be api(). Everything else (OkHttp internals, logging interceptors) stays implementation(). Using api() unnecessarily increases the compilation scope for all consumers.
5. How do feature modules communicate without depending on each other?
Intermediate⌄
Three patterns: (1) Shared ViewModel scoped to a navigation graph entry — both features access the same ViewModel via NavBackStackEntry. (2) SharedFlow event bus defined in :core:common — features emit and collect events without knowing about each other. (3) Best: define interface contracts in :core:domain, implement them in feature/data modules, and bind them in :app via Hilt — features depend only on the interface, never the implementation.
6. What is a Dynamic Feature Module and when would you use one?
Intermediate⌄
A DFM is a module whose code/resources are NOT in the base APK. They're downloaded on demand via Play Store using SplitInstallManager. Use them for optional features (AR scanner, premium features, rarely-used tools) to reduce the initial install size. Note the reversed dependency: DFM depends on :app, not the other way. Requires app to be an AAB distributed via Play Store.
7. How does parallel Gradle build work with modules?
Intermediate⌄
With org.gradle.parallel=true, Gradle compiles modules concurrently as long as they have no dependency relationship between them. All :feature:* modules can compile in parallel once :core:* modules finish. In a monolith, compilation is sequential. A well-modularized app with 10 feature modules effectively parallelizes across CPU cores, cutting build time proportionally.
8. You inherit a monolith Android app with 300K LOC. How do you start modularizing it?
Senior⌄
Start bottom-up: (1) Extract :core:common first (utilities, extensions — lowest coupling). (2) Extract :core:network (Retrofit setup). (3) Extract :core:database (Room). (4) Extract :core:domain (entities, repository interfaces). (5) Then extract feature modules one at a time, starting with the most isolated feature. Never try to extract a feature before its dependencies are modularized. Use Dependency Analysis Gradle Plugin to detect illegal dependencies before they block extraction.
9. What is the role of :app in a modularized architecture?
Senior⌄
:app should be a thin orchestration layer — it declares the main Application class, the root Hilt component, the root NavHost, and Hilt module bindings that wire interface to implementation across modules. It doesn't contain business logic. Its build.gradle.kts is the only place that depends on all feature modules. This makes :app the most frequently recompiled module, so keep it minimal.
10. How does modularization affect Hilt dependency injection?
Scenario⌄
Each module can have its own @InstallIn Hilt modules. Feature modules install their bindings in the appropriate component (SingletonComponent for singletons, ViewModelComponent for VMs). The Hilt annotation processor in :app aggregates all @HiltAndroidApp, @InstallIn, and @AndroidEntryPoint components from all modules at compile time. Interfaces are typically defined in :core:domain, implemented in the feature module, and bound via @Binds in the feature's Hilt module.
