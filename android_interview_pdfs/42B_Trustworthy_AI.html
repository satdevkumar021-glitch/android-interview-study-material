42B — Trustworthy AI: Principles & Responsible Development

The 6 universal principles of trustworthy AI — explainability, fairness, robustness, transparency, privacy, and accountability — with concrete Android examples, interview answers, and developer responsibilities.

ID: 42B ⭐ Tier 1 🔥 Interview Critical
🧠
1. Why Trustworthy AI Matters

AI systems now make consequential decisions that affect real people — loan approvals, medical triage, content moderation, fraud detection, job candidate screening. Unlike traditional software where bugs produce wrong outputs, AI failures can produce systematically wrong outputs for specific groups of people, at scale, without anyone noticing until significant harm has occurred.

The cost of untrustworthy AI

  • Amazon's hiring algorithm (2018) — trained on historical hiring data (predominantly male engineers), the model penalised CVs containing the word "women's". Shelved after discovery.
  • COMPAS recidivism tool (2016) — risk assessment tool used in US courts showed racial bias: Black defendants were nearly twice as likely to be incorrectly flagged as high-risk for re-offending.
  • Facial recognition misidentification — MIT Media Lab study found error rates of 0.8% for lighter-skinned men vs 34.7% for darker-skinned women. Several wrongful arrests followed.
  • LLM hallucinations in legal filings (2023) — lawyers cited cases invented by ChatGPT. The court found no such cases existed.

Android context — AI is everywhere now

AI is no longer an optional feature. It is embedded in the Android platform itself and in every production app:

  • ML Kit — face detection, text recognition, barcode scanning used in millions of apps
  • Gemini Nano — on-device LLM available in Android 14+ for summarisation, smart reply, image description
  • Recommendation systems — personalised product feeds, content ranking, search autocomplete
  • Fraud detection — payment risk scoring, anomaly detection in banking apps
  • Accessibility AI — Live Transcribe, Look Out, TalkBack enhancements
Senior Mental Model
Trustworthy AI is not about making AI perfect — it's about making AI accountable. You can't always prevent bias or explain every prediction. But you can detect it, measure it, document it, and give users recourse when it goes wrong. The goal is a system that fails gracefully, visibly, and reparably — not silently and irreversibly.

The 7th implicit principle: Human Oversight

The EU AI Act adds a legally binding requirement that high-risk AI systems must have human-in-the-loop checkpoints. High-risk categories include: biometric identification, critical infrastructure, employment decisions, access to essential services, and law enforcement. If your Android app falls into one of these categories — a banking credit scoring feature, a medical diagnosis assistant, a job application ranker — you legally need a human review step before consequential decisions take effect.

Interview Tip
Interviewers often ask: "If an AI feature you shipped causes harm, who is responsible?" The answer is always: the developer/team who shipped it. Not the model provider, not the data scientist, not the AI SDK vendor. You integrated it, you validated it (or failed to), you shipped it. Own that responsibility — it signals seniority.

3. Explainability in Practice

Two levels of explainability

  • Global explainability — Why does the model generally prefer certain inputs? What features matter most overall? (SHAP global importance, decision tree surrogate models)
  • Local explainability — Why did the model make THIS specific prediction for THIS user at THIS moment? (LIME, SHAP values per-instance, attention maps)

Techniques

TechniqueWhat it doesBest for
SHAPAssigns each feature a contribution value for a specific predictionTabular models (fraud detection, credit scoring)
LIMEBuilds a local linear approximation around one predictionImage and text models
Attention mapsShows which tokens/regions the model attended toNLP, vision transformers
Saliency mapsGradient-based highlight of input pixels that influenced outputCNN image classifiers
Confidence scoreModel's own probability estimate for its predictionAll models — simplest first step

Android implementation pattern

Return confidence score and top contributing features alongside every prediction:

// Data class carrying prediction + explanation
data class PredictionResult(
    val label: String,
    val confidence: Float,               // 0.0 – 1.0
    val topFeatures: List<FeatureContribution>,
    val isHighConfidence: Boolean = confidence >= 0.75f
)

data class FeatureContribution(
    val name: String,       // e.g. "Purchase history", "Location"
    val contribution: Float, // positive = pushed toward this label
    val humanLabel: String  // "Because you viewed similar items last week"
)

// In the ViewModel — only show AI recommendation if confidence is high enough
fun getRecommendation(userId: String): Flow<UiState> = flow {
    val result = recommendationEngine.predict(userId)
    if (result.confidence < 0.6f) {
        // Below confidence threshold — fall back to editorial picks
        emit(UiState.Editorial(getEditorialPicks()))
    } else {
        emit(UiState.Personalised(result))
    }
}

// In the UI — show explanation to the user
@Composable
fun RecommendationCard(result: PredictionResult) {
    Column {
        Text(result.label)
        if (result.topFeatures.isNotEmpty()) {
            Text(
                text = "Recommended because: ${result.topFeatures.first().humanLabel}",
                style = MaterialTheme.typography.bodySmall,
                color = MaterialTheme.colorScheme.onSurfaceVariant
            )
        }
    }
}
Senior Distinction
Separate model explainability (ML concern — SHAP, gradients) from product explainability (UX concern — plain language reasons). Users don't want gradient attribution values. They want "We recommended this because you bought X last month." Your job as the Android developer is to translate the model's technical explanation into human-readable UI copy.

When you can't explain: black-box strategy

Deep neural networks are often inherently opaque. When you can't explain why, you can still explain what:

  • Always show the confidence score
  • Provide a "Why am I seeing this?" UI element
  • Give users control: "Show me less like this"
  • Log the input context for audit purposes even if you can't explain the reasoning

4. Fairness & Bias Mitigation

Types of bias in the ML pipeline

Bias TypeWhere it entersExampleFix
Historical biasTraining data reflects past discriminationHiring model trained on mostly-male engineering hiresRebalance training data; add fairness constraints to loss
Representation biasTraining data underrepresents certain groupsFace recognition trained on mostly lighter-skinned facesCollect more diverse data; oversample underrepresented groups
Measurement biasProxy variable correlates with protected attributeCredit model penalises certain postcodes (racial proxy)Remove proxy features; use fairness-aware feature selection
Label biasHuman annotators apply subjective criteria inconsistentlyContent moderation labels vary by annotator demographicsMultiple annotators + inter-rater reliability checks
Feedback loop biasBiased predictions generate biased new training dataRecommendation system amplifies popularity of majority-group contentInject diversity; break feedback loops with exploration

Slice-based evaluation — the correct way to test fairness

Aggregate accuracy (e.g. "95% accuracy") hides fairness problems. Always evaluate accuracy broken down by demographic subgroups.

// Android unit test: validate model fairness across age groups
@Test
fun faceDetection_accuracyEquitableAcrossAgeGroups() {
    val testSlices = mapOf(
        "age_18_30"  to loadTestImages("test_data/age_18_30"),
        "age_31_50"  to loadTestImages("test_data/age_31_50"),
        "age_51_plus" to loadTestImages("test_data/age_51_plus")
    )
    val accuracies = testSlices.mapValues { (_, images) ->
        faceDetector.evaluateAccuracy(images)
    }
    // Assert no slice is more than 5% below the best-performing slice
    val best = accuracies.values.max()
    accuracies.forEach { (slice, acc) ->
        assertTrue(
            "Slice $slice accuracy $acc is more than 5% below best ($best)",
            best - acc <= 0.05f
        )
    }
}

Mitigation strategies

  • Pre-processing — resampling (oversample underrepresented groups), re-weighting training examples by inverse group frequency
  • In-processing — add fairness constraint to the training loss function; adversarial debiasing (a second model learns to predict protected attribute — first model penalised if it's possible)
  • Post-processing — calibrate decision thresholds per group to equalise false positive rates; reject-option classification
Critical Insight
Bias is predominantly a data problem, not an algorithm problem. The same neural network architecture that produces biased results on biased data will produce fair results on balanced, representative data. Fix the data pipeline first. Algorithmic mitigation is a patch, not a cure.

Android-specific defences

// 1. Confidence threshold gating — reject uncertain predictions
fun SafeClassifier.classifyWithGate(input: Bitmap): ClassificationResult? {
    val result = model.run(input)
    return if (result.topScore >= 0.70f) result else null
    // null = fall back to rule-based or human review
}

// 2. Input validation before inference
fun sanitizeForInference(userText: String): String {
    return userText
        .take(2000)                              // limit length
        .replace(Regex("[<>&\"']"), "")           // strip injection chars
        .replace(Regex("ignore.*instructions",    // block prompt injection
            RegexOption.IGNORE_CASE), "[blocked]")
}

// 3. TFLite model file integrity check before loading
fun verifyModelIntegrity(modelBytes: ByteArray, expectedHash: String): Boolean {
    val digest = MessageDigest.getInstance("SHA-256")
    val actualHash = digest.digest(modelBytes)
        .joinToString("") { "%02x".format(it) }
    return actualHash == expectedHash
}

Out-of-distribution (OOD) detection

When an input is too different from the training data distribution, the model's prediction is unreliable — even if it outputs a high confidence score. OOD detection catches this:

  • Temperature scaling — calibrate confidence scores to be more reliable
  • Mahalanobis distance — measure how far an input is from the centroid of training class clusters
  • Ensemble disagreement — if multiple models disagree, the input is likely OOD
Key Insight
Robustness and security are converging. A model trained with adversarial examples is also more robust to natural distribution shifts (different lighting, compression artefacts, device variation). Adversarial training improves both attack resistance and generalisation.

6. Privacy & Data Governance

Privacy by design for AI features

  • Data minimisation — don't send a full user profile when only age range is needed for inference
  • Purpose limitation — data collected for personalisation should not be used for unrelated model training
  • On-device first — run inference locally when possible; data never leaves the device
  • Time-limited retention — inference inputs should not be stored longer than necessary

On-device vs cloud inference tradeoff

FactorOn-device (ML Kit, TFLite, Gemini Nano)Cloud (Gemini API, Vertex AI)
Privacy✅ Data never leaves device❌ Data sent to server — requires consent
Latency✅ No network round-trip; offline works❌ Network-dependent; fails offline
Model freshness❌ Requires app update to refresh model✅ Update model without app release
Compute❌ Limited by device hardware (NPU/GPU)✅ Unlimited server-side compute
Model size❌ Limited (~few hundred MB practical max)✅ Trillion-parameter models available
Cost✅ No server costs❌ Per-inference billing
GDPR compliance✅ Straightforward — no data transfer❌ Requires DPA, data residency, consent

GDPR / privacy regulation obligations for AI

  • Article 22 (right to explanation) — users have the right to a meaningful explanation for decisions made solely by automated systems that significantly affect them. This legally mandates explainability for high-impact AI decisions.
  • Right to erasure (Art. 17) — if a user requests deletion, you must remove their data from model fine-tuning datasets and inference logs, not just your database
  • Data minimisation (Art. 5) — collect and process only what is strictly necessary for the stated AI purpose
  • Consent (Art. 6/7) — explicit consent is required before using personal data for AI personalisation
// Check consent before enabling AI personalisation
@Composable
fun PersonalisedFeed(viewModel: FeedViewModel) {
    val consentState by viewModel.aiConsentState.collectAsStateWithLifecycle()
    when (consentState) {
        ConsentState.GRANTED  -> AiPersonalisedFeed(viewModel)
        ConsentState.DENIED   -> EditorialFeed(viewModel)     // fallback
        ConsentState.PENDING  -> ConsentDialog(                  // ask first
            onGrant = { viewModel.grantAiConsent() },
            onDeny  = { viewModel.denyAiConsent() }
        )
    }
}

Federated learning — privacy-preserving model improvement

Federated learning trains models on user data without centralising it. Model updates (gradients) are aggregated across devices; raw data never leaves. Used by Google for Gboard next-word prediction and Chrome phishing detection. Key properties:

  • No raw user data is transmitted — only model updates
  • Differential privacy can be added to model updates (add noise to gradients before aggregation)
  • Secure aggregation prevents the server from seeing individual device updates

7. Developer Accountability

The accountability chain

AI systems involve many actors — and each is accountable for their specific role. As the Android developer integrating AI, you sit at the critical point between the model and the user:

ActorResponsible forExample failure
Data providerRepresentative, legal, documented training dataTraining on scraped personal data without consent
Model builder / data scientistModel architecture, training, evaluation, bias testingShipping without per-slice fairness evaluation
Android developer (YOU)Integration, validation, monitoring, kill switch, user recourseShipping SDK integration without acceptance tests or monitoring
Product managerUse case definition, risk classification, user disclosureUsing AI for consequential decisions without disclosing it
Legal / complianceRegulatory compliance (GDPR, EU AI Act), terms disclosureOperating high-risk AI without human oversight

Your responsibilities as the integrating developer

  • Validate before shipping — write acceptance tests against the AI SDK output, not just unit tests of your own code
  • Define acceptance criteria — "accuracy ≥ 90% on our test set" or "confidence threshold ≥ 0.70 before showing to user"
  • Build the kill switch — every AI feature needs a feature flag that can disable it instantly without an app release
  • Monitor in production — log confidence distributions, track user feedback, alert on distribution shift
  • Own the rollback plan — what is the non-AI fallback when the model is disabled?
  • Document what you ship — model card reference, version, known limitations, in the PR description
// Feature flag + telemetry for AI feature — kill switch pattern
class RecommendationRepository(
    private val remoteConfig: RemoteConfig,
    private val analytics: Analytics,
    private val aiEngine: RecommendationEngine,
    private val editorialFallback: EditorialRepository
) {
    suspend fun getRecommendations(userId: String): List<Product> {
        // Kill switch — disable instantly via Firebase Remote Config
        val aiEnabled = remoteConfig.getBoolean("ai_recommendations_enabled")
        if (!aiEnabled) return editorialFallback.get(userId)

        return try {
            val result = aiEngine.recommend(userId)
            // Log for monitoring — track confidence distribution over time
            analytics.logEvent("ai_recommendation", bundleOf(
                "confidence" to result.avgConfidence,
                "model_version" to aiEngine.modelVersion,
                "fallback_used" to false
            ))
            result.products
        } catch (e: Exception) {
            // Log failure + fall back gracefully
            analytics.logEvent("ai_recommendation_error", bundleOf(
                "error" to e.message,
                "fallback_used" to true
            ))
            editorialFallback.get(userId)
        }
    }
}

Model cards — the transparency document

A model card is a short document that describes an ML model's intended use, performance, limitations, and evaluation methodology. Every AI feature you ship should have one — even if informal:

  • Model overview — what it does, version, training data summary
  • Intended use — what it was designed for; what it should NOT be used for
  • Performance metrics — aggregate accuracy + per-slice fairness metrics
  • Known limitations — failure modes, edge cases, demographic gaps
  • Evaluation methodology — how it was tested before ship
From the Field
A widely held industry principle: "The developer who ships the code is accountable for what the AI does in production." This means you don't just integrate the SDK — you define acceptance criteria, write validation tests, set up monitoring, and own the rollback plan. The model provider built the engine. You put it in the car and handed the keys to the user. If the car crashes, you are responsible for the integration.

9. Interview Questions
Q1. Name the 6 principles of trustworthy AI.
Easy⌄
Explainability (users understand decisions) · Fairness (equitable across groups) · Robustness (correct on adversarial/edge cases) · Transparency (capabilities and limitations documented) · Privacy (data minimisation, user rights) · Accountability (humans remain responsible for outcomes).
Q2. Why is on-device inference preferred from a privacy perspective?
Easy⌄
Data never leaves the device — no network transmission, no server storage, no third-party data exposure. This directly satisfies GDPR data minimisation (Art. 5) and avoids the need for a Data Processing Agreement with a cloud AI provider. ML Kit, TFLite, and Gemini Nano all run entirely on-device. The tradeoff is limited model size and compute compared to cloud inference.
Q3. Your face recognition feature has 30% higher error for users over 60. What do you do?
Medium⌄

Do not ship until the disparity is acceptable. Steps:

  1. Quantify: run full slice-based evaluation across all age/gender/skin-tone combinations to understand the full extent
  2. Root cause: likely a representation bias — training data underrepresents older faces. Collect more diverse training data.
  3. Mitigate: oversample underrepresented groups, add fairness constraint to training loss, re-train and re-evaluate
  4. If shipping is forced before fix: add a fallback path for low-confidence cases (PIN entry, manual verification), disclose the limitation in documentation, set a remediation timeline
  5. Post-ship: add production telemetry to monitor per-age-group error rate and alert if it worsens
Key point: a 30% accuracy gap is a fairness failure. Shipping it harms older users and creates legal liability. Slice-based evaluation should have caught this before it reached a decision point.
Q4. A user complains your AI recommendation is wrong. How do you explain the decision to them?
Medium⌄

Two levels of response:

  • User-facing: "We recommended this because you viewed similar products recently and this matches your size preference." — translate model features into plain language. Show confidence. Provide "Not interested" feedback mechanism.
  • Developer/support: log the decision context (top features, confidence score, model version, timestamp) at inference time so support can investigate. Without this log, the decision is unauditable.
GDPR Article 22 gives users the right to a meaningful explanation for significant automated decisions. Even without legal obligation, explainability is a product quality concern — users who understand why they see a recommendation are more likely to trust your AI feature.
Q5. You're integrating a third-party AI SDK into a banking app. What trustworthy AI checks do you perform before shipping?
Hard⌄
  1. Explainability: Can the SDK return confidence scores and feature attributions? If not, build a wrapper that at minimum exposes confidence.
  2. Fairness: Run the SDK on a diverse test dataset. Measure accuracy per demographic slice. Define acceptable disparity threshold before testing.
  3. Robustness: Fuzz test with adversarial inputs. Test edge cases: empty input, extremely long input, special characters, non-ASCII.
  4. Transparency: Obtain the vendor's model card. What was it trained on? What are the known failure modes? What is the update policy?
  5. Privacy: Does the SDK send data off-device? If so, to where, under what DPA, with what retention policy? For banking, on-device only is strongly preferred.
  6. Accountability: Wrap the SDK call with a feature flag kill switch. Define the fallback. Write acceptance tests. Set up production monitoring of confidence distributions.
Q6. How do you detect if your shipped ML model starts performing worse over time (model drift)?
Hard⌄

Two types of drift:

  • Data drift — input distribution changes (seasonal behaviour, new user demographics). Detect: monitor average confidence scores and input feature distributions over time.
  • Concept drift — the relationship between inputs and correct outputs changes (user preferences evolve, language changes). Detect: track downstream business metrics (CTR, conversion, user feedback).

Detection strategy in Android:

  1. Log confidence score distribution daily. Alert if average confidence drops by >5% week-over-week.
  2. Collect optional user feedback (thumbs up/down on recommendations). Track rating ratio over time.
  3. Shadow mode: run the new model in parallel with the old one, compare outputs before switching.
  4. A/B testing: canary release to 5% of users, compare downstream metrics before full rollout.
Q7. A prompt injection attack causes your LLM feature to output harmful content. Walk through your incident response.
Hard⌄
  1. Immediate: Toggle the feature flag to disable the LLM feature for all users. This is why the kill switch exists.
  2. Assess: Pull audit logs. How many users were affected? What input triggered it? What output was produced? Is there PII exposure?
  3. Contain: If user data was exposed, initiate GDPR breach notification procedure (72-hour clock starts).
  4. Root cause: Identify the injection pattern. Was it a known attack vector? Was there no input sanitisation? Was the system prompt exposed?
  5. Fix: Add input sanitisation for the injection pattern. Add output filtering (block harmful content before displaying). Harden system prompt isolation.
  6. Re-enable: Staged rollout (1% → 10% → 100%) with monitoring at each stage. Verify the injection pattern no longer works.
  7. Post-mortem: Document the incident, root cause, fix, and prevention. Update threat model for LLM integration.
Q8. The EU AI Act classifies your app's AI feature as "high-risk." What does that mean for your development process?
Hard⌄

High-risk AI systems (biometric identification, credit scoring, employment screening, medical devices, law enforcement) under the EU AI Act require:

  • Human oversight: A human must be able to understand, override, and shut down the AI system. Implement human-in-the-loop review for consequential decisions.
  • Risk management system: Documented identification and mitigation of foreseeable risks throughout the lifecycle.
  • Data governance: Training data must be representative, free of errors, and complete. Documented data provenance required.
  • Technical documentation: Full model card, architecture documentation, validation methodology — must be kept up to date.
  • Transparency to users: Users must be informed they are interacting with an AI system. Explanation of the system's capabilities and limitations.
  • Accuracy and robustness: Required to meet specific accuracy targets; must be tested against adversarial conditions.
  • Conformity assessment: Before deployment, must demonstrate compliance — either through self-assessment (lower risk) or third-party audit (higher risk categories).
  • Post-market monitoring: Mandatory ongoing monitoring and incident reporting to national authorities.
In practice: a designated AI officer, formal risk assessment documentation, human review workflows, incident reporting procedures, and potentially a third-party audit — all before launch. This significantly changes your development timeline and process.
