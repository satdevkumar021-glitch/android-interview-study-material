5A — Coroutines Fundamentals

What a coroutine is, how it differs from a thread, CoroutineScope, CoroutineContext, Job, and Dispatchers — the core concepts every Android engineer must own.

ID: 5A ⭐ Tier 1
🔍
1. Overview

What is a coroutine?

A coroutine is a suspendable computation — a unit of work that can pause execution at suspension points and resume later without blocking the underlying thread. Under the hood it is a state machine, not a thread.

  • Thread: OS-managed, 1–2 MB stack, expensive context switch, blocking I/O blocks the thread
  • Coroutine: library-managed, ~a few hundred bytes on the heap, context switch is a function call, I/O suspends without blocking
  • You can run 100,000 coroutines on a small thread pool — you cannot run 100,000 threads

Core building blocks

  • CoroutineScope — defines the lifetime/lifecycle boundary for coroutines launched within it
  • CoroutineContext — a set of key-value elements: Dispatcher + Job + CoroutineName + CoroutineExceptionHandler
  • Job — a handle to the coroutine lifecycle (active → completing → completed / cancelling → cancelled)
  • Dispatcher — decides which thread(s) a coroutine runs on
Senior Mental Model
CoroutineContext is an immutable set — adding elements creates a new context via the + operator. When you do Dispatchers.IO + job + handler, you get a new CoroutineContext combining all three. Every child coroutine inherits and merges its parent's context unless explicitly overridden.

2. How It Works

Continuation-Passing Style (CPS) under the hood

The Kotlin compiler transforms every suspend function into a state machine. The function receives an additional hidden Continuation<T> parameter at compile time.

// What you write:
suspend fun fetchUser(id: String): User {
    val raw = apiCall(id)      // suspension point
    return parseUser(raw)
}

// What the compiler generates (simplified):
fun fetchUser(id: String, continuation: Continuation<User>): Any {
    when (label) {
        0 -> { label = 1; return apiCall(id, this) }  // suspend
        1 -> { return parseUser(result) }              // resume
    }
}

When apiCall suspends, the coroutine saves its local variables into the Continuation object (on the heap) and returns control to the thread. When I/O completes, the dispatcher calls continuation.resume(result), the state machine picks up at label 1.

CoroutineContext — the four elements

val context: CoroutineContext =
    Dispatchers.IO +                           // which thread
    Job() +                                    // lifecycle handle
    CoroutineName("PaymentFlow") +            // for debugging
    CoroutineExceptionHandler { _, e ->        // uncaught errors
        Timber.e(e, "Coroutine failed")
    }

Dispatcher internals

// Dispatchers.Main — posts to Android main looper
// Dispatchers.IO   — shared thread pool, up to 64 + CPU threads
// Dispatchers.Default — CPU-bound pool, threads == CPU count
// Dispatchers.Unconfined — no thread switching, runs inline

// Custom dispatcher for DB work:

Key Insight
Dispatchers.IO and Dispatchers.Default share the same backing thread pool since Kotlin 1.7. limitedParallelism() creates a view that caps concurrency without creating new threads.

3. When to Use

Use coroutines when:

  • Network I/O: Retrofit suspend functions, any HTTP calls
  • Database operations: Room DAO suspend functions
  • File I/O: reading/writing files on Dispatchers.IO
  • Parallel work: running multiple API calls concurrently with async/await
  • Sequential async: chaining async operations without callback hell
  • Lifecycle-aware work: viewModelScope / lifecycleScope auto-cancel on destroy

Thread vs Coroutine decision matrix

4. Production Example

Banking app: transaction history with scope & context

// Domain layer — pure suspend function
class GetTransactionHistoryUseCase(
    private val repository: TransactionRepository
) {
    suspend operator fun invoke(accountId: String): List<Transaction> =
        repository.getTransactions(accountId)
}

// ViewModel layer — scoped to ViewModel lifecycle
class TransactionViewModel(
    private val getHistory: GetTransactionHistoryUseCase
) : ViewModel() {

    private val _state = MutableStateFlow<UiState>(UiState.Loading)
    val state: StateFlow<UiState> = _state.asStateFlow()

    fun loadTransactions(accountId: String) {
        // viewModelScope uses Dispatchers.Main.immediate + SupervisorJob
        viewModelScope.launch {
            _state.update { UiState.Loading }
            try {
                // withContext switches to IO pool for network/db
                val txns = withContext(Dispatchers.IO) {
                    getHistory(accountId)
                }
                _state.update { UiState.Success(txns) }
            } catch (e: Exception) {
                _state.update { UiState.Error(e.localizedMessage()) }
            }
        }
    }
}

// Repository layer — Room + Retrofit both expose suspend fns
class TransactionRepositoryImpl(
    private val api: TransactionApi,
    private val dao: TransactionDao
) : TransactionRepository {

    override suspend fun getTransactions(id: String): List<Transaction> {
        return try {
            val remote = api.fetchTransactions(id)  // Retrofit suspend
            dao.insertAll(remote)                   // Room suspend
            remote
        } catch (e: IOException) {
            dao.getAll(id)                          // fallback to cache
        }
    }
}

6. Pitfalls & Best Practices

Common mistakes

Pitfall 1 — Blocking the main thread
Calling Thread.sleep() or blocking network code on Dispatchers.Main freezes the UI. Always use delay() inside coroutines and withContext(Dispatchers.IO) for I/O.
Pitfall 2 — Leaking coroutines with GlobalScope
GlobalScope.launch creates coroutines that live forever — they outlive Activities, ViewModels, even the app screen. Use viewModelScope or lifecycleScope.
Pitfall 3 — Creating a new Job in scope
viewModelScope.launch(Job()) { ... } breaks structured concurrency — the new Job has no parent, so cancellation from the scope won't propagate to this child. Never add a raw Job to a launch/async call; use SupervisorJob at scope level.
Best Practice — Inject Dispatchers
Never hardcode Dispatchers.IO directly in production classes. Inject a CoroutineDispatcher interface so tests can inject TestCoroutineDispatcher. 
// ✅ Testable — inject dispatcher
class UserRepository(
    private val api: UserApi,
    private val ioDispatcher: CoroutineDispatcher = Dispatchers.IO
) {
    suspend fun getUser(id: String) = withContext(ioDispatcher) {
        api.fetchUser(id)
    }
}

7. Interview Framework

30-second answer

"A coroutine is a suspendable computation — it can pause at suspension points without blocking the thread, saving state on the heap instead of the stack. Unlike threads, they're extremely lightweight: you can run 100,000 coroutines on a small thread pool. They're structured through CoroutineScope which ties their lifetime to a lifecycle owner, preventing leaks."

2-minute answer

"Under the hood, the Kotlin compiler transforms suspend functions into state machines via continuation-passing style. Each suspension point becomes a label in the state machine; the continuation object preserves local variables on the heap so the thread is freed. The runtime is just a library — no OS involvement.

The four core pieces: CoroutineScope defines the lifetime boundary. CoroutineContext is an immutable set combining a Dispatcher, a Job, and optional handlers. Job tracks the lifecycle (New→Active→Completing→Completed). The Dispatcher decides which thread pool runs the coroutine.

In production, viewModelScope gives us a SupervisorJob + Main dispatcher, so any child failure doesn't cancel siblings, and everything auto-cancels when the ViewModel is cleared. I always inject dispatchers to keep classes testable."

2

3

4

Follow-up Q&A

Q: "What's in a CoroutineContext?"

A: It's an indexed set of elements. The key ones are: Job (lifecycle), ContinuationInterceptor (Dispatcher), CoroutineName (debug), CoroutineExceptionHandler. Child coroutines inherit and override individual elements.

Q: "Why can't you call a suspend function from a regular function?"

A: Suspend functions compile to functions that take a hidden Continuation parameter. The caller must be inside a coroutine context to pass that continuation and handle the COROUTINE_SUSPENDED return value. Regular functions have no such mechanism.

Senior insight

Senior Insight
In high-throughput services (e.g., banking backend on Ktor), we use Dispatchers.IO.limitedParallelism(n) to create fair-use pools — for example a dedicated 4-thread pool for Postgres connections matching the JDBC pool size. This prevents thread starvation where one feature monopolises all IO threads.

9. Interview Questions
What is a coroutine and how does it differ from a thread?
Basic⌄
A coroutine is a suspendable computation — it can pause at suspension points (marked with suspend) without blocking its thread. State is saved on the heap via a Continuation object. Threads are OS-managed with 1–2 MB stacks; coroutines cost ~hundreds of bytes and are library-managed, making 100,000 concurrent coroutines feasible.
What is CoroutineContext and what elements does it contain?
Basic⌄
CoroutineContext is an immutable indexed set of elements. Key elements: Job (lifecycle, parent-child links), ContinuationInterceptor / Dispatcher (which thread to run on), CoroutineName (debugging), CoroutineExceptionHandler (uncaught error handling). Combine them with + operator.
Which Dispatcher would you use for a database query and why?
Basic⌄
Dispatchers.IO. It uses a thread pool optimised for blocking I/O with up to 64 threads (+ CPU count), so blocking JDBC/file calls don't starve CPU threads. For Room with suspend DAO functions, Room handles the dispatcher internally. For custom blocking calls, wrap with withContext(Dispatchers.IO).
How does the Kotlin compiler implement suspend functions? Walk through the transformation.
Intermediate⌄
The compiler performs Continuation-Passing Style (CPS) transformation. Each suspend function gets an extra Continuation<T> parameter and becomes a state machine. Each suspension point is a label. On suspension, local variables are stored in the Continuation (heap), the function returns COROUTINE_SUSPENDED, freeing the thread. On resume, the dispatcher calls continuation.resume(value) and execution picks up at the saved label.
Why should you never use GlobalScope in Android?
Intermediate⌄
GlobalScope has no parent Job and lives for the entire app process. Coroutines launched in it are never automatically cancelled — they survive screen rotations, ViewModel clears, and even back navigation. This causes memory leaks, duplicate API calls, and crashes when coroutines try to update destroyed UI components. Use viewModelScope or lifecycleScope instead.
What is the difference between Dispatchers.IO and Dispatchers.Default? When does it matter?
Intermediate⌄
Since Kotlin 1.7, both share the same thread pool internally. The difference is the concurrency limit: Default limits to CPU count (e.g., 8 on an 8-core device) — suitable for CPU-bound work where more parallelism adds contention. IO allows up to 64 + CPU threads — suitable for blocking I/O where threads spend most time waiting. Using IO for CPU work wastes threads; using Default for I/O creates bottlenecks.
Why should dispatchers be injected rather than referenced directly?
Intermediate⌄
Hardcoded Dispatchers.IO makes unit tests non-deterministic and slow because tests run on real thread pools. By injecting a CoroutineDispatcher interface, tests can provide StandardTestDispatcher or UnconfinedTestDispatcher which give full control over execution. This also makes classes more composable — a caller can provide a dispatcher matching their concurrency model.
A coroutine in a banking app is processing a payment when the user rotates the device. The ViewModel is recreated. What happens and why?
Senior⌄
The ViewModel survives rotation (it's not destroyed), so viewModelScope coroutines continue running undisturbed. The new Activity attaches to the same ViewModel and its StateFlow/LiveData re-emits the current state. If the ViewModel were cleared (e.g., user navigates away), viewModelScope is cancelled, which cancels all children cooperatively. For critical financial operations that must complete regardless, they should be delegated to a WorkManager task or a Service scope — not tied to the ViewModel's lifecycle.
Explain how parent-child Job relationships work in structured concurrency.
Senior⌄
When a coroutine is launched inside a scope, the new coroutine's Job becomes a child of the scope's Job. This creates a hierarchy: cancelling a parent cancels all children; a parent won't complete until all children complete; a child failure propagates up and cancels siblings (unless using SupervisorJob). This tree structure is the core of structured concurrency — no coroutine can outlive its scope, preventing leaks. The child coroutine inherits the parent's CoroutineContext but replaces the Job element with its own new Job.
Design a coroutine scope for a Repository that should survive configuration changes but not the app process exit. Justify your choices.
Senior⌄
Use a custom scope tied to the ViewModel or application component: val scope = CoroutineScope(SupervisorJob() + Dispatchers.IO + exceptionHandler). SupervisorJob ensures one failed child (e.g., one fetch failing) doesn't cancel the others. Dispatchers.IO is the default for repository work. Inject this scope via Hilt using @ApplicationScoped for app-level repositories, or let ViewModel provide it via viewModelScope for UI-bound repos. For true process-level durability (crash recovery), delegate to WorkManager.
