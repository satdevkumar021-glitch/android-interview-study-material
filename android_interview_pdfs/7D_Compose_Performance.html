1. Overview

What triggers recomposition — and what should NOT

Recomposition is triggered by State changes. The performance question is: how much of the tree recomposes? Compose can skip composables where all parameters are equal — this is called smart recomposition. For a composable to be skippable, all its parameters must be stable.

The stability contract

  • Stable type: if a == b then a will never produce a different result for the same inputs — Compose can safely skip it
  • Immutable type: stronger — value never changes after creation (primitives, String, @Immutable data class)
  • Unstable type: Compose cannot trust equals() — cannot skip (List<>, MutableList, regular classes without @Stable)
Senior Mental Model
Every composable parameter that is an unstable type prevents the composable from being skippable — it MUST re-run on every parent recomposition, even if the actual value didn't change. In a 500-item list, this means 500 items recompose when the parent recomposes. Understanding stability is the key to Compose performance at scale.

2. Stability System

@Stable annotation

// @Stable: promises that equals() is reliable AND observable
// (Compose will be notified when observable properties change)
@Stable
class UserState {
    var name by mutableStateOf("")  // observable via State
    var email by mutableStateOf("")
}
// Compose can skip composables with UserState params if the reference
// is the same — it trusts the State fields to trigger recomposition

@Immutable annotation

// @Immutable: all public properties never change after construction
// Strongest stability guarantee
@Immutable
data class ProductUiModel(
    val id: String,
    val name: String,
    val price: Double
)
// data class is @Immutable IF all fields are val and stable types
// Compose compiler may infer this automatically in some cases

What the compiler infers automatically

3. Unstable Types — The List Problem

Why List<T> is unstable

// List<T> is an interface — Compose sees it as potentially mutable
// Even if you pass a listOf(), Compose can't trust equals()

// ❌ UNSTABLE: composable cannot be skipped
@Composable
fun ProductList(products: List<Product>) { /* ... */ }
// Parent recomposes → ProductList ALWAYS recomposes, even if list unchanged

// ✅ Fix 1: @Immutable wrapper
@Immutable
data class ProductList(val items: List<Product>)

@Composable
fun ProductListScreen(products: ProductList) { /* stable ✅ */ }

// ✅ Fix 2: kotlinx.collections.immutable
implementation("org.jetbrains.kotlinx:kotlinx-collections-immutable:0.3.7")

@Composable
fun ProductListScreen(products: ImmutableList<Product>) { /* stable ✅ */ }

Lambda stability

// Lambdas that capture unstable values are themselves unstable
@Composable
fun Parent() {
    val list: List<String> = remember { listOf("a", "b") }

    // ❌ Lambda captures unstable list — unstable lambda
    Child(onClick = { process(list) })
}

// ✅ Fix: stabilize the list, or move lambda out of recomposition scope
val stableList: ImmutableList<String> = remember { persistentListOf("a", "b") }
Child(onClick = { process(stableList) })  // ✅ stable

4. LazyColumn Keys & remember

LazyColumn keys — stable item identity

// ❌ Without key: index is the identity
// Insert an item → all positions shift → all items recompose
LazyColumn {
    items(products) { product ->
        ProductCard(product)  // identity = index in list
    }
}

// ✅ With key: item.id is the identity
// Insert an item → only new item created, others keep their composition
LazyColumn {
    items(products, key = { it.id }) { product ->  // stable String ID
        ProductCard(product)
    }
}
// Keys enable: correct animations, proper remember state per item,
// efficient reuse of composition for unchanged items

remember for expensive computations in composables

// ❌ Expensive computation runs every recomposition
@Composable
fun ChartComposable(data: List<DataPoint>) {
    val chartPath = buildBezierPath(data)  // ❌ O(n) on every recompose
    Canvas { drawPath(chartPath) }
}

// ✅ Memoize with remember(key)
@Composable
fun ChartComposable(data: List<DataPoint>) {
    val chartPath = remember(data) {    // ✅ only recomputes when data changes
        buildBezierPath(data)
    }
    Canvas { drawPath(chartPath) }
}

Modifier.graphicsLayer — avoid recomposition for visual changes

// ❌ alpha in modifier triggers recomposition to update UI
Box(Modifier.alpha(animatedAlpha))  // recomposes on alpha change

// ✅ graphicsLayer: runs in draw phase, no recomposition
Box(
    Modifier.graphicsLayer(alpha = animatedAlpha)
) // No recomposition — handled by render layer

5. Production Example

E-commerce: performant product list

// ✅ Stable state wrapper for list
@Immutable
data class ProductScreenState(
    val products: ImmutableList<ProductUiModel> = persistentListOf(),
    val isLoading: Boolean = false
)

@Immutable
data class ProductUiModel(
    val id: String,
    val name: String,
    val price: String,       // Pre-formatted string — stable
    val imageUrl: String
)

@Composable
fun ProductListScreen(
    state: ProductScreenState,    // @Immutable → stable
    onAddToCart: (String) -> Unit  // lambdas on stable types → stable
) {
    LazyColumn {
        items(
            items = state.products,
            key = { it.id }  // stable String key
        ) { product ->
            // ProductCard: all params are @Immutable types → skippable
            ProductCard(
                product = product,
                onAddToCart = { onAddToCart(product.id) }
            )
        }
    }
}

// ✅ Skippable ProductCard — all params stable
@Composable
fun ProductCard(
    product: ProductUiModel,       // @Immutable → stable
    onAddToCart: () -> Unit        // no capture → stable
) {
    // derivedStateOf for expensive display computation
    val displayPrice by remember(product.price) {
        derivedStateOf { formatWithCurrency(product.price) }
    }
    /* ... */
}

6. Pitfalls & Best Practices
Pitfall 1 — Passing List<T> to composables
List<T> is unstable — any composable that takes it as a parameter cannot be skipped. In a list screen, this means every item recomposes whenever the parent updates. Use ImmutableList<T> (kotlinx.collections.immutable) or wrap in an @Immutable data class.
Pitfall 2 — Lambdas capturing non-stable values
A lambda that captures a List<T> or any unstable value is itself unstable. This prevents the composable receiving it from skipping. Fix: ensure captured values are stable, or use remember { { ... } } to stabilize the lambda reference.
Pitfall 3 — LazyColumn without keys
Without stable keys in LazyColumn, inserting or removing items causes all items to recompose and loses per-item state (expanded state, animations). Always provide key = { item.id }.
Best Practice — Compose compiler metrics
Enable compiler reports: freeCompilerArgs += ["-P", "plugin:androidx.compose.compiler.plugins.kotlin:reportsDestination=build/compose_reports"]. The output shows skippable vs restartable composables and identifies unstable parameters. Use this to find performance bottlenecks.

Follow-up Q&A

Q: "What is the difference between @Stable and @Immutable?"

A: @Immutable: stronger contract — all public properties never change after construction. The compiler treats all fields as constants for stability purposes. @Stable: weaker — equals() is reliable AND changes to public properties are observable (via State/observable property). Use @Immutable for pure value objects (UI models). Use @Stable for observable state holders (StateHolder classes with mutableStateOf fields).

Q: "How do you enable Compose compiler reports?"

A: In your app's build.gradle: kotlinOptions { freeCompilerArgs += ["-P", "plugin:androidx.compose.compiler.plugins.kotlin:reportsDestination=${project.buildDir}/compose_reports"] }. Run a build and inspect the `*-composables.txt` file — it shows each composable as skippable/restartable and lists stable/unstable parameters.

Senior insight

Senior Insight
In a banking transaction list with real-time updates, use @Immutable data class TransactionUiModel with pre-computed display strings (formatted amount, date string) rather than passing BigDecimal and Instant. This ensures all fields are stable primitives/strings, the composable is fully skippable, and formatting happens once in the ViewModel — not on every recomposition.

9. Interview Questions
What does it mean for a composable to be "skippable"?
Basic⌄
A skippable composable can be skipped during recomposition if all its parameters are equal to their previous values. Compose checks each parameter using equals(). If all are equal, it assumes the output would be the same and skips executing the function — saving CPU time. For a composable to be skippable, all parameters must be stable types.
Why is List<T> unstable in Compose?
Basic⌄
List<T> is a Kotlin interface. Compose cannot verify that the implementation won't change after the composable receives it — a mutable list could change without notifying Compose. Since Compose can't trust that equals() reliably indicates whether the content changed, it marks List as unstable. Any composable receiving a List parameter is non-skippable and will recompose whenever its parent recomposes.
What is the difference between @Stable and @Immutable?
Basic⌄
@Immutable: all public properties never change after construction — strongest guarantee. Every field is treated as a compile-time constant for stability. Use for value objects (UI models). @Stable: weaker — equals() is reliable AND any changes to public properties are observable (the Compose runtime will be notified). Use for mutable state holders that use mutableStateOf internally. In practice, most UI model classes should use @Immutable.
Why should you always provide keys in LazyColumn?
Intermediate⌄
Without keys, each item's identity is its index. Inserting an item at position 0 shifts all other items' indices — Compose thinks every item changed and recomposes all of them. Remember state per item is also lost. With key = { item.id }, each item has a stable identity. Compose can correctly identify which items moved, which are new, and which are unchanged — only recomposing what actually changed and preserving per-item state.
How do you fix the performance issue caused by passing List<T> to a composable?
Intermediate⌄
Two approaches: (1) Use ImmutableList<T> from the kotlinx.collections.immutable library — it's a stable type by design. Convert in ViewModel: _state.update { it.copy(products = newList.toImmutableList()) }. (2) Wrap in an @Immutable data class: @Immutable data class ProductListState(val items: List<T>) — the annotation makes the wrapper stable, and the inner List is treated as immutable by contract.
When should you use Modifier.graphicsLayer vs setting a modifier property directly?
Intermediate⌄
Modifier.alpha(value) updates a modifier that Compose reads during composition — if the alpha changes, a recomposition is needed to apply the new modifier. Modifier.graphicsLayer { alpha = value } applies the change in the draw phase — no recomposition required. For animated values that change every frame (alpha, scale, translation), graphicsLayer skips the composition phase entirely, giving better performance. For static properties that only change occasionally, direct modifiers are fine.
A product list screen shows 200 items. Typing in a search box causes all 200 items to flicker/recompose. What is the root cause and fix?
Intermediate⌄
Root cause: either (1) ProductCard takes a List parameter (unstable, non-skippable), or (2) the state update changes the list reference even if content is the same, or (3) the search query state is being read by the parent that contains the LazyColumn, causing the LazyColumn's parent to recompose, and without stable/skippable ProductCard, all 200 items recompose. Fix: ensure ProductCard takes @Immutable ProductUiModel (not List). Hoist the search query state to a ViewModel so it doesn't live in the same composable as the list. Add stable keys to LazyColumn.
How do you use Compose compiler metrics to diagnose performance issues?
Senior⌄
Add to app build.gradle: kotlinOptions { freeCompilerArgs += ["-P", "plugin:androidx.compose.compiler.plugins.kotlin:reportsDestination=${buildDir}/compose_reports", "-P", "plugin:androidx.compose.compiler.plugins.kotlin:metricsDestination=${buildDir}/compose_metrics"] }. Run an assembleDebug/Release. Open build/compose_reports/*-composables.txt. Each composable is marked: skippable/non-skippable, restartable/non-restartable. Non-skippable composables list their unstable parameters. The metrics JSON provides counts. Focus on non-skippable composables in hot paths (list items).
Explain why a lambda that captures a non-stable type is itself unstable and how to fix it.
Senior⌄
Compose compiler analyzes lambda capture sites. If a lambda captures an unstable value (e.g., List<T>), the compiler cannot guarantee the lambda's output is stable — calling it with the same "arguments" might produce different results because the captured state may have changed. The lambda is therefore marked unstable, preventing composables that receive it from skipping. Fix: (1) ensure the captured value is stable (ImmutableList, @Immutable class); (2) use remember { { } } to create a stable lambda reference; (3) in Compose 1.5+, lambdas with stable captures are automatically stabilized by the compiler.
An automotive dashboard has a speedometer recomposing at 60fps. The needle is animated but the rest of the dashboard should not recompose. How do you architect this?
Senior⌄
Isolate the high-frequency state. The speed value from sensors updates at 60fps — keep it in a separate StateFlow or animatable. The Speedometer composable reads this directly. Use Modifier.graphicsLayer { rotationZ = needleAngle } for the needle rotation — this runs in the draw phase without recomposition. For the rest of the dashboard (current music, temperature, warnings), use derivedStateOf for threshold-crossing booleans. Structure: DashboardScreen (reads all states) → SpeedGauge (reads only speed via derivedStateOf thresholds) + StaticDashboardPanels (@Stable, skippable). The needle rotation via graphicsLayer avoids even SpeedGauge recomposition at 60fps.
