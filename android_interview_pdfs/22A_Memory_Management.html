22A — Memory Management & Leaks

JVM/ART Memory Model, Generational Garbage Collection, Reference Types (Strong, Weak, Soft, Phantom), the 7 Classic Android Leaks, and LeakCanary heap analysis.

ID: 22A ⭐ Tier 2 (Core System Optimization)
🚀
1. Overview & ART Memory Model

Android applications execute on the Android Runtime (ART). Understanding how memory is partitioned between thread execution and object allocation is essential to preventing OutOfMemoryErrors (OOM) and memory leaks.

JVM / ART Memory Structure
  • Stack Memory: Stores primitive local variables and method call stack frames. Allocated per thread; automatically reclaimed when a function frame pops.
  • Heap Memory: Stores all allocated objects (Bitmaps, Activities, ViewBindings, Singletons). Managed by ART Garbage Collection (GC).
  • GC Root: Objects that are guaranteed to be alive (static variables, running thread stacks, JNI global references). Anything unreachable from GC Roots is eligible for garbage collection.
⚙
2. How It Works: GC & Reference Types

1. The 4 Object Reference Types

Reference TypeGC BehaviorTypical Use Case
Strong Reference val obj = MyClass(). Never collected as long as reachable from a GC root. Standard variables, business models, ViewModels.
WeakReference WeakReference(activity). Reclaimed immediately on the very next GC cycle if no strong references exist. Listeners, static Handlers holding Activity context.
SoftReference Reclaimed only when the JVM is low on memory before throwing OOM. Memory-sensitive bitmap/file caches (rarely used modernly).
PhantomReference Enqueued in a ReferenceQueue after finalization. Low-level native cleanup (used internally by LeakCanary).

2. ART Garbage Collection Algorithms

ART uses Concurrent Copying (CC) and Generational Mark-and-Sweep. Young objects allocate into the nursery (Eden). Surviving objects promote to the Old generation. Garbage collection runs concurrently without freezing UI threads for long pause times.

3. The 7 Classic Android Memory Leaks
1. Activity Context in Singleton

Passing an Activity Context to a Singleton outlives the Activity's lifecycle. Fix: Pass context.applicationContext.

2. Static Reference to View or Activity

companion object { var currentView: View? = null }. The static GC root holds the View and its entire Activity context tree forever. Fix: Never store Views/Activities in static fields.

3. Anonymous Inner Class / Non-Static Inner Class

Non-static inner classes hold an implicit reference to the enclosing Activity (this$0). Fix: Use top-level classes, static nested classes, or Kotlin standalone functions.

4. Handler PostDelayed Holding Activity

A message posted via handler.postDelayed({ ... }, 60_000) places a Message in the Main Looper.MessageQueue holding an implicit reference to the target runnable and Activity. Fix: Call handler.removeCallbacksAndMessages(null) in onDestroy().

5. Uncancelled Coroutine in GlobalScope

Launching a coroutine in GlobalScope or non-lifecycle scope referencing Activity properties keeps the Activity alive in RAM until the job finishes. Fix: Use lifecycleScope or viewModelScope.

6. Unregistered Callback / Listener

Registering LocationManager.requestLocationUpdates() or a custom EventBus without calling removeUpdates() in onStop() / onDestroy() keeps the listener and Activity retained in the system service.

7. Fragment ViewBinding Not Nulled in onDestroyView

A Fragment's View lifecycle is shorter than the Fragment instance lifecycle (e.g. when placed on the back stack). Failing to set _binding = null in onDestroyView() retains the entire View hierarchy in memory.

4. Production Example (Fixing Leaks & LeakCanary)

1. Proper Fragment ViewBinding Lifecycle

class TransactionDetailsFragment : Fragment(R.layout.fragment_details) {

    private var _binding: FragmentDetailsBinding? = null
    private val binding get() = _binding!!

    override fun onViewCreated(view: View, savedInstanceState: Bundle?) {
        super.onViewCreated(view, savedInstanceState)
        _binding = FragmentDetailsBinding.bind(view)
        binding.titleText.text = "Transaction History"
    }

    override fun onDestroyView() {
        super.onDestroyView()
        // MUST nullify to prevent view leak while Fragment is on back stack
        _binding = null
    }
}

2. How LeakCanary Works Under the Hood

  1. Registers an ActivityLifecycleCallbacks listener.
  2. When an Activity reaches onDestroy(), LeakCanary wraps it in a KeyedWeakReference associated with an internal ReferenceQueue.
  3. Waits 5 seconds, forces GC, and checks if the weak reference was cleared.
  4. If still reachable from a GC root, it dumps the heap (.hprof), parses it using Shark, and prints the exact leak trace path.

6. Pitfalls & Best Practices
Pitfall 1: Retaining ViewModel in Static / Long-Lived Scope

ViewModels are intended to survive configuration changes, but NOT app process scope. Storing a ViewModel in a static cache will leak the entire ViewModel and any Activity/Context callbacks attached to it.

Pitfall 2: Including LeakCanary in Release Builds

Never include LeakCanary in release production builds (debugImplementation 'com.squareup.leakcanary:leakcanary-android:...'). Heap dumping freezes the UI and leaks user PII stored in memory to disk.

Pitfall 3: Shallow Size vs Retained Size Confusion

Shallow Size is the memory consumed by the object itself (e.g. 32 bytes). Retained Size is the total memory freed if this object is garbage collected (including all dependent objects it holds, which can be 50+ MB for an Activity).

7. Interview Framework

30-Second Elevator Pitch

"Memory management on Android is handled by ART Generational Garbage Collection. A memory leak occurs when an unused object is prevented from being garbage collected because a surviving GC root (like a singleton, static field, running coroutine, or looper message) retains a strong reference to it. We catch leaks automatically using LeakCanary in debug and Memory Profiler in Android Studio."

2-Minute Deep Dive

"In the ART memory model, local variables live on the Stack while objects occupy the Heap. An object is eligible for GC when it has no strong reference chain leading back to a GC root.

The 7 classic leaks are:
1. Activity context passed to a Singleton instead of applicationContext.
2. Static references to Views or Activities.
3. Non-static inner classes holding an implicit reference to the outer Activity.
4. Handler.postDelayed messages lingering in the Looper MessageQueue.
5. Coroutines launched in unmanaged scopes like GlobalScope.
6. System service callbacks (LocationManager) registered without unregistering.
7. Fragment ViewBinding properties not nulled in onDestroyView.

LeakCanary detects leaks by attaching KeyedWeakReferences to destroyed Activities and watching a ReferenceQueue after a 5s forced GC. If retained, it parses the HPROF heap dump using Shark to produce an actionable leak trace."

Must-Mention Checklist

1
GC Roots: Static fields, thread stacks, JNI globals.
2
Reference Types: Strong vs Weak vs Soft vs Phantom.
3
The 7 Leaks: Context in singleton, static View, inner class, Handler, coroutine, listeners, Fragment binding.
4
LeakCanary Mechanism: KeyedWeakReference + ReferenceQueue + Shark heap dump.

9. Interview Questions (Self-Check)

Basic Questions

B1 — What is a memory leak in Android?
Easy▼
A memory leak occurs when an object that is no longer needed by the application (such as an Activity that has finished and called onDestroy()) cannot be garbage collected because another surviving object with a longer lifecycle holds a strong reference to it. Over time, accumulated leaks exhaust available heap space and cause an OutOfMemoryError (OOM).
B2 — What is the difference between StrongReference and WeakReference?
Easy▼
A StrongReference is the default reference type in Kotlin/Java; as long as an object has a strong reference chain from a GC root, it will never be collected. A WeakReference does not prevent its referent from being collected; on the very next GC cycle, if no strong references remain, the GC immediately reclaims the object.
B3 — Why should you pass applicationContext instead of Activity context to a Singleton?
Easy▼
A Singleton lives for the entire lifetime of the application process. If you pass an Activity Context to a Singleton, that Singleton retains a strong reference to the Activity even after the user closes it, leaking the Activity, its View hierarchy, Bitmaps, and resources permanently. applicationContext is tied to the Application lifecycle and is safe for singletons.

Intermediate Questions

I1 — Why must Fragment ViewBinding be set to null in onDestroyView()?
Medium▼
In Android, a Fragment instance outlives its View hierarchy (e.g., when a Fragment transaction is added to the back stack). When navigating away, onDestroyView() is called and the View is destroyed, but the Fragment instance remains in memory. If _binding is not set to null, the binding property retains strong references to all inflated Views, creating a view hierarchy leak on the back stack.
I2 — How does LeakCanary detect memory leaks automatically?
Medium▼
1. LeakCanary registers ActivityLifecycleCallbacks and FragmentLifecycleCallbacks.
2. When an Activity/Fragment reaches onDestroy(), LeakCanary passes it to an AppWatcher that wraps it in a KeyedWeakReference linked to a ReferenceQueue.
3. After a 5-second delay, it forces a GC check. If the object has not appeared in the ReferenceQueue, it is considered retained.
4. It dumps the heap into a .hprof file and uses Shark parser to find the shortest path from GC roots to the leaking object.
I3 — How can Handler.postDelayed() cause an Activity memory leak?
Medium▼
When you post a runnable via handler.postDelayed(runnable, delay), the Android Looper.MessageQueue holds a Message containing a reference to the Runnable, which has an implicit reference to the outer Activity (if written as an anonymous class or lambda). The Looper is a static GC root, so the Activity cannot be garbage collected until the delay expires and the message is processed.
I4 — What is the difference between Shallow Size and Retained Size in memory profiling?
Medium▼
Shallow Size is the memory allocated to hold the object itself (its fields and header), excluding references to other objects. Retained Size is the total amount of memory that would be freed if this specific object were garbage collected, including all downstream child objects that are exclusively reachable from it.

Senior & Scenario Questions

S1 — How do Kotlin Coroutines prevent memory leaks compared to RxJava or Java Threads?
HardScenario▼
Kotlin Coroutines utilize Structured Concurrency. Scopes like lifecycleScope and viewModelScope are directly bound to the lifecycle of the host component (Activity, Fragment, or ViewModel). When the host is destroyed (e.g. onDestroy() or onCleared()), the scope automatically cancels its parent Job, which recursively cancels all child coroutines and releases object references. In contrast, RxJava requires manual compositeDisposable.clear() and raw Java Threads have no lifecycle integration.
S2 — Android Profiler shows native memory continuously climbing after loading high-res images in a RecyclerView. What is the root cause?
HardScenario▼
Since Android 8.0 (API 26), Bitmap pixel byte buffers are allocated in Native C++ memory (via GraphicBuffer/HardwareBuffer) rather than JVM Java heap. If images are not downsampled (using inSampleSize) and image views retain bitmaps in memory or custom caches without recycling, native memory balloons until ART triggers an OOM. Fix: Use an image loading library like Coil/Glide configured with strict memory cache limits and bitmap pooling.
S3 — How do you diagnose and fix a native cursor window leak reported by StrictMode?
HardScenario▼
StrictMode.VmPolicy.detectLeakedSqlLiteObjects() flags instances where a database Cursor or SQLiteDatabase connection was finalized without calling close(). The root cause is queries opened without try-finally or Kotlin's use {} block. Fix: Wrap all direct Cursor queries in cursor.use { cursor -> ... } or migrate entirely to Room Database, which manages cursor lifecycles automatically.
