}

3. Systematic Debug Approach for Version Regressions

Step-by-Step Process

  1. Reproduce on a specific API level — use emulator with Android 15/16 API. Note the exact error in Logcat.
  2. Check the Android behavior changes page — developer.android.com/about/versions/15/behavior-changes. New versions document all breaking changes.
  3. Binary search API levels — does it fail on Android 14? 13? Narrow down which version introduced the break.
  4. Check Logcat for security exceptions or permission denials — these have specific messages pointing to the issue.
  5. Search Crashlytics by OS version filter — compare crash rates by Android version to confirm which versions are affected.
  6. Check targetSdkVersion — some changes only apply when targetSdk is ≥ a certain level.
// Common log messages that identify the cause
// "SecurityException: Permission Denial" → missing permission or exported flag
// "IllegalArgumentException: Receiver not registered" → lifecycle mismatch
// "ActivityNotFoundException" → intent-filter or exported=false issue
// "Foreground service did not call startForeground" → FGS type change

// Runtime permission check pattern
fun hasNotificationPermission(): Boolean =
    if (Build.VERSION.SDK_INT >= 33) {
        checkSelfPermission(Manifest.permission.POST_NOTIFICATIONS) ==
            PackageManager.PERMISSION_GRANTED
    } else true  // pre-Android 13: always granted

4. Architect an Android App for Millions of Users
2
Design an Android client architecture for a consumer app with millions of daily active users
Architecture Overview
:app (shell — navigation + DI)
  └─ :feature:home, :feature:checkout, :feature:profile (10+ feature modules)
  └─ :core:data, :core:domain, :core:ui, :core:network, :core:featureflags
Offline-first
  • Room as single source of truth for all persistent data
  • Network is a cache-refresh mechanism, not the primary data source
  • WorkManager for background sync (survives app death)
  • Optimistic updates for user actions (like, add to cart) — sync later
Feature Flags + A/B Testing
  • Firebase Remote Config for all feature flags — kill switch for any feature
  • A/B experiments through Remote Config parameters with user targeting
  • All flags have local defaults (work offline, on first launch before fetch)
  • Staged rollout: internal → 10% → 50% → 100%
Performance at Scale
  • Cold start target <2s: Baseline Profiles + App Startup library
  • Crash-free sessions >99.5%: Crashlytics alerts at 99%
  • ANR rate <0.1%: strict no-main-thread-I/O enforcement
  • Memory <200MB p95: Coil with size limits, no bitmap leaks
CI/CD Pipeline
  • Every PR: unit tests + lint + Detekt + Compose metrics check
  • Every merge to main: instrumented tests on Firebase Test Lab (API matrix)
  • Nightly: full regression suite + startup benchmark
  • Release: automatic Play Console upload to internal track

6. Trade-offs & Team Structure

Key Trade-offs

DecisionTrade-off
ModularizationFaster incremental builds & team isolation vs initial setup complexity and Gradle config overhead
Offline-first (Room)Better UX & resilience vs more complex sync logic and potential data staleness
Feature flags everywhereEasy rollback & experiments vs configuration complexity, stale flag cleanup debt
Optimistic updatesInstant UI feedback vs rollback complexity on sync failure
DFMs for optional featuresSmaller initial install vs install friction when feature is first accessed

Team Ownership Model

  • Each feature team owns its :feature:X module end-to-end (UI → ViewModel → UseCase)
  • :core:Y modules owned by a platform team (no feature team modifies core without review)
  • Breaking changes to core require RFC (Request for Comment) with affected teams
  • Each team maintains their module's test coverage (>80% unit, >critical UI paths instrumented)

1) Reproduce on target API level emulator → 2) Check Logcat for SecurityException/permission denial → 3) Check Android behavior changes page for that version → 4) Common suspects: PendingIntent mutability, exact alarms, exported components, notification permission → 5) Fix + add CI test on that API level to prevent regression
Millions of Users Framework (10 min answer)
1) Modularization (feature isolation, fast builds) → 2) Offline-first (Room single source of truth) → 3) Feature flags (kill switch, A/B testing) → 4) Performance SLAs (<2s startup, >99.5% crash-free) → 5) CI/CD (parallel tests, automated release) → 6) Monitoring + progressive delivery → 7) Team ownership model

Common Mistakes

  • For version regressions: guessing random causes without a systematic approach
  • For scale architecture: focusing only on code patterns, ignoring team structure and delivery processes
  • Not mentioning monitoring and alerting — production reliability is as important as architecture

9. Practice Questions
Your app shows a SecurityException crash on Android 14 but not Android 12. How do you diagnose it?
Hard▼
Step 1: Read the SecurityException message in Logcat — it usually names the missing permission or the component that rejected the call. Step 2: Check Android 14 behavior changes page for breaking security changes. Step 3: Common Android 14 causes: missing foregroundServiceType in manifest (AFGT requirement), background activity launch restrictions, intent redirect restrictions. Step 4: Fix and add an API 34 emulator test to CI to prevent regression.
Why must all PendingIntent calls on Android 12+ specify FLAG_IMMUTABLE or FLAG_MUTABLE?
Medium▼
Android 12 tightened PendingIntent security to prevent PendingIntent hijacking attacks. An app could potentially intercept a PendingIntent with extras and modify it before it was used. FLAG_IMMUTABLE prevents the receiving app from modifying the intent's extras (safer for most cases). FLAG_MUTABLE must be used explicitly when you intentionally want the system or another app to modify the intent (e.g., notification direct reply). Not specifying either throws an IllegalArgumentException.
How do you handle the case where a user denies the POST_NOTIFICATIONS permission?
Medium▼
On first denial: explain value of notifications with a rationale dialog (shouldShowRequestPermissionRationale() returns true), then request again. On second denial (shouldShowRequestPermissionRationale() returns false after denial): don't request again — direct to Settings: Intent(Settings.ACTION_APP_NOTIFICATION_SETTINGS). Design the app to work without notifications — they're an enhancement, not required functionality. Track notification permission state in DataStore and conditionally show notification opt-in prompts in-app.
How would you architect offline-first data for a banking app with real-time balance updates?
Hard▼
Room as single source of truth. Balance data: cache in Room with a timestamp; show stale data with "last updated X minutes ago" banner. Real-time updates: WebSocket connection when app is foreground; on balance change event, update Room → Flow auto-emits to UI. Background sync: WorkManager polls balance every 15 min (minimum WorkManager interval). On network restore: ConstrainedWork triggers immediate refresh. Sensitive operations (transfers): require network, don't allow offline. Show clear offline indicator in app bar.
What is the foregroundServiceType requirement in Android 14?
Medium▼
Android 14 requires foreground services to declare a specific type in the manifest: android:foregroundServiceType="location|camera|microphone|mediaPlayback|dataSync|phoneCall|mediaProjection|health|remoteMessaging|shortService|specialUse|systemExempted". If you start a foreground service without the correct type declared (or start a type that requires a permission you don't have), it throws a MissingForegroundServiceTypeException. This forces apps to be explicit about what the foreground service is doing.
How do feature flags improve production reliability beyond just enabling/disabling features?
Hard▼
Kill switch: instantly disable a broken feature without releasing a new app version (update propagates within minutes). Gradual rollout: enable for 1% of users first, monitor metrics, expand — same as staged rollout but within a single app version. Canary testing: enable for internal users or beta testers only. Configuration flags: change API timeouts, retry counts, page sizes without a release. Seasonal toggles: enable holiday features on a schedule. Emergency response: during an incident, flip a flag to use a backup API endpoint.
How do you test your app across multiple Android API levels in CI?
Medium▼
Firebase Test Lab: upload your APK/AAB and run instrumented tests on a matrix of real devices (API 21, 26, 28, 31, 33, 34+). Emulator matrix in CI: use GitHub Actions with multiple emulator runners (each API level in parallel). Minimum coverage: test on minimum supported API (e.g., API 26), the most popular version in your user base, and the latest stable API. Add specific regression tests when you fix a version-specific bug. This catches version regressions before production.
What is predictive back gesture and what does it require from app code?
Medium▼
Predictive back gesture (Android 13+) shows a preview of the previous screen as the user swipes back, before completing the gesture. To opt in: set android:enableOnBackInvokedCallback="true" in the manifest. Migrate custom back handling from onBackPressed() (deprecated) to OnBackPressedCallback registered with the Activity's onBackPressedDispatcher. Navigation Component handles this automatically for fragment back stack. Custom back animations must use the new Android 14 predictive back APIs (BackEventCompat).
How would you monitor and alert on ANR (Application Not Responding) events?
Medium▼
Firebase Crashlytics automatically captures ANR reports (since Crashlytics SDK 17.3+). These appear separately from crashes in the Crashlytics dashboard with a main thread stack trace. Play Console also provides ANR rate metrics. Set up alerts: in Crashlytics, configure alert thresholds; below 0.1% ANR rate is the Play Store target for "good" apps. For prevention: strict mode in debug builds (StrictMode.setThreadPolicy with penaltyDeath) catches blocking main thread operations during development.
What is the Play In-App Update API and when would you force an update?
Easy▼
Play In-App Update API has two modes: Flexible update — shows an unobtrusive download prompt, user can continue using the app, update installs in background, prompts for restart. Immediate update — full-screen blocking UI, user must update to continue. Use Immediate for: critical security patches, API contract changes where old app will break with new backend, compliance requirements. Use Flexible for: feature updates, non-critical improvements. Check for updates at app startup using AppUpdateManager.getAppUpdateInfo().
