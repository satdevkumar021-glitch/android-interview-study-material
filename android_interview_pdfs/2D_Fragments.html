2D — Fragments

Tier 2 Fragment lifecycle · View lifecycle · FragmentManager · transactions · back stack · communication · Navigation Component

1 · Overview

A Fragment is a reusable UI component hosted inside an Activity. It has its own lifecycle, view hierarchy, and can be added/removed/replaced dynamically. Fragments enable modular, adaptive UI — the same Fragment can be used on phone (one at a time) and tablet (dual-pane side by side).

Why Fragments exist: Before Fragments (introduced API 11), building adaptive UIs required multiple Activities with duplicated logic. Fragments allow one codebase, one Activity, multiple interchangeable screen segments.

Two separate lifecycles: Fragments have a Fragment lifecycle (the Fragment object) and a View lifecycle (the View tree). This distinction is the source of the most common Fragment bugs. Observers should be tied to viewLifecycleOwner, not the Fragment itself.

2 · How It Works

Fragment Lifecycle (Fragment object)

onAttach() ← Fragment attached to Activity; context available onCreate() ← Fragment created; init non-UI state, args onCreateView() ← Inflate layout, return View onViewCreated() ← View ready; set up UI, observers, listeners onStart() ← Fragment visible onResume() ← Fragment interactive --- USER INTERACTION --- onPause() ← Fragment partially hidden onStop() ← Fragment hidden onDestroyView() ← View destroyed (but Fragment object still exists in back stack) onDestroy() ← Fragment object destroyed onDetach() ← Fragment detached from Activity

Fragment View Lifecycle (viewLifecycleOwner)

Fragment back-stacked: onDestroyView() called — View destroyed Fragment object STAYS ALIVE (in back stack) onCreateView() called again when Fragment returns to foreground Activity rotation: Fragment onDestroyView() → onDestroy() → onCreate() → onCreateView() → onViewCreated() (But Fragment TAG matches — FragmentManager restores it automatically)

FragmentManager and Transactions

// Get FragmentManager
val fm = supportFragmentManager           // from Activity
val fm = childFragmentManager             // from Fragment (for nested fragments)
val fm = parentFragmentManager            // from Fragment (host's FM)

// Transaction — atomic set of operations
fm.beginTransaction()
    .replace(R.id.container, HomeFragment(), "home")  // replace with tag
    .addToBackStack("home")                              // add to back stack
    .commit()                                             // async commit

// commitNow() — synchronous; cannot be used with addToBackStack
// commitAllowingStateLoss() — use when state may be lost (risky)

add() vs replace()

add()

Adds Fragment on top of existing ones. Both are alive simultaneously. Used for overlapping UIs (bottom sheets, dialogs).

replace()

Removes existing Fragment in container and replaces with new one. Used for full-screen navigation. Previous Fragment's view is destroyed (onDestroyView called).

3 · Why and When to Use Fragments

Use caseFragment approach
Adaptive tablet/phone layoutsSame Fragment shown in single-pane (phone) or dual-pane (tablet)
Tab-based navigationEach tab is a Fragment; ViewPager2 + FragmentStateAdapter
Bottom sheet dialogsBottomSheetDialogFragment
Single-activity navigation (pre-Compose)Navigation Component + Fragment destinations
Reusable complex UI component with lifecycleFragment with its own ViewModel

When NOT to Use Fragments

  • Logic-only modules: Use ViewModel / UseCase instead — no need for Fragment lifecycle.
  • New Compose-only projects: Composable functions replace Fragments entirely. A Composable has no lifecycle complexity.
  • Simple UI elements: If you just need a reusable view, use a custom View or Composable, not a Fragment.

4 · Production Example (E-Commerce App)

Single-activity e-commerce app with Navigation Component: Home → Product List → Product Detail, plus a Cart bottom sheet.

Fragment with viewLifecycleOwner (critical pattern)

@AndroidEntryPoint
class ProductListFragment : Fragment(R.layout.fragment_product_list) {

    private val viewModel: ProductListViewModel by viewModels()
    private var _binding: FragmentProductListBinding? = null
    private val binding get() = _binding!!

    override fun onViewCreated(view: View, savedInstanceState: Bundle?) {
        super.onViewCreated(view, savedInstanceState)
        _binding = FragmentProductListBinding.bind(view)

        // ✅ Use viewLifecycleOwner — NOT 'this' (Fragment) — for observe/collect
        viewLifecycleOwner.lifecycleScope.launch {
            repeatOnLifecycle(Lifecycle.State.STARTED) {
                viewModel.products.collect { products ->
                    adapter.submitList(products)
                }
            }
        }

        binding.cartFab.setOnClickListener {
            findNavController().navigate(R.id.action_products_to_cart)
        }
    }

    override fun onDestroyView() {
        super.onDestroyView()
        _binding = null   // ✅ Null binding to avoid view memory leak in back stack
    }
}

Shared ViewModel Between Fragments

// Both fragments share one CartViewModel scoped to the Activity
@AndroidEntryPoint
class ProductDetailFragment : Fragment() {
    // activityViewModels() — same instance as CartFragment's ViewModel
    private val cartViewModel: CartViewModel by activityViewModels()

    fun onAddToCart(product: Product) {
        cartViewModel.addItem(product)
    }
}

@AndroidEntryPoint
class CartFragment : Fragment() {
    private val cartViewModel: CartViewModel by activityViewModels()
    // Observes same CartViewModel instance
}

Fragment Result API — Confirmation Dialog

// Dialog Fragment sets result
class ConfirmDeleteDialog : DialogFragment() {
    override fun onCreateDialog(...): Dialog =
        AlertDialog.Builder(requireContext())
            .setTitle("Delete item?")
            .setPositiveButton("Delete") { _, _ ->
                setFragmentResult("deleteConfirmed", Bundle())
            }
            .create()
}

// Parent Fragment listens for result
override fun onViewCreated(view: View, savedInstanceState: Bundle?) {
    setFragmentResultListener("deleteConfirmed") { _, _ ->
        viewModel.deleteSelectedItem()
    }
}

6 · Pitfalls and Best Practices

Pitfall 1: Observing with 'this' Instead of viewLifecycleOwner

❌ Bad — potential duplicate observers

// 'this' is the Fragment object lifecycle
// When Fragment goes to back stack: View destroyed but Fragment lives
// When returning: onCreateView() called again — new observer added
// Now TWO observers active — duplicate updates
viewModel.products.observe(this) { ... }

✅ Good — tied to View lifecycle

// viewLifecycleOwner starts fresh each onCreateView
// Auto-removed in onDestroyView — no duplicates
viewModel.products.observe(viewLifecycleOwner) { ... }

Pitfall 2: ViewBinding Memory Leak

❌ Bad — binding holds View reference

private lateinit var binding: FragmentBinding

override fun onCreateView(...): View {
    binding = FragmentBinding.inflate(inflater)
    return binding.root
    // binding never nulled — leaks View after back stack
}

✅ Good — null in onDestroyView

private var _binding: FragmentBinding? = null
private val binding get() = _binding!!

override fun onDestroyView() {
    super.onDestroyView()
    _binding = null   // releases View reference
}

Other Critical Pitfalls

  • Accessing view in onCreate(): View is not created yet — always use onViewCreated().
  • Fragment constructor arguments: Never pass arguments to Fragment constructors. Use Fragment.newInstance() with a Bundle or Safe Args. On recreation, the framework uses the no-arg constructor — custom constructors cause crashes.
  • commitAllowingStateLoss(): Called after onSaveInstanceState — state loss means the Fragment transaction may be lost. Use commit() and ensure transactions happen at the right lifecycle moment.
  • Nested fragments with wrong FragmentManager: Always use childFragmentManager for nested Fragments (inside another Fragment), not parentFragmentManager or supportFragmentManager.
  • Duplicate Fragments after rotation: Not using tags + findFragmentByTag before add creates duplicates after system-restored Fragments.

7 · Interview Answer Framework

30-Second Answer

"A Fragment is a reusable UI component hosted inside an Activity with its own lifecycle. The critical subtlety is that a Fragment has two separate lifecycles — the Fragment object lifecycle and the View lifecycle. Observers must be tied to viewLifecycleOwner, not the Fragment itself, to avoid duplicate observers when the Fragment returns from the back stack. In modern apps I use single-activity with Navigation Component and Fragments (or Compose for new projects), sharing state between Fragments via activityViewModels() and using Fragment Result API for one-shot communications."

2-Minute Structured Answer

What a Fragment is: A modular UI component hosted inside an Activity. It has its own view hierarchy, lifecycle, and can be added/removed at runtime via FragmentManager transactions.

Two lifecycles: The Fragment object lifecycle (onAttach → onDetach) and the View lifecycle (onCreateView → onDestroyView). When a Fragment is on the back stack, its View is destroyed (onDestroyView) but the Fragment object stays alive. This is why observers must use viewLifecycleOwner — not this — to avoid duplicate observers.

Communication: I share state between Fragments via a ViewModel scoped to the Activity (activityViewModels()). For one-shot results (dialog confirmations, pickers), I use the Fragment Result API — setFragmentResult/setFragmentResultListener. I avoid interface callbacks; they're legacy and create tight coupling.

ViewBinding leak: Always null the binding reference in onDestroyView to avoid holding a reference to the destroyed View while the Fragment object is still in the back stack.

Modern context: In new projects I prefer Compose which eliminates the dual-lifecycle complexity entirely. For XML-based codebases, Navigation Component manages the Fragment back stack automatically.

Must-Mention Points

  1. Fragment has TWO lifecycles: Fragment object + View lifecycle (viewLifecycleOwner).
  2. Use viewLifecycleOwner for observers — not 'this' — to prevent duplicate observers on back-stack return.
  3. Null ViewBinding in onDestroyView to prevent View memory leaks.
  4. Never pass constructor arguments — use Bundle/newInstance() or Safe Args.
  5. childFragmentManager for nested Fragments; parentFragmentManager to reach host.
  6. activityViewModels() for shared state between Fragments.
  7. Fragment Result API replaces interface callbacks and startActivityForResult.
  8. Navigation Component manages Fragment back stack — prefer over manual transactions.

Senior-Level Insight

"The dual-lifecycle problem in Fragments is a design flaw that Compose eliminates entirely. In Compose, there is no separate View lifecycle — a Composable is either in composition or not. But in XML Fragment apps, understanding the dual lifecycle is what separates junior from senior: specifically, the pattern of _binding = null in onDestroyView, using viewLifecycleOwner for all observers, and knowing that back-stack Fragments are alive but viewless. Navigation Component's Fragment back stack management encapsulates all of this, which is why I treat direct FragmentManager transaction code as a code smell in new projects — it should almost always be replaced by a NavController.navigate() call."

9 · Interview Questions (Self-Check)

Basic What is the Fragment lifecycle and how does it differ from Activity lifecycle?
Fragment lifecycle has extra steps: onAttach (before onCreate), onCreateView (inflate layout), onViewCreated (view ready — most setup goes here), onDestroyView (view destroyed, Fragment may stay alive on back stack), and onDetach (after onDestroy). The key difference from Activity: a Fragment has two separate lifecycles — the Fragment object and its View. The Activity has only one lifecycle. Fragment's View is destroyed when it goes on the back stack, while the Fragment object persists.
Basic What is viewLifecycleOwner and why is it important?
viewLifecycleOwner is the LifecycleOwner tied to the Fragment's View lifecycle (created in onCreateView, destroyed in onDestroyView). It is different from the Fragment itself as a LifecycleOwner (which lives longer). Using viewLifecycleOwner for LiveData/Flow observers ensures the observer is removed in onDestroyView. Using 'this' (the Fragment) keeps observers active between onDestroyView and onCreateView — leading to duplicate observers when the Fragment returns from the back stack.
Basic How do you pass data to a Fragment correctly?
Use arguments Bundle with companion object newInstance(), or Safe Args via Navigation Component. Never use constructor arguments — the Fragment framework instantiates Fragments using the no-arg constructor on recreation (rotation, process death), so custom constructors cause InstantiationException.
companion object {
    fun newInstance(productId: String) = ProductDetailFragment().apply {
        arguments = Bundle().apply { putString("productId", productId) }
    }
}
// In Fragment: val id = requireArguments().getString("productId")
Intermediate What is the difference between add() and replace() in Fragment transactions?
add(): Adds the new Fragment on top of the existing one. Both Fragments exist simultaneously in the container. Used for overlapping UIs: BottomSheetDialogFragment, overlay Fragments. The previous Fragment's onStop() is NOT called (it's still visible underneath).
replace(): Removes all existing Fragments in the container and adds the new one. Previous Fragment goes through onStop → onDestroyView (if addToBackStack) or full destruction. Used for full-screen navigation between screens.
Intermediate How do two sibling Fragments communicate without coupling?
Two patterns: (1) Shared ViewModel — both Fragments use activityViewModels() to get the same ViewModel instance scoped to the Activity. One Fragment writes to it, the other observes it. (2) Fragment Result API — setFragmentResult("key", bundle) in the sender; setFragmentResultListener("key", viewLifecycleOwner) in the receiver. Avoids direct Fragment-to-Fragment references and interface callbacks.
Intermediate When would you use childFragmentManager vs parentFragmentManager?
childFragmentManager: used inside a Fragment to manage Fragments that are children (nested) within that Fragment. E.g., a ViewPager inside a Fragment uses childFragmentManager as the FragmentManager for its page Fragments. parentFragmentManager: used inside a Fragment to access the FragmentManager that owns this Fragment (the parent Fragment's childFragmentManager, or the Activity's supportFragmentManager). Wrong choice leads to lifecycle ownership issues and potential memory leaks.
Intermediate What is the Fragment Result API and when was it introduced?
Fragment Result API (introduced in Fragment 1.3.0, 2020) provides a type-safe, lifecycle-aware way to pass one-shot results between Fragments. It replaces the pattern of interface callbacks and the deprecated targetFragment API. The sender calls setFragmentResult("requestKey", bundle). The receiver registers a listener with setFragmentResultListener("requestKey", viewLifecycleOwner) { key, bundle -> }. The listener is only invoked when the Fragment is at least STARTED, and is automatically removed in onDestroyView.
Senior/Scenario [Scenario] After rotation, users report seeing duplicate list items. You suspect the Observer is firing twice. How do you diagnose and fix this?
Root cause: LiveData/Flow is being observed with 'this' (Fragment lifecycle) instead of viewLifecycleOwner. When the Fragment goes to back stack, its View is destroyed but the Fragment object is alive — observer 1 still active. When it returns, onCreateView is called again and a second observer is added — observer 2 now also active. After rotation (full Fragment recreation), there may be 2+ observers emitting to the same adapter.

Diagnose: Place a log in the observe lambda and count how many times it fires per update.

Fix: Change all observe() calls from this to viewLifecycleOwner. For StateFlow/Flow: use viewLifecycleOwner.lifecycleScope.launch { repeatOnLifecycle(STARTED) { ... } } inside onViewCreated.
Senior/Scenario [Coding] Implement a Fragment with ViewBinding that correctly nulls the binding, uses viewLifecycleOwner for observation, and handles arguments safely. 
@AndroidEntryPoint
class OrderListFragment : Fragment(R.layout.fragment_order_list) {

    private val viewModel: OrderListViewModel by viewModels()
    private var _binding: FragmentOrderListBinding? = null
    private val binding get() = _binding!!  // safe non-null accessor

    override fun onViewCreated(view: View, savedInstanceState: Bundle?) {
        super.onViewCreated(view, savedInstanceState)
        _binding = FragmentOrderListBinding.bind(view)

        // ✅ viewLifecycleOwner — not 'this'
        viewLifecycleOwner.lifecycleScope.launch {
            repeatOnLifecycle(Lifecycle.State.STARTED) {
                viewModel.orders.collect { binding.recyclerView.adapter?.let { a ->
                    (a as OrderAdapter).submitList(it)
                }}
            }
        }
    }

    override fun onDestroyView() {
        super.onDestroyView()
        _binding = null  // ✅ prevent View memory leak
    }

    companion object {
        fun newInstance(userId: String) = OrderListFragment().apply {
            arguments = Bundle().apply { putString("userId", userId) }
        }
    }
}
Senior/Scenario [Debug] "IllegalStateException: Can not perform this action after onSaveInstanceState" — when does this crash occur and how do you fix it?
This crash occurs when a Fragment transaction (commit()) is called after the Activity has saved its state (post-onSaveInstanceState). Common causes: async callback finishes after the Activity is paused (e.g., network response, dialog dismiss from a background thread).

Fix options:
1. Use commitAllowingStateLoss() — accepts state may be lost (acceptable for non-critical UI).
2. Check lifecycle before committing: if (lifecycle.currentState.isAtLeast(Lifecycle.State.STARTED)) { commit() }
3. Better: Don't commit transactions in async callbacks directly. Use a shared ViewModel to emit navigation events, and observe them in the Fragment with viewLifecycleOwner so they only fire when STARTED.
4. In Navigation Component: navController.navigate() is safe to call from lifecycle-aware coroutines — it handles the state check internally.
