5B — Builders & Dispatchers

launch, async/await, withContext, runBlocking — when each builder fits, plus dispatcher internals and thread pool selection.

ID: 5B ⭐ Tier 1
🔍
1. Overview

Coroutine builders

  • launch — fire-and-forget; returns a Job; exceptions propagate to parent
  • async — concurrent with a result; returns Deferred<T>; call .await() to get value
  • withContext — switch context in-place; suspends caller; sequential, not concurrent
  • runBlocking — bridge blocking code to coroutines; blocks the calling thread; tests & main() only

Dispatchers

  • Dispatchers.Main — Android main looper thread; UI updates, observe LiveData/Flow
  • Dispatchers.IO — shared pool up to 64 + nCPU threads; network, files, DB
  • Dispatchers.Default — CPU-bound pool, nCPU threads; sorting, parsing, heavy computation
  • Dispatchers.Unconfined — no thread pinning; resumes on whatever thread called it; avoid in production
Senior Mental Model
async is not "async/await like JavaScript." It starts a coroutine immediately and concurrently. The concurrency happens at async { } creation, not at .await(). If you val d = async { ... }; d.await() sequentially, you get concurrency. If you do withContext instead of async, you get sequential switching — completely different performance characteristics.
⚙
2. How It Works

launch — fire-and-forget

// launch returns a Job immediately, runs the block concurrently
val job = viewModelScope.launch {
    loadUserData()  // runs concurrently with caller
}
job.cancel()  // can cancel it later

// launch with a specific dispatcher
viewModelScope.launch(Dispatchers.IO) {
    // runs on IO pool from the start
}

async/await — concurrent result

// ✅ TRUE CONCURRENCY: both start simultaneously
suspend fun loadDashboard(): Dashboard = coroutineScope {
    val userDeferred = async { api.getUser() }       // starts now
    val ordersDeferred = async { api.getOrders() }   // starts now
    // Both running in parallel!
    Dashboard(userDeferred.await(), ordersDeferred.await())
}

// ❌ WRONG: sequential despite async — each await blocks the next async
val user = async { api.getUser() }.await()    // blocks here
val orders = async { api.getOrders() }.await() // then runs

withContext — sequential context switch

// withContext suspends caller and resumes in new context
// Returns the result directly — no Deferred needed
suspend fun parseJson(json: String): User =
    withContext(Dispatchers.Default) {  // CPU-bound parsing
        gson.fromJson(json, User::class.java)
    }
// After withContext returns, we're back on the original dispatcher

runBlocking — bridge for tests & main()

// Blocks current thread until all coroutines complete
// ✅ OK in tests and top-level main()
fun main() = runBlocking {
    launch { doWork() }
}

// ❌ NEVER in Android production code — blocks main thread
fun onClick() = runBlocking { /* FREEZE */ }

Dispatcher selection guide

  • Main: any update to UI state, observing LiveData/Flow, any composable state change
  • IO: Retrofit calls, Room queries, SharedPreferences, file reads, WebSocket connections
  • Default: JSON parsing at scale, image processing, sorting large lists, regex matching
  • limitedParallelism(n): when you need fairness — e.g., 4 DB connection threads matching pool size

4. Production Example

E-commerce: parallel product + recommendations load

class ProductViewModel(
    private val productRepo: ProductRepository,
    private val recommendRepo: RecommendationRepository
) : ViewModel() {

    private val _state = MutableStateFlow<ProductScreenState>(Loading)
    val state = _state.asStateFlow()

    fun loadProductScreen(productId: String) {
        viewModelScope.launch {
            _state.value = Loading
            try {
                // coroutineScope creates a scope; both async blocks run in parallel
                val (product, recs) = coroutineScope {
                    val productDef = async(Dispatchers.IO) {
                        productRepo.getProduct(productId)
                    }
                    val recsDef = async(Dispatchers.IO) {
                        recommendRepo.getFor(productId)
                    }
                    // Destructuring: both awaited here
                    productDef.await() to recsDef.await()
                }
                // Back on Main (viewModelScope default)
                _state.value = Success(product, recs)
            } catch (e: Exception) {
                _state.value = Error(e.message)
            }
        }
    }
}

Automotive: sensor data processing on Default

// Heavy sensor fusion — needs Default dispatcher
suspend fun processSensorBatch(readings: List<SensorReading>): FusedData =
    withContext(Dispatchers.Default) {
        // CPU-intensive: Kalman filter, matrix operations

            .map { applySensorFusion(it) }
            .reduce { acc, data -> acc.merge(data) }
    }

5. Alternatives & Trade-offs

Common Confusion
withContext(Dispatchers.IO) { async { ... } } — the inner async runs in the IO dispatcher but the withContext block still awaits the async before returning. The nesting gives you the dispatcher without adding parallelism.
⚠
6. Pitfalls & Best Practices
Pitfall 1 — async without await loses exceptions
If you create a Deferred and never call .await(), any exception thrown inside the async block is silently ignored until await() is called. Always await() inside a try/catch or use coroutineScope.
Pitfall 2 — withContext inside async adds unnecessary nesting
async { withContext(IO) { ... } } — just use async(Dispatchers.IO) { ... }. The dispatcher can be passed directly to the builder.
Pitfall 3 — runBlocking in tests with real delay()
runBlocking { delay(5000) } actually waits 5 seconds in tests. Use runTest from kotlinx-coroutines-test which uses a virtual clock and skips delays.
Best Practice — coroutineScope for structured parallel work
Always wrap parallel async calls in coroutineScope { } or supervisorScope { } rather than launching them in the outer scope. This ensures all parallel work completes (or fails) before the enclosing function returns.

7. Interview Framework

30-second answer

"There are four coroutine builders: launch for fire-and-forget, async for concurrent work with a result via Deferred, withContext for sequential context switching, and runBlocking for bridging blocking code — but only in tests and main(). For dispatchers: Main for UI, IO for blocking I/O, Default for CPU work."

2-minute answer

"The key distinction is between concurrency and context switching. launch and async create new coroutines that run concurrently with the caller. withContext suspends the current coroutine, switches context, does the work, and returns — no concurrency, but also no Deferred overhead.

For parallelism, you'd use multiple async blocks inside a coroutineScope and then await() all of them — this is the structured way to fan out and join. In production, I always wrap parallel async in coroutineScope so exceptions propagate correctly and cancellation works.

For dispatchers: IO and Default actually share one thread pool since 1.7, but IO allows up to 64 threads for I/O blocking, while Default caps at CPU count for CPU work. For even finer control, limitedParallelism(n) creates a view of the IO dispatcher with a cap — useful for matching a JDBC pool size."

Must-mention points

1
launch = fire-and-forget (Job); async = concurrent result (Deferred)
2
withContext ≠ async — sequential switch vs concurrent new coroutine
3
runBlocking = test/main only — never in Android Activity/Fragment/ViewModel
4
coroutineScope wrapping parallel async — structured fan-out
5
IO vs Default — blocking I/O vs CPU-bound; same pool, different concurrency cap

Follow-up Q&A

Q: "What's the difference between async and launch?"

A: launch returns a Job — you can cancel it but not get a value back. async returns a Deferred<T> — call .await() to get the result or rethrow any exception. Both start immediately and run concurrently.

Q: "When would you use withContext instead of async?"

A: When you need a single result from a different context but don't need concurrency. For example, parsing JSON on Default from a Main coroutine: val user = withContext(Default) { parse(json) } — cleaner than async(Default) { parse(json) }.await() and semantically correct.

Senior insight

Senior Insight
In a banking app with multiple parallel API calls (balance, transactions, pending), use supervisorScope instead of coroutineScope when partial failures are acceptable — e.g., if transactions fail but balance loads, show what you have. With coroutineScope, any single failure cancels everything.

9. Interview Questions
What does launch return and when would you use it?
Basic⌄
launch returns a Job. Use it for fire-and-forget operations where you don't need a result — updating UI state from a ViewModel, sending analytics events, triggering a background sync. You can call job.cancel() to stop it early.
What is the difference between async and withContext?
Basic⌄
async creates a new child coroutine that runs concurrently — it starts immediately and returns a Deferred<T> you later await(). withContext suspends the current coroutine, switches to the given context, does the work sequentially, then returns the result directly — no new coroutine, no Deferred. Use async for parallel work, withContext for dispatcher switching.
Why is runBlocking forbidden in Android production code?
Basic⌄
runBlocking blocks the calling thread until all coroutines inside complete. If called on the main thread, it freezes the UI — causing ANR if it takes more than ~5 seconds. If called on a Dispatcher.IO thread, it wastes a thread from the pool. It is only appropriate in tests (runTest is better) and in non-Android main() entry points.
How would you run two API calls in parallel and wait for both results?
Intermediate⌄
Use coroutineScope { } with two async blocks: val a = async { api.fetchA() }; val b = async { api.fetchB() } — both start immediately and run in parallel. Then val result = Result(a.await(), b.await()). The coroutineScope wrapper ensures both complete before returning, and if either fails, both are cancelled.
What is Dispatchers.Unconfined and when should you use it?
Intermediate⌄
Dispatchers.Unconfined runs the coroutine on the current thread until the first suspension point, then resumes on whatever thread the suspending function uses. It has no thread confinement. In production, this is unpredictable — avoid it. In tests, it can be useful as it executes eagerly, similar to UnconfinedTestDispatcher.
What happens if an async block throws and you never call await()?
Intermediate⌄
The exception is stored in the Deferred and only re-thrown when .await() is called. If you never call await(), the exception is silently swallowed in most cases — except when using coroutineScope or when the Deferred is part of a structured scope that completes. This is a dangerous pattern; always ensure every async result is either awaited or explicitly cancelled.
What is limitedParallelism() and when would you use it in production?
Intermediate⌄
Dispatchers.IO.limitedParallelism(n) creates a view of the IO dispatcher that caps concurrent coroutines at n. Use it to match a resource pool size — e.g., if your JDBC connection pool has 4 connections, use limitedParallelism(4) for database coroutines. Without it, 64 IO threads compete for 4 connections, causing timeout cascades under load.
Design the concurrency strategy for a checkout flow that must: (1) validate stock, (2) charge payment, (3) update inventory, (4) send confirmation email — where steps 1+2 can be parallel but 3+4 depend on both completing successfully.
Senior⌄
Use structured concurrency: coroutineScope { val stockOk = async { validateStock() }; val charged = async { chargePayment() }; val (s, c) = stockOk.await() to charged.await() }. If either fails, the other is cancelled. Then sequentially: updateInventory(s, c); sendConfirmation(c). Steps 3 and 4 are sequential because inventory must be updated before confirmation is accurate. Wrap the whole thing in try/catch for rollback logic. Use coroutineScope not supervisorScope here — partial success in checkout is a business error.
Explain how the Kotlin compiler optimises withContext when called back-to-back on the same dispatcher.
Senior⌄
The Kotlin coroutine runtime performs fast-path optimisation: if the current dispatcher is already the target dispatcher, withContext does not create a new coroutine or do any thread switching — it executes inline. This means withContext(Dispatchers.Main) called from a Main dispatcher coroutine has near-zero overhead. The check happens in ContinuationInterceptor.isDispatchNeeded() — if it returns false, the block runs directly.
A junior developer wrote: async(Dispatchers.IO) { fetchData() }.await() at the top level of a ViewModel function. What are the issues and how would you fix it?
Senior⌄
Issues: (1) async { }.await() immediately is functionally identical to withContext but creates unnecessary overhead (new coroutine, Deferred allocation). (2) If this is directly in a suspend fun or launch block without coroutineScope, exceptions from the async may not propagate correctly to the parent. Fix: replace with withContext(Dispatchers.IO) { fetchData() } — semantically identical but correct and efficient. If real parallelism is needed, wrap in coroutineScope and keep multiple async blocks un-awaited until all are launched.
