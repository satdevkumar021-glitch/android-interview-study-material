4C — Lifecycle, Scopes & repeatOnLifecycle

Tier 1 · Architecture Core LifecycleOwner · DefaultLifecycleObserver · lifecycleScope · repeatOnLifecycle · flowWithLifecycle

1 · Overview

The Android Lifecycle library provides abstractions to build lifecycle-aware components. Instead of writing bloated lifecycle management code inside Activities or Fragments, components can monitor lifecycle state changes independently.

The Core Problem Solved: Manually coordinating external resource subscriptions (GPS listeners, camera hardware, WebSockets) across onStart()/onStop() in Activities leads to race conditions, missed unsubscriptions, and memory leaks. The Lifecycle library inverts control: components observe the LifecycleOwner directly.

Key Lifecycle Primitives:
  • LifecycleOwner: Interface implemented by ComponentActivity, Fragment, and ProcessLifecycleOwner.
  • DefaultLifecycleObserver: The standard interface with default methods (onStart, onResume, onPause, onStop, onDestroy). Replaces deprecated @OnLifecycleEvent.
  • lifecycleScope: Coroutine scope bound to the owner's lifecycle, automatically cancelled on onDestroy().
  • repeatOnLifecycle: Suspends the calling coroutine and restarts the block whenever the lifecycle enters the target state (e.g. STARTED), pausing/cancelling when it drops below.

2 · How It Works: State Machine & repeatOnLifecycle

[INITIALIZED] │ ▲ ON_CREATE│ │ON_DESTROY ▼ │ [CREATED] │ ▲ ON_START│ │ON_STOP ▼ │ [STARTED] ◄── repeatOnLifecycle(STARTED) active window! │ ▲ ON_RESUME│ │ON_PAUSE ▼ │ [RESUMED]

State vs Event Mapping

  • Events: Lifecycle transitions fired by the framework (ON_CREATE, ON_START, ON_RESUME, ON_PAUSE, ON_STOP, ON_DESTROY).
  • States: Current status in the state machine (INITIALIZED, CREATED, STARTED, RESUMED, DESTROYED).
  • When an Activity moves from onStart() to onResume(), its state is STARTED then RESUMED. When it moves to onPause(), its state falls back to STARTED.

Why repeatOnLifecycle Replaced launchWhenStarted

Historically, Jetpack provided lifecycleScope.launchWhenStarted { ... }. However, launchWhenStarted only pauses execution (suspends) when the lifecycle drops below STARTED. It does not cancel the underlying upstream Flow collection!

If a cold Flow is emitting location updates or database emissions, launchWhenStarted keeps the producer active in the background, wasting CPU and battery. repeatOnLifecycle completely cancels the inner coroutine block upon ON_STOP and relaunches a fresh coroutine block upon ON_START.

3 · When to Use: Lifecycle Scope Selection

Scope / Method Trigger & Behavior Recommended Use Case
repeatOnLifecycle(STARTED) Starts on ON_START, cancels on ON_STOP, restarts on next ON_START. Collecting UI state flows (StateFlow / SharedFlow) in Activities/Fragments.
flowWithLifecycle(STARTED) Flow operator wrapping repeatOnLifecycle. Collecting a single flow when functional operator chaining is preferred.
lifecycleScope.launch Launches once; stays alive until ON_DESTROY. One-shot UI operations (e.g. starting a transition animation).
ProcessLifecycleOwner Tracks entire Application process lifecycle (app moved to foreground/background). App-wide session timeouts, biometric lock triggers, global analytics.

4 · Production Example: Lifecycle-Aware GPS Tracker & Safe Flow Collection

Production automotive location tracker that automatically starts GPS updates when the screen is visible and halts hardware sensors when the app is backgrounded.

package com.enterprise.automotive.location

import android.content.Context
import androidx.activity.ComponentActivity
import androidx.lifecycle.*
import kotlinx.coroutines.flow.StateFlow
import kotlinx.coroutines.launch

/**
 * Self-contained Lifecycle-Aware Location Observer.
 * Automatically binds and unbinds hardware sensors.
 */
class GpsLocationTracker(
    private val context: Context,
    private val onLocationChanged: (LocationPoint) -> Unit
) : DefaultLifecycleObserver {

    override fun onStart(owner: LifecycleOwner) {
        // Screen is visible — connect GPS hardware
        startHardwareGpsUpdates()
    }

    override fun onStop(owner: LifecycleOwner) {
        // Screen hidden — halt GPS to conserve battery
        stopHardwareGpsUpdates()
    }

    private fun startHardwareGpsUpdates() { /* Connect sensor */ }
    private fun stopHardwareGpsUpdates() { /* Disconnect sensor */ }
}

/**
 * Activity safely collecting UI StateFlow using repeatOnLifecycle.
 */
class NavigationActivity : ComponentActivity() {

    private val viewModel: NavigationViewModel by viewModels()

    override fun onCreate(savedInstanceState: android.os.Bundle?) {
        super.onCreate(savedInstanceState)

        // Attach self-managing lifecycle observer
        val gpsTracker = GpsLocationTracker(this) { point ->
            viewModel.onNewLocation(point)
        }
        lifecycle.addObserver(gpsTracker)

        // Safe UI state collection
        lifecycleScope.launch {
            repeatOnLifecycle(Lifecycle.State.STARTED) {
                viewModel.uiState.collect { state ->
                    renderNavigationUi(state)
                }
            }
        }
    }

    private fun renderNavigationUi(state: NavigationUiState) {
        // Render map coordinates & route guidance
    }
}

5 · Flow Collection Patterns Comparison

Pattern Background Behavior (onStop) Resource Leak Risk Modern Status
lifecycleScope.launch { flow.collect() } Keeps collecting in background until onDestroy(). 🚨 High (wastes CPU/battery processing background UI updates). Avoid for UI flows.
lifecycleScope.launchWhenStarted { flow.collect() } Suspends consumer coroutine, but keeps upstream Flow active! ⚠️ Moderate (producer stays hot). Deprecated in Jetpack.
repeatOnLifecycle(STARTED) Cancels collection on stop; restarts fresh on start. ✅ Zero leak risk. Official Google standard for Views.
collectAsStateWithLifecycle() Compose-native version of repeatOnLifecycle. ✅ Zero leak risk. Official standard for Jetpack Compose.

6 · Pitfalls & Memory Leak Traps

1. Using launchWhenStarted with Cold Flows: launchWhenStarted does not cancel the coroutine when the app goes into the background; it merely suspends the receiver. If collecting a cold flow emitting location updates or database queries, the producer continues running in the background, causing severe battery drain.
2. Collecting Multiple Flows in a Single repeatOnLifecycle without child launches: Putting two sequential flowA.collect() and flowB.collect() inside a single repeatOnLifecycle block will cause flowB to never start because flowA.collect() suspends indefinitely! Each flow collection must be wrapped in its own launch { ... } inside the block.
3. Using Deprecated @OnLifecycleEvent Annotation: The annotation-based lifecycle observer requires reflection or KAPT code generation at runtime. Always implement DefaultLifecycleObserver.

7 · Interview Framework (Senior Differentiator)

30-Second Answer (Elevator Pitch)

"Jetpack Lifecycle enables components to observe Android lifecycle states without tightly coupling logic to Activities. While lifecycleScope cancels tasks on onDestroy(), UI state flows must be collected using repeatOnLifecycle(STARTED). This ensures coroutines are cancelled when the screen is stopped (saving CPU and battery) and automatically restarted when the screen becomes visible again."

2-Minute Structured Answer

  1. Core Abstraction: LifecycleOwner exposes a Lifecycle object that maintains a state machine (INITIALIZED → CREATED → STARTED → RESUMED → DESTROYED).
  2. Inverting Lifecycle Management: By implementing DefaultLifecycleObserver, external managers (e.g., Camera, Sensors, WebSockets) subscribe via lifecycle.addObserver() and manage their own setup/teardown.
  3. Evolution of Coroutine Lifecycle Collection:
    • lifecycleScope.launch runs until onDestroy (wasting battery in background).
    • launchWhenStarted suspended the consumer but kept upstream Flows emitting (deprecated).
    • repeatOnLifecycle(STARTED) cancels the coroutine on onStop and restarts it on onStart, freeing all upstream resources.
  4. Process-Level Lifecycle: ProcessLifecycleOwner tracks whole-app foreground/background transitions across all activities.

Must-Mention Points (Key Vocabulary)

  • LifecycleOwner, LifecycleObserver, and DefaultLifecycleObserver.
  • lifecycleScope vs viewModelScope.
  • repeatOnLifecycle vs deprecated launchWhenStarted.
  • flowWithLifecycle operator.
  • ProcessLifecycleOwner for app-level backgrounding detection.

Likely Follow-Up Questions & Short Answers

Q: Why was launchWhenStarted deprecated in favor of repeatOnLifecycle?

Because launchWhenStarted only pauses the consumer coroutine when stopped. It does not cancel the upstream Flow producer. For cold flows (like database or sensor streams), the producer keeps running in the background. repeatOnLifecycle properly cancels the coroutine, stopping the upstream producer.

Q: How do you detect when the entire application goes into the background?

Observe ProcessLifecycleOwner.get().lifecycle with a DefaultLifecycleObserver. It dispatches ON_START when the first Activity becomes visible and ON_STOP with a small debounce when the last Activity is backgrounded.

Q: What is collectAsStateWithLifecycle in Jetpack Compose?

It is the Compose equivalent of repeatOnLifecycle. It collects a Flow and represents its latest value as Compose State, automatically subscribing on ON_START and unsubscribing on ON_STOP.

Senior-Level Insight: "Senior Android engineers treat resource lifecycles as a battery and memory contract. If an app collects flows on lifecycleScope.launch, it is continuously processing background emissions while the user is in another app. Always enforce repeatOnLifecycle(STARTED) or collectAsStateWithLifecycle() in code reviews."

9 · Quiz (10 Questions)

BASIC 1. What is a LifecycleOwner in Android?
A LifecycleOwner is an interface implemented by components that have an Android lifecycle (such as ComponentActivity and Fragment). It exposes a getLifecycle() method returning a Lifecycle object.
BASIC 2. Why is DefaultLifecycleObserver preferred over @OnLifecycleEvent?
DefaultLifecycleObserver uses direct interface method overrides, avoiding the runtime reflection overhead and annotation-processing compilation penalties of the deprecated @OnLifecycleEvent annotation.
BASIC 3. When does lifecycleScope get cancelled?
lifecycleScope is tied directly to the LifecycleOwner and is cancelled automatically when the lifecycle reaches the Lifecycle.State.DESTROYED state.
INTERMEDIATE 4. What is the key danger of collecting a Flow inside lifecycleScope.launch directly?
lifecycleScope.launch continues collecting the Flow even when the Activity is in the background (stopped). If the UI receives state updates while stopped, it wastes CPU cycles, network data, and battery, and can cause crashes if performing Fragment transactions.
INTERMEDIATE 5. Why was launchWhenStarted deprecated?
launchWhenStarted pauses the coroutine when the lifecycle drops below STARTED, but it does not cancel it. The upstream Flow continues emitting items in the background. repeatOnLifecycle was introduced to cancel and restart the coroutine block cleanly.
INTERMEDIATE 6. How do you collect multiple Flows safely inside a single repeatOnLifecycle block?
Inside the repeatOnLifecycle block, launch separate child coroutines for each flow:
repeatOnLifecycle(Lifecycle.State.STARTED) {
  launch { flow1.collect { ... } }
  launch { flow2.collect { ... } }
}
INTERMEDIATE 7. What is ProcessLifecycleOwner and when is its ON_STOP event dispatched?
ProcessLifecycleOwner tracks the entire application lifecycle. It dispatches ON_STOP after a short delay (approx. 700ms) after the last Activity has stopped, ensuring configuration changes (rotations) do not trigger false app-backgrounding events.
SENIOR 8. What is the difference between repeatOnLifecycle and flowWithLifecycle?
repeatOnLifecycle is a suspend function that executes a block of code when the lifecycle reaches the target state. flowWithLifecycle is a Flow operator that applies repeatOnLifecycle under the hood to a single Flow stream, allowing functional chaining (e.g. flow.flowWithLifecycle(lifecycle, STARTED).onEach { ... }.launchIn(lifecycleScope)).
SENIOR 9. How does collectAsStateWithLifecycle() optimize recomposition in Jetpack Compose?
collectAsStateWithLifecycle() collects a Flow and converts it into Compose State only while the lifecycle is in the specified state (default STARTED). When the app is backgrounded, it cancels the collector, stopping recompositions and halting upstream emissions until the app is foregrounded.
SENIOR 10. Explain how LifecycleRegistry synchronizes observer states during rapid lifecycle transitions.
LifecycleRegistry maintains a custom FastSafeIterable map of observers. When an observer is added, it steps the observer through historical states one by one until it catches up to the current state. If states transition backward (e.g. RESUMED → DESTROYED), it cascades down through intermediate states in reverse order, ensuring invariants and event ordering are strictly preserved.
