20C — UI & Network Testing

Espresso view assertions, Compose UI testing via SemanticsMatchers, cross-app testing with UI Automator, and OkHttp MockWebServer for reliable network integration tests.

ID: 20C ⭐ Tier 2 (Testing & QA)
🚀
1. Overview & UI Testing Landscape

Instrumentation tests run inside an Android process on an emulator or physical device (under src/androidTest/java). They verify that UI components, system dialogs, and real network layers behave correctly under actual Android OS conditions.

The 4 UI & Network Testing Frameworks
  • Jetpack Compose Testing: Semantic tree navigation and assertions using createComposeRule().
  • Espresso: View-based UI testing framework with built-in UI thread synchronization via IdlingResource.
  • UI Automator: Cross-application black-box testing framework (e.g. testing system permission dialogs, notifications, external settings).
  • MockWebServer (OkHttp): Embedded local HTTP server that intercepts real network requests to return deterministic responses.

2. How It Works Under the Hood

1. Jetpack Compose UI Testing

Compose testing relies on the Semantics Tree rather than pixel layout or View IDs:

@get:Rule
val composeTestRule = createComposeRule()

@Test
fun loginButton_whenClicked_displaysLoading() {
    composeTestRule.setContent {
        LoginScreen()
    }

    // Match by text / testTag
    composeTestRule.onNodeWithText("Login")
        .assertIsDisplayed()
        .performClick()

    composeTestRule.onNodeWithTag("loading_spinner")
        .assertIsDisplayed()
}

2. Espresso ViewInteraction Pattern

Espresso follows a three-step formula: Find View → Perform Action → Check Assertion.

onView(withId(R.id.username_input))
    .perform(typeText("alice@bank.com"), closeSoftKeyboard())

onView(withId(R.id.login_btn))
    .perform(click())

onView(withId(R.id.welcome_msg))
    .check(matches(withText("Welcome back, Alice!")))

3. Network Integration Testing with MockWebServer

MockWebServer starts a lightweight HTTP server on localhost. It tests the entire networking stack (OkHttp Interceptors, Retrofit converters, Coroutine call adapters, error response parsing) without hitting real staging servers:

class BankingApiIntegrationTest {

    private lateinit var server: MockWebServer
    private lateinit var apiService: BankingApiService

    @Before
    fun setUp() {
        server = MockWebServer()
        server.start()

        val retrofit = Retrofit.Builder()
            .baseUrl(server.url("/"))
            .addConverterFactory(MoshiConverterFactory.create())
            .build()

        apiService = retrofit.create(BankingApiService::class.java)
    }

    @After
    fun tearDown() = server.shutdown()

    @Test
    fun fetchBalance_returnsCorrectDtoAndHeaders() = runTest {
        // Enqueue mock response
        server.enqueue(
            MockResponse()
                .setResponseCode(200)
                .setBody("""{"balance": 1500.50, "currency": "USD"}""")
        )

        val response = apiService.getBalance("ACC_99")

        assertEquals(1500.50, response.balance, 0.01)
        val recordedRequest = server.takeRequest()
        assertEquals("/accounts/ACC_99/balance", recordedRequest.path)
    }
}

4. Production Example (Cross-App UI Automator Permission Test)
class SystemPermissionUiAutomatorTest {

    private val device: UiDevice = UiDevice.getInstance(InstrumentationRegistry.getInstrumentation())

    @Test
    fun grantLocationPermission_enablesGpsTracking() {
        // 1. Launch App
        val context = ApplicationProvider.getApplicationContext<Context>()
        val intent = context.packageManager.getLaunchIntentForPackage("com.example.bank")?.apply {
            addFlags(Intent.FLAG_ACTIVITY_CLEAR_TASK)
        }
        context.startActivity(intent)
        device.wait(Until.hasObject(By.pkg("com.example.bank").depth(0)), 5000)

        // 2. Click "Find Nearby ATMs" button in Compose
        val atmButton = device.findObject(UiSelector().text("Find Nearby ATMs"))
        atmButton.click()

        // 3. System Permission Dialog appears (outside app process!)
        val allowPermissionButton = device.findObject(
            UiSelector().textMatches("(?i)While using the app|Allow")
        )
        if (allowPermissionButton.exists()) {
            allowPermissionButton.click()
        }

        // 4. Verify map screen loaded
        val mapMarker = device.findObject(UiSelector().description("ATM Map View"))
        assertTrue(mapMarker.waitForExists(5000))
    }
}

6. Pitfalls & Best Practices
Pitfall 1: Flaky Tests Caused by Thread.sleep()

Using Thread.sleep() in UI tests causes arbitrary delays and flaky CI failures. Espresso automatically syncs with the main thread queue. For custom background tasks, implement an IdlingResource or use Compose mainClock.autoAdvance.

Pitfall 2: Relying on Real Backend APIs in CI

Testing against live staging servers makes UI tests vulnerable to network latency, server downtime, and changing backend test databases. Always use MockWebServer for reproducible network integration tests.

Pitfall 3: Using Hardcoded Coordinates in UI Automator

Clicking by screen coordinates (x, y) breaks across different device screen sizes and densities. Always match by UiSelector().text(), resourceId(), or contentDescription().

7. Interview Framework

30-Second Elevator Pitch

"Android UI and integration testing spans Compose UI Testing, Espresso, UI Automator, and MockWebServer. Compose tests query the Semantics tree via createComposeRule(), Espresso handles View-based UI synchronization, UI Automator handles system permission dialogs and cross-app workflows, and MockWebServer tests the entire Retrofit/OkHttp network stack deterministically on localhost."

2-Minute Deep Dive

"For in-app UI testing, Jetpack Compose uses the Semantics tree via createComposeRule(). Nodes are matched using onNodeWithText or onNodeWithTag, and asserted via assertIsDisplayed() or performClick(). Unlike Espresso, which synchronizes via IdlingResources, Compose automatically waits for recomposition and layout passes to settle.

When tests must cross app boundaries—such as interacting with Android OS runtime permission dialogs, launcher icons, or notification drawer banners—we use UI Automator's UiDevice API.

For network integration testing, we avoid hitting live backends by running OkHttp's MockWebServer locally. MockWebServer enqueues mock HTTP responses, verifies headers and query parameters via takeRequest(), and validates custom OkHttp interceptors and Moshi/Kotlinx serialization parsers."

Must-Mention Checklist

1
Compose Semantics: createComposeRule(), onNodeWithText(), performClick().
2
Espresso Triad: onView(), perform(), check() + IdlingResource.
3
UI Automator: UiDevice for system permissions, notifications, cross-app tests.
4
MockWebServer: enqueue(MockResponse) and takeRequest() for hermetic network testing.

9. Interview Questions (Self-Check)

Basic Questions

B1 — What is the difference between unit tests and instrumentation tests?
Easy▼
Unit tests (src/test) run on the local development machine's JVM in milliseconds without Android OS dependencies. Instrumentation tests (src/androidTest) are compiled into an APK and run on an Android physical device or emulator, testing real UI rendering, database integration, and OS components.
B2 — How does Jetpack Compose find UI elements during testing?
Easy▼
Compose uses the Semantics Tree. Composable functions attach semantics properties (text, content description, role, test tag, selection state) to nodes. Test matchers like onNodeWithText() or onNodeWithTag() traverse this semantics hierarchy to find elements.
B3 — What is MockWebServer?
Easy▼
MockWebServer (by Square / OkHttp) is a scriptable embedded HTTP server for testing HTTP/HTTPS clients locally. It lets tests enqueue mock HTTP responses (status codes, headers, JSON bodies) and inspect incoming HTTP requests (path, body, authorization headers) with zero external network connectivity.

Intermediate Questions

I1 — When should you use UI Automator instead of Espresso / Compose Rule?
Medium▼
Use UI Automator when your test needs to interact with elements outside your application's process: system runtime permission dialogs ("Allow Notifications / Location"), system settings, launching third-party apps, clicking status bar notification banners, or device hardware keys (Home, Back, Volume).
I2 — What is an IdlingResource in Espresso and how does Compose handle it?
Medium▼
An IdlingResource informs Espresso that background operations (e.g. data loading) are still in progress, telling Espresso to pause UI actions until the resource becomes idle. Jetpack Compose handles synchronization automatically: createComposeRule() automatically synchronizes with Compose's internal clock and waits for recompositions to finish before executing assertions.
I3 — How do you test error responses (e.g., 500 Internal Server Error) with MockWebServer?
Medium▼
server.enqueue(
    MockResponse()
        .setResponseCode(500)
        .setBody("""{"error": "Database unavailable"}""")
)
val result = repository.fetchData()
assertTrue(result.isFailure)
I4 — What is testTag in Jetpack Compose and why should you use it judiciously?
Medium▼
Modifier.testTag("tag_name") assigns a unique identifier to a composable node for onNodeWithTag() lookup. It should be used judiciously because over-tagging introduces test-specific code into production layouts. Prefer testing user-facing semantics (text, content description, accessibility roles) whenever possible.

Senior & Scenario Questions

S1 — How do you test an end-to-end checkout flow with OkHttp Auth Interceptors using MockWebServer?
HardScenario▼
1. Enqueue a 401 Unauthorized for the initial checkout request.
2. Enqueue a 200 OK for the token refresh request.
3. Enqueue a 200 OK for the retried checkout request.
4. Trigger the checkout action.
5. Inspect server.takeRequest() 3 times: verify that request 1 had the old token, request 2 called /oauth/refresh, and request 3 contained the refreshed Authorization: Bearer <newToken> header.
S2 — How do you isolate and test a single Composable without launching the entire Application / NavHost?
HardScenario▼
Use createComposeRule() (which launches an empty ComponentActivity). Inside composeTestRule.setContent { }, render the isolated Composable passing mock lambda callbacks (e.g. onItemClicked = { }) and dummy UI state. This tests the composable in total isolation from ViewModels, navigation routers, and backend repositories.
S3 — Why do UI tests fail on CI machines with animation timeouts and how do you fix it?
HardScenario▼
Continuous animations (infinite progress spinners, Lottie animations) prevent Espresso and Compose clocks from reaching an idle state, resulting in test timeouts. Fixes:
1. Disable system animations on the test emulator via ADB before running tests: settings put global window_animation_scale 0, transition_animation_scale 0, animator_duration_scale 0.
2. In Compose, use mainClock.autoAdvance = false to manually advance infinite transition clocks.
