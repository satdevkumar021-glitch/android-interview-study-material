21B — Baseline Profiles & Macrobenchmark

Profile-guided optimisation for Android apps: writing Baseline Profiles, measuring startup and scrolling with Macrobenchmark, automatic profiles via Play Store, and CI integration for performance regression detection.

ID: 21B ⭐ Tier 1 🔥 Hot Topic
📋
Overview

A Baseline Profile is a plain-text file listing class and method signatures that the Android Runtime (ART) should pre-compile ahead of first use. Without profiles, ART uses JIT (just-in-time) compilation — code runs interpreted until it's "hot" enough to JIT-compile into native code. With Baseline Profiles, critical startup and UI interaction code is AOT (ahead-of-time) compiled on device install, so the first launch uses pre-compiled native code.

Measurable impact: Google reports up to 40% faster startup, smoother first-frame rendering, and significantly reduced jank on first scroll. Supported since Android 7 via ART's profile-guided compilation infrastructure. Delivered to apps via the ProfileInstaller library — no Play Store required for development testing.

💡 Key Insight
Baseline Profiles are the single highest-ROI performance optimisation for most apps. A few hours of setup gives 20–40% startup improvement with no code changes — just a profile file shipped in your AAB.

How Baseline Profiles Work

The Compilation Pipeline

  1. Developer writes profile rules (or auto-generates with BaselineProfileRule)
  2. ProfileInstaller compiles profile on device install (converts text → binary .prof)
  3. ART pre-compiles matching methods to native code in the background
  4. First app launch uses pre-compiled native code — no interpretation overhead

Profile Rule Format

Rules are written in human-readable method descriptor format. Each line is one class or method:

# Class rule — all methods in this class get warm-compiled
Lcom/example/MainActivity;

# Startup method rule — compiled for startup path
HSPLcom/example/MainActivity;->onCreate(Landroid/os/Bundle;)V

# Post-startup rule
PLcom/example/ui/ProductListFragment;->onViewCreated(Landroid/view/View;Landroid/os/Bundle;)V

Rule Prefixes

PrefixMeaningUse Case
HHot — frequently calledCore business logic, render methods
SStartup — called during app startupApplication.onCreate, Activity.onCreate
PPost-startup — called shortly after startupFragment transitions, ViewModels
LClass-level (no prefix) — warm compile entire classData classes, utility classes

What Gets Included

  • Activities and Fragments launched at startup
  • ViewModels initialised at startup
  • Key Compose composables for the first screen
  • DI graph construction code (Hilt/Dagger modules)
  • Network/database initialisation paths

Delivery Mechanism

Profiles are shipped inside your AAB at assets/dexopt/baseline.prof (binary format). The ProfileInstaller library (included transitively by many Jetpack libs) detects this file on first launch and triggers ART profile compilation in the background. On subsequent cold starts, the compiled code is ready.

Play Store Enhancement
Cloud Profiles: Play Store aggregates anonymous profiles from real early-adopter users. Subsequent installs receive pre-compiled code before the user ever launches the app — even better than your shipped Baseline Profile alone.
✍️
Writing Baseline Profiles

Two Approaches

(1) Manual: Write baseline-prof.txt by hand after inspecting a startup trace. Tedious and error-prone — method descriptors must be exact.
(2) Automated with BaselineProfileRule (recommended): Run a UI automation test; the framework records which classes and methods were called and outputs a ready-to-use profile file.

Gradle Module Setup

// :baseline-profile/build.gradle.kts
plugins {
    id("com.android.test")
    id("androidx.baselineprofile")
}

android {
    targetProjectPath = ":app"
    defaultConfig {
        minSdk = 28
        testInstrumentationRunner = "androidx.test.runner.AndroidJUnitRunner"
    }
}

dependencies {
    implementation("androidx.test.ext:junit:1.1.5")
    implementation("androidx.test.uiautomator:uiautomator:2.3.0")
    implementation("androidx.benchmark:benchmark-macro-junit4:1.2.4")
}

Profile Generator Test

@RunWith(AndroidJUnit4::class)
class BaselineProfileGenerator {
    @get:Rule val rule = BaselineProfileRule()

    @Test
    fun generate() = rule.collect(
        packageName = "com.example.myapp"
    ) {
        pressHome()
        startActivityAndWait()

        // Navigate to key screens the user visits at startup
        device.findObject(By.text("Products")).click()
        device.waitForIdle()

        // Scroll through a list (captures RecyclerView / LazyColumn paths)
        device.findObject(By.scrollable(true)).fling(Direction.DOWN)
        device.waitForIdle()

        // Open a detail screen
        device.findObject(By.res("com.example.myapp:id/product_item")).click()
        device.waitForIdle()
    }
}

Running the Generator

# Generates the profile and copies it to the correct location
./gradlew :baseline-profile:generateBaselineProfile

Output: app/src/main/baseline-prof.txt — automatically formatted and ready to ship in your next release build.

App Module Configuration

// app/build.gradle.kts
plugins {
    id("com.android.application")
    id("androidx.baselineprofile")
}

dependencies {
    implementation("androidx.profileinstaller:profileinstaller:1.3.1")
    baselineProfile(project(":baseline-profile"))
}

baselineProfile {
    // Automatically merge generated profiles
    automaticGenerationDuringBuild = false
    // Save to src/main/baseline-prof.txt
    saveInSrc = true
}
✅ Best Practice
Cover all critical user journeys in your generator: app launch, first screen interaction, navigation to the 2–3 most-visited screens, and at least one list-scroll. The more real-world code paths you cover, the higher the first-launch improvement.

Macrobenchmark Setup

Macrobenchmark is the measurement framework for real-world app performance — startup time, scrolling smoothness, and arbitrary UI interactions. Unlike unit benchmarks, Macrobenchmark runs your actual app process in a separate instrumented test process, measuring real end-to-end timing.

⚠️ Requirement
Macrobenchmark requires a physical device or Firebase Test Lab. Emulators share CPU with the host machine and produce completely unreliable results — variance can exceed 200%.

Gradle Module Setup

// :macrobenchmark/build.gradle.kts
plugins {
    id("com.android.test")
}

android {
    targetProjectPath = ":app"
    defaultConfig {
        minSdk = 29
        testInstrumentationRunner = "androidx.benchmark.junit4.AndroidBenchmarkRunner"
        testInstrumentationRunnerArguments["androidx.benchmark.suppressErrors"] =
            "EMULATOR,LOW-BATTERY,UNLOCKED"
    }
    buildTypes {
        create("benchmark") {
            isDebuggable = false
            signingConfig = signingConfigs.getByName("debug")
            matchingFallbacks += listOf("release")
        }
    }
}

dependencies {
    implementation("androidx.benchmark:benchmark-macro-junit4:1.2.4")
    implementation("androidx.test.ext:junit:1.1.5")
    implementation("androidx.test.uiautomator:uiautomator:2.3.0")
}

App Build Variant

// app/build.gradle.kts — add benchmarkRelease build type
buildTypes {
    create("benchmark") {
        initWith(getByName("release"))
        signingConfig = signingConfigs.getByName("debug")
        matchingFallbacks += listOf("release")
        isDebuggable = false
        // Enable profiling for Macrobenchmark
        proguardFiles(getDefaultProguardFile("proguard-android-optimize.txt"))
    }
}

Stabilise CPU for Consistent Results

# Lock CPU clocks before running benchmarks (requires rooted device or eng build)
./gradlew :macrobenchmark:lockClocks
# Run benchmarks
./gradlew :macrobenchmark:connectedBenchmarkAndroidTest
# Restore CPU scaling
./gradlew :macrobenchmark:unlockClocks

Measuring with Macrobenchmark

Full Benchmark Test

@RunWith(AndroidJUnit4::class)
class StartupBenchmark {
    @get:Rule val benchmarkRule = MacrobenchmarkRule()

    @Test
    fun startup_cold() = benchmarkRule.measureRepeated(
        packageName = "com.example.myapp",
        metrics = listOf(StartupTimingMetric()),
        iterations = 5,
        startupMode = StartupMode.COLD,
        setupBlock = { pressHome() }
    ) {
        startActivityAndWait()
    }

    @Test
    fun startup_warm() = benchmarkRule.measureRepeated(
        packageName = "com.example.myapp",
        metrics = listOf(StartupTimingMetric()),
        iterations = 5,
        startupMode = StartupMode.WARM
    ) {
        startActivityAndWait()
    }

    @Test
    fun scrolling_smoothness() = benchmarkRule.measureRepeated(
        packageName = "com.example.myapp",
        metrics = listOf(FrameTimingMetric()),
        iterations = 5,
        startupMode = StartupMode.WARM
    ) {
        startActivityAndWait()
        val recycler = device.findObject(By.res("com.example.myapp:id/product_list"))
        repeat(3) { recycler.fling(Direction.DOWN) }
    }
}

Cloud Profiles & Automatic Profiles

Cloud Profiles (Play Store)

Play Store aggregates anonymous performance profiles from early adopter users. After your app has enough install volume (typically after a few thousand installs), Play delivers pre-compiled code to new installs — before the user ever launches the app. This is separate from your shipped Baseline Profile and adds on top of it.

Automatic Profiles (Android 9+)

ART collects execution profiles per-device in the background and updates them nightly via a background dex2oat pass. Over the first 1–3 days of use, the app becomes progressively faster as more methods are AOT-compiled based on real usage.

How They Layer Together

Profile TypeWhen AppliedSourceCovers
Baseline ProfileOn install (via ProfileInstaller)Developer-shipped in AABDay-0 first launch
Cloud ProfileBefore first launch (Play pre-compilation)Aggregated real user profiles from PlayDay-0 + common paths
Automatic ProfileNight 1–3 after installDevice-local ART profilingThis user's specific usage

Startup Profiles (Android 13+)

A Startup Profile is a subset of the Baseline Profile applied even earlier in the compilation pipeline — specifically for methods called in the first 5 seconds of app startup. Defined with the S prefix in your profile rules. Provides the fastest possible first-frame on Android 13+ devices.

Verifying Profile Installation

# Force profile compilation on device (for testing)
adb shell cmd package compile -m speed-profile com.example.myapp

# Check profile data exists
adb shell ls -la /data/misc/profiles/cur/0/com.example.myapp/

# View compilation state
adb shell dumpsys package com.example.myapp | grep -i compile

Pitfalls & CI Integration

Common Pitfalls

❌ Running Macrobenchmark on Emulator
Emulators share CPU with the host machine. Results are unreliable — variance exceeds 200%, making it impossible to detect real regressions. ✅ Fix: Use a physical device or Firebase Test Lab with EMULATOR error suppressed only if you understand the limitations.
❌ Not Locking CPU Clocks
Thermal throttling and CPU governor changes during the benchmark run skew results significantly. ✅ Fix: Run ./gradlew :macrobenchmark:lockClocks before benchmarking on rooted/eng devices.
❌ Generating Profiles on Debug Builds
Debug builds include extra logging, disable R8, and add overhead not present in production. Your generated profile will include non-production code paths. ✅ Fix: Always generate on the benchmarkRelease (or benchmark) build variant.
❌ Not Regenerating After Major Refactors
Class and method names change with refactoring. The old profile refers to methods that no longer exist — it becomes effectively useless or actively misleading. ✅ Fix: Regenerate profiles in CI on each release branch, or when the diff includes significant renames/restructuring.

CI Integration

Add a benchmark step to your release CI pipeline using Firebase Test Lab as the device farm:

# .github/workflows/benchmark.yml
name: Performance Benchmarks
on:
  push:
    branches: [release/"**"]
  schedule:
    - cron: "0 2 * * 1"  # Weekly on Monday 2am

jobs:
  benchmark:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - name: Build benchmark APKs
        run: |
          ./gradlew :app:assembleBenchmark
          ./gradlew :macrobenchmark:assembleBenchmark
      - name: Run on Firebase Test Lab
        run: |
          gcloud firebase test android run \
            --type instrumentation \
            --app app/build/outputs/apk/benchmark/app-benchmark.apk \
            --test macrobenchmark/build/outputs/apk/benchmark/macrobenchmark-benchmark.apk \
            --device model=redfin,version=30,locale=en,orientation=portrait \
            --results-bucket gs://my-benchmark-results
      - name: Check for regressions
        run: python3 scripts/check_benchmark_regression.py --threshold 10
🎯 Regression Threshold
Set your CI regression threshold at 10% degradation in TTID as a starting point. This balances noise (device variance is ~5%) with real regression detection. Tighten to 5% once you have stable measurements from consistent devices.

Interview Questions
What is a Baseline Profile and what problem does it solve?
Easy▾

A Baseline Profile is a text file listing class and method signatures that ART should compile ahead-of-time (AOT) on device install.

Problem it solves: Without profiles, the Android Runtime starts by interpreting bytecode and only JIT-compiles "hot" methods after they've been called many times. This means the first app launch — and first interactions — are always slow due to interpretation overhead. The user experiences slow startup, dropped frames, and jank specifically on first use.

Solution: ProfileInstaller converts the profile to binary format at install time. ART pre-compiles all listed methods to native code in the background. On next cold start, those methods execute at native speed — no interpretation or JIT compilation latency.

What is the difference between cold, warm, and hot app starts?
Easy▾
  • Cold start: App process does not exist. System forks from Zygote, creates Application, creates Activity, inflates layout, draws first frame. Slowest — full initialization path.
  • Warm start: App process still exists but Activity was destroyed (e.g., back pressed, memory pressure). System recreates the Activity only — no Application.onCreate(). Faster than cold.
  • Hot start: Both process and Activity exist (e.g., user switched to another app briefly). Activity just brought to foreground — fastest, nearly instant.

Baseline Profiles primarily improve cold start, since that's when all the JIT/AOT decisions happen. Macrobenchmark's StartupMode.COLD kills the app process before each measurement to ensure a true cold start.

How do you generate a Baseline Profile automatically? Walk through the setup.
Medium▾
  1. Create a separate :baseline-profile Gradle module with com.android.test and androidx.baselineprofile plugins.
  2. Write a test class using BaselineProfileRule that navigates the critical user journeys using UiAutomator: app launch, main screen interaction, navigation to key screens, list scrolling.
  3. In the app module, apply the androidx.baselineprofile plugin and add a baselineProfile(project(":baseline-profile")) dependency.
  4. Run ./gradlew :baseline-profile:generateBaselineProfile on a physical device (connected via ADB).
  5. The plugin automatically generates app/src/main/baseline-prof.txt and it will be packaged into the AAB on next release build.

Key point: Run on benchmarkRelease build variant, not debug — debug builds include extra overhead and the profile will contain non-production paths.

How do you measure the improvement from a Baseline Profile using Macrobenchmark?
Medium▾
  1. Create a :macrobenchmark module with com.android.test plugin, targeting the app module.
  2. Write a benchmark using MacrobenchmarkRule.measureRepeated() with StartupTimingMetric(), StartupMode.COLD, and at least 5 iterations.
  3. Build the benchmark APK and app APK in benchmark build type (release optimisations, debuggable=false).
  4. Run the benchmark without the profile (comment out or remove baseline-prof.txt), record timeToInitialDisplay.
  5. Restore the profile, rebuild, run again — compare TTID.

Typical result: 30–80ms reduction in cold start TTID, which represents 15–40% improvement depending on app complexity and how much startup code the profile covers.

Important: Run on a physical device. Lock CPU clocks with ./gradlew lockClocks for stable results.

When should you regenerate your Baseline Profile?
Medium▾

Regenerate when the listed class/method names are no longer valid. Specifically:

  • Major refactoring: Any significant rename of Activity, Fragment, ViewModel, or composable classes invalidates profile rules pointing to the old names. Old profile becomes useless — methods no longer exist under those signatures.
  • New major features added to startup path: Profile only covers what was in the app when it was generated. New startup code won't be pre-compiled.
  • Each release branch: As a CI step, regenerate and commit the updated profile so shipping code always has a fresh profile.
  • After upgrading major dependencies: Library method signatures can change between versions, especially Compose.

Best practice: Automate profile generation in CI on each release branch. The generateBaselineProfile Gradle task makes this straightforward.

What are Cloud Profiles and how do they relate to your shipped Baseline Profile?
Hard▾

Cloud Profiles are aggregated anonymous performance data collected by Play Store from real users across all installs of your app. Play uses this data to pre-compile the app before delivering it to new users.

Relationship to Baseline Profile:

  • Your Baseline Profile covers day-0: developer-specified methods guaranteed to be AOT-compiled on any install via ProfileInstaller, even without Play Store (sideloaded, dev testing).
  • Cloud Profiles enhance this with real-world data: which methods actual users call most. This includes user-journey-specific paths that your generator might not cover.
  • Automatic device profiles (collected nightly by ART) further personalise for each user's specific usage pattern over days 1–3.

The profiles stack: Baseline Profile guarantees a minimum performance floor at install. Cloud + Automatic profiles improve further over time for Play-distributed apps.

Implication: Never rely solely on Cloud Profiles — they only apply to Play Store installs and require sufficient install volume (~thousands). Always ship a Baseline Profile for day-0 coverage.

How would you integrate Baseline Profile generation and Macrobenchmark regression detection into your CI pipeline?
Hard▾

Two separate CI jobs:

1. Profile Generation Job (on each release branch):

  • Build benchmark variant of app + baseline-profile test module
  • Run on physical device via Firebase Test Lab or connected device
  • Execute generateBaselineProfile task
  • Commit updated baseline-prof.txt back to the release branch

2. Regression Detection Job (on each PR or scheduled):

  • Build benchmark APKs for both app and macrobenchmark module
  • Run on Firebase Test Lab with a consistent device model (same model every time)
  • Download benchmark results JSON from GCS bucket
  • Parse timeToInitialDisplay and compare against stored baseline
  • Fail the job if P50 TTID degrades more than 10% from baseline
  • Post results as PR comment with before/after numbers

Key considerations: Use the same device model consistently (variance between models is huge). Lock CPU clocks if using rooted test devices. Store historical baselines in a database or artifact store to detect gradual regressions.

A Baseline Profile was added but Macrobenchmark shows no improvement in cold start TTID. What are the likely causes?
Hard▾

Diagnose systematically:

  1. Profile not being applied: Run adb shell cmd package compile -m speed-profile com.example.myapp and check dumpsys package for compilation state. If profile shows 0 methods compiled, ProfileInstaller may not be initialised.
  2. Profile generated from debug build: Methods listed include debug-only overhead. Regenerate from benchmarkRelease build.
  3. Benchmark running on emulator: Emulator results are meaningless. Must use physical device.
  4. CPU clocks not locked: Thermal throttling causes high variance masking the real improvement. Lock clocks before benchmarking.
  5. Too few iterations: With 3 iterations the variance is too high. Use at least 5, ideally 10.
  6. Profile is stale: After refactoring, old method names don't exist. Profile has zero effect. Check that baseline-prof.txt contains method names present in current build by cross-referencing with APK's dex classes.
  7. Startup bottleneck is I/O, not JIT: If cold start is dominated by disk I/O (SharedPreferences, SQLite), AOT compilation won't help. Check with Perfetto to identify the actual bottleneck.
