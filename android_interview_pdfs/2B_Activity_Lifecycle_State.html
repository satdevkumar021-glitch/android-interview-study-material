2B — Activity Lifecycle & State

Tier 2 onCreate · onStart · onResume · onPause · onStop · onDestroy · config changes · process death · onSaveInstanceState

1 · Overview

An Activity's lifecycle is the sequence of callbacks the Android OS calls as it creates, shows, hides, and destroys the Activity. Understanding it is mandatory for correctness: doing the wrong work in the wrong callback causes ANRs, memory leaks, UI glitches, and data loss.

The lifecycle exists because Android is a resource-constrained, multi-app environment. The OS can pause, stop, or kill your Activity at any time to reclaim memory. Your job is to react correctly to each transition so the app remains consistent regardless of interruptions.

Key problems the lifecycle solves:
  • Releasing resources (camera, GPS, network) when not visible
  • Saving and restoring UI state across configuration changes and process death
  • Knowing when to start / stop work (animation, polling, observers)

2 · How It Works

Callback Flow

┌─────────────────────────────────────────────────────┐ │ Activity Created │ └──────────────────────┬──────────────────────────────┘ ▼ onCreate() ← setContentView, init ViewModel, observe ▼ onStart() ← Activity becomes visible (not interactive) ▼ onResume() ← Activity in foreground, user can interact │ ┌────────────────────┴────────────────────┐ │ Another Activity / dialog in front │ ▼ │ onPause() ← still partially visible │ │ │ ▼ (fully hidden) │ onStop() ← not visible │ │ │ ├──── onRestart() ──────────────────────► onStart() │ ▼ onDestroy() ← finishing OR config change Config change (rotation): onPause → onStop → onDestroy → onCreate → onStart → onResume Process death: OS silently kills; no callbacks after onStop

Callback Responsibilities

CallbackWhat to do hereWhat NOT to do
onCreate()setContentView / setContent, init ViewModel, observe LiveData/Flow, restore state from savedInstanceStateLong blocking work, animations
onStart()Register lightweight observers, start animations that should show when visibleAcquire exclusive resources (camera)
onResume()Acquire exclusive resources (camera, sensor), resume paused mediaHeavy init (already done in onCreate)
onPause()Release exclusive resources, pause media, commit critical unsaved dataHeavy operations — this must be fast; blocks the new Activity from showing
onStop()Release observers, stop network polling, unregister receiversSaving data that must not be lost — use onPause or ViewModel
onDestroy()Release anything not yet released; called on finish() OR config changeSaving state — too late; use onSaveInstanceState
onRestart()Refresh data that may have changed while stopped (rare)Heavy re-init — use ViewModel

Configuration Change Flow

A rotation, locale change, or dark-mode toggle triggers a full Activity teardown and recreation by default. The OS calls onSaveInstanceState before onStop, then recreates the Activity passing the saved Bundle to onCreate.

Rotation detected → onPause() → onStop() → onSaveInstanceState(bundle) ← save cheap UI state (scroll pos, selected tab) → onDestroy() ← ViewModel NOT destroyed (ViewModelStore survives) → onCreate(savedInstanceState) ← restore from bundle → onStart() → onResume()

Process Death

When the OS kills your process (low memory), it calls nothing after onStop(). On relaunch, the OS restores the back stack and passes the saved instance state Bundle to onCreate() — but only if onSaveInstanceState() was called before death.

Process death ≠ normal finish: onDestroy() is NOT called on process death. Never rely on onDestroy to save critical data.

State Saving Mechanisms

3 · Why and When to Use It

You cannot opt out of the Activity lifecycle — it is the contract between your app and the OS. What you control is where you put your logic:

ScenarioRight callback / mechanism
Initialize ViewModel, observe data streamsonCreate()
Start camera or audio recordingonResume()
Stop camera or audio recordingonPause()
Unregister BroadcastReceiveronStop()
Persist critical unsaved form dataonPause() (guaranteed) or autosave in ViewModel
Save selected tab / scroll positiononSaveInstanceState()
Survive rotation with loaded dataViewModel
Survive process death with small stateSavedStateHandle in ViewModel
When NOT to: Never start long-running coroutines or network calls directly inside lifecycle callbacks — use ViewModel + lifecycleScope with repeatOnLifecycle so they auto-cancel when appropriate.

4 · Production Example (E-Commerce: Product Detail Screen)

An e-commerce product detail Activity that loads product data, tracks analytics, and saves the selected variant across rotation and process death.

ViewModel with SavedStateHandle

@HiltViewModel
class ProductDetailViewModel @Inject constructor(
    private val getProductUseCase: GetProductUseCase,
    private val savedState: SavedStateHandle   // survives process death
) : ViewModel() {

    // Reads productId from navigation argument via SavedStateHandle
    private val productId: String = checkNotNull(savedState["productId"])

    // Selected variant persisted across rotation AND process death
    var selectedVariant: String?
        get() = savedState["selectedVariant"]
        set(value) { savedState["selectedVariant"] = value }

    val uiState: StateFlow<ProductUiState> = flow {
        emit(ProductUiState.Loading)
        emit(getProductUseCase(productId).fold(
            onSuccess = { ProductUiState.Success(it) },
            onFailure = { ProductUiState.Error(it.message) }
        ))
    }.stateIn(viewModelScope, SharingStarted.WhileSubscribed(5_000), ProductUiState.Loading)
}

Activity — Lifecycle-Aware Observation

@AndroidEntryPoint
class ProductDetailActivity : ComponentActivity() {

    private val viewModel: ProductDetailViewModel by viewModels()

    override fun onCreate(savedInstanceState: Bundle?) {
        super.onCreate(savedInstanceState)
        setContent {
            ProductDetailScreen(viewModel)
        }
        // Collect Flow safely: pauses when Activity goes to background
        lifecycleScope.launch {
            repeatOnLifecycle(Lifecycle.State.STARTED) {
                viewModel.uiState.collect { state ->
                    // update UI based on state
                }
            }
        }
    }
}

// Note: In Compose, you would use collectAsStateWithLifecycle() instead —
// it handles lifecycle awareness automatically.

onSaveInstanceState — Light UI State Only

// Use ONLY for cheap, non-sensitive UI state
override fun onSaveInstanceState(outState: Bundle) {
    super.onSaveInstanceState(outState)
    // scroll position, selected tab — NOT loaded data (that's ViewModel's job)
    outState.putInt("scrollY", binding.scrollView.scrollY)
}

override fun onCreate(savedInstanceState: Bundle?) {
    super.onCreate(savedInstanceState)
    savedInstanceState?.getInt("scrollY")?.let { binding.scrollView.scrollTo(0, it) }
}

Handling Configuration Changes in Manifest (opt-out — use sparingly)

<!-- Only for Activities that manually handle config changes (e.g., video player) -->
<activity
    android:name=".player.VideoPlayerActivity"
    android:configChanges="orientation|screenSize|keyboardHidden"
    />

// Then in Activity:
override fun onConfigurationChanged(newConfig: Configuration) {
    super.onConfigurationChanged(newConfig)
    // Manually adjust layout; no onCreate called — ViewModel already has state
}
Opting out of configuration changes with android:configChanges is acceptable for media players and maps. For most screens, letting the system recreate and using ViewModel is cleaner.

6 · Pitfalls and Best Practices

Collecting Flow in onCreate Without repeatOnLifecycle

❌ Bad — collects in background, wastes resources

override fun onCreate(...) {
    lifecycleScope.launch {
        // Keeps collecting even when Activity is stopped
        viewModel.uiState.collect { render(it) }
    }
}

✅ Good — pauses when not STARTED

override fun onCreate(...) {
    lifecycleScope.launch {
        repeatOnLifecycle(Lifecycle.State.STARTED) {
            viewModel.uiState.collect { render(it) }
        }
    }
}

Doing Work in onDestroy

onDestroy() is NOT guaranteed to be called (process death). Never save critical data here. Use onPause() for must-save data or a ViewModel + Room for persistence.

Other Critical Pitfalls

  • Heavy work in onCreate/onResume: Causes jank and slow start. Move I/O to ViewModel/coroutine.
  • Leak via anonymous inner class: An inner class in Activity captures Activity reference. If passed to a background thread, leaks the Activity.
  • Not restoring state from Bundle: After process death + relaunch, the user sees a blank screen instead of their previous position.
  • Forgetting isFinishing() check in onStop: Some cleanup (like analytics flush) should only happen if actually finishing, not just hiding.
  • Starting Activity from onResume in a loop: If you start another Activity in onResume and that Activity finishes back to you, you get an infinite loop.
  • Network calls in lifecycle callbacks: Put them in ViewModel with viewModelScope. Callbacks may be called multiple times on rotation.
Best Practice checklist:
  • Use ViewModel for all UI state — it survives rotation automatically
  • Use SavedStateHandle for small state that must survive process death
  • Use repeatOnLifecycle(STARTED) to collect Flows
  • In Compose, use collectAsStateWithLifecycle() from lifecycle-runtime-compose
  • Never call blocking operations in lifecycle callbacks
  • Release exclusive resources (camera, GPS) in onPause(), not onStop()

7 · Interview Answer Framework

30-Second Answer

"The Activity lifecycle is a series of callbacks the OS uses to manage screen visibility and memory. The key transitions are onCreate → onStart → onResume for coming to foreground, and onPause → onStop → onDestroy for leaving. The critical insight is: configuration changes like rotation destroy and recreate the Activity, but ViewModel survives. Process death is silent — no callbacks after onStop — so I use SavedStateHandle for small state that must survive that. In modern code with Compose, I use collectAsStateWithLifecycle() to observe flows safely."

2-Minute Structured Answer

The six main callbacks: onCreate (setup), onStart (visible), onResume (interactive), onPause (partially hidden — release exclusive resources), onStop (fully hidden), onDestroy (finishing or config change).

Configuration changes: Rotation triggers full teardown + recreation. onSaveInstanceState is called before onStop, letting you save cheap UI state. ViewModel survives via ViewModelStore — it's retained across config changes by the framework.

Process death: The OS kills the process silently when memory is needed. Callbacks stop after onStop. On relaunch the system reconstructs the back stack and passes saved instance state to onCreate. For critical ViewModel state I use SavedStateHandle, which is backed by the saved instance state Bundle.

In production: I put data loading in ViewModel with viewModelScope. UI observes via StateFlow using repeatOnLifecycle(STARTED) — or collectAsStateWithLifecycle() in Compose — to automatically pause collection when the Activity is in background, preventing unnecessary work and wasted resources.

Must-Mention Points

  1. Six main callbacks and what belongs in each (especially onCreate vs onResume).
  2. Configuration change = full Activity recreation; ViewModel survives via ViewModelStore.
  3. Process death is silent — onDestroy is NOT guaranteed.
  4. onSaveInstanceState called before onStop, Bundle size limited — for small UI state only.
  5. SavedStateHandle in ViewModel for state that survives both rotation AND process death.
  6. repeatOnLifecycle(STARTED) for safe Flow collection (or collectAsStateWithLifecycle in Compose).
  7. Release exclusive resources (camera, sensors) in onPause — not onStop.
  8. Never do blocking/heavy work in lifecycle callbacks — always delegate to ViewModel/coroutine.

Likely Follow-up Questions

QuestionShort Answer
What's the difference between onStop and onDestroy?onStop = Activity is no longer visible but still in memory. onDestroy = Activity is being destroyed (finish() called or config change). onStop is always called; onDestroy may not be called on process death.
Why does ViewModel survive rotation but not process death?ViewModel is held by ViewModelStore, which is retained by the framework's NonConfigurationInstance mechanism during config changes. Process death kills the entire process — all in-memory objects are gone. SavedStateHandle bridges this by persisting data in the Bundle.
What's the difference between finish() and pressing Back?Back navigates up the back stack (can be intercepted via OnBackPressedDispatcher). finish() explicitly destroys the Activity and removes it from the task.
When is onSaveInstanceState called?Before onStop — guaranteed even if onDestroy is not called. Called for rotation, going to home screen, receiving a call — any time the Activity might be destroyed and recreated.

Senior-Level Insight

"The important distinction is that there are three kinds of 'death' for an Activity: (1) config change — only Activity dies, ViewModel survives; (2) user presses Back/finish() — ViewModel also dies, back stack removed, no state to restore; (3) process death — everything dies, system restores back stack and Bundle only. Many bugs come from conflating these three. SavedStateHandle is only for case 3. ViewModel is for case 1. Room/DataStore is for persistent user data across all cases. In a Compose+ViewModel architecture this is clean: ViewModel holds all state, SavedStateHandle holds the survival-critical subset, and Room holds user data — no onSaveInstanceState override needed in most Activity code."

9 · Interview Questions (Self-Check)

Basic List the six Activity lifecycle callbacks in order and describe what each one means.
onCreate → Activity created; onStart → visible but not interactive; onResume → foreground, interactive; onPause → partially hidden (another Activity/dialog in front), release exclusive resources; onStop → fully hidden; onDestroy → being destroyed (finish or config change). onRestart is called between onStop and onStart when coming back to a stopped Activity.
Basic What is the difference between a configuration change and process death?
Configuration change (rotation, locale): Activity is torn down and recreated. ViewModel survives via ViewModelStore. onSaveInstanceState is called.
Process death: OS kills entire process silently. No callbacks after onStop. ViewModel is gone. Only saved instance state Bundle + Room/DataStore data survives. On relaunch, the system reconstructs the back stack and passes the Bundle to onCreate.
Basic When is onSaveInstanceState called?
Before onStop, when the Activity may be destroyed and recreated. This includes rotation, going to home screen, receiving a phone call, going to another app. It is NOT called when the user presses Back (intentional finish) because there's no expectation of restoration.
Intermediate Why does ViewModel survive rotation but not process death?
ViewModel is stored in ViewModelStore, which is attached to the Activity's NonConfigurationInstance. When a configuration change occurs, the framework retains NonConfigurationInstance across teardown/recreation, so ViewModelStore (and thus ViewModel) survives. During process death, the OS terminates the process entirely — all JVM objects are gone, including ViewModelStore. SavedStateHandle bridges this by serialising ViewModel state into the saved instance Bundle, which the OS does persist across process death.
Intermediate What is the correct way to collect a StateFlow from an Activity in 2025?
Two correct approaches:
1. lifecycleScope.launch { repeatOnLifecycle(Lifecycle.State.STARTED) { flow.collect { ... } } }
2. In Compose: val state by viewModel.uiState.collectAsStateWithLifecycle() from lifecycle-runtime-compose.
Both automatically pause collection when the Activity goes below STARTED (background), preventing unnecessary work. The anti-pattern is plain lifecycleScope.launch { flow.collect { ... } } with no repeatOnLifecycle, which keeps collecting even in background.
Intermediate When should you release the camera — in onPause or onStop?
onPause. Camera is an exclusive resource. Another Activity (like the system camera app) may need it while your Activity is partially hidden (onPause state). If you release in onStop, the other app may fail to open the camera. Release exclusive hardware resources (camera, microphone, GPS with FINE location via requestSingleUpdate) in onPause.
Intermediate What happens to a ViewModel when the user presses Back?
When the user presses Back and the Activity finishes (not just a config change), the Activity's ViewModelStore is cleared. ViewModel.onCleared() is called. The ViewModel is destroyed. This is intentional — the user left that screen. SavedStateHandle also loses its data since the system discards the saved state for a finished Activity.
Senior/Scenario [Scenario] After a rotation, users report that a form they were filling out is blank. What went wrong and how do you fix it?
Root cause: Form state (text fields, selections) was stored only in the View/Composable local state without being backed by ViewModel or SavedStateHandle. On rotation, the Activity recreates, the View is re-inflated, and state is lost.

Fix in Compose: Use rememberSaveable for local UI state (it's backed by saved instance state). For important form fields, hoist state to ViewModel using MutableStateFlow or SavedStateHandle — savedState.getStateFlow("email", "").

Fix in XML Views: Use EditText's built-in state saving (it saves if the view has an android:id) for simple cases. For complex forms, use ViewModel with SavedStateHandle. Never reconstruct form state from scratch in onCreate without checking savedInstanceState.
Senior/Scenario [Coding] Show how to use SavedStateHandle in a ViewModel to persist a search query across process death. 
@HiltViewModel
class SearchViewModel @Inject constructor(
    private val searchUseCase: SearchProductsUseCase,
    private val savedState: SavedStateHandle
) : ViewModel() {

    // StateFlow backed by SavedStateHandle — survives process death
    val query: StateFlow<String> =
        savedState.getStateFlow("query", "")

    val results: StateFlow<List<Product>> = query
        .debounce(300)
        .flatMapLatest { searchUseCase(it) }
        .stateIn(viewModelScope, SharingStarted.WhileSubscribed(5_000), emptyList())

    fun onQueryChanged(newQuery: String) {
        savedState["query"] = newQuery   // persisted immediately
    }
}
savedState.getStateFlow() returns a StateFlow directly backed by the Bundle. Any assignment to savedState["query"] is immediately persisted.
Senior/Scenario [Debug] Your app crashes with "IllegalStateException: Fragment already added" after rotation. What caused it and how do you fix it?
Caused by adding a Fragment in onCreate without checking if it already exists. On rotation, the FragmentManager automatically restores previously added Fragments from the back stack. If your code then calls fragmentManager.beginTransaction().add(MyFragment()) unconditionally, the Fragment is added twice — crash.

Fix: Check before adding:
if (supportFragmentManager.findFragmentByTag("myFragment") == null) { supportFragmentManager.beginTransaction().add(R.id.container, MyFragment(), "myFragment").commit() }

Better: Prefer Navigation Component (manages back stack for you) or Compose (no Fragment add/remove boilerplate).
