8A — Architecture Patterns

MVC, MVP, MVVM, MVI — what each solves and its trade-offs. Full layered architecture: UI → ViewModel → UseCase → Repository → Data Sources. When to use each pattern.

ID: 8A ⭐ Tier 1
🔍
1. Overview

Why architecture patterns matter

Architecture patterns solve the same fundamental problem: separation of concerns. In Android, without architecture, Activities and Fragments become God objects — containing business logic, UI code, data fetching, and state management all tangled together. The result: untestable, fragile, impossible-to-maintain code.

The evolution

  • MVC — classic pattern; Controller = Activity; View = XML; Model = data; Controller too big
  • MVP — Presenter separates logic; testable; but Presenter leaks View references; boilerplate
  • MVVM — ViewModel + LiveData/StateFlow; lifecycle-aware; two-way binding optional; Android recommended
  • MVI — strict UDF; immutable state; sealed Intents; single state object; most predictable
Senior Mental Model
In interviews, say: "We use MVVM with Clean Architecture layers — UI → ViewModel → UseCase → Repository → Remote/Local data sources. UseCases encapsulate single business rules, making them independently testable. Repository provides a single data access abstraction, hiding whether data comes from network or cache. We could layer MVI on top of MVVM if we need stricter state management."

2. MVC, MVP, MVVM

MVC — Model-View-Controller

LayerAndroid mappingResponsibility
ModelData classes, DB, APIBusiness data and logic
ViewXML layoutsDisplay only
ControllerActivity / FragmentGlue — handles events, updates View, calls Model

Problem: In Android, Activity is both Controller AND part of the lifecycle. Business logic in Activity = untestable. God Activity anti-pattern.

MVP — Model-View-Presenter

LayerAndroid mappingResponsibility
ModelRepository, data layerData and business logic
ViewActivity/Fragment (behind interface)UI only, delegates all logic
PresenterPlain Kotlin classBusiness logic, mediates between View and Model

Improvement: Presenter is testable (no Android deps). Problem: Presenter holds a View reference → memory leaks on rotation. Weak references or detach pattern needed. 1:1 Presenter-View coupling is boilerplate-heavy.

MVVM — Model-View-ViewModel

// View observes ViewModel state — no direct reference from VM to View
class OrderViewModel(
    private val placeOrder: PlaceOrderUseCase
) : ViewModel() {

    // ViewModel never holds a reference to View/Activity
    private val _state = MutableStateFlow(OrderState())
    val state: StateFlow<OrderState> = _state.asStateFlow()

    fun submitOrder(order: Order) {
        viewModelScope.launch {
            _state.update { it.copy(isLoading = true) }
            val result = placeOrder(order)
            _state.update { it.copy(isLoading = false, result = result) }
        }
    }
}
// View lifecycle: Activity destroyed → ViewModel survives rotation
// View lifecycle: navigated away → ViewModel.onCleared() called

3. MVI — Model-View-Intent

MVI takes UDF to its strictest form: a single immutable state object, sealed class Intents (user actions), and pure reducers that produce new state from old state + intent. No side effects in state — everything is explicit.

// Intent: sealed class representing all possible user actions
sealed class TransferIntent {
    data class AmountChanged(val amount: String) : TransferIntent()
    data class RecipientSelected(val id: String) : TransferIntent()
    object SubmitTransfer : TransferIntent()
}

// State: single immutable data class
data class TransferState(
    val amount: String = "",
    val recipientId: String? = null,
    val isLoading: Boolean = false,
    val error: String? = null,
    val isSuccess: Boolean = false
)

// ViewModel processes intents → produces new state
class TransferViewModel : ViewModel() {
    private val _state = MutableStateFlow(TransferState())
    val state = _state.asStateFlow()

    fun processIntent(intent: TransferIntent) {
        when (intent) {
            is TransferIntent.AmountChanged ->
                _state.update { it.copy(amount = intent.amount) }
            is TransferIntent.RecipientSelected ->
                _state.update { it.copy(recipientId = intent.id) }
            TransferIntent.SubmitTransfer -> submitTransfer()
        }
    }

    private fun submitTransfer() {
        viewModelScope.launch {
            _state.update { it.copy(isLoading = true) }
            // ... call use case
        }
    }
}

4. Clean Architecture Layers
UI Layer (Compose Screens + ViewModels)
    ↕ StateFlow / Events
Domain Layer (UseCases / Interactors)
    ↕ suspend functions / Flow<T>
Data Layer (Repositories)
    ↕ suspend functions / Flow<T>
Data Sources (Remote API + Room DB + Preferences)

Each layer's responsibilities

// UI Layer: display state, forward events
@Composable
fun TransferScreen(viewModel: TransferViewModel) {
    val state by viewModel.state.collectAsStateWithLifecycle()
    /* render state, send intents to viewModel */
}

// Domain Layer: business rules, no Android deps
class ValidateTransferUseCase {
    operator fun invoke(
        amount: BigDecimal, balance: BigDecimal
    ): ValidationResult = when {
        amount <= BigDecimal.ZERO -> ValidationResult.InvalidAmount
        amount > balance -> ValidationResult.InsufficientFunds
        else -> ValidationResult.Valid
    }
}

class ExecuteTransferUseCase(
    private val repository: TransferRepository
) {
    suspend operator fun invoke(
        from: Account, to: Account, amount: BigDecimal
    ): Result<Transfer> = runCatching {
        repository.executeTransfer(from.id, to.id, amount)
    }
}

// Data Layer: data access abstraction
interface TransferRepository {
    suspend fun executeTransfer(fromId: String, toId: String, amount: BigDecimal): Transfer
}

class TransferRepositoryImpl(
    private val remoteApi: TransferApi,    // Retrofit
    private val localDao: TransferDao     // Room
) : TransferRepository {
    override suspend fun executeTransfer(fromId: String, toId: String, amount: BigDecimal): Transfer {
        val transfer = remoteApi.postTransfer(TransferRequest(fromId, toId, amount))
        localDao.insert(transfer.toEntity())
        return transfer
    }
}

5. Production Example

Banking: full transfer flow with all layers

// ViewModel: MVVM orchestrator
class TransferViewModel(
    private val validateTransfer: ValidateTransferUseCase,
    private val executeTransfer: ExecuteTransferUseCase,
    private val getAccount: GetAccountUseCase
) : ViewModel() {

    val uiState: StateFlow<TransferUiState> =
        getAccount()
            .map { account -> TransferUiState(balance = account.formattedBalance()) }
            .stateIn(viewModelScope, SharingStarted.WhileSubscribed(5_000), TransferUiState.Loading)

    private val _events = MutableSharedFlow<TransferEvent>(extraBufferCapacity = 1)
    val events = _events.asSharedFlow()

    fun submitTransfer(amount: BigDecimal, recipientId: String) {
        viewModelScope.launch {
            val account = (uiState.value as? TransferUiState.Ready)?.account ?: return@launch

            val validation = validateTransfer(amount, account.balance)
            if (validation != ValidationResult.Valid) {
                _events.emit(TransferEvent.ValidationError(validation))
                return@launch
            }

            executeTransfer(account, recipientId, amount)
                .onSuccess { _events.emit(TransferEvent.Success(it)) }
                .onFailure { _events.emit(TransferEvent.Error(it)) }
        }
    }
}

6. Pitfalls & Best Practices
Pitfall 1 — Fat ViewModel
Moving all business logic to the ViewModel without UseCases creates a "Fat ViewModel" anti-pattern — the same problem as Fat Controller in MVC, just moved. UseCases should encapsulate discrete business rules; the ViewModel should only orchestrate them.
Pitfall 2 — Repository doing too much
The Repository should be a clean data access abstraction — not the place for business logic. If a Repository method is called "validateAndSaveIfFundsAvailable", the validate part belongs in a UseCase, not the Repository.
Pitfall 3 — Domain layer depending on Android
UseCases should be pure Kotlin with zero Android dependencies — no Context, no ViewModel, no Room entities. This is what makes them unit-testable with JUnit without Robolectric.
Best Practice — Repository interface in domain layer
Define the Repository interface in the domain layer, implementation in the data layer. This inverts the dependency — data layer depends on domain, not the other way. Enables mocking in UseCase tests without a real DB or network.

7. Interview Framework

30-second answer

"We use MVVM with Clean Architecture. The UI layer has Compose composables and ViewModels. ViewModels expose StateFlow and receive events. The domain layer has UseCases — pure Kotlin, no Android deps, one business rule each. The data layer has Repositories that abstract Remote API and local Room database. Dependencies only flow inward: UI → Domain ← Data."

2-minute answer

"The architecture evolution: MVC had Activity as the Controller — god class, untestable. MVP extracted a Presenter but it held a View reference, causing memory leaks on rotation. MVVM solved this — ViewModel survives rotation, never holds a View reference, exposes observable state that the View subscribes to. Android Jetpack's ViewModel + LiveData/StateFlow makes MVVM lifecycle-safe.

On top of MVVM, Clean Architecture adds layers: UI calls UseCases, not Repositories directly. Each UseCase does one thing and is unit-testable without Robolectric. Repository interfaces live in the domain layer — implementations in the data layer — this inverts the dependency, enabling proper mocking in tests.

MVI adds stricter UDF on top: sealed class Intents describe all actions, a single immutable State describes all UI state, and a reducer maps Intent + State → new State. It's more boilerplate but makes complex checkout-style flows auditable — you can replay every state transition."

Must-mention points

1
MVVM + Clean Architecture = the Android standard; ViewModel has no View reference
2
UseCases = pure Kotlin — no Android deps, one business rule, independently testable
3
Repository interface in domain — dependency inversion; data layer depends on domain
4
MVI = strict UDF — sealed Intents, single immutable state, for complex flows
5
Layer diagram: UI → ViewModel → UseCase → Repository → API/DB

Follow-up Q&A

Q: "Why use a UseCase between ViewModel and Repository?"

A: Three reasons: (1) Testability — UseCases can be unit-tested with JUnit, injecting a mock Repository. (2) Reuse — multiple ViewModels can use the same UseCase without duplicating logic. (3) Single responsibility — each UseCase encapsulates exactly one business rule. Without UseCases, business logic leaks into ViewModels, making them fat and hard to test.

Q: "When would you choose MVI over MVVM?"

A: For complex, multi-step flows with many possible states and transitions — checkout flows, onboarding, complex forms with multiple validation rules. MVI's single state object and sealed Intents make the state machine explicit and auditable. You can log every Intent and replay the state transitions for debugging. For simpler screens (list + detail), MVVM is less boilerplate and equally appropriate.

Senior insight

Senior Insight
In a banking app, we use MVVM for most screens but MVI for the payment flow. The payment screen has 12+ possible states (form idle, amount entered, recipient selected, validating, payment pending, 3DS challenge, success, various error states). MVI's sealed state class makes every state explicit — no boolean flags, no "can this be null here?" guessing. The reducer is a pure function — testable with exhaustive when expressions. This is exactly the kind of complex flow where MVI pays its boilerplate cost.

9. Interview Questions
What is the main problem with MVC in Android?
Basic⌄
In Android MVC, Activity/Fragment acts as the Controller. This creates a God Class — Activities handle button clicks, network calls, database queries, navigation, lifecycle management, and UI updates all in one place. The Controller is tightly coupled to Android SDK, making it untestable with JUnit. It's also lifecycle-unsafe: the Controller is destroyed on rotation, interrupting ongoing work.
What is the key difference between MVP and MVVM?
Basic⌄
In MVP, the Presenter holds a direct reference to the View interface and calls methods on it — tight coupling that requires careful lifecycle management (detach on destroy). In MVVM, the ViewModel exposes observable state (LiveData/StateFlow) and never holds a View reference. The View subscribes and unsubscribes independently. This makes MVVM lifecycle-safe automatically — ViewModel survives rotation, View re-subscribes on recreation.
Why use UseCases between ViewModel and Repository?
Basic⌄
Three reasons: (1) Single Responsibility — each UseCase encapsulates one business rule; (2) Testability — UseCases are pure Kotlin, no Android dependencies, unit-testable with JUnit using mock Repositories; (3) Reuse — multiple ViewModels can use the same UseCase. Without UseCases, business logic accumulates in ViewModels (Fat ViewModel anti-pattern) or Repositories.
What is MVI and how does it differ from MVVM?
Intermediate⌄
MVI (Model-View-Intent) enforces strict UDF with three components: sealed Intent class (all user actions explicit), immutable State data class (all UI state in one object), and a reducer (Intent + State → new State). Unlike MVVM where ViewModels may have multiple state flows and methods, MVI has one state object and one entry point (processIntent). This makes state transitions auditable and the complete state machine visible. Tradeoff: more boilerplate.
Where should the Repository interface be defined — in the domain layer or data layer?
Intermediate⌄
Domain layer. This is the Dependency Inversion Principle — the domain layer should not depend on the data layer. By defining the interface in domain and the implementation in data, the data layer depends on the domain (not the other way). This means UseCases can reference the interface without knowing about Retrofit or Room. In tests, you inject a fake Repository that implements the domain interface — zero Android SDK needed.
What dependencies should a UseCase have?
Intermediate⌄
Only Repository interfaces (defined in domain) and other UseCases or domain services. A UseCase should have zero Android SDK dependencies — no Context, no ViewModel, no Room entities, no Retrofit annotations. This purity makes it unit-testable with plain JUnit5. If you find yourself adding import android.* in a UseCase, that's a code smell — the logic probably belongs in the data layer or a domain-specific service.
When would you choose MVI over MVVM for a feature?
Intermediate⌄
Use MVI when a screen has many possible states and transitions that are hard to track with boolean flags across multiple StateFlows — checkout flows, complex onboarding, multi-step forms, game UIs. MVI's single state object makes every combination of booleans explicit; you can't have an "impossible state" (loading AND error simultaneously) if the State is a sealed class. Use MVVM for simpler screens — list/detail, settings, profile — where the overhead of sealed Intents and reducers isn't justified.
A junior dev put network retry logic in the ViewModel. Is this correct? Where should it go?
Senior⌄
Not correct for reusable retry logic. Network retry is a data-layer concern — it applies regardless of which screen triggers the request. Retry logic belongs in: (1) Repository (retryWhen on Flow, or manual retry in suspend function), or (2) a generic data source interceptor (OkHttp Interceptor for HTTP retries). The ViewModel should handle UI state for retries (show retry button, update loading state) but not implement the retry policy itself. If it's a business-level retry (e.g., retry payment only if network error, not if card declined), a UseCase can add retry semantics before calling the repository.
How would you test a UseCase that executes a bank transfer?
Senior⌄
class ExecuteTransferUseCaseTest { private val fakeRepo = FakeTransferRepository(); private val sut = ExecuteTransferUseCase(fakeRepo); @Test fun `transfer succeeds when funds available`() = runTest { val result = sut(fromAccount, toAccount, 100.toBigDecimal()); assertTrue(result.isSuccess); assertEquals(1, fakeRepo.recordedTransfers.size) }; @Test fun `transfer fails when API throws`() = runTest { fakeRepo.shouldThrow = IOException(); val result = sut(fromAccount, toAccount, 100.toBigDecimal()); assertTrue(result.isFailure) } }. FakeTransferRepository implements the domain interface — no Retrofit, no Room, no Hilt. Tests run on JVM in milliseconds.
Design the full architecture for a real-time price tracking screen in a banking app.
Senior⌄
UI: Compose screen collecting StateFlow. ViewModel: exposes PriceScreenState via stateIn(WhileSubscribed(5000)); uses SubscribeToPriceUpdatesUseCase. UseCase: SubscribeToPriceUpdatesUseCase(repo): returns Flow<PriceUpdate> — pure kotlin, composable with Flow operators. Repository interface (in domain): PriceRepository.observePrices(symbols): Flow<PriceUpdate>. Repository impl (in data): bridges WebSocket via callbackFlow; shareIn(appScope, WhileSubscribed(5000)) to share one socket among multiple subscribers. Local fallback: Room observeLatestPrices() on network error. Dependencies: ViewModel depends on UseCase; UseCase depends on Repository interface; RepositoryImpl depends on WebSocket client and Room DAO.
