1I — Inline & Recursion

inline, noinline, crossinline, reified type parameters, and tail recursion — performance and type-safety features that power Kotlin's standard library and Flow operators.

ID: 1I ⭐ Tier 1
🔍
1. Overview

What it is

inline functions eliminate the lambda object allocation overhead by copying the function body (and lambda bodies) directly into the call site at compile time. reified type parameters (only usable in inline functions) preserve generic type info at runtime, bypassing JVM type erasure. noinline and crossinline modify how lambdas in inline functions behave. Tail recursion (tailrec) optimizes recursive functions into iterative loops, eliminating stack overflow risk.

Why it matters for Android

  • inline — Flow operators like map, filter, transform are inline; run, let, apply are inline — zero lambda allocation overhead.
  • reified — type-safe Intent extras, ViewModelProvider, Gson/Moshi deserialization: inline fun <reified T> intent()
  • tailrec — deep recursive tree traversal (file systems, JSON parsing, navigation graphs) without StackOverflowError
  • Understanding inline explains why return inside a lambda can exit the outer function (non-local return)
Senior Mental Model
inline trades binary size for performance. The compiler copy-pastes the function body at every call site. Good for small, frequently-called HOF utilities. Not for large functions called rarely — increases APK size.
⚙
2. How It Works

inline — how the compiler transforms it

// Source:
inline fun measure(block: () -> Unit) {
    val start = System.nanoTime()
    block()
    Timber.d("${System.nanoTime() - start}ns")
}

// Call site:
measure { expensiveOp() }

// Compiled to (conceptually):
val start = System.nanoTime()
expensiveOp()                   // lambda body inlined here
Timber.d("${System.nanoTime() - start}ns")
// No lambda object created, no virtual call — just inlined code

Non-local return — enabled by inline

// Possible ONLY because measure is inline
fun processIfActive(user: User) {
    measure {
        if (!user.isActive) return   // returns from processIfActive, not just the lambda!
        doWork(user)
    }
}
// This works because the lambda is inlined — the 'return' is in processIfActive's body

noinline — opt a single lambda out of inlining

// When you need to pass a lambda as an object (store, pass to another function)
inline fun runWithCallback(
    action: () -> Unit,            // inlined — body copied at call site
    noinline callback: () -> Unit   // noinline — kept as lambda object
) {
    action()
    handler.post(callback)  // callback passed to Handler.post — must be an object
}

crossinline — no non-local return allowed

// crossinline: lambda IS inlined but cannot use non-local return
// Used when the lambda is called in a different execution context (another lambda, async)
inline fun withThread(crossinline block: () -> Unit) {
    Thread {
        block()      // called inside Thread lambda — non-local return not safe here
    }.start()
}

fun example() {
    withThread {
        // return  // ❌ compile error — crossinline prevents non-local return
        doWork()
    }
}

reified — preserve type at runtime

// Without reified — type erased at runtime
fun <T> parse(json: String): T = gson.fromJson(json, T::class.java)  // ❌ won't compile

// With reified — type available at runtime via inlining
inline fun <reified T> parse(json: String): T =
    gson.fromJson(json, T::class.java)  // ✅ T::class.java available at each call site

val user: UserProfile = parse(jsonString)  // no explicit class param needed

// Type-safe Intent creation
inline fun <reified T : Activity> Context.startActivity(
    noinline block: Intent.() -> Unit = {}
) = startActivity(Intent(this, T::class.java).apply(block))

// Usage:
startActivity<DetailActivity> { putExtra("id", productId) }

tailrec — safe deep recursion

// Without tailrec — StackOverflowError for deep trees
fun sumTo(n: Int): Int = if (n == 0) 0 else n + sumTo(n - 1)
// sumTo(100_000) → StackOverflowError

// With tailrec — compiled to a loop
tailrec fun sumTo(n: Int, acc: Int = 0): Int =
    if (n == 0) acc else sumTo(n - 1, acc + n)
// sumTo(1_000_000) works fine — no stack growth

// Requirement: recursive call must be the LAST operation (tail position)
// n + sumTo(n-1) — NOT tail position (addition happens after the call)
// sumTo(n-1, acc+n) — IS tail position (call is the last thing)

3. Why and When to Use It

When to Use inline

  • Small higher-order functions called in tight loops — collection operators, coroutine builders
  • Functions that need reified type parameters — always requires inline
  • Functions where non-local return is desired — scope functions (run, let, apply, etc.)

When NOT to use inline

Do NOT
  • Mark large functions as inline — bloats every call site (APK size increase)
  • Mark functions with no lambda parameters as inline — no benefit; warning from compiler
  • Inline a function that's called rarely — overhead not worth the complexity
  • Use tailrec when the recursive call is not in tail position — compiler silently ignores it

When to Use reified

Use CaseExample
Type-safe Intent/Activity startinline fun <reified T: Activity> Context.startActivity()
JSON deserializationinline fun <reified T> Gson.fromJson(json): T
ViewModel retrievalinline fun <reified T: ViewModel> ComponentActivity.viewModels()
Type checking without castinline fun <reified T> Any.isInstanceOf(): Boolean = this is T

4. Production Example
Scenario
Banking app — inline utility functions, reified type-safe API parsing, tailrec for tree traversal.

inline — safeApiCall with non-local return

// data/remote/NetworkUtils.kt
inline fun <T> safeCall(block: () -> T): Result<T> = try {
    Result.success(block())
} catch (e: CancellationException) {
    throw e
} catch (e: Exception) {
    Result.failure(e)
}
// ✅ inline: no lambda object allocation per API call
// ✅ non-local return from the lambda propagates correctly

// Usage in Repository:
override suspend fun getTransactions() = safeCall { api.getTransactions() }

reified — type-safe JSON parser extension

// data/remote/JsonExtensions.kt
inline fun <reified T> String.fromJson(): T =
    Gson().fromJson(this, T::class.java)

inline fun <reified T> Response<*>.errorBodyAs(): T? =
    errorBody()?.string()?.fromJson()

// Usage — no explicit class needed:
val profile: UserProfile = jsonString.fromJson()
val error: ApiError? = response.errorBodyAs()   // T inferred as ApiError

reified — type-safe Activity start

// presentation/extensions/ActivityExtensions.kt
inline fun <reified T : Activity> Context.startActivity(
    noinline extras: Intent.() -> Unit = {}
) {
    startActivity(Intent(this, T::class.java).apply(extras))
}

// Usage — clean and type-safe:
startActivity<PaymentActivity> {
    putExtra("orderId", orderId)
    putExtra("amount", amount)
}

tailrec — traversing a navigation graph

// domain/util/NavigationUtils.kt
data class NavNode(val id: String, val parent: NavNode?)

// Find root of navigation graph — tailrec avoids StackOverflow for deep stacks
tailrec fun findRoot(node: NavNode): NavNode =
    if (node.parent == null) node
    else findRoot(node.parent)   // tail position — last operation

// Find all ancestor IDs (tail-recursive accumulator)
tailrec fun collectAncestors(
    node: NavNode?,
    acc: List<String> = emptyList()
): List<String> =
    if (node == null) acc
    else collectAncestors(node.parent, acc + node.id)

6. Pitfalls & Best Practices

Inlining large functions — APK bloat

// ❌ BAD — large function inlined; body copied at every call site
inline fun complexSetup(block: () -> Unit) {
    // 50 lines of setup code...
    block()
    // 30 lines of teardown...
}
// Called 10 times → 800 lines of bytecode vs 80
// ✅ GOOD — keep inline functions small (under ~10 lines)
inline fun <T> timed(block: () -> T): T {
    val t = System.nanoTime(); return block().also { Timber.d("${System.nanoTime()-t}ns") }
}

tailrec warning ignored — no optimization applied

// ❌ BAD — NOT tail position! Compiler silently skips optimization
tailrec fun factorial(n: Int): Int =
    if (n <= 1) 1 else n * factorial(n - 1)  // multiplication happens AFTER call
// tailrec keyword is silently ignored — no loop generated
// ✅ GOOD — accumulator pattern puts call in tail position
tailrec fun factorial(n: Int, acc: Long = 1): Long =
    if (n <= 1) acc else factorial(n - 1, acc * n)  // call IS the last op

noinline forgotten — compile error

// ❌ BAD — passing inlined lambda to a function that needs a function object
inline fun withDelay(action: () -> Unit) {
    handler.postDelayed(action, 1000)  // ❌ Handler.postDelayed needs a Runnable object
}
// ✅ GOOD — noinline keeps it as a lambda object
inline fun withDelay(noinline action: () -> Unit) {
    handler.postDelayed(action, 1000)
}

Production Best Practices

  1. Use inline only for higher-order functions that are small and called frequently.
  2. Use reified to eliminate boilerplate Class<T> parameters from generic functions.
  3. Always use an accumulator with tailrec to place the recursive call in tail position.
  4. Use noinline when a lambda needs to be passed to another function, stored, or returned.
  5. Use crossinline when the lambda is called in a different context (Thread, Handler, async callback).
  6. Verify tailrec optimization works — Kotlin compiler warns if it can't apply it (but sometimes silently skips).

7. Interview Answer Framework

30-Second Answer

"The inline keyword copies a function's body — and its lambda arguments — directly into the call site at compile time. This eliminates lambda object allocation for higher-order functions and enables two advanced features: reified type parameters, which preserve generic type info at runtime to bypass JVM erasure, and non-local returns from lambdas. noinline and crossinline control lambda behavior within inline functions. Tail recursion with tailrec converts recursive functions to loops, preventing StackOverflowErrors."

2-Minute Structured Answer

"Inline functions solve the overhead of higher-order functions. Normally, every lambda passed to a function creates a new object on the heap — allocation + virtual dispatch. For small utility functions called in loops or on every collection element, this adds up. Marking the function inline tells the compiler to copy the function body and all lambda bodies to the call site — zero allocation, zero virtual call.

This enables two things. First, non-local return: inside an inline HOF, a return statement returns from the enclosing function. This is why the scope functions (run, let, apply) are inline. Second, reified: normally generic type parameters are erased at runtime. Inside an inline function, the compiler substitutes the actual type at each call site, so T::class.java is valid. I use this for type-safe Intent creation, JSON deserialization, and ViewModelProvider extensions — no explicit Class parameter needed.

noinline opts a single lambda out of inlining — needed when you must pass the lambda as an object (to Handler.post, store it, etc.). crossinline inlines the lambda but prevents non-local return — needed when the lambda is called inside another lambda or thread.

Tail recursion: tailrec converts a recursive function to a loop when the recursive call is in tail position — the last operation. I use it for tree traversal in navigation graphs. The trick is using an accumulator pattern to put the call in tail position."

Must-Mention Points

1
inline copies function body + lambda bodies to call site — eliminates lambda object allocation
2
Non-local return: only possible in lambdas passed to inline functions — return exits the outer function
3
reified T requires inline — preserves generic type at runtime; enables T::class.java, is T
4
noinline: lambda stays as object — needed when passing to functions expecting a function reference
5
crossinline: lambda is inlined but non-local return forbidden — for lambdas called in different execution context
6

  • Kotlin compiler IR details of inlining

Likely Follow-up Questions

QuestionShort Answer
Why can't reified be used without inline?Because inlining is the mechanism that preserves the type. The compiler substitutes the actual type at each call site during inlining. Without inlining there's only one copy of the bytecode, and the JVM erases generic types at runtime.
What is a non-local return?A return inside a lambda that returns from the enclosing named function, not just the lambda. Only possible in lambdas passed to inline functions, because the lambda body is inlined into the outer function.
When would you use crossinline over noinline?crossinline: lambda IS inlined (no allocation) but non-local return is forbidden — use when the lambda runs in a different context (Thread, runOnUiThread). noinline: lambda NOT inlined — use when you need a lambda object to store, return, or pass elsewhere.
What happens if tailrec can't be applied?Kotlin will issue a warning (or in some cases silently ignore) — the code still compiles and runs, but as regular recursion. Check by ensuring the recursive call is truly the last expression in every code path.

9. Interview Questions (Self-Check)
How to use
Answer first, then reveal.

Basic

B1 — What does the inline keyword do? What problem does it solve?
Easy▼
The inline keyword instructs the compiler to copy the function body — and the bodies of any lambda parameters — directly into the call site. This eliminates the overhead of creating lambda objects on the heap and the virtual method dispatch for every call. It solves the performance cost of higher-order functions: without inlining, every filter { } or let { } call creates a new anonymous class instance.
B2 — What is a reified type parameter and why does it require inline?
Easy▼
A reified type parameter is one that's available at runtime — you can call T::class.java, use is T, and as T inside the function. Normally, JVM erases generic types at runtime, making this impossible.

It requires inline because inlining is the mechanism: when the function is inlined, the compiler substitutes the actual type at each call site. So T::class.java is replaced with UserProfile::class.java at one call site and Order::class.java at another. Without inlining there'd be one copy of the bytecode and the type would be erased.
B3 — What is tail recursion? Why is it useful and what does tailrec require?
Easy▼
Tail recursion is when the recursive call is the last operation in the function — nothing else happens after it returns. This allows the compiler to reuse the current stack frame instead of allocating a new one, converting the recursion to an iterative loop. This prevents StackOverflowError for deep recursion (thousands/millions of steps).

tailrec requirement: the recursive call must be in tail position — the very last thing the function does. n * factorial(n-1) is NOT tail position (multiplication happens after the call). factorial(n-1, acc * n) IS tail position. Use an accumulator parameter to restructure if needed.

Intermediate

I1 — What is the difference between noinline and crossinline?
Medium▼
noinline: the lambda is NOT inlined — it's kept as a regular lambda object. Use when the lambda needs to be stored in a variable, passed to another function expecting a function type, or returned from the inline function.

crossinline: the lambda IS inlined (no object allocation) but non-local returns are forbidden. Use when the lambda is called inside another lambda or a different execution context (like a Thread or Handler callback). The reason: the lambda body is inlined at the call site, but when it's inside a Thread block, a return couldn't reliably exit the outer function because execution has moved to a different thread.
I2 — (Coding) Write a reified extension function that safely gets an extra from an Intent.
MediumCoding▼
inline fun <reified T> Intent.getExtraOrNull(key: String): T? =
    extras?.get(key) as? T

// Usage:
val orderId: String? = intent.getExtraOrNull("order_id")
val amount: Double? = intent.getExtraOrNull("amount")

// Or with a required version:
inline fun <reified T> Intent.requireExtra(key: String): T =
    getExtraOrNull(key) ?: throw IllegalArgumentException("Missing required extra: $key")
I3 — Why does a return inside a let { } block sometimes exit the outer function? How do you prevent it?
Medium▼
let is an inline function. When a function is inline, its lambda body is copied into the call site. A bare return inside an inline lambda is a non-local return — it exits the enclosing named function, not just the lambda.

Example: if you're inside a function and write user?.let { return }, that return exits the outer function entirely.

To exit only the lambda, use a labeled return: return@let. This limits the return to the lambda scope only: 
user?.let {
    if (it.isBlocked) return@let   // exits let only
    processUser(it)
}
I4 — (Coding) Why doesn't tailrec optimize this? Fix it.
MediumCoding▼
// ❌ Not tail-recursive — multiplication happens AFTER the recursive call
tailrec fun factorial(n: Int): Long =
    if (n <= 1) 1 else n * factorial(n - 1)
// The last operation is multiplication, not the recursive call
// ✅ Fix — accumulator puts recursive call in tail position
tailrec fun factorial(n: Int, acc: Long = 1L): Long =
    if (n <= 1) acc
    else factorial(n - 1, acc * n)   // call is the LAST thing — tail position
// Now: tailrec compiles this to a while loop — no stack growth

Senior / Scenario

S1 — Why are Kotlin's scope functions (let, run, apply, etc.) inline? What benefits does this give them?
Hard▼
All five scope functions are inline. Benefits:

1. Zero lambda allocation: calling user?.let { } millions of times (e.g., in a hot loop or for every item in a large list) doesn't create a new anonymous class instance each time.

2. Non-local return: you can write return inside a run { } or let { } block to exit the enclosing function — useful for early return patterns without breaking the fluent style.

3. Performance transparency: the compiler inlines them, so there's no extra call stack frame or virtual dispatch overhead. They behave as if you wrote the code inline manually.

This is intentional design — scope functions are meant to be used pervasively throughout Kotlin code. Making them inline ensures they have zero performance cost at any call frequency.
S2 — (Scenario) You write an inline function that takes two lambdas. One needs to be stored in a list for later execution. What happens and how do you fix it?
HardScenario▼
Problem: When a function is marked inline, ALL lambda parameters are inlined by default. An inlined lambda doesn't exist as an object — it's just code pasted at the call site. If you try to store it in a list (which requires an object reference), the compiler rejects it with an error: "Illegal usage of inline-parameter."

Fix: Mark the lambda that needs to be stored as noinline: 
inline fun setupWithCallback(
    action: () -> Unit,              // inlined — no object
    noinline onComplete: () -> Unit  // noinline — kept as object
) {
    action()                          // inlined at call site
    callbacks.add(onComplete)         // stored as object — works
}
You get the inlining benefit for action (no allocation) while onComplete remains a proper function object that can be stored, called later, and referenced by multiple consumers.
