7B — State Management

ID: 7B ⭐ Tier 1

1. Overview

State types in Compose

  • remember { mutableStateOf(x) } — in-composition state; survives recomposition; lost on rotation/process death
  • rememberSaveable { mutableStateOf(x) } — persists through config changes and process death (via Bundle/SavedState)
  • ViewModel StateFlow → collectAsStateWithLifecycle() — screen-level business state; survives rotation
  • derivedStateOf { } — derived computation from other state; avoids over-recomposition

Unidirectional Data Flow (UDF)

State flows DOWN — from ViewModel → composable → child composable (as parameters). Events flow UP — from child composable → parent → ViewModel (as lambda callbacks). The ViewModel is the single source of truth.

Senior Mental Model
State hoisting = moving state up to the lowest common ancestor that needs it. The rule: hoist state to the highest level that needs to read or write it. Local toggle state (isExpanded) stays in the composable. Business data (user profile) belongs in ViewModel. Navigation state belongs in NavController / ViewModel.

2. remember vs rememberSaveable
// remember: composition lifetime only
var isExpanded by remember { mutableStateOf(false) }
// Survives: recomposition ✅
// Survives: configuration change (rotation) ❌ — resets to false
// Survives: process death ❌ — resets to false

// rememberSaveable: survives config changes + process death
var searchQuery by rememberSaveable { mutableStateOf("") }
// Survives: recomposition ✅
// Survives: configuration change (rotation) ✅ — saved to Bundle
// Survives: process death ✅ — saved to SavedStateHandle

// Custom saver for non-primitive types
val scrollState = rememberSaveable(saver = ScrollState.Saver) {
    ScrollState(0)
}

// mapSaver for data classes
val userSaver = mapSaver(
    save = { mapOf("id" to it.id, "name" to it.name) },
    restore = { User(it["id"] as String, it["name"] as String) }
)

3. State Hoisting & UDF

Stateful vs Stateless composables

// ❌ Stateful — hard to test, can't be reused with different state
@Composable
fun SearchBar() {
    var query by remember { mutableStateOf("") }
    TextField(value = query, onValueChange = { query = it })
}

// ✅ Stateless — testable, reusable, follows UDF
@Composable
fun SearchBar(
    query: String,                   // state flows DOWN
    onQueryChange: (String) -> Unit   // event flows UP
) {
    TextField(value = query, onValueChange = onQueryChange)
}

// Caller holds the state:
@Composable
fun SearchScreen(viewModel: SearchViewModel = hiltViewModel()) {
    val query by viewModel.query.collectAsStateWithLifecycle()
    SearchBar(
        query = query,
        onQueryChange = viewModel::onQueryChange
    )
}

collectAsStateWithLifecycle vs collectAsState

// collectAsState: collects even when app is in background
val state by viewModel.state.collectAsState()  // ❌ runs in background

// collectAsStateWithLifecycle: stops collection in background
// Uses repeatOnLifecycle(STARTED) semantics
val state by viewModel.state.collectAsStateWithLifecycle()  // ✅

4. derivedStateOf

derivedStateOf { } creates a State that is derived from other State values. It only recomputes when the dependencies change — and only triggers recomposition when the derived result changes.

// WITHOUT derivedStateOf — recomputes filter on every recompose
@Composable
fun ProductList(products: List<Product>, minPrice: Float) {
    // This filters on EVERY recomposition — expensive
    val filtered = products.filter { it.price >= minPrice }
    LazyColumn { items(filtered) { ProductCard(it) } }
}

// WITH derivedStateOf — only recomputes when products or minPrice changes
@Composable
fun ProductList(products: List<Product>, minPrice: Float) {
    // derivedStateOf: runs only when dependencies change
    val filtered by remember(products, minPrice) {
        derivedStateOf { products.filter { it.price >= minPrice } }
    }
    LazyColumn { items(filtered) { ProductCard(it) } }
}

// Classic use case: scroll position → show/hide FAB
val showFab by remember {
    derivedStateOf { scrollState.value > 100 }
}
// scrollState changes hundreds of times per scroll
// But showFab only changes when crossing the threshold
// → FAB composable only recomposes on threshold crossing
derivedStateOf vs remember(key)
Use derivedStateOf when the derivation is expensive and the source state changes frequently but the derived result changes rarely. Use remember(key) { compute(key) } when the computation should run exactly when key changes (simpler, less overhead for cheap operations).

5. Production Example

Banking: checkout form with state management

// ViewModel: single source of truth
class CheckoutViewModel : ViewModel() {
    private val _state = MutableStateFlow(CheckoutFormState())
    val state = _state.asStateFlow()

    fun onCardNumberChange(number: String) {
        _state.update { it.copy(cardNumber = number, cardError = validateCard(number)) }
    }
    fun onSubmit() { /* validate + submit */ }
}

// Screen composable: stateless, events go up
@Composable
fun CheckoutScreen(viewModel: CheckoutViewModel = hiltViewModel()) {
    val state by viewModel.state.collectAsStateWithLifecycle()  // ✅

    // derivedStateOf: submit enabled only when form is valid
    val isSubmitEnabled by remember(state) {
        derivedStateOf {
            state.cardError == null &&
            state.cardNumber.length == 16 &&
            state.expiryDate.isNotBlank()
        }
    }

    CheckoutForm(
        state = state,
        isSubmitEnabled = isSubmitEnabled,
        onCardNumberChange = viewModel::onCardNumberChange,
        onSubmit = viewModel::onSubmit
    )
}

// Form composable: fully stateless, testable in isolation
@Composable
fun CheckoutForm(
    state: CheckoutFormState,
    isSubmitEnabled: Boolean,
    onCardNumberChange: (String) -> Unit,
    onSubmit: () -> Unit
) {
    // Local UI state: only this composable needs it
    var showCvvHelp by remember { mutableStateOf(false) }

    Column {
        OutlinedTextField(
            value = state.cardNumber,
            onValueChange = onCardNumberChange,
            isError = state.cardError != null
        )
        Button(onClick = onSubmit, enabled = isSubmitEnabled) {
            Text("Pay")
        }
    }
}

6. Pitfalls & Best Practices
Pitfall 1 — Using remember for state that must survive rotation
Search query, scroll position, form input — these must survive rotation. remember loses them. Use rememberSaveable for small values or ViewModel + SavedStateHandle for complex data. A classic bug: user fills a form, rotates device, all fields reset.
Pitfall 2 — collectAsState instead of collectAsStateWithLifecycle
collectAsState() continues collecting when the app goes to background — processing updates the user can't see, potentially doing network calls or DB queries. Always use collectAsStateWithLifecycle() in production.
Pitfall 3 — Hoisting too high
Moving state to a parent/ancestor that doesn't need it creates unnecessary recompositions in the ancestor. Hoist state to the LOWEST common ancestor that needs it — not all the way to the ViewModel unless the state is business-critical.
Best Practice — derivedStateOf for expensive filtered lists
For any list filtering or sorting that runs during recomposition, wrap in derivedStateOf. Source state can change frequently (scroll, typing); the derived list should only recompute when actual filter parameters change.

7. Interview Framework

30-second answer

"In Compose, state flows down as parameters and events flow up as lambda callbacks — UDF. remember stores state in the slot table across recompositions. rememberSaveable persists through configuration changes. For screen-level business data, the ViewModel holds StateFlow and the UI collects it with collectAsStateWithLifecycle. derivedStateOf creates derived state that only recomputes when its dependencies change."

2-minute answer

"State hoisting is the core pattern — separate 'what state' from 'who owns it'. Stateless composables take state as parameters and report events via lambdas. They're testable, reusable, and previewable. Stateful composables own their own state with remember — but that state is local and ephemeral.

The rule: use remember for pure UI state (isExpanded, hasFocus) that doesn't need to survive navigation. Use rememberSaveable for state that must survive rotation (search query, scroll offset). Use ViewModel for business data that drives screens.

derivedStateOf is underused but important: in a banking transaction list, scroll position changes hundreds of times per scroll gesture. Without derivedStateOf, filtering the list on every scroll recompose is expensive. With derivedStateOf, Compose only recomputes the filtered list when the filter criteria actually changes."

Must-mention points

1
UDF: state down, events up — ViewModel is single source of truth
2

3
collectAsStateWithLifecycle — not collectAsState; stops in background
4
derivedStateOf — for expensive derived computations from rapidly-changing state
5
Hoist to lowest common ancestor — not always to ViewModel

Follow-up Q&A

Q: "How do you decide between remember and rememberSaveable?"

A: Ask: "Would it be confusing to the user if this resets on screen rotation?" If yes (search query, scroll position, form fields, selected tab) — use rememberSaveable. If no (tooltip visibility, animation state, hover state) — use remember. Also: rememberSaveable only works for Bundle-serializable types; for complex data, use ViewModel + SavedStateHandle.

Q: "What is the difference between derivedStateOf and remember(key)?"

A: remember(key) { compute() } recomputes when key changes and always triggers recomposition. derivedStateOf { compute() } also recomputes when dependencies change, but it ONLY triggers recomposition if the computed result is different. For the FAB show/hide example: scroll position changes 60 times/second but the boolean threshold crosses once — derivedStateOf prevents 59 unnecessary FAB recompositions.

Senior insight

Senior Insight
In an automotive app dashboard with live sensor readings updating 60fps, every piece of UI that derives a value from sensor state should use derivedStateOf. Speed gauge, warning lights, fuel level — each is derived from raw sensor data. Without derivedStateOf, a 60fps sensor update rate would cause 60fps recomposition of every derived composable. With derivedStateOf, each composable only recomposes when its threshold changes.

9. Interview Questions
What is the difference between remember and rememberSaveable?
Basic⌄
remember stores values in the composition's slot table — survives recomposition but is lost on configuration changes (rotation, language change) and process death. rememberSaveable additionally saves the value to the Bundle/SavedState system, surviving both configuration changes and process death. For primitive types it works automatically; for complex types you need a custom Saver.
What is state hoisting and why is it important?
Basic⌄
State hoisting is moving state from a composable to its caller, making the composable stateless. Instead of the composable owning state internally, it receives the current value as a parameter and reports changes via a lambda callback. Benefits: the composable becomes testable (control state in tests), reusable (caller decides initial state), previewable (pass any state in preview), and follows UDF (single source of truth).
What is Unidirectional Data Flow in Compose?
Basic⌄
State flows down the composable tree as parameters, events flow up as lambda callbacks. The ViewModel holds and owns the state (single source of truth). It exposes state as StateFlow. The UI consumes state via collectAsStateWithLifecycle() and sends events (user clicks) back to the ViewModel via callbacks. The ViewModel mutates state in response to events, triggering a new UI render.
What is derivedStateOf and when should you use it?
Intermediate⌄
derivedStateOf { } creates a State that is computed from other State values. It only recomputes when its dependencies change, and only triggers recomposition when the computed result is different. Use it when source state changes frequently but derived result changes rarely: scroll position (60fps) → show FAB (boolean, changes rarely); item list → filtered list (filtered count changes occasionally).
Why use collectAsStateWithLifecycle instead of collectAsState?
Intermediate⌄
collectAsState() keeps collecting the Flow even when the app is in the background (Activity paused/stopped). collectAsStateWithLifecycle() uses repeatOnLifecycle(STARTED) semantics — collection pauses when the app goes to background and resumes when it comes to foreground. This prevents unnecessary processing when the UI is invisible, saving battery and avoiding potential issues with background-only updates.
A form composable has 5 fields. Which state should use remember, rememberSaveable, and ViewModel?
Intermediate⌄
The field values (text, selections) that the user typed: rememberSaveable or ViewModel + SavedStateHandle — user would be frustrated if their input reset on rotation. UI-only state like "is this field focused" or "show password": remember — acceptable to reset on rotation. If the form involves business logic (validation, submission state, server errors): ViewModel StateFlow with collectAsStateWithLifecycle(). Rule: data the user entered → survives rotation; pure UI decoration → doesn't need to.
What is the difference between derivedStateOf and remember(key)?
Intermediate⌄
remember(key) { compute() }: re-runs compute() when key changes, always triggers recomposition. derivedStateOf { compute() }: re-runs when State dependencies read inside the lambda change. Crucially, it only triggers recomposition if the result changes — an additional optimization. Use derivedStateOf when the computation's input (State) changes more often than the output (e.g., filtering a 1000-item list when only 1 item changes but the filtered result doesn't change).
Design the state management for a banking transfer screen with: amount input, recipient selection, real-time validation, and submit-in-progress state.
Senior⌄
ViewModel owns all: data class TransferState(val amount: String = "", val amountError: String? = null, val recipient: Contact? = null, val isSubmitting: Boolean = false) as MutableStateFlow. ViewModel handles events: onAmountChange (validates), onRecipientSelect, onSubmit (sets isSubmitting). Submit button enabled via derivedStateOf { state.amountError == null && state.recipient != null && !state.isSubmitting }. Amount + recipient persist across rotation via SavedStateHandle in ViewModel. No rememberSaveable needed — ViewModel handles it. UI is fully stateless composable.
When should you hoist state to the ViewModel vs keep it in rememberSaveable?
Senior⌄
Use ViewModel when: (1) state is shared across multiple composables; (2) state requires business logic (validation, computation); (3) state needs to survive process death with unlimited size (SavedStateHandle for complex objects); (4) state comes from or must be synced to a data layer. Use rememberSaveable when: (1) state is purely local UI state in one composable; (2) it's a primitive or Bundle-serializable value; (3) no business logic needed; (4) examples: expanded/collapsed, scroll offset for a sub-list. rememberSaveable keeps components self-contained; ViewModel provides testability and data layer access.
A ScrollState-based parallax header is causing 60fps recompositions. How do you fix it using derivedStateOf?
Senior⌄
Instead of reading scrollState.value directly in composables that don't need continuous updates: val isHeaderCollapsed by remember { derivedStateOf { scrollState.value > COLLAPSE_THRESHOLD } } and val headerAlpha by remember { derivedStateOf { (1f - scrollState.value / FADE_RANGE).coerceIn(0f, 1f) } }. The scrollState changes 60fps but isHeaderCollapsed changes once (boolean threshold). The alpha changes continuously — for this, accept the 60fps recomposition on the alpha composable specifically, or use the Modifier.graphicsLayer approach which doesn't trigger recomposition at all.
