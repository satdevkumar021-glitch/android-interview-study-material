1A — Kotlin Basics & Null Safety

Core Kotlin syntax and the type-system mechanism that eliminates NullPointerExceptions at compile time.

ID: 1A ⭐ Tier 1 — Highest Priority
🔍
1. Overview

What it is

Kotlin's type system distinguishes nullable (T?) from non-null (T) types at compile time. Combined with val/var, type inference, and safe-access operators, it makes null handling explicit and eliminates entire classes of runtime crashes.

Why it exists

Java's null is untyped — any reference can be null, but the compiler never tells you. Kotlin makes nullability part of the type signature, enforced by the compiler. A String cannot be null; only a String? can.

Problems it solves

  • NullPointerException (NPE) — the "billion-dollar mistake"
  • Verbose, defensive Java null-checks scattered through every layer
  • Unclear API contracts ("does this function return null or not?")
Senior Mental Model
Nullability is a compile-time type distinction, not a runtime wrapper. String and String? are genuinely different types to the Kotlin compiler. This means violations are caught during development, not in production.
⚙
2. How It Works

val vs var

val userId: String = "u_123"   // immutable reference — prefer this
var retryCount: Int = 0        // mutable reference — use only when needed

val = assign once (like Java final). Does not mean the object itself is immutable.

Type Inference

val name = "Alice"          // inferred: String
val scores = listOf(1,2,3)  // inferred: List<Int>

Explicit types only needed for clarity or when inference fails.

Nullable vs Non-null

var email: String  = "a@b.com"  // non-null — compiler guarantees never null
var phone: String? = null        // nullable — must handle null explicitly

Safe Call ?.

val length = phone?.length  // returns null instead of throwing NPE

Short-circuits the entire chain if the receiver is null.

Elvis Operator ?:

val displayPhone = phone ?: "N/A"       // default if null
val len = phone?.length ?: 0            // safe call + default
phone ?: throw IllegalStateException("Phone required")  // throw on null

let with Null Handling

phone?.let { p ->
    // p is non-null String inside this block
    sendSms(p)
}

Executes the lambda only when the receiver is non-null. Cleaner than if (x != null) when you need a scoped non-null reference.

!! (Not-Null Assertion)

val len = phone!!.length  // throws KotlinNullPointerException if null
⚠ Avoid in Production
Every !! bypasses compile-time safety. It's a deliberate "crash if wrong" override. Use requireNotNull() with a message instead.

lateinit

@Inject lateinit var analytics: AnalyticsService

// later, after Hilt injection:
analytics.track("screen_view")

// safe check:
if (::analytics.isInitialized) analytics.track("event")
  • var only, reference types only (no Int, Boolean)
  • Throws UninitializedPropertyAccessException if accessed before init
  • Used for DI injection, Android lifecycle-bound properties

by lazy

val heavyConfig: Config by lazy {
    Config.load()   // called once, on first access, thread-safe by default
}
  • val only, computed once and cached
  • Default: LazyThreadSafetyMode.SYNCHRONIZED
  • Modes: SYNCHRONIZED, PUBLICATION, NONE

Null Safety Decision Flow

Access property on T? | receiver null? / \ YES NO | | returns null safe access or default returns value

3. Why and When to Use It

Real Android Use Cases

SituationTool
ViewModel injected by Hiltlateinit var
Expensive singleton (e.g., OkHttpClient)by lazy
Optional API field (e.g., middleName)String? + ?. / ?:
Fragment arguments from Bundle?.let { }
Chained nullable calls?. chain
Providing default for missing config?:
Assert non-null with context messagerequireNotNull()

When NOT to Use

Do NOT
  • Use !! in production — use early-return or requireNotNull()
  • Use lateinit for val — use by lazy
  • Use var when val works — harder to reason in Compose/Flow
  • Use lazy for values that may need re-initialization
  • Use sentinel values ("", -1) instead of T?

4. Production Example
Scenario
Banking app — user profile screen. Profile fields like middle name are optional from the backend; analytics service is Hilt-injected.

Domain Model

// domain/model/UserProfile.kt
data class UserProfile(
    val userId: String,           // always present
    val fullName: String,
    val middleName: String?,      // optional — backend may omit
    val accountNumber: String,
    val email: String?            // optional until verified
)

ProfileViewModel

// presentation/profile/ProfileViewModel.kt
@HiltViewModel
class ProfileViewModel @Inject constructor(
    private val getUserProfileUseCase: GetUserProfileUseCase
) : ViewModel() {

    // lateinit: Hilt injects after constructor; guaranteed non-null post-injection
    @Inject lateinit var analytics: AnalyticsService

    private val _uiState = MutableStateFlow<ProfileUiState>(ProfileUiState.Loading)
    val uiState: StateFlow<ProfileUiState> = _uiState.asStateFlow()

    // lazy: expensive formatter — created once, only if loadProfile is called
    private val currencyFormatter: NumberFormat by lazy {
        NumberFormat.getCurrencyInstance(Locale("en", "IN"))
    }

    fun loadProfile(userId: String) {
        viewModelScope.launch {
            val result = getUserProfileUseCase(userId)
            result.fold(
                onSuccess = { profile ->
                    // ?.let + ?: reads as: "include middle name if present, else use fullName"
                    val displayName = profile.middleName?.let { middle ->
                        "${profile.fullName} ($middle)"
                    } ?: profile.fullName

                    // Safe call chain — short-circuits at any null, Elvis provides fallback
                    val maskedEmail = profile.email
                        ?.takeIf { it.contains("@") }
                        ?.replace(Regex("(?<=.).(?=[^@]*@)"), "*")
                        ?: "Not provided"

                    _uiState.value = ProfileUiState.Success(
                        displayName = displayName,
                        maskedEmail = maskedEmail,
                        formattedBalance = currencyFormatter.format(0)
                    )
                },
                onFailure = {
                    _uiState.value = ProfileUiState.Error(it.message ?: "Unknown error")
                }
            )
        }
    }
}

Key Lines Explained

  • @Inject lateinit var analytics — Hilt injects after construction; non-null guaranteed post-injection. No ? needed.
  • by lazy { ... } — NumberFormat creation is deferred; cost paid only on first loadProfile call.
  • ?.let { } ?: fullName — idiomatic: "if middle name exists, format it; otherwise default to full name."
  • ?.takeIf { }?.replace(...) ?: "Not provided" — chain short-circuits to null at any null point.
  • No !! anywhere — compiler-enforced contract holds throughout all layers.

5. Alternatives & Trade-offs
ApproachProsConsWhen to pick
Kotlin nullable T? + operators Compile-time safety, idiomatic, concise Requires nullable discipline across all layers Always — default choice
!! (force-unwrap) One less null-check Runtime crash if null; bypasses safety entirely Never in prod; tests only when you own the invariant
lateinit var Clean DI / lifecycle init, non-null contract Crash if accessed before init; reference types only Non-null var that can't be init'd at declaration
by lazy Thread-safe, one-time init, val Can't re-init; slight overhead on first access Expensive val deferred to first use
Optional<T> (Java) Familiar to Java devs Verbose, heap allocation per wrap, not idiomatic Kotlin Never — use T?
Sentinel value ("", -1) No nullability plumbing Implicit contract, error-prone, misleading Never — use T?

Common Interviewer Comparisons

Expect These
  • lateinit vs by lazy — mutable/deferred init vs immutable/computed-once
  • ?. vs !! — safe short-circuit vs force-crash; always prefer safe
  • val vs var — immutability preference in reactive/functional code
  • Kotlin nullability vs Java Optional — type-system vs wrapper object

6. Pitfalls & Best Practices

!! in Production

// ❌ BAD — crashes if userData is null
val name = userData!!.name
// ✅ GOOD — explicit contract with early exit
val name = userData?.name ?: return
// or: assert with a meaningful message
val name = requireNotNull(userData) { "userData must not be null here" }.name

lateinit for Primitives

// ❌ BAD — won't compile: lateinit not allowed on Int
lateinit var count: Int
// ✅ GOOD
var count: Int = 0

Ignoring isInitialized

// ❌ BAD — throws UninitializedPropertyAccessException
fun track() = analytics.track("event")  // may not be initialized yet
// ✅ GOOD
fun track() {
    if (::analytics.isInitialized) analytics.track("event")
}

Mutable State in Compose / Flow

// ❌ BAD — var breaks unidirectional data flow
var userName: String = ""
// ✅ GOOD — val + StateFlow
val userName: StateFlow<String> = _userName.asStateFlow()

lazy on a Value That Changes

// ❌ BAD — lazy caches the first value; token updates not reflected
val token: String by lazy { prefs.getToken() }
// ✅ GOOD — use a function or StateFlow for mutable values
fun getToken(): String = prefs.getToken()

Threading / Lifecycle Traps

  • lateinit is not thread-safe — avoid concurrent access without synchronization.
  • by lazy default (SYNCHRONIZED) uses a lock — correct. Choose NONE only in verified single-threaded contexts.
  • Smart casts fail inside lambdas on var fields — capture to a local val first.

Production Best Practices

  1. Prefer val over var everywhere possible.
  2. Prefer T? with ?. / ?: over !!.
  3. Use requireNotNull() / checkNotNull() to document invariants with a message.
  4. Model optional API fields as T? in domain model — never use sentinel values.
  5. Use by lazy for expensive one-time inits (parsers, formatters, heavy config).
  6. Use lateinit only for DI / lifecycle-bound non-null properties; check isInitialized if any doubt.

7. Interview Answer Framework

30-Second Answer

"Kotlin's null safety makes nullability part of the type system. A plain String can never be null — only String? can. The compiler forces you to handle the null case via safe calls ?., the Elvis operator ?:, or smart casts. This eliminates NPEs at compile time rather than at runtime. For deferred init, lateinit handles DI/lifecycle-bound vars, and by lazy handles expensive val computations that should run once."

2-Minute Structured Answer

"The core idea is that nullability is a compile-time type distinction, not a runtime surprise. String and String? are different types. The compiler refuses to let you call methods on a String? without handling the null case first.

In practice, I use ?. for safe chaining — the whole chain short-circuits to null if any receiver is null. ?: provides a default or triggers an early return. let executes a block only when the receiver is non-null, which is cleaner than an if (x != null) block when you need a scoped non-null reference.

!! exists but I treat it as a code smell. Every !! means 'I'm overriding the compiler — crash if I'm wrong.' In production I replace it with requireNotNull() with a message, or restructure so null is impossible at the call site.

For property initialization: lateinit var is for Hilt-injected or lifecycle-driven non-null properties that can't be set in the constructor. by lazy is for expensive val computations deferred to first access — thread-safe by default. They're complementary — lazy requires val, lateinit requires var."

Senior-Level Insight (Stand Out)

Say This
"In a multi-module Clean Architecture, nullable types in your domain model act as a formal API contract between modules. If UserProfile.email is String?, every consumer — presentation, domain, data — must handle the missing case explicitly. This is far more robust than a convention or a sentinel value. I enforce a rule: domain models never use !!, and any conversion from data-layer DTO to domain model must resolve nullability explicitly in the mapper — never with a force-unwrap."

9. Interview Questions (Self-Check)
How to use
Try to answer each question before revealing the answer. Click the arrow to reveal.

Basic

B1 — What is the difference between val and var in Kotlin?
Easy▼
val is an immutable reference — assigned once, cannot be reassigned (like Java final). var is mutable — can be reassigned at any time. Neither controls whether the object itself is mutable — a val list can still have items added if it's a MutableList.
B2 — What is the difference between String and String?? How does the compiler enforce it?
Easy▼
String is a non-null type; the compiler guarantees it will never hold null. String? is nullable; the compiler forces you to handle the null case (via ?., ?:, or a null check) before calling any method on it. Assigning null to a String is a compile error.
B3 — What does the Elvis operator ?: do? Give an example.
Easy▼
Returns the left-hand expression if non-null, otherwise evaluates and returns the right-hand expression. Example: val name = user?.name ?: "Guest" — if user is null or user.name is null, name becomes "Guest". The right side can also be a return or throw.

Intermediate

I1 — When would you use lateinit var vs by lazy? What happens if you access lateinit before init?
Medium▼
lateinit var: for non-null var properties that can't be initialized at declaration time (DI injection, lifecycle callbacks). Reference types only. Throws UninitializedPropertyAccessException if accessed before init — check with ::prop.isInitialized.

by lazy: for non-null val properties with an expensive computation that should run once and be cached. Thread-safe by default. Cannot be re-initialized.

They're complementary: lazy requires val, lateinit requires var.
I2 — Why avoid !! in production? What are the better alternatives?
Medium▼
!! bypasses compile-time null safety — if the value is null at runtime, it throws KotlinNullPointerException, defeating the purpose of the type system. Better alternatives:
• requireNotNull(x) { "descriptive message" }
• x ?: return (early exit)
• x ?: throw IllegalStateException("...")
• Restructure so null is impossible at the call site
I3 — Explain smart casts. When does a smart cast fail?
Medium▼
Smart cast is when the compiler automatically promotes a nullable type to non-null after a null check (or is type check), so you don't need explicit casting.

Smart cast fails when the compiler can't guarantee the value hasn't changed between the check and the use:
1. var properties — another thread could reassign them
2. Mutable class members — a custom getter could return a different value each time

Fix: capture to a local val before using.
I4 — Rewrite without any !!: fun getDisplayName(user: User?): String { return user!!.profile!!.displayName!! }
MediumCoding▼
// Option 1: concise safe-call chain
fun getDisplayName(user: User?): String =
    user?.profile?.displayName ?: "Unknown"

// Option 2: early-return pattern (more explicit)
fun getDisplayName(user: User?): String {
    val profile = user?.profile ?: return "Unknown"
    return profile.displayName ?: "Unknown"
}

Senior / Scenario

S1 — What's wrong with this ViewModel code? How do you fix it?
var userSession: UserSession? = null; viewModelScope.launch { userSession = repo.getSession(); dashboard.load(userSession!!.token) }
HardScenario▼
Problems:
1. userSession is a var — the compiler cannot smart-cast it because another coroutine could reassign it between assignment and userSession!!.token
2. !! crashes if getSession() returns null

Fix: capture to a local val — the compiler can smart-cast a local val: 
fun loadDashboard() {
    viewModelScope.launch {
        val session = repository.getSession() ?: run {
            _uiState.value = UiState.Error("No session")
            return@launch
        }
        dashboard.load(session.token)  // session is non-null here
    }
}
S2 — A junior dev maps email: String? in the DTO to domain with userProfile.email = dto.email!!. What's wrong? How do you enforce the right pattern?
Hard▼
Problem: The !! asserts the email is never null from the DTO — a contract violation. The DTO declares it nullable for a reason: the backend may omit it. This will crash in production when the backend returns a user without an email.

Fix: The mapper must be honest about nullability: 
fun UserDto.toDomain() = UserProfile(
    email = email  // String? maps to String? — honest contract
)
If the domain requires a non-null email, that validation belongs in the UseCase as business logic, not in the mapper.
S3 — by lazy is used to init an OkHttpClient in a Repository. App crashes in prod with ConcurrentModificationException inside the initializer. Why? How do you fix it?
HardScenario▼
Why: by lazy default mode is SYNCHRONIZED — it uses a lock to ensure single initialization. The ConcurrentModificationException is not caused by two threads entering the initializer simultaneously (the lock prevents that). More likely: the initializer lambda itself modifies a collection (e.g., adding interceptors) that is concurrently iterated, or OkHttpClient builder internal state is being mutated by another thread.

If the developer changed the mode to LazyThreadSafetyMode.NONE for performance, then yes — two threads could enter the initializer simultaneously, causing the exception.

Fix: Revert to SYNCHRONIZED (default) and ensure the initializer lambda is free of concurrent collection mutation. Use Hilt to scope OkHttpClient as a @Singleton instead of using lazy manually.
