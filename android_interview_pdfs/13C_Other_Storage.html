Senior Mental Model
The storage hierarchy in Android: Keystore (keys in hardware) → EncryptedSharedPreferences (Keystore-backed, for sensitive prefs like tokens) → DataStore (coroutine-safe, atomic) → Files (blobs, media) → Room (structured relational). SharedPreferences is legacy — avoid in new code. DataStore is the modern replacement.

2. How It Works

1. SharedPreferences (Legacy)

XML-based key-value storage. Simple but has serious problems: not type-safe, not thread-safe, blocking I/O on the main thread, no error propagation, and no observability without workarounds.

// DO NOT USE in new code — legacy only
val prefs = context.getSharedPreferences("settings", Context.MODE_PRIVATE)
prefs.edit().putBoolean("dark_mode", true).apply()  // apply() = async write (not guaranteed)
prefs.edit().putBoolean("dark_mode", true).commit() // commit() = sync write (blocks!)
val isDark = prefs.getBoolean("dark_mode", false)    // no type safety on key name

2. Preferences DataStore

DataStore is the modern replacement for SharedPreferences. Uses Kotlin coroutines and Flow; atomic writes; handles exceptions gracefully; no main thread I/O.

// Define keys
val DARK_MODE_KEY = booleanPreferencesKey("dark_mode")
val USER_ID_KEY   = stringPreferencesKey("user_id")
val FONT_SIZE_KEY = intPreferencesKey("font_size")

// Create DataStore (one per file name)
val dataStore: DataStore<Preferences> by preferencesDataStore(name = "settings")
// Inject via Hilt as @Singleton

// READ — returns a Flow; null if key not set
val darkModeFlow: Flow<Boolean> = context.dataStore.data
    .map { prefs -> prefs[DARK_MODE_KEY] ?: false }
    .catch { e -> if (e is IOException) emit(false) else throw e }

// WRITE — atomic; only via edit lambda
suspend fun setDarkMode(enabled: Boolean) {
    context.dataStore.edit { prefs ->
        prefs[DARK_MODE_KEY] = enabled
    }
}

3. Proto DataStore

Type-safe, schema-driven DataStore using Protocol Buffers. Define the schema in a .proto file; Protocol Buffers generates Kotlin classes.

// settings.proto
// syntax = "proto3";
// message UserSettings {
//   bool dark_mode = 1;
//   string locale = 2;
//   int32 font_size = 3;
// }

// Serializer for Proto DataStore
object UserSettingsSerializer : Serializer<UserSettings> {
    override val defaultValue: UserSettings = UserSettings.getDefaultInstance()
    override suspend fun readFrom(input: InputStream): UserSettings =
        UserSettings.parseFrom(input)
    override suspend fun writeTo(t: UserSettings, output: OutputStream) =
        t.writeTo(output)
}

val protoDataStore: DataStore<UserSettings> by dataStore(
    fileName = "user_settings.pb",
    serializer = UserSettingsSerializer
)

// READ — type-safe access to settings fields
val darkMode: Flow<Boolean> = protoDataStore.data.map { it.darkMode }

// WRITE — copy with modified field (immutable proto)
suspend fun setDarkMode(enabled: Boolean) {
    protoDataStore.updateData { current ->
        current.toBuilder().setDarkMode(enabled).build()
    }
}

4. Android Keystore

The Keystore system generates and stores cryptographic keys in a hardware-backed secure element (TEE/StrongBox). Private keys never leave the hardware — they're used in-place for operations.

// Generate an AES key stored in Keystore
val keyGenerator = KeyGenerator.getInstance(KeyProperties.KEY_ALGORITHM_AES, "AndroidKeyStore")
keyGenerator.init(
    KeyGenParameterSpec.Builder("myKeyAlias", KeyProperties.PURPOSE_ENCRYPT or KeyProperties.PURPOSE_DECRYPT)
        .setBlockModes(KeyProperties.BLOCK_MODE_GCM)
        .setEncryptionPaddings(KeyProperties.ENCRYPTION_PADDING_NONE)
        .setKeySize(256)
        .setUserAuthenticationRequired(false)  // true = requires biometric unlock
        .build()
)
keyGenerator.generateKey()  // key is stored in Keystore, never in app memory

// Use the key for encryption — key stays in hardware
val keyStore = KeyStore.getInstance("AndroidKeyStore").apply { load(null) }
val key = keyStore.getKey("myKeyAlias", null) as SecretKey
val cipher = Cipher.getInstance("AES/GCM/NoPadding")
cipher.init(Cipher.ENCRYPT_MODE, key)
val encrypted = cipher.doFinal(plaintext)

5. EncryptedSharedPreferences

Uses Android Keystore to encrypt both keys and values in a SharedPreferences file. The encryption/decryption key is stored in hardware, never in app memory. This is the recommended way to store sensitive small data like tokens.

// EncryptedSharedPreferences — backed by Keystore, API-compatible with SharedPreferences
val encryptedPrefs = EncryptedSharedPreferences.create(
    context,
    "secure_prefs",                  // file name
    MasterKeys.getOrCreate(MasterKeys.AES256_GCM_SPEC),  // master key in Keystore
    EncryptedSharedPreferences.PrefKeyEncryptionScheme.AES256_SIV,
    EncryptedSharedPreferences.PrefValueEncryptionScheme.AES256_GCM
)

// Use exactly like SharedPreferences — but encrypted at rest
encryptedPrefs.edit().putString("access_token", token).apply()
val token = encryptedPrefs.getString("access_token", null)

6. Files — Internal vs External

// Internal storage — private to your app, deleted on uninstall
val internalFile = File(context.filesDir, "report.pdf")
val cacheFile = File(context.cacheDir, "temp_image.jpg")  // system may delete if low space

// External storage — shared with other apps (requires WRITE_EXTERNAL_STORAGE or Scoped Storage)
// API 29+: Scoped Storage — use MediaStore API for media, FileProvider for sharing

// FileProvider — share a file with another app without exposing internal path
// In FileProvider.xml:
// <files-path name="reports" path="reports/" />
val fileUri: Uri = FileProvider.getUriForFile(
    context,
    "${context.packageName}.fileprovider",
    File(context.filesDir, "reports/statement.pdf")
)
// Share via Intent — only the receiving app gets temporary read permission

3. When to Use
ScenarioStorage choiceReason
Auth tokens (access + refresh)EncryptedSharedPreferencesEncrypted at rest with hardware key; simple API
App settings (theme, locale, font size)Preferences DataStoreCoroutine-safe, atomic, Flow reactive
Typed settings with schemaProto DataStoreType-safe, schema versioning, efficient binary format
User-generated files (exports, reports)Internal files + FileProviderPrivate by default; FileProvider for controlled sharing
Biometric key pair generationAndroid Keystore (asymmetric)Private key never leaves hardware
Legacy integrationSharedPreferencesOnly if existing code can't be migrated
Never Store Tokens in Plain SharedPreferences
Plain SharedPreferences stores data as plain XML in /data/data/com.app/shared_prefs/. On rooted devices, this is readable by any app. Always use EncryptedSharedPreferences (backed by hardware Keystore) for tokens, user credentials, or any sensitive small data.

4. Production Example

Banking App — Token Store with EncryptedSharedPreferences + DataStore

// ── Encrypted Token Store ─────────────────────────────────────
class SecureTokenStore @Inject constructor(
    @ApplicationContext private val context: Context
) : TokenStore {

    private val prefs: SharedPreferences by lazy {
        EncryptedSharedPreferences.create(
            context, "auth_tokens",
            MasterKeys.getOrCreate(MasterKeys.AES256_GCM_SPEC),
            EncryptedSharedPreferences.PrefKeyEncryptionScheme.AES256_SIV,
            EncryptedSharedPreferences.PrefValueEncryptionScheme.AES256_GCM
        )
    }

    override fun getAccessToken(): String? = prefs.getString("access_token", null)
    override fun getRefreshToken(): String? = prefs.getString("refresh_token", null)

    override fun saveTokens(accessToken: String, refreshToken: String) {
        prefs.edit()
            .putString("access_token", accessToken)
            .putString("refresh_token", refreshToken)
            .apply()
    }

    override fun clearTokens() = prefs.edit().clear().apply()
}

// ── DataStore for User Preferences ────────────────────────────
val Context.settingsDataStore: DataStore<Preferences> by preferencesDataStore("settings")

class UserSettingsDataSource @Inject constructor(
    @ApplicationContext private val context: Context
) {
    private companion object {
        val DARK_MODE     = booleanPreferencesKey("dark_mode")
        val NOTIFICATIONS = booleanPreferencesKey("notifications_enabled")
        val CURRENCY      = stringPreferencesKey("preferred_currency")
    }

    val settings: Flow<AppSettings> = context.settingsDataStore.data
        .catch { if (it is IOException) emit(emptyPreferences()) else throw it }
        .map { prefs ->
            AppSettings(
                darkMode = prefs[DARK_MODE] ?: false,
                notificationsEnabled = prefs[NOTIFICATIONS] ?: true,
                currency = prefs[CURRENCY] ?: "GBP"
            )
        }

    suspend fun setDarkMode(enabled: Boolean) {
        context.settingsDataStore.edit { it[DARK_MODE] = enabled }
    }
}

6. Pitfalls & Best Practices

DataStore Pitfalls

Multiple DataStore Instances for the Same File
Creating two DataStore instances pointing to the same file causes IllegalStateException: There are multiple DataStore files with the same name. Use the by preferencesDataStore() property delegate (on Context) which is a Kotlin singleton — only one instance is created per file name. Inject as @Singleton via Hilt.
No Migration from SharedPreferences to DataStore
DataStore doesn't automatically read existing SharedPreferences files. If migrating, use SharedPreferencesMigration to copy values: preferencesDataStore(name, produceMigrations = { SharedPreferencesMigration(it, "old_prefs_name") }). Without this, users lose their settings on first launch after update.

Keystore Pitfalls

Keystore Keys Lost on Factory Reset
Android Keystore keys are bound to the device. Factory reset wipes all Keystore keys. Any data encrypted with a Keystore key (including EncryptedSharedPreferences) becomes unreadable. Always have a recovery path: on KeyPermanentlyInvalidatedException, clear the encrypted data and ask the user to log in again.

File Provider Pitfalls

  • Never share a file URI from internal storage directly — use FileProvider. Direct file URIs fail with FileUriExposedException on API 24+
  • Grant read permission to the receiving app via Intent.FLAG_GRANT_READ_URI_PERMISSION
  • FileProvider paths must be declared in res/xml/file_paths.xml

Best Practices

  • Store tokens in EncryptedSharedPreferences — never plain SharedPreferences or Room
  • Use DataStore (not SharedPreferences) for new code
  • Handle IOException in DataStore flows — file corruption is possible
  • Set expiry on Keystore keys linked to biometrics to prevent key use after biometric enrollment change

7. Interview Framework

30-Second Answer

"For small key-value data: DataStore is the modern replacement for SharedPreferences — it's coroutine-safe, atomic, and never blocks the main thread. Two flavours: Preferences DataStore (typed key-value) and Proto DataStore (full schema with protocol buffers). For sensitive data like auth tokens: EncryptedSharedPreferences wraps SharedPreferences with Keystore-backed encryption — keys and values are encrypted using a hardware key that never leaves the device. For arbitrary files: internal storage for app-private data, FileProvider to share files with other apps. Android Keystore generates and stores cryptographic keys in hardware — used for biometric auth and encryption operations."

2-Minute Deep Dive

"The SharedPreferences problems that DataStore solves: commit() blocks the main thread; apply() is async but reads can block; it's not thread-safe (concurrent writes can corrupt the file); no error propagation. DataStore uses coroutines and Flow, writes are atomic, and IOExceptions are propagated through the Flow where you can handle them. For EncryptedSharedPreferences: it uses Android Keystore's AES-256 hardware-backed key to encrypt both the key names and values before writing to the XML file. On rooted devices, the XML is still just encrypted bytes — useless without the hardware key. The important gotcha: Keystore keys are lost on factory reset — any data encrypted with them becomes inaccessible. Always catch KeyPermanentlyInvalidatedException and handle it by clearing the encrypted data and re-authenticating."

Follow-up Q&A

QuestionAnswer
"Why is SharedPreferences not thread-safe?"Multiple threads can call edit() and apply() simultaneously, leading to partial writes or lost updates if they operate on different editor instances without coordination. DataStore uses Kotlin's serialised coroutine execution to ensure writes are always sequential.
"Can DataStore replace Room?"No. DataStore is for simple key-value or small structured settings. Room is for relational data with querying, filtering, sorting, and complex relationships. DataStore has no query language.
"What is StrongBox?"StrongBox is a dedicated tamper-resistant hardware security module (separate chip from the main CPU) for Keystore keys. More secure than TEE (which shares the main CPU's secure world). Available on Pixel 3+ and some other devices. Requested via setIsStrongBoxBacked(true) in KeyGenParameterSpec.

Senior Insight

Senior Signal
The most important security insight: "encrypted at rest" doesn't mean the data is safe against all attackers — it's about the threat model. EncryptedSharedPreferences protects against: an attacker with physical access to a backed-up device image, or a rooted device that can read files. It does NOT protect against: malware running with the same UID (same process isolation boundary), or a device that has already been unlocked by the user (the Keystore key is accessible). For genuine secrets, you need to combine EncryptedSharedPreferences with user-authentication-required Keystore keys (setUserAuthenticationRequired(true)) so the key is only accessible after biometric verification.

9. Interview Questions
Basic What are the main problems with SharedPreferences that DataStore solves? ⌄
1. Main thread blocking: commit() blocks the main thread for disk I/O. DataStore never blocks the main thread — it's fully coroutine-based.
2. Thread safety: SharedPreferences isn't thread-safe — concurrent edit() calls can corrupt the file. DataStore uses Kotlin's serialised execution for writes.
3. No error propagation: SharedPreferences silently ignores I/O errors. DataStore propagates IOException through the Flow.
4. Not atomic: a crash during a SharedPreferences write can leave a partially written file. DataStore writes are atomic.
5. No observability: SharedPreferences requires a change listener that must be managed manually. DataStore returns a Flow.
Basic What is the difference between Preferences DataStore and Proto DataStore? ⌄
Preferences DataStore: stores typed key-value pairs — booleanPreferencesKey("dark_mode"), stringPreferencesKey("locale"). No schema enforcement. Easy to add new keys. Key names are the schema — if you rename a key, you lose the old value. Works without any additional dependencies.

Proto DataStore: stores a single typed Kotlin object generated from a .proto schema file using Protocol Buffers. Fully type-safe — accessing settings.darkMode is a property, not a string key lookup. Schema evolution follows Protobuf rules (field numbers, backward compatibility). Requires the Protobuf Gradle plugin. Better for complex settings with many fields or when you need schema versioning.
Basic What is EncryptedSharedPreferences and how does it work? ⌄
EncryptedSharedPreferences is a drop-in replacement for SharedPreferences that encrypts both key names and values using Android Keystore-backed keys. It uses AES-256-SIV to encrypt key names (deterministic, allows look-up) and AES-256-GCM to encrypt values. The master key is generated and stored in Android Keystore — it never leaves the hardware. The resulting XML file contains encrypted bytes that cannot be read even on a rooted device without the hardware key. Suitable for storing access tokens, refresh tokens, and other secrets that must survive process death but shouldn't be readable from disk.
Intermediate How does Android Keystore protect cryptographic keys? ⌄
Android Keystore stores keys in a Trusted Execution Environment (TEE) or a dedicated StrongBox chip — hardware isolated from the main application processor. Cryptographic operations (encrypt, decrypt, sign) happen inside this hardware using the key; the raw key material is never exposed to the application. Even with root access to the device, you cannot extract the key. The only way to use the key is via the Keystore API on the same device. For biometric-protected keys (setUserAuthenticationRequired(true)), the key is additionally locked until biometric authentication succeeds.
Intermediate What happens to EncryptedSharedPreferences data after a factory reset? ⌄
A factory reset wipes all Keystore keys along with all user data. The master key used to encrypt the EncryptedSharedPreferences file is permanently destroyed. The encrypted file (if somehow preserved) becomes unreadable forever — without the key, the data is irretrievably encrypted.

For the app: on next launch after factory reset, accessing EncryptedSharedPreferences may throw KeyPermanentlyInvalidatedException or GeneralSecurityException. Handle this by: catching the exception, deleting the old encrypted prefs file, and creating a fresh one. The user will need to log in again to re-populate the tokens.
Intermediate Why can't you share an internal file directly using a file:// URI? ⌄
Since Android 7 (API 24), sharing file:// URIs outside the app's process throws FileUriExposedException. The reason: a file URI gives the receiving app direct path access to your app's internal storage — bypassing Android's permission model. The receiving app would need to have permission to read that path, which ordinary apps don't have.

The solution is FileProvider: it converts an internal file path to a content:// URI that Android routes through a ContentProvider. The receiving app is granted temporary read permission only for that specific URI. No direct file system access is needed.
Intermediate How do you migrate existing SharedPreferences data to DataStore? ⌄
Use SharedPreferencesMigration:

val dataStore by preferencesDataStore(name = "settings", produceMigrations = { context -> listOf(SharedPreferencesMigration(context, "old_prefs_name")) })

On first access to the DataStore, it reads all keys from the named SharedPreferences file and copies them to DataStore. You can filter which keys to migrate. After migration, DataStore deletes the old SharedPreferences file. Without this migration, users lose their settings on first launch after the update.
Senior Design a token storage system for a banking app that survives app updates, handles biometric authentication, and gracefully handles Keystore invalidation. ⌄
Token storage: EncryptedSharedPreferences backed by a Keystore AES-256-GCM master key. Access and refresh tokens stored here. Survives app updates (Keystore keys are per-device, not per-app-version).

Biometric protection: For accessing the token, generate a separate Keystore key with setUserAuthenticationRequired(true) and setUserAuthenticationValidityDurationSeconds(30). Biometric prompt must succeed before this key is usable. This prevents token access without the user's consent — even if someone has physical device access.

Invalidation handling: Wrap all EncryptedSharedPreferences operations in try-catch for KeyPermanentlyInvalidatedException (biometric enrollment changed) and GeneralSecurityException (factory reset, or key deleted). On exception: (1) delete the encrypted prefs file, (2) emit an "authentication required" event via a StateFlow, (3) navigate to login. The repository layer handles this transparently so ViewModels never see low-level crypto exceptions.
Senior When would you use Proto DataStore over Preferences DataStore and how do you handle schema migrations? ⌄
Choose Proto DataStore when: (1) you have 10+ settings fields and type-safe access matters, (2) the settings have complex structure (nested objects, lists), (3) the project uses KMM (protobuf is multiplatform), or (4) you need strict schema versioning for regulatory compliance (e.g., audit logs).

Schema migrations: Protobuf handles backward compatibility at the format level — adding a new field is safe (older versions read default values). Removing a field requires reserving the field number (reserved 3;) to prevent reuse. For DataStore itself, if you rename the .pb file or change the Serializer, existing data is lost unless you: (1) read the old file as raw bytes, (2) deserialise with the old schema class, (3) write to the new file with the new serialiser. This is manual — no equivalent of Room's addMigrations(). If schema evolution is frequent, consider Preferences DataStore with explicit versioning keys.
Senior A developer reports that DataStore is throwing "There are multiple DataStore files with the same name" in tests. What's the cause and fix? ⌄
The error occurs when two DataStore instances are created pointing to the same file in the same process. Most commonly: (1) the by preferencesDataStore() delegate is defined inside a class (creating one per instance) rather than at the top level as an extension on Context; or (2) in tests, the DataStore from production code and the DataStore from a test module both try to use the same file name.

Production fix: define the DataStore as a top-level property: val Context.settingsDataStore by preferencesDataStore("settings"). Kotlin's property delegation ensures only one instance is created per Context.

Test fix: use TestCoroutineRule + a temporary file per test: PreferenceDataStoreFactory.create(scope = testScope) { context.preferencesDataStoreFile("test_settings") }. Clean up the file in @After. This gives each test an isolated DataStore without file name conflicts.
